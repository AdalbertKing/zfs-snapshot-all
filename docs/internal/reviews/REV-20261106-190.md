# REV-20261106-190 — replica family value becomes shell syntax in cron

Reviewer: ChatGPT. Date: 2026-11-06.

Target: development `main` at `d89e4cc4b8db36179aaf1be1161bcd92eac265c7`
(PR #1107, A22). Release `AdalbertKing/zfsbackup` main is still

cron or pool was changed by this review.

## F1 — `--exclude-family` accepts shell operators that gen-cron emits unquoted

- Severity: **P2**.
- Blocking: **yes for claiming the new replica family exclusion is safe to
  install**; the older trusted `flags` config has the same rendering boundary
  and should be checked in the fix.
- Affected: `zfs-backup.sh` `cmd_add_replica`, `replica_section_upsert`;
  `gen-cron.sh` `build_replica_section` / `replica_engine_cmd` and cron rendering.

### Contract and evidence

A22 adds `add-replica --exclude-family=A,B`. Each entry is appended to the
replica's `flags` as `-E <entry>`. The CLI rejects leading `-`, whitespace and
quotes but accepts `;`, `>`, `&`, `|`, `$`, backticks and other shell operators.
The generator interpolates the resulting flags into the cron command without
quoting each argument; `lint_flags` checks selected option letters, not shell
syntax. A family of snapshots cannot contain these operators, so accepting
them has no legitimate family-name meaning.

I rendered a throwaway `[replica:pe]` config with `passive = yes` and
`flags = -E foo;touch>/tmp/review-a22-proof` using the shipped `gen-cron.sh -c`.
It succeeded and emitted the literal command segment
`snapget.sh -e -M -E foo;touch>/tmp/review-a22-proof "tank/a" "usb/rep"`.
The command was **not executed**; the temporary config was removed. The same
value passes the new `cmd_add_replica` validation shown in the submitted diff
and is stored in `flags`. Under cron's shell, the semicolon starts a separate
command and the redirection can create a file. Depending on the operator,
this can alter or interrupt the backup job and run unintended commands in the
cron account. The A22 tests exercise ordinary family names and a leading
`-`, but not a shell operator or the complete CLI-to-cron boundary.

### Required outcome

Treat each family as data from CLI or config through the generator. Reject
values outside the documented ZFS snapshot-family grammar, or render them as
unambiguous literal shell arguments while still refusing names ZFS cannot
have. A malformed value must fail before a cron entry is installed. Preserve
the GUI's three ordinary exclusions and existing valid `-E` behavior.

### Acceptance criteria and verification

- [ ] Close the `--exclude-family` CLI path, the replica section's `flags`
  path and the generated cron command as one contract. Check repeated and
  comma-separated entries, empty entries and shell metacharacters. Explain
  how hand-edited configs are handled.
- [ ] Add a negative control against `d89e4cc4` that demonstrates the unsafe
  emitted command, then tests asserting invalid entries are refused and valid
  families render as literal `-E` arguments. Exercise CLI plan and install
  candidate, direct config, and the GUI create/edit default. Do not run a
  deliberately injected cron command.
- [ ] Run relevant replica, cron and GUI suites, shell syntax,
  `git diff --check`, `./test/impact.sh --verify` and exact-head CI. State any
  manual obligation. No production-host test is authorized here.

### Scope and uncertainty

This review proves an unsafe emitted cron line, not execution on a host. The
existing generic `flags` field already allows hand-authored shell text; A22
newly exposes the same boundary through an ordinary `add-replica` argument.
The fix may keep trusted raw flags as an explicit administrative escape hatch,
but the new family argument must have a defined safe grammar and a test of
the resulting cron line. Review future CLI-to-cron additions with an operator
character, not only a leading dash, as the negative input.
