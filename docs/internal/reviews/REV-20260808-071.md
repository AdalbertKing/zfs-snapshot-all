# REV-20260808-071 — Stage 4 reconciliation is not yet trustworthy on the fleet

**Review time:** 2026-08-08 12:22:13 CEST

**Verdict:** **CHANGES REQUIRED**

The report-only boundary is correct, and the local suite meaningfully tests comparison logic. It demonstrates, however, that the current output cannot yet be treated as a reliable scope audit.

## F1 — receive targets are reported as unprotected source datasets

- Severity: **P1**
- Blocking: **yes, for Stage 4 acceptance**
- Affected: `gen-cron.sh::do_reconcile`, `test/reconcile/run.sh`, live topology interpretation

On collector hosts, received backup trees such as:

```text
hdd/backups/pve2/rpool/data/vm-106-disk-0
hdd/backups/pve2/hdd/vm-disks/subvol-103-disk-0
```

are emitted as “exists, and no send job backs it up”. Those datasets are destinations of backup jobs, not uncovered workloads. Guest-name attribution makes the false finding look more authoritative: a received copy of guest 103 is labelled `pct/103` as though the live guest were unprotected.

The cause is visible in the code: `covered` contains source-side dataset sections only; no destination/receive topology is modelled.

**Required:** derive received roots from the actual CONFIG v4 transfer topology and classify their exact subtrees separately from source-side coverage. Prove both push and pull direction semantics. Do not quiet-classify a path merely because its name contains `backup`, `test`, or a guest volume name, and do not assume that one host's local outgoing config necessarily describes every inbound push; the derivation must match the configuration facts actually available.

**Decisive regression:** a dataset beneath a proven receive root is shown as a received backup and never as `UNCOVERED`; an adjacent similarly named workload remains `UNCOVERED`. Include push and pull cases and an exact-boundary case.

## F2 — descendants of a real Proxmox system root are misclassified

- Severity: **P1**
- Blocking: **yes**
- Affected: `gen-cron.sh::reconcile_is_system`, `test/reconcile/run.sh`

`reconcile_is_system()` accepts only an exact depth-1 final component `ROOT` or `swap`. Therefore the normal Proxmox boot dataset `rpool/ROOT/pve-1` is not system-classified and is reported as uncovered. The current deeper-name test protects the different and valid rule that `rpool/data/swap` must not be waived merely because its final name is `swap`; it does not cover descendants beneath the exact system anchor `rpool/ROOT`.

**Required:** recognise the exact depth-1 system anchor and its descendants, while retaining the negative boundary for nested workload names such as `rpool/data/swap`, `swap-backups`, and `rootfs`.

**Decisive regression:** `rpool/ROOT` and `rpool/ROOT/pve-1` are visibly system-classified; `rpool/data/swap` and `rpool/swap-backups` remain ordinary scope findings.

## F3 — the audit input is not yet bound to what the hosts actually run

- Severity: **P1**
- Blocking: **yes for fleet proof; no new deployment architecture is required in this response**
- Affected: live evidence procedure, CONFIG v4 provenance

The measurement found that the configs are absent from the hosts and that `jobs.11.11.v4.conf` is pre-migration and no longer parses, while the live cron has already moved on. Comparing ZFS inventory against a stale or non-authoritative config does not establish whether the active backup jobs cover the host.

**Required:** for each host, identify the exact CONFIG v4 input used for reconciliation and prove that its generated send-job set matches the currently installed cron/job set. A temporary copied config is acceptable for this report-only slice; do not invent a deployment subsystem merely to close this review. The stale 11.x pve1 config must be migrated or reconstructed sufficiently to run the audit against what that host actually executes.

The permanent delivery path for configs and any future cron alert remain a separate design step after report correctness.

## F4 — the four-host truth-set evidence is incomplete

- Severity: **P1**
- Blocking: **yes**
- Affected: `docs/testing/RECONCILE-FALSE-POSITIVE-MEASUREMENT-2026-08-08.md`

The new document reports approximate counts, preserves only three example lines, and did not execute reconciliation successfully on the fourth host. It does not classify every emitted item, does not preserve each host's actual output, does not explicitly test false negatives against known guest/storage datasets, and does not record the system-descendant result. It proves that the detector is currently noisy, but not the acceptance property.

After F1–F3:

1. run `--reconcile` successfully on all four actual Proxmox hosts;
2. preserve the complete output for each host;
3. build a manual truth-set from real `zfs`, `qm`, `pct`, installed cron, and the exact config used;
4. classify every line as true uncovered, true declared-but-absent, received backup, intentional system/structural, intentional scratch/test, or false positive;
5. explicitly enumerate known guest/storage datasets and show that none disappears from both covered and finding classes;
6. record exact counts, not “~3”, “a handful”, or equivalent estimates.

Test scratch must remain visible in this report-only slice and may be classified manually as intentional. Do not add a `*test*` heuristic. An explicit owner-managed ignore mechanism can be considered before alerting is enabled, after the detector itself is correct.

Add decisive cases for a prune-only/no-send dataset and a valid pull destination. The same configuration must not be accepted by reconciliation while normal generation would reject it.

F2's anchor/descendant correction remains directionally satisfactory, subject to the submitted response and required verification. F4 still follows only after F1-F3 are genuinely complete.
