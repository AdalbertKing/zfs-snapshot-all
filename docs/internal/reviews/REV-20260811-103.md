# REV-20260811-103 — source-retention design overstates grant gap and bookmark guarantee

## Scope

Review of `docs/discussions/PHASE5-SOURCE-RETENTION-DESIGN-2026-08-11.md` at `b0e292517133c194f6494ece980308e4b4de41b3`, as a follow-up to open REV-102. No production implementation exists yet; this review is intentionally design-time so the destructive source-prune path is not built on incorrect premises.

## F1 — Q3's grant diagnosis is stale and proposes unnecessary privilege

The design says the current PULL source grant is only `send,hold,snapshot`, lacks `destroy`, and therefore should be extended with `destroy,mount`.

Current `deploy.sh` contradicts that. `do_commit_scope` already delegates, per granted source dataset:

`snapshot,destroy,send,hold,release,bookmark`

Therefore `destroy` and `bookmark` are already present at the exact relationship scope. `mount` is not shown as a requirement of snapshot deletion and must not be added merely because the design assumed it was needed. Destructive privilege changes must be derived from the actual command path (`delsnaps.sh` + ZFS operation), not from an outdated remembered grant shape.

Required correction: re-derive the minimum source-prune capability from the current code and live delegated identity. If existing `destroy` is sufficient, do not widen the grant. If another permission is genuinely required, prove it with a negative-control/live test that fails without exactly that permission and succeeds with it.

## F2 — Q4 treats bookmarks as a guaranteed incremental base when current runtime does not guarantee that

The design states that the per-target bookmark "is the safety mechanism" that preserves incremental transfer after source snapshot pruning and outage. That is only conditionally true today.

`lib-zfs-snap.sh` explicitly documents two constraints:

1. bookmark fallback is implemented only for single-dataset/non-recursive transfers; recursive streams deliberately fall through to FULL because they would need a bookmark/GUID match on every child;
2. `record_send_bookmark()` is best-effort: bookmark refresh failure logs a warning and does not fail an otherwise successful transfer.

A scheduled source-prune can therefore delete the last source snapshot that would have been a common incremental base even though no usable bookmark was recorded, or can operate on a recursive relationship for which bookmark fallback does not exist. In those states "bookmark protects the base" is not a property the product can currently rely on.

Required correction: define the invariant the source-prune path will actually enforce before implementation. At minimum, the design must distinguish non-recursive vs recursive relationships and must not claim an incremental guarantee unless a usable bookmark/base is proven. If source pruning is allowed to make a later FULL resend necessary, that must be an explicit product decision surfaced in preview/status, not an accidental consequence of a non-fatal bookmark failure.

Do not solve this by broadly changing the frozen transfer engines without first proving that is the smallest necessary boundary.

## What remains accepted from the REV-102 design

The following direction is sound and should remain:

- collector owns source and target retention scheduling;
- no autonomous source-side cron;
- default CREATE proposes the same ladder on source and target, then renders two independent native CONFIG policies;
- remote source prune should reuse `[prune:remote-scope]` + existing relationship SSH pinning rather than invent a new DSL/channel;
- existing CONFIGs require explicit audit/previewed migration, not hidden reactivation repair;
- Phase 5 transactional install remains blocked until source retention is safe and proven.

## Evidence required before closure

For the corrected design/implementation, use the smallest evidence set that proves the destructive boundary:

- deterministic generation test for separate source/target policies;
- current-grant negative control proving the exact permission set source prune needs (no speculative widening);
- non-matching/manual source snapshot survives;
- target-only old snapshots survive source prune;
- real ZFS: source prune followed by another incremental transfer;
- explicit case where bookmark creation is unavailable/fails, proving the chosen fail-closed/degraded behavior;
- explicit recursive case, or a clear refusal/limitation if recursive bookmark-backed continuity is not supported;
- remote PULL proof under the actual delegated identity and pinned SSH path;
- dependency-selected cascade + `./test/impact.sh --verify`.

## Reviewer follow-up — submitted correction `2e4853d8...` rejected

The response at `2e4853d8eff104d1d9854cc3c58aa529248d1fb2` fixes the top-level Q3/Q4 paragraphs but leaves the active design internally inconsistent.

### Residual F1

The same design note still says in **Sequencing step 3**:

`Remote grant: deploy.sh --join destroy,mount on source + fail-closed activation check.`

and later says remote PULL is deferred because the source `destroy` grant does not yet exist. Both statements contradict corrected Q3 and current `ZFS_PERMS`, where `destroy` is already delegated. The next implementation slice must not be driven by this stale widening premise.

Required: remove every active `destroy,mount` / "grant does not exist" instruction. Step 3 is remote-prune composition plus fail-closed verification of the existing delegated `destroy` capability and pinned SSH path; negative control = revoke/omit `destroy` and prove refusal/failure.

### Residual F2

The corrected note says the equal default ladder means the last-sent snapshot "survives by construction" and that FULL-resend risk arises only when the operator shortens source retention or uses recursive mode. That is still too strong.

A non-recursive relationship can also lose ordinary common-snapshot continuity under the default ladder if bookmark refresh failed/was absent and later failed backup attempts created newer snapshots that retention keeps while aging out the last successfully transferred snapshot. Therefore the design may not limit the risk to operator-shortened windows/recursive mode.

Required: state the actual invariant: incremental continuity is guaranteed only when a usable ordinary common snapshot or proven usable bookmark remains. Default equal retention reduces risk; it does not by itself prove the base survives all failure sequences. The live/negative-control campaign for REV-102 must include a bookmark-unavailable case with later snapshot creation/prune.
