# REV-20260807-066 — Stage 2 verification must follow the dependency/risk graph

**Review time:** 2026-08-07 20:58 CEST

**Reviewed design commit:** `8b69e1afc40ab6a25a0b42532db9769508797fde` (`docs: Stage 2 contract and tests, for approval before any code`).

## Verdict

The three Stage 2 behavior contracts are technically sound and may stand:

1. snapshot suffix once per run;
2. exactly one semantic recursion declaration per invocation;
3. long recursion options without changing generated cron spelling.

**CHANGES REQUIRED applies only to the proposed verification scope.** The document correctly states the new project rule that local green suites are not final proof for environment-sensitive paths, but then applies one broad common cascade to all three changes regardless of which dependency each change actually touches. That recreates the test-cost pattern the project has just decided to stop using.

## F1 — one common campaign over-tests unrelated paths instead of following impact/deps

- Severity: P2
- Blocking: yes — Stage 2 implementation gate
- Affected: `docs/design/stage2-engine-contract.md`, section `Wspólne`

### Evidence

The current common list requires, for all three independent changes:

- `test/snapsend`;
- `test/delsnaps`;
- `test/monitor`;
- `test/cron`;
- `test/cron2conf`;
- `impact.sh --verify`;
- `test/scenarios` on real ZFS;
- a delegated-account host run;
- negative controls.

This is not risk-shaped.

For example:

- 2.1 changes snapshot creation timing/correlation in `snapsend`; real-ZFS `scenarios` is high-value evidence here because the property exists only in actual snapshot behavior.
- 2.2 changes recursion-declaration parsing. Its core proof is parser/regression behavior in the transfer engines. A full real-ZFS scenarios pass does not add evidence to cases such as `-r -r`, `--recursive=no -r`, invalid values or post-`--` parsing unless the scenario suite explicitly exercises them.
- 2.3 adds CLI spelling aliases in the engines while explicitly promising that **generated cron remains unchanged**. `test/cron` tests the crontab writer and `cron2conf` tests reverse conversion of generated lines; neither should be rerun merely because a human-facing engine alias was added unless `impact/deps` shows a real edge or the implementation actually changes their contract.

The project has just accumulated several examples where a large green count was weaker evidence than one correctly placed live test. The inverse is also true: a live-host run on a path that cannot discriminate the changed behavior is expensive decoration, not stronger proof.

### Required outcome

Keep the behavior contracts and per-change negative controls, but replace the unconditional `Wspólne` campaign with a **dependency-driven verification matrix**.

Minimum expected shape:

#### 2.1 suffix/correlation

- focused `snapsend` regression covering multi-dataset flat mode and a clock crossing a second boundary;
- negative control against current behavior showing the correlation case fails there while unaffected cases pass;
- the suites selected by `impact/deps` for the actual diff;
- one real-ZFS scenario that proves the run-level correlation property end to end;
- delegated-account execution only if the modified runtime path is exercised under that supported identity.

#### 2.2 single recursion declaration

- focused parser tests for both transfer engines and every spelling/conflict in the table;
- negative control against current code;
- graph-selected dependent suites only;
- no mandatory real-ZFS/full-host campaign unless the implementation changes something beyond argument normalization or the dependency graph identifies an environment-sensitive edge.

#### 2.3 long aliases

- focused equivalence tests for the scripts that actually gain the aliases (`snapsend`, `snapget`, `delsnaps`, `check-snap-age` as applicable);
- negative control proving the old version rejects/does not understand the new spelling while old short spelling remains unchanged;
- graph-selected dependent suites;
- one delegated live invocation where it materially proves the real installed script accepts the new spelling, rather than a broad fleet campaign;
- generated cron byte identity should be verified only through the cheapest discriminating proof required by the actual diff. If `gen-cron.sh` is untouched, do not mechanically rerun four-host cron/`cron2conf` campaigns just to prove an unchanged file did not change.

`./test/impact.sh --verify` remains the common gate because it validates the graph itself.

### Acceptance criteria

- [ ] `docs/design/stage2-engine-contract.md` maps each of 2.1/2.2/2.3 to its own minimal automated, negative-control and live evidence.
- [ ] A live-host or real-ZFS requirement is attached to a property that the live environment can actually discriminate.
- [ ] `test/cron` / `test/cron2conf` are not unconditional merely because Stage 2 mentions cron compatibility; they run when selected by the dependency/contract graph or by an actual touched contract.
- [ ] Broad campaign escalation is explicitly conditional on implementation blast radius or graph expansion, not the default.
- [ ] Negative controls report both changed failures and unaffected passes.

### Required verification

This finding is documentation/test-planning only. No runtime campaign is required to answer it. Validate the revised design against `test/deps.conf` and `impact.sh` semantics; do not run the Stage 2 campaign before the code exists.
