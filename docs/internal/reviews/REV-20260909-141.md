# REV-20260909-141 — legacy GFS migration re-derives installed policy from the active profile

Review date: 2026-09-09
Reviewer: ChatGPT
Reviewed delivery: PR #368, GFS/retention implementation through `28bd60ecb53b5ba0583bac21afa8aad5aefaf110`
Canonical merge checked: `fe454984f39528d3bedc2adc0f741ebdaff2c93d`

## Verdict

**CHANGES REQUIRED — P1: re-activating a relationship with the old peer-root
GFS ladder correctly narrows its scope, but silently rebuilds the replacement
from the profile currently on disk. An administrator's installed retention
policy is therefore discarded during the automatic migration.**

The used-template detector, the refusal of a new retention-less relationship
and the move to disjoint per-landing scopes are not rejected. The blocker is
confined to preserving installed policy while that old scope is migrated.

## F1 — P1 BLOCKING — automatic scope migration overwrites CONFIG-owned retention

- Severity: P1
- Blocking: yes
- Affected: the `PLAN_PRUNE_LEGACY` branch in `client_section_plan()` and
  `emit_client_sections()`.

### Evidence

On exact implementation `28bd60ecb53b5ba0583bac21afa8aad5aefaf110`, the
reviewer supplied one existing backup relationship with:

```ini
[prune:tank/backups/pve9]
	# managed-by: zfs-backup.sh client=c9
	use_template = profile__prof__keep_hourly,profile__prof__keep_daily,profile__prof__keep_weekly,profile__prof__keep_monthly
	gfs          = yes
	gfs_pattern  = automated_hourly
	recursive    = yes
	pair_label   = c9
	notify       = c9-custom-policy
```

The active `prof` file was the valid built-in `default` profile, whose
`gfs_pattern` is `automated_`. A direct existing-relationship call
`emit_client_sections "$CFG" c9 0` returned `rc=0` and replaced the section
with `[prune:tank/backups/pve9/rpool/data]`, but its policy contained:

```ini
	gfs_pattern  = automated_
```

The old custom `automated_hourly` value was lost. The scope migration itself
succeeded; the failure is that the replacement policy came from
`PROFILE_PRUNE_FILE`, not from the installed legacy section.

This is the migration-only gap in the otherwise explicit REV-20260809-089
contract: an installed CONFIG is runtime truth and re-activation must not
re-derive its policy from a profile that may have changed since CREATE. The new
`gfsshape` control proves preservation only after the relationship is already
in the new per-landing shape; it does not exercise the automatic migration from
the peer-root shape.

### Failure mode and impact

`gfs_pattern` is the family prefix passed to the GFS delete engine. Widening it
from `automated_hourly` to `automated_` makes additional snapshot families
eligible for deletion; changing other installed ladder fields can likewise
shorten retention or remove monitoring. The re-activation reports success, and
the fifth anti-clobber exemption deliberately permits the old line to
disappear, so neither the operator nor the install guard sees that policy was
replaced. This is a credible silent snapshot-loss path and is therefore P1.

### Existing verification and why it missed the defect

- PR #368 exact-head CI is green: run `34364182455`.
- Independent focused run on canonical `main`:
  `./test/zfsbackup/run.sh --section gfsshape` — `21 PASS / 0 FAIL`.
- The migration assertion checks only the planned old and new scopes. The
  preservation assertion starts from an already-migrated section. No test
  combines a legacy peer-root ladder with policy that differs from the active
  profile.

### Acceptance criteria

1. When an owned legacy `[prune:TARGET/<peer>]` is split into per-landing
   sections, derive the replacement retention policy from that installed
   section, not from the active profile.
2. Preserve every policy-owned directive and its effective generated command,
   including custom `use_template`, `gfs`, `gfs_pattern`, schedules, retention
   and monitor fields. Recompute only fields whose meaning necessarily changes
   with the new path topology.
3. Add a discriminator using a valid legacy ladder whose `gfs_pattern` differs
   from the active profile: re-activation must return `rc=0`, remove the
   peer-root section, create the per-landing section and retain the installed
   pattern in the real `gen-cron.sh` output.
4. Keep the new relationship behavior already covered by `gfsshape`: orphan
   templates do not vote, genuinely referenced flat templates do, a
   retention-less CREATE refuses, sibling relationships receive disjoint
   scopes, and a foreign peer-root ladder is never removed.
5. The migration exception in `assert_target_block_not_clobbered()` must remain
   fail-closed for any policy-bearing generated job that has no semantically
   equivalent replacement under the new scope.

### Required verification

No live ZFS mutation or broad campaign is required. A synthetic CONFIG and the
