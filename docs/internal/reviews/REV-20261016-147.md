## F1 — a second --deny-restore bypasses the failed-revocation pause guard

- Severity: P1
- Blocking: yes
- Affected: `deploy.sh`, `do_deny_restore()` (initial no-file branch and
  removal of the grant before `zfs unallow`); subsequent
  `zfs-backup.sh resume-writers`.
- Introduced safety boundary: PR #551, in particular
  `e502b130fb8171c2684fe2d40a75607e90bebb21`.

### Evidence and failure mode

`do_deny_restore()` unlinks the grant before revoking the scope/namespace ZFS
delegation. If `zfs unallow` fails on a dataset that still exists, it correctly
returns 1 and keeps the target's own relationships paused. However, its retry
finds no grant file, immediately calls `restore_grant_resume_writers`, and
returns 0. No further attempt to revoke or verify the delegation occurs.

This is an ordinary retry of the CLI's own partial failure, with an intact
pairing manifest; nobody manually removed the grant. The account can retain
receive/rollback/create capability while this host's scheduled writers and
pruning jobs are released into the same scope. Removing the declaration does
not remove the ZFS capability. This defeats PR #551's stated ordering rule and
can reopen conflicting writes during recovery.

Independent executing discriminator, using the shipped `deploy.sh` and its
real `zfs-backup.sh` pause/resume path with disposable records and fake ZFS:

```text
allow rc=0 grant=yes paused=yes unallow_calls=0
first_deny rc=1 grant=no paused=yes unallow_calls=2
retry_deny rc=0 grant=no paused=no unallow_calls=2
```

The two failed calls are on `pool/a` and `pool/restore`, both reported as
existing. The retry logs `no restore grant ... nothing to take back` followed
by `client 'puller' resumed`. The unchanged call count proves that the retry
does not even attempt the revocation.

The same reproduction produces the same discriminator on PR #560's exact
head. Its remount additions do not fix this failure.

Control with successful `unallow`: first denial returns 0, removes the pause,
and a repeated denial is harmless. No real ZFS, SSH, cron or production state
was accessed. Consequently this proves the CLI/state-machine failure, not an
observed production data-loss incident.

### Minimal reproduction

Save the following as a temporary script and run `bash script.sh /path/to/repo`.
Every write and cleanup stays in the newly created temporary directory.

```bash
#!/usr/bin/env bash
set -u
repo="${1:?repository path required}"
lab=$(mktemp -d)
trap 'rm -rf "$lab"' EXIT
mkdir -p "$lab/bin" "$lab/peers" "$lab/relationships/lab1" \
    "$lab/clients" "$lab/grants" "$lab/state"
printf '%s\n' 'PEER_JOIN_ACCOUNT="backup-test"' \
    'PEER_JOIN_GRANTED_DATASETS="pool/a"' > "$lab/peers/lab1.conf"
printf '%s\n' 'CLIENT_NAME=puller' 'STATE=active' \
    'MANAGED_DATASETS=pool/a' > "$lab/clients/puller.conf"
printf '%s\n' '#!/bin/sh' '[ "$1" = -u ] && { echo 0; exit; }' \
    'exec /usr/bin/id "$@"' > "$lab/bin/id"
printf '%s\n' '#!/bin/sh' 'printf "%s\n" "$*" >> "$ZFS_TRACE"' \
    '[ "$1" = unallow ] && [ "${TEST_UNALLOW_FAIL:-1}" = 1 ] && exit 1' \
    'exit 0' > "$lab/bin/zfs"
chmod +x "$lab/bin/id" "$lab/bin/zfs"
export ZFS_TRACE="$lab/zfs-trace"
run() {
    PATH="$lab/bin:$PATH" PAIR_GATE_STATE_DIR="$lab/relationships" \
    PEER_STATE_DIR="$lab/peers" RESTORE_GRANT_DIR="$lab/grants" \
    CLIENTS_DIR="$lab/clients" RELATIONSHIPS_DIR="$lab/state" \
    bash "$repo/deploy.sh" "$@"
}
state() {
    local tag="$1" rc="$2" grant=no paused=no
    [ ! -e "$lab/grants/lab1" ] || grant=yes
    [ ! -e "$lab/state/puller/paused" ] || paused=yes
    printf '%s rc=%s grant=%s paused=%s unallow_calls=%s\n' \
        "$tag" "$rc" "$grant" "$paused" \
        "$(grep -c '^unallow ' "$ZFS_TRACE" || true)"
}
run --allow-restore=lab1 > "$lab/allow.log" 2>&1; rc=$?
state allow "$rc"
run --deny-restore=lab1 > "$lab/deny1.log" 2>&1; rc=$?
state first_deny "$rc"
run --deny-restore=lab1 > "$lab/deny2.log" 2>&1; rc=$?
state retry_deny "$rc"
```

For the successful-revocation control, prefix the invocation with
`TEST_UNALLOW_FAIL=0`.

### Strongest existing evidence and its limit

PR #551 explicitly reports the missing-file path as resume-only, and its
section-12 tests exercise one failed revocation. They do not execute a second
denial after that failure; the suite reissues `--allow-restore` instead. The
PR's note frames this as a manually removed file, but the CLI itself creates
exactly that state on every failed revocation. No owner risk acceptance for
this failed-operation retry was found in the reviewed artifacts.

Green CI therefore does not resolve this retry gap.

### Acceptance criteria and required verification

1. A failed revocation must preserve sufficient durable information to retry
   account/scope/namespace revocation. A subsequent `--deny-restore` must not
   resume any grant-owned pause while a prior revocation remains unproven.
2. Repeated failure on existing datasets remains nonzero and preserves pauses;
   no success/no-op message may imply the capability is gone.
3. When a later retry succeeds, revoke the relevant delegations before resuming
   only the pauses owned by this grant. Preserve unrelated/operator pauses.
4. Handle the already-published partial state (grant file absent after a failed
   denial) fail-closed: retry from trustworthy existing facts or refuse with
   actionable recovery. Absence of the grant alone is not proof of revocation.
5. Add one executing regression sequence: allow -> unallow failure -> another
   failure -> successful retry. Assert exit status, attempted ZFS calls and
   pause ownership at every step. The current tree must fail the discriminator.
   Keep successful repeated-denial and genuinely gone-dataset cases working.

Keep the fix scoped to revocation/retry ordering and evidence. No production
fix was made by the reviewer. Claude should publish the response for this REV
with a full implementation SHA reachable from main, exact-head CI, the focused
regression and `./test/impact.sh --verify`. Additional engine, GUI, X27 and
remote-snapshot-only proposals in the backlog are not approved by this review.
