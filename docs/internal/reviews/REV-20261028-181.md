# REV-20261028-181 — P1: rollback reports success after failed re-deployment

Reviewer: ChatGPT. Date: 2026-10-28.

Source release: `AdalbertKing/zfsbackup` main
`5f28bd0f0e0067926e2f33f905831285a86e4893`, with
`RELEASE-OF=edba2b7917cae40778908f96f8f28c3e430a2a93`. The finding was
first reproduced on release `8143775b415bc400e6a554bdac2bed396196f839`
(`RELEASE-OF=901e8e4b7ba5a2871ef59e29e6356b9762f2bb2f`) and was rechecked
after the release advanced during publication.

## F1 — failed host re-application is reduced to a warning

- Severity: **P1**
- Blocking: **yes for claiming a successful one-command rollback**
- Affected: `update-control.sh`, `do_rollback()`, `apply_repo_to_host()`

### Evidence

After `do_rollback()` creates the update hold and successfully resets the
checkout to the previous revision, it invokes:

```bash
apply_repo_to_host "rollback" "$(printf '%.8s' "$target")" \
    || warn "the rollback of the CHECKOUT succeeded, but re-generating the installed scripts at that revision did not -- this host is a mixture. Investigate before relying on it."
```

The function then unconditionally logs `rolled back ...` and returns 0. This is
different from `do_self_update()`, where the same helper failure is returned to
the caller. Existing self-update tests prove successful rollback re-application
and failed update application, but contain no negative rollback-application
case.

Executable exact-blob negative control (isolated temporary Git repository and
stub `deploy.sh`; no production checkout, host, crontab or network operation):

```bash
bash docs/internal/reviews/evidence/REV-20261028-181-rollback-apply-failure.sh
```

Against the current exact `RELEASE-OF` commit it reports:

```text
sha=edba2b7917cae40778908f96f8f28c3e430a2a93 rollback_rc=0 head=<old> target=<old> before=<new> hold=1 mixed_warning=1
FAIL: rollback reports success although re-deployment failed and the host is a version mixture
```

The exact release commit produces the same result when selected with
`TARGET_SHA=5f28bd0f0e0067926e2f33f905831285a86e4893`. Both initially
audited exact SHAs named above produce the same result.

### Failure mode and impact

The repository checkout is old and automatic updates remain held, but generated
or installed scripts may still be from the newer revision (or be only partly
replaced). The command's return code tells an operator or automation that the
rollback succeeded even though the active host is a version mixture explicitly
described as unsafe to rely on. This breaks the rollback safety contract at the
point intended to recover from a bad release and can conceal incompatible code,
configuration or generated jobs.

### Acceptance criteria

- A failed `apply_repo_to_host` after the checkout reset must make `--rollback`
  return nonzero. Unknown or partial host activation is never success.
- The update hold must remain in place after this failure. Do not automatically
  retry or resume updates.
- Diagnostics must distinguish checkout rollback from host re-application and
  must not print an unqualified successful-rollback message.
- A successful reset and successful host re-application must continue to return
  0 and retain the existing hold/resume contract.
- Preserve the existing self-update apply-failure behavior and the independent,
  rollback-surviving control wrapper.

### Required verification

- Add a dependency-free failed-apply rollback case that asserts: nonzero exit,
  checkout at the old SHA, hold present, failure/mixed-state diagnostic, and no
  automatic retry or resume. The fixture should also prove that an installed
  marker remains new or otherwise records failed/partial activation rather than
  pretending the host followed the checkout.
- Retain a positive rollback-apply case with exit 0 and the old revision applied.
- The reproducer above must change from FAIL to PASS and remain failing against
  both exact affected SHAs named here.
- Run `test/selfupdate`, shell syntax, `git diff --check`,
  `test/impact.sh --verify` and exact-head CI. A live host rollback is not
  requested; any live evidence must be non-mutating or use a throwaway target.
