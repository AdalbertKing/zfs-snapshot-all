## Owner decisions established in the discussion

1. A collector administrator on `pve1` must not be required to know the ZFS layout of `pve2`.
2. `--datasets=...` is therefore wrong as a required argument to `add-client`.
3. In backup mode, `pve1` supplies a target, or inherits the server default target.
4. In sync mode, no target is supplied: selected source paths are reproduced at the same paths on `pve1`.
5. Dataset discovery and selection occur on `pve2`, after the enrolment material from `pve1` is accepted.
6. `pve2` generates a default editable config from all ZFS pools. The default active roots are non-system datasets at the first level below each pool, for example `rpool/data`, `rpool/olds`, and `hdd/LXC`.
7. A default root means:
   - `include_parent = no` — do not send the root dataset itself;
   - `include_children = yes` — send all descendants;
   - the corresponding root may still be created on `pve1` as an empty structural ancestor with `canmount=noauto`.
8. Pool roots and obvious system datasets such as `rpool`, `rpool/ROOT`, and `rpool/ROOT/pve-1` are not selected by default.
9. The same editable file also contains a commented inventory of the complete `zfs list`, so the administrator can replace the default with one VM, one zvol/subvolume, several explicit leaves, or another branch.
10. Avoid a second manifest/config representation. The file edited on `pve2` is transferred byte-for-byte to `pve1`. It remains data, never shell: no `source`, `eval`, or equivalent execution.
11. `pve1` parses that file and performs the authoritative validation and dry-run. The owner accepts this simpler design over a distributed transaction or a second normalized scope manifest.
12. The normal enrolment path is online. Manual package movement remains an offline/recovery path, not the expected workflow.
13. LAN-to-WAN relocation must distinguish an application endpoint (`host:port`) from the network route carrying it. A routed site-to-site OpenVPN can preserve the original `pve2` LAN endpoint while only the route changes. `set-endpoint` must not be required merely because the collector moved.
14. A new endpoint is needed only when the address used by SSH actually changes, for example Tailscale/MagicDNS, a tunnel address used directly, or a public address plus port-forwarding.

These decisions revise specific parts of `docs/discussions/DEPLOY-UX-AGREED-POSITION.md`, especially §§5–9 and §14. The snapget-first model, pve1 as control plane, stable relationship identity, pinned host key, no cron before final verification, and expert backend remain valid.

## F1 — Dataset scope is chosen on the wrong host and too early

- Severity: P1
- Blocking: yes, for the simplified enrolment workflow
- Status: OPEN
- Affected: `zfs-backup.sh` usage and `cmd_add_client`; `deploy.sh --pair/--join`; current seed/draft sequence

### Evidence

Current `zfs-backup.sh` advertises and enforces:

```text
zfs-backup.sh add-client NAME --lan=HOST[:PORT] --datasets="A B" [--target=X]
```

`cmd_add_client` refuses an empty dataset list before any interaction with `pve2`, then passes that list into `deploy.sh --pair --peer-datasets=...`. The generated package carries the preselected list, and `deploy.sh --join` grants only that list. `cmd_seed` asks `deploy.sh --draft-config` to list the peer only later, after the scope has already been chosen and granted.

This makes the collector administrator provide facts that are authoritative only on the source host.

### Failure mode

A general administrator must log into `pve2` or already know its ZFS naming before they can even create the relationship on `pve1`. The high-level workflow therefore exposes an internal provisioning assumption instead of discovering the source.

It also biases the administrator toward one remembered root (`rpool/data`) and can silently omit valid branches on other pools such as `rpool/olds` or `hdd/LXC`.

### Required outcome

`add-client` must create relationship/bootstrap material without a source dataset list. The source host discovers and presents its own layout during enrolment.

Expected high-level shape, names still open:

```text
backup: zfs-backup add-client pve2 --mode=backup --lan=<reachable pve2> [--target=<or server default>]
sync:   zfs-backup add-client pve2 --mode=sync   --lan=<reachable pve2>
```

The response must explain how to preserve the existing safe pair/join backend when `deploy.sh --pair` currently requires `--peer-datasets`, and where the minimum seam should be introduced. Do not answer merely “make the argument optional”; identify what the package can safely contain before the source scope exists and when the source-side account/delegation can be created.

### Acceptance criteria for the later implementation

- [ ] High-level `add-client` does not require or solicit source datasets.
- [ ] Backup mode accepts/inherits a target; sync mode rejects a target unless a later owner decision explicitly introduces mapping.
- [ ] Source scope is selected on `pve2` before ZFS delegation is committed.
- [ ] Existing expert `deploy.sh --pair/--join --peer-datasets=...` remains available and compatible.
- [ ] No empty or guessed dataset list is passed to a backend path that interprets it as a real grant.
- [ ] Tests prove the old high-level requirement is gone while the expert path still enforces its own contract.

### Required response now

Describe the minimum backend/API change and all current assumptions that prevent delayed scope selection.

## F2 — The source needs one editable, transferable config, not a second scope manifest

- Severity: P1
- Blocking: yes, for enrolment design
- Status: OPEN
- Affected: proposed peer-side `enroll`; `deploy.sh --draft-config`; INI parsing; ZFS delegation; collector config generation

### Required user experience

After accepting the relation material, `pve2` runs one high-level command. It inventories all pools and opens a generated file like `crontab -e`, using `$VISUAL`, `$EDITOR`, then a sensible fallback.

Illustrative active portion:

```ini
[dataset:rpool/data]
include_parent = no
include_children = yes

[dataset:rpool/olds]
include_parent = no
include_children = yes

[dataset:hdd/LXC]
include_parent = no
include_children = yes
```

Illustrative inventory portion:

```ini
# Full ZFS inventory — informational, edit/copy entries above as needed.
# Source command may use:
# zfs list -H -o name,type,used,refer,mountpoint

# [dataset:rpool/data/vm-100-disk-0]
# include_parent = yes
# include_children = no
# type=volume used=64G refer=48G mountpoint=-
```

The exact syntax is not yet approved. Claude must first determine whether this can be represented directly in the existing `gen-cron.sh` INI grammar without dragging schedule, retention, remote credentials, and target policy onto `pve2`. If it cannot, propose the smallest data grammar and parser reuse that still obeys the owner decision: one file moves 1:1 from `pve2` to `pve1`; no separate normalized scope manifest is introduced.

### Failure mode to avoid

A “friendly selection file” converted into a second manifest and then into a third collector config creates three representations, three parsers, and drift between:

- what the administrator selected;
- what `pve2` delegated;
- what `pve1` backs up.

The owner explicitly rejects that complexity.

### Required outcome

One byte-identical file is the durable scope artifact on both hosts. It may be stored at different paths, but it is not rewritten in transit.

`pve1` performs the authoritative parse and dry-run. The same parsed scope must also drive source-side delegation. A safe minimal local syntax check on `pve2` is acceptable, but it must not create a second canonical representation.

### Security boundary

The file is untrusted data from another host. It must never be executed with `source`, `eval`, shell interpolation, or equivalent. Dataset grammar must reject option-like names, dot segments, control characters, duplicate/ambiguous sections, and unsupported keys. Unknown syntax fails closed and returns the user to the same editable file.

The response must state exactly which existing parser can be reused, which cannot, and why.

### Acceptance criteria for the later implementation

- [ ] Default active roots are generated from every pool, not only `rpool`.
- [ ] Pool roots and known system branches are not active by default.
- [ ] The complete inventory is included as comments in the same file.
- [ ] The operator can select one explicit leaf without also backing up its siblings.
- [ ] The edited file is transferred byte-for-byte to `pve1`.
- [ ] No second normalized scope manifest exists.
- [ ] Both delegation and collector job scope derive from this one file.
- [ ] The file is parsed as data and fails closed on malformed or ambiguous input.
- [ ] A failed validation reopens or preserves the same file instead of restarting enrolment.

### Required response now

Provide a concrete minimal grammar proposal, parser reuse analysis, and the exact lifecycle of this single file on both hosts. Do not implement it yet.

## F3 — Backup and sync need distinct destination contracts

- Severity: P1
- Blocking: yes, for `--mode=sync`
- Status: OPEN
- Affected: high-level mode model; target mapping; preflight; seed

### Required backup mapping

With collector target `rpool/backups`, a source leaf such as:

```text
pve2:rpool/data/vm-100-disk-0
```

lands under a client namespace, conceptually:

```text
rpool/backups/pve2/rpool/data/vm-100-disk-0
```

When `include_parent=no`, `rpool/backups/pve2/rpool/data` may exist only as a structural ancestor with `canmount=noauto`; it does not receive the parent dataset stream.

### Required sync mapping

Sync preserves source paths:

```text
pve2:rpool/data/vm-100-disk-0
→ pve1:rpool/data/vm-100-disk-0
```

A sync enrolment therefore supplies no target. It must preflight that every required destination pool already exists on `pve1`. The tool may create datasets, but not pools.

Example: if the source selection includes `hdd/LXC/...` and `pve1` has no `hdd` pool, sync must stop before transfer and name that incompatibility. It must not silently remap the branch under another pool or switch the relation to backup mode.

### Required response now

Identify what the current snapget destination composition already supports, what needs orchestration only, and what new collision/destructive checks sync requires. Include the interaction with an existing local dataset at the same path, mounted Proxmox storage, local VM/CT ownership, and `canmount=noauto`.

### Acceptance criteria for the later implementation

- [ ] Backup and sync produce the mappings above from the same selected source config.
- [ ] Sync refuses a missing destination pool before any receive.
- [ ] Sync refuses or explicitly reports local workload/path collisions; it never overwrites a live local VM/CT dataset as a side effect of enrolment.
- [ ] Structural parents are created unmounted where appropriate.
- [ ] No target argument is required in sync mode.

## F4 — LAN/VPN is a route distinction, not necessarily an endpoint change

- Severity: P1
- Blocking: yes, for relocation UX
- Status: OPEN
- Affected: `zfs-backup.sh` endpoint model, `final-catchup`, `set-endpoint`, `verify-endpoint`, `activate-client`; `DEPLOY-UX-AGREED-POSITION.md` §§3, 5, 6, 10

### Evidence

The current wrapper models two fixed endpoint slots, `lan` and `vpn`, and the agreed-position document says that after relocation the endpoint is explicitly changed to VPN.

That is correct only when the address used by SSH changes.

In a routed site-to-site OpenVPN installation, `pve1` may still reach `pve2` at the original LAN address, for example `192.168.11.11:22`. Before relocation the kernel routes that address over Ethernet; afterward it routes the same address through the VPN. The application endpoint, host key, relationship key, target, and job identity are unchanged.

Conversely, Tailscale, MagicDNS, a directly addressed tunnel IP, or public NAT/port-forwarding may present a genuinely different `host:port`.

### Failure mode

Forcing an endpoint transition whenever the collector is moved makes an administrator invent or repeat an address that did not change. It conflates network topology with application identity and adds a needless state transition to the common routed-VPN case.

The opposite mistake is also unsafe: blindly assuming the old endpoint works can hide that the new route reaches a different host or that the next run would be full.

### Required outcome

Relocation starts by testing the current endpoint from the collector's new location:

```text
current host:port reachable
→ pinned fingerprint matches
→ authentication works
→ dry-run says incremental for every selected dataset
→ no endpoint mutation
```

Only when the current endpoint is unreachable does the workflow request a replacement `host:port`, pin it to the same stable `HostKeyAlias`, and verify it before activation.

The source may see a different source IP for `pve1`; the relationship remains key-based. The response must inspect whether current `authorized_keys`, delegated accounts, firewall assumptions, or any `from=` restriction bind the collector to its old source address.

### Catch-up contract

Before physically moving `pve1`, perform a real final incremental over the still-working LAN route. After relocation, verify the route and common base; the owner also prefers one real incremental over the production route before cron activation.

Current messages must be checked for a role error: in this scenario the moved machine is the collector `pve1`, not the source `pve2`.

### Acceptance criteria for the later implementation

- [ ] Routed VPN with unchanged `host:port` requires no `set-endpoint` operation.
- [ ] The current endpoint is always reverified after relocation, including pinned host key and `PLAN=INCREMENTAL` for every selected dataset.
- [ ] A changed endpoint preserves relationship identity, key, target, bookmarks, and job state.
- [ ] A replacement endpoint is requested only when needed and is verified fail-closed.
- [ ] Source-IP restrictions, when present, are detected or clearly reported rather than silently breaking the first scheduled run.
- [ ] A real final LAN catch-up and a real post-relocation incremental are represented in the high-level workflow before cron activation.
- [ ] User-facing messages name the collector as the machine being moved.

### Required response now

Compare these requirements to the exact current state machine and propose the smallest correction. State whether the fixed `lan`/`vpn` slots should remain internal compatibility fields, be generalized, or be removed from the new UX while retaining backend commands.

## F5 — Online enrolment must reduce manual work without inventing an unsafe bootstrap service

- Severity: P1
- Blocking: owner-decision after implementer analysis
- Status: OPEN
- Affected: proposed peer-side `enroll`; current package transfer instructions; trust bootstrap

### Owner requirement

The normal path should not require manually copying a `.tgz` from `pve1` to `pve2` and manually returning a config. The administrator should receive one high-level command for `pve2`; the relationship material is obtained online and the edited config returns online. Offline import/export remains available.

### Constraint

There is no pre-existing trust between the two hosts. “Online” is not permission to add an unauthenticated web service, trust arbitrary DNS, use `StrictHostKeyChecking=no`, expose a root API, or embed a reusable secret in logs/history.

The current package-validation work is valuable and should be reused rather than bypassed.

### Required response now

Present the smallest credible online bootstrap design, including:

- who listens or connects first;
- what the one-time secret/token authenticates;
- how the owner verifies the collector/source identity;
- package/config size and expiry limits;
- replay prevention;
- where transient state is stored;
- retry/idempotence behavior;
- how the offline package path uses the same validation and commit logic;
- which new dependency or daemon, if any, is required.

Prefer a design built from existing SSH/package primitives. If no safe low-complexity online path exists without a new service, say so explicitly and offer the least-bad alternative for owner decision. Do not implement a server merely to satisfy the word “online”.

### Acceptance criteria for the later implementation

Deferred until the owner chooses among the concrete designs in Claude's response.
