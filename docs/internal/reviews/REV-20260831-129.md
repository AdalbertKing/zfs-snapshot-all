# REV-20260831-129 — recursive landing verification compares child snapshots with the parent's GUID

Review date: 2026-08-31
Reviewer: ChatGPT
Reviewed delivery: PR #220, head `4cb82baead4ecaa05b4b4bd8ba0521e4c5622562`
Canonical base checked: `9661159bc79842735da74b9592bc3a117aab477b`

## Verdict

**CHANGES REQUIRED — P1: a successful recursive restore is reported as changed
and unfinished when the restored relation contains a child dataset.**

The new identity check correctly rejects a same-name snapshot with the wrong
GUID for a single dataset. Its recursive call, however, supplies one expected
GUID for the root and applies it to every descendant. Snapshot GUIDs belong to
individual dataset snapshots, so a valid child snapshot does not have its
parent's GUID.

## F1 — P1 BLOCKING — one root GUID is applied to the entire recursive subtree

- Severity: P1
- Blocking: yes
- Affected: `zfs-restore.sh`, `restore_one()` and
  `restore_remote_off_point()`; `test/restore/offpoint.sh`.

### Evidence

`restore_one()` extracts only `${copy}@${point}` from `rows` and passes that
single GUID to the remote verifier:

```sh
_vguid="$(printf '%s\n' "$rows" | awk -F'\t' \
    -v p="${copy}@${point}" '$1 == p {print $3; exit}')"
_off="$(restore_remote_off_point ... "$_vdepth" "$_vguid")"
```

When `RESTORE_ENGINE_RECURSED=1`, `_vdepth` is empty and the verifier enumerates
the root and all descendants. For each one it compares `"$d@$point"` with the
same root GUID:

```sh
if [ -n '$want' ] && [ "$g" != '$want' ]; then
    echo "$d has a snapshot NAMED $point but a DIFFERENT one ..."
fi
```

The submitted focused suite is green but contains only `rpool/data`:

```text
$ bash test/restore/offpoint.sh
PASS=6 FAIL=0
```

A reviewer-only control used the submitted function unchanged with a successful
recursive landing fixture:

```text
rpool/data@p        guid 111
rpool/data/child@p  guid 222
```

Both datasets have `p` as their newest snapshot. The verifier was called exactly
as the recursive path calls it, with the root's expected GUID `111`. Observed:

```text
rpool/data/child has a snapshot NAMED p but a DIFFERENT one -- guid 222, expected 111
```

There is no incorrect child snapshot in this fixture. `222` is the child's own
snapshot identity; comparing it with the parent's `111` is a category error.

### Failure mode and impact

After the engine successfully restores a recursive relation, the verifier emits
a false identity mismatch for every child. `restore_one()` converts the
non-empty result to `RESTORE_ONE_VERDICT="the engine reported success but the
target is NOT at $point"` and returns the changed/incomplete status. Operators
are therefore told that a completed recovery needs manual intervention, and a
recursive Restore slice cannot produce a trustworthy success result.

The same-name/wrong-GUID protection is necessary and must remain. The defect is
only the use of one dataset's expected identity for other datasets.

### Acceptance criteria

1. In recursive mode, verify each enumerated dataset against the GUID of its
   corresponding copy-side snapshot, never against the root snapshot's GUID.
   An equivalent design that verifies each dataset in its own already-mapped
   call is acceptable.
2. A root and child whose newest snapshots are their respective valid recovery
   points must produce no off-point report and a successful Restore verdict.
3. Preserve refusal when either the root or a child has the right snapshot name
   but a different GUID from its own corresponding copy snapshot.
4. Preserve detection of a missing recovery snapshot and of any newer snapshot
   for every dataset that was included in the recursive send.
5. Add one focused parent-plus-child regression to
   `test/restore/offpoint.sh`; keep the existing single-dataset identity cases.

### Required verification

- automated: `bash test/restore/offpoint.sh` with the new recursive case;
- negative control: the valid parent-plus-child case must fail against
  `4cb82baead4ecaa05b4b4bd8ba0521e4c5622562` with the false child mismatch;
- consistency: `./test/impact.sh --verify` and exact-head CI;
- no live destructive Restore campaign is required for this bounded verifier
  correction.

### Notes and uncertainty

This finding does not challenge verification by identity or the removal of
`written@point`. It is limited to carrying the correct per-dataset identity
through the recursive verification boundary. REV-20260831-128 remains a
separate, earlier Restore targeting blocker.
