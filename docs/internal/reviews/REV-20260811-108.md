# REV-20260811-108 — source-retention audit would take ownership of passive `-e` sources

## Finding

`audit-source-retention` currently treats every active remote-PULL dataset with an installed remote `src` and no effective bounded `delsnaps` as missing source retention. The scan does not discriminate the installed transfer semantics before adding the scope to `MISS_SRC`; `--apply` then emits a source `[prune:]` and requires the remote `destroy` grant.

That establishes the unconditional rule `remote PULL without source prune => repair it`, which is not the project contract.

The recorded passive-source design explicitly defines a legitimate native CONFIG shape:

- transfer uses `snapget -e` and consumes an already-existing externally owned snapshot;
- SOURCE has no `[prune:]` because this package does not own the source snapshot lifecycle;
- TARGET retention remains managed normally;
- REV-102 must not silently turn such a relationship into package-owned source retention.

Therefore `audit-source-retention` can currently report a correct passive CONFIG as defective and `--apply` can propose taking destructive ownership of externally managed snapshots.

## Required correction

Keep this small. Do not add a new retention state or ownership language.

The audit already treats installed CONFIG as runtime truth. Use that same installed `[dataset:]` transfer semantics to determine whether the relationship is one that creates/manages source snapshots. A passive `-e` relationship must not be entered into `MISS_SRC` merely because source `[prune:]` is absent.

The exact implementation should reuse the existing CONFIG/runtime representation; no `unmanaged` token, no second policy model.

## Minimum discriminating evidence

1. managed/default remote PULL, no effective source prune -> audit reports missing and `--apply` remains eligible to add bounded source retention;
2. passive remote PULL whose installed transfer flags select `-e`, no source prune -> audit reports it as intentionally outside source-retention ownership and `--apply` leaves CONFIG byte-identical, with no `destroy` grant requirement;
3. passive relationship still retains normal TARGET prune behaviour;
4. one negative control proving that adding a source prune to the passive fixture would be observable as the wrong result.

No broad suite is required unless the dependency graph selects it. The targeted `zfsbackup` audit/generation regression plus the normal dependency-selected cascade is sufficient for this correction; no live destructive ZFS proof is needed for the classification itself because the remote-prune execution path already has separate live proof.

## Interaction with REV-102

REV-102 remains OPEN independently for its current F3 managed-prefix false-green and continuity/runtime evidence. REV-108 is a separate ownership/classification guard: fixing F3 must not make the audit more precise about the wrong universe of relationships.

## Verdict
