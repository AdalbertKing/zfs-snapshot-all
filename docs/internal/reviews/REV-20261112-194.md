# REV-20261112-194 — removable-replica attach does not establish the same contract on every path

Reviewer: ChatGPT / GPT-6.1 Sol. Date: 2026-11-12.

Target: development main `2e6f652b30dd585e0ccce1e55d97213c31e8c3d0` and released 1.0.19, release main `47b5e090871b04c4109088134f06b2e98d83e14e` (`RELEASE-OF` names that development revision). The mechanisms were independently identified during the 2026-11-11 model comparison against `dcd474d673d733bd14253f58ee788f47998865c7`; the affected media-gate, generator and parser code is unchanged in this revision. ## F1 — local replica validation and the engine disagree about a source containing a colon

- Severity: **P1**. Blocking: **yes for correct source/target identity and media preflight**.
- Path: `gen-cron.sh:3192–3205,4097–4098,4612–4620,4713–4723`; `snapget.sh:2870–2899,3265–3275`; `zfs-media-gate.sh:833–837,898–905`.
- Contract: a `[replica:]` copies datasets on THIS host. Its gate and engine must identify the same source and destination.
- Evidence: the validator accepts `source=backupnode:tank/data`: it contains `/` and only allowed characters. The generator passes it literally to both the gate and `snapget.sh`. The engine's `if [[ "$_item" == *":"* ]]` splits it into host `backupnode`, dataset `tank/data`, and builds the target from that stripped dataset. The gate uses the literal value locally, checking `BASE/backupnode:tank/data` and asking local ZFS for the size of `backupnode:tank/data`. Failed local size reads disable its size check. Running the exact validator/parser fragments yields `validated replica source=backupnode:tank/data; engine host=backupnode dataset=tank/data`.
- Impact: an accepted local-replica config may initiate a remote-source operation (if SSH access succeeds), while the gate inspects a different identity. A legitimate local dataset containing `:` is also ambiguous to this parser. Removing everything before the first colon unconditionally would break such local names.
- Acceptance: establish an unambiguous local-source representation end to end, or reject unsupported remote notation before generating the job while preserving the documented valid local-name contract. Show identical source and target identities in config, gate and engine. Include `host:tank/data`, a legitimate local `tank/data:part`, ordinary local sources and multi-source replicas. Unsupported remote input must not reach SSH or produce a runnable misleading job.
- Required evidence: focused generator/parser tests, old-code negative control, mapped CI, impact verification; distinguish any live ZFS/SSH evidence from stubs. Reviewer did not contact SSH hosts.

## F2 — the gate rejects a healthy renamed snapshot although the engine recognizes its GUID

- Severity: **P1**. Blocking: **yes for safe return of existing media**.
- Path: `zfs-media-gate.sh:835–866`; `snapget.sh:1025–1055` recognizes common snapshot GUIDs independently of names.
- Evidence: the gate first compares snapshot names. Its fallback compares target snapshot GUIDs only to source BOOKMARK GUIDs, omitting source snapshot GUIDs. With source `tank/src@replica_new`, target `BASE/tank/src@replica_old`, both GUID `777`, and no bookmark, full `attach` with stubbed ZFS returns **2**, says `DIFFERENT lineage`, and prints `zfs destroy -r` as one of the offered actions. The source/target snapshots have a valid common identity after a rename; the engine already supports this.
- Impact: a usable copy is blocked and the operator is given a false diagnosis plus an unnecessary destructive option. No automatic destroy was observed or claimed.
- Acceptance: use validated GUID evidence for snapshots as well as bookmarks. Test different names/same GUID, same name/different GUID, a valid latest-target bookmark, a bookmark of an older target snapshot, and failure to read the evidence. Unknown evidence must not be described as proven foreign lineage or justify discarding a copy. Run the new test against old behavior as a negative control.

## F3 — pre-existing imports bypass both content and capacity checks

- Severity: **P2**. Blocking: **yes for the first-copy preflight and consistent attach decisions**.
- Path: `zfs-media-gate.sh:718–734` exits successfully before `831–886` (lineage) and `896–912` (capacity). The generated bracket runs the engine after `attach` returns 0 (`gen-cron.sh:4137–4138`).
- Evidence: both accepted already-imported branches return 0 after `check_dataset`: a matching ownership marker and no marker. For the same first-copy fixture (source used 1,000,000,000 bytes, available 500,000,000), a fresh import returns **2**; a pool imported before attach returns **0**. Existing U183 tests always start with the medium not imported, so they miss this branch.
- Impact: an oversized first copy starts only because the administrator or interrupted job imported the same pool earlier. The lineage refusal is similarly bypassed. The engine's own downstream guards do not establish the promised media preflight.
- Acceptance: apply the same preflight to all three states: new import, resumed own import, operator import. Preserve ownership: refusal must never export an operator's import. Cover positive capacity, insufficient space, foreign/unknown lineage and failed export of an owned import. Require the new cases to fail on this baseline.

## F4 — missing tree enumeration is accepted as proof that no source has work

- Severity: **P1**. Blocking: **yes for truthful skip/current state**.
- Path: `zfs-media-gate.sh:655–670,692–709`.
- Evidence: after a successful source-existence probe, the recursive `zfs list` result is fed into a loop without checking its exit code or requiring a nonempty complete list. Empty output leaves `_work=no`. A matching medium GUID/root-snapshot record then sets `_skip=yes`, calls `mark_current`, and returns 1 as `skipped_nothing_to_do`. A full attach fixture with an empty enumeration and matching record produced **rc=1**, `SKIPPED ... already current`; no child or its written state was verified. Failed enumeration with empty output follows the same path.
- Impact: a transient failed or incomplete enumeration may suppress a needed backup and renew the current/age evidence. A successful root-existence probe does not prove the subtree was read.
- Acceptance: an empty, partial-failing or failed enumeration is unknown and must not permit the no-work skip or advance the current proof. Let the existing engine decide or report a probe failure according to the established contract. Test successful root probe followed by empty output, rc!=0 with no output, rc!=0 with partial output, and a positive complete quiet tree. Include a child with new work and the old-code negative control.
