# REV-20260811-110 — managed-prefix lookup is not relationship-exact

## Finding

The REV-102 F3 residual correctly tightened `source_scope_is_bounded()` so that an unrelated bookmark cleanup or unrelated snapshot-prefix prune cannot certify source retention. However, the helper that supplies the relationship's managed snapshot prefix is still not bound to the exact relationship.

`managed_source_prefix_for_scope()` scans rendered transfer lines and accepts the first `snapget`/`snapsend` line satisfying:

```sh
case "$line" in *"$2"*) ;; *) continue ;; esac
```

That is a substring test. For valid neighbouring remote scopes such as:

- `zfsbackup@10.5.5.5:rpool/data`
- `zfsbackup@10.5.5.5:rpool/data2`

(or parent/child names with one textual scope contained in the other), the line for the second relationship also matches the first scope. If it appears first and carries a different `snapget -m` prefix, the audit can associate relationship A with relationship B's managed family.

`source_scope_is_bounded()` then performs the stronger exact quoted-scope match for `delsnaps`, but compares that prune against the wrong `managed` prefix. Depending on the two patterns, this can produce either a false-green (wrong source prune accepted as bounding the relationship's actual managed snapshots) or a false-missing result.

This violates the property the F3 residual is intended to prove: effective retention must bound THIS relationship's managed snapshot family, not merely a family found on a transfer line whose text contains the scope.

## Required correction

Keep the fix narrow. Do not add a second CONFIG model or new policy state.

Bind `managed_source_prefix_for_scope()` to the exact rendered source argument for the relationship, using the same level of argument identity already required by `source_scope_is_bounded()` (or a small shared exact-token helper). Substring containment is not sufficient.

Preserve the existing fallback only for the genuine "no exact transfer line found" case; a colliding neighbouring line must never satisfy the lookup.

## Minimum discriminating evidence

A targeted regression is sufficient:

1. render two transfer relationships where one source scope is a textual prefix of the other (`...:rpool/data` and `...:rpool/data2`);
2. give them deliberately different `-m` managed prefixes;
3. put the colliding relationship first, so the old substring implementation deterministically selects the wrong prefix;
4. prove the audit classifies each relationship against its own prefix only;
5. include one negative control where a prune that bounds only the neighbouring relationship's prefix must NOT make the requested relationship safe.

No live ZFS or broad destructive campaign is required for this parser/association correction. Under REV-109 policy this should be an L0 targeted regression during iteration; the full affected suite remains L1 for the complete resubmission.

REV-102 remains unclosed: `d747b35` fixes the previous F3 residual but does not yet prove relationship-exact prefix association. REV-108 remains independently open for passive `-e` ownership classification, and REV-109 for targeted test granularity.
