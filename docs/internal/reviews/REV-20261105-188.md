## F1 — unreadable guest or whitelist datasets become an empty warning

- Severity: **P2**
- Blocking: **yes for claiming the new delegated quiesce preflight detects
  uncovered guests reliably**; not a general prohibition on unrelated jobs.
- Affected: `zfs-backup.sh`, `quiesce_whitelist_gaps()` and its call from
  `atomic_replace_and_install()`.

### Contract and evidence

U149-c adds an advisory check when installing a generated cron block with
`-q`. It must name guests whose disks are outside the delegated account's
quiesce whitelist. The warning is the operator's opportunity to correct the
grant before a scheduled `,degrade` run snapshots a guest unfrozen.

The function enumerates both the job's dataset and each whitelisted root with
`while ... done < <(zfs list ...)`. The process-substitution command's status
is never tested. If either `zfs list` fails before producing rows, the loop
looks empty and the function can return 0 with no output. A failure after
partial rows can produce a misleadingly complete-looking guest set. Its
caller warns only when the captured output is nonempty, so the failed check
can be silent.

I extracted the actual function from `main` and ran an isolated, read-only
stub control with one `-R -q auto,degrade` line over `hdd/lxc` and no whitelist.
The stub's healthy answer listed `hdd/lxc/subvol-105-disk-0`: result
`rc=0`, `105 hdd/lxc/subvol-105-disk-0`. The same invoked stub returned 77
without rows: result `rc=0`, no warning rows. A trace confirmed `zfs list`
was called in both cases. No live guest was frozen or snapshotted. The new
U149-c test in `test/zfsbackup/run.sh` covers a healthy ZFS listing and absent
whitelist, but injects no listing failure.

### Required outcome

An unreadable job dataset or whitelist root must be reported explicitly as
**unknown/incomplete**, never as proof that no guests are uncovered. The check
may remain advisory as designed, but the operator must see that its answer
could not be established. Preserve the healthy no-gap and known-gap behavior.

### Acceptance criteria

- [ ] Capture and check each `zfs list` producer status, including failures
  before output and after partial output, for both the job dataset and the
  whitelisted roots. Do not form a complete no-gap answer from partial data.
- [ ] Surface a clear warning through the real install/plan caller when the
  answer is unknown, naming the affected dataset and reason; do not silently
  substitute an empty guest set.
- [ ] Keep root, no-`-q`, successful empty, and known uncovered-guest controls.

### Required verification

- Automated: actual-function and caller regressions with failed `zfs list`
  before and after partial output on each side; assert warning text, final
  status and that no check claims complete coverage. Add a negative control
  that fails on the submitted `63ee92c4` implementation.
- Automated: relevant quiesce, generator and installer suites, syntax,
  `git diff --check`, `./test/impact.sh --verify` and exact-head CI.
- Manual: no production guest or dataset test is authorized by this review.
  Disclose any throwaway-host obligation triggered by the eventual diff.

### Process note

This was missed by the U149-c healthy-path fixture because it asserted the
warning contents only when `zfs list` returned rows. Future preflight reviews
must inject producer failures at every enumeration feeding a safety warning,
then trace the result to the user-facing install message. Documentation and
green CI alone do not prove that path.
