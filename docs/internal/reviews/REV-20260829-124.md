## F1 — P1 BLOCKING — retry after an interrupted media run erases our ownership marker

### Evidence

In `zfs-media-gate.sh`, the `attach` path for an already-imported pool executes:

```bash
rm -f "$OURS" 2>/dev/null || :
```

and then promises that `detach` will leave the pool imported. That is correct
only when another actor imported the pool. It is wrong when `$OURS` already
exists because this package imported it during the previous run and that run was
interrupted after `attach` but before `detach` (process kill, host interruption,
or overlapping retry).

The durable marker is the only fact distinguishing those states. Deleting it
converts a package-owned import into an apparently foreign import. The following
`detach` returns success without exporting, so every later retry can leave the
removable pool active indefinitely while the bracket reports success.

The `mediagate` suite separately covers a fresh import and an already-imported
foreign pool, but not the lifecycle sequence `our attach -> interrupted before
detach -> retry attach -> detach`.

### Acceptance criteria

1. An already-imported pool with a valid existing `$OURS` marker retains package
   ownership across a retry; the successful retry's `detach` exports it.
2. An already-imported pool without our marker remains foreign and is still left
   alone.
3. Add a discriminating lifecycle test that performs our successful `attach`,
   deliberately omits `detach`, then performs another `attach` and `detach`.
   It must prove that the marker survives the second attach, the pool is
   exported, and the marker is removed only after that export. The case must
   fail on `37499663a64797377593675f74144767289d8315`.
4. If the chosen marker format needs stronger pool/run identity to distinguish a
   stale marker from a foreign import, fail closed rather than deleting the only
   ownership evidence and returning success.

## F2 — P2 BLOCKING — `pause-client` says prune is not paused after the branch made it paused

### Evidence

This candidate adds `-L` to generated `delsnaps.sh` lines and makes
`delsnaps.sh` exit before any listing, SSH, or destroy when the relationship is
paused. The PR body correctly presents this as the pause reaching prune.

But `zfs-backup.sh` `cmd_pause_client` still prints the previous limitation:

```text
NOT covered: retention. This relationship's delsnaps lines carry no '-L' and keep pruning on schedule
```

It then warns that a long pause may cost the common base. `gen-cron.sh` also
retains a source comment claiming the `delsnaps` line is never gated. These
statements now contradict the executable behavior and can make an operator take
unnecessary or wrong recovery action precisely while relying on a safety pause.

### Acceptance criteria

1. Update the `pause-client` output to describe the actual boundary: generated,
   labeled transfer, monitor, and prune jobs are paused; an unlabeled manual
   engine invocation remains outside the logical-pause boundary.
2. Remove or correct the stale generator comment and any adjacent validation
   wording that still describes prune as ungated.
3. Add a focused assertion for the operator-facing pause text alongside the
   existing generated-`delsnaps -L` coverage, so code and safety message cannot
   diverge silently again.

## WIP follow-up at `a3cb1e3a2d3c8413b9e0258cc31faa46cd7cb2f6`

F1 remains unmet in the current PR #166 candidate. The new GUID-bearing marker
correctly makes `attach` return 2 when the imported pool does not match the
recorded GUID. However, `gen-cron.sh` deliberately emits `detach` outside the
conditional and therefore runs it after every `attach` result:

```text
attach ...; a=$?; ...; detach ...
```

The real `detach` path checks only that the marker file exists. It does not call
`marker_is_ours` or otherwise compare the recorded GUID with the currently
imported pool before `zpool export "$POOL"`. Thus the bracket can refuse the
wrong same-named medium in `attach`, then immediately export that same wrong
medium in `detach` and remove the marker that records the original ownership.
This is the unsafe action acceptance criterion 4 requires to fail closed.

The reported 72/0 suite does not discriminate this lifecycle. I6 calls the real
`attach` and proves that it returns 2, exports nothing, and keeps the marker, but
then stops without calling the real `detach`. G3 does run the generated bracket,
but both gate verbs are stubs; its detach stub cannot expose the wrong export or
marker deletion. The required control must run the generated bracket, or the
equivalent real `attach 2 -> detach` sequence, against the real gate and prove
that neither the wrong pool nor the ownership evidence is touched.
