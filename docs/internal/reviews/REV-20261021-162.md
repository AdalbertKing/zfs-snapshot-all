## F1 — P1: EXIT cleanup cannot restore `snapdev` after TERM interrupts the locked restore transition

- Severity: **P1**
- Blocking: **yes** for unrestricted browse of zvol snapshots
- Affected: `tui/browse.sh`, `restore_snapdev()`, `restore_snapdev_locked()`, `cleanup()` and the `INT TERM` / `EXIT` traps

### Evidence

`restore_snapdev()` opens and owns the per-dataset `flock`, then calls `restore_snapdev_locked()`. During that function, a TERM is handled by `trap 'exit 130' INT TERM`; Bash subsequently runs the EXIT trap and `cleanup()` calls `restore_snapdev()` again. The nested call opens a second independent file description for the same lock and waits against the lock still owned by the interrupted outer call. On timeout it fails closed, but leaves the zvol exposed.

The reviewer added temporary test-only instrumentation to the existing mock-backed actual entry point. It sends one TERM exactly at the existing `restore` pause, and on re-entry lets cleanup continue rather than sending another signal or pausing again. No production file was modified for publication.

Current implementation (`d89e75a173f39ca878ba2e6fb5b94bd03c328983`):

```text
PASS 19 ...
PASS 20 ...
PASS 21 ...
PASS 22 ...
PASS 23 ...
FAIL 24 SIGTERM podczas przywracania pod blokada -> EXIT sprzata bez samozakleszczenia
  snapdev po SIGTERM: visible (oczekiwano hidden)
browse: PASS=23 FAIL=1
```

### Failure mode and impact

If SIGTERM arrives after the holder marker is removed but before the original `snapdev` value is restored, cleanup waits up to `BROWSE_LOCK_WAIT` (30 seconds by default), reports that it cannot acquire the lock, and exits nonzero while `snapdev` remains `visible`. The valid `orig2` recovery record remains, but the safety property promised by graceful signal cleanup is broken and manual recovery is required. This reopens neither the already-fixed same-dataset race nor the cross-dataset key fix.
