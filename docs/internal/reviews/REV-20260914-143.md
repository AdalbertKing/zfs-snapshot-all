## F1 — P2 BLOCKING — successful SSH stderr is parsed as dataset rows

- Severity: P2
- Blocking: yes
- Affected path: `zfs-backup.sh`, `cmd_list_datasets()`

For a remote host the implementation captures the successful command as:

```bash
rows=$(rux_root_ssh "$host" "${port:-22}" "zfs list ..." 2>&1) || rc=$?
```

It then parses every captured line as tab-separated `name/type/used/avail` data. A legal SSH banner or warning written to stderr while the remote `zfs list` exits zero is therefore converted into a dataset object. A line without tabs becomes a dataset whose name is the diagnostic text, with an empty type and zero sizes. The TUI picker consumes this JSON and defaults to the first item, so it can offer or select a non-dataset string.

### Minimal reproduction

Use an `ssh` stub which:

1. writes `Authorized access only` to stderr;
2. writes `pool/data\tfilesystem\t1024\t2048` to stdout;
3. exits 0.

Run `zfs-backup.sh list-datasets peer --json`.

Expected: exactly one dataset, `pool/data`.  
Actual at the reviewed SHA: `Authorized access only` is also emitted as a dataset because stdout and stderr were merged before TSV parsing.

This is a deterministic shell-stream failure in the exact merged source. The final PR CI was green ([run 34856238525](https://github.com/AdalbertKing/zfs-snapshot-all/actions/runs/34856238525)); its clean-success and failing-SSH cases do not exercise successful stdout together with non-empty stderr.

## Acceptance criteria

1. Keep remote stdout and stderr separate.
2. On exit 0, parse dataset records from stdout only; stderr must never appear in the dataset array.
3. Add the focused success-plus-stderr discriminator above and assert the exact dataset count and name.
4. Preserve the existing nonzero-SSH behavior: nonzero exit, no success JSON, and a useful diagnostic.
5. Report the full implementation SHA, focused discriminator result, `listdatasets` result, TUI result if TUI code changes, `impact.sh --verify`, and exact-head CI.
