## F1 — P1 — `creation | tail -1` does not uniquely define the default recovery point

The planner still derives the default target from the final row of the backup-copy snapshot listing:

```sh
latest="$(printf '%s' "$snaps" | tail -1 | cut -f1)"
latest_guid="$(printf '%s' "$snaps" | tail -1 | cut -f3)"
```

The supplied `snaps` set is ordered by ZFS `creation`. The project has now independently demonstrated that distinct snapshots can share the same `creation` second. `creation` therefore supplies the operator-meaningful capture time, but not a total order. Choosing an arbitrary tied row via `tail -1` can make the destructive primitive restore to a different recovery point from another equally-timestamped candidate without the ambiguity being surfaced.

That violates the fail-closed restore direction: when the program cannot uniquely derive the administrator's intent, it must not invent one.

## Required behavior

Keep `creation` as the semantic time axis for the default/latest backup point; do not silently replace it with local `createtxg`, because receive assigns a new local transaction order and that would change policy from capture time to arrival order.

For the default target:

1. determine the maximum `creation` value;
2. if exactly one snapshot has that value, select it;
3. if multiple snapshots share that maximum capture time and no stronger canonical fact already defined by the Owner contract disambiguates them, fail closed and name the tied candidates rather than selecting by incidental list order.

The same principle must feed the future `--at=TIME` grammar: exact/nearest-time resolution must be deterministic and explicit about ambiguity, but public parser work remains out of scope for this REV.

## Acceptance evidence

- Targeted fixture with two backup snapshots sharing the maximum `creation` but adverse names/order must refuse as ambiguous (or deterministically resolve only if an already-canonical stronger fact is identified and justified).
- A unique maximum continues to select the expected GUID.
- Planner preview must state the ambiguity before any mutation/fence/confirmation.
- No use of `tail -1` over a non-total `creation` order remains in recovery-target selection.
- Existing GUID-proven strategy selection and REV-120 final-state verification remain unchanged.

No broader live campaign is required: the live evidence already supplied for REV-120 proves same-second creation is reachable and that `zfs recv` preserves sender `creation` while assigning local `createtxg`.
