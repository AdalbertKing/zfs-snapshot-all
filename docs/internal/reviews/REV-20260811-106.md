# REV-20260811-106 — source/target retention split depends on a `keep_*` naming convention that profiles do not require

## Scope

Fresh `main` reviewed: `799bd0d7b6998bcf8db98bc70784a91b6dbbffde`.

REV-104 correctly established the required product property for the built-in `default` profile: SOURCE and TARGET start from equal CREATE-time retention values but become distinct native CONFIG template authorities, so an operator can change one side without changing the other.

The current implementation is not profile-agnostic even though the public high-level path accepts `--profile=NAME` and the profile boundary permits valid template names other than `keep_*`.

## Finding F1 — hard-coded `__keep_` text rewriting silently re-couples a valid custom profile

`cmd_local_backup()` creates the SOURCE template family by selecting only rendered template headers matching `__keep_` and then performing textual replacement:

```sh
awk '/^\\[template:/{p=($0 ~ /__keep_/)} p' "$PROFILE_TPL_FILE" \
    | sed 's/__keep_/__src_keep_/g'
...
profile_emit "$PROFILE_PRUNE_FILE" | sed 's/__keep_/__src_keep_/g'
```

That works for the current built-in profile because its prune templates are named `keep_hourly`, `keep_daily`, `keep_weekly`, `keep_monthly`.

But `lib-profile.sh` does not define `keep_*` as part of the profile grammar. A valid profile may instead contain, for example:

```ini
[template:ret_hourly]
    prune_schedule = 21 * * * *
    pattern = automated_hourly
    retain = -H24

[template:ret_daily]
    prune_schedule = 21 * * * *
    pattern = automated_hourly
    retain = -D7
```

with `prune.inc` referencing `ret_hourly,ret_daily`. Such a profile passes the documented naming/field boundary, but the current SOURCE-family extraction matches no `__keep_` section and the `sed` rewrite changes no `use_template` name. The resulting SOURCE `[prune:]` therefore points at the same original template identities as TARGET. The candidate still validates, so the failure is silent: editing TARGET retention can again change SOURCE retention and recreate the constrained-source disk-fill risk REV-102 exists to remove.

The code comment claiming the transform is "namespace-agnostic (works for any --profile)" is therefore false; it is namespace-agnostic but **not template-name-agnostic**.

## Required correction

Preserve the established architecture and do not touch `gen-cron.sh` or frozen transfer/prune engines merely to fix composition.

The CREATE composer must derive the SOURCE retention family from the **actual prune templates referenced by the selected profile's rendered `prune.inc`**, not from a naming convention such as `keep_*`.

Required properties:

1. any profile accepted by the existing profile validator and usable for GFS pruning gets distinct SOURCE-vs-TARGET native template identities;
2. initial resolved values remain equal because SOURCE is copied from the selected profile's actual prune policy;
3. changing only SOURCE affects only SOURCE cron semantics, and changing only TARGET affects only TARGET semantics;
4. missing/unresolvable referenced templates fail closed rather than silently falling back to shared authority;
5. the built-in `default` output remains semantically unchanged from the accepted REV-104 result;
6. remote PULL source-prune composition under REV-102 must reuse the same profile-agnostic split rather than adding a second naming implementation.

Prefer putting the mapping/copy operation at the profile/composition boundary (`lib-profile.sh` or one shared helper) if that avoids a second parser in `zfs-backup.sh`; do not create another configuration representation.

## Minimum evidence

- keep the existing default-profile REV-104 independence tests;
- add a valid synthetic custom profile whose prune template names do **not** contain `keep_`;
- prove its generated candidate has distinct SOURCE/TARGET template identities and equal initial retention values;
- mutate only SOURCE and prove TARGET unchanged;
- mutate only TARGET and prove SOURCE unchanged;
- negative control demonstrating the current `799bd0d...` `__keep_` transform silently leaves the custom profile coupled;
- dependency-selected cascade + `./test/impact.sh --verify`.

No live-ZFS campaign is required for this template-identity compatibility finding; REV-102 retains the destructive live-host obligations.

## Verdict

CHANGES REQUIRED (P1). The built-in `default` profile's REV-104 result remains accepted, but generalized `--profile=NAME` retention composition is not safe until this naming dependency is removed. REV-102 remains OPEN and Phase 5 transactional install remains blocked.
