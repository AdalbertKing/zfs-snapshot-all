## F1 — P1: `new_account_abort` runs recursive home deletion without proving the home was newly created

- Severity: **P1**
- Blocking: **yes** for delegated account creation while this rollback is shipped
- Affected: `deploy.sh`, `new_account_abort()`, and both `useradd -m` call sites guarded by `new_account_drop_inherited_grants()`

### Evidence

Both authorised call sites create the account with `useradd -m` and immediately run the U42 inherited-grant guard. Any `zfs list`, `zfs allow`, or `zfs unallow` failure reaches:

```bash
new_account_abort() {
    if userdel -r "$1" >/dev/null 2>&1; then
        die "... the account was removed again; nothing else was changed ..."
    fi
    ...
}
```

That rollback does not record whether `/home/<account>` existed before `useradd`. Debian documents `useradd -m` as creating the home directory only if it does not exist, while `userdel -r` removes the home directory and its files. See the Debian `passwd` package manual pages:

- <https://manpages.debian.org/bookworm/passwd/useradd.8.en.html>
- <https://manpages.debian.org/bookworm/passwd/userdel.8.en.html>

The destructive scenario is inside U42's own stated threat model:

1. An operator previously ran ordinary `userdel <account>` by hand. U42 explicitly names “a hand userdel” as a source of orphaned numeric ZFS grants; without `-r`, a former `/home/<account>` can remain with files.
2. A later join sees no account and runs `useradd -m`. The already-existing home is not created by this invocation.
3. A real or injected ZFS inventory/ACL/revoke failure enters `new_account_abort`.
4. `userdel -r` recursively deletes the retained home and its files, although the diagnostic states that nothing else changed.

The shipped REV-163 tests confirm that list failure, ACL-read failure, and revoke failure all select `userdel -r newacct`; `userdel` is stubbed, so the tests cannot observe the filesystem deletion. The reviewer independently ran those exact shipped checks: all six REV-163 cases passed. No live account or home directory was created or deleted.

### Failure mode and impact

An availability or permission error while reading ZFS can turn account-enrolment rollback into deletion of files that predate the invocation. Those files may include an old checkout, SSH material, operator-retained recovery data, or unrelated content placed in the conventional home path. The operation is not rollback-owned and is not recoverable from the tool itself.

### Required outcome / acceptance criteria

- [ ] A failed U42 guard removes or disables the just-created account without recursively deleting a home directory that existed before this invocation.
- [ ] Record the pre-`useradd` home state or otherwise make ownership of rollback artifacts explicit; do not infer that a home was newly created merely because the account was newly created.
- [ ] Add a deterministic call-boundary regression with an absent account, a pre-existing home containing a sentinel, successful mocked `useradd -m`, and each of the list/allow/unallow failures. The account must not bypass the guard on re-run, while the sentinel and pre-existing home remain intact.
- [ ] Add the control where the home is genuinely created by this invocation and prove that any cleanup is limited to artifacts owned by this invocation.
- [ ] Cover failure of account rollback with an actionable, non-destructive manual command. The message must not instruct `userdel -r` when ownership of the home is unproven.
- [ ] Negative control against `22f38474d16e2439514d4f209d16f1b27f67021e` must show that the pre-existing-home case selects `userdel -r` and would remove the sentinel.
- [ ] Preserve REV-163's fail-closed ZFS read handling and REV-164's fail-closed leave/scope logic; run the focused account-creation/deployment suites, `impact.sh --verify`, and CI with the exact follow-up SHA.

### Evidence boundary

This finding combines the exact shipped command/call ordering with the documented semantics of the Debian account-management tools used by supported hosts. A temporary/mock call-boundary regression is sufficient and safer than a live destructive test. No production implementation change is made by the reviewer.
