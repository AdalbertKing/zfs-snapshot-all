# REV-20260811-107 — remote source retention is regenerated from profile after CREATE

## Scope

REV-102 step 3 remote-PULL source retention as merged at `d8febbdab1487d2590eb00b4feab854bf562a7d2` and submitted by `1a86d379fb144b4b015fe93b1b87ff097ccddbae`.

## Finding F1 — endpoint reactivation discards installed SOURCE policy

REV-102's owner-approved contract is explicit: the preset may initialize SOURCE and TARGET from the same values at CREATE, but after rendering CONFIG v4 holds **two independent native policies**. The administrator may edit either independently, and after installation CONFIG v4 is runtime truth; there must be no runtime re-coupling through the profile.

The step-3 implementation deliberately violates that contract for remote PULL. On every activation it removes this relationship's remote source `[prune:account@host:dataset]` sections and regenerates them from the current profile/source template family. The implementation notes and updated regression test explicitly accept that a hand-edit to remote source retention is discarded on reactivation.

The reason given — the section header contains topology and therefore must move when the endpoint moves — justifies changing the **scope/header and SSH transport facts**, not regenerating the policy body. This is the same architectural distinction already enforced by REV-089 for dataset topology: topology may move while installed policy remains authoritative.

Concrete failure:

1. CREATE proposes SOURCE = TARGET = 24H/7D/4W/12M.
2. Administrator edits only remote SOURCE retention in canonical CONFIG to 6H/2D because the production source is space-constrained; TARGET remains 24H/7D/4W/12M.
3. Ordinary endpoint/reactivation operation runs.
4. Current code deletes the installed remote source prune and recreates it from the profile, silently restoring the profile ladder and losing the administrator's 6H/2D policy.

That breaks both REV-102 policy independence and the established CREATE-only / CONFIG-truth architecture.

## Required correction

Preserve the installed remote source-prune **policy semantics** on ordinary reactivation/endpoint change. Move only topology-derived facts required by the endpoint change: remote scope/header and its SSH transport fields. Do not reconstruct retention from the profile after CREATE.

A first CREATE may generate the source policy from the preset. An explicit previewed migration may add missing source policy. Neither rule authorizes ordinary reactivation to regenerate an existing policy.

Keep the implementation minimal: no new representation, inheritance, drift manager, or source-profile authority. If renaming the remote `[prune:]` section requires rebuilding text, rebuild from the installed section as the source of truth, changing only topology fields.

## Required evidence

Smallest discriminating regression is sufficient:

- create a remote-PULL relationship;
- edit SOURCE retention only to values different from TARGET/profile;
- change endpoint/reactivate;
- prove source scope/SSH moves to the new endpoint while the edited SOURCE retention is byte/semantically preserved;
- prove TARGET remains unchanged;
- negative control against `d8febbd` must fail this property;
- run the dependency-selected cascade and `./test/impact.sh --verify`.

No new destructive live-ZFS campaign is required for this finding: the destructive remote path was already live-proven under REV-102; this defect is config composition/preservation. Existing REV-102 live obligations remain separate.

## Interaction with REV-102

REV-102 cannot close while this finding is open. Its submitted implementation is also explicitly incomplete on the already-required migration/audit path and on the unresolved continuity/bookmark/recursive evidence. Those are not waived by this review.

## Verdict

CHANGES REQUIRED (P1). Remote source retention is correctly bounded and live-proven, but its policy ownership is wrong after CREATE. CONFIG v4 must remain execution truth.
