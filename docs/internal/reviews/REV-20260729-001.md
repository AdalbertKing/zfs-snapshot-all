## Executive assessment

The ZFS lifecycle logic, operational commentary, and dependency-aware test design are unusually strong for a Bash backup toolkit. The project records real production failures and converts many of them into explicit contracts.

The current pairing and delivery path nevertheless contains one critical trust-boundary defect and several high-priority correctness or operational-safety defects. The pairing feature should not be deployed to additional untrusted hosts until F1 is closed. The project should also stop treating the moving `main` branch as an automatic production release channel before broader fleet rollout.

This review did not execute root/ZFS/two-host integration campaigns. Findings below are derived from the reviewed source and documented behavior. Each finding states the verification needed for closure.

## F1 — `--join` executes pairing-package configuration as root

- Severity: **P0**
- Blocking: **yes**
- Status: `OPEN`
- Affected: `deploy.sh`, `do_join()`, pairing archive extraction and `peer.conf` ingestion

### Evidence

The reviewed flow:

1. requires `deploy.sh` to run as root;
2. creates a temporary directory;
3. runs `tar -C "$workdir" -xzf "$JOIN_PACKAGE"`;
4. checks that `peer.conf` and `pubkey.pub` exist;
5. executes `. "$workdir/peer.conf"`.

A shell `source` operation does not parse assignments as inert configuration. It executes arbitrary shell syntax contained in the file with the privileges of the calling process, which here are root.

The archive is also extracted before validating that it contains only the two expected regular files with safe relative paths. A hostile or corrupted archive can therefore attempt path traversal, absolute paths, symlinks, unexpected file types, or additional payloads.

### Failure mode

A modified pairing package can execute arbitrary commands as root on the host running `--join`. The threat does not require a parser bug: command execution is the documented behavior of `source`.

This violates the feature's stated purpose of establishing trust between hosts that have no prior trust relationship. Manual transfer alone does not turn an executable configuration format into safe data.

### Required outcome

Treat the pairing package as untrusted structured data. It must be validated before extraction or use, and configuration values must be parsed without shell execution.

### Acceptance criteria

- [ ] `do_join()` never uses `source`, `.`, `eval`, command substitution from package values, or an equivalent execution path for package metadata.
- [ ] Archive preflight accepts exactly two members: `peer.conf` and `pubkey.pub`.
- [ ] Both members must be regular files with relative, top-level names; reject absolute paths, `..`, directories, hard links, symlinks, devices, FIFOs, duplicate names, and extra members.
- [ ] Extraction occurs into a private `0700` temporary directory and does not preserve archive owner, group, mode, ACL, xattr, or special-file semantics.
- [ ] `peer.conf` is parsed by an allow-list schema with exactly the expected keys.
- [ ] Duplicate keys, unknown keys, malformed lines, empty required values, embedded newlines/control characters, and values outside their declared grammar are rejected.
- [ ] `PEER_CONF_ROLE` accepts only `pull|push`; `PEER_CONF_AS` only `root|delegated`; port is numeric and within `1..65535`.
- [ ] Dataset, target, account, and initiator-label values are validated for the syntax actually supported by the scripts before any user, key, dataset, or manifest is created.
- [ ] `pubkey.pub` is validated as exactly one acceptable SSH public key record; no options, second key, or trailing command text is accepted.
- [ ] All validation completes before the first persistent mutation.
- [ ] Failure removes the temporary directory and leaves no account, `authorized_keys` entry, ZFS delegation, dataset, or manifest behind.

### Required verification

Automated regression cases must prove rejection without side effects for at least:

- `peer.conf` containing `touch /root/REV-F1-PWNED` or command substitution;
- archive member `../../etc/cron.d/payload`;
- absolute archive path;
- symlink named `peer.conf`;
- duplicate `peer.conf` members;
- extra archive member;
- unknown and duplicate configuration keys;
- invalid role, account, dataset, target, and port;
- two public keys or an `authorized_keys` option prefix.

A positive fixture must complete parsing and produce the same normalized values as the current legitimate package.

### Notes and uncertainty

Cryptographic signing of the package would improve authenticity but does not replace safe parsing. The parser and archive constraints are required even for a signed package.

## F2 — `gen-cron.sh` can emit unsupported `-q` for `snapget.sh`

- Severity: **P1**
- Blocking: **yes for affected pull jobs**
- Status: `OPEN`
- Affected: `gen-cron.sh`, dataset send generation; `snapget.sh` option contract

### Evidence

For a dataset section with `src`, `gen-cron.sh` resolves the direction as `pull`. It then resolves `quiesce` and calls `maybe_add_quiesce()` without conditioning that behavior on the direction. This can add `-q <mode>` to the generated flags.

The reviewed `snapget.sh` option parser and documentation do not define `-q`. The repository's own commit history records a live confirmation: generated pull execution fails with `illegal option -- q`.

### Failure mode

A syntactically valid INI configuration can generate a cron line that fails every run before performing a pull. The generator therefore promises a supported configuration that the target executable rejects.

### Required outcome

Do not emit a quiesce promise for pull jobs unless real pull-side quiescing is designed and implemented end to end.

### Acceptance criteria

Preferred minimal fix:

- [ ] For `direction=pull`, `quiesce` omitted, blank, or `no` is accepted and emits no `-q`.
- [ ] For `direction=pull`, `quiesce=agent|sync|auto` causes `gen-cron.sh` to fail with a clear diagnostic naming the dataset, tier, direction, and unsupported value.
- [ ] Push behavior remains unchanged.
- [ ] No compatibility alias is added to `snapget.sh` that silently accepts and ignores `-q`.

An alternative full implementation is acceptable only if it defines which host and guest are quiesced, how remote Proxmox commands are authorized, and how thaw is guaranteed across SSH failure. That is larger than the minimal correction and should be a separate design review.

### Required verification

- [ ] Golden or negative fixture: pull + `quiesce=auto` fails with the expected message.
- [ ] Golden fixture: pull + `quiesce=no` emits a valid `snapget.sh` line without `-q`.
- [ ] Existing push quiesce fixtures remain unchanged.
- [ ] Contract check proves every flag generated for pull parses in `snapget.sh`.

## F3 — resume and in-flight state filenames can collide and ignore job identity

- Severity: **P1**
- Blocking: **yes**
- Status: `OPEN`
- Affected: `lib-zfs-snap.sh`, `resume_state_file()`, `inflight_snap_file()`

### Evidence

Both state-file helpers derive a filename from the target dataset by replacing `/` with `_`.

This mapping is not injective. For example:

- `tank/a_b`
- `tank/a/b`

both map to `tank_a_b`.

The state key also omits the `-j` identifier, even though `-j` explicitly creates independent jobs with separate locks and bookmarks for the same source/target pair. Those independent jobs can therefore share resume-attempt and in-flight-snapshot state.

The main invocation lock already uses an MD5 hash of source, target, and identifier, demonstrating that a collision-resistant relationship key is available conceptually.

### Failure mode

One job may:

- increment or reset another job's resume-attempt counter;
- abandon resume state earlier or later than intended;
- read, release, or clear another job's recorded in-flight snapshot;
- behave differently solely because another legal dataset path normalizes to the same filename.

### Required outcome

Use one stable, collision-resistant state key derived from the complete logical job identity, consistently for every per-job state file.

### Acceptance criteria

- [ ] Introduce a shared state-key function using length-safe or NUL-delimited input and a stable hash.
- [ ] Include script/direction namespace, source, target, and `IDENTIFIER` in the key, matching the independence semantics documented for `-j`.
- [ ] Resume-attempt and in-flight-snapshot files for the same logical job use the same key.
- [ ] Different legal dataset paths cannot collide through character replacement.
- [ ] Different `-j` identifiers do not share state.
- [ ] Existing stale state files are handled deliberately: migrate safely when possible or document that they are ignored/cleaned after upgrade. Do not accidentally interpret an old ambiguous file as a new job's state.

### Required verification

- [ ] Unit test proving distinct paths `tank/a_b` and `tank/a/b` produce different files.
- [ ] Unit test proving identifiers `hourly` and `offsite` produce different files for the same pair.
- [ ] Unit test proving the same logical job produces a stable key across invocations.
- [ ] Integration test or stubbed test proving one job cannot reset or release another job's state.

## F4 — production hosts automatically follow mutable `main`

- Severity: **P1**
- Blocking: **owner decision**
- Status: `OPEN`
- Affected: `deploy.sh`, Phase 7 auto-pull cron deployment

### Evidence

`deploy.sh` installs an hourly root crontab line that runs `git pull --ff-only origin main` in the production checkout. Backup cron jobs later execute the scripts from that checkout as root.

The repository's current development pattern includes multiple same-day corrective commits to operational code. A fast-forward only protects history shape; it does not prove release approval, test completion, or deployment suitability.

### Failure mode

Any merged regression, accidental commit, compromised maintainer account, or insufficiently tested AI-generated change automatically propagates to every enrolled host. The next scheduled backup or deployment invocation executes the new code as root. There is no staged rollout, explicit release approval, pinned version, health gate, or automatic rollback.

### Required owner decision

Choose and document one production delivery policy. Recommended default:

- production tracks a signed or explicitly approved release tag/commit;
- `main` remains a development branch;
- updates are an explicit deploy action with preflight tests and a recorded previous revision for rollback.

### Acceptance criteria

- [ ] `deploy.sh` does not silently enroll production hosts into following `main` by default.
- [ ] The selected revision is explicit and visible in `--check-only` output.
- [ ] Update performs fetch, revision verification, dependency-free smoke tests, and only then switches the active revision.
- [ ] Previous known-good revision is retained or recorded for one-command rollback.
- [ ] Tracking mutable `main`, if retained at all, requires an explicit high-risk opt-in with a warning.
- [ ] Documentation distinguishes development branch, release artifact, update, rollback, and fleet rollout.

### Required verification

- [ ] Fresh deployment test proves default install is pinned.
- [ ] Upgrade test proves a failed smoke test leaves the active version unchanged.
- [ ] Rollback test restores the previous revision without network access.
- [ ] `--check-only` reports desired revision, active revision, dirty worktree, and drift.

### Notes and uncertainty

This is partly a risk-policy decision, so only the owner can accept the current behavior. The reviewer recommends changing it before adding more production hosts or multiple autonomous contributors.

## F5 — no automated PR gate for dependency-free tests and contract graph

- Severity: **P2**
- Blocking: **no for this documentation PR; required before scaling AI collaboration**
- Status: `OPEN`
- Affected: repository process, GitHub Actions, branch protection

### Evidence

The repository contains a valuable dependency graph and several suites that require only Bash and coreutils, but the reviewed repository has no workflow that runs them automatically for Pull Requests. There is also no enforced PR-only path visible in repository activity; recent development is committed directly to `main`.

### Failure mode

The project can document a required suite while merging a change that never ran it. Two AI agents working asynchronously increase the probability of contract drift, fixture blessing, and direct-to-main regressions unless the repository enforces a shared gate.

### Required outcome

Create a fast, deterministic PR workflow for all tests that do not require a real ZFS pool or second host. Keep privileged integration tests separate and explicit.

### Acceptance criteria

- [ ] GitHub Actions runs on every PR and push to `main`.
- [ ] It performs Bash syntax checking for every tracked shell script.
- [ ] It runs `./test/impact.sh --verify`.
- [ ] It runs the dependency-free impact, gen-cron, quiesce, and tune suites.
- [ ] The workflow fails on an untracked shell script missing from `test/deps.conf`.
- [ ] Workflow permissions are read-only except where strictly required.
- [ ] No untrusted PR code receives production secrets or access to production/self-hosted ZFS hosts.
- [ ] `main` requires the workflow and Pull Request review before merge.
- [ ] Root/ZFS/remote/destructive obligations remain visible in the PR template or implementation response; a green lightweight workflow must not imply they ran.

### Required verification

- [ ] Deliberately broken syntax fails CI.
- [ ] New unregistered `.sh` file fails graph verification.
- [ ] Changed golden output without matching expected behavior fails.
- [ ] Normal documentation-only change completes quickly and does not require privileged runners.

## F6 — README component versions drift from executable versions

- Severity: **P3**
- Blocking: **no**
- Status: `OPEN`
- Affected: `README.md` component table and executable `VERSION` constants

### Evidence

At the reviewed base, README reports older versions than the scripts themselves for at least:

- `snapsend.sh`;
- `snapget.sh`;
- `gen-cron.sh`.

### Failure mode

Operators cannot reliably tell whether the documentation describes the checkout they are running. Manual duplication guarantees future drift.

### Required outcome

Remove duplicated version maintenance or verify it automatically.

### Acceptance criteria

One of:

- [ ] remove versions from the static README component table and direct users to each executable's `-V`; or
- [ ] generate/update the table from executable output and fail CI when it differs.

The chosen mechanism must not execute privileged or mutating code merely to read a version.

### Required verification

- [ ] A deliberate version mismatch fails the documentation check, or the table no longer duplicates versions.
