# REV-20260806-047 — pair-gate audit logging can disappear silently

**Reviewed head:** `6914c11cf7142f1eccdeeebba86d6d74dbe1458b`  
**Scope:** hard-disable campaign, peer-side `zfs-pair-gate.sh`, live checkpoint follow-up  
**Response path:** `docs/internal/reviews/responses/REV-20260806-047.md`

## Verdict

**CHANGES REQUIRED.** The stderr-noise regression found live is fixed, but the replacement logging path is fail-open in a different way: when `logger(1)` exists but cannot deliver to syslog, the code does not execute the advertised file fallback. The outer `|| :` then hides the failure and the gate proceeds with no audit record.

This does not weaken the DISABLED decision itself, but it breaks the stated audit contract at the security boundary and must be corrected before the `pairgate-live` checkpoint is accepted.

## F1 — fallback is selected by executable presence, not delivery success

Current shape in `gate_log()`:

```sh
if command -v logger >/dev/null 2>&1; then
    logger ...
else
    printf ... >> "$GATE_LOG"
fi
```

On hosts where `logger` is installed but syslog/journald is unavailable, its socket is absent, or `logger` returns non-zero, the `else` branch is never reached. The surrounding subshell redirects stderr and ends with `|| :`, so this becomes a silent loss of the audit event.

The implementation comment and commit message both describe "syslog first, falling back to the file". The code currently means "syslog when the executable exists; file only when it does not exist".

### Required correction

Attempt `logger`; only when that invocation fails, attempt the file append. Preserve the newly established caller contract:

- logging failure must never alter the gate's decision or exit code;
- logging diagnostics must never reach caller stdout/stderr;
- a failed syslog attempt must exercise the file fallback;
- if both sinks fail, the gate may continue silently as documented best-effort behavior.

## F2 — tests do not prove both branches

The new tests vary `GATE_LOG`, but on a machine with `logger` available they exercise only the syslog branch; the unwritable file path is irrelevant. On a machine without `logger`, they exercise only the file branch. Therefore `pairgate 24/24` does not prove the claimed fallback behavior.

### Required tests

Add deterministic PATH-controlled stubs covering at least:

1. `logger` succeeds — file sink is not required and caller remains silent;
2. `logger` exists and fails — file sink receives exactly one bounded record;
3. `logger` fails and file sink also fails — command/refusal result is unchanged and caller sees no logging noise;
4. refusal stderr still contains exactly the single refusal line under cases 2 and 3.

Include a negative control showing the logger-fails/file-writable case fails against `6914c11`.
