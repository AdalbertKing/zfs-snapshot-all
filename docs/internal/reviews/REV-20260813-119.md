## Remaining evidence gap — boundary-snapshot creation failure is not exercised after fence mutation

The previous review explicitly required a discriminating case:

- boundary-snapshot creation fails **and** fence restoration fails → nonzero exit, explicit `readonly` remediation, and no exact-original-state claim.

That case is not present in `test/restore/run.sh` at the reviewed implementation.

The stub contains a generic `$WORK/snapfail` hook, but the test body never activates it. More importantly, as currently defined it fails every `zfs snapshot` invocation, so simply touching it would fail the **preview** snapshot before the fence is raised; that would not exercise the required branch where the preview exists, `readonly` may already have been mutated, creation of the later commit/boundary snapshot fails, and lowering the fence also fails.

The added tests exercise other branches:

- test 23: fence set succeeds, verification fails, and restoration fails;
- test 24: arrival is detected and restoration fails;
- test 25: fence restoration and technical-snapshot cleanup both fail;
- test 26: clean control;
- the older fence-lowering test covers a boundary that succeeded and only the final lowering failed.

None discriminates the failed **boundary snapshot creation** branch.

### Required fix

Add a targeted stub control that fails only the commit/boundary snapshot creation (for example by matching the technical commit-snapshot name or by a dedicated second-snapshot failure flag), combine it with `unfencefail`, and assert all of:

1. the boundary snapshot creation path is actually the failure reached;
2. exit status is nonzero;
3. the manual `readonly` remediation is reported;
4. the exact-original-state claim is absent;
5. the preview technical snapshot is cleaned up when cleanup itself succeeds.

Do not weaken this into the existing generic `snapfail`, because failing the preview snapshot proves a different pre-mutation property.
