# REV-20260813-119 — Phase 7 destructive-recovery gates

Reviewed implementation: `d0aacdce5edefe1d7a8232096a13e4d348b0f551`

Reviewer verdict: **CHANGES REQUIRED**

The F1.1–F1.4 delivery materially improves the gate and independently closes three of the four residuals from the previous round. One F1.2 residual remains on failure paths after the `readonly` property may already have been changed.

## Accepted in this round

- **F1.1 accepted:** snapshot arrival is now detected by explicit snapshot-set difference rather than wall-clock ordering. This removes the same-second ordering false-green. An intervening snapshot may shorten the later `written` interval, but it is itself in the set delta and therefore forces refusal.
- **F1.3 accepted:** `local`, `received`, and inherited provenance now take different restoration paths; `received` uses the received-value restore mechanism rather than becoming a local override.
- **F1.4 accepted for technical-snapshot cleanup:** cleanup now returns status and the final clean-state claim is conditional on successful removal of run-owned technical snapshots.

## F1.2 residual — failed fence restoration is ignored before a clean-state claim

The implementation correctly splits capture from mutation and, if `restore_fence_raise()` fails, attempts an unconditional restoration because the property change may have succeeded before verification failed.

However, several post-mutation failure branches still discard the result of that restoration attempt (`restore_fence_lower ... || true`) and then call `restore_die_after_cleanup()`. That helper only knows whether technical snapshots were removed. If snapshot cleanup succeeds, it appends the statement that the source is exactly in its pre-command state even when restoring `readonly` just failed.

The same shape exists after a failed boundary snapshot and on the detected-arrival refusal path. Therefore a production dataset can still be left with the wrong `readonly` state while the operator receives a false exact-state guarantee.

### Required property

Once the fence may have been mutated, final status must combine **both** independent cleanup facts:

1. whether the original `readonly` value/provenance was restored; and
2. whether every run-owned technical snapshot was removed.

If either fails, fail loudly, preserve the precise manual-remediation message, and never claim the source is exactly as before. Do not hide a failed fence restoration behind `|| true` on any exit path that later emits a clean-state claim.

### Regression evidence required

Add discriminating tests for at least:

- fence set succeeds, verification fails, restoration also fails, technical-snapshot cleanup succeeds → nonzero exit, explicit readonly remediation, **no** exact-original-state claim;
- boundary-snapshot creation fails and fence restoration fails → same property;
- arrival is detected and fence restoration fails → same property.

A control where restoration and snapshot cleanup both succeed must retain the exact-original-state message.
