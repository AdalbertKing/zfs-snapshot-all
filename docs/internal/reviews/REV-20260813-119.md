## F1 — P1 — confirmation is specified before the exact live-loss set is captured

The revised `docs/design/destructive-recovery-contract.md` specifies this order for the future destructive path:

1. resolve / preview;
2. explicit destructive confirmation;
3. snapshot the live source as a measurement;
4. rollback/discard and receive.

That ordering does **not** satisfy the authoritative Owner property: show exactly what will be lost **before** destructive confirmation.

REV-118 already proved why: `written=0` can lag the open txg. A live write can therefore exist without appearing in the read-only preview. The proposed post-confirmation snapshot would capture that write only after the operator has already approved destruction. It improves the after-the-fact measurement, but it cannot retroactively make the confirmation informed.

There is also a TOCTOU form of the same defect: even when the preview was accurate at time T1, the source can acquire a new write or snapshot before the destructive boundary. Destroying it without a fresh, operator-visible loss set would discard state that was never approved.

### Required property

Before any destructive execution slice can land:

- the exact state that would be discarded must be captured/measured and shown **before** confirmation;
- the implementation must establish a commit-boundary check so that a source change after the preview/confirmation cannot be silently included in the destruction;
- if the source changes after the approved preview, fail closed and re-preview/re-confirm rather than destroy the new state;
- preserve the Owner's zero-choice policy: do not reintroduce `preserve-source` vs `discard-source-changes` or transport-policy choices;
- this fix remains below the public CLI boundary while the grammar discussion is open.

A pre-confirmation technical snapshot may be one possible implementation technique, but it is not automatically sufficient: the code still needs to prove that state created after that snapshot cannot cross the destructive boundary unnoticed. Do not call a temporary snapshot a preserved/safety copy if the restore will destroy it.

### Regression evidence required

Add a test that distinguishes the dangerous race from the clean case. At minimum, model state appearing after the first preview and prove that the destructive path **refuses/re-previews** instead of proceeding under the earlier approval. The test must fail if a post-confirmation snapshot merely measures newly arrived state and then destroys it.
