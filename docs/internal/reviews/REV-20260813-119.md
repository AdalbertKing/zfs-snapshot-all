Reviewer verdict: **CHANGES REQUIRED**

The new source write fence is directionally correct and closes the ordinary-write window that remained after the previous review. Exact routing head `4f462c0b9d19d17904d635616d7b88d3cbcc2ce2` is green. The same F1 acceptance property still has four residual correctness gaps.

## F1.1 — same-second snapshot arrival

The boundary check decides that a snapshot is new by its position after the preview snapshot in a list sorted by wall-clock creation time. That is not a trustworthy total order for snapshots created in the same second. A later snapshot can therefore escape the unexpected-snapshot set. An intervening snapshot also changes the interval represented by the later written-data measurement, so this can become a false-green rather than only a display problem.

Required: compare snapshot identities/sets explicitly or use a true creation-order fact and prove the set delta. Add a regression where an unexpected snapshot is created after the preview within the same wall-clock second.

## F1.2 — partial fence acquisition

Fence acquisition changes the source property and only afterwards verifies it. If the property change succeeds but verification becomes unreadable, the helper returns failure without giving the caller enough saved state to restore the previous setting. A production source can therefore be left read-only by a failed acquisition path.

Required: make acquisition rollback-safe after every possibly successful mutation. Test successful property change followed by failed verification and prove the old state is restored, or report the exact leftover state and remediation loudly.

## F1.3 — received property provenance

The restore helper preserves the value for a previously received property but converts its source into a local override. Value equality is not exact state restoration.

Required: preserve property provenance as well as value. Add a received-source regression.

## F1.4 — cleanup truthfulness

Technical-snapshot cleanup warns on failure but returns success, after which some callers state that cleanup succeeded or that the source is exactly back in its original state.

Required: propagate cleanup failure into final status and never claim clean/original state while a run-owned technical snapshot remains.
