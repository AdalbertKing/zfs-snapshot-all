# REV-20260813-119 — Phase 7 destructive-recovery gates

Reviewed implementation: `e84f4bd876da4bc974ebe4f57b90ee71efa20e65`
Reviewer verdict: **CHANGES REQUIRED**

The internal-only placement remains correct and the implementation materially improves informed confirmation: it takes a technical preview snapshot before asking for approval, measures the live delta at a committed point, detects writes/snapshots that arrived before a second commit-boundary snapshot, fails closed on unreadable arrival state, and cleans up its own technical snapshots. The control test is also valuable because it prevents an always-refuse implementation from satisfying the race tests.

## F1 — P1 — final destructive boundary is still not fenced

The implementation now executes this sequence:

1. take preview snapshot P1;
2. show the P1-derived loss set;
3. operator confirms;
4. take commit snapshot P2;
5. verify no state arrived between P1 and P2;
6. remove the technical snapshots / future destructive execution follows this check.

This closes the original read-only/TXG gap and the P1→P2 TOCTOU window, but it still does **not** prove the required property at the destructive commit boundary.

A write can arrive **after P2/check and before rollback/destruction**. That write is outside the approved loss set and would be destroyed by the future rollback. P2 therefore proves the approved state only through P2; it does not fence the source for the destructive transition that follows.

This is not hypothetical parser wording: `restore_replace_internal()` performs no write/execution fence after validating `arrived`/`unexpected`. The current slice stops before destruction, so it is safe today, but the execution slice may not be attached to that unchecked gap.

### Required property

Before destructive execution can land:

- the exact state that would be discarded must be captured/measured and shown before confirmation — **satisfied by e84f4bd**;
- changes between the approved preview and final validation must fail closed and force re-preview/re-confirm — **satisfied by e84f4bd for the P1→P2 interval**;
- after final approved-state validation, new source state must be unable to appear and be silently destroyed before/during the destructive transition — **NOT YET SATISFIED**;
- establish an actual write/execution fence or an equivalent atomic construction around the final validation + rollback/destruction boundary;
- fail closed if that fence cannot be established or released;
- if the fence changes source availability or another operator-visible property, preview/output and cleanup semantics must state that accurately;
- do not solve this with an ordinary-user policy flag. This is internal execution safety under the existing zero-choice intent.

The exact mechanism is an implementation choice. The review does not prescribe a particular ZFS property, mount manipulation, service stop, or host-level lock; it requires proof of the safety property rather than a named mechanism.

### Regression evidence required

Keep the current tests for:

- state appearing after P1 but before P2 → refuse/re-preview;
- unexpected snapshot appearing in that interval → refuse/re-preview;
- clean P1→P2 interval → proceed to the next internal boundary.

Add a discriminating test/proof for the remaining window:

- state attempts to appear after final validation but before rollback/destruction → it is prevented/fenced or otherwise provably cannot be silently destroyed.

The test must fail if the implementation merely validates P2 and then leaves an ordinary writable source until rollback.
