## F1 — P1 — rendered native fragments are accepted broadly but applied through a hand-written field map

The agreed profile contract is intentionally simple: a profile is native CONFIG v4 fragments. `lib-profile.sh` validates `dataset.inc` against the real `gen-cron.sh --dump-fields` dataset schema, subtracting only relationship-owned fields; dataset `recursive=no|flat|atomic` is explicitly profile-owned. The design says the high-level layer may copy or reject native fragment fields, but must not grow a second semantic mapping layer.

B1 step 2 violates that boundary in `emit_client_sections()`.

After `profile_render_fragment()` has produced `PROFILE_DS_FILE`, the runtime does not compose the rendered fragment. It extracts only:

```text
use_template
```

with `profile_value()` and writes that one field manually. Every other dataset field that the profile boundary currently accepts — including the already-agreed `recursive` policy — is silently dropped.

The prune side repeats the same pattern: `PROFILE_PRUNE_FILE` is not composed as a native fragment; the runtime manually extracts only `use_template`, `gfs`, and `gfs_pattern`. A future native profile-owned prune field can therefore validate successfully at the one declared profile boundary and still have no effect at runtime.

The built-in `default/dataset.inc` currently contains only `use_template`, deliberately preserving the old byte shape, so the current default fixture hides the defect. That makes this exactly the kind of false-green B1 must not freeze: the validator and renderer promise a generic native-fragment contract while the first production consumer implements a private three/four-key subset.

This is also contrary to the Owner's reduction rule. A generic validated fragment followed by a hand-maintained key-to-key extractor is more machinery, not less; every future native field would require another edit in `zfs-backup.sh` even though `gen-cron.sh` already owns its semantics.

### Required correction for F1

Keep the ownership split, but make the production composition generic over the validated rendered fragment:

- every accepted/rendered dataset policy field must reach the generated `[dataset:*]` section unless a named orchestration-owned collision is explicitly refused;
- every accepted/rendered prune policy field must reach the generated `[prune:*]` section;
- relation-owned fields (`src`, `flags`, `pair_label`, `notify`, concrete section path) remain injected by orchestration;
- prune topology `recursive=yes|no` remains orchestration-owned and is already forbidden in `prune.inc` by the profile boundary;
- namespaced `use_template` rewriting remains inside `lib-profile.sh` as now;
- do not replace the current small field map with a larger field map. The point is to remove the duplicate semantic list.

Comments/formatting may be handled separately if byte-identity requires it; the required property is that all validated policy fields survive composition without a second allow-list in `zfs-backup.sh`.

### Minimal proof for F1

Use one discriminating profile, not a catalog campaign:

1. copy the built-in default into a temporary profile;
2. add one already-valid profile-owned native field to `dataset.inc`, preferably `recursive = flat`;
3. prove the real `profile_validate_dir()` accepts it;
4. run the real `zfs-backup.sh` composition path used by `emit_client_sections()`;
5. assert the resulting managed `[dataset:*]` section contains the effective `recursive = flat` and the real `gen-cron.sh` accepts/renders that candidate;
6. negative control: the same assertion against reviewed implementation `0dccb0be...` must fail because the field is currently dropped;
7. keep the current default byte/semantic regression and pre-GFS refusal tests green.

One additional analogous prune field is useful only if the schema has a stable profile-owned field beyond the three currently exercised; do not invent a field merely to increase PASS count.

## F2 — P1 test graph — `lib-profile.sh` changes do not route to the `zfsbackup` runtime suite

B1 step 2 creates a new production dependency:

```text
zfs-backup.sh -> lib-profile.sh
```

but `test/deps.conf` still declares:

```text
[file:lib-profile.sh]
suites = profiles
```

while `zfs-backup.sh` has `suites = zfsbackup`.

Normally `impact.sh` derives source edges and would make a library change inherit every consumer's obligations. Here it cannot: `zfs-backup.sh` sources the library through the indirect variable form:

```bash
LIBPROFILE="$SCRIPT_DIR/lib-profile.sh"
. "$LIBPROFILE"
```

whereas `derive_source_edges()` only recognises source expressions of the `$DIR/file.sh` shape. The new edge is therefore invisible to the automatic parser. `--verify` only verifies the source edges it successfully discovers; it cannot complain about an edge it never parsed.

Result: a future change to rendering/validation in `lib-profile.sh` can select only `profiles`, even though B1 has made `zfs-backup.sh` its production consumer. A green profile suite would not prove the high-level runtime still consumes the changed output correctly.

### Required correction for F2

Make the dependency explicit in the graph or make the source-edge derivation understand this real sourcing form. Choose the smaller durable solution; do not create a special test runner.

Acceptance property:

```text
impact plan for a lib-profile.sh change
=> profiles + zfsbackup (and their normal transitive/contract obligations)
```

Add a targeted impact regression for that property and run `impact.sh --verify` without piping away its exit status.

The latest routing commit explicitly records that a `--verify | tail -1` invocation masked a GRAPH DRIFT. That is evidence that the gate invocation itself must preserve `--verify`'s status; PASS text is not enough.
