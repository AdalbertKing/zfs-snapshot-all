**APPROVED on implementation `20f333d9d96de3b2e814d6cd87a86cfe515d3568`.**

The original Phase 2 delivery correctly identified a missing CREATE-only property, but its first implementation made profile content a standing runtime authority and compared raw template text. The submitted correction resolves both findings without adding a profile-drift framework.

## F1 — resolved — collision checking is CREATE-time only

The original bad shape put the collision comparison inside `ensure_cron_config()` for every activation/re-activation. The corrected implementation adds `check_new_template_collision` and `cmd_activate_client()` passes it only for a genuine first activation (`STATE=endpoint_verified`). Ordinary re-activation does not compare an already-installed template against the current profile rendering.

This satisfies the Phase 2 boundary for the finding under this REV: a genuinely new additive CREATE may check whether a template identity can be reused, while an already-installed template is not rejected merely because the current profile renders different policy text.

A stronger lifecycle issue remains outside this REV: ordinary re-activation still enters `ensure_cron_config()`, which currently loads the active profile and may append missing current-profile templates. That distinct residual is tracked as REV-20260810-090 and does not reopen the narrower collision-gate correction here.

## F2 — resolved — semantic rather than raw-text reuse

The corrected implementation normalizes both template sections with the existing `profile_emit()` grammar normalizer and sorts normalized fields before comparison. The regression proves that accepted cosmetic differences (comments/order/formatting) reuse the existing template while a real policy-value difference refuses.

This is intentionally a small canonicalization for the existing CONFIG field grammar, not a general profile diff/version framework.
