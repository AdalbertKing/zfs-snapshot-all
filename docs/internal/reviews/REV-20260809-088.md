# REV-20260809-088 — Phase 2 template collision check turns the preset back into runtime authority

Review time: 2026-08-09 21:44 CEST
Reviewed implementation: `5f2201c55c46b1867349d909b830facb5a93a23a`
Response path: `docs/internal/reviews/responses/REV-20260809-088.md`

## Verdict

**CHANGES REQUIRED before Gate 2 is closed.**

The delivery correctly identified a real missing Phase 2 property: when a genuinely new CREATE/additive operation wants to reuse an existing template identity, equal semantics may be reused and conflicting semantics must refuse rather than silently overwrite or silently keep the wrong template.

However, the implementation puts that comparison inside `ensure_cron_config()`, which is called by ordinary `activate-client` / re-activation. That changes a CREATE-time collision rule into a permanent profile-drift gate and conflicts with the Owner's already-canonical one-way handoff:

```text
PROFILE/PRESET -> generate once -> CONFIG v4 -> runtime truth
```

The same implementation also compares raw section text while the Gate 2 contract says **semantic** identity.

## F1 — P1 — current profile content is now consulted as authority during every activation/re-activation

`cmd_activate_client()` always creates a workfile and calls:

```bash
ensure_cron_config "$workfile"
```

`ensure_cron_config()` now calls `load_active_profile`, re-renders every namespaced profile template and, if that name already exists in the installed CONFIG, refuses whenever the on-disk section differs from what the profile renders **now**.

That means an already-installed CONFIG is no longer independent of later profile edits. A perfectly deliberate native CONFIG customization after initial generation can make the next endpoint re-activation fail solely because `profiles/default` no longer reproduces the installed text/content.

This is exactly the lifecycle we explicitly rejected:

- profiles are CREATE/preinstall presets only;
- CONFIG v4 is canonical execution truth after install;
- updating a shipped profile must not mutate or police already-installed policy;
- no profile drift/version/adoption manager without a concrete new safety need;
- endpoint/reactivation must preserve installed policy rather than reconstructing or validating it against a profile.

The fact that this implementation **refuses** instead of overwriting is safer than silent mutation, but it is still the wrong authority boundary. It makes ordinary runtime maintenance depend on the current preset definition.

### Required correction for F1

Keep the useful collision property, but scope it to the operation that is actually trying to **CREATE/add a new task/template**.

Required behavior:

1. Existing installed policy that is merely being re-activated / moved to another endpoint must not be rejected because the current profile definition changed or because an administrator deliberately customized native CONFIG after generation.
2. A genuinely new additive CREATE that needs template identity `X` may:
   - REUSE an existing `X` if its effective semantics are equal;
   - REFUSE before mutation if `X` already exists with different effective semantics.
3. Do not introduce persistent profile ownership, drift checks, re-apply, adoption or version state to achieve this. Use the smallest boundary that distinguishes "new template needed for CREATE" from "existing CONFIG is already the runtime truth".

This is not asking Phase 2 to implement all of Phase 3. It is asking Phase 2 not to introduce a new dependency on profile drift that Phase 3 would immediately have to remove.

### Minimal proof for F1

Add one discriminating regression using the real activation/composition boundary:

- start with a CONFIG containing the profile-namespaced template but deliberately customized after generation;
- perform the ordinary re-activation path that does **not** create a new policy package;
- prove it does not fail merely because the current profile renders different policy text;
- prove the customized policy section remains unchanged;
- negative control against `5f2201c...`: the same case must fail at the new `no longer matches what the active profile renders` gate.

No live ZFS/SSH campaign is needed for this correction unless the fix itself crosses those boundaries; the defect is a deterministic CONFIG/profile authority error.

## F2 — P1 — Gate 2 says semantic reuse, implementation compares raw text

The new comparison is:

```bash
existing="$(cron_config_section ...)"
wanted="$(profile_template_section ...)"
[ "$existing" = "$wanted" ] && continue
```

That is byte/text equality of the section body, not semantic equality.

Therefore a template with the same effective CONFIG semantics but harmless formatting differences (for example whitespace/comment layout accepted by CONFIG v4) can be rejected as a collision. The documented Gate 2 property is explicitly:

> identical **semantic** template may be reused

A raw-text drift detector is both stricter than the contract and another sign that this code is solving profile drift rather than CREATE-time collision.

### Required correction for F2

At the CREATE/additive collision boundary, compare the effective template semantics using the existing CONFIG parser/normalization semantics, or another minimal canonical representation derived from the same accepted fields. Do not build a general profile-diff framework.

Minimal regression:

- existing template `X` semantically equal to the requested template but with harmless accepted formatting differences -> REUSE / no mutation;
- one real policy value changed -> REFUSE before mutation;
- negative control shows the current raw-text comparison rejects the harmless-equivalence case.
