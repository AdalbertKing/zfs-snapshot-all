## F1 — Initial per-pool capacity-read failure is silently skipped

- Severity: **P2**
- Blocking: **yes for enabling the unattended capacity guard on production**; this is not an independent declaration that the entire 1.0 release is blocked.
- Affected: `hostscripts/capacity-guard.sh`, `cap_of()` and main pool loop, around lines 102, 322–325.
- Evidence (inspected current code):

```bash
cap_of() { zpool list -H -o capacity "$1" 2>/dev/null | tr -d '% '; }
# ...
cap="$(cap_of "$pool")"
case "$cap" in ''|*[!0-9]*) continue ;; esac
```

`cap_of` is a pipeline without direct status checking. A failing `zpool list` can be masked by the successful `tr`; an empty or non-numeric result executes `continue`. If this is the only pool, a run with `guard=on` can return success without having evaluated it, and without raising an alert. `--plan` can omit it entirely.

### Failure mode

An inaccessible pool/capacity property, a transient ZFS CLI failure, or malformed output causes the emergency guard to silently not monitor that pool. No destructive operation is triggered by *this* failure, but the administrator is falsely reassured by a zero exit status even if the pool needs urgent attention.

### Required outcome

For each pool enumerated, require a successful capacity command and a valid numeric result **before** the threshold decision. A failed/unreadable result must not be interpreted as `below threshold`, `nothing to delete`, or `success`.

### Acceptance criteria

- [ ] Failed `zpool list -H -o capacity <pool>` (including partial stdout with nonzero rc) and malformed/empty output yield nonzero guard status and a pool-specific diagnostic; in normal guard mode raise an alert. `--plan` reports without sending alerts.
- [ ] Zero `zfs destroy` calls on the unreadable pool, even if other pools can be read.
- [ ] Successful capacity checks still honor `guard_at`, and existing post-destroy `zpool sync` hard-stop rules remain unchanged.
- [ ] Isolated regression cases distinguish command failure, `NaN`/empty output, and valid numeric output. Compare against the original blob and show a discriminating negative control.

## F2 — Failure of global pool discovery has no alert

- Severity: **P2**
- Blocking: **yes for enabling the unattended capacity guard on production**
- Affected: `hostscripts/capacity-guard.sh`, main loop, around line 322.
- Evidence:

```bash
pools="$(zpool list -H -o name 2>/dev/null)" || { say "zpool list nie działa"; exit 1; }
```

When enumeration fails, the script prints a log line and exits 1, without invoking its existing `alert()` helper. An unattended scheduled guard can be nonfunctional across all pools while no alert is delivered.

### Required outcome

- [ ] `zpool list -H -o name` failure triggers a diagnostic and an alert in normal `guard=on` mode, with zero `zfs destroy`.
- [ ] `--plan` gives a nonzero status and diagnostic without sending an alert.
- [ ] Distinguish a command that exits nonzero from a valid empty pool listing, with explicitly documented behavior for the latter.
- [ ] Inject failure with fake `zpool` and verify rc, alert/no-alert, and destructive-call count.
