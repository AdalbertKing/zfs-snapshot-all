# REV-20261104-186 — fail-open snapshot discovery and retention defects

Reviewer: ChatGPT. Date: 2026-11-04.

Target: canonical development `main` at
`dc6333ae36346ad477e8fd3e66ab52b5f0e6d266`. The independent audit also
inspected production `AdalbertKing/zfsbackup` release 1.0.9 at `f30fbc35`;
the acceptance boundary for this review is the development implementation.

This review contains six findings from an independent audit. F1 and F4 block
use or release of the affected destructive force-full paths. F2, F3, F5 and F6
block claiming reliable retention/selection behavior in their affected paths.
No live ZFS host, production system or product script was changed during the
audit. The negative controls exercised isolated copies of the identified logic;
the implementation must add regressions against the actual scripts.

## F1 — protected-snapshot discovery failure can permit destructive force-full

- Severity: **P1**
- Blocking: **yes for forced full transfer/reconciliation paths**
- Affected: `snapget.sh`, `snapsend.sh`; Proxmox protected-snapshot check before
  force-full destruction (`zfs destroy -R` path)

### Evidence

The protected-snapshot enumeration is allowed to fail through `|| true`. The
following decision therefore cannot distinguish a successfully observed empty
set from a failed observation. An isolated negative control returned an error
from the listing step; the guard then continued into the destructive branch.
The corresponding positive control with a protected snapshot blocked it.

### Failure mode and impact

An SSH, permission or `zfs list` failure can be interpreted as proof that no
protected replication snapshots exist. A forced full transfer can then destroy
the target tree and dependent snapshots. This is a credible data-loss path.

### Required outcome

Protected-snapshot discovery must be a fail-closed precondition. Destruction
must be unreachable unless the listing completed successfully and its result
was parsed successfully.

### Acceptance criteria

- [ ] Preserve and check the exact status of local and remote enumeration.
- [ ] Distinguish an empty successful result from command, transport and parse
      failures; every failure stops before any destructive command.
- [ ] Apply the same contract to both send and receive engines and every
      force-full entry path.
- [ ] Keep diagnostics actionable without printing secrets or weakening the
      existing protected-snapshot policy.

### Required verification

- Automated: actual-script regressions for non-empty, empty-success, local
  listing failure, remote SSH failure and malformed output; assert that the
  destructive stub is never called on failure in both engines.
- Automated: focused engine suites, shell syntax, `git diff --check`,
  `test/impact.sh --verify`, and exact-head CI.
- Manual: a throwaway-ZFS force-full exercise is required before release; no
  production dataset or host is authorized by this review.

### Notes and uncertainty

The fail-open control is established at the decision-logic level. The audit did
not execute an end-to-end destructive ZFS test.

## F2 — age retention can report success after `zfs get` fails

- Severity: **P2**
- Blocking: **yes for reliable age-based retention claims**
- Affected: `delsnaps.sh`; ordinary age-retention snapshot path near the
  creation-time read, plus the analogous bookmark path

### Evidence

When `zfs get` cannot return the creation timestamp, the subsequent numeric
comparison fails. That failure is consumed as if the object merely were not
old enough. The isolated control returned an error from `zfs get`, skipped the
snapshot and still ended with `EXIT_CODE=0`. The GFS path already performs a
stricter validation, demonstrating the intended fail-closed alternative.

### Failure mode and impact

Retention can silently leave expired snapshots or bookmarks in place, consume
space and report success to scheduling/monitoring despite incomplete work.

### Required outcome

Every creation-time read must validate command status and numeric output before
age comparison; an unreadable object must make the run non-successful.

### Acceptance criteria

- [ ] Check `zfs get` status separately from output validation for snapshots
      and bookmarks.
- [ ] Reject empty, non-numeric and ambiguous timestamp output with a clear
      diagnostic and nonzero final result.
- [ ] Preserve successful behavior and existing selection semantics for valid
      timestamps.

### Required verification

- Automated: actual-script tests for command failure, empty/non-numeric output,
  snapshot and bookmark cases, mixed success/failure, and valid boundary ages.
- Automated: retention suites, shell syntax, `git diff --check`, impact
  verification and exact-head CI.
- Manual: none beyond any obligations reported by the impact graph.

### Notes and uncertainty

The audit reproduced false success in isolated logic, not on a live pool.

## F3 — recursive retention can succeed after child enumeration is interrupted

- Severity: **P2**
- Blocking: **yes for reliable recursive retention claims**
- Affected: `delsnaps.sh`; recursive child enumeration through `zfs list -r`

### Evidence

The recursive listing status is not preserved and checked. An isolated control
processed the root, simulated an SSH/listing failure with status 255 before any
child was processed, and the overall operation still returned success.

### Failure mode and impact

The root dataset may be pruned while descendants are silently omitted. The
reported success hides an incomplete retention pass and can allow unbounded
space growth or inconsistent retention across one tree.

### Required outcome

Recursive enumeration must be all-or-explicitly-failed: any local or remote
listing failure produces a nonzero result and cannot be represented as a
complete empty child list.

### Acceptance criteria

- [ ] Capture the producer/transport status without pipeline masking.
- [ ] Distinguish a valid root-only tree from failed or truncated enumeration.
- [ ] Return nonzero while preserving diagnostics when enumeration fails before
      or after partial output.
- [ ] Do not silently continue destructive work on an incompletely discovered
      tree unless a separately documented fail-closed policy proves it safe.

### Required verification

- Automated: actual-script local and SSH regressions for root-only success,
  failure before output, failure after partial output and complete trees.
- Automated: assert both processed datasets and final status; run retention
  suites, syntax, diff check, impact verification and exact-head CI.
- Manual: none beyond impact obligations.

### Notes and uncertainty

The audit simulated transport status 255; it did not interrupt a live SSH/ZFS
enumeration.

## F4 — nested recursive GUID comparison constructs the wrong source path

- Severity: **P1**
- Blocking: **yes for recursive reconciliation/force-full on nested trees**
- Affected: `snapsend.sh`, `snapget.sh`; `find_recursive_name_collisions()`

### Evidence

The collision scanner enumerates recursive descendants but maps a target child
back to the source using only the final path component. For
`pool/src/child/grand`, it can query `pool/src/grand` rather than the relative
path `pool/src/child/grand`. An isolated three-level fixture with matching GUIDs
on the true source and target reported a false collision for
`pool/dst/child/grand@base`.

### Failure mode and impact

A false GUID/name collision can discard an incremental plan. With force-full
enabled, that can select a full transfer preceded by target destruction even
though the correct nested source snapshot matches. The defect therefore widens
the destructive scope based on a misaddressed comparison.

### Required outcome

Map every target descendant to the source by its complete relative dataset
path, with explicit validation that it remains under the intended roots.

### Acceptance criteria

- [ ] Preserve every relative path component for arbitrary tree depth in both
      engines.
- [ ] Correctly classify equal GUIDs, genuine mismatches and missing peers.
- [ ] Reject malformed/out-of-root mappings before collision or destructive
      decisions.
- [ ] Keep send and receive behavior symmetric.

### Required verification

- Automated: actual-function tests for root, child and at least three-level
  descendants; duplicate leaf names in different branches; spaces/safe special
  names supported by the existing grammar; equal, unequal and missing GUIDs.
- Automated: prove the old mapping fails the three-level fixture and the fixed
  mapping does not choose destructive fallback; run both engine suites, syntax,
  diff check, impact verification and exact-head CI.
- Manual: throwaway-ZFS recursive incremental and force-full dry-run/evidence
  before release; no production operation is authorized.

### Notes and uncertainty

The wrong-path and false-collision result are reproduced in isolated logic. No
live target was destroyed and no end-to-end transfer was run.

## F5 — remote `zfs list` failure is masked by a successful `awk`

- Severity: **P2**
- Blocking: **yes for reliable remote snapshot discovery**
- Affected: `snapsend.sh`, `snapget.sh`; remote snapshot-list pipelines ending
  in `awk`

### Evidence

The remote listing command is piped into `awk` without preserving the producer
status. In the isolated control, remote `zfs list` returned 77 while `awk`
returned 0, so the compound operation appeared successful with an empty list.

### Failure mode and impact

Transport, permission or ZFS failures can become an apparently valid empty
snapshot inventory. Downstream selection may choose a full transfer, report no
common snapshot, or otherwise take the wrong recovery path while claiming the
discovery succeeded.

### Required outcome

Snapshot discovery must preserve and validate the status of every load-bearing
producer and transport command; filters must not convert failures into empty
success.

### Acceptance criteria

- [ ] Detect local command, SSH/remote command and filter/parse failures
      independently in both engines.
- [ ] Preserve a legitimate empty list as success.
- [ ] Stop before transfer/destructive selection when discovery failed.
- [ ] Avoid relying on ambient shell options whose state differs by caller;
      make the function contract explicit and tested.

### Required verification

- Automated: actual-script tests with producer statuses 0, 1, 77 and 255,
  successful/failed filters, empty success and non-empty success in both
  engines; assert no transfer/destructive stub on failure.
- Automated: engine/SSH fixture suites, syntax, diff check, impact verification
  and exact-head CI.
- Manual: none beyond impact obligations.

### Notes and uncertainty

Pipeline masking is directly demonstrated; the audit did not cause a real
remote host failure.

## F6 — snapshot family prefix is interpreted as a regular expression

- Severity: **P2**
- Blocking: **yes for correct `-m` snapshot-family selection**
- Affected: `snapsend.sh`, `snapget.sh`; candidate filtering using
  `grep "^$MESSAGE"`

### Evidence

The user/configured `-m` prefix is interpolated into a regular expression
instead of compared literally. In the isolated control, `daily.2026` also
matched `dailyX2026`; when the latter was newer it could become the selected
transfer source.

### Failure mode and impact

Regex metacharacters broaden or alter the requested snapshot family. The engine
can choose a snapshot from the wrong policy/family, producing an incorrect base
or transfer plan without reporting the mismatch.

### Required outcome

Treat the message as a literal prefix under the documented name grammar, or
reject unsupported values explicitly before selection.

### Acceptance criteria

- [ ] Literal `daily.2026` matches `daily.2026...` and never `dailyX2026...`.
- [ ] Define and test behavior for all regex metacharacters accepted by the
      current CLI/config grammar in both engines.
- [ ] Preserve ordering and newest-valid-candidate behavior within the exact
      requested family.
- [ ] Do not introduce option injection or locale-dependent matching.

### Required verification

- Automated: actual-script regressions for `.`, `[`, `]`, `*`, `+`, `?`, `^`,
  `$`, backslash and leading `-` where currently accepted, plus neighboring
  families and newest-candidate ordering in send and receive paths.
- Automated: CLI/engine suites, syntax, diff check, impact verification and
  exact-head CI.
- Manual: none beyond impact obligations.

### Notes and uncertainty

The wrong-family selection was reproduced in isolated filtering logic. The
audit did not run an end-to-end transfer using the selected snapshot.

### F5 — filter and caller failures still become an empty success

Both engines' `get_sorted_snapshots()` now check the raw remote `zfs list`
status, but then assign `snaps=$(printf '%s\\n' "$_out" | awk ...)` without
checking that assignment, and finish with `echo "$snaps"`. If the local
filter fails, `echo` returns success with an empty or partial list. This is the
same failure-to-empty-success class F5 requires us to remove; F5 explicitly
requires detecting filter/parse failures independently. The added F5 tests
cover remote producer statuses 1, 77 and 255, but not a failed local filter.

The dry-run conflict path also uses
`local src_snaps=($(get_sorted_snapshots ...))` and the corresponding target
assignment in `find_conflicting_snapshots()` in both engines. Bash `local`
returns success even when the command substitution failed (an isolated
`f(){ return 77; }; local a=($(f))` control yielded `local rc=0 count=0`).
The caller can therefore report an empty conflict set after remote discovery
failed. The actual-script regression required by F5 is absent: its new tests
extract and invoke `get_sorted_snapshots()` rather than exercising the
caller and its resulting decision. This second path is read-only but still
produces an untrustworthy verification result.

### Acceptance delta

- Preserve and check the status of the local filter, then propagate any
  discovery error through the callers that form a decision from that list.
  A failed `-n`/dry-run conflict scan must not report a complete empty set.
- Add actual-script regressions in both engines for a failed filter and for
  failed remote discovery at the dry-run conflict caller. Assert final status,
  diagnostic, output and that no transfer or destroy is selected. Keep the
  existing successful-empty and non-empty controls.
- Re-run impact obligations and exact-head CI, report the exact new
  implementation SHA in the Claude-owned response, and retain the manual
  evidence or explicitly disclose what the new diff requires to repeat.
