# REV-20260807-065 — V2 rejection derives the wrong workflow state

**Review time:** 2026-08-07 20:04 CEST

**Reviewed implementation:** `135c0311caddaa0a620168ec8bca089f712441bd` (`Review Protocol V2: the ledger is generated, so it cannot drift`).

**Fresh main at verdict:** `b3a7fe37762276497c1e69f086932ec93208ac21`, committed **2026-08-07 20:00:07 CEST**; the later commit only registers/regenerates the V2 artifacts and does not alter the derivation defect below.

## F1 — rejecting the submitted SHA leaves ownership with Reviewer instead of returning to Claude

- Severity: P1
- Blocking: yes — Protocol V2 cutover
- Affected: `test/reviewctl.sh`, `test/reviewctl/run.sh`

### Evidence

`docs/project/PROTOCOL.md` defines the only backward transition as:

`IMPLEMENTED -> OPEN`

when the reviewer rejects the currently submitted implementation.

The implementation in `135c031` does not implement that rule. Current `state_of_raw()` ignores `reviewed-implementation` for `CHANGES-REQUIRED`; if any response implementation exists it always emits `IMPLEMENTED`:

```bash
if [ "$v" = APPROVED ]; then
    ...
fi
[ -n "$im" ] && { echo IMPLEMENTED; return; }
echo OPEN
```

Therefore the exact rejection state

- review verdict = `CHANGES-REQUIRED`
- reviewed-implementation = `sha1`
- response implementation = `sha1`

is derived as `IMPLEMENTED`, whose generated owner is `Reviewer`. The protocol requires `OPEN`, owner `Claude`, because Claude owes the next implementation attempt.

The deterministic test contains the same defect visibly. Case `world c` is labelled:

`reviewer rejects sha1 -> OPEN again for the implementer`

but its expected value is currently `IMPLEMENTED`. The test therefore pins the implementation bug instead of the agreed state machine.

This is a release-process defect, not a wording issue: after the first rejected V2 implementation, generated routing would tell the reviewer to review the same rejected SHA again and would not route the correction back to Claude.

### Required outcome

1. Derive `OPEN` when `verdict=CHANGES-REQUIRED` and `reviewed-implementation` equals the current response `implementation`.
2. Preserve `IMPLEMENTED` when Claude advances the same response to a new SHA after that rejection.
3. Correct case `world c` so the expected state is `OPEN` and add/assert the generated owner/next action (`Claude`, `implement and respond`) for that case.
4. Keep the existing approval-mismatch behavior: an old approval must never approve a newer submitted SHA.

### Required verification

No broad campaign and no live-host proof are warranted: this path is pure artifact/state derivation with no ZFS, crontab, UID, SSH, grants or deployment dependency.

Run only the dependency-driven slice:

- `./test/reviewctl/run.sh`;
- `./test/impact.sh --verify`;
- negative control against `135c031` showing the corrected rejection case fails there while unaffected happy-path cases still pass.

The graph edge is already correct: `test/reviewctl.sh -> suite reviewctl` and `test/reviewctl/run.sh -> suite reviewctl` are declared in `test/deps.conf`.
