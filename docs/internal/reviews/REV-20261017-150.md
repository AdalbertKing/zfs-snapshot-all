# REV-20261017-150 — mirror cleanup bypasses the live-guest safety gate after an already-present snapshot

Review date: 2026-10-17. Reviewer: ChatGPT.  
Fresh canonical main: `80d58e482f939adfbe129a87b277ea67ccbf6157`.  
Origin under review: PR #460, head

## F1 — mirror can delete a target snapshot while the matching Proxmox guest is running

- Severity: **P0**
- Blocking: **yes**
- Affected: `snapget.sh`, the already-present return in `process_dataset()`,
  `guest_disk_is_live()`, the main result loop, and `mirror_target()`.

### Evidence

`process_dataset()` returns success when the latest source snapshot already
exists on the target with the expected GUID. That return occurs before the
`guest_disk_is_live()` call. The caller treats the result as successful and,
when `-M` is active, calls `mirror_target()` independently. Mirror cleanup can
then run `zfs destroy` for target-only snapshots even though the matching
Proxmox VM is running. The nearby comment that the guest guard "runs first in
process_dataset" is false for this path.

I reproduced the complete current CLI path with disposable external `ssh`,
`zfs`, `qm`, `pvesh`, `logger`, `mbuffer` and compression stubs. No real host
or ZFS pool was accessed and no tracked file was changed. The fixture supplied:

- source `root@source:tank/vm-100-disk-0` with snapshot `base`;
- local target `tank/vm-100-disk-0` with snapshots `old` and `base`;
- matching GUIDs for `base`, so the transfer path takes the early skip;
- local VM 100 configuration containing that disk and `qm status 100`
  reporting `running`.

The actual invocation was:

```bash
bash snapget.sh -N -M -e root@source:tank/vm-100-disk-0
```

Observed decisive result:

```text
rc=0
Mirror (-M) on 'tank/vm-100-disk-0': 1 removed (gone from the source, older than 'base')
ZFS destroy tank/vm-100-disk-0@old
DESTROYED tank/vm-100-disk-0@old
```

The trace contains no `QM status 100` call. Thus the test did not merely
choose a permitted stopped-guest branch: the guard was never evaluated.

### Failure mode

An otherwise valid incremental target is especially likely to have the newest
source snapshot already present after a retry or interrupted orchestration.
With `-M`, that ordinary idempotent path skips the safety gate but continues
into destructive convergence. A target-only snapshot — potentially the only
local rollback point — is removed while the guest is live. The command returns
success. This violates the engine's fail-closed live-guest contract and is a
credible destructive data-loss path.

`docs/project/ENGINE-ALREADY-EXISTS-SKIP-2026-10-15.md` records the broader
shortcut concern but does not fix or formally accept this destructive mirror
case. This finding supplies new executable evidence for the still-unreviewed
PR #460 backlog item; it does not reopen any closed REV.

### Required outcome

Every destructive `-M` cleanup for a target identified as a Proxmox guest disk
must pass the live-guest safety gate before the first `zfs destroy`, including
the already-present/no-transfer path. A running guest or an unknown/unreliable
guest status must refuse nonzero with a clear diagnostic and no mirror
mutation. A stopped guest and a non-guest dataset must retain the intended
PR #460 mirror semantics.

Only `snapget.sh` is opened by the marker above. Keep the correction at the
smallest owning control-flow boundary; do not redesign mirror policy, receive,
P-0, quiesce, naming, statistics or unrelated target-state handling. Update
the normal freeze/twin evidence for the actual diff. No production fix was
made by the reviewer.

### Acceptance criteria

- [ ] With the newest source snapshot already valid on the target, `-M` checks
  the matching guest before mirror cleanup; `running` returns nonzero and
  performs no `zfs destroy`.
- [ ] Unknown, failed or ambiguous guest status also fails closed before any
  destroy and emits a source-specific diagnostic.
- [ ] The stopped-guest control returns the established success status and
  removes exactly the eligible target-only snapshot.
- [ ] A non-guest dataset retains normal mirror behaviour; the correction does
  not make all already-present runs fail or silently disable `-M`.
- [ ] The safety decision is made before `mirror_target()` can mutate state,
  rather than checking after deletion or relying on transfer execution.
