# REV-20260810-097 — Phase 5 local planning does not yet satisfy the authoritative-source/additive-preview/public-UX contract

Review time: 2026-08-10 23:20 CEST
Reviewed implementation: `f8ec3eaec11210884a10af311b0e02e56443cf4b`

## Verdict

**CHANGES REQUIRED.** The read-only-first split is good and the overlap/same-pool/profile checks are useful, but this slice currently plans a local backup against a weaker contract than the Owner-approved Phase 5 workflow. Fix these now, before slice 2 turns the plan into an installer.

## F1 — P1 — explicit `--source` is syntax-checked but never proven to exist

`cmd_local_backup()` accepts a non-empty, syntactically plain dataset name and immediately proceeds to profile rendering. It never asks local ZFS whether that explicit dataset exists.

Therefore a typo such as:

```bash
./zfs-backup.sh local-backup --source=rpool/dtaa --target=hdd/backups
```

can produce a valid-looking CONFIG and cron plan even though the operator explicitly selected a nonexistent dataset.

This violates the Owner contract recorded in `docs/discussions/EXPLICIT-SOURCE-BEATS-DISCOVERY-2026-08-09.md` and the reviewer checkpoint:

- no explicit source -> discovery may propose;
- 1..N explicit sources -> validate all;
- any missing explicit source -> **REFUSE the whole operation**;
- never reinterpret an invalid explicit choice as discovery/empty/fallback.

### Required correction

At the LOCAL boundary, validate the explicit source against real local ZFS before rendering a candidate. A missing source must hard-refuse with no fallback. Keep validation read-only; no install is required for this proof.

Required regression: stub/fixture the ZFS query so an existing source proceeds and a missing explicit source refuses. The negative control against `f8ec3ea...` must show the missing source currently reaches/plans past this boundary.

## F2 — P1 — the preview ignores the installed/shared CONFIG it claims it would target

The command resolves a destination config path (`CRON_CONFIG` / `--config`) and prints it as `Config docelowy`, but then builds `$cand` **from scratch**:

```text
[defaults]
profile templates
[dataset:<new source>]
[prune:<target>]
```

It does not read/copy the existing target CONFIG before rendering the candidate cron.

That means on a host with existing remote/local relationships the displayed cron is not the cron that a safe additive installation is allowed to produce. It omits every old job, cannot exercise template reuse/collision against the installed file, cannot prove old policy remains unchanged, and cannot expose global CONFIG interactions such as `[excluded:]`.

This directly conflicts with the already-closed Gate 2 property: **add B, do not mutate A**. It also makes slice 1's wording "cron it WOULD install" misleading for the shared CONFIG model.

### Required correction

Planning must compose the **actual additive candidate** from the existing target CONFIG when one exists, using the same ownership/overlap/template-collision rules that slice 2 will install. Preview the complete candidate CONFIG and the complete resulting managed cron block. If the existing CONFIG cannot be safely read/understood, refuse rather than inventing a fresh file.

Required regressions:

1. existing CONFIG with unrelated task A -> plan B -> A remains semantically/byte unchanged where no global normalization is required and rendered cron still contains A + B;
2. collision/overlap with existing content refuses before any install;
3. missing target CONFIG may create a fresh candidate only when there is no installed managed block claiming that file (reuse the existing fail-closed safety model rather than adding a second one).

Do not build a merge framework; reuse the existing CONFIG-v4/additive primitives.

## F3 — P2 — public command surface diverges from the canonical Phase 5 UX

The canonical `ACTIVE-WORK-PLAN.md` still defines the basic local workflow as:

```bash
./zfs-backup.sh --source=rpool/data --target=hdd/backups
```

and explicitly says to avoid exposing internal command-tree complexity when one logical workflow can own it.

This slice instead documents and exposes:

```bash
./zfs-backup.sh local-backup --source=... --target=...
```

The implementer design note made that choice solely to keep dispatch uniform, but that is an implementation convenience overriding an Owner-approved UX target. This is exactly the kind of accidental public surface that becomes expensive to remove after slice 2/install documentation lands.

### Required correction

Make the Owner-approved bare high-level form the canonical public entrypoint for LOCAL backup. An internal helper/subcommand alias is acceptable only if it is not made the required operator workflow and does not force administrators to learn the old command tree.

Pin the public dispatch in a regression so the documented zero-extra-verb form reaches the same planning logic.
