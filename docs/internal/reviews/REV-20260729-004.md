## Executive result

The core design requested by `REV-20260729-003` is now present:

- no-op updates preserve the previous-revision pointer;
- real updates record the prior SHA;
- rollback creates an update hold;
- hourly self-update respects the hold;
- explicit resume mode exists;
- old cron forms are migrated toward `--self-update`;
- the new dependency-free suite exercises the normal A → B → rollback → hold → resume cycle.

That closes the original logical defect, but the implementation is not yet safe enough to claim durable rollback. The update-control files live in a directory deliberately writable by delegated service accounts, and several state writes fail open because `deploy.sh` uses `set -uo pipefail`, not `set -e`, and does not check their results.

The first implementation commit also temporarily broke every ordinary `deploy.sh` invocation through an unbound variable. The corrective commit and added canaries address that specific defect, but direct-main mode makes pre-push execution of the affected suite mandatory: a later corrective commit is not a substitute when live hosts poll hourly.

## F1 — update-control state shares a group-writable alert directory

- Severity: **P1**
- Blocking: **yes for closing REV-20260729-003**
- Status: `OPEN`
- Affected: `deploy.sh`, `UPDATE_STATE_DIR`, `PREV_REV_FILE`, `UPDATE_HOLD_FILE`, Phase 4 permissions

### Evidence

The default update state is derived from `ALERT_SHARED_DIR`:

```sh
UPDATE_STATE_DIR="${UPDATE_STATE_DIR:-$ALERT_SHARED_DIR}"
PREV_REV_FILE="$UPDATE_STATE_DIR/previous-revision"
UPDATE_HOLD_FILE="$UPDATE_STATE_DIR/update-hold"
```

Phase 4 intentionally creates that directory as:

```text
2775 root:zfsalert
```

The purpose of those permissions is to let delegated backup accounts create and maintain alert data. Directory write permission also lets such an account remove, rename, or replace the update-control directory entries.

The implementation acknowledges only that a `zfsalert` member can create a hold. The larger problem is that it can also:

- remove `update-hold`, causing the next root cron run to re-enable the revision that an administrator rolled back;
- replace `previous-revision` or `update-hold` with symlinks before root writes them;
- replace the pointer content and influence a later administrator-triggered rollback;
- disrupt or corrupt the update-control state independently of the root-owned Git checkout.

A backup service account did not previously have authority to resume root code deployment. This is a new trust-boundary violation, not merely a harmless denial-of-service capability.

### Required outcome

Update-control state must be stored under a root/private trust boundary separate from group-writable alert data.

### Acceptance criteria

- [ ] The production default `UPDATE_STATE_DIR` is not inside a directory writable by `zfsalert` or any other delegated account.
- [ ] The directory is owned by the effective updater account and is not group- or world-writable; production should be `0700 root:root`.
- [ ] The path itself and both state files are rejected if they are symlinks or unexpected file types.
- [ ] State replacement is atomic and does not follow attacker-controlled links.
- [ ] A delegated `zfsalert` account cannot create, remove, replace, or modify `previous-revision` or `update-hold`.
- [ ] Test overrides remain possible through a private temporary directory owned by the test user.

### Required verification

- reject a group-writable update-state directory;
- reject a symlinked update-state directory;
- reject symlinked `previous-revision` and `update-hold` entries without touching their targets;
- verify production setup creates the root-private directory with the expected owner and mode;
- verify a delegated account cannot remove a live hold.

## F2 — state-write failures do not stop update or rollback

- Severity: **P1**
- Blocking: **yes for closing REV-20260729-003**
- Status: `OPEN`
- Affected: `do_self_update()`, `do_rollback()`, `do_resume_updates()`

### Evidence

`deploy.sh` runs with:

```sh
set -uo pipefail
```

The following operations are not checked:

```sh
mkdir -p "$UPDATE_STATE_DIR"
printf '%s\n' "$current" > "$PREV_REV_FILE"
printf 'rolled back ...' > "$UPDATE_HOLD_FILE"
rm -f "$UPDATE_HOLD_FILE"
```

Consequences:

1. A real A → B update can continue even if recording A failed. The checkout moves to B without a usable rollback pointer.
2. `--rollback` resets B → A first and writes the hold afterwards. If that write fails, the command still logs success and returns success; the next hourly invocation restores B.
3. Restoring the prior pointer after a failed fast-forward can itself fail without changing the final return path.
4. `--resume-updates` can claim that it removed the hold without checking whether removal succeeded.

These are direct violations of the acceptance criteria that A must be recorded before activating B, rollback must create a durable hold, and failure must leave usable state.

### Required outcome

All update-control state transitions must fail closed and be atomic.

### Acceptance criteria

- [ ] Directory creation/validation is checked before any fetch, merge, reset, or state mutation.
- [ ] A → B does not activate B unless A has been durably and atomically recorded.
- [ ] Pointer restoration after a failed update is checked; uncertain state leaves automatic updates held.
- [ ] Rollback establishes a durable hold before or transactionally with the reset and never reports success without the hold.
- [ ] If reset fails, the system remains held and reports the actual state.
- [ ] Resume verifies hold removal. If the explicit update then fails, the safe default is to restore the hold rather than silently enable hourly retries.
- [ ] Temporary files are created inside the private state directory and atomically renamed over final regular files.

### Required verification

Inject failures for:

- unwritable state directory;
- pointer write failure;
- atomic rename failure;
- hold write failure;
- reset failure;
- failed update after `--resume-updates`.

Each test must assert checkout SHA, pointer content, hold state, exit code, and diagnostic.

## F3 — updater does not refuse a dirty checkout

- Severity: **P1**
- Blocking: **yes for the moving-main production model**
- Status: `OPEN`
- Affected: `do_self_update()` before `git merge --ff-only`

### Evidence

The updater fetches and then runs:

```sh
git -C "$REPO_DIR" merge --ff-only "$target"
```

There is no explicit clean-worktree check. The regression test modifies the same file changed by the incoming commit, which forces the merge to fail. That does not cover a local modification in an unrelated file: Git may fast-forward successfully and retain the local modification.

The resulting host then executes a mixture of the fetched revision and unreviewed local code. This is particularly unsafe because the backup scripts run as root, and the repository already contains a live example of a host with local modifications.

### Required outcome

Self-update must refuse any dirty tracked or untracked worktree before recording a pointer or activating a new revision.

### Acceptance criteria

- [ ] `git status --porcelain` is empty before an update may proceed.
- [ ] Dirty state fails with a precise diagnostic and leaves SHA, pointer, and hold unchanged.
- [ ] A local modification in a file untouched by the incoming commit is covered.
- [ ] An untracked file is covered.
- [ ] The no-op case may report dirtiness but must not overwrite state.

## F4 — cron normalization can preserve duplicates or match another updater

- Severity: **P2**
- Blocking: **no for the current four hosts after live verification; required for idempotent deployment**
- Status: `OPEN`
- Affected: Phase 7 cron detection and migration

### Evidence

The first condition is global:

```sh
crontab -l | grep -qF -- "--self-update"
```

If any unrelated command contains `--self-update`, the script assumes this repository already has the correct line. Also, if the correct line and an older `git pull` line coexist, the first condition wins and the duplicate old updater remains.

The current unit test validates the text-removal pipeline for either old form in isolation. It does not test:

- current + old together;
- two current lines;
- an unrelated `--self-update` line for another program/repository.

### Required outcome

Every non-check deployment should normalize this repository's known updater lines to exactly one exact current line. Check-only should report missing or duplicate lines without changing them.

### Required verification

- no line → one current line;
- one old line → one current line;
- current + old → one current line;
- two current lines → one current line;
- unrelated `--self-update` line remains untouched and does not satisfy this repository's check.
