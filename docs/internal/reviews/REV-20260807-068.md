# REV-20260807-068 — PROJECT_STATUS freshness gate is blind before the behavior commit

**Review time:** 2026-08-07 23:33 CEST

**Reviewed head:** `eea6339edc29368af7eadc059aee3360847d7803` (2026-08-07 23:13:49 CEST).

**Verdict:** **CHANGES REQUIRED**

Stage 2.2 itself is not rejected by this review. The recursion parser change is narrow, the dedicated suite exercises the real engines at the argv boundary, the negative control is discriminating, and no live-ZFS run would add evidence to that pure parsing invariant.

A new process/mechanism defect is visible around that delivery, however: the machine freshness gate added after REV-061 can report a clean pre-commit tree even though the commit being prepared will make `PROJECT_STATUS.md` stale immediately after it lands.

## F1 — pre-stage `impact.sh --verify` does not see pending watched changes

- Severity: **P2**
- Blocking: **yes, for declaring another behavior/deployment stage complete**
- Affected: `test/impact.sh::status_freshness`, `test/impact/run.sh`, the Stage-1 freshness contract

### Evidence

At reviewed HEAD, `docs/PROJECT_STATUS.md` still carries:

```text
<!-- status-covers-commit: d4a1e7d -->
```

while `eea6339` is a later behavior-changing commit modifying both transfer engines. The same commit edits the PROJECT_STATUS suite table to add `recursion`, but does not advance the machine marker.

`status_freshness()` only searches committed history:

```bash
behind="$(git log --format='%h %s' "${marker}..HEAD" -- "${watched[@]}")"
```

It never inspects the working tree or index. Therefore this sequence is possible and has now happened:

1. HEAD still points at the previous committed state.
2. `snapsend.sh` / `snapget.sh` behavior changes are staged or present in the working tree.
3. `./test/impact.sh --verify` sees only `marker..HEAD` and returns clean for freshness.
4. The behavior commit lands.
5. The same marker is now behind a watched behavior-changing commit, so the committed tree is stale.

The `eea6339` commit message reports `./test/impact.sh --verify consistent`, yet the committed HEAD it created has exactly that stale marker. This is a false-green at the lifecycle boundary the mechanism was intended to police, not a prose issue.

The current `test/impact/run.sh` does not pin this case. Its real-tree assertion runs `--verify` against the already-committed tree; there is no deterministic case with a clean marker plus a pending watched-file change.

This does **not** reopen REV-061. REV-061 required a committed later behavior change to be detectable, and the current implementation can detect that after the commit. The new finding is that the workflow calls the same command a **pre-stage gate**, where its current implementation cannot prove the property it is being cited for.

### Required outcome

The normal stage-finalization mechanism must fail closed on this exact lifecycle gap. It must no longer be possible to cite a successful pre-stage `impact.sh --verify` as freshness evidence when pending changes to a `project-status`-watched path will make the marker stale as soon as they are committed.

Do not solve this by inventing a future commit SHA in the marker; a commit cannot reliably contain its own hash. Acceptable designs include, but are not limited to:

- teaching the gate to detect pending watched changes and explicitly refuse freshness proof until a required post-commit status refresh/verification is completed; or
- changing the machine invariant to something that can be proved against the staged tree and remains valid after commit.

Whichever design is chosen, there must be one mechanically enforced sequence from behavior change to a clean committed status. A human reminder to rerun `--verify` after committing is not sufficient; that is the class of mechanism Stage 1 was created to eliminate.

Also refresh the current `PROJECT_STATUS.md` marker/current-state material to cover the actual latest behavior commit it describes (`eea6339` unless superseded by the fix).

### Minimal acceptance evidence

No ZFS, SSH, crontab, root, delegated-account or fleet campaign is required. This is a repository-state invariant.

Required evidence is deliberately small:

1. deterministic `test/impact` case: marker is current at HEAD, a watched behavior file is changed/staged, and the finalization gate **must not report clean freshness**;
2. the existing committed-stale case remains rejected;
3. a clean tree with an up-to-date status invariant remains accepted;
4. negative control against the current implementation showing the pending-change case passes incorrectly there and fails after the fix;
5. `./test/impact.sh --verify` clean on the final committed fix/status state.

Do not rerun engine/ZFS campaigns for this finding; they cannot discriminate it.
