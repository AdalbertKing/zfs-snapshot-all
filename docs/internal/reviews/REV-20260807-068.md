# REV-20260807-068 — PROJECT_STATUS freshness gate at the commit boundary

**Original review time:** 2026-08-07 23:33 CEST

**Original reviewed head:** `eea6339edc29368af7eadc059aee3360847d7803`.

## Original finding

The Stage-1 `PROJECT_STATUS.md` freshness gate could report CLEAN before a behavior commit and then allow that commit to land with stale status metadata. The root contract is not “the working tree looks current”; it is that a successful finalization gate certifies the **prospective normal commit** when the Git index is not changed afterwards.

This review stayed on one F1 through several implementations because each rejection exposed another part of the same prospective-tree invariant rather than a new independent finding:

- the original commit-SHA marker was only checkable after the commit it purported to guard;
- `41bd774ae761751c3160e3ec8c8dd94f2a8f2c84` moved to a content digest but measured the working tree while `git commit` writes the index;
- `c077b8250ab49ad210ab0a9284766ed10b58391e` moved the invariant onto the index but hashed blob IDs only, so a mode-only index change could still alter the prospective commit without changing the digest.

## Approval — 2026-08-08 02:12 CEST

**APPROVED implementation:** `bda56027ab78d6cd929fa32db4f0ad29009809af`.

Round 4 closes the remaining F1 gap. `status_digest()` now derives each watched path from the canonical stage-0 index entry via `git ls-files --stage`, so the verdict covers the tree-entry semantics that matter here: **mode + object ID + path**. `PROJECT_STATUS.md` and `test/deps.conf` continue to be read from their staged blobs, so the status marker, the definition of the watched set, and the watched entries are all evaluated against the same prospective commit view.

The previously demonstrated mode-only false-green is therefore removed: `git update-index --chmod=...` changes the indexed mode even when the blob object is unchanged, and the digest now changes with it. The changed-files hint was also made mode-aware, which is useful diagnostics but is not relied on for the verdict.

The implementation's boundary is explicit and acceptable: the guarantee applies to an ordinary `git commit` performed after a green verification **without changing the index**. Commands such as `commit -a`, pathspec commits, or other operations that mutate the index are outside that guarantee and must be re-verified after the mutation. That is a truthful, mechanically enforceable boundary for the Stage-1 contract.

## Evidence assessment

The evidence is appropriately small and discriminating for this repository-state invariant:

- `test/impact` adds the exact mode-only regression: staged mode change => NOT-CLEAN; refresh + stage status => CLEAN; immediate commit => CLEAN afterwards;
- the negative control against `c077b82` has exactly one new assertion fail, the mode-only case, while the prior prospective-index cases remain green; this demonstrates that round 4 addresses the missing tree-entry dimension rather than merely perturbing the suite;
- the implementation updates `PROJECT_STATUS.md` to the new digest and records the four-round invariant explicitly;
- no ZFS, SSH, crontab, UID/account, permission, root/delegated, or fleet test would add evidence to this purely Git-index/tree property.

I independently inspected the implementation diff rather than relying on the response's PASS count. I do not find another unresolved edge within F1: symlink/file-type changes are represented by tree-entry mode/object changes, and renames are handled through the staged `deps.conf` watched-set definition plus the graph's declared-path existence verification.
