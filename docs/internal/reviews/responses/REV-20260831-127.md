# Response to REV-20260831-127

## F1 — IMPLEMENTED

### Analysis

The finding is correct, and both halves of it are.

The relation controller classifies the per-dataset step's exit status, which it
can only do if that step **returns**. `die` in this tree is `exit 1`, and the
step reaches a large amount of shared code -- config reads, relationship
resolution, strategy classification, the technical measurement snapshot -- any of
which may refuse by exiting. One `exit` there and policy B silently stops being
"continue and give back what can be given back" and becomes "stop here": the
datasets after it are never attempted, and the promised per-dataset summary is
not printed at all.

The second half is the sharper one. The committed stub could only `return`,
including for the simulated pre-destruction failure, so it did not have the
control-flow contract of the function it stood for. That is not a gap in the
cases; it is a gap in what the harness was able to express, and it is how a
defect of this shape survives a green suite. It is the same class of error the
implementer hit earlier the same day, in the opposite direction -- a policy
wrapped around a function nothing called. A control proves that a case measures
the function it names; it cannot notice that the function's contract differs from
the real one, and it cannot notice that nobody calls it.

### Scope correction

The review names `restore_replace_relation_internal()` at head
`97b2f93f159232b0037119955ee654351c9578c3`. That function no longer exists.
`f4051ea93239787f7cfcc31a6b2e32928be60801` (PR #199, merged as `96dab71`) moved
the policy onto `restore_run_scope` / `restore_one` -- the path every public form
of the verb actually goes through. The original had been wrapped around
`restore_replace_internal`, the older single-dataset engine whose own header
records that it has no public door. The finding is therefore applied to the live
controller rather than to the function the review inspected; the acceptance
criteria are unchanged by that move.

### Measured, before fixing

`restore_one` and every helper it calls are return-based: no `die` appears in the
function or in `restore_at_pick`, `restore_engine_argv`, `restore_grant_ask`,
`restore_grant_require`, `restore_plan_strategy`, `restore_point_unique`,
`restore_remote_ahead`, `restore_remote_newer_snaps`, `restore_remote_off_point`
or `restore_remote_state`. So this was not a live incident on the merged tree.

That is stated because it is true, not as a defence. It is a fact about today's
code and not a guarantee: the next `die` added anywhere under that call graph
would reintroduce the defect silently. That is precisely why the correction is
structural rather than a comment saying "do not add one".

### Implemented change

`restore_one_isolated()` runs the per-dataset step in a subshell. Whatever leaves
it -- `return`, `exit`, or a `die` deep in a helper -- leaves through an EXIT trap
that carries three things back to the parent through a temporary file:

| carried | what its absence would cost |
|---|---|
| the verdict | the run reports "no reason recorded" while the real reason went to stderr with the process |
| `RESTORE_ONE_CHANGED` | an exit AFTER the first mutation is demoted to an untouched failure -- this flag is the difference between telling the operator a machine needs a person tonight and not |
| the `RESTORE_ROLLED_BACK` appends | a subshell takes them with it |

`RESTORE_ONE_CHANGED` stopped being `local` for exactly that reason: the trap runs
after the function has left, where its locals no longer exist. `die` carries
`exit 1` and no idea of what it had already done; the flag does, so the promotion
to status 2 happens in the parent rather than being lost with the process.

Both passes go through the boundary, the pre-flight included. A `die` there would
end the run before the pre-flight could report which datasets are unfit, which is
the same defect one step earlier.

No single-dataset refusal was weakened, removed or reworded. Only the delivery of
their status changed.

### Against the acceptance criteria

1. **Isolate each real single-dataset execution** -- subshell plus EXIT trap; the
   safety refusals are untouched.
2. **A pre-destruction exit classifies as `nietkniete`, continues, emits the
   complete summary, returns 1** -- case E1, four assertions.
3. **Status 2 preserved for a step whose destruction began** -- case E2, via the
   carried flag; it still outranks ordinary untouched failures.
4. **One focused regression with `a b c`** -- E1: all three pass pre-flight, `b`
   exits rather than returns during execution, `c` must execute, `b` is named
   untouched. E2 adds the after-mutation variant. The stub gained an exiting
   shape (`die` / `die2`) so the case can be written at all.
5. **D pre-flight, internal-only surface, grant and destructive checks unchanged.**

### Side effect, stated because it is a contract change

Each dataset now runs in its own process, so one step can no longer leak mutable
state into the next. That is a property rather than a cost, and it broke a
fixture relying on the opposite: `test/restoregrant` kept a cursor in the parent
shell, which stopped advancing. It reads its answer by dataset name now. The same
fixture also extracts the boundary along with the loop -- without it every dataset
came back "unfit" with no reason, which is what an unresolved call looks like from
inside the runner rather than a missing-function error.

## Remaining risk

One `fork` per dataset per pass. For a relation of four disks that is eight forks
against transfers measured in minutes -- not material, and named rather than
assumed.

The pre-flight and the execution read the world at two different moments, so a
dataset can pass pre-flight and be refused during execution when something
changed in between. That is inherent to the shape and is exactly what the
`nietkniete` outcome and criterion 2 exist to handle; the claim in the design note
that "a pre-flight refusal IS an execution refusal" is about the two using the
same code, not about them observing the same instant. The wording in
`PROJECT_STATUS.md` was left as "the same code" for that reason.

No live destructive relation restore was run for this correction, and none is
claimed. Per the review's own scope, no Restore campaign was required.
