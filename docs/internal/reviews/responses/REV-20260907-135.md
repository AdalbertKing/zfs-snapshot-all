# Response to REV-20260907-135

## F1 — IMPLEMENTED

### Analysis

The finding is correct, and it is the same defect REV-20260822-122 F4 removed
from `tx_approve` left standing in `tx_close`. The two replay paths were written
at different times and only one of them was repaired:

```sh
# tx_approve, after F4
tx_guard "$LEDGER" "$THREADS"
tx_regenerate_and_verify
echo "... no write needed; derived views verified"

# tx_close, before this change
echo "reviewctl: $rev is already closed by $acommit -- nothing to do"
return 0
```

The closure branch is reached only when the canonical facts are all still
valid — the review says `APPROVED`, the named commit provably carried that
approval for the implementation the response submits now, and a closure naming
that same commit already exists. Everything the early return asserts is true.
What it does not assert is the thing the caller is actually asking about: that
the **derived** views still agree with those facts. `REVIEW_LEDGER.md` and
`OPEN-THREADS.md` are generated, so they are precisely the files a partial
manual edit, a conflict resolution or an interrupted publication can damage
while every canonical artifact stays intact — and a replay is what an operator
reaches for after exactly that kind of interruption.

One correction to the review's premise, stated because the acceptance criteria
are written against it. Criterion 1 asks closure to guard, regenerate, verify
**and reconfirm `--expected-parent`**, "mirroring the already-correct approval
replay semantics". The approval replay did the first three and *not* the fourth:
it returned straight after `tx_regenerate_and_verify`, without
`tx_reconfirm_parent`. Since the replay path can now write (it repairs the
derived views), the post-write reconfirmation is meaningful on both paths, so
this change adds it to both rather than making closure stricter than the path it
is supposed to mirror. That is the only edit to `tx_approve`.

### Planned or implemented change

`test/reviewctl.sh`:

- `tx_close` — the early return is replaced by the same transaction the approval
  replay performs: `tx_guard "$LEDGER" "$THREADS"`, `tx_regenerate_and_verify`,
  `tx_reconfirm_parent "$parent"`, then the success line, now
  `"... no write needed; derived views verified"` so the two paths report the
  same fact in the same words. The guard means criterion 3 is satisfied by the
  existing rollback machinery rather than by new code: a failed regeneration or
  verification goes through `tx_die`, which restores every guarded byte.
- `tx_approve` — one added `tx_reconfirm_parent "$parent"` in the replay branch,
  as above.
- Untouched, per criterion 5: the proof that `--approval-commit` carried
  `APPROVED` for the response's current implementation, and the refusal that a
  *different* existing closure is never overwritten. Both sit above the replay
  branch and still run first.

`test/reviewctl/run.sh` — three assertions, built as the mirror of the existing
approval control T14:

- **T14b** closes `REV-20260814-120` with the real approval commit
  `211d378` from this repository's history (the control that the closure really
  happened), appends `TAMPERED` to the generated ledger and `tampered` to the
  routing view, replays the identical close, and asserts the replay reports
  `derived views verified`, that **both** damaged lines are gone, and that
  `--verify` accepts the result afterwards.
- **T14c** is the negative control for the repair itself: with an orphan
  response in the tree the regeneration cannot derive, the replay must refuse
  rather than report success — otherwise "regenerate and verify" could be
  satisfied by a regeneration that quietly produced nothing.

### Remaining risk

The replay now regenerates before it reports success, so it costs one full
`--generate` pass where it previously cost nothing. That is the same cost the
approval replay has carried since REV-122 F4 and is bounded by the number of
review artifacts.

`tx_reconfirm_parent` narrows, and does not close, the window between the last
check and the publication; the compare-and-swap remains the push, exactly as the
comment above that function has said since REV-122 F3. This change does not
alter that boundary — it only stops a replay from claiming a clean publication it
never checked.

No ZFS, fleet or product path is touched: the diff is the review-protocol writer
and its suite.
