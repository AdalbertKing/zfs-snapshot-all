# Response to REV-20261023-173

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. The REV-172 failed-refresh gate refused a hand-written list of action
keys (`ACTION_KEYS`), and `ins` was not on it, so on Templates it dispatched
`save-profile --ask --from=<stale selected profile>`. The same list also missed `m` in the
child panel, and any key added later would have been let through by default. The review
of this response found one more: with the focus in the command line every key was let
through, and the command line passes its F keys on to the rows (`F7` there ran the stale
row's action).

### Planned or implemented change

`tui/zfs-tui.py`: the rule is inverted. After a failed full refresh (`bg_failed`), the gate
in `UI.key()` lets through only keys that take nothing from the retained rows
(`UI.ROW_FREE_KEYS`, checked by `UI.row_free()`):

- movement in a list: `up`, `down`, `j`, `k`, `pgup`, `pgdn`, `home`, `end`, `left`, `right`;
- focus and screens: `tab`, `esc`, the screen keys of `SCREENS` (F2-F6, F11: they only switch
  the screen);
- `F1` (help), `F10` (host settings dialog, not a row), `ctrl-r` (the recovery), `q`/`F12`;
- what the command line takes as typing and editing (any non-F key while the focus is the
  command line or it holds text; a single printable character outside the child panel,
  which is command-line text): the admin types the command, no row is used. F keys are
  never row-free there, because the command line passes them on to the rows.

Every other key, including `ins`, `del`, `enter` on a list, `m` in the child panel and
`F7`-`F9` (also from the command line), is refused: it returns `"stay"`, schedules nothing, and the message keeps the stale-state
diagnostic with the Ctrl-R instruction. A new row action is therefore refused unless it is
deliberately added to the row-free set. A full successful refresh (`apply_data(full=True)`,
what Ctrl-R ends in) clears `bg_failed`, and the next key acts on the refreshed rows.
The REV-172 timeout branch is unchanged.

Audit of the other dispatches against the same rule: on the main screen the row-dependent
branches are `F7` on Jobs (`run_job_now`), `F7`/`F8`/`F9`/`del`/`ins` on Relations and
Replica, `del`/`ins` on Templates, `F7` and `enter` on Restore, `enter` on any list and `m`
in the child panel; all are reached only through the gate and are outside the row-free set,
from the list and from the command line. Keys inside an open window (`e`, `s`, `c`, `d` in
the relation, template and replica windows) are not gated, but each of them closes its
window before its dialog, a window is opened from a list only by `enter` (refused on stale
rows), and the background refresh starts after a dialog has returned, with no window open.

### Remaining risk

The row-free set is itself a list, but a missing entry now fails closed (a harmless key is
refused until Ctrl-R), not open: a new key is refused on a stale screen unless it is added to
the set on purpose. `F10` is allowed because the settings dialog reads the host
configuration itself, not the screen rows.
