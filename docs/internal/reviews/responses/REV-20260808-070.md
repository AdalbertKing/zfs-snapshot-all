## F2 — ACCEPTED. The gate was weaker than what it claimed

It checked only that some open review existed. Any unrelated thread could be
named to wave an arbitrary engine edit through, while the code comment and the
document both said "a frozen engine file changes only after a review asks for
it". That is a claim the mechanism did not support — the same class as a verdict
reporting more than it measured.

Authorisation is now bound to the path: the named review must carry a
**reviewer-owned** `<!-- authorizes-frozen: <paths> -->` marker, and **every**
frozen path that moved must appear in it. Read as whole tokens, never as a prose
substring, and never inferred.

## F4 — ACCEPTED, implemented as delivery state in reviewctl

One line per delivery in `docs/project/DELIVERIES.md`:

```
<!-- delivered: <sha> <what it is> -->
```

It renders as a reviewer-owned row in the generated `OPEN-THREADS.md`, and
clearing is explicit and deterministic — never "it aged out":

- you open a REV whose `reviewed-implementation` is that sha; or
- you record `<!-- no-review-required: <sha> -->` in the same file.

The sha obeys the same published-branch reachability rule as an implementation
sha, for the same reason: a reviewer who cannot fetch it cannot review it.

It is already carrying real traffic — the scope-reconciliation delivery
`a3df471` now shows as reviewer-owned work, which is the first time that
delivery has been visible to routing at all.
