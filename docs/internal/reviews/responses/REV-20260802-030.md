# Response to REV-20260802-030

Delivery: direct to `main`, per the owner-approved exception. Commit `9fbf1df`.

## The four questions, answered against the code

The review asks whether the surviving snapshot is harmless before proposing a
fix. It is not, and the answers are why the preferred contract is the right one
rather than merely the tidier one.

### 1. Can a later path consume the surviving pool-A snapshot as if the job completed?

**Yes.** `snapsend.sh`, the `USE_EXISTING_SNAPSHOT` branch:

```bash
src_snaps=($(get_sorted_snapshots "$src_dataset"))
src_snaps=($(printf "%s\n" "${src_snaps[@]}" | grep "^$MESSAGE"))
local latest_snap="${src_snaps[-1]}"
```

`-e` takes the **newest** snapshot matching the prefix. Nothing distinguishes
one made by a completed run from one left by a failed one. The concrete harm is
not to pool A — that snapshot is internally consistent — it is that the next
tier job would ship **pool A at T and pool B at T-1** as though both were the
current tier, and report success.

### 2. Do monitors distinguish partial from complete?

**No.** `check-snap-age.sh` compares the newest snapshot per dataset against
warn/crit thresholds. Pool B's datasets are one interval behind, which for the
hourly tier (`90m` warn) is comfortably inside the window. The failed run's own
non-zero exit does fire `notify-fail.sh`, so the operator is told *something*
failed — nothing anywhere says *the set at T is partial*.

### 3. On retry, can the partial timestamp collide with or outrank the new set?

**No collision.** The suffix is `date '+%Y-%m-%d_%H-%M-%S'`, so the next run's
name sorts later and `-e` prefers it.

**But** the orphan occupies a slot in pool A's count-based retention ladder that
has no counterpart in pool B's, so the two pools' histories drift by one entry
per incident.

### 4. Is there a persistent marker proving the timestamp is incomplete?

**No.** None exists, anywhere.

## Consequence

My earlier justification — *"they were taken while the freeze held"* — was true
and irrelevant. It is a statement about one snapshot; what every downstream path
actually reads is the set.

## Implemented: the preferred contract

- both paths keep a **ledger** of what this invocation created, appended only
  after `zfs` confirms each pool. It can therefore never name something that
  does not exist, which is what makes *"never delete a pre-existing snapshot"*
  true by construction rather than by care;
- a refused boundary or a failed `zfs snapshot` destroys exactly those and
  nothing else, then thaws;
- one outcome reaches the operator:

  | | |
  |---|---|
  | complete quiesced set created | exit 0 |
  | nothing committed, rollback complete | the reason's own code — 3 boundary / 1 snapshot locally, 5 / 4 remotely |
  | **ROLLBACK INCOMPLETE** | exit 7, every surviving snapshot named next to the exact `zfs destroy` that removes it |

The reason is not lost when the state is stated, which is why the clean-rollback
exit keeps the diagnosing code instead of collapsing everything into one.

I did not take the alternative (mark incomplete sets and teach every send,
base-selection, prune and monitor path to ignore them). The review is right that
it is substantially more machinery; it is also more surface for exactly the kind
of silent-consumption defect this whole review series has been about.

## Remaining risk

`zfs destroy` on a snapshot can fail for reasons that outlive the run — a hold,
a clone, a dataset busy. That is precisely the case exit 7 exists for, and it is
tested; but the run cannot resolve it, so an operator has to. The message names
the snapshot and the command, which is the most the tool can honestly offer.

`snapsend`, `scenarios` and `remote` have still not been run for this commit or
the three before it: they need root, ZFS and a second host, and the VPN to both
clusters is down. No managed block on the fleet uses remote quiesce, and none
spans two pools in a single quiesced job, so the unverified code is not on a
path cron executes tonight. A mitigation, not a substitute.
