### Planned or implemented change

`snapsend.sh`: the check now runs when `common_snapshot != null` OR `bookmark_base` is set. On the
bookmark path `recv_base` is the target's head, the snapshot whose GUID the bookmark carries.

- backup landing: D3 discards, and says so;
- `written@` query failed: refuse;
- bytes written on a sync or `-t` target: refuse;
- snapshots only, nothing written: receive without `-F`.

### Round 2 — F4a-F4d IMPLEMENTED

#### Analysis

All four counterexamples are accepted. Revision 1 asked "is every commit an ancestor of some
named SHA". That question is wrong three ways. Ancestry is not scope (F4b). Non-merge commits are
not the whole delta (F4c). The candidate's path list is not the package change (F4d). F4a is
separate: the baseline was a mutable working file.

The gate now asks about the PACKAGE, not about commits. The question is: for every shipped
run-time file whose state differs between the published release and the candidate, do submitted
ranges lead from the old state to the new one? A file's state is its blob, or "not shipped".

#### Implemented change

- `release/package-list.sh` (new): resolves a revision's MANIFEST, the same way publish always
  did. `publish.sh` and the gate both use it.
- `release/coverage-gate.sh <dev> <published-rev> <rev> < ledger`:
  - A submission is a ledger row whose Implementation is in `rev`'s history and not yet
    published, and whose response names `<!-- base: <sha> -->`, an ancestor of the implementation.
  - A submission covers file X only as one step: state(base, X) -> state(impl, X), and only when
    the two differ.
  - X is covered when a chain of such steps leads from state(published, X) to state(rev, X).
  - F4b: a review of B does not change A's file, so it adds no step for that file.
  - F4c: a merge-only edit is a state no range reached. A mechanical merge reproduces a submitted
    state.
  - F4d: "not shipped" is a state, so a removal, a newly shipped file and a changed exclusion
    each need a step.
  - Docs, `*.md`, `LICENSE`, `.gitattributes` and `.github/` are not compared.
  - Each covered file is printed with the REVs that reached it. Each uncovered file is named with
    its kind (changed / newly shipped / no longer shipped) and the commits that touched it.
  - A response without `base:` covers nothing, and the gate says so.
- `publish.sh --push` (F4a) fetches the release repo's `origin` and reads `RELEASE-OF` from
  `refs/remotes/origin/main`, never from the checkout. A failed fetch, a missing `origin/main` or
  a missing `RELEASE-OF` refuses with the reason. Every local, not yet pushed commit lies between
  the published state and the candidate, so all of them are checked.
- `Reviewed` pointers no longer count. A CHANGES-REQUIRED verdict acknowledges a snapshot. It does
  not submit that snapshot's ancestry.
- From now on every response states its range with `<!-- base: <sha> -->`. Added here to REV-194
  (`d30fd5f0`) and REV-195 (`8be7e06d`, the parent of the first REV-195 commit `a66aca67`).
  PROTOCOL V3.14 revision 2 replaces the ancestry wording of revision 1.
- The docs-only fixture is fixed. Setup errors now fail the suite (`cw`), and the case first
  asserts that `docs/n.md` is in the commit.
