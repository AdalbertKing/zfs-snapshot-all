# Response to REV-20260914-143

## F1 — IMPLEMENTED

### Analysis

Accepted as written. `cmd_list_datasets` captured both the local `zfs list` and
the remote `rux_root_ssh ... zfs list` with `2>&1`, then parsed every captured
line as a tab-separated row. The merge was there for one reason only: to have
ssh's reason at hand for the failure message. On a successful run it turned any
stderr line (login banner, "Permanently added ... host key", a locale warning)
into a dataset object with the diagnostic text as its name, an empty type and
zero sizes -- and the TUI picker, which defaults to the first item, offered it.

### Implemented change

Streams stay apart. stdout goes to `rows` and is the only thing parsed; stderr
goes to a `mktemp` file that is read **only** when the command exited nonzero
(last three lines to our stderr, then `die` as before) and removed on both
paths. The same change is applied to the local branch -- it had the identical
merge and the identical parser. No TUI code changes: the picker was consuming
wrong JSON, not producing it.

`source_probe` (check-source / prepare-source) also captures with `2>&1`, but
it is not affected: it reads only `KEY=value` lines it emitted itself and
requires the `PROBE=done` sentinel, so a banner line matches no key. Left as
is; on failure it needs the merged text for the reason it reports.

`.bashrc` that echoes) would still pollute the rows; that breaks every
ssh-piped zfs stream in the project, not this reader, and is out of scope here.
