# Response to REV-20260810-092

## F1 — IMPLEMENTED

### Analysis

Accepted. The review is right about the defect and right that my own REV-091
guard could not have caught it: `91 F1: a policy-creating call still installs the
reserved-prefix floors` ran against a fixture containing nothing but
`[defaults]`. With no established task in the file, "installs the floors" and
"mutates shared policy" are the same observation. The guard proved the floor was
not silently dropped, which was its job, and proved nothing about ownership.

The mechanism is the part worth being precise about, because it is what makes
this a Gate 2 violation rather than a cosmetic one. `[excluded:]` is not a
section that belongs to anybody. `gen-cron.sh` resolves all of them **once**
into a single `PROTECT_FLAGS` fragment and concatenates it onto **every**
generated prune line in the file. So appending one missing floor during an
additive CREATE does not add something next to the existing relationships — it
rewrites the command line each of them will run tonight.

### The rule implemented

Exactly the reviewer's four bullets, and nothing wider:

| bullet | implementation |
|---|---|
| initializing a genuinely new CONFIG may install the standard defaults | new `config_has_relationship_policy()` — true when any `[dataset:]`/`[prune:]` section exists. The floors are laid down only when it is false, i.e. when there is no installed relationship for them to affect |
| explicit migration may deliberately change global policy with preview/confirmation | new fourth parameter `global_policy_mode`, default `auto`; `cmd_migrate_profile()` passes `always` |
| additive CREATE into a populated CONFIG reuses installed `[excluded:]` state exactly | the `auto` path appends nothing once the file carries relationship policy |
| refuse rather than mutate old policy silently | see below — the honest answer is that this case never arises |

#### On the refusal bullet

I did not add a refusal, and I want to be explicit about why rather than let its
absence look like an oversight.

`[excluded:]` is uniform global policy: whatever is installed applies identically
to every relationship in the file, old and new. A new relationship added under a
CONFIG missing a floor is therefore in exactly the state every existing
relationship is already in — there is no configuration in which the new one
"cannot be safely created" while the existing ones continue safely. Reuse is
always possible, so the refusal branch would be unreachable.

The review's own proof step 6 requires the same thing from the other direction:
*"prove B is added successfully if the existing global policy is acceptable"*,
in a scenario whose step 2 has removed a standard entry. A refusal on a missing
floor would fail that step.

#### One addition beyond the required minimum, flagged for rejection

Inheriting the installed policy is correct; inheriting it **silently** is not.
The new relationship is about to get a prune sweep that runs without a protection
this estate normally carries, and this project has already paid once for a prune
sweep meeting unprotected reserved snapshots. So the `auto` path, when it
declines to repair, emits a `warn` naming the absent floors and saying plainly
that they are not being repaired here because that would change every
relationship in the file.

A warning is neither a mutation nor a refusal, and `activate-client` shows its
full proposal before installing, so this adds no new authority. It is the one
thing here the review did not ask for; it is three lines and one assertion, and
I will remove it if you would rather the path stayed silent.

#### Where the boundary now sits for each caller

- `cmd_activate_client()` → `auto`. First relationship into a fresh CONFIG gets
  the defaults; every later relationship inherits what is installed.
- `cmd_setup_server()` → `auto` (unchanged call). A fresh host gets the defaults;
  re-running it against a populated CONFIG no longer repairs global policy, which
  is the same rule and, I think, a small improvement it inherits for free.
- `cmd_migrate_profile()` → `always`, deliberately. It is a previewed, confirmed
  transaction that shows the exact config and cron diff first, and it is the one
  command that **installs** the broad GFS ladder these floors exist to fence —
  leaving a legacy host with that ladder and no protection would be a real
  regression dressed up as purity.

The assertion is deliberately on the **rendered `delsnaps.sh` command**, not on
config text. `PROTECT_FLAGS` is a generator-side concatenation, so comparing
config sections would not test what Gate 2 actually promises — an operator does
not care whether a section moved, they care whether last night's prune command
changed. `92 step 3` pins that the removal is visible in the rendered line first,
so `92 step 5`'s "unchanged" cannot pass vacuously against a line that never
carried the flag.

### Remaining risk

- **`zfsbackup-live-pair` not run.** Deterministic CONFIG composition only: no
  install/rollback semantics, no transfer, no host state. Per the review's
  evidence boundary, no live campaign required. Left `IMPLEMENTED`, not `CLOSED`.
- **A CONFIG can now stay permanently without a floor** an operator removed,
  including for relationships added later. That is the intent — it is their
  policy decision, applied uniformly — but it is a real behavioural change from
  "the tool quietly keeps putting it back", and the warning is the only thing
  that surfaces it. If the project would rather this be loud at a different
  moment (say, `status`), that is a small follow-up rather than part of this fix.
- **`setup-server` re-run against a populated CONFIG** no longer restores global
  floors. I believe that is correct under the same rule and is covered by the
  same code path, but it is a behaviour change to a second command, so I am
  naming it rather than leaving it to be discovered.
