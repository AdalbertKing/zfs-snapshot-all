## F1 — IMPLEMENTED

### Analysis

Accepted in full, including the part that is easy to argue away. The command did
return nonzero, and that is not the property. The property is that a refusal
leaves the reviewer's fact byte-identical, because the next run reads the
artifact, not the exit code. A transaction that mutates and then reports failure
without restoring has done something worse than not existing: it looks like a
guard in review.

The mechanism is exactly as described. `tx_guard` appended the path to
`TX_FILES` and then ran `mkdir -p`, `cp -p`, or the absent-list append with no
result checked. A failed snapshot therefore produced an entry in `TX_FILES` with
no file under `present/` and no line under `absent/` — and `tx_restore`'s two
branches are keyed on exactly those two artifacts, so neither matched. It
silently skipped the path, `tx_cleanup` removed the only remaining copy, and the
verdict stayed flipped.

`tx_restore` ignoring its own `cp`/`rm` results and `tx_cleanup` deleting
unconditionally is the same failure on the other side of the mutation boundary,
and I am treating it as one finding rather than two because a fix to either half
alone still loses data.

### Implemented change

`test/reviewctl.sh`.

**Snapshot is a hard precondition.** Every `mkdir -p`, `cp -p` and absent-list
append is checked, and any failure calls `tx_die` *before* the writer touches a
live artifact. The copy is additionally verified to exist afterwards, because a
`cp` that reports success and produces nothing would otherwise reintroduce the
same hole one layer down. A path joins `TX_FILES` only **after** its snapshot
exists, so `tx_restore`'s invariant now holds by construction: every entry has
either a `present/` copy or an `absent/` record.

**Restoration checks every operation.** `tx_restore` returns nonzero if any path
could not be put back and prints `UNRECOVERED: <path>` for each one, naming the
backup it should be restored from.

**The backup survives a failed restoration.** `tx_cleanup` deletes the
transaction directory only when it is provably no longer needed. On a nonzero
`tx_restore` it keeps it and says where it is, because at that moment it holds
the only intact copy of the reviewer's facts.

### Implemented change

X1 now digests five surfaces before the run and compares each independently, so
any one of them fails the case on its own: the role artifact, `REVIEW_LEDGER.md`,
`OPEN-THREADS.md`, and the real repository's working tree and index. The last two
are taken from the real checkout because the throwaway world is not a git repo;
every git call `reviewctl` makes today is read-only, so they are a tripwire for a
future writer that starts staging rather than a restatement.

### Which of them discriminate, measured rather than claimed

Against canonical `test/reviewctl.sh`, X1's ledger, routing-view, tree and index
assertions **do not** discriminate, and I am not going to present them as if they
did. The reason is structural: the views are written only by `--generate`, which
refuses in this world, so they never move on either build.

So the control the reviewer asked for -- one that detects the canonical failure
on a surface other than the role artifact -- is **X3**, added for it. It fails
the snapshot of `DELIVERIES.md`, a file `approve` genuinely writes, and then
proves that same file is byte-identical. That pairing is what discriminates,
because `tx_restore` can only put back what `tx_guard` managed to copy: the
surface whose snapshot failed is exactly the one the old code left mutated with
no way home.

An earlier cut of X3 aimed at the ledger and did NOT discriminate, for the reason
above. It is recorded in the suite rather than quietly replaced -- a control that
cannot fail is what this whole round is about.
