## F1 — IMPLEMENTED

### Analysis

Accepted without reservation. The verb committed the config and both crontabs
through `atomic_replace_and_install` and only then appended to the two client
records, with either append failure reduced to `warn`. Execution continued into
pausing the old relationship and printing the successful final state.

The reviewer's reading of the consequence is the one that matters: `status`, a
second `move-to-client` and `remove-client` all read those records, so a failed
append does not merely lose a line — it leaves the next administrative action
operating on ownership that is false in a specific, actionable direction. The
destination owns sections its record disclaims, or both records claim the same
datasets.

### Implemented change

`zfs-backup.sh` `cmd_move_to_client`. Both records are now written IN FULL into
temporary files in the same directory as the originals, before a single live
byte is replaced. Writing them there is what proves the directory is writable
and has room; what remains after the install is a rename within one directory.

Byte copies of the config, both records and the target's crontab are taken for
rollback, because `atomic_replace_and_install` discards its own backups once it
succeeds. If either rename still fails, all five are put back and the command
dies with `NOTHING was moved. '<from>' has NOT been paused`. The pause is
unreachable from every failure path.

### Evidence

- commit: on `3bfe5ff`; the ordering is `to_tmp="$(mktemp ...)"` before
  `atomic_replace_and_install`
- `./test/moveclient/run.sh` — **35/0**

Two of the new assertions discriminate against `3a78b1dc` and two do not, and
the suite says so in its own comments rather than presenting four passes as four
proofs:

- **discriminating**: the record contents are prepared before
  `atomic_replace_and_install` is called at all (asserted on the source, because
  no stub can prove an ordering that only shows itself when a disk fills up
  mid-command); and a failed rename carries a rollback path.
- **not discriminating**: the four assertions driven through the real verb with
  an unwritable records directory. On `3a78b1dc` the verb also refuses there —
  earlier, at config resolution, for a different reason — so they pass on both
  SHAs. They still pin that a refusal never pauses and never prints success.

### Remaining risk — criterion 3 is NOT fully met

The review asks each injected failure to **prove byte restoration** of the
config, both client records and both crontabs, and to prove the pause state is
unchanged. That needs the verb driven all the way to publication, which needs a
real config, real records, a real crontab and the account's `gen-cron`. That is
a lab, it is declared as the manual obligation `moveclient-live`, and it has
**not been run**. Leaving this finding `IMPLEMENTED`, not closed.

## F2 — IMPLEMENTED

### Analysis

Accepted. The whole state write ended in `|| :`, so an unwritable state
directory produced exit 0 plus the message that this run would export the pool
again, while leaving no `imported-by-us` marker. `detach` then read the missing
marker as somebody else's import, left the pool active, and also exited 0 — a
successful bracket leaving a pool imported while the job reports success, which
is precisely when an operator believes the disk is safe to unplug.

### Implemented change

`zfs-media-gate.sh`. Failure to record ownership after a successful import is a
hard error. The error path first tries to put the machine back by exporting; if
that succeeds the run reports that nothing was transferred and exits 2, and if
it fails the message retains `DO NOT UNPLUG THE DISK` and still exits 2.

### Evidence

- `./test/mediagate/run.sh` — **48/0**, including section F2's cases driven with
  `MEDIA_STATE_DIR` pointing at an unwritable path, for both the successful and
  the failed compensating export. Both fail on the reviewed SHA.

## Beyond the four findings — the removable-media lab

The manual obligation `mediagate-live` has been discharged on pve0 and is
recorded in `docs/PROJECT_STATUS.md`. It found four defects, none of which the
stub suite could see, and all four are fixed with negative controls:

| | defect |
|---|---|
| M1 | `zpool import` scans `/dev` by default, so a disk that IS present but outside that path read as absent and the job skipped for ever without saying anything was amiss. `--dir` added. |
| M2 | `detach` asked who owned the pool before asking whether the pool was there, so the commonest case of all — the disk in a safe — was answered with `leaving POOL imported`. That sentence names the one state in which unplugging corrupts the replica. The suite passed on both orders. |
| M3 | the generated bracket was emitted as a command SEQUENCE into a slot `job_cron_line` builds for ONE command, so `2>"$e"` and `rc=$?` bound to `detach` alone: the engine's stderr went to cron's own stderr and a failed transfer logged `rc=0` with no mail. Measured live: engine 1, line 0. |
| M4 | the gate was handed the LANDING path, which the engine creates, so a freshly prepared disk was refused as the wrong medium on its first sync — and after M3's fix, that refusal alerts. A new removable disk could never be seeded. |

M3 and M4 share one cause: the suite tested the gate and never the line that
comes out of the generator. Section G of `test/mediagate/run.sh` now renders the
real line with the real `gen-cron.sh` and runs it, stubbing only the gate and
the engine.
