# Response to REV-20260807-068

## F1 — IMPLEMENTED

### Analysis

Correct, and it is my own false claim that made it visible: `eea6339`'s commit
message reports `./test/impact.sh --verify consistent` while the commit it
created carries a marker that is behind it. The run happened and returned clean.
The claim I built on it was wrong.

The root cause is the one the review names. The marker identified a **commit**,
and a commit cannot contain its own hash, so the property was only ever
checkable *after* the boundary it was being cited to guard.

### Implemented change — the reviewer's second option

The invariant is now a digest over the **content** of every file that declares
the `project-status` obligation:

    <!-- status-covers-digest: e4c05a332a488b55 -->

Why this closes the lifecycle gap rather than moving it:

- it is computable from the working tree **before** the commit, so the
  pre-stage gate proves the real property;
- it is **unchanged by** the act of committing, so the same run stays true
  afterwards — no second verification step to remember;
- there is no self-reference: `PROJECT_STATUS.md` is not itself watched, so
  writing the digest into it does not change the digest.

It is also strictly stronger than what it replaces: it fails on a watched edit
that has not been committed at all, which the commit marker could not see.

`--refresh-status` writes it. That half is not convenience — without a command
that can satisfy the invariant, the only way to meet it is a human remembering
to act, which is the mechanism class Stage 1 was created to remove. The
sequence is one commit: edit, refresh, stage together, commit.

The legacy marker is refused with a message naming this review and the command
to run, rather than being silently ignored.

**What the redesign loses, stated plainly.** A digest cannot say what went into
it, so the old `STALE. These behaviour-changing commits landed after the
marker` message is gone. It is replaced by a hint listing watched files whose
content differs from their version at the commit that last touched
`PROJECT_STATUS.md` — labelled as a hint and never part of the verdict, because
it is a heuristic and the digest is not.

### Evidence

- commit: `41bd774ae761751c3160e3ec8c8dd94f2a8f2c84`
- `./test/impact/run.sh` → **27/27** (+7). Each case is a throwaway git repo
  holding a **copy of the script under test**, so its own `$REPO` resolves
  there with no override and the same construction runs the control.
- pinned: an up-to-date status on a clean tree is accepted; a **pending**
  watched change is not clean; **staging** it does not launder it; a
  **committed** watched change without a refresh is still stale (the REV-061
  property); `--refresh-status` makes it clean **before** the commit and it is
  still clean **after**; an unwatched file demands nothing.
- negative control vs `eea6339`: **4 assertions fail**, including both decisive
  ones (pending, staged), while the committed-stale case **passes** against the

- `./test/impact.sh --verify` clean on this committed state.
- no ZFS, SSH, root or fleet run, per the review.

**One case in that control does not discriminate and I am not counting it as
evidence:** "refresh-status makes a pending change clean before the commit"
also passes against the old implementation, because the fallback marker it is
given happens to be current there. The two cases that carry the finding are the
pending and staged ones.

### Two contaminated controls before this one

Recorded because both are the same failure mode as the finding — a green result
that measured something other than the property:

1. the first control gave the old script no marker it understood (it has no
   `--refresh-status`), so **every** case came back NOT-CLEAN and the
   pending-change case "passed", appearing to show there was nothing to fix;
2. the second still failed, because the pre-REV-068 gate resolves `git`
   against the **current directory** rather than `$REPO` — run from the real
   repository it measured the real repository, and reported the throwaway
   world's marker as "not a commit in this repository".

Both are documented in `test/impact/run.sh` where the next person will hit them.

### Remaining risk

The digest covers content, so a watched file changing for a **non-behavioural**
reason — a comment, a typo — now demands a status refresh where the commit
marker's `git log` filter did not. That is stricter than the obligation
strictly requires. I chose it deliberately: the alternative is a checker
deciding what counts as "behavioural", which is judgement, and judgement in a
gate is how the old one came to certify something it had not checked.

The gate proves the document is **synchronised** with the watched files. It
cannot prove the prose is **true**. That remains a manual obligation and this
change does not narrow it.

# Round 3 — response to the rejection of `41bd774`

## F1 — IMPLEMENTED (again)

### Analysis

The rejection is correct and the reasoning is exact. My round-2 fix removed the
commit-SHA problem and then measured the wrong tree. `git commit` records the
**index**; `status_digest()` hashed the **working tree**. The two coincide most
of the time, which is what made it feel safe, and the review's step-by-step is a
real sequence, not a hypothetical:

    git add engine.sh                 # index = NEW
    ./test/impact.sh --refresh-status # working-tree status = NEW digest
    #   (PROJECT_STATUS.md left unstaged)
    ./test/impact.sh --verify         # CLEAN -- worktree is self-consistent
    git commit                        # records NEW behaviour + OLD status

Same class as round 1: the gate certifies something other than what crosses the
boundary.

### Implemented change

Everything the verdict rests on is now read from the index:

| input | source |
|---|---|
| watched blobs | `git rev-parse :<path>` |
| `PROJECT_STATUS.md` carrying the marker | `git cat-file blob :<status>` |
| `deps.conf` defining the watched set | staged blob, parsed from the index |

The last row matters as much as the first: a config change that widens or
narrows the watched set is itself part of what is about to land, so reading it
from the working tree would reintroduce the split one level up.

`--refresh-status` still writes the working-tree file, as permitted, but it
computes the digest **from the index**, and `--verify` fails closed until that
refreshed file is staged. A status file absent from the index is refused with
that reason named, rather than treated as a missing marker.

The enforced sequence, which is now the one the tool prints:

    git add <intended behaviour/config changes>
    ./test/impact.sh --refresh-status
    git add docs/PROJECT_STATUS.md
    ./test/impact.sh --verify
    git commit

**The guarantee, and its boundary.** If a normal `git commit` runs immediately
after a successful `--verify` without changing the index, the committed tree
satisfies the invariant. `git commit -a`, `git commit <path>` and `--amend` all
move the index after verification and are therefore outside it. I have written
that into the code rather than leaving it as an assumption a reader has to
reconstruct.

### One case from round 2 is REVERSED

Round 2 pinned "a pending working-tree change is not clean". That is now wrong
and is deliberately inverted: an unstaged edit is not in the next commit, so it
cannot make that commit stale.

I want to be plain about why this is not a weakening. The round-2 invariant
failed on edits the commit would **not** contain, and passed the split that the
commit **would** contain. It was stricter about the wrong thing, which reads as
a safety margin and is not one.

### Evidence

- commit: `c077b8250ab49ad210ab0a9284766ed10b58391e`
- `./test/impact/run.sh` → **32/32** (+5)
- decisive case pinned twice: the staged-change/unstaged-status split is
  refused, **and** committing exactly what was staged is then shown to leave a
  stale tree — the consequence demonstrated, not argued
- also pinned: staging the refreshed status makes it clean and the tree it
  commits is clean; moving the index afterwards invalidates it; a staged
  `deps.conf` widening the watched set is seen; the REV-061 committed-stale case
  is still rejected; an unwatched file demands nothing
- negative control vs `41bd774`: **3 assertions fail** — the split, its
  consequence, and the reversed unstaged case — while the clean-tree and
  REV-061 cases still **pass** there
- `./test/impact.sh --verify` clean on this committed state, reached through the
  enforced sequence above
- no ZFS, SSH, root or fleet run, per the review

**Which new cases do NOT discriminate, so they are not offered as evidence:**
"staging a further watched change invalidates it" and "a staged `deps.conf` that
widens the watched set is seen" also pass against `41bd774`, because those
scenarios move the working tree as well. They are regression cover.

### Remaining risk

The suite's world builder had to stage before refreshing — with an index-derived
marker there is nothing to hash before `git add`. That is a real ergonomic
change for a first-ever commit in a fresh repository, and the refusal says so.

A watched file changing for a non-behavioural reason still demands a refresh, as
in round 2, and for the same reason: the alternative is a gate exercising
judgement about what counts as behavioural, which is how the original one came
to certify something it had not checked.
