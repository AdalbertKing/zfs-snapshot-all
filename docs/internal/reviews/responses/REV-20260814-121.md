# Response to REV-20260814-121

## F1 — ACCEPTED and IMPLEMENTED

This is the residual I flagged in the REV-120 round-1 response, now correctly
separated into its own finding. I said then that it was the same unsound rule one
step earlier and that fixing it needed a decision about which notion of "latest"
the owner's policy means. The review makes that decision explicitly, and it is the
one I would have argued for.

### Analysis

`tail -1` over a `creation`-sorted listing answers "which of two equal rows did
ZFS print last". Under REV-120 F2 that produced a wrong verdict about a restore
that had already happened. Here it produces something worse: the wrong *target* —
the point the source gets rolled back to — chosen by incidental list order and
never surfaced as a choice at all.

The axis is not the problem, and I agree it must not move. On a backup copy every
snapshot arrived by receive, so `createtxg` is arrival order; `creation` is when
the data was captured, which is what "the latest backup recovery point" means in
`OWNER-RECOVERY-DEFAULT-POLICY-2026-08-12`. Silently swapping them would change
policy while looking like a bug fix. The problem is only what happens when the
axis does not decide.

### Implemented change

`restore_plan_strategy` now:

1. computes the maximum `creation` across the copy's snapshots;
2. collects every row carrying it;
3. selects when exactly one does;
4. otherwise sets `RESTORE_STRATEGY=ambiguous`, prints the tied candidates with
   their GUIDs, and explains that one-second resolution is why the answer is not
   available — before any mutation, fence or confirmation, since this happens in
   the preview the destructive path shares with `--plan`.

The destructive verb refuses on `ambiguous` by name, saying that guessing would
destroy state under a decision nobody took.

Rows whose `creation` cannot be read as a number never enter the maximum, so a
copy with unreadable capture times resolves to zero candidates and is ambiguous
too — the same fail-closed direction as REV-120's unproven loss set.

### Evidence

- commit/PR: see the machine header above.
- suites, pve0/zfs-2.1.9: `restore` **108/108**, `zfsbackup` **401/401**,
  `localbackup` **57/57**.
- **Targeted fixture** (acceptance 1): two copy snapshots share the maximum
  `creation`, adverse names. The run refuses, names both candidates with their
  GUIDs, prints no loss set, takes no technical snapshot, and leaves the source
  snapshot count unchanged — so the ambiguity is stated before any mutation
  (acceptance 3).
- **Unique maximum still selects the expected GUID** and runs to completion
  (acceptance 2).
- **Two further controls**, because a guard that refuses too much is also broken:
  a tie *below* the maximum is not an ambiguity — refusing there would stop the
  verb working on any busy backup — and unreadable capture times are an ambiguity
  rather than an empty maximum.
- **No `tail -1` remains in recovery-target selection** (acceptance 4): asserted
  against the planner's own source, comments excluded, so the next listing added
  there cannot quietly reach for it again.
- **REV-120's properties are untouched** (acceptance 5): the GUID-proven common
  base, the createtxg-anchored loss set and the identity-anchored final state are
  unchanged, and the same suite run covers them.
- No live campaign, per the review. The REV-120 transcripts already establish both
  premises: same-second `creation` occurs on real hosts, and `zfs recv` preserves
  the sender's `creation` while assigning a fresh local `createtxg`.

### Remaining risk

An operator whose copy genuinely holds two snapshots captured in the same second
now cannot run the default recovery at all until the public grammar gives them a
way to name the point explicitly. That is deliberate — the alternative is a
destructive operation choosing its own target — but it is a real operational edge,
and it is the strongest argument for the `--at=TIME` selector the review defers.
The refusal names both candidates precisely so the operator can resolve it on the
copy side meanwhile.

The tie test is applied to the copy's snapshot set as the planner receives it. If
a future caller ever passes a pre-filtered set, the ambiguity check inherits that
filter. Nothing does today, and `restore_relations` remains the single authority
on where a copy lives.
