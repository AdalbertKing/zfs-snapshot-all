## F2 — IMPLEMENTED (unreadable queue returned success against the contract)

### Analysis

Confirmed, and the hole was wider than the finding's own example. Three
shapes of "cannot inspect the queue" all ended `audit clean`:

1. the branch the review quotes: `mail_queue_depth` emits nothing
   (sendmail(8) present but neither postfix nor exim4), `log()` + `return 0`;
2. **a `postqueue` that itself fails**: its empty output still flowed through
   the awk reducer, whose `END {if (!f) print 0}` turned "the command died"
   into a literal `0` — an uninspectable queue read back as an EMPTY one, so
   the verdict never even reached its unreadable branch;
3. non-numeric queue output: `[ "$q" -gt 0 ] 2>/dev/null` fails for garbage,
   which fell through to the healthy branch and (before the F1 fix) printed
   `this host can send` for a queue depth of `mailq: command garbage`.

### Planned or implemented change

`deploy.sh` commit `c668b51`:

- `mail_queue_depth()` checks `postqueue`'s exit status before any counting;
  a failed queue command emits nothing (the documented "could not tell"),
  never a synthesized `0`;
- `alert_delivery_verdict()` folds empty and non-numeric depth into one
  fail-closed branch: `warn()` (which feeds the global `PROBLEMS`) + `return 1`,
  wording `alert delivery UNVERIFIED: ... dispatch is unproven, not proven`.
  `--check-only` on such a host now exits non-zero, matching the function's
  contract comment, which was rewritten in `b4de04a` to state the whole
  passive/active split explicitly.

### Evidence

- commit: `c668b51`
- commands run: `bash test/alertmail/run.sh` (HEAD) and
  `DEPLOY_SRC=<a567328's deploy.sh> bash test/alertmail/run.sh` (reviewed base)
- results: HEAD 18/18. On the reviewed base the three F2 regression cases
  fail exactly as claimed: `unreadable queue is non-clean` got `rc=0
  problems=0`; `non-numeric output fails closed` got `rc=0 problems=0` with
  the base printing `queue empty -- this host can send` for garbage input;
  `mail_queue_depth emits nothing when postqueue fails` got a synthesized `0`.

### Remaining risk

An MTA whose queue tool succeeds but lies (prints `0` with mail actually
waiting) is indistinguishable from a healthy host at this layer. Accepted:
the audit trusts the queue tool's output when the tool itself succeeds.

## F3 — IMPLEMENTED (post-send drain is local dispatch, not delivery)

### Analysis

Confirmed on both halves. `queue empty after the send -- the MTA accepted
and dispatched it` overstated a three-second local observation (a smarthost
can bounce later, a bounce can arrive after the window). Separately, the
submission itself was fire-and-forget: `mail(1)` could exit non-zero and the
run still pointed the operator at an inbox.

### Planned or implemented change

`deploy.sh` commit `d859af5`. The Phase 4 inline block became
`alert_delivery_probe()` (extractable, so the claims are pinned by tests):

- submission failure: `warn` + `return 1`
  (`the test message was NOT ACCEPTED: mail(1) exited non-zero`);
- still queued: unchanged hard warning, now also `return 1`;
- drained: `local queue empty after the submission -- the message LEFT THIS
  MTA; recipient delivery is NOT independently verified. Confirm arrival at
  <addr>.` — the bounded statement the review prescribes;
- unreadable-after-send stays bounded to "mail(1) accepted it", and
  non-numeric output now lands there instead of sliding past `[ -gt 0 ]`
  into the positive branch (same fail-closed shape as F2).

No end-to-end acknowledgement mechanism was added; none is claimed.

### Evidence

- commit: `d859af5`
- commands run: `bash test/alertmail/run.sh`

  drained branch never says `accepted and dispatched` / `can send`. (These
