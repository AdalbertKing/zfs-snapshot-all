## F1 (§2) — a window is not a correlation — ACCEPTED, claim retracted

### Analysis

The finding is correct and I had this wrong in the direction that matters.

`sqlfreeze` answers *"did SQL participate in at least one freeze/resume inside
this window"*. I wrote it up as if it answered *"did this backup freeze SQL"*.
Those differ by exactly the property nothing in the data supplies: an event
carries no requester identity, so on a guest where pvesr (2-hourly), snapsend
(nightly) and a human all quiesce the same VM, a neighbouring operation's events
sitting inside the window produce `engaged` for a run that never reached its
snapshot at all.

vsql2 is the worst possible host for that confusion, because those three callers
overlap there constantly — which is precisely why it is the host I drew the
conclusion from.

The 20-hour balanced totals are also weaker than I made them sound. 227/227 and
187/187 prove that nothing froze without resuming across the period. They do not
partition into pairs per backup, and I presented an aggregate as if it were a
per-run result.

### Implemented change

I have taken option (a): `sqlfreeze` stays a manual diagnostic and now says so
where it cannot be missed. The verdict line ships the review's wording verbatim:

```
SQLFREEZE-NOTE SQL participated in at least one VSS freeze/resume within the
selected window. This is not correlated to a specific snapshot run.
SQLFREEZE-NOTE counted per instance, not per database; engaged does not prove
the snapshot restores
```

The caveat travels with the data rather than living only in documentation,
because a verdict line is what gets pasted into a ticket.

Corrected in the same pass, since a retraction that leaves the original claim

### Not implemented: per-run correlation

§2's numbered design is right, and I have deliberately not built it here. Two
reasons, both worth your disagreement if you see it differently.

It is not a change to `sqlfreeze`. Steps 1–3 require the read to happen inside
the same remote operation as the freeze, and the freeze lives in `snapget -q`'s
single-SSH freeze/snapshot/thaw path, not in this verb. Bolting a "before" read
onto a separate helper invocation gives a window between two calls that a foreign
job can fill — the exact hole §2's last sentence warns about. So the correlated
version belongs in the quiesce path as a new verb pair, sequenced by the caller
that already owns the atomic window.

And it is new privileged surface, which §5 asks to hold until REV-009 closes.
That is your call to make, not mine to assume.

## F3 (§4) — granularity — IMPLEMENTED

Answering the four questions directly:

- **Databases, instances, or both?** Instances only. `Group-Object ProviderName`
  groups by event provider: `MSSQLSERVER` for the default instance, `MSSQL$<name>`
  for a named one.
- **Is one good database enough for `engaged`?** The verb never sees databases. It
  requires every instance that logged anything to be balanced, and `engaged` means
  "at least one instance participated, and none of them froze without resuming".
- **Offline / restoring / unavailable databases?** Invisible. They log no 3197, so
  they cannot be missed by counting — a fully offline database and one that was
  never asked to freeze look identical.
- **Is the expected instance list known beforehand?** No. There is no notion of
  what *should* have appeared, so `engaged` cannot mean "the whole intended scope
  was frozen".

The per-database granularity the docs implied is not a small step away — it is on
the far side of the locale rule. The database name exists only in the message
TEXT, which is translated on this estate, and parsing translated text is the exact
bug that produced `total=0` in `writers`. Choosing per-instance counting is a
consequence of that, so the honest fix was to correct the documentation, which is
now explicit in the helper header, in the `SQLFREEZE-NOTE` output and in
`deps.conf`.
