# Response to REV-20261016-147

## F1 — IMPLEMENTED

### Analysis

Accepted as written. I introduced the defect myself in PR #551 (`e502b130`).
That PR moved the fail-closed decision onto the revocation's outcome but left
`rm -f "$gpath"` *before* `zfs unallow`. A failed revocation therefore
destroyed the only record of what remained to revoke. The next `--deny-restore`
fell into the "no grant -- nothing to take back" branch, resumed the writers
and returned 0.

My #551 notes framed the missing-file path as "someone removed the file by
hand". As the review says, the CLI itself produced that state on every failed
revocation.

I reproduced it with the reviewer's script on `main` (`757c5d9c` tree) before
changing anything:

```text
allow rc=0 grant=yes paused=yes unallow_calls=0
first_deny rc=1 grant=no paused=yes unallow_calls=2
retry_deny rc=0 grant=no paused=no unallow_calls=2
```

The success control (`TEST_UNALLOW_FAIL=0`) behaved correctly there too.

### Implemented change

Code in `deploy.sh` only (`do_deny_restore`, `do_allow_restore`, two helpers); tests in
`test/restoregrant/run.sh`:

1. **The grant is moved, not unlinked.** `--deny-restore` renames
   `RESTORE_GRANT_DIR/<label>` to `RESTORE_REVOKE_DIR/<label>`. The default for
   `RESTORE_REVOKE_DIR` is `${RESTORE_GRANT_DIR}.revoking`, a sibling directory,
   root-only (0700). The rename stays on one filesystem, so it is atomic. The
   gate reads only `RESTORE_GRANT_DIR/<label>`, so the declaration is withdrawn
   at once. The record keeps the facts needed for the retry: the scope
   (`RESTORE_GRANT_DATASETS`, written at grant time), **the account**
   (`RESTORE_REVOKE_ACCOUNT`, appended at withdrawal, because the grant file
   never named it) and P10's `RESTORE_GRANT_MOUNTED`. The retry takes the
   account and the scope **from the record first**, so it revokes what was
   actually delegated even if the pairing manifest is gone or edited. The
   manifest only fills a gap: a record from before the account line, or the
   legacy state. It is a separate directory rather than a suffix, because
   labels may contain dots.
2. **The record goes only after the revocation is proven.** The rule for
   "proven" is unchanged from #551:
   - every scope `unallow` succeeded, or failed on a dataset that no longer
     exists;
   - every namespace `unallow` succeeded;
   - the manifest supplied the account and the datasets.

   On success the record is removed and `resume-writers` releases only the
   pauses tagged `PAUSED_BY_GRANT=<label>`. P10's remount runs before the
   outcome check in both cases, since mounting is root's and does not widen
   the collector's capability. On failure the
   record stays, the pauses stay, the exit status is 1, and the message says
   to run the same command again. The old hint to call `resume-writers` by hand
   is gone, because it was a second way around the guard.
3. **The retry retries.** With no grant file but a record present,
   `--deny-restore` runs the full revocation again from the record and the
   manifest. It never reaches the "nothing to take back" no-op.
4. **The already-published partial state** (criterion 4). Older code left no
   grant file and no record, but still left pauses tagged with this grant. That
   combination is now treated as "revocation not proven":
   - the revocation is attempted again from the pairing manifest;
   - pauses are released only if it succeeds;
   - with no facts at all (no record, no usable manifest) it revokes nothing,
     keeps the pauses, returns 1 and names the manual way: `zfs allow`,
     `zfs unallow` by hand, then `resume-writers`. It does **not** advise a
     retry that cannot succeed.

   With no file, no record and no grant-owned pause, the call is still the
   harmless no-op (criterion 3's repeated-denial case).
5. **No success line over a failure** (criterion 2). The scope's `revoked: …`
   line is printed only when no scope `unallow` failed. The per-namespace lines
   report each namespace on its own, success or failure, and the run's verdict
   is the final line. A failed run ends with
   `WITHDRAWN -- the collector is refused new restores` plus the "NOT proven
   revoked … STAY PAUSED … run the same command again" warning, never with
   `TAKEN BACK`.
6. **No new grant over a pending revocation.** `--allow-restore=<label>`
   refuses while `RESTORE_REVOKE_DIR/<label>` exists and names the command that
   finishes the revocation. A fresh grant would otherwise either race the
   pending record or overwrite the facts it needs.

The scope stayed limited to revocation ordering and retry evidence: no engine,
GUI or gate change.

### Remaining risk

- I could not make a real `zfs unallow` fail on the lab. The failure branch is
  proven with the stub (the reviewer's and section 15); the success and
  idempotence semantics are measured on real ZFS.
- A grant issued before this change and denied *successfully* by the old code
  leaves nothing behind, so it needs no migration. A grant denied
  *unsuccessfully* by the old code is the legacy state in item 4. It is
  recovered only if its grant-owned pauses still exist. If someone resumed
  them by hand meanwhile, nothing on the host says a revocation is pending, and
  `zfs allow <scope>` is the only evidence. I cannot detect that case from
  local state without trusting `zfs allow` output parsing, which is outside
  this scope.
- PR #560 must merge first (or together). This implementation includes its
  commits.
