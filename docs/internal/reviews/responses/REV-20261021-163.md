# Response to REV-20261021-163

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `new_account_drop_inherited_grants` read the inventory
through `< <(zfs list ... 2>/dev/null)`. The loop's status is the status of
`read`, not of `zfs list`. Every ACL was read through
`zfs allow ... 2>/dev/null | grep -q`, where the pipeline status is the status
of `grep`. So a failed inventory looked like an empty one, and a failed ACL
read looked like "no grant for this account".

There was a second, related hole in the call sites. Both call sites skip the
guard when the account already exists ("already exists, leaving it alone").
After any guard failure the account stayed behind, so a re-run would take it
as an existing account and never run the check again. The old `unallow`
failure message even said "re-run".

### Implemented change

`deploy.sh`:

- **Reads are captured and checked.** `list="$(zfs list -H -o name -t
  filesystem,volume)"` and, per dataset, `acl="$(zfs allow "$ds")"` are each
  tested with `if !`. `zfs` stderr is no longer discarded, so the diagnostic is
  visible. The match runs on the captured text, and the loop reads
  `<<< "$list"` instead of a process substitution.
- **Every failure stops the run and removes the new account.**
  `new_account_abort` covers three failures: `zfs list`, `zfs allow` and
  `zfs unallow`. It runs `userdel -r` on the account just created and dies
  with the reason. "Nothing else was changed" holds because both call sites
  invoke the guard right after
    `useradd`, `passwd -l` and the "created …" log line, before the
  home `.ssh`, lock directory, grants, manifest or keys are created.
  - A re-run therefore creates the account again and checks again.
  - If `userdel` fails too, the message says to remove the account by hand
    before re-running, and why.
- The revoke-failure message now gives the hand command by **uid**
  (`zfs unallow -u <uid> <ds>`). After `userdel` the name no longer resolves,
  but the stale delegation is still keyed by that uid.
- **Unchanged:**
  - a clean inventory still returns 0 and keeps the account;
  - an inherited grant is still revoked, warned about, and returns 0;
  - another account's grant is left alone.

  this round. The original U42 live measurement on pve11 (2026-10-20) covered
  the revoke path, not read failures. A live read failure cannot be produced
  safely without breaking `zfs` on the host.
