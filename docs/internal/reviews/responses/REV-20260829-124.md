## F1 — IMPLEMENTED

### Analysis

Accepted, and the reviewer's framing is the correct one: the already-imported
branch was written as if "this pool is imported" implied "somebody else imported
it". That is true exactly once — when we never imported it. It is false after
our own run was interrupted between `attach` and `detach`, and in that state the
marker is the only fact that says the pool is ours to put away.

`rm -f "$OURS"` therefore destroyed the sole piece of evidence and converted a
package-owned import into an apparently foreign one. The consequence compounds
rather than repeating: the following `detach` reports success without exporting,
and so does every retry after it, so the removable pool stays live indefinitely
while the bracket keeps telling the operator the disk is safe to unplug. That is
the precise moment a replica gets corrupted.

The suite could not have caught it. Every case in it looked at a single run;
this defect only exists across two.

### Implemented change

`zfs-media-gate.sh`.

The marker now records the pool's GUID (`pool=` / `guid=`), and `marker_is_ours`
returns three distinct answers rather than a boolean:

| | meaning | what `attach` does |
|---|---|---|
| 0 | a marker exists and its GUID matches the pool in the slot | our interrupted run resuming. The marker **stays**; this run will export |
| 1 | no marker | a foreign import. Left alone, exactly as before |
| 2 | a marker exists that cannot be confirmed against this pool | **refuse, exit 2** |

Answer 2 covers the reviewer's criterion 4. A GUID mismatch means a different
disk of the same name is in the slot while we still owe an export on another one
— reachable, because rotated media routinely share a pool name. Exporting would
hit the wrong disk and clearing the marker would discard the only record that an
export is owed, so the gate stops and says which GUID it holds and which it
found.

### Residual risk, stated rather than implied

One case remains indistinguishable: our run died, an operator exported the pool
and imported it again themselves, and the GUID is naturally identical. We will
treat that as ours and export it. Nothing observable separates the two states,
criterion 1 asks for exactly this behaviour, and the window is only ever open
between an interrupted `attach` and the next run. It is recorded in the source
next to the function rather than left for the next reader to rediscover.

### Implemented change

`zfs-backup.sh` `cmd_pause_client` now states the real boundary:

- **covered**: the labeled transfer, monitor and prune jobs, on the source as
  well as the target, exiting before any listing, SSH or destroy;
- **not covered**: an engine invoked by hand without `-L`. That is left in
  deliberately and named as such. The pause is a property of the relationship
  label, so a manual run that does not name the label is outside it by
  construction — the pause exists to stop the schedule, not to take the machine
  away from the administrator sitting at it. Replacing one untrue reassurance
  with another would have been a worse outcome than the original defect.

`gen-cron.sh`'s comment claiming the `delsnaps` line "is never gated by logical
pause" is corrected in place, with the reason recorded. A comment that
contradicts the code is how the next reader puts the gap back.

## Follow-up at `a3cb1e3` — F1 ACCEPTED, and it was a real hole

The reviewer is right, and the shape of the mistake matters more than the fix.

`attach` refusing the wrong same-named medium with exit 2 was undone by the very
next statement. `detach` sits OUTSIDE the generated bracket's `if` on purpose --
so a failed transfer still puts the pool back -- and it asked only whether the
marker FILE existed. So the bracket could refuse a medium and then export that
same medium two statements later, deleting the marker recording what an export
was still owed on. The guard and the thing that undid it were fifteen lines
apart, and I read both while writing them.

The reviewer's reading of the suite is also right: I6 called the real `attach`,
proved it returned 2, exported nothing and kept the marker -- and then stopped,
one verb before the damage. G3 ran the whole bracket but with both gate verbs
stubbed, so its detach stub could not show an export that should not have
happened. 72/0 was measuring the half that worked.

### Implemented change

`detach` now asks `marker_is_ours`, the same three-way answer `attach` uses:
ours-and-this-pool exports; no marker is left alone; a marker that cannot be
matched to the imported pool REFUSES with exit 2, exports nothing, and keeps the
evidence.

A second case the same reading exposed: `detach` on an absent pool silently
cleared the marker. A marker plus an absent pool means the medium went away
while this package still held it -- pulled without a detach, or a run cut short.
That is exactly the event that can leave the copy on that disk needing a scrub,
and nothing else would ever mention it. It is now said out loud; the marker is
still cleared, or every later run would fail closed for a disk that no longer
exists.

  refusal followed by the real `detach`, both verbs, wrong medium still in the
  slot) and I8 (pulled while held).
- **Negative control against `a3cb1e3`**: `PASS=74 FAIL=5`, failing all four I7
