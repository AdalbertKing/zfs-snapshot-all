# Response to REV-20261107-191

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `zfs send -I a b` carries every snapshot between `a` and `b`. The `-E` filter in
`process_dataset` only chose the two ends. So an excluded snapshot (pvesr's `__replicate_`) inside
the interval reached the target in two cases:

- on the new first copy of a mirror (#1111);
- on every ordinary incremental run.

The second path predates #1111 and is already in the released 1.0.12. S8 hid this: it removed
`__replicate_` from the target list before comparing.

`snapsend.sh` has the same `-E` filter and the same `-I` send, so the push engine had the same
defect. It is fixed in the same way, and the two engines stay in step.

Trace of `-E` and `-m`:

- **CLI:** `-E` may repeat. Each value is a prefix in `EXCLUDE_SNAPS`. gen-cron renders replica
  families as `-E <name>` (REV-190).
- **Selection:** `-E` acts only under `-e`; it is applied inside the `USE_EXISTING_SNAPSHOT`
  block. Without `-e` the engine creates its own snapshot and `-E` has no effect. That is
  unchanged and outside this finding. `-m` filters after `-E`, so the endpoints are the newest and
  the oldest snapshot that is not excluded and has the `-m` prefix.
- **Send:** the new step runs after the send command is built. It applies only when all of these
  hold:
  - `-E` is given and the run is in `-e` mode;
  - there is a common snapshot;
  - the command is the ordinary `-I <common> <newest>`.

  It walks the unfiltered, creation-ordered source list from the common snapshot to the newest. If
  no excluded snapshot lies between them, the single `-I` stream stays. If one does, the same
  transfer is made as a chain of `-i` steps through every snapshot in the interval that is not
  excluded. Other families (for example `manual_x` beside a `-m` family) are carried, as `-I`
  would have carried them.

  Each step uses the original command's flags and the same `zfs recv`. If a step fails, the last
  good step stays on the target and becomes the next run's common snapshot.
- **No eligible snapshots:** unchanged. The run still refuses ("nothing eligible to adopt"), or
  skips scaffolding under `-R`.
- **`-i` / `-T` / `-H`:**
  - `-i`, and `-T` when its catch-up fires, send one `-i` diff. The new step does not apply to
    them.
  - `-T` without catch-up, and `-H` with a common snapshot, still send `-I <common> <newest>`, so
    the step does apply to them. That is intended: `-E` means the same in every mode.
  - `-H` without a common snapshot (`-R` full stream) and the bookmark base never produce that
    form, so they are unchanged.

### Implemented change

- `snapget.sh` and `snapsend.sh`:
  - the unfiltered list is kept as `src_all`;
  - the new stepwise block runs before "Starting transfer...";
  - log line: `-E: N excluded snapshot(s) lie between @a and @b -- ... one at a time instead`.
- `test/scenarios/run.sh`:
  - **S8** compares the whole target list, unfiltered and in `createtxg` order, after the first
    mirror copy. The interval holds `__replicate_` and the non-excluded `manual_x`. It also checks
    each GUID against the source.
  - **S8, later incremental run:** `__replicate_`, `vzdump-x` (with `-E __replicate_ -E vzdump`)
    and new eligible snapshots lie inside the interval. The whole target list is compared again.
  - **S8 control:** with nothing excluded inside the interval, the `-I` path is taken. The step
    message appears exactly twice in the log, from the two earlier runs, and not from the control
    run.
  - **S9 (new):** the same contract for `snapsend.sh -e -E` on an incremental push.

### Remaining risk

## F1 round 3 (verdict on d37d5044, the `-r` path) — IMPLEMENTED

### Analysis

Accepted that the round-2 step loop took endpoints from a name list without checking that they are
root snapshots. That is fragile under `-r`, and the outcome the verdict asks for is right. The
concrete failure path in the verdict does not happen on the lab ZFS, though. Measured on pve9
(zfs-2.1.11), with the verdict's layout (root `@a @skip @c`, child `@a @b @skip @c`):

- `zfs list -H -o name -t snapshot -s creation <root>` without `-d`, which is what
  `get_sorted_snapshots` runs under `-r`, lists the root's snapshots only. So does `-d 1`.
  Only `-r` adds `<root>/ch@...`.
- So under `-r`, `src_all` held `a skip c`, not `a a b skip skip c c`. The round-2 code sent
  `-R -i root@a root@c`; `root@b` was never an endpoint.

The same measurement shows a real hole that the verdict's direction covers. Because the list is
root-only, an excluded snapshot that only a CHILD has was invisible. pvesr names its snapshots per guest disk
(the field case in A20 was `vm-105-disk-0@__replicate_...`), so under an `-r` root they sit on the children. With no excluded name on the root, the
single `-R -I root@common root@latest` stayed and carried the child's excluded snapshot. A mirror
cannot hit this, because gen-cron refuses `-M` with `recursive = atomic`. A plain `-e -r -E` job
can.

`-R` (flat) does not reach this case. Each dataset is its own job with its own `-d 1` list and its
own endpoints.

### Implemented change

- `lib-zfs-snap.sh`: new `exclusion_step_plan`. It lists `name,createtxg` (`-d 1`, or `-r` under
  `-r`) and orders by createtxg, which is pool-wide, so the root's and the descendants' snapshots
  compare.
  - Step endpoints are the root's own snapshots that are not excluded. No endpoint is ever built
    from a descendant's name.
  - An excluded snapshot anywhere in the subtree inside the interval counts. An excluded snapshot with the
    same createtxg as an endpoint counts against that step.
  - A step whose own interval holds an excluded snapshot is `-i`. A clean step stays `-I`, so
    what `-I` carried there (a child's own snapshots included) is still carried.
  - It prints nothing, and the single `-I` stays, in three cases: nothing excluded lies inside;
    the two ends are not both found on the root with the newer one later; the last step is not the
    newest snapshot. The last two do not happen when the ends came from the same root list a moment
    earlier.
  - If the list cannot be read, the engine logs the reason and does not send, instead of falling
    back to `-I`.
- `snapget.sh` and `snapsend.sh` (`process_dataset`): the name-based loop is replaced by the plan.
- `test/scenarios/run.sh`: S10 and S11 check the whole target list of root AND child.
  - S10 uses the verdict's layout plus two additions: a clean step (child-only `@d`) and
    child-only excluded snapshots (`@skip_ch`, `@skip_only_child`). It is run once with `-r` and
    once with `-R`.
  - S11 runs `snapsend -e -r -E` with a child-only excluded snapshot.

Stated limit: under `-r`, a child-only snapshot inside a step that crosses an excluded snapshot
is not carried (the verdict's `ch@b`). `zfs send -i` sends only the difference between the two ends, with no intermediate snapshots ([OpenZFS zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html), `-i` vs `-I`). `-I` would
carry it, but only together with the excluded one. Exclusion wins. `-R` (flat) keeps it (S10).

## F1 round 4 (verdict on 35769184, first full `-R` stream) — IMPLEMENTED

### Analysis

Accepted as stated. Under atomic `-r` the first copy is `zfs send -R root@latest`. It replicates
every snapshot up to `@latest`, in the root and in every descendant
([OpenZFS zfs-send(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html), `-R`).
The round-3 plan ran only when a common snapshot existed, so the first copy carried a child-only
`@skip_x`. The same holds for `-H` on a single dataset. `-H` also sends `-R`, so it carried the
root's own excluded history. A replication stream has no per-snapshot filter, so the stream itself
must start below every excluded snapshot.

### Implemented change

- `lib-zfs-snap.sh`: new `exclusion_full_base <dataset> <latest> [user host]` (the pull engine passes the source host). It lists the subtree
  (`name,createtxg`, `-r`).
  - If no excluded snapshot lies at or before `@latest`, it returns `@latest` and the full stream is
    unchanged.
  - Otherwise it returns the newest non-excluded ROOT snapshot older than the oldest excluded one.
    A root snapshot with the same createtxg as an excluded one is not eligible.
  - If there is no such snapshot, or `@latest` is not found on the root, it returns 3.
- `snapget.sh` and `snapsend.sh` (`process_dataset`): this applies with no common snapshot, no
  bookmark, `-E` under `-e`, and `-r` or `-H`.
  - The full `-R` stream names that base. The common snapshot becomes the base, and the round-3
    step plan carries the rest to `@latest`.
  - rc 3: the run logs why and refuses before any transfer, which is the fail-closed outcome the
    verdict asks for. rc 1 (the list could not be read): no send either.
- `test/scenarios/run.sh` S12, on a fresh target each time:
  - pull and push `-r` with a child-only `@skip_x` between `@a` and `@b`;
  - pull `-H` with `@skip_h` on a single dataset;
  - the refusal: `ch@skip_0` older than every root snapshot.

  The copy checks read the whole target list of root and child; the refusal check counts `@skip_0` on every target under it and reads the log line.

Not changed: `-R` (flat) and the incremental paths of round 3.
