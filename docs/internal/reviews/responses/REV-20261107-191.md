# Response to REV-20261107-191

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `zfs send -I a b` carries every snapshot between `a` and `b`. The `-E` filter in
`process_dataset` only chose the two ends. So an excluded snapshot (pvesr's `__replicate_`) inside
the interval reached the target in two cases:

- on the new first copy of a mirror (#1111);
- on every ordinary incremental run.

The second path predates #1111 and is already in the released 1.0.12. S8 hid this: it removed
`__replicate_` from the target list before comparing.

`snapsend.sh` has the same `-E` filter and the same `-I` send, so the push engine had the same
defect. It is fixed in the same way, and the two engines stay in step.

Trace of `-E` and `-m`:

- **CLI:** `-E` may repeat. Each value is a prefix in `EXCLUDE_SNAPS`. gen-cron renders replica
  families as `-E <name>` (REV-190).
- **Selection:** `-E` acts only under `-e`; it is applied inside the `USE_EXISTING_SNAPSHOT`
  block. Without `-e` the engine creates its own snapshot and `-E` has no effect. That is
  unchanged and outside this finding. `-m` filters after `-E`, so the endpoints are the newest and
  the oldest snapshot that is not excluded and has the `-m` prefix.
- **Send:** the new step runs after the send command is built. It applies only when all of these
  hold:
  - `-E` is given and the run is in `-e` mode;
  - there is a common snapshot;
  - the command is the ordinary `-I <common> <newest>`.

  It walks the unfiltered, creation-ordered source list from the common snapshot to the newest. If
  no excluded snapshot lies between them, the single `-I` stream stays. If one does, the same
  transfer is made as a chain of `-i` steps through every snapshot in the interval that is not
  excluded. Other families (for example `manual_x` beside a `-m` family) are carried, as `-I`
  would have carried them.

  Each step uses the original command's flags and the same `zfs recv`. If a step fails, the last
  good step stays on the target and becomes the next run's common snapshot.
- **No eligible snapshots:** unchanged. The run still refuses ("nothing eligible to adopt"), or
  skips scaffolding under `-R`.
- **`-i` / `-T` / `-H`:**
  - `-i`, and `-T` when its catch-up fires, send one `-i` diff. The new step does not apply to
    them.
  - `-T` without catch-up, and `-H` with a common snapshot, still send `-I <common> <newest>`, so
    the step does apply to them. That is intended: `-E` means the same in every mode.
  - `-H` without a common snapshot (`-R` full stream) and the bookmark base never produce that
    form, so they are unchanged.

### Implemented change

- `snapget.sh` and `snapsend.sh`:
  - the unfiltered list is kept as `src_all`;
  - the new stepwise block runs before "Starting transfer...";
  - log line: `-E: N excluded snapshot(s) lie between @a and @b -- ... one at a time instead`.
- `test/scenarios/run.sh`:
  - **S8** compares the whole target list, unfiltered and in `createtxg` order, after the first
    mirror copy. The interval holds `__replicate_` and the non-excluded `manual_x`. It also checks
    each GUID against the source.
  - **S8, later incremental run:** `__replicate_`, `vzdump-x` (with `-E __replicate_ -E vzdump`)
    and new eligible snapshots lie inside the interval. The whole target list is compared again.
  - **S8 control:** with nothing excluded inside the interval, the `-I` path is taken. The step
    message appears exactly twice in the log, from the two earlier runs, and not from the control
    run.
  - **S9 (new):** the same contract for `snapsend.sh -e -E` on an incremental push.

### Remaining risk

- A chain of `-i` steps is N streams in place of one: more round trips, the same data.
- Snapshots that an older version already copied onto a target stay there. This change does not
  delete anything. A replica made before it keeps any `__replicate_` it already received;
  retention or the operator removes them.
- No production host or pool was touched. Live ZFS runs were made only on the lab host pve9.
