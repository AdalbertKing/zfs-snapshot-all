# Response to REV-20261021-161

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. The REV-160 key separates different datasets, but two
sessions on the same dataset still raced. An entrant B could validate
`orig2.<key>` and then be preempted before it wrote `hold2.$$.<key>`. In that
gap an exiting A saw no other holder, restored `snapdev` and deleted `orig2`.
B then set `visible` and later had nothing to restore from. The
check-then-`mv -f` creation of `orig2` raced in the same way. The new test
reproduces both directions on the old blob through the shipped entry point
(see Evidence).

### Implemented change

`tui/browse.sh`:

- **One transaction lock per exact dataset.** `snap_lock` opens
  `$BROOT/lock2.<key>` on a dynamically allocated fd and takes
  `flock -w ${BROWSE_LOCK_WAIT:-30}`. The key is the REV-160 sha256 key.
  - `expose_snapdev` runs its whole entry transition under that lock: legacy
    check, `orig2` validation or creation, holder registration and
    `zfs set snapdev=visible`.
  - `restore_snapdev` runs its whole exit transition under the same lock:
    holder removal, remaining-holder check, restore and `orig2` deletion.
  - The lock is released before mount, `mc` and unlock dialogs. No lock is
    held across user interaction, and neither transition calls the other, so
    no session can wait on itself.
- **Fail closed.**
  - On entry: no `flock` binary, a lock file that cannot be opened, or a
    lock wait over the limit means nothing is changed. There is no `orig2`
    write, no holder and no `snapdev=visible`, and the dialog says why. A failed holder write also refuses the entry; `snapdev` is then
    unchanged, and an `orig2` this session created stays with the true
    original value, to be reused by the next entrant.
  - On exit: if the lock cannot be taken, the holder, `orig2` and the current
    `snapdev` all stay. The residue says so and the exit status is nonzero
    (REV-159 path). The EXIT trap retries once.
- The lock file is never removed. Deleting a lock file is itself a race.
- The cleanup and residue reporting are unchanged, as are SIGTERM and EXIT
  handling and stale-holder recovery: a dead pid's marker is removed inside
  the locked `other_holders`.
- **Test-only pause.** `test_pause` stops a session at two points under the
  lock: after entry validation and before the holder is written (`expose`),
  and after the decision to restore (`restore`). It runs only when
  `BROWSE_TEST_PAUSE_AT` and `BROWSE_TEST_PAUSE` are both set; otherwise it
  does nothing.

### Remaining risk

- Hosts need `flock` (util-linux, present on every Proxmox host). Without it,
  browsing a VM disk is refused rather than run unlocked.
- The 30 s lock wait covers only the short transitions. It never covers a
  session that is merely browsing, because the lock is not held while
  browsing.
- No live two-session run on a lab zvol in this round.
