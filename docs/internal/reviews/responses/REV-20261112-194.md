## F1 — IMPLEMENTED

### Analysis

Confirmed. `snapget.sh` reads everything before the first `:` of a source as `[user@]host`
(`snapget.sh:2889-2895`). The media gate uses the same string as a local dataset name. ZFS allows
`:` in pool names and dataset names, so `backupnode:tank/data` is also a valid local name: the pool
`backupnode:tank`, dataset `data`. The text alone cannot tell "remote notation" from "local name".
Rejecting every `:` would break the valid `tank/data:part`.

The engine already has an unambiguous local spelling: an empty host part. For `:tank/data:part`,
`IFS=':' read -r _host_part _item_path` gives `_host_part=""` and `_item_path="tank/data:part"`,
because `read` gives the last variable the rest of the line, later `:` included. With an empty
host the engine takes its local paths (`[ -n "$REMOTE_HOST" ]` is false).

### Planned or implemented change

`gen-cron.sh` (replica emitter): if any source of a `[replica:]` holds `:`, every engine argument
of that replica gets the prefix `:` (`":tank/data:part"`, and `":$s"` in the multi-source loop).
The media gate gets the names as written, with `--source tank/data:part`. Gate and engine now name
the same local dataset. `backupnode:tank/data` is one local name for both, and neither ever
reaches ssh with it. If no such dataset exists, both report it missing. A replica whose sources
hold no `:` is not touched: `lp` stays empty (R194-F1d checks its engine arguments, not whole lines). REFERENCE pl/en: a replica `source` is always local,
a name holding `:` included.

  `--source tank/data:part`; `backupnode:tank/data` → engine `":backupnode:tank/data"`, gate
  literal; multi-source with one `:` → `":$s"`; control: no `:` → unchanged lines, no prefix.
- pve9, `./test/remote-suite.sh cron origin/fix/rev-194-media-attach`: PASS=296 FAIL=0.
  Negative control (`fix/rev-194-negctl`): PASS=293 FAIL=3; F1a, F1b and F1c fail and the F1d

  `snapget.sh -m replica_ -M ":hdd/lab/r194:part" hdd/lab/r194dst` gave rc 0. A second run sent
  the increment (rc 0, `replica_t2` and the new `replica_` on the target). Control: the old

### Remaining risk

An operator who writes `host:dataset` meaning a remote source now gets "dataset not found" for a
local name (from ZFS and the engine), not an explicit "remote sources are not supported". The docs say a replica source is
local. Not covered: a `dst` holding `:`, which the engine already refuses
(`snapget.sh:2916-2919`) and which the review did not raise.

## F2 — IMPLEMENTED

### Analysis

Confirmed. The gate accepted any name match without checking its GUID. Its fallback compared
target GUIDs only with source bookmarks. `find_common_snapshot` (`snapget.sh:991-1060`) takes a
name match only after `validate_snapshot`, and otherwise matches by GUID against the source
snapshots. So the gate refused a renamed snapshot that the engine would use, and let through a
same-name, different-GUID snapshot that the engine would not use. A failed read was treated as an
empty list, so it ended in "DIFFERENT lineage" and `zfs destroy -r` advice.

### Planned or implemented change

`zfs-media-gate.sh`, lineage check (now inside `media_preflight`): the gate reads target and source
snapshots as `name,guid` and the source bookmarks as `guid`. "Common" means some target snapshot
GUID equals a source snapshot GUID or a source bookmark GUID. Names are used only in the message.
A failed read, or a listed snapshot without a numeric GUID, counts as unknown. The gate then skips
the check for that source: no refusal and no destroy advice, and the engine decides.

### Evidence

- commits: `323656d8`, `8e1b645e`.
- `test/mediagate`:
  - R194-F2a: different names, same GUID → rc 0, no lineage diagnosis.
  - R194-F2b: same name, different GUID → rc 2, the medium exported.
  - R194-F2c: the target's latest snapshot survives as a source bookmark → rc 0.
  - R194-F2d: a bookmark of an older target snapshot → rc 0.
  - R194-F2e: control, no common GUID → rc 2.
  - R194-F2f, F2g, F2h: unreadable source snapshot list, source bookmark list or target list →
    rc 0; F2f also checks that no `zfs destroy` advice is given.
  - R194-F2i: a target snapshot without a GUID → rc 0.
  - The earlier N1, N1b, N1c, N1d and N2 cases still pass.
- pve9 `mediagate`: fix PASS=246 FAIL=0. Negative control: PASS=227 FAIL=19. Of the F2 cases,
  F2a (2 assertions), F2b, F2f (2), F2g and F2i fail. F2e and F2h pass on the old code too: they
  are controls, the old code already refused there or already skipped.

### Remaining risk

The stub models GUIDs; ZFS's own GUID reporting is assumed. The live lineage behaviour was
measured for B01 (2026-11-11) and was not repeated for the renamed-snapshot case.

## F3 — IMPLEMENTED

### Analysis

Confirmed. Both accepted already-imported branches (`present_ours_resumed`, `present_not_ours`)
ended in `exit 0` before the lineage and capacity checks.

### Planned or implemented change

The lineage and capacity checks moved into `media_preflight <new|ours|theirs>`. All three states
call it: `new` after a fresh import, `ours` for our interrupted run (marker matches) and `theirs`
for a pool imported without our marker. A refusal puts the medium away through
`preflight_put_away`:
- `new` and `ours`: export; clear the marker only after the export succeeded (REV-126 F2
  unchanged); otherwise DO NOT UNPLUG and keep the marker.
- `theirs`: never exported; the gate says it leaves the pool as it found it.

The refusal itself (rc 2, `lineage_mismatch` / `medium_too_small`) is the same in all three
states.

## F4 — IMPLEMENTED

### Analysis

Confirmed. The quiet-source check fed `zfs list -r` into its loop with the exit status discarded.
An empty or failed listing ran the loop zero times and left `_work=no`, so the copy could be
skipped with nothing proved.

### Planned or implemented change

The tree listing is captured with its exit status. A non-zero status, or output without the
source's own line, sets `_work=unknown`, so the medium is imported and the engine decides. The
loop reads the captured listing and does not list the tree a second time.
