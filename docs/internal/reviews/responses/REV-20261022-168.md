# Response to REV-20261022-168

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `import_restore_relblock()` recovered the `relation` object
with `/"[^"]*":"[^"]*"/`. That expression ends a string at the first escaped quote
and never decodes, although `cmd_export_relation()` writes every value through
`json_escape()` (which escapes `\` and `"`) and `json_value_of()` reads strings
escape-aware. The result was a false "differs" from `--check`, and a restore that
installed `snap\` for `snap"shot` with rc 0. The U28 test stubbed the restore, so
the parser never ran on an escaped value.

### Planned or implemented change

- New `json_flat_object()` reads the `relation` object the way `json_value_of()`
  walks strings. It emits one `key<TAB>value` line per member and decodes each key
  and value exactly once: `\"`, `\\` and `\/` (`json_escape` writes the first two).
- Anything it cannot restore exactly is refused with rc 3:
  - any other escape (`\n`, `\t`, `\uXXXX`);
  - a raw tab, newline or CR inside a string (the `key<TAB>value` form and an ini
    value cannot carry them);
  - an empty key;
  - a non-string value;
  - a missing brace or colon;
  - trailing text.
- `import_restore_relblock()` uses it in place of the regex. On rc != 0 it dies
  with "not a flat object of strings this build can restore exactly ... nothing
  was installed". This happens before the working copy is written, in both normal
  and `--check` mode.
- Unchanged: rendering of the temporary block, the whole-config `gen-cron`
  validation, and atomic replacement.

### Remaining risk

Values carrying a tab or newline cannot round-trip. The ini format and the
`relblock_dump` form cannot hold them either, so they are refused rather than
altered. Such a relation block has to be re-set by hand with
`set-tiers`/`set-transfer`, and the refusal says so.
