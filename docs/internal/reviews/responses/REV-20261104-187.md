`zfs-backup.sh` `snaponly_tiers_apply_ops` now applies the three ops to the relation's own

  default for T, in the letter case and gfs of the sibling. Monitor thresholds come from the
  default table with `monitor_since` = now. T is inserted into `use_template` in cadence order;
- `snaponly_cfg_tiers` lists tiers finest first, so an appended tier shows in the table in its place;
- `--add-src-tier` / `--drop-src-tier` mean the same as the target forms (a snaponly tier has one side);

### Implemented change

`zfs-backup.sh`: `snaponly_use_template_set` is replaced by `snaponly_use_template_edit <config>
<name> <snaponly|prune> <add|drop> <tier>`. It reads each managed section's own `use_template`
and edits that list in place:
- **add T**: a section that already lists T is left alone. Otherwise T goes in before the first
  entry of this relation with a coarser cadence, or at the end if there is none. Every other
  entry and the order stay as installed.
- **drop T**: T leaves the sections that list it; the others are not touched. A section whose
  only tier is T is refused ("<section> takes only the 'T' tier -- dropping it would leave that
  dataset with none ..."), and nothing is written. The refusal goes through the same
  working-copy `fail` as the other refusals.

The tier sections themselves (`[template:snaponly__NAME__T]`, `[template:snaponly_src__NAME__T]`)
are still added or removed once per relation, as in round 1. No profile is read.

### Analysis

Accepted. "Krótka retencja źródła" in `tui/edit-relation.sh` built the hidden profile

### Implemented change

- `zfs-backup.sh` `set-tiers`, snaponly: `--monitor-warn=AGE` and `--monitor-crit=AGE`
  (empty = no threshold) set the tier's thresholds in `[template:snaponly__NAME__T]`.
  The value is checked: empty, or like `26h`, `100m`, `9d`. On a copy relationship the
  two flags are refused with a reason. The usage text names them.
- `tui/fastprune-lib.sh`:
  - `fp_cfg <show-tiers.json>` reads N from the CONFIG: every tier that takes snapshots
    holds `retain = -h<N>` (the same N) and cleans every hour.
  - `fp_ops <show-tiers.json> <N>` gives the `set-tiers` words. For every tier with a
    `send_schedule` they are `--tier=T --retain=-hN --prune-schedule='<its own minute> * * * *'`
    (minute 21 when the tier has no prune schedule).
    A tier whose interval is at least N also gets `--monitor-warn= --monitor-crit=`, if
    it has thresholds. Nothing else is named, so every other field stays as installed.
- `tui/edit-relation.sh`, the fastprune row:
  - It reads `show-tiers --json` and computes `fp_ops`.
  - It runs the `set-tiers` line with `--plan`, and the change waits in the change list like the
    tier table; "Zapisz zmiany" runs `set-tiers ... --yes`.
  - No profile is read or written on this path. The hidden-profile backup and restore
    (`restore_fastprune`, `FP_BAK`) are gone with it.
  - An empty field (or 0) changes nothing, and the field says so ("Puste = bez zmiany";
    the creation wizard keeps "Puste = wyłączone"). When N is set, a message says where a
    different source retention is set: Harmonogram -> Ręcznie, or a template. This window
    therefore cannot switch short source retention off; before, an empty field returned to
    the base profile.
  - The current N on the card comes from `fp_cfg`.
