## Round 1 (Reviewer verification of 83602af7, 2026-11-05) -- IMPLEMENTED

### Analysis

Both points accepted. (1) The table `harm_flow` shows for a snaponly relation offers the
counting method and the tier set; `tui/template.sh` turns those into `--method=`,
`--add-tier=`, `--drop-tier=`, and round 0's `snaponly_tiers_apply_ops` refused all three with
"use the template action". An ordinary edit in the config-derived table could not be committed
without a template. (2) No CI run had `head_sha` 83602af7; the green run belonged to a later head.

### Planned or implemented change

`zfs-backup.sh` `snaponly_tiers_apply_ops` now applies the three ops to the relation's own
sections, with the same meaning as `tiers_apply_ops` has for a copy relation. No profile is read:
- `--method=gfs|flat|age`: in every `[template:snaponly_src__NAME__T]` the number stays, the case
  of the `retain` letter says count (upper) or age (lower), and `gfs = yes` is written (gfs) or
  removed (flat, age);
- `--drop-tier=T` (never the last): both sections of T are removed (`snaponly_section_remove`; the
  gaps around other sections stay as they were) and T leaves `use_template` of every `[snaponly:]`
  and `[prune:]` section of the relation (`snaponly_use_template_set`). The family's existing
  snapshots stay on the source and are no longer taken or pruned; the change line says so;
- `--add-tier=T`: both sections are appended. The family is the sibling's prefix with its tier
  word replaced (tag kept; refused when the sibling's prefix does not name its tier). The schedules
  are the copy relation's defaults for T, retimed to the relation's minute. The count is the
  default for T, in the letter case and gfs of the sibling. Monitor thresholds come from the
  default table with `monitor_since` = now. T is inserted into `use_template` in cadence order;
- `snaponly_cfg_tiers` lists tiers finest first, so an appended tier shows in the table in its place;
- `--add-src-tier` / `--drop-src-tier` mean the same as the target forms (a snaponly tier has one side);
- refusals remain for a tier it already has or a word that is no tier, dropping a tier it lacks,
  an unknown method, `keep=0`, an unknown tier and a field op with no tier.

"Use template" (`edit-relation --profile=`) is unchanged and stays the one action that reads a
profile.

## Round 2 (Reviewer verification of 2d1851aa, 2026-11-05) -- IMPLEMENTED

### Analysis

Accepted. `snaponly_use_template_set` built one list from all the relation's tiers and wrote
it into every `[snaponly:]` and `[prune:]` section. A dataset whose installed list left a tier
out got that tier back on the next `--add-tier` or `--drop-tier`. The round-1 regression and
the lab run could not see this, because every source in them had the same list. Measured on
`main` (the round-1 code) with the new test below: `hdd/so/b`, installed without daily, came

### Implemented change

`zfs-backup.sh`: `snaponly_use_template_set` is replaced by `snaponly_use_template_edit <config>
<name> <snaponly|prune> <add|drop> <tier>`. It reads each managed section's own `use_template`
and edits that list in place:
- **add T**: a section that already lists T is left alone. Otherwise T goes in before the first
  entry of this relation with a coarser cadence, or at the end if there is none. Every other
  entry and the order stay as installed.
- **drop T**: T leaves the sections that list it; the others are not touched. A section whose
  only tier is T is refused ("<section> takes only the 'T' tier -- dropping it would leave that
  dataset with none ..."), and nothing is written. The refusal goes through the same
  working-copy `fail` as the other refusals.

The tier sections themselves (`[template:snaponly__NAME__T]`, `[template:snaponly_src__NAME__T]`)
are still added or removed once per relation, as in round 1. No profile is read.
