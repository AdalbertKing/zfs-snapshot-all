## F1 — endpoint written as shell code without validation or quoting — ACCEPTED, FIXED (blocker)

Correct, and this was a real root command-injection I introduced. `add-client`/`set-endpoint` wrote
`--lan`/`--vpn` values into the client conf unvalidated and unquoted, and every other command reads
that file back with `.` -- bash EXECUTES it, as root. `--vpn='$(id)'`, `a;reboot`, a space or a
newline would have corrupted the state file or run as root on the next
`status`/`seed`/`verify-endpoint`.

Two independent defences, since either alone is one mistake from the same hole:

1. `parse_endpoint_arg` validates the host to a charset that cannot express shell syntax at all
   (hostname/IPv4: letters, digits, dot, dash; no leading/trailing dot or dash) and the port to a
   real 1-65535 integer, `die`ing otherwise. IPv6 literals are refused outright rather than
   half-parsed -- their brackets collide with the `HOST:PORT` split and nothing in this project is
   IPv6 today.
2. `write_client_field` `%q`-quotes every value on write, so a value that somehow reached the file
   still could not break out of its assignment. Every client-conf write now goes through it.

Tests cover exactly the cases the review named -- `host;id`, `$(id)`, backticks, space, empty,
newline, leading/trailing dot and dash, port `0`/`65536`/`abc`/`-1`/`22x` -- plus legitimate values
that must still pass, plus a payload test proving `write_client_field`'s output sources back with
the value intact and nothing executed.

## F2 — incremental inferred from the absence of "full send" — ACCEPTED, FIXED (blocker)

Correct: a negative heuristic over a log message, which a reworded line or any new rc=0 planner
branch would silently have turned into a false "verified".

`snapget.sh -n` now prints exactly one machine-readable verdict per dataset on **stdout** (logging
goes to stderr, so the two can no longer be conflated):

```
PLAN=INCREMENTAL base=<snapshot> src=<...> tgt=<...>
PLAN=FULL base=- src=<...> tgt=<...>
```

It is derived from the same `$common_snapshot` the real transfer branches on -- `zfs send -I base`
versus a full stream -- so the plan cannot drift from what the run would actually do. This is the
review's first suggested option (an explicit marker from `snapget.sh`), chosen over re-deriving the
common base in the wrapper because a second implementation of that logic is exactly what would
drift.

`verify-endpoint` parses that line and treats **anything it does not recognise as UNKNOWN and
fails** -- fail-closed, as required. It no longer merges stderr into the parsed output at all.

## B1 — remote quiesce (snapget.sh v2.65)

Implemented, so a pull client can be application-consistent rather than crash-consistent.

**Design is driven by one property: the thaw must survive losing the connection.** Locally an EXIT
trap suffices (the process that froze thaws). Over ssh it does not -- a dropped link, a killed job
or a rebooted collector would leave a PRODUCTION GUEST FROZEN, which is an outage and strictly
worse than never quiescing. So freeze → atomic snapshot → thaw runs **entirely inside one remote
invocation**, carrying its own EXIT trap *and* a setsid-detached deadman that thaws unconditionally
if the main path never gets there (`-Q`, default 120s). The deadman's streams are fully redirected;
a background process still holding the ssh channel's stdout would hang every quiesced run until it
expired. Keeping it in one invocation also keeps network latency out of the freeze window, which
blocks guest writes for its duration.

**Privileges — measured, not assumed.** `qm`/`pct` need root: a delegated pull account cannot even
read `/etc/pve/qemu-server/<id>.conf` (0640 root:www-data), and `qm guest cmd` as non-root dies with
"Unable to load access control list". Verified with a real throwaway account on pve1, then removed.
So remote quiesce needs `--as=root` or a sudo rule on the source, and snapget.sh **fails loudly**
when it cannot -- never silently delivering the crash-consistent snapshot the flag exists to
prevent.

The remote script is a constant; every dataset/snapshot name reaches it as a positional parameter
(`printf %q`), never interpolated into executed code.

`gen-cron.sh`: `lint_quiesce` no longer rejects quiesce on pull outright -- `agent`/`auto` are
allowed, `sync` still refused (the container `pct exec` flush buys nothing across an ssh hop). The
old negative fixture pinned exactly the contract that changed, so it was rewritten
(`quiesce-on-pull` → `quiesce-sync-on-pull`) and a positive golden added
(`fixtures/pull-quiesce`), with the `gen-cron-flags` contract text updated to match -- including an
explicit note that it *cannot* cover the source-side privilege question, which only run time can
answer.

## Live verification (pve0 / pve1 192.168.11.11)

- **Full remote-quiesce path, non-guest dataset** (zero risk): privilege probe, arg passing, atomic
  snapshot, deadman setup/teardown, output relay, full send then incremental on a re-run -- all
  clean.
- **Real VM freeze (vm-106, win2008, owner-approved choice)**: `quiesce_remote_run` froze the guest
  via qemu-guest-agent, took the snapshot inside the window, thawed it. Verified after:
  `fsfreeze-status` = `thawed`, `qm status` = `running`, and the guest agent still answering
  `get-osinfo`. Only the quiesce path was exercised, deliberately -- a real transfer of that disk
  would have moved 100 GB for nothing, and the transfer path was already proven separately above.
- **Deadman, on the same real VM**: froze VM 106, left the state file in place with no trap (exactly
  the shape of a SIGKILLed run), started the deadman verbatim with a 15s timeout, walked away. It
  thawed the guest and logged
  `zfs-quiesce[...]: DEADMAN: thawed guest(s) after 15s -- the controlling backup run vanished
  mid-window`. The hard fallback thaw afterwards was a no-op. This is the safety property the whole
  design exists for, verified against a production guest.
- **A real defect this testing found**: the first deadman used one long `sleep $deadman`, and
  killing the setsid'd wrapper does not kill its `sleep` child -- every quiesced run left a stray
  `sleep 120` behind. Harmless in itself (the state file is gone by then) but litter, and a stale
  deadman outliving its run becomes a real bug the day an mktemp name is reused. Now it polls in 5s
  steps using the state file's existence as the "still running" signal; verified the process is gone
  within ~5s of a normal run, and that a SIGKILLed run still gets thawed at the timeout.

Cleanup after every test: throwaway datasets destroyed on both hosts, the test snapshot on
`vm-106-disk-0` removed, harness scripts deleted, both VMs confirmed `running`/`thawed`, vm-100
never touched.

Local suites: gencron 56/56, quiesce 22/22, statekey 16/16, tune 48/48, zfsbackup 60/60,
`impact.sh --verify` clean.
