# Response to REV-20260809-088

## F1 — IMPLEMENTED

ACCEPTED. The critique is exactly right: putting the collision comparison
inside `ensure_cron_config()` made it fire on every `activate-client` call,
first activation and every later re-activation alike, turning a CREATE-time
collision rule into a standing dependency on the current profile
definition — precisely the coupling the one-way handoff
(`PROFILE/PRESET -> generate once -> CONFIG v4 -> runtime truth`) and
Phase 3's "reactivation preserves installed policy" boundary forbid.

### Fix

`ensure_cron_config()` gained an explicit parameter,
`check_new_template_collision` (default `0`), documented at the function
header. The comparison inside the per-template loop now runs only when that
parameter is `1`; otherwise an already-present name is left untouched
exactly as before Phase 2 (append-only, presence-by-name).

`cmd_activate_client()` computes `is_new_relationship` from `STATE` **before**
the case statement that validates it: `STATE=endpoint_verified` means this
relationship has never reached `active` before — the genuine first-CREATE
moment — while `STATE=active` means this is a re-activation (e.g. after
`set-endpoint`). Only the first case passes `1` through to
`ensure_cron_config "$workfile" "$is_new_relationship"`.

The other two callers (`setup-server`, `migrate-profile`) are unaffected —
both pass no second argument, defaulting to `0`. Neither is a per-relationship
CREATE moment: `setup-server` runs before any relationship exists, and
`migrate-profile` already removes the legacy template family immediately
before calling `ensure_cron_config`, so there is never a pre-existing
namespaced section to compare against at that call site regardless.

## F2 — IMPLEMENTED

ACCEPTED. The comparison was `[ "$existing" = "$wanted" ]` — literal text
equality — against Gate 2's explicit "identical **semantic** template may
be reused."

### Fix

Both sides are now normalized through `profile_emit()` before comparison —
the existing function that already strips comment lines and blank lines and
trims leading whitespace for this exact `key = value` field grammar (it is
what wrote the section content in the first place, via
`profile_template_section`) — and the normalized output is sorted, making
the comparison field-order independent as well, since CONFIG v4 resolves
fields by name, not position. No new parser or profile-diff framework was
introduced; the existing normalizer and `sort` are the "minimal canonical
representation derived from the same accepted fields" the finding asks for.
