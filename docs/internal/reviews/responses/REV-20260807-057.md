## Chosen surface, and why it is the smallest

`gen-cron.sh --migrate-recursion [-c CONFIG]`.

`gen-cron.sh` already owns all three things the migration needs: the config
schema, the getopts-equivalent option walker the detection must reuse, and the
renderer the equivalence proof depends on. Putting it in `zfs-backup.sh` would
have duplicated the walker and the render across a file boundary that
`deps.conf` already carries a contract about (`cron-line-shape`). No new
framework; one flag on the tool that owns the format.

## Contract

1. **Detection uses the generator's own semantics.** `split_recursion_flags()`
   walks characters and consults the same `FLAGS_ARG_LETTERS` as
   `flags_opt_letters()`, so `-m R-daily_` and `-v R` are untouched — an option
   argument is not an option. Pinned by B1/B2, which assert the file's checksum
   is unchanged, not merely that the tool said nothing.

2. **Deterministic, narrow mapping.** `-r`→`atomic`, `-R`→`flat`; every other
   option and argument preserved. Bundled forms are **split**, not refused
   (`-Rv 3`→flat + `-v 3`, `-rZ`→atomic + `-Z`) — refusing them would leave a
   legal config with no path off the old spelling. `-r` and `-R` together is
   refused: they are different modes and guessing is not migration.

3. **No semantic drift — three-way, control first.** Render the current config
   in legacy mode, render the migrated one, require identical; then check the
   legacy render against the **installed block**. If that control fails the
   drift predates the migration, and the run aborts naming the likely cause
   (render environment) rather than adopting it.

   This structure is deliberate. Doing it by hand during REV-055 produced a
   diff whose own baseline differed, and it was only caught because the control
   was there. Mechanised, the step cannot be skipped.

   Two lines are normalised out before comparing, neither cosmetic: the
   BEGIN/END markers (`cron_block_read` returns contents, not markup) and
   `# Source:` (the migrated config renders from a temp file, so that line
   would differ on every migration).

4. **Transactional commit.** Rollback copy first, `cp -p` staging that inherits
   owner and mode, content written into the staged file, read-back against the
   validated text, then rename. Any failure before the rename leaves the source
   byte-identical — asserted by checksum in D1–D4, not by message text.

5. **No cron reinstall.** The crontab is never touched. If the block is
   unchanged there is nothing to install, and this is a schema migration.

6. **Idempotent.** C1/C2: second run rc=0, file byte-identical.

7. **Operator output.** Names the file, each migrated section with `atomic` or
   `flat`, whether the installed-block control passed, the rollback copy, and
   that the crontab was not touched. Refusals name the section and the reason.

8. **Fleet preflight — done, all four hosts.**

## The legacy-render escape, stated plainly

The baseline render needs a code path that accepts the spelling v4.27 refuses.
It is `--internal-legacy-render`: undocumented, refused together with
`--install` (so it can only ever reach stdout, never a crontab), and
`MIGRATE_LEGACY` is assigned unconditionally at startup so an inherited
environment variable cannot preset it. E4 pins the `--install` refusal.

I am flagging it rather than burying it: it is the one path that accepts the
old shape, and the review asked not to weaken the rejection.

## A real defect found by running the suite as the delegated account

`test/migrate` passed 34/34 on this workstation and as root on a real host. Run
as **`zfsbackup`** on `192.168.11.11` it failed 10 of 34 — and not for
permissions.

The installed-block control compared the render against whatever
`zfs-backup-managed` block the *current user* had, regardless of which config
produced it. Migrating any second config, staging copy or test fixture aborted
with "the installed managed block does not match this config", which was simply
untrue. Fixed in `23d616b`: the block records its origin in its own
`# Source:` line, and the control now runs only when that path resolves to the
file being migrated.

This is the failure mode the project keeps rediscovering — root and the
delegated account are different environments, and only one of them runs in
production.

## NEW FINDING, found by doing it: the control skips exactly when it is needed

The run had to be made **as root**, and the installed-block control therefore
**skipped**:

```
  before/after render: identical
  installed crontab block: none found -- skipping that control
```

Two facts collide:

1. configs live in `/etc/zfs-snapshot-all/` owned by `root:root 644`, so the
   delegated account **cannot write them** — my own `[ -w ]` guard refused the
   account run, correctly;
2. the control reads the **current user's** crontab, and the managed block
   belongs to the *account*, not to root.

So on this fleet the migration must run as root, and run as root the strongest
check silently degrades to a notice. Contract item 3 said "if the control
cannot be made trustworthy, abort; do not call a noisy comparison success" —
this is not calling a bad comparison good, but it is proceeding without the
comparison, which is weaker than the contract intends.

It did not cause a bad outcome here: the before/after render check still ran
and passed, the dress rehearsal on a copy had already proven equivalence
against the installed block, and I verified the same thing again afterwards by
hand (row 6 above). But the guarantee came from me, not from the tool, and next
time there may be no me.

**Proposed fix, not implemented** — I am not redesigning a contract you
approved three hours ago without asking. The managed block already records its
origin in `# Source:`. When the control finds no block for the current user,
root could locate the block whose `# Source:` names this config among the
crontabs it can read, and use that as the control; if it finds none, *then*
abort rather than notice. That keeps the check available in the only
configuration this fleet actually has, with no new flag and no operator input.

The alternative — a `--as-user <account>` hint — is a knob, and knobs are what
this whole thread has been about avoiding.

Findings left **IMPLEMENTED**; closure is the reviewer's. F1 is now fully
executed; the finding above is offered as its own item rather than folded in.
