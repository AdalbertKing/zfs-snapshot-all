# Response to REV-20260807-062 — the lock audit must check the group

**ACCEPTED.** The finding is correct and the hole is mine, in code shipped an
hour before the review.

## The invariant, and which half I pinned

`cron_lock_files_repair()` does `chgrp` **and** `chmod`.
`cron_lock_files_audit()` checked only the mode. So

```
-rw-rw-r-- root root  .../lib-cron.zfsbackup.lock
```

passed: group-writable, yes — to a group the delegated account is not in. It
still cannot open the file. The production invariant is **shared group AND
group-write**, and I asserted the second half alone.

The sharper way to say it, which is what makes this worth more than a one-line
fix: **the audit did not verify what its own repair function guarantees.** That
is the only reason an audit exists next to a repair. If the two can disagree,
the audit is decoration.

It is also the same shape as everything else corrected today — a check that
looks complete and admits the exact state it was written to prevent.

## Changes

`cron_lock_files_audit() <lock dir> <expected group>` now reads `stat -c '%G'`
as well as the mode, and the two findings are reported **separately**:

```
lock files in the WRONG GROUP (expected zfsalert): lib-cron.acct.lock(group=root)
  -- the delegated account is not in that group, so it cannot open them
     whatever the mode says.
lock files NOT group-writable: lib-cron.root.lock(644)
  -- whichever identity did not create them cannot write that crontab at all.
```

Different causes, different fixes, and the operator reads this line to decide
whether something else is misconfigured too.

Repair stays root-side in `deploy.sh`. Nothing moved into `lib-cron.sh`, which
runs unprivileged and may not chmod a foreign file — per contract item 3.

## Tests, and the blind spot they shared

My L cases varied **modes**. L2 called repair with `$(id -gn)` — a group that
was already correct. Nothing exercised a wrong group, which is precisely why
the defect survived the suite I wrote for it.

**L6** — a `0664` lock in the wrong group is refused, and the diagnostic says
*wrong group*, not *wrong mode*.
**L7** — repair moves it into the expected group and the audit then passes.

They SKIP where the user has only one group, or where `chgrp` does not take,
and run on Linux.

### Evidence

- `test/join` **94/94 on Linux as the delegated account** (`zfsbackup`, groups
  `zfsbackup zfsalert`);
- **negative control against `2f69c2d`: L6 fails, L7 passes.**

That control is worth reading closely. L7 passing on the old tree is not a
weakness — repair was always correct, it always did `chgrp`. The control
discriminates on exactly the function that was wrong, and on nothing else. A
control that had failed both would have proved less, not more.

No campaign beyond the dependency-selected suites, per contract item 4.
