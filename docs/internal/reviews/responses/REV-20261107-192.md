# Response to REV-20261107-192

## F1 — IMPLEMENTED

### Analysis

Accepted. The name gate held the customer and site names as a literal in a public repository,
and its tests repeated them. A public list of customer names is itself the disclosure it is
meant to prevent. The problem was also wider than the two cited files. The tracked dev tree
carried such names in about 140 files: guides, status, tests, comments and three file names.
This response names none of them. The evidence below gives only paths, counts and PASS/FAIL.

Owner direction, 2026-11-07, on outcome 3: the developer repository stays public for now, and
the tree is cleaned ("Czyść").

### Planned or implemented change

1. **Private name source, with an explicit missing-configuration policy** (668b09c6, a3bdca65).
   `release/name-gate.sh` reads names from a private file named by `$ZFS_NAME_DENYLIST`. The
   file holds one extended regex per line, without Polish letters, with `#` comments; CR is
   stripped. The list lives in the private configuration repository (anonymous read: 404).
   - No list: the public address patterns are checked, names are not, and stderr says so.
   - An unreadable, empty or malformed list (invalid regex), or a grep failure: rc 2. This is
     an error, never a pass.
   - `release/publish.sh --push` refuses without a readable, non-empty list. It does so before
     it reads or writes anything.
   - `release/publish.sh` stops on gate rc 2, with or without `--push`. Before, it swallowed the
     gate's status (`|| true`).
2. **Synthetic tests** (`test/release` 4b) use a made-up list and made-up words, a different
   Polish letter in each fixture, under `C` and `C.UTF-8`. A clean Polish file and a binary
   pass. New cases:
   - no list: addresses refused, names not checked, the note printed;
   - missing, empty or malformed list: rc 2;
   - `publish --push` without the list refuses and writes nothing;
   - a local publish with a malformed list stops with no release commit.

   The later `--push` cases test other gates, so they get the synthetic list.
3. **Outcome 1: the tracked tree is cleaned** (b84b61a6). Customer and site names are replaced
   with synthetic labels: Site-A, Site-B, Site-C, Site-D, `vm-sql`, `biuro`, and for the domains
   `example.org` and `biuro.example`. Three file names followed.
   - `release/scrub.sed` keeps no site name. Its only remaining name-like rule maps the old
     scrub result domain `site-a.net`, itself a synthetic label, to `example.org`.
   - In the engines only comment lines changed. ENGINE-FREEZE has an entry and was refrozen;
     twins were re-blessed on pve9 with no hash changed.
4. **Not touched: the reviewer's own files.** 9 files under `docs/internal/reviews/` (`REV-*.md`
   and `closures/`) still carry such names, 13 lines in all. They are the reviewer's to edit, so
   outcome 1 is complete only once they are cleaned. The Reviewer is asked to clean them, or the
   Owner to allow the implementer to.

Compatibility and security: publishing now needs `ZFS_NAME_DENYLIST` for `--push` (a
deliberate refusal). No host, engine behaviour or release-package file changes. Documentation:
the gate and publish headers describe the list and the policy.
