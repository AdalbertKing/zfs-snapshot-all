# Response to REV-20260803-035

## Verdict: F1 — ACCEPTED, IMPLEMENTED

The finding is correct and the reproduction is exact. `CRON_LOCK_DIR` was
`${CRON_LOCK_DIR:-/run}`, falling back to `${TMPDIR:-/tmp}` when `/run` was
not writable by the caller. Root can create files under `/run`; a delegated
account normally cannot. So a `deploy.sh`/`migrate-to-account` run as root
locked `/run/lib-cron.<user>.lock` while `gen-cron.sh` running AS that same
delegated account, writing its own crontab, locked
`/tmp/lib-cron.<user>.lock`. Two lock objects guarding one crontab is not a
lock — it silently reopened REV-034 F2 for exactly the two identities that
matter most (root and the delegated account), which is the case F2 was
written for.

The review's diagnosis of why the existing suite missed it is also exactly
right: `test/cron/run.sh` sections P/Q/R/S all pass `CRON_LOCK_DIR` to both
sides of every contention test identically (both writer subshells export the
same throwaway directory), so they could prove flock semantics work but could
never have caught two *different* callers choosing two different paths.

### Analysis

Root cause: a writability-detected fallback is, definitionally, a function of
the caller's identity — that is what "writable by me" means. Any such
function will disagree between two different identities acting on the same
target, which is precisely the property a shared lock cannot have. The
correct fix removes the detection, not the specific paths it chose.

### Planned or implemented change

- `lib-cron.sh`: `CRON_LOCK_DIR` is now `${CRON_LOCK_DIR:-/var/lib/zfs-snapshot-all/locks}`
  — one fixed default, overridable only for tests, with no fallback logic of
  any kind after that. `cron_lock_acquire` checks the directory is present and
  writable and refuses with a named diagnostic if not (`could not... Run
  deploy.sh to (re)create it`), rather than silently trying somewhere else.
- Chose `/var/lib/zfs-snapshot-all` over the review's illustrative
  `/run/lock/zfs-snapshot-all`: it is `$ALERT_SHARED_DIR`, the directory this
  project already uses for exactly this problem (shared, persistent state
  both root and the delegated account must reach) and already gives the
  `2775 root:zfsalert` treatment. `/run` is tmpfs and would need its own
  recreate-after-reboot logic that `/var/lib` does not; reusing the existing
  group means no new group, no new membership bookkeeping, and no new
  attack surface — `zfsalert` membership already implies "this account may
  touch this project's shared, root-owned-but-group-writable state."
- `deploy.sh` Phase 4 now creates `$CRON_LOCK_DIR` (`mkdir -p`, `chgrp
  zfsalert`, `chmod 2775`) in the same block that provisions
  `$ALERT_SHARED_DIR`, and audits it the same way under `--check-only`. Phase
  8's existing "not in group zfsalert" warning now names both consequences
  (cannot queue alerts, and — new — `lib-cron.sh` would refuse to lock its own
  crontab).
- Added a symlink guard `cron_lock_acquire` did not have before: a directory
  two identities can write into is exactly where a predictable filename
  (`lib-cron.<user>.lock`) could be pre-planted as a symlink, and the old code
  would have opened straight through it via the persistent `exec`. Now
  refused by name before that `exec` runs.

### Evidence

- `test/cron/run.sh` section U (+8 new checks, 2 SKIP on this Windows/MSYS
  dev machine):
  - U1: greps the source to confirm the old `[ -d ] && [ -w ] ||` fallback
    pattern is gone, not merely bypassed by a test's own env.
  - U2/U2b: two subshells that source `lib-cron.sh` with `CRON_LOCK_DIR`
    unset but different `TMPDIR`/`HOME` — standing in for the real
    root-vs-account split — resolve the identical, fixed lock path. This is
    the exact property the bug violated and the fix restores.
  - U3/U3b/U3c: an existing-but-unwritable canonical directory makes
    `cron_lock_acquire` fail closed with a diagnostic naming the real
    problem, and — the assertion that would have caught the old bug directly
    — nothing appears under `$TMPDIR` as a silent fallback. SKIP here: this
    filesystem does not enforce `0555` against its owner (needs a real Linux
    host).
  - U5/U5b/U5c: a symlink at the lock path is refused, named as a symlink,
    and its target is left untouched. SKIP here: this environment cannot
    create a real symlink without elevation (Windows/MSYS, no Developer
    Mode) — needs a real Linux host to exercise.
- Full impact graph re-run after the change: `cron` **123/123** (was 120;
  section U adds 8 checks, of which 5 SKIP on this Windows/MSYS dev machine —
  the permission-bit and symlink cases above — leaving +3 counted PASS here),
  `run.sh` (gen-cron) **56/56**, `join` **54/54**, `quiescehelper` **119/119**,
  `selfupdate` **28/28**, `zfsbackup` **211/211**.
- `test/scenarios/run.sh`: **not run here** — needs root and a real pool.
  This is the suite that would prove actual `flock` contention across the
  real root/delegated-account UID boundary on a live host, as opposed to the
  path-computation property this commit's own tests can prove without one.
  Flagging as the manual obligation the review itself anticipates ("Required
  tests" #3: "each process starts with its natural permissions and
  environment") — the closest available substitute for a true cross-identity
  test until it runs on metropolis pve1 or another live host with both a root
  session and the delegated account's own session.

### Remaining risk

Everything up to and including "does the lock path agree across identities,
and does an unusable directory fail closed" is proven, including the
specific symlink and permission-bit properties the review's "no arbitrary
replacement or symlink tricks" language asked for (two of those checks SKIP
on this dev machine and need a Linux host to actually exercise, not just to
compile). What is not yet proven on a live host: an actual `flock -w`
contention between a real root process and a real delegated-account process
racing the same crontab, under the new shared directory. Section P already
proves flock's blocking semantics when both sides agree on the directory (by
construction of the test); what a live run adds is proving they *do* agree in
production, which requires the group-membership and directory permissions
this commit sets up to actually be live on a host. That is the next manual
step, and it is cheap: any host already running `deploy.sh` picks this up on
its next run (Phase 4 is idempotent), after which the existing production
`migrate-to-account`/`gen-cron.sh --install` traffic exercises it for free.
