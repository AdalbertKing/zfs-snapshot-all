# Response to REV-20260811-099

## F1 — IMPLEMENTED

Accepted. This is the recurring drift I had been patching by hand all through
the Phase 5 reviews, now correctly named as a defect: a `delivered:` record with
no durable `reviewed-by:` is only cleared while some REV's *moving*
`reviewed-implementation` still equals that exact sha. The moment a review
advances its pointer to a cumulative follow-up (REV-095 -> 8db8c4d, REV-097 ->
9b4a6e5), the original delivery sha stops matching and reappears as unreviewed —
so `OPEN-THREADS.md` said both "REV CLOSED" and "review this delivery", the exact
duplicate-routing failure PROTOCOL V2 exists to remove.

### Change

Two parts, both minimal and inside the existing mechanism (no new machinery):

1. **Retired the reviewed deliveries durably.** `DELIVERIES.md` now carries an
   explicit `reviewed-by:` record beside each already-reviewed delivery:
   - `9074fe55…` (Phase 4 slice 1) — REV-20260810-095;
   - `5df74522…` (Phase 6 examples) — REV-20260810-094;
   - `f8ec3eae…` (Phase 5 slice 1) — REV-20260810-097;
   - plus `3495ec4d…` (Phase 3.5) — REV-20260810-093, which was still cleared only
     by pointer-match and would resurface identically the first time REV-093 got
     a follow-up. `reviewed-by:` is a fact about the past, so it survives any
     future pointer advance. After `--generate`, OPEN-THREADS lists only the open
     REV-099 row — the three DELIVERED rows are gone.

2. **Pinned the full lifecycle in `test/reviewctl`.** The suite already had the
   moving-pointer case (`reviewed-by clears a delivery whose REV has moved on`,
   d6/d7). Added the exact REV-099 scenario on top (d8/d9): a delivery, a review
   whose `reviewed-implementation` advances to a cumulative follow-up sha and
   then **CLOSES**, and a `reviewed-by:` for the original — after generate the
   original delivery is absent from OPEN-THREADS and the closed REV is not open
   either; and a third, genuinely unreviewed delivery in the same closed world
   still shows as open (the load-bearing negative control, so the retirement is
   the `reviewed-by` fact and not "closing a REV silences every delivery").

No production code, no ZFS/SSH/crontab/deploy: pure review bookkeeping, as the
finding scoped it.

### Remaining risk

`reviewed-by:` is now the durable retirement mechanism for a reviewed delivery.
The one discipline it needs: when a direct-main delivery is reviewed, record the
`reviewed-by:` (or `no-review-required:`) at that point rather than relying on
the ledger's moving pointer — which is exactly what the new d8/d9 case guards
against regressing.
