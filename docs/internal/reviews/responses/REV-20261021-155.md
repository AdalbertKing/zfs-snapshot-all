# Response to REV-20261021-155

## F1 — IMPLEMENTED

### Analysis

Accepted as reproduced. `AT`, `TARGET` and `KEEP` rejected only non-digits,
and even those were silently replaced by defaults; `TARGET >= AT` was coerced
to `AT - 1`. So `guard_at=0`/`guard_target=0` became a target of -1 and the
loop removed every eligible snapshot.

### Implemented change

`hostscripts/capacity-guard.sh`: the effective values are validated before
the lock, the crontab read and any pool listing. Ranges are the F10 registry
contract (`zfs-backup.sh` `capacity.*`): `guard_at` 50-99, `guard_target`
40-98 and strictly below `guard_at`, `guard_min_keep` 1-100; `guard` must be
`on` or `off`. Any violation, non-numeric included, is no longer coerced:
the run destroys nothing, exits 1, logs the bad setting(s) and alerts naming
them (`--plan` reports and exits 1 without alerting). Precedence stays as
fixed in #655: an explicitly supplied invalid environment value wins over a
valid `settings.ini` value and is refused, not replaced.

### Evidence

- `bash test/alertmail/run.sh` (pve9): PASS=130 FAIL=0, 43 guard cases.
  New F1 cases, each asserting zero `zfs` calls, rc 1 and the named setting
  in the alert: env 0/0; `guard_at` 49 and 100; `guard_target` 39;
  `guard_target == guard_at` (85/85); `settings.ini` `guard_min_keep` 0, 101
  and `x`; legacy conf `guard_target=0`; env `guard_at=abc`; `guard=ON`;
  env 0 over a valid settings 89. Boundary control: 50/40/1 and 99/98/100
  accepted.
- Negative control, same suite with `capacity-guard.sh` from `b23a2a73`
  (main): all 12 F1 safety cases FAIL; the boundary control passes on both.
- `bash docs/internal/reviews/evidence/REV-20261021-155-capacity-guard.sh` on
  the fixed tree: 4 PASS / 0 FAIL.

### Remaining risk

An empty value (`ZFS_GUARD_AT=`) is treated as not supplied and falls through
to the next source, as everywhere else in `alert-env.sh`.

## F2 — IMPLEMENTED

### Analysis

Accepted as reproduced. The status of `zpool sync` was discarded, and an
unreadable capacity only broke out of one pool's loop; the deletion decision
was taken without the measurement the contract requires.

### Implemented change

After each successful destroy: a failed `zpool sync`, or a post-delete
capacity that is empty or non-numeric, ends the whole run -- no further
`zfs destroy` on this or any other pool, exit 1, a log line and an alert
("ZATRZYMANY") naming the cause and listing what was already removed.

### Evidence

- New cases: sync failing after the first destroy -> exactly one destroy,
  rc 1, alert names `zpool sync tank` and lists the removed snapshot;
  unreadable capacity after the first destroy -> one destroy, rc 1, alert.
  Healthy control: three destroys, stop below target (92 -> 83 %), rc 0.
- Negative control on main: both stop cases FAIL; the healthy control passes.
- The reviewer's evidence script: "failed zpool sync stops the destructive
  loop and is reported" PASS.
- `./test/impact.sh origin/main` selects `alertmail` only; `./test/impact.sh
  --verify`: rc 0.

### Remaining risk

No live destructive run was repeated for this change: both defects are
decided before or between `zfs destroy` calls and are proven with injected
failures. U35 stays off by default.
