# Response to REV-20261021-165

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. The rollback I added in REV-163 (`new_account_abort`)
ran `userdel -r` on every guard failure. `useradd -m` creates the home only
when it is absent. So in U42's own threat case — a hand `userdel` without
`-r`, a recycled uid, the old home still on disk — a failed `zfs` read during
the next join would delete files this run never created. The message also
said "nothing else was changed", and the rollback-failure path instructed
`userdel -r` by hand.

### Implemented change

`deploy.sh`:

- **Both call sites check the home before `useradd`.**
  - The join path does `local home_pre=0; [ -e "/home/$account" ] &&
    home_pre=1`.
  - The standalone path does the same into `HOME_PREEXISTED` on `$HOMEDIR`.
  - Both pass the path and the result:
    `new_account_drop_inherited_grants "$account" "/home/$account"
    "$home_pre"` and the matching `$USERNAME`/`$HOMEDIR` form.
- **The guard decides ownership of the home once, up front.** It counts the
  home as created by this run (`NEW_ACCOUNT_HOME_OURS=1`) only when both hold:
  - the caller saw it absent (`0`);
  - `getent passwd` gives the account exactly that home path.

  Anything else is "not proven ours": the home existed, the caller passed
  nothing (default `1`), or passwd names another path (a non-default
  `useradd` HOME base, for example).
- **`new_account_abort` acts on that decision.**
  - Ours: `userdel -r <account>`, as before.
  - Otherwise: plain `userdel <account>`. The home is left in place, and the
    message says it was not created by this run (or that could not be proven)
    and should be looked at before anything is removed.
  - If the rollback command itself fails, the by-hand instruction is that same
    command, never `userdel -r` for an unproven home.
- **Unchanged.** REV-163's checked reads are unchanged. Every failure still
  removes the account, so a re-run creates and checks it again rather than
  skipping it as "already exists". REV-164's `--leave` and scope paths are
  untouched.

  where `deploy.sh` runs as root.
- No live account creation was run with an injected `zfs` failure; a mocked

## F1 rejection of `a8ebb8a1` (2026-10-21) — IMPLEMENTED

### Analysis

Accepted. The first fix checked the home before `useradd` and trusted
"absent then, passwd path matches now" as proof of ownership. A directory
created between that check and `useradd` passed both tests, and the rollback
still ran `userdel -r` on it. That is the reviewer's counterexample, and it
cannot be closed by a better check: `useradd -m` gives no signal that it,
rather than someone else, created the directory.

### Implemented change

`deploy.sh`:

- The rollback **never deletes the home**. `new_account_abort` always runs
  plain `userdel <account>`. The message names the home it leaves ("a
  rollback never deletes a directory it cannot prove it created"). It says to
  look at it, and to remove it by hand (`rm -r <home>`) only if it holds
  nothing but what `useradd` copied from `/etc/skel`.
- If `userdel` itself fails, the by-hand command is plain `userdel`.
- The ownership guess is gone: no pre-`useradd` check, no
  `NEW_ACCOUNT_HOME_OURS`, no `getent` comparison. Both call sites pass only
  the home path, and only for the message.
- A re-run's `useradd -m` reuses the left directory, so the guard still runs
  again on the re-created account. The REV-163 read handling and REV-164 are
  unchanged.

### Evidence

- commit: `accc597b` (branch `finisz/REV-165b`)
- `test/draftscope`: the harness `userdel` stub deletes on `-r`, so any
  recursive rollback shows up as a missing home or sentinel.
  - **race:** the reviewer's counterexample. The caller passes a "no home"
    hint (`0`) while the directory with a sentinel already exists. The
    sentinel survives and `userdel` runs without `-r`.
  - an empty home ("created by this run" in the first fix's terms) is kept
    too, and is named with the by-hand `rm -r`.
  - list/allow/unallow failure with a pre-existing home, a passwd path
    mismatch, and a failing `userdel` all leave the home and use plain
    `userdel`.
  - the rollback code contains no `userdel -r` and no ownership variable.
  - both call sites pass the home path.
  - the REV-163 cases now expect plain `userdel`.
- pve9 clone:
  - fixed tree: `test/draftscope` 70/0.
  - negative control: `deploy.sh` from main (`a8ebb8a1`), `race` fails with
    `1||-r newacct` — the reviewer's result. The other new expectations fail
    as well (6 cases in total).

### Remaining risk

- After a failed join, an empty home directory is left behind until someone
  removes it. That is deliberate: a leftover directory is recoverable, a
  deleted one is not.
