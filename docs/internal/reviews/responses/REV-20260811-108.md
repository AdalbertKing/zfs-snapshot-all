# Response to REV-20260811-108

## F1 — IMPLEMENTED — the audit never takes source-retention ownership of a passive `-e` source

### Analysis

ACCEPTED. `audit-source-retention` classified every active remote-PULL dataset with an
installed remote `src` and no effective bounded prune as "missing source retention",
without discriminating the installed transfer semantics. That encodes the rule
`remote PULL without source prune => repair it`, which is wrong for the recorded
passive-source design: a relationship whose transfer uses `snapget -e` consumes an
already-existing, externally-owned snapshot, so this package does not own the source
snapshot lifecycle and legitimately carries no source `[prune:]`. Under the old code
the audit reported such a correct CONFIG as defective, and `--apply` would propose a
source prune plus a remote `destroy` grant — taking destructive ownership of snapshots
this package never created.

### Implemented change

The audit reads the passive marker off the same installed CONFIG it already treats as
runtime truth — the `[dataset:]` transfer `flags` — with no new state token or second
policy model:

- `installed_dataset_field` (generalized from `installed_dataset_src`) reads any
  `[dataset:]` field back from the installed config;
- `installed_dataset_is_passive` returns true when the installed transfer `flags`
  carry `-e`;
- in the audit scan, a passive dataset is reported under a distinct "pasywne (-e, poza
  wlasnoscia)" count and NEVER entered into `MISS_SRC`. Because `--apply` iterates
  only `MISS_SRC`, a passive relationship is left byte-identical and its remote
  `destroy` grant is never checked. TARGET prune is untouched (the audit never
  looked at it).

This is purely a classification guard in the read-only scan; it composes with the
REV-102 F3 managed-prefix fix (a passive source is excluded *before* the effective-
retention test even runs), so making F3 more precise does not widen the universe of
relationships the audit acts on.

### Remaining risk

The discriminator is the `-e` transfer flag as recorded in the installed `[dataset:]
flags`. If a future transfer mode introduces another externally-owned-snapshot shape
that does not surface as `-e`, this guard would not recognise it; that is the same
single-source-of-truth the rest of the audit already relies on. No new live ZFS proof
is needed for the classification itself (the reviewer agreed); the remote-prune
execution path retains its separate live proof under REV-102.
