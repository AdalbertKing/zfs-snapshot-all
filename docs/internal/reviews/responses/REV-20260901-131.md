# Response to REV-20260901-131

## F1 — IMPLEMENTED

### Analysis

The finding is correct and the defect is mine. The exemption was written to
justify one thing and coded to permit two:

```sh
case "$field" in gfs|gfs_pattern) ;; *)          # matches the FIELD
    if [ "$kind" = dataset ] || [ "$kind" = prune ]; then
```

The prose beside it argued only the `[prune]` case — there `gfs` is a property
of the section, one combined `-G` line over every tier it names, so that is the
only place it can be said at all. The code never looked at the kind, so
`[dataset] gfs` came along for free.

In a `[dataset]` fragment it is exactly what the rule exists to prevent, and
worse than the cases the rule was written for. The fragment is pasted into every
`[dataset:]` section the profile creates; `resolve_field gfs "$ds" "$tmpl"` reads
the section before the template; so one `gfs = yes` converts every referenced
tier from flat-count retention to time buckets. Nothing fails — the config is
valid and the jobs run — so a lowercase profile simply starts rendering ladders
while its own text still assigns policy per tier.

### Planned or implemented change

The exemption now matches on the kind together with the field, and sits inside
the branch it belongs to:

```sh
if [ "$kind" = dataset ] || [ "$kind" = prune ]; then
    case "${kind}:${field}" in prune:gfs|prune:gfs_pattern) ;; *)
        ...the template-only rule...
    ;; esac
fi
```

`[template:] gfs` is untouched: it never entered this branch, which is why the
per-tier ladders keep working.

### Remaining risk

The rule now reads "policy with a template layer may not appear in a fragment,
except `gfs`/`gfs_pattern` in `[prune]`". That is one exception, stated with its
reason, and the suite pins both sides of it.

What this does not address, and is worth naming because the REV's reproduction
depends on it: the catalogue suite's shape check (`lowercase but rendered a -G
ladder`) is what caught the consequence, not the boundary. It still only sees
SHIPPED profiles. A user profile that does the same thing is now refused at
validation, but the shape check would not have found it — the ownership
boundary is the only guard for anything not in `profiles/`.
