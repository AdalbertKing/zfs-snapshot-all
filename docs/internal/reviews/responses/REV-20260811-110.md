# Response to REV-20260811-110

## F1 — IMPLEMENTED — managed-prefix lookup is now relationship-exact

### Analysis

ACCEPTED. `managed_source_prefix_for_scope()` selected the relationship's managed
snapshot prefix from the first rendered transfer line satisfying a **substring** test
`case "$line" in *"$2"*)`. For neighbouring scopes where one is a textual prefix of the
other — `zfsbackup@10.5.5.5:rpool/data` vs `…:rpool/data2`, or a parent/child pair —
the line for `data2` also contains `…:rpool/data`. If it renders first with a different
`snapget -m` prefix, relationship A (`data`) was handed relationship B's (`data2`)
managed family, and `source_scope_is_bounded()` then compared A's prune against the
wrong prefix — a false-green or false-missing depending on the two patterns.

### Implemented change

One-token tightening, no new CONFIG model: the scope is now matched as an EXACT quoted
argument, the same identity level `source_scope_is_bounded()` already uses:

```sh
case "$line" in *"\"$2\""*) ;; *) continue ;; esac
```

`"…:rpool/data"` (with the closing quote) does not appear inside `"…:rpool/data2"`, so
a colliding neighbour can no longer satisfy the lookup. The genuine "no exact transfer
line found" fallback to `automated_hourly_` is preserved for that case only.

### Remaining risk

The association depends on gen-cron rendering the scope as a quoted argument in the
transfer line (it does, and section 56 pins that format). If a future render dropped
the quotes, the exact match would fall back to the default prefix rather than
mis-associate — fail-safe, not false-green. No live ZFS needed for a parser/association
correction.
