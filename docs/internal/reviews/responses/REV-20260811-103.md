# Response to REV-20260811-103

Both findings ACCEPTED. Design-time review of my design note; corrected in place
(`docs/discussions/PHASE5-SOURCE-RETENTION-DESIGN-2026-08-11.md`), re-derived from
the current code rather than a remembered shape. No production code was built on
the wrong premises — the step-2 LOCAL composition already delivered is unaffected
(it neither prunes remotely nor relies on bookmarks).

## F1 — IMPLEMENTED — grant re-derived; no widening

You are right and my Q3 was stale. `deploy.sh` `do_commit_scope` already delegates
`snapshot,destroy,send,receive,create,mount,rollback,hold,release,canmount,bookmark`
per granted source dataset (`ZFS_PERMS`, deploy.sh:146), so `destroy` (and
`bookmark`) are present at exactly the relationship scope. The default source prune
is a plain `delsnaps.sh` → `zfs destroy <snap>` of `automated_hourly_` snapshots,
which needs only `destroy` — **already granted, no gap, no widening**. `mount` is
needed only for `-F` clear-cut (`zfs destroy -R` unmounting a dependent clone,
which on Linux needs root regardless of delegation), and the collector-owned source
prune is deliberately not clear-cut. Q3 rewritten to say so, and step 3/4 now
require a **current-grant negative control** — the delegated identity with `destroy`
succeeds, with it revoked the remote prune fails closed and activation refuses —
so the required permission is proven from the command path, not assumed.

## F2 — IMPLEMENTED — bookmark treated as conditional, FULL-resend made explicit

Accepted. Q4 no longer claims the bookmark guarantees an incremental base. The
corrected invariant distinguishes:

- **non-recursive + confirmed bookmark** → base survives the prune; incremental
  continuity is claimed only here;
- **recursive, or a failed/absent best-effort bookmark** → source pruning past the
  last common snapshot forces a FULL resend, which must be an **explicit product
  decision surfaced in preview/status**, never an accidental result of a non-fatal
  bookmark failure.

The default source window equals the target ladder (24H/7D/4W/12M), generous enough
that under normal cadence the last-sent snapshot stays inside it and the base
survives by construction; the FULL-resend risk arises only when the source window
is shortened below the transfer gap or on a recursive relationship, which the
preview states plainly. Left as one open sub-decision for owner/reviewer: hard-
refuse collector-owned source pruning on recursive relationships, or allow it with
the explicit FULL-resend warning (recommended, since a recursive relationship
already takes a FULL on its first miss). No frozen-engine change is proposed to
manufacture a recursive bookmark guarantee.

## Accepted design unchanged

Collector owns both retentions; no autonomous source cron; default CREATE proposes
the same ladder rendered as two independent native policies; remote prune reuses
`[prune:remote-scope]` + the relationship's pinned SSH; existing CONFIGs get an
explicit audit/previewed migration; Phase 5 install stays blocked until source
retention is safe and proven.
