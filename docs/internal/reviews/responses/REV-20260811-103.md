## Residual F1 — IMPLEMENTED — every stale `destroy,mount` / "grant does not exist" removed

You are right the note was internally inconsistent: corrected Q3 said `destroy` is
already delegated, while Sequencing step 3 and the step-2 status still said
`deploy.sh --join destroy,mount` and "before the source destroy grant exists". Both
removed. Step 3 now reads: **remote-prune composition + fail-closed verification of
the ALREADY-delegated `destroy` capability and the pinned SSH path — no grant
widening** (`do_commit_scope` already grants `destroy`); the negative control is to
**revoke/omit** `destroy` and prove the remote prune refuses/fails. No active
instruction to widen the grant remains anywhere in the note.

## Residual F2 — IMPLEMENTED — "survives by construction" replaced with the real invariant

Accepted. The note no longer claims the default ladder makes the base survive by
construction, nor limits the risk to operator-shortened windows / recursive mode.
The stated invariant is now: **incremental continuity is guaranteed only when a
usable ordinary common snapshot OR a proven usable bookmark remains.** The default
equal ladder *reduces* the risk but does not prove survival through every failure
sequence — including your exact case: a non-recursive relationship whose bookmark
refresh failed/was absent, where later failed backups create newer snapshots that
retention keeps while aging out the last successfully transferred one. The step-4
live/negative-control campaign now explicitly requires a bookmark-unavailable case
with later snapshot creation/prune, proving the chosen fail-closed/degraded
behaviour (explicit FULL-resend surfaced in status, never a silent broken chain).

## Related — REV-102 step-2 F2 (destructive scope mismatch) fixed in the same pass

The reviewer's REV-102 review found a real defect in the delivered step-2 local

`test/localbackup` now asserts the source prune is non-recursive and adds the
child-survives control. (Recorded here for context; REV-102 stays OPEN as a
