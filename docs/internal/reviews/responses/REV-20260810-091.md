### Analysis

The review's one-sentence rule is the right one and is what the fix implements:
**pure topology reactivation does not create, repair, normalize or migrate
policy.** `needs_profile=0` was supposed to mean exactly that; it did not,
because two policy operations sat outside the gate.

#### F1 — the reserved-prefix floors

The `[excluded:__replicate_|vzdump|__migration__]` loop ran on every call. It is
CONFIG-WIDE policy scaffolding: `gen-cron.sh` pastes its `PROTECT_FLAGS` onto
every emitted prune line in the whole file. Appropriate when policy is being
created or migrated; wrong as a side effect of an endpoint refresh. An operator
who deliberately removed one floor from an installed native CONFIG would find it
restored by the next `set-endpoint` follow-up, with only a log line to say so.

Now inside the same `needs_profile` gate as the template loop. The floor is not
abolished — a genuine policy-creating call still installs it, pinned by its own
assertion so the fix cannot be mistaken for silently dropping a safety default.

#### F2 — the pre-GFS refusal

The refusal exists because adding the current GFS ladder on top of a legacy
config whose `standard_*` still carries `prune_schedule` would prune the same
snapshots twice on the same schedule. That hazard is real **only when policy is
actually being added**. When nothing is generated there is no second ladder, no
double prune, and nothing to refuse — so refusing anyway made a topology change
depend on a policy migration, which is the Phase 3 violation.

Now gated on `needs_profile` as well. Two details worth stating because they are
easy to get wrong:

- `detect_profile_gfs()` still runs **unconditionally**. Only the refusal is
  conditional. `PROFILE_GFS` is read downstream — `client_section_plan()` uses
  it to decide the prune shape, and the activation summary prints it — so
  skipping the detection would have broken things the refusal has nothing to do
  with.
- The gating is self-consistent on a legacy host: `PROFILE_GFS=0` means
  `client_section_plan()` plans no `[prune:]` at all, so `PLAN_NEEDS_PROFILE`
  turns on exactly when a `[dataset:]` section must be generated — which is
  precisely the case where the GFS `dataset.inc` and its namespaced templates
  would land on a legacy host. The refusal fires there and nowhere else.

#### One defect found in my own patch before it shipped

The first version of the F1 gate was written as
`[ "$needs_profile" -eq 1 ] && \` in front of the `for` loop. As the last
statement of the function that makes `ensure_cron_config`'s exit status 1
whenever the gate is closed — the same fail-open-by-exit-status shape REV-084
was filed for, and it would have been invisible here because no caller checks
this function's status. Replaced with an explicit `if` block and an explicit
`return 0`.

### Observation, not a finding, and deliberately not fixed here

Writing the F1 fixture surfaced an unrelated small defect: when
`ensure_cron_config()` dies, `cmd_activate_client()` has already created its
working copy via `mktemp` next to the config, and that die path does not remove
it — so a failed activation leaves a `.zfsbackup-work.XXXXXX` file behind. Every
path `cmd_activate_client` controls itself does clean up; this one exits from
inside the callee.

It cost real time here, because the test's capture stub then had two sources for
one destination and `cp` failed silently, which read exactly like a code defect
in the change under test. It is harmless in production (a 0644 temp file next to
the config, ignored by `gen-cron.sh`), so I have not folded a second, unrelated
change into a commit whose negative control has to stay clean. Happy to fix it
as its own commit on request.

### Remaining risk

- **`zfsbackup-live-pair` not run.** The change alters two conditionals inside a
  candidate-CONFIG composition step. No crontab install path, no transfer, no
  grants, no UID, no host state. Per the review's evidence boundary no live
  campaign is required. Left `IMPLEMENTED`, not `CLOSED`.
- **A legacy host is now reactivatable without ever being migrated**, which is
  the intent, but it does mean a pre-GFS host can stay pre-GFS indefinitely
  while its endpoints change. That was already true of `gen-cron.sh` itself,
  which happily runs a legacy config; the difference is that the wrapper no
  longer forces the question at an unrelated moment. `migrate-profile` remains
  the deliberate, previewed way to move, unchanged.
