# Response to REV-20260901-132

## F1 — IMPLEMENTED

### Analysis

Correct, P1, and mine. The suppression was right about one profile and wrong
about the catalogue.

I disabled the source-retention block in no-copy mode because it duplicated the
pruning — measured on pve9 with `y5m12d31h24-gfs`: eight `delsnaps` lines
instead of four, each family cut twice, once by its own `-G` ladder and once by
a flat count that would undo it. That measurement was real. The conclusion drawn
from it — "with no destination the tiers already prune" — was a generalisation
from the one profile in front of me.

For `default` it is false, and the consequence is the one the REV names:

```
--source=... --target=''  with profile `default`
  ->  1 snapsend line, 0 delsnaps lines
```

Its send tier carries no `prune_schedule`; the retention lives in the `[prune]`
fragment and in the source-retention templates the fragment names. Suppressing
that block left a job that creates a snapshot every hour and schedules nothing
to remove one. Valid config, running jobs, unbounded pool — silent, which is the
class this project treats as worse than a refusal.

### Planned or implemented change

Retention must be emitted exactly ONCE, and where it lives is a property of the
profile rather than of the mode. The distinguishing question already exists in
this file and is asked by `schedule_tier_exprs` in as many words — *"a flat
profile prunes from the tiers its `[dataset]` references, so its prune fragment
is empty"*:

```sh
if [ -n "$LB_RETFRAG" ] \
   && { [ "$no_copy" -eq 0 ] || [ -s "${PROFILE_PRUNE_FILE:-}" ]; }; then
```

- a profile with its own `[prune]` fragment (`default`, `passive`) keeps its
  retention there and nowhere else, so the source-prune section is emitted and
  the result is bounded;
- a profile without one (`y5m12d31h24-gfs`, `-age`) has retention in the send
  tiers, and `profile_retention_fragment` then falls back to those same tiers —
  so emitting the block would restate what the tiers already schedule.

No new predicate, no mode-specific special case: the same split the generator
already makes.

### Remaining risk

**Not covered, and it is the same gap in a different place.** The rule is now
"emit source retention unless the profile's tiers already carry it", decided by
whether the profile has a `[prune]` fragment. That is true of every shipped
profile and was checked against all seven. A hand-written profile that has NO
`[prune]` fragment and whose tiers ALSO carry no `prune_schedule` would still
render snapshots with no retention — the composer has no way to notice, because
"this profile schedules no pruning at all" is a property of the rendered config,
not of the fragment.

The honest guard for that is a check on the CANDIDATE — refuse to install a
no-copy plan whose generated block creates snapshots and prunes none — and it
would catch this class rather than this instance. I have not built it here
because it is a new refusal on a shared path rather than a correction to this
one, and it belongs in its own change with its own evidence.
