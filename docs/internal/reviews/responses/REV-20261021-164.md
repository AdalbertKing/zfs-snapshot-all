# Response to REV-20261021-164

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `do_leave()` read each recorded dataset with
`zfs list -H -o name -- "$ds" >/dev/null 2>&1 || continue` at three
stages: the hold check, the revoke and the post-revoke verification. A failed
read was therefore indistinguishable from "this dataset no longer exists".

The verification read the ACL as `zfs allow "$ds" 2>/dev/null | grep -Eq …`,
whose status is `grep`'s, so a failed `zfs allow` meant "no grant left". In
the worst combination, `zfs unallow` failed (only a warning) and then the
re-read failed. `do_leave` then went on to `userdel -r`, removed the manifest
and scope files and released the uid with its grant still on the dataset.

`commit_scope_dataset_held` had the same shape: a process-substitution
inventory and a `zfs holds | awk | grep` pipeline. So an unreadable hold read
as "no hold". The new test reproduces all of these on the reviewed blob (see
Evidence).

### Implemented change

`deploy.sh`:

- **`leave_ds_exists <label> <dataset> <what-is-left>`.** A dataset counts as
  absent only on ZFS's own word for it: `zfs list` fails and its output
  (`LC_ALL=C`) contains `dataset does not exist`. Any other failure dies with
  the dataset, the first line of the `zfs` error and what is left. It is used
  at all three stages:
  - hold check: "Nothing has been changed.";
  - revoke and verification: grants already revoked where that succeeded; the
    account, key and manifest are left in place; re-run `--leave`.
- **Verification reads the ACL into a variable and checks the read.**
  `acl="$(zfs allow "$ds" 2>&1)" || die …`. The message names the dataset,
  the exact uid and the account, and says that an unreadable ACL is not an
  empty one. The residual match then runs on the captured text with the
  unchanged uid/account pattern.
  - A failed `unallow` followed by a failed re-read stops.
  - A successful `unallow` followed by a failed re-read stops.
  - A grant that is read back still blocks, as before.
- **`commit_scope_dataset_held` returns 2** when the snapshot list or a
  snapshot's holds cannot be read. Both reads are captured and checked.
  - `--leave` tells 2 apart and dies ("an unreadable hold is not 'no hold'",
    nothing changed).
  - The other caller, `do_commit_scope`: see R1 below. The first version
    (`f434f61b`) claimed its `elif` reads 2 as *held*. That was wrong. The
    reviewer's R1 is correct.
- **Unchanged:** the manifest-bound uid rule (REV-20260804-040). It still
  matches only the exact bound uid, `(unknown: uid)` or the exact account
  name, never another principal. All refusals happen before
  `revoke_quiesce_grant`, `passwd -l`, `userdel`, and before the manifest,
  scope or pair-gate files are removed.

## R1 — IMPLEMENTED (reviewer rejection of `f434f61b`, 2026-10-21)

### Analysis

Accepted. In bash `elif commit_scope_dataset_held "$p"` with status 2 is
false. The dataset therefore went to `revoke_clean`, and the narrowing loop
unallowed it while its hold could not be read. My response for `f434f61b`
stated the opposite without running that caller; it is recorded as E96 in the
implementer error log.

The reviewer also pointed at the first read in the same loop,
`zfs list … || revoke_gone`. It took an unreadable dataset as gone and dropped
it from the manifest's granted list without revoking it. The grant was not
removed, only forgotten.

### Implemented change

- **`zfs_ds_presence <dataset>` is the one presence read.** It returns
  0 = exists, 1 = ZFS says "dataset does not exist" (`LC_ALL=C`),
  2 = the read itself failed. `ZFS_READ_ERR` holds the first error line.
  `leave_ds_exists` now uses it, with no behaviour change for `--leave`.
- **`do_commit_scope` handles 0/1/2 of both reads explicitly in its plan
  loop.**
  - presence 1: `revoke_gone`, as before.
  - presence 2: die.
  - presence 0, then hold 0: `revoke_held`; hold 1: `revoke_clean`; hold 2:
    die.
  - Both refusals happen inside the plan, before the first `zfs allow` or
    `zfs unallow` and before the manifest's `PEER_JOIN_GRANTED_DATASETS` is
    rewritten. Each names the dataset and the reason and says "No grant or
    revoke was made".
  - The only earlier write in `do_commit_scope` is the legacy uid recording
    into the manifest. It is a record, not a grant.
- The comment on `commit_scope_dataset_held` now says that every caller must
  tell 2 apart and that `if`/`elif` reads 2 as false.
