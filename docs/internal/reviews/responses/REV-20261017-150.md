# Response to REV-20261017-150

## F1 — IMPLEMENTED

### Analysis

Accepted as written. The control flow is as the review describes it.
`process_dataset()` returns 0 when the newest source snapshot is already on
the target with the same GUID, and that return comes before its
`guest_disk_is_live()` call. The main loop then calls `mirror_target()` for
any successful `process_dataset()` when `-M` is set. `mirror_target()` had no
guest check of its own. The comment above `BACKUP_LANDING` said the guard
"runs first in process_dataset", which is false for this path.

I reproduced it with the new suite's fixture against `snapget.sh` from `main`
`0f7c26b0` (the review's invocation, `-N -M -e root@source:tank/vm-100-disk-0`,
target `@old` and `@base`, source `@base`, same GUID, VM 100 running). Result:
`zfs destroy tank/vm-100-disk-0@old` with no `qm status` call in the trace.

### Implemented change

`snapget.sh` only, in two places:

1. **`mirror_target()` checks the guest first.** Its first statement is now
   `if guest_disk_is_live "$tgt"; then log 0 "Mirror (-M) on '<tgt>':
   refused -- the live-guest check did not clear this target (its reason is
   the log line before this one), NOTHING deleted"; return 1; fi`. It runs before the source and target listings
   and before any `zfs destroy`.
   - `guest_disk_is_live` is the existing gate, unchanged. It returns "live"
     for a running guest. It also returns "live" when the status cannot be
     read (fail-closed), with its own diagnostic: "could not determine
     whether that guest is running".
   - It returns "not live" for a stopped guest and for a dataset whose name
     is not a guest disk.
   - On refusal the main loop's existing `FAILED_DATASETS+=("<ds> (mirror)")`
     makes the run exit 1.
2. **The comment above `BACKUP_LANDING` is corrected.** It now names both
   checks and says why the second one exists.

The check is placed in the mirror, not by moving the early return. Every
route into the mirror then passes it, and the already-present return,
receive, P-0, the mirror policy, naming and statistics stay unchanged. On the
ordinary transfer path into an existing target the guest is now queried
twice: once before the receive (only when the target exists and `-f` is not
set) and once before the mirror. For a running VM, `quiesce_guest_status`
also asks `qm guest cmd ... fsfreeze-status`. Nothing else changes.

**Twin:** not ported. `mirror_target` and `-M` exist only in `snapget.sh`, and
no twinned function moved (`test/twins` 94/0). snapget stays v2.75. Refreeze
done, and the freeze entry names this REV.
