# Response to REV-20261027-177

## F1 — IMPLEMENTED

### Analysis

Accepted as reported. `rel_panel_pairs()` chose the dataset named by the error with
`s in text`, a substring test. `pool/vm-10` therefore matched an error naming `pool/vm-100`,
and `data` matched `metadata`. When that happened, the panel listed the whole shared scope
instead of the one dataset the error named.

### Implemented change

- `tui/zfs-tui.py`: new `text_names_dataset(text, ds)` counts a match only on the whole
  dataset name.
  - Before the name: anything except a name character (`A-Za-z0-9_`), `.` or `-`. In practice
    the start of the text, whitespace, a quote, `:` (`host:ds`, `account@host:ds`) or `/` (the
    copy under a target base, e.g. `hdd/backups/pve2/rpool/ROOT/pve-1`).
  - After the name: anything except a name character, `-`, `/` (that is a child dataset), or
    `.` followed by a name character. In practice the end of the text, `@` (a snapshot), `:`,
    whitespace, a quote, or a period that ends a sentence.
- `rel_panel_pairs()` uses it. Grouping by cron label (one failure counted once) is unchanged.
  Exactly one named member names that member; none or more than one shows the complete
  shared scope.

### Remaining risk

- A `/` is accepted before the name so that the copy under a target base counts. When one
  shared line carries both `data` and `pool/data`, an error naming `pool/data` therefore names
  both members, and the panel shows the whole scope. That is the "no guessing" outcome, not a
  misattribution.
- Engine errors that name no dataset at all (e.g. `cannot receive incremental stream: dataset
  is busy`) still show the whole shared scope. Naming the dataset there would need the engine
  log line, which is out of scope here.
