## F1 — IMPLEMENTED

### Analysis

Confirmed as reported. `mirror_target` built `on_src` from the source's snapshot NAMES and
destroyed an older target snapshot whose name was not among them. The transfer decides lineage
by GUID (`find_common_snapshot`), so the two disagreed on a rename. The source still held the
recovery point, and its copy on the target was destroyed with rc 0.

Frozen-engine opening: `snapget.sh` is frozen. The Owner opened it for this REV: "Tak, otwórz",
the answer to "Otwierasz zamrożenie snapget.sh/snapsend.sh pod REV-196?". It is recorded in
`docs/project/ENGINE-FREEZE.md` and refrozen. `snapsend.sh` has no mirror and is not changed.
`lib-zfs-snap.sh` is not changed: the fix reuses its `get_snapshot_guids`.

### Planned or implemented change

`snapget.sh` `mirror_target`, after the existing guards (live guest, readable non-empty source
list, readable target list, common base found by name on the target), all unchanged:

- It reads both GUID lists with `get_snapshot_guids`, the reader `find_common_snapshot` uses. The
  source is read over the same ssh identity when it is remote.
- Every doubt deletes nothing and returns rc 1:
  - either GUID list cannot be read;
  - a listed snapshot has an empty or non-numeric GUID;
  - a target snapshot older than the base is missing from the target's GUID list.
- The decision is complete before the first `zfs destroy`. A doubt found halfway leaves nothing
  half-done.
- A target snapshot older than the base:
  - **stays** when any source snapshot carries its GUID, under any name. A rename on either side
    is logged at level 1: `kept <tgt>@<name> -- the source still holds it as @<name> (same GUID
    ...)`;
  - **is destroyed** when no source snapshot carries its GUID. That includes a snapshot that
    only shares its name with a source snapshot under another GUID;
  - is never a Proxmox-reserved family, as before.
- The summary line adds `N kept (on the source under another name)`.
- Retained under its existing name, not renamed to the source's name: renaming on the target
  could collide with a later received snapshot.

Entry paths: generated replica jobs (`snapget.sh -e -M` / `-m PREFIX -M`, `gen-cron.sh`) and a
direct `snapget.sh -M` all reach this one function after a successful pull. Local and remote
sources go through `get_snapshot_guids`, which takes the remote user and host.

No profile, template or retention setting is read or added.

  real pool: a new snapshot under an old name is newer than the base, so `-M` does not judge it.

  `get_snapshot_guids` call with user and host, already used by `find_common_snapshot`.
- **MANUAL / NOT RUN:** a restore from the kept point beyond the clone read; physical media;
  production hosts.
- `snapget -n` still lists target-only snapshots by name in its conflict report. That report is
  not destructive, and it is not changed here.
