# Response to REV-20261028-182

## F1 — IMPLEMENTED

### Analysis

Accepted as reported. In `delete_snapshots`, `mode=gfs`, each creation value was captured with
`$(run_zfs ... get -H -p -o value creation ...)` without checking the command status or the
value. An empty or non-numeric value failed every `-gt`/`-le` bucket test, so that snapshot was
never a survivor, fell through to destroy, and the dataset finished with success stats and
`EXIT_CODE` untouched.

`delsnaps.sh` is a frozen engine. The Owner unfroze it for this change in chat on 2026-10-28
("Tak, odmrażam"); the entry with that direction is in `docs/project/ENGINE-FREEZE.md` and the
baseline is re-taken with `./test/impact.sh --refreeze`.

### Planned or implemented change

`delsnaps.sh` v1.29 -> v1.30, `delete_snapshots`, GFS branch only:

- every candidate's creation is read with its status checked (`|| gfs_c=""`), a trailing CR
  removed, and the value accepted only when it is a non-empty string of digits (so empty, text
  and negative values are refused);
- if any value is unusable, the dataset fails closed BEFORE the ladder and the first destroy:
  one error line names every affected snapshot and the value read, `emit_stats ... failed`,
  `EXIT_CODE=1`, `return 1`. No partial ladder over the readable subset.

Bucket selection, reserved-prefix protection, holds, dry run, the `run_zfs` remote transport,
clear-cut and the age/count modes are unchanged.

### Round 2 -- the remote path (reviewer verification of `040e4b4a`)

The reviewer: CI never runs `sudo ./test/delsnaps/run.sh`, and the new cases only shimmed a
local `zfs`, never the ssh branch of `run_zfs`. Accepted. Implementation
`83a00d30fd62765582f7ff1a75a0dff4301bac4d` (test-only; `delsnaps.sh` unchanged since
`040e4b4a`) adds, in `test/delsnaps/run.sh`, a block that takes the remote branch:

- the dataset entry is remote (`root@shimhost:<pool>/<ds>`); a shim `ssh` first on PATH runs the
  exact command `run_zfs` builds (`zfs '-H' ... -- 'name'`) through `bash -c`, as the remote shell
  would, against a shim `zfs`; status, stdout and stderr of every call travel back as over a real
  connection, and each call is logged (a case asserts the calls really went through ssh);
- the shim `zfs` fakes creation times (`RS_CRE`), so the ladder is exact, breaks the creation read
  for a LIST of snapshots (`RS_BAD`, partial failure), and passes everything else to the real zfs;
  the shim `ssh` can fail the transport itself (exit 255) on the creation `get` only;
- positive, single tier (`-H24`): three snapshots in one hourly bucket -> the newest survives, two
  destroyed, all through ssh;
- positive, multi tier (`-H24 -D7`), creation times T-40d / T-3d / T-5h / T-30m: survivors exactly
  the last three, one destroy; the same input LOCAL gives the same survivors;
- fail closed over ssh: creation read failed / empty / not a number / negative for one of four,
  partial (two of four unreadable), and the ssh transport failing on the read -- each: rc 1, zero
  destroys, all four kept, the unreadable snapshot(s) named in one error line.
