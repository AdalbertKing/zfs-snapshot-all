# Response to REV-20261028-182

## F1 — IMPLEMENTED

### Analysis

Accepted as reported. In `delete_snapshots`, `mode=gfs`, each creation value was captured with
`$(run_zfs ... get -H -p -o value creation ...)` without checking the command status or the
value. An empty or non-numeric value failed every `-gt`/`-le` bucket test, so that snapshot was
never a survivor, fell through to destroy, and the dataset finished with success stats and
`EXIT_CODE` untouched.

`delsnaps.sh` is a frozen engine. The Owner unfroze it for this change in chat on 2026-10-28
("Tak, odmrażam"); the entry with that direction is in `docs/project/ENGINE-FREEZE.md` and the
baseline is re-taken with `./test/impact.sh --refreeze`.

### Planned or implemented change

`delsnaps.sh` v1.29 -> v1.30, `delete_snapshots`, GFS branch only:

- every candidate's creation is read with its status checked (`|| gfs_c=""`), a trailing CR
  removed, and the value accepted only when it is a non-empty string of digits (so empty, text
  and negative values are refused);
- if any value is unusable, the dataset fails closed BEFORE the ladder and the first destroy:
  one error line names every affected snapshot and the value read, `emit_stats ... failed`,
  `EXIT_CODE=1`, `return 1`. No partial ladder over the readable subset.

Bucket selection, reserved-prefix protection, holds, dry run, the `run_zfs` remote transport,
clear-cut and the age/count modes are unchanged.
