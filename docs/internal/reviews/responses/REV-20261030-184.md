# Response to REV-20261030-184

## F1 — IMPLEMENTED

### Analysis

Accepted. In `zfs-job.sh` the tree scanner has two gates. The outer gate (PR #1007) takes a word
with a `/` or of the form `account@host:dataset`, so `pveA:tank/data` passes it. The inner split
then kept only `*@*:*` as remote and dropped every other word with a `:` (`*:*) continue`). So
`host:dataset` was never listed. The same inner rule also dropped a local name that carries a `:`
after its pool (`tank/data:x`, a legal ZFS name).

The inner rule is older than PR #1007. It came with the tree guard (`fbe8f4c0`), and the current
release `AdalbertKing/zfsbackup` `630841d2` has it at `zfs-job.sh:217`. That release does not have
the PR #1007 outer gate.

PR #1007 was merged into `main` at 10:46 (`37049f55`). This review was already on `main` at 10:29
(`78147d15`). That is the implementer's error, recorded as E110 in
`docs/internal/IMPLEMENTER-ERROR-LOG.md`. Nothing was published or tagged from `37049f55`.

### Planned or implemented change

`zfs-job.sh`, inner split: a word is remote when it has a `:` and nothing before the first `:`
contains a `/`. This is the rule of `delsnaps.sh` `parse_remote`, the engine of the prune.
`snapget.sh` reads any word with a `:` as `[user@]host:path`; both default the user to `root`. `host:dataset` and `user@host:dataset` are listed over the
line's own ssh options and get the same `-X` exclusions, `rc=76` refusal and unlisted-tree policy.
A local `pool/name:x` stays local. The outer gate is unchanged, so option values such as
`__replicate_:2`, key and known_hosts paths, and the copy target are still not taken for the
source.

The ssh target is the host as written. With `host:dataset`, ssh uses the user the wrapper runs as.
The engines default that spelling to `root`. Cron jobs run as root, so the two match there.

cannot pass for any implementation of `zfs-job.sh`. The wrapper's ssh call puts
`-o BatchMode=yes -o ConnectTimeout=10` before the host, so no line of the fixture's `ssh.log`

fix. With only the anchor moved after the options, it passes on the fix and fails on both earlier
SHAs, as listed above. Requested: the reviewer corrects the anchor in the evidence file, or accepts
the anchor-corrected run.
