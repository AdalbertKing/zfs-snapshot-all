**The seam is smaller than the review assumes, and the reason is worth stating
precisely rather than as "make the argument optional".** The package *format*
already tolerates an absent scope:

- `PEER_CONF_DATASETS` is **not** in the required-key list;
- its validation loop is `for ds in ${PC[PEER_CONF_DATASETS]:-}`;
- `--join`'s grant loop is `for ds in $PEER_CONF_DATASETS`, which on an empty
  list grants nothing and does not fail;
- `--draft-config` already handles an empty manifest list by listing **every**
  candidate unfiltered.

So the data model is ready. What is genuinely new is the **second act**: a
finalize step on the source that grants from the edited file. That is the design
work; the flag is bookkeeping.

**One package-format change is unavoidable.** Sync supplies no target, but
`PEER_CONF_TARGET` is currently required and validated as a dataset name. Either
target becomes optional-when-sync, or a new `PEER_CONF_MODE=backup|sync` key is
added. I propose **both**: an explicit mode, and target required only in backup
mode. Because the key set is fixed and unknown keys are a hard error, a package
carrying `PEER_CONF_MODE` fails on an older peer with a clear message rather
than silently — which is the correct failure and should be documented, not
worked around.

## 3. Minimal design

**New commands: two. New states: one. New parsers: one, small. New files: one.**

```
pve1:  zfs-backup add-client pve2 --mode=backup --lan=<addr> [--target=<or default>]
       zfs-backup add-client pve2 --mode=sync   --lan=<addr>          (no target)
         -> keyscan + pin (unchanged) -> package WITHOUT scope

pve2:  deploy.sh --join=<package>                    (existing command, one behaviour removed)
         -> account + key, ZERO zfs permissions
         -> generates the scope file from every pool, opens $VISUAL/$EDITOR
       deploy.sh --commit-scope[=FILE]               (NEW)
         -> parse fail-closed -> diff against what is granted now -> grant/revoke

pve1:  zfs-backup activate pve2                      (NEW: fetch + existing seed/verify/activate)
         -> fetch the file over the relationship key, check its digest
         -> dry-run -> seed -> verify -> install cron
```

Avoided duplicate representations, explicitly:

- **no second scope manifest.** `PEER_SAVED_DATASETS` in the peer manifest stops
  being an independent list and becomes a **derived cache** of what the scope
  file says — or is dropped in favour of reading the file. Either way there is
  one editable list.
- **the collector's cron config is generated, not authored.** It is not a second
  representation of the choice any more than a binary is a second representation
  of source. A second *editable* dataset list would be; there will not be one.
- **the digest is not a representation.** It is a statement that the
  representation is one (T3).

## 4. One-file lifecycle

| Stage | Host | What happens |
|---|---|---|
| create | pve2 | `--join` inventories **every pool**; active roots default to the first level below each pool, excluding pool roots and known system branches (`rpool`, `rpool/ROOT`, `rpool/ROOT/pve-1`); the full `zfs list` follows as comments, plus a census of snapshot prefixes present on this host (T5) |
| edit | pve2 | `$VISUAL`/`$EDITOR`, `crontab -e` style; repeated freely — the file is inert until finalized (U2) |
| finalize | pve2 | `--commit-scope`: parse fail-closed → show the diff **against what is granted now** → `zfs allow` additions, `zfs unallow` removals **limited to what this relationship granted** (U3) → record the file's digest |
| transfer | pve2 → pve1 | byte-for-byte over the relationship key; no rewriting in transit (T2) |
| validate | pve1 | authoritative parse; digest must equal the one the finalize recorded, else refuse: *"pve2 granted from a different version of this file"* |
| use | pve1 | the same parsed scope drives the generated `[dataset:]` sections and the `[prune:]` ladder |
| re-edit | pve2 | any later edit repeats finalize; the collector refuses to run until the digests match again |

### Grammar

The file uses the project's existing INI shape so an administrator sees one
format, with a **much smaller key set** and no job semantics:

```ini
[dataset:rpool/data]
include_parent   = no
include_children = yes
exclude      = rpool/data/vm-999-disk-0
exclude_tree = rpool/data/scratch
```

**Parser reuse — what can and cannot be reused, and why.**

- **Reusable:** `deploy.sh`'s untrusted-input validators (`pc_is_dataset` above
  all) and its whole discipline — fixed key set, unknown key is fatal, values
  are data. This file arrives from another host and gets exactly the treatment
  `peer.conf` already gets.
- **Not reusable:** `gen-cron.sh`'s parser. Not because the grammar differs — it
  does not — but because its semantics do: it *requires* `use_template`
  referencing an existing `[template:]`, and it carries schedule, retention,
  `-K`/`-k` flags and target. Pointing it at the scope file would fail on the
  first section, and making it tolerate scope-only sections would drag collector
  policy onto the source. That is the U4 boundary.
- Therefore: a small dedicated reader, ~1 section kind and 4 keys, built from
  the existing validators.

Rejected by the grammar, fail-closed, returning the operator to the same file:
option-like names, `.`/`..` segments, control characters, duplicate or ambiguous
sections, unknown keys, and an `exclude`/`exclude_tree` that does not lie under
an included root.

**Exclusions are explicit paths, not regexes** (U5). Today's `-X` is an
unanchored regex — `-X 'lxc'` also removes `rpool/data/mylxcbackup`. Fine for an
expert, a mine for the audience this feature exists for. `snapsend -X` is
unchanged for expert use.

## 5. Online bootstrap

**First, a correction to my own earlier claim, which also narrows this finding.**
I had written that pairing is offline. It is not: `--pair` runs `ssh-keyscan`
against the peer, pins what comes back, and dies when the host is unreachable or
when the name resolves to more than one address. **The network is already
required.** Only the package *transfer* is manual.

**Owner fact that settles the rest:** the administrator running `add-client` on
pve1 has SSH access to pve2. It is the same person who would otherwise walk over
and run `--join`.

### Design (chosen)

- The package is delivered **using the administrator's own credentials**, over
  **the host key we already pinned** (`-o UserKnownHostsFile=<our pin> -o
  StrictHostKeyChecking=yes`). No prompt, no weakening, and the same key the
  relationship will use afterwards. The trust is not weaker than the pairing —
  it *is* the pairing's trust.
- The scope file **returns over the relationship key**, which exists by then.
- **Nothing listens.** No daemon, no token, no new dependency, no replay window,
  no transient secret to store or expire. There is nothing to replay: the
  package carries the collector's **public** key, role, mode, target, account
  name and label — no secret. What matters is integrity, and the human who has
  access to both machines is the integrity.
- Manual transfer remains, using the identical validation and commit path.

### Optional, opt-in: remote `--join` and the editor over `ssh -t` (U10)

My first answer was against this, and it was a reflex from a state we had
already changed. In today's code `--join` grants, so running it remotely would
be the collector provisioning the source. **After U2 it does not grant** — it
creates the account, installs the key, and ends with zero ZFS permissions. The
principle survives untouched, because the protected act is the grant.

Under one explicit flag (`--join-remotely`, name open): run `--join` on pve2, and
open the scope editor there over `ssh -t` so the whole flow is drivable from one
terminal. We are not moving authority, only the keyboard.

Three conditions:

1. **finalize stays local, always** — no flag changes that;
2. it rides the pinned host key; no `accept-new`, no exception;
3. the peer's manifest records that the entry was created **remotely**, from
   which collector and by whose session.

The flag *is* the declaration that the network is trusted. We do not try to
detect that: "trusted network" is not a measurable property and any test would
be theatre.

## 6. LAN-to-WAN flows

Identity is the peer's **host key under a stable alias**, and the generated jobs
already pin it that way. Changing address or port therefore does not invalidate
the pin. Every variant reduces to one question: *does `host:port` change?*

| Case | `host:port` | Action |
|---|---|---|
| routed OpenVPN, same address | unchanged | **re-verify only**, no mutation |
| Tailscale / new private endpoint | changed | one field; alias, key, target, bookmarks, job identity all survive |
| public IP + forwarded port | changed (host **and** port) | same as above |

Relocation always begins the same way:

```
verify current endpoint
  -> reachable, pinned fingerprint matches, dry-run says INCREMENTAL for every dataset
       -> change nothing
  -> unreachable
       -> try the other known endpoints
       -> only then ask for a replacement, pin it to the SAME alias, verify before activation
```

**Source-IP restrictions.** The peer's `authorized_keys` entry is plain — **no
`from=`** — so key auth does not care where the collector connects from. What
can bite is outside our code: a firewall on the peer limiting SSH to the LAN,
`sshd` `AllowUsers`/`Match Address`, fail2ban, and in the port-forward case the
router itself. All present as "cannot connect", not "permission denied", and we
already discriminate those (exit 255).

**The pinned key earns its keep twice here.** With a forwarded port the endpoint
names a *router*, not a machine. If the forward ever lands on a different host,
the key mismatches and the job **fails instead of backing up the wrong
machine**. This is why `accept-new` stays forbidden on this path.

**Catch-up contract.** A real final incremental over the still-working route
before the move (`final-catchup` exists), then re-verify and one real incremental
over the production route before cron. **Confirmed defect:** the messages name
the **source** as the machine being moved; it is the **collector**.

## 7. Failure and retry table

| Situation | Behaviour |
|---|---|
| editor interrupted / file unchanged | nothing granted, nothing transferred; the file stays; re-run the editor |
| malformed or ambiguous scope file | finalize refuses, names line and reason, **reopens the same file**; no partial grant |
| exclusion outside every included root | refused as malformed (typo caught at finalize, not after the first backup) |
| finalize interrupted mid-grant | grants are per dataset and idempotent; re-running converges. The manifest records what was granted, so a partial state is visible rather than guessed |
| revoke blocked by an in-flight hold | **refuse** while a `zfssnapall_inflight` hold from this relationship exists, or release it first — never `zfs unallow` and leave a hold nobody but root can lift (T4) |
| collector cannot fetch the file | relationship unchanged; retry. Scope already granted on the peer is not a problem: nothing consumes it until the collector validates it |
| digest mismatch between file and grant | refuse: the peer granted from a different version. Re-run finalize on the peer |
| dry-run fails for any dataset | no cron installed, config file untouched (existing `activate-client` behaviour) |
| sync: destination pool missing | refuse **before any receive**; the tool creates datasets, never pools |
| sync: destination exists, `written@head > 0` | refuse, with the number ("3.2 GB written since the common snapshot") |
| sync: destination is a live guest disk | **unconditional refusal**, no override |
| sync: peer is a member of the same PVE cluster | refused **at enrolment** (U8); pvesr already owns that job and we would be a second writer |
| endpoint mismatch after relocation | try known endpoints, then ask; never mutate a working endpoint |
| post-relocation plan says FULL | stop and report. A full send after a move is an operator decision, not a side effect — the existing `--allow-stale-catchup` shape is the model |

# Addendum, 2026-08-02 evening — owner decisions and a change of ground

Written after the owner worked through this review with me. Everything below is
**decided**, not proposed; the full record with the reasoning is in

## The three questions in §9 are answered

1. **Flag name: `--drive-peer`.** `--trusted-network` and its relatives were
   rejected for naming a property nobody can verify, and for reading as an
   assurance. `--drive-peer` names what happens: this host runs the peer's
   steps.
2. **All three reserved prefixes drop to `:2`** on the collector's own copies —
   `__replicate_`, `__migration__` and `vzdump`. (U6a had kept `__migration__`
   absolute; the owner leveled them.)
3. **Existing clients are migrated only on an explicit `--force`.** Metropolis
   keeps working untouched.

## The ground under §8 has changed: there is now a single crontab writer

Between this response and this addendum, the owner directed a refactor that the
review did not ask for and that changes how its slices land.

**Before:** six crontab write sites in three programs — four hand-rolled
`crontab -l | ... | crontab -` in `deploy.sh`, `gen-cron.sh`'s line-by-line
rebuild, `zfs-backup.sh`'s own reader/restorer/awk — plus **two lines loose in
root's crontab on every host**, indistinguishable from something a human typed.

**Now:** one writer, `lib-cron.sh`, whose only entry point takes the **block
name as an argument**, so writing outside your own block is not expressible.
Two requesters: `deploy.sh` owns `zfs-backup-host`, the job layer owns
`zfs-backup-managed`. Deployed on all four hosts; **zero loose job lines**
anywhere; job counts unchanged (root 3→3 everywhere, accounts 16/12/28/8
unchanged).

Why it was done first, and why it matters to this review: the enrolment adds
**new cron install paths** (activation, teardown of a relation). Under the old
model each would have been a fourth, fifth and sixth writer, and rewriting them
afterwards would mean touching production crontabs again. They will now be
requesters.

Two properties worth the reviewer's attention, because both are behaviour and
not tidying:

- **adoption preserves content.** A hand-tuned schedule keeps its time; only the
  line's location changes. `deploy.sh` promises "already present, leaving it
  alone", and the first thing this refactor did on a live host must not be to
  undo an operator's edit. The updater line is the single deliberate exception,
  normalised because three historical spellings had to collapse to one;
- **every write is read back.** `rc=0` from `crontab(1)` was never evidence, and
  the restore path — the one taken when something has already gone wrong — could
  previously claim success without looking.

`test/cron/run.sh`, 75 checks, stubs `crontab(1)` including a stub that accepts
a write and stores something else.

## One finding of my own, offered for the reviewer's verdict

The config layer has the same shape of problem one level up, and the owner has
agreed to fix it **inside** the enrolment work rather than separately.

`jobs.<host>.v4.conf` has **three machine writers plus the operator** —
`zfs-backup.sh`, `cron2conf.sh`, and a human, who is a *legitimate* writer here
unlike with the crontab. This review adds a fourth (the scope file). So "one
writer" is the wrong goal; **ownership per section** is:

- generated sections carry a marker naming their owner and client, so
  `remove-client` removes its own and never a hand-written section that happens
  to name the same dataset. Today `remove_managed_sections` matches by dataset
  name alone — the same "no owner means guessing" shape the loose crontab lines
  had;
- plus the digest already agreed as T3, so a config cannot drift from what was
  installed and granted.

Stated plainly for balance: the config is **better protected today than the
crontab was** before this refactor (`ensure_cron_config`,
`assert_cron_config_matches_installed`, atomic replace with both-sided restore,
two diffs before every change, and version control in a private repo). This is
not an emergency; it is a decision made at the moment the fourth writer appears.

## What I am starting on

Slice 1 of §8: the scope grammar, its reader and its validators — a new file
plus tests, no production path touched. Everything else depends on it (grants on

The implementer's position on the remaining slices is unchanged from §8, except

## Slice 1 (`ff712df`): `lib-scope.sh`

Grammar, reader (`scope_read`) and the yes/no decision (`scope_includes`) for
`[dataset:<path>]` sections with `include_parent`/`include_children`/

## Slice 2 (`4190d83`): `--join` stops granting; `--commit-scope` grants

**What changed.** `do_join`'s pull-role branch used to `zfs allow` straight
from the package's `PEER_CONF_DATASETS` and, if `--allow-quiesce` was given,
provision the quiesce whitelist from the same list. Both are gone from
`--join`. In their place:

- `--join` (pull, non-root) now grants **nothing**, logs where the scope file
  belongs and what to run next, and records `PEER_JOIN_AS` in the manifest so
  a later command can tell a root peer apart from a delegated one without
  re-deriving it from the account name.
- `--commit-scope=<label>` reads `/etc/zfs-snapshot-all/peers/<label>.scope`
  (created and edited by hand for now — slice 4 automates the generation),
  parses it with `lib-scope.sh`, and for each `[dataset:]` root walks its
  **real** descendants via `zfs list -r` (not `zfs allow`'s own inheritance:
  inheritance has no matching "deny", so an `exclude_tree` under an included
  root could not otherwise be honoured). Every dataset `scope_includes`
  accepts gets the same `zfs allow` the old code used. `--allow-quiesce` moves
  here too, same reasoning as before — one dataset list, so replication and
  quiesce scope cannot drift apart.
- `--commit-scope-check=<label>` is the file-format half alone: manifest

  No `zfs` command runs. This is `do_join_check`'s exact shape applied to the
  new command, and for the same reason: it is what makes the format half
  testable without root on any machine.
- `PEER_STATE_DIR`/`PEER_KEY_DIR` and their path helpers (`peer_manifest_path`,
  the new `peer_scope_path`) moved up next to `do_join_check`, and

- `PEER_JOIN_GRANTED_DATASETS` is now written to the manifest after a commit —
  not consumed yet, but slice 3's revoke-on-narrow needs exactly this list

**What did not change.** Root peers and push peers: unaffected, a scope file
has no bearing on either. The package format, `PEER_CONF_DATASETS`: still
present and still read (slice 5 makes it optional) — it is no longer what
anything grants from, only what the package itself asked for.

## Slice 3 (`b7e0478`): revoke-on-narrow, bounded by the manifest

**What changed.** `do_commit_scope` granted from a scope file but never took
anything back: narrowing the file by hand and re-running `--commit-scope`
left every previously-granted dataset delegated forever, silently. This
slice closes that.

- Before granting, `do_commit_scope_check`'s own `. "$mpath"` (already run at
  the top of `do_commit_scope`) has `PEER_JOIN_GRANTED_DATASETS` in scope if
  a prior commit happened — captured into `prior_datasets` before this run's
  write replaces it.
- After the grant loop, revoke candidates are computed as `prior − granted`
  (the current scope's set) — **never** derived from what `zfs allow` shows
  for the account now. That is the whole mechanism behind U3's "bounded by
  the manifest": a dataset is a candidate only if this relationship's own
  prior commit put it there. A foreign grant (another peer, an older
  deployment, a manual job) on a dataset this scope file never selected is
  never even inspected, let alone touched.
- Each candidate is checked for an in-flight transfer hold first
  (`commit_scope_dataset_held`, tag `zfssnapall_inflight` — the same one
  `lib-zfs-snap.sh`'s `hold_snapshot()` uses, duplicated as a literal since
  `deploy.sh` deliberately does not source that library). Held → left
  granted, warned by name, and re-recorded in the manifest so the **next**
  commit tries again instead of forgetting it was ever a candidate. Not held
  → `zfs unallow` with the exact same permission string the grant used (not
  a blanket per-account unallow, which could remove an unrelated permission
  on the same dataset) → revoked and dropped from the manifest.
- The quiesce whitelist (when `--allow-quiesce` is given) now installs from
  `still_granted` — the grant list *after* revoke, including anything held
  back — instead of the pre-revoke `granted`, so quiesce scope cannot drift
  from replication scope in either direction.

**What did not change.** `do_commit_scope_check`'s refusals (as=root,
role=push, missing/malformed manifest or scope file) — untouched, slice 3
only extends what happens once the check has already passed. A dataset that
was never in `PEER_JOIN_GRANTED_DATASETS` is not a new kind of case; it is
simply outside the diff, exactly like before this slice.

**Evidence — live, on metropolis pve2 (192.168.28.8), scratch datasets under
`hdd/backuptest`, throwaway `PEER_STATE_DIR=/tmp/scope3test` (never touched
`/etc/zfs-snapshot-all/peers`).** Chosen over a stub-based unit test for the
same reason slice 2's grant loop was: this is real `zfs allow`/`zfs
unallow`/`zfs holds` behavior, and a stubbed `zfs` would only prove fidelity
to my own stub, not the real primitive REV-20260802-028's own lesson (a
generated command that only proves itself against inspection, not the real
staging/commit path) is exactly what this project stopped trusting.

Manifest seeded with `PEER_JOIN_GRANTED_DATASETS="…/a …/b …/d"` (as if a
prior commit had granted all three); scope file narrowed to `…/a` only;
`…/foreign` pre-granted with no manifest entry anywhere (the foreign-grant
control); `…/b` given an in-flight hold before the run.

| dataset | before | scope now | hold | after `--commit-scope` |
|---|---|---|---|---|
| `…/a` | granted | included | no | granted (unchanged) |
| `…/b` | granted | excluded | **yes** | **still granted**, warned by name, kept in manifest |
| `…/d` | granted | excluded | no | **revoked**, dropped from manifest |
| `…/foreign` | granted (never in manifest) | n/a | n/a | **untouched** |

Manifest read back after the run: `PEER_JOIN_GRANTED_DATASETS="…/a …/b"` —
exactly `still_granted`, not the pre-revoke `granted`. Released the hold on
`…/b` and re-ran `--commit-scope` with no other change: `…/b` revoked
cleanly this time, manifest reduced to `"…/a"` alone — confirming a held-back
candidate is retried on the next commit rather than forgotten. `zfs allow`
on `…/foreign` never changed across either run. Cleaned up afterward:
scratch datasets destroyed, `--revoke-quiesce=zfsbackup` removed the
whitelist/sudoers rule this test created (birth-time confirmed they did not
exist before the test), `/tmp/scope3test` removed, `git status --porcelain`

**Remaining risk.** No stub-based regression test exists for this logic —
matches slice 2's own precedent for the grant loop, and for the same reason:

again without a live host handy, re-run the same scratch scenario before

## Slice 5 (`d839c91`): `--peer-datasets` optional via `PEER_CONF_MODE`

**What changed.** F1's core complaint — `--pair --role=pull` unconditionally
requires `--peer-datasets` (the SOURCE's own datasets) before it will even
contact the peer — now has an alternative. `--mode=backup|sync`, pull-role
only:

- carries `PEER_CONF_MODE` in the package instead of a dataset list;
  dataset selection is deferred to the peer's own `--draft-scope`/
  `--commit-scope` (slice 4), run there after `--join`;
- mutually exclusive with `--peer-datasets` — naming the source's datasets
  directly and deferring the decision to the source are alternative ways of
  reaching the same field, and combining them is refused rather than
  silently preferring one;
- `--mode=sync` also refuses `--target` (F3: sync reproduces source paths
  verbatim on the collector, so there is no separate target root to name);
  `--mode=backup` allows `--target` or leaves it absent — "inherits the
  server default target" (F1) is `zfs-backup.sh`'s own `DEFAULT_TARGET`
  (confirmed already present in that wrapper), resolved *before* it calls
  `deploy.sh --pair`, not something this layer invents.

**The actual trust boundary** is `validate_peer_conf` — a wsad crosses
hosts, so this is where a hostile or simply outdated package gets read.
`PEER_CONF_MODE` joins the allowed-key set; `PEER_CONF_TARGET`'s
requirement, previously unconditional, is now conditional on mode (absent
for sync, optional for backup, still required exactly as before for
everything else — push, or a legacy package with no mode at all); the old
"pull with no datasets" refusal now also accepts "pull with a recognized
mode instead". A package with neither datasets nor a recognized mode is
still refused, same as before this slice, just with the message extended to
name both possibilities.

**Backward compatibility, checked explicitly, not assumed:** a package with
no `PEER_CONF_MODE` key at all — the literal shape of every wsad this
project has ever produced before this commit — validates identically to
before: `parse_peer_conf` leaves the field unset, `mode=""`, every new rule
in `validate_peer_conf` falls through its `if [ -n "$mode" ]`/`if [ -z "$mode" ]`
guards to exactly the prior behavior. This is the acceptance criterion
"existing expert `deploy.sh --pair/--join --peer-datasets=...` remains
available and compatible", proven by a dedicated test case rather than
inferred from the diff.

**What did not change.** Push-role packages: unaffected, `--mode` refuses to
combine with `--role=push` at the CLI layer and `PEER_CONF_MODE` on a push
package is refused by `validate_peer_conf` too — a source in push role
already knows its own datasets, which is exactly the case F1 is not about.
`do_join`'s pull-role branch: still grants nothing (slice 2), now also
records `PEER_JOIN_MODE` in its own manifest for a later slice to read (the
collector wrapper, slice 6, needs to know whether it is generating a backup
or sync job).

**Remaining risk.** `--pair`'s own live network half (host-key pinning via
`ssh-keyscan`, account creation, key installation) is not exercised by any
suite in this project for ANY role or mode — a pre-existing gap this slice
does not close, since testing it would need a live two-host pairing, the
same category of manual obligation slice 2's grant loop and slice 3/4's

## Patches against `ENROLMENT-AGREED-2026-08-02.md`: T3, U2, T5

## Slice 6 (`9f08af6`): collector fetch/digest/generate

**The model this slice implements, for the record.** The reference scenario
at the top of `docs/discussions/ENROLMENT-AGREED-2026-08-02.md` — "I get a
ready default config for pve1 ... the config lands on pve1 and backup
starts" — is the actual specification here, agreed in more detail in that
discussion than the review's own acceptance criteria state. The result of
this slice is a READY, auto-installed default config, not draft/candidate
stanzas for manual review. That is not a new mechanism: `zfs-backup.sh`
already has exactly this shape for the dataset-list path — `activate-client`
dry-runs, shows a diff, asks once, and installs, using the existing
`PROFILE_GFS` default policy (one send cadence, one GFS ladder) in
`emit_client_sections`. Slice 6 only changes where the DATASET LIST that
feeds that existing machinery comes from; it does not touch how the config
gets generated, previewed, or installed. Noting this explicitly because the
older `do_draft_config` convention (still live, on the dataset-list path's
`--pair --draft-config`) produces commented candidates for hand assembly,
and a reviewer without the discussion's detail could reasonably expect this
slice to follow that older shape instead.

**`resolve_mode_datasets()`**, wired into `load_client_and_connection` (the
setup every command — `seed`, `final-catchup`, `verify-endpoint`,
`activate-client`, `migrate-profile`, `test` — already calls first): a no-op
for a legacy `--peer-datasets` client (`PEER_SAVED_DATASETS` already
non-empty). For a mode-based client (`PEER_SAVED_MODE` set, dataset
selection deferred to the peer at pairing time — slice 5), it:

1. fetches the peer's scope file and its T3 hash sidecar over the same
   pinned-key ssh channel `check_inherited_grants` already uses;
2. refuses if either fetch fails, naming which of `--draft-scope`/
   `--commit-scope` has not run yet on the peer;
3. refuses if the fetched file's sha256 does not match the sidecar (T3) —
   a source-side edit made since the last `--commit-scope` that nobody
   re-ran, same contract slice 4/5's patch established, now consumed;
4. reads the file with `lib-scope.sh`'s own `scope_read` (a real source
   edge — `zfs-backup.sh` now sources `lib-scope.sh` directly, not a
   duplicate);
5. walks each `SCOPE_ROOTS` entry via a remote `zfs list -H -o name -r`,
   filtering every name through `scope_includes` (T1: `zfs list` is not
   gated by `zfs allow`, so this succeeds whether or not `--commit-scope`
   has granted yet — order between them does not matter to this fetch);
6. populates `PEER_SAVED_DATASETS` in memory, in exactly the space-separated
   form every existing consumer already expects.

No caller changed. That is the point of the seam: `seed`, `activate-client`,
`emit_client_sections`, `migrate-profile` read `PEER_SAVED_DATASETS` the
same way regardless of which path filled it in.

**`add-client --mode=backup|sync`** is the CLI entry to the above: an
alternative to `--datasets`, passed through to `deploy.sh --pair` as
`--mode=` instead of `--peer-datasets=`. Same mutual-exclusion and
`sync`-refuses-`--target` rules slice 5 already enforces at the `deploy.sh`
layer, checked again here so the refusal happens before any network call,
not after.

**`cmd_seed`** no longer runs its unconditional `deploy.sh --pair
--draft-config` refresh for a mode-based client — that call is
dataset-list-specific (it lists every unfiltered candidate on the peer when
`PEER_SAVED_DATASETS` is empty, which is always true for a mode-based
client, and would write a misleading suggested-config artifact).
`resolve_mode_datasets`, called moments later by `load_client_and_connection`
in the same `seed` run, is this client's actual connectivity-and-readiness
check: it is the same ssh link, and it fails loudly and specifically
(missing scope file, missing hash, hash mismatch) exactly where the old
call would have failed generically ("could not reach $PEER_HOST").

**U11 — per-section config ownership.** `emit_client_sections` writes
`# managed-by: zfs-backup.sh client=<name>` as the first content line of
every `[dataset:]`/`[prune:]` section it generates. `remove_managed_sections`
(used by re-activation, `migrate-profile`, and `remove-client`) now accepts
a header match as its own prior output only when EITHER that marker is
present and names the same client, OR the path was already recorded in the
caller's own `MANAGED_DATASETS`/`MANAGED_PRUNE_SCOPE` (sourced from the
client's own conf before this runs, in every caller). The second test is
what keeps every client activated before this slice working unchanged on
its very next rewrite: their sections predate the marker, this call adds it
going forward, and nothing has to be migrated by hand. A header match with
neither the marker nor a prior record — a path this client has never
managed before, occupied by something that looks hand-written — is refused
outright, naming the file and the path, rather than silently deleted. A
marker naming a DIFFERENT client is treated the same as no marker: refused,
not trusted, even though path-uniqueness (each client's paths are

## Slice 7: endpoint model (F4) — two targeted corrections, not a rewrite

**Finding.** F4 says fixed `lan`/`vpn` slots must not force a `set-endpoint`
call merely because the collector moved: a routed site-to-site VPN that
preserves the peer's original `host:port` is a route change, not an
application-endpoint change, and `set-endpoint` should be needed only when
the address SSH actually uses is different (owner decisions 13–14).

**What the review asked for now** (F4, "Required response now"): "Compare
these requirements to the exact current state machine and propose the
smallest correction. State whether the fixed `lan`/`vpn` slots should remain
internal compatibility fields, be generalized, or be removed from the new UX
while retaining backend commands."

**Finding on inspection: the state machine built under REV-20260730-004/005
and REV-20260731-007/008 already satisfies decisions 13–14 structurally.**
`cmd_set_endpoint` requires an explicit `--lan=`/`--vpn=` argument — nothing
mutates the client record on its own, ever. So the routed-VPN case (host:port
unchanged) already needs zero `set-endpoint` calls, by construction: an
operator relocating the collector and finding the peer still reachable at the
address on record simply runs `verify-endpoint` again against
`ACTIVE_ENDPOINT` as it already stands. `set-endpoint` exists to RECORD a
changed address, not to declare a relocation occurred. Identity survives a
real endpoint switch already, too — `CLIENT_NAME` (not the address-derived
`label`) drives the `HostKeyAlias`, and `label`/target/pairing key are set
once at `seed` and never revisited by `set-endpoint` (file header, REV-
20260730-004 F1). Given that, removing or renaming the `lan`/`vpn` slots
would be pure churn: they already work as "two addresses this client may be
reached at, at most one active", which is what a seed-then-relocate flow
actually needs — not a signal that a mutation is mandatory.

**So the smallest correction is not a state-machine change.** It is closing
the two places where the CODE did not yet match that already-correct model:

1. **`cmd_verify_endpoint` discarded `snapget.sh`'s stderr** (`2>/dev/null`)
   on every dry-run call. That is exactly where F4's "source-IP restrictions
   ... detected or clearly reported" would have to surface — `snapget.sh`
   already distinguishes a connection-level failure from a data problem
   (`lib-zfs-snap.sh`'s `log 0 "... CONNECTION-level failure (authentication,
   host key, network or DNS) ..."` for ssh exit 255, see `snapget.sh:511-512`)
   but the wrapper threw that diagnostic away and printed only
   `FAILED (rc=$rc): $ds`. A firewall/`AllowUsers`/fail2ban restriction after
   a collector relocation would have read as an opaque number, not a
   reported cause. Fixed: stderr now goes to a per-call temp file, printed
   (each line, via `warn`) whenever that dataset's check fails, then removed;
   stdout parsing for the `PLAN=` verdict is unchanged (still never mixed
   with stderr — REV-20260730-005 F2's fix for the old text-heuristic bug
   stays intact).

2. **The post-`seed` hint presented `set-endpoint` as a mandatory step**:
   "Next: relocate if needed, then set-endpoint/verify-endpoint, then
   activate-client" read as a fixed sequence, which is F4's own named failure
   mode — "makes an administrator invent or repeat an address that did not
   change". Reworded to state the actual condition: run `final-catchup`
   before disconnecting, then `set-endpoint` ONLY if SSH now reaches the peer
   at a different host or port, otherwise skip straight to `verify-endpoint`.

**F4 acceptance criteria, checked against the tree as it now stands:**

| Criterion | Status |
|---|---|
| Routed VPN, unchanged `host:port`, needs no `set-endpoint` | already true (no code mutates the record except an explicit `--lan=`/`--vpn=`) |
| Current endpoint always reverified after relocation, including pinned key + `PLAN=INCREMENTAL` per dataset | already true — `verify-endpoint` is exactly this check, fail-closed (REV-20260730-005 F2) |
| Changed endpoint preserves relationship identity, key, target, bookmarks, job state | already true — `CLIENT_NAME`-keyed alias, `label`/target/pairing key untouched by `set-endpoint` (REV-20260730-004 F1) |
| Replacement endpoint requested only when needed, verified fail-closed | already true — `set-endpoint` is always operator-initiated; `verify-endpoint` gates `activate-client` |
| Source-IP restrictions detected/clearly reported | **fixed this slice** — stderr no longer discarded in `verify-endpoint` |

| User-facing messages name the collector, not the source, as the machine being moved | **deliberately deferred to slice 10** ("message/role corrections") — a real, separate defect (confirmed in §6 above: `final-catchup`'s prose says "the source may now be disconnected and moved", presuming the peer always moves), kept out of this slice so each is independently reviewable |

**Evidence.** `test/zfsbackup/run.sh` **232/232** (+2). New: a source-grep

## Slice 8: sync contracts (F3, U7, U8) — snapget.sh safety + wrapper mapping

**Two independent halves, per the slice table: `snapget.sh` (safety, applies
to every caller including today's backup-mode production traffic) and the
wrapper (path mapping, sync-mode only).**

### snapget.sh: `-F` stops being the unconditional default

**Finding (F3 "Remaining risk", confirmed live 2026-08-02 on the 192.168.11.x
cluster, see U7 in `ENROLMENT-AGREED-2026-08-02.md`).** `process_dataset`
built `recv_flags="-F -s"` unconditionally, for every receive, regardless of
whether this run created the target or found it already there. Harmless for
backup mode's own namespaced target (nothing else ever writes into a path
this pull created), unsafe for anything else landing at a pre-existing path
-- sync mode addresses the source's own path directly, so "already there"
can mean an independently live dataset. The worked example: `vsql2` (VM 100)
runs on `pve1`, `pve0` holds a `pvesr` replica of the same dataset;
`snapget.sh -r pve0:rpool/data/vm-100-disk-0` (sync, no second argument)
targets the **live guest disk**, a common base exists, and `-F` would have
rolled the database back to the replica's snapshot and destroyed the
newer one. Today only ZFS's own "dataset is busy" on an open zvol prevents
this -- not a safety property; it disappears the moment the guest is
stopped, the target is a container subvol instead of a zvol, or the guest
runs on another cluster node.

**Implemented, `process_dataset` (`snapget.sh`):** a new `recv_force_flag`
replaces the literal `-F`, computed right before the send/recv command is
built, skipped entirely when `FORCE_FULL_SEND` is already 1 (`-f`, an
explicit human decision that already destroyed and recreated the target
above -- `-F` on a freshly emptied dataset is a no-op). Otherwise, per the
agreed preflight table (U7):

| Condition | `recv_force_flag` |
|---|---|
| target does not exist | `""` (nothing to roll back) |
| target exists, live guest disk (`guest_disk_is_live`, see below) | **refuse**, unconditionally |
| target exists, no common snapshot by GUID (and no rescuing bookmark) | **refuse** -- "a full resend needs `-f`, a human decision" |
| target exists, common snapshot found, `written@<common> != 0` or unreadable | **refuse**, names the amount (or says it could not be measured) |
| target exists, common snapshot found, `written@<common> = 0` | `""` -- nothing to roll back, incremental proceeds without `-F` |

Dropping `-F` rather than merely warning is deliberate: once it is gone, a
genuinely diverged **child** dataset under a `-R` recursive stream still
gets ZFS's own native refusal (`-F` is what silently forces past that), so
correctness does not depend on this gate measuring `written@` on every
child individually -- only the top-level target is checked explicitly, for
a clear, early, human-readable refusal instead of a raw `zfs recv` failure
mid-transfer.

**New `guest_disk_is_live()` (`snapget.sh`, next to `process_dataset`).**
Reuses `quiesce_guest_id`/`quiesce_guest_status` (`lib-zfs-snap.sh`)
unchanged -- same dataset-naming convention (`vm-*-disk-*`/
`subvol-*-disk-*`), same local-node-only reach a replica's guest already
gets (`kind=absent` when the guest's config lives on another cluster node,
identical to what the quiesce path already does). Checked **before** the
`written@` test and treated as an unconditional override: a written@=0 read
taken a moment earlier proves nothing about the instant `zfs recv -F`
actually runs against a dataset a running guest keeps writing to.
Deliberately fail-closed: if guest status cannot be determined (no root, no
quiesce-helper access -- `QUIESCE_VIA` never initialised because this run
did not request `-q`) the dataset is treated as unsafe, not as stopped.

### `deploy.sh --mode=sync` peer, same PVE cluster: refused at enrolment (U8)

**Finding.** Migrating the live guest to the OTHER node in the same cluster
silently flips which side sync's destination collides with, without
touching this tool's own configuration at all -- and after the move, sync
and `pvesr` become two independent replicators racing for the same
destination.

**Implemented, `cmd_add_client` (`zfs-backup.sh`), `--mode=sync` only.**
Cluster membership is cheap and already answered by the cluster itself:
node ownership is visible under `/etc/pve/nodes/<name>` (shared cluster
filesystem, world-searchable). Refused **at enrolment**, before `deploy.sh
--pair` is ever called -- matching U8's "odrzucony na wejściu, nie przy
odbiorze". `PVE_NODES_DIR` (default `/etc/pve/nodes`) is a plain overridable
global, the same pattern `lib-zfs-snap.sh`'s `QUIESCE_PVE_DIR` already
established, specifically so this is testable against a fake cluster tree
rather than only against a real one.

**Acknowledged limitation, stated rather than hidden:** the check matches
`--lan=`'s hostname (or, for a bare IPv4, a `getent hosts` reverse lookup)
against `/etc/pve/nodes/`, which is this fleet's own hostname == PVE-node-
name convention (see infra memory), not a universal identity check. A peer
reachable only by an IP whose PVE node name differs from the address given
would not be caught by this specific gate -- but it is not the only guard
against the underlying scenario: `guest_disk_is_live` in `snapget.sh` (above)
catches a live guest's disk directly, per dataset, on every single run,

### Wrapper: F3's required backup/sync mapping

**Finding.** Every `localpath`/local-base computation in `zfs-backup.sh`
(`seed`, `final-catchup`, `verify-endpoint`, `activate-client`, `test`,
`emit_client_sections`) hardcoded the backup mapping

this; `--mode=sync` selected datasets correctly but generated jobs that
targeted the wrong local path.

**Implemented.** Two helpers, `snapget_local_base`/`client_local_path`
(`zfs-backup.sh`), are now the ONE place this branches on

convention for an omitted `LOCAL_BASE` -- "sync: identical local name", not
a new mechanism), `$PEER_SAVED_TARGET/$LOAD_LABEL` for backup, unchanged.
Every call site above now goes through them instead of composing the path
itself. `gen-cron.sh`'s own `emit_send` (pull branch) already handles a bare

had to stop overriding that with a namespaced header for sync.

**`emit_client_sections` (`zfs-backup.sh`), GFS ladder.** Backup mode's

prune-scope race this project already fixed once for `delsnaps.sh`.
`MANAGED_PRUNE_SCOPE` becomes a space-separated list for sync (one entry per
dataset) instead of backup's single shared value; `is_previously_managed`

reads `MANAGED_DATASETS`, so the single-entry backup case keeps working
unchanged.

## U9 implemented: one current endpoint + known candidates

Done immediately after being flagged (owner: "Napraw U9 teraz, nie czekaj na
plasterek 9/10"), rather than folded into a later slice.

**Model.** `ACTIVE_ENDPOINT` generalizes from a named slot ("lan"/"vpn") to
the literal `"host:port"` itself. A hostname can never contain `:`
(`endpoint_host_valid`'s charset forbids it), so "contains a colon" is an
unambiguous, version-free discriminator between the new shape and a
pre-U9 record — `active_endpoint_host_port()` resolves either without a
separate schema-version field. `ENDPOINT_LAN_*`/`ENDPOINT_VPN_*` and an
`ACTIVE_ENDPOINT` of literally `"lan"`/`"vpn"` are kept exactly as U9
specified: read-only compatibility for records that predate this, never
written again. `ENDPOINT_KNOWN` is new — a space-separated list of other
addresses that have worked for this client before.

**`set-endpoint NAME --host=HOST[:PORT]`** replaces `--lan=`/`--vpn=`, a real
breaking CLI change (no fleet client currently uses a non-default endpoint,
so the blast radius is zero today). Giving the address already on record is
now a **no-op** — no gate, no write — which is what makes "a routed VPN needs
no set-endpoint call" true by construction rather than by an operator simply
choosing not to call it. Every actual change goes through the same
freshness/identity gate uniformly; the old asymmetry ("correcting the
inactive slot is not gated", tested as `c5`/`f7` pre-U9) no longer exists
because there is no inactive slot left to correct — replaced by two U9-native
behaviors: the address just left is recorded into `ENDPOINT_KNOWN`, and a
legacy record's dormant second slot (whichever of LAN/VPN was not active) is
folded into `ENDPOINT_KNOWN` on its first switch, so migrating loses nothing.

**`verify-endpoint`** now tries the current endpoint, and on failure walks
`ENDPOINT_KNOWN` in order, trying each — an address that already worked once
is a much better second guess than immediately asking the operator to type
one in, which is the entire reason U9 asks for a candidate list at all. A
candidate extracted the per-dataset probe into `probe_snapget_endpoint()`,
reusable per-candidate (each may need its own port, hence its own
`ensure_alias_known_hosts` call — `LOAD_ALIAS`/`LOAD_KEYFILE` stay fixed,
since identity is the relationship's pinned host key, not the address).
Whichever candidate answers clean is **promoted** to `ACTIVE_ENDPOINT`; the
one that stopped answering becomes a known candidate in turn. Only when
NONE answer does it refuse, naming every address tried and pointing at
`set-endpoint --host=NEW`.

**Gate simplification, as a side effect.** `FINAL_CATCHUP_ENDPOINT` is now
always the literal `"$LOAD_HOST:$LOAD_PORT"` (never `$ACTIVE_ENDPOINT`
directly), so `set-endpoint`'s freshness gate compares it to the address
being left by simple string equality — the old three-way name+host+port
cross-check existed only because a SLOT NAME alone was ambiguous (it could
point at a different address than when the catch-up ran); a literal address
carries its own identity, so the extra check was pure overhead once the slot
indirection was gone.

**Role-naming (U9's other confirmed finding).** `final-catchup`'s messages
and the post-`seed` hint now say "this collector may now be relocated" /
"if this collector relocates", not "the source" — U9 confirmed in code that
this project's actual scenario is the collector being physically moved, not
the source.

**One-time migration costs, named rather than hidden:** a legacy client's
most recent PRE-upgrade catch-up (recorded as `"lan"`/`"vpn"` under the old
code) will not match the new literal-address comparison on its first
`set-endpoint` call after this lands — it reads as "no catch-up recorded",
fail-closed, asking for a fresh one rather than trusting a record in a
format the new gate cannot parse. Cheap (`final-catchup` is idempotent) and
safer than the alternative (trusting an old record blindly).

**Evidence.** `test/zfsbackup/run.sh` **244/244** (+6 net over slice 8's
238, after rewriting the pre-U9 gate/freshness fixtures rather than just
adding cases on top — the old `--lan=`/`--vpn=` fixtures do not compile
against the new CLI at all). New: `active_endpoint_host_port`/
`endpoint_display` for both record shapes, `set-endpoint`'s no-op path,
`ENDPOINT_KNOWN` population on a real switch, the legacy-dormant-slot fold-in,
`verify-endpoint`'s fallback-and-promote path and its names-everything-tried
refusal (both via a `SNAPGET` stub that branches on which candidate host it
was called against, no `ssh` involved). Rewritten: the whole final-catchup
gate section (`c1`-`c7`, `f1`-`f6`) onto `--host=` and literal-address
fixtures — same safety properties, `--lan=`/`--vpn=`-specific asymmetry
tests dropped because the asymmetry they tested no longer exists. Existing
section 38b (verify-endpoint stderr surfacing, built against a legacy-shape
fixture) needed no changes at all — confirms the compatibility shim actually
works, not just compiles. `./test/impact.sh`: clean, same standing
obligations as slice 8 (`zfsbackup-live-pair`, `project-status`).

**Not tested here, and why:** the real end-to-end promotion (current
endpoint genuinely unreachable over a real network, a real known candidate
genuinely answering) needs two real hosts and a real relocation — folded
into the same standing "Live-test the full enrolment cycle end to end"
obligation, not a new gap.

## Slice 9: remote `--join` + scope editor over `ssh -t` (U10)

Both pieces, under one opt-in flag (`--join-remotely`, the working name
`ENROLMENT-AGREED-2026-08-02.md` itself proposed and never replaced).
**Off by default** — every existing `add-client`/`--pair` call keeps
today's behaviour (print the wsad, print the exact commands to run by
hand) with zero code-path change unless the flag is given.

### Design, held to U10's three conditions exactly

1. **Finalize stays local, always.** Nothing this slice adds ever runs
   `--commit-scope` (the grant) over ssh, automated or otherwise — not
   inside the flag's own logic, not as a "convenience" follow-on to the
   editor session. `do_pair`'s remote block ends at opening the editor;
   the human who is now sitting in that `ssh -t` session runs
   `--commit-scope` themselves, on the peer, seeing its own diff/plan
   output first (U2, already built).
2. **Rides the pin already established.** `do_pair` already runs
   `ssh-keyscan` and pins the result to `/root/.ssh/known_hosts` moments
   before this block would run — the `scp`/`ssh`/`ssh -t` calls all pass
   `-o UserKnownHostsFile=/root/.ssh/known_hosts -o
   StrictHostKeyChecking=yes` against exactly that file. No `accept-new`,
   no separate trust decision, no new pin.
3. **The peer's manifest records the remote origin.** A new, optional wsad
   field, `PEER_CONF_REMOTE_JOIN=yes` (fixed literal, allow-listed like
   every other peer.conf key — absent means "no", same as a package that
   predates this slice). `do_join`, on the PEER, when it sees this field,
   writes `PEER_JOIN_REMOTE`/`PEER_JOIN_REMOTE_FROM`/`PEER_JOIN_REMOTE_AT`/
   `PEER_JOIN_REMOTE_SESSION` into its own manifest — the session is
   captured locally, on the peer, at the moment `--join` actually runs
   (`${SUDO_USER:-$(whoami)}@$(hostname -s)`), which is more trustworthy
   than a claim the collector could make about itself in the package.

### Mechanics

`do_pair`, right after writing the wsad (unchanged) and pinning the host
key (unchanged), if `--join-remotely` was given:

1. `scp` the wsad to `root@$PEER_HOST:/root/` over the pin.
2. `ssh ... "cd /root && ./deploy.sh --join=/root/<wsad>"` — remote
   `--join`. Safe to automate specifically because U2 already made
   `--join` grant nothing (creates the account, installs the key, ends at
   zero ZFS permissions) — the protected act (the grant) stays local
   regardless of where `--join` itself ran, exactly the reasoning
   `ENROLMENT-AGREED-2026-08-02.md` used to reverse the implementer's own
   first (pre-U2) instinct against this.
3. If `$PEER_MODE` is set (a scope-based pairing — the only case with a
   scope file to edit at all), `ssh -t ... "./deploy.sh
   --draft-scope=$my_label 2>/dev/null; \${VISUAL:-\${EDITOR:-vi}}
   <scope-path>"` — drafts the file if it does not exist yet (silently
   no-ops if it does, same as `--draft-scope`'s own existing "already
   exists" refusal, discarded here rather than surfaced, matching
   `crontab -e`'s own first-time-vs-repeat UX), then opens it in the
   peer's own `$VISUAL`/`$EDITOR`/`vi`, running ON the peer, in the
   operator's own `ssh -t` terminal.

Any failure in step 1 or 2 **warns and falls through** to the exact same
manual instructions `do_pair` has always printed — U10's "manual transfer
remains as the emergency path" means a failed automation attempt must not
strand the operator with nothing. A failure in step 3 (the editor session)
warns and names the scope file's path so the operator can still reach it
by hand; it does not undo the already-succeeded remote `--join`.

`zfs-backup.sh`'s `add-client --join-remotely` is pure pass-through — the
new flag is parsed, forwarded into `deploy.sh --pair`'s own argument list,
nothing else. This file does not reimplement any of the scp/ssh/`ssh -t`
orchestration, consistent with its own charter (it orchestrates `deploy.sh`
as a subprocess, it does not extend into implementing what `deploy.sh`
itself does). The post-`add-client` hint is conditional now: when the flag
was given, it points at `deploy.sh`'s own just-printed output (which
already says whether the remote attempt succeeded or fell back) instead of
repeating the now-possibly-stale manual instructions unconditionally.

## Slice 10: message/role corrections

### Finding

The U9 correction (see above) fixed the half of the role-naming defect
that F4/U9 named explicitly: `cmd_seed`'s and `cmd_final_catchup`'s
messages now say "this collector relocates" / "this collector may now be
relocated" for the machine actually being moved, never "the source".

Re-reading those same two messages end to end for slice 10 found the other
half was still there, one sentence later: both messages, right after
correctly naming the collector as the one moving, used "the source" for
the *other* party — the peer SSH connects to — e.g. "if this collector
relocates ... If SSH now reaches **the source** at a DIFFERENT host or
port afterward". A third message (`cmd_verify_endpoint`'s "none of the
known endpoints answered" failure) had the same word for the same party,
standalone.

This is the identical defect in a subtler shape, not a new one: a reader
who just parsed "the collector relocates" has no textual signal that "the
source" two clauses later means the far end, not the same machine renamed
back. It also contradicts the vocabulary used everywhere else in this
file — every other user-facing message names the enrolled remote machine
"the peer" (`$PEER_HOST`, "the peer's committed scope file", "no pinned
host key found for '$PEER_HOST'", etc.); "the source" appears nowhere else
in the file for this role. `grep -n source zfs-backup.sh` confirms every
remaining non-role use of the word is unrelated: `source "$LIBCRON"` (shell
builtin), the crontab `# Source:` field (a config provenance marker, wholly
different meaning), and ZFS send/receive terminology ("source dataset",
"source path").

### Implementation

Three messages corrected, `zfs-backup.sh`:

- `cmd_seed`'s post-seed hint: "If SSH now reaches the source at a
  DIFFERENT host or port" → "...the peer...".
- `cmd_final_catchup`'s completion message: "If the source is still
  reachable at the SAME host:port" → "...the peer...".
- `cmd_verify_endpoint`'s failure message: "If the source has a genuinely
  new address" → "...the peer...".

No behaviour changes — string literals only. The explanatory comments
directly above the first message were extended (not rewritten) to record
why "the peer" and not "the source" for this word specifically, since a
future edit could otherwise reintroduce the exact same subtler mistake
right next to the fix for the first one.
