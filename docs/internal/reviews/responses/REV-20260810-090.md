# Response to REV-20260810-090

## F2 — IMPLEMENTED

Both findings are accepted without dispute, and both are fixed by the same

### Analysis

The review is right, and the reason it is right is worth stating plainly: my
REV-089 evidence proved the property at the wrong boundary. Section 49 drove
`emit_client_sections()` directly and kept the profile directory present and
valid throughout. That can only ever prove "changed profile content is not
copied into preserved sections". It cannot prove "reactivation does not depend
on the profile", because nothing in it ever removed the profile. The residual
dependency sat in the caller I did not cross.

Two distinct holes, both in `ensure_cron_config()`:

- **F1, availability.** `load_active_profile` ran unconditionally after the
  pre-GFS check. It calls `profile_validate_dir` and dies on a missing or
  invalid profile. So a relationship created from profile `P` became
  un-reactivatable the moment `P` was renamed, removed, or edited into something
  that no longer validates — none of which should matter to already-installed
  policy. That is still persistent profile authority, as the review says, just
  expressed as an availability dependency instead of a content comparison.
- **F2, additive mutation.** The template loop appends any
  `PROFILE_TEMPLATE_NAMES` entry the config does not carry, and
  `check_new_template_collision` never governed that. REV-088 narrowed only what
  happens when a name is PRESENT; it left untouched what happens when a name is
  ABSENT. So an operator who deliberately deleted a generated template they no
  longer needed would have it silently restored by the next endpoint refresh.

#### Why the fix is a lazy dependency, not a removed one

The review's own boundary is the design: *"If the implementation needs profile
material only when a newly-added dataset or missing managed section must be
generated, gate that dependency at that exact additive boundary."*

So the profile is not removed from the reactivation path — it is made
conditional on there being something to generate. Concretely, `ensure_cron_config()`
takes a third parameter `needs_profile` (default **1**, so a caller that has not
thought about it keeps the old, safe behaviour), and both `load_active_profile`
and the entire template-append loop move inside it. `emit_client_sections()`
likewise loads the profile only once its plan says a section must be written.

`setup-server` and `migrate-profile` are unchanged and keep the default 1: both
genuinely create policy.

#### The circularity, and how it is broken

"Does this run need the profile" cannot be answered by code that has already
loaded the profile. The answer therefore had to be computed from the installed
config and the client record alone, before `ensure_cron_config` runs.

Two extractions make that possible:

- `detect_profile_gfs()` — the pre-GFS detection was already a `grep`/`sed` over
  the **installed file**, never over a profile, despite living inside
  `ensure_cron_config` and being named after one. Lifting it out unchanged makes
  that fact usable earlier.
- `client_section_plan()` — the preserve/regenerate split REV-089 introduced,
  lifted out of `emit_client_sections()` into one function that also reports
  `PLAN_NEEDS_PROFILE`. It reads ownership markers, the peer's dataset list and
  `PROFILE_GFS`; it consults no profile.

`cmd_activate_client()` now calls both, then passes the answer down:

```bash
detect_profile_gfs "$workfile"
client_section_plan "$workfile" "$name" "$is_new_relationship"
ensure_cron_config "$workfile" "$is_new_relationship" "$PLAN_NEEDS_PROFILE"
```

**One implementation, deliberately.** `emit_client_sections()` now consumes the
same `client_section_plan()` rather than recomputing the split with a second
copy of the rule. Two copies of a preserve/regenerate decision drifting apart is
a failure mode this project has already paid for; the plan exists once.

`PLAN_NEEDS_PROFILE` is 1 when any `[dataset:]` section must be generated, or
when the `[prune:]` shape must be. That covers exactly the cases the review
names: first activation, a dataset newly in scope, and a managed section that is
missing or not owned.

#### What is deliberately NOT changed

- The candidate config is still validated by real `gen-cron.sh` before install —
  untouched, and it is what catches a genuinely broken installed CONFIG
  regardless of how it got that way.
- Ownership-marker checks, fail-closed refusal of foreign sections, and the
  pre-GFS refusal are unchanged.
- No profile versioning, no merge framework, no provenance record.
- Dataset-set reconciliation / source removal remains deferred, per the scope
  note carried over from REV-089.

Two notes on how the evidence was made discriminating:

- **The unused template had to be genuinely unused.** The shipped profile's five
  templates are all referenced by the generated sections, so removing one and
  proving it is not re-added would have been indistinguishable from `gen-cron.sh`
  rejecting a dangling `use_template`. Section 50 therefore adds an
  `extra_unused` template to the fixture profile that nothing references, and
  `90 F2 precondition` proves it really was installed before the removal — an
  assertion whose only job is to stop the main one from passing vacuously.
- **The working copy is observed, not inferred.** `cmd_activate_client()` removes
  its working copy on any failure and swaps it away on success, so the dry-run
  `$SNAPGET` stub copies it out at the one moment it is guaranteed to exist —
  the same substitution pattern sections 38/39 already use to observe an interior
  step. Without it these assertions would have been reduced to grepping log text.

### Remaining risk

- **The protocol blocker is cleared.** The reviewer repaired REV-088's headers
  and regenerated routing mid-implementation, so `./test/impact.sh --verify` now
  passes every gate including the ledger one, and this work was rebased onto
  that state rather than merged over it.
- **`zfsbackup-live-pair` not run.** The change alters no crontab install path,
  no transfer, no grants, no UID, no host state — only which inputs a
  deterministic CONFIG composition reads. Per the review's own boundary no live
  campaign is required. Left `IMPLEMENTED`, not `CLOSED`.
- **Honest limit of the F1 fix.** A reactivation that must generate a section
  still requires the profile, by design and per the review's instruction. So a
  host whose profile is gone can still fail — but now only when a genuinely new
  dataset appears, and it fails at that additive boundary with the profile's own
  error rather than during pure endpoint maintenance. `90 a first activation
  with no profile still fails loudly at the additive boundary` pins that this
  failure did not get quietly swallowed by the fix.
