# Response to REV-20260812-113

## F1 — IMPLEMENTED — measured first; the hypothesis does not hold, the selector is now explicit anyway

The finding is a fair challenge and it was the right thing to ask: a stub that
answers any listing shape proves the parser, not the selector. I measured before
touching anything, and the measurement disproved both your hypothesis and my own.

### Live evidence — pve1, `zfs-2.1.9-pve1`, disposable datasets, 2026-08-12 19:38

**Positive control** — the exact command the planner ran, no depth selector:

```
# zfs create -p hdd/backuptest/p7sel
# zfs snapshot hdd/backuptest/p7sel@automated_hourly_2026-08-12_19-40-00
# zfs list -H -p -t snapshot -o name,creation -s creation hdd/backuptest/p7sel
rc=0  output=[hdd/backuptest/p7sel@automated_hourly_2026-08-12_19-40-00	1786556292]
```

The snapshot is returned. The planner was **not** reporting `BRAK` on a healthy
backup on this platform.

Same dataset with `-d 1` and with `-r`, for comparison — byte-identical output,
rc=0 in both cases.

**Negative control** — a dataset with no snapshots:

```
# zfs create -p hdd/backuptest/p7empty
# zfs list -H -p -t snapshot -o name,creation -s creation -d 1 hdd/backuptest/p7empty
rc=0  output=[]
```

Empty, rc=0 — so the selector does distinguish present from absent recovery
points, and the planner's `BRAK` branch is reached for the right reason.

**A control you did not ask for, and my own hypothesis** — I suspected the
opposite defect: that without a depth bound the command would sweep a child
dataset's snapshots into the parent's plan, which would misattribute recovery
points during a recovery. Tested:

```
# zfs create -p hdd/backuptest/p7par/child
# zfs snapshot hdd/backuptest/p7par@parent-snap
# zfs snapshot hdd/backuptest/p7par/child@CHILD-snap
# zfs list -H -p -t snapshot -o name,creation -s creation hdd/backuptest/p7par
    hdd/backuptest/p7par@parent-snap	1786556328
# zfs list -H -p -t snapshot -o name,creation -s creation -d 1 hdd/backuptest/p7par
    hdd/backuptest/p7par@parent-snap	1786556328
```

The child's snapshot does **not** appear. My hypothesis was wrong too.

**One more environment property, since the finding is about environment
dependence:** the pool carries `listsnapshots=off`, and `-t snapshot` listed
regardless — so the historic pool-property gate on snapshot visibility does not
reach this call path.

All four datasets destroyed afterwards; `hdd/backuptest` is empty again.

### What changed, and why anything changed at all

No defect existed, so nothing had to change. The selector is now explicit anyway:

```sh
zfs list -H -p -t snapshot -o name,creation -s creation -d 1 "${copy[$i]}"
```

The reasoning is not "the test failed" — it is that I can measure exactly one ZFS
version, the finding is about depending on a default at the planner's single most
important lookup, and naming the depth costs nothing while removing the dependence
permanently. Re-measuring this after every OpenZFS upgrade is a worse plan than
writing down what we mean.

Per your point 4, only the selector changed. The implementation was not broadened.

### The stub is no longer permissive

`test/restore`'s `zfs` stub now **requires** `-d 1` on any `-t snapshot` listing
and fails the call otherwise. Its permissiveness is precisely what let an unproven
selector reach a live host, so the fixture now pins the option shape: remove the
flag from the planner and every snapshot assertion goes red instead of passing
quietly. That is the durable half of this finding — the live evidence above is a
fact about today, the stub requirement is what keeps it true.
