## F1 — IMPLEMENTED

### Analysis

Confirmed as stated. The group TERM reached the engine, the engine died before
`progress_done`, and the watcher's record kept `"state":"running"`. It was measured before
the fix (below).

### Implemented change

- `lib-zfs-snap.sh`: `progress_interrupt_own [watcher pid]`. It stops the active watcher
  first; otherwise the watcher rewrites `running` 2 s later. It then marks only records that
  are `running` and carry `"pid":<this engine's $$>`. The watcher writes `$$` of the engine
  shell, because `$$` does not change in a subshell. Another run's record and a finished
  record are not touched.
- `snapsend.sh`, `snapget.sh`: `trap 'progress_interrupt_own "${_pg_pid:-}"; exit 143' TERM
  INT HUP`, the same block in both engines. The exit still runs the EXIT trap (thaw, ssh
  close).
- `tui/zfs-tui.py`: F4 reads `interrupted` and `dead` as PRZERWANY.
- ENGINE-FREEZE entry and refreeze.

## F3 (found during F2) — IMPLEMENTED

### Analysis

The lineage check in `attach` (2026-08-30) compared snapshot NAMES on the medium with the
source's snapshots only. After retention pruned the shared snapshot, the source bookmark
still carries its GUID, and the engine sends the increment from it. The gate refused the
medium as a different lineage. With the gate bypassed (hand import), the engine made the
increment on origin/main. This is a pre-existing defect, not one of the batch's changes.
It is the path that `mediagate-live` exists to prove.

### Implemented change

`zfs-media-gate.sh`: when no name is shared, a target snapshot whose GUID equals a source
bookmark's GUID counts as the shared lineage.

### Evidence

  (bookmark of another guid → still rc 2). N1/N1b/N2 are unchanged. Suite mediagate on pve9
  at d27a1855: 214/0 (211 before, plus 3 new checks). twins 94/0.
