## F1 — a disjoint target block would be overwritten — ACCEPTED, IMPLEMENTED

### Analysis

Accepted, and the reproduction shape is exact. I had the two halves of this in
my head as one thing and they are not:

- *is the target already doing this work?* — the overlap guard, which correctly
  answers "no" for disjoint jobs;
- *would this install destroy work the target is doing?* — never asked.

`gen-cron.sh --install` owns and replaces the target's single managed block, and
the proposal is rendered only from the config being migrated, so a disjoint
block is not merged into it. It is deleted — immediately after the overlap guard
has said the two workloads are unrelated, which is the worst possible moment for
a reassuring answer. And a backup that stops running does not alert.

### Implemented change

`assert_target_block_not_clobbered()` asks the narrower question: would this
install REMOVE job lines the target runs today? Losses are refused and named.
Anything the proposal reproduces is fine by definition — installing a config is
what makes its jobs run — so an idempotent re-install and a config that adds
jobs both still work.

Wired into `activate-client` and `migrate-profile`. `migrate-to-account`
additionally refuses **any** pre-existing managed block in the target, which is
the review's preferred rule 1; that check was already there and is tested in
section 22.

On the review's instruction to "remove or narrow the test asserting that
disjoint managed blocks are generally safe to allow": narrowed rather than
removed. The assertion now reads *"disjoint jobs are not a DUPLICATE (says
nothing about clobbering)"*, with a comment pointing at section 26. The guard's
own answer is still correct and worth pinning; what was wrong was reading it as
authorisation.

### Preview

Also accepted. The account side diffed `/dev/null` against the proposed block,
which can show what will be added and can never show what would be removed. It
now builds the exact post-install crontab — unmanaged lines preserved, any
existing managed block replaced — and diffs the real one against that. Today the
removal half is always empty because the verb refuses an existing block; a
preview that can only be right by luck is not a preview.

### Evidence

- commit: `1edca10`
- test: section 26, built on the review's shape — root runs `tank/a`, the
  account runs disjoint `tank/b`, and the install must refuse rather than delete
  `tank/b`. Plus: a proposal that keeps every current job and adds one is
  allowed; an unrenderable proposal fails closed; a target with no managed block
  passes.
- results: `PASS=152 FAIL=0`; five of the six new checks fail against `HEAD~`

### Remaining risk

The guard compares job identities, so it inherits `job_identity()`'s
normalisation list. A target job whose line embeds a path that list does not
know would fingerprint differently from its own re-render and read as a loss —
failing closed, which is the safe direction, but noisily.

## Separate observation — dropped ≠ host-level — ACCEPTED, IMPLEMENTED

### Analysis

Accepted, and this one I should have caught when writing it. I computed the
host-level set as "every root job the account's render does not reproduce",
which is a definition of *what is left over*, not of *what belongs to the host*.
An unrecognised send or prune would have been parked in root's crontab —
ownership split in half with nobody deciding it, which is exactly what the host
block was introduced to prevent one paragraph earlier in the same design.

### Implemented change

Only recognised host-level jobs are carried. Today that is the digest, which is
one-per-host by construction. Anything else that the account's render drops
stops the migration and is named, on the reasoning the review gives: leaving it
splits ownership silently, dropping it stops a backup silently, and neither is
the tool's decision to make.

### Evidence

- commit: `1edca10`
- test: section 27 — a dropped `alert-digest.sh` line is recognised and kept and
  the run proceeds; a dropped `snapsend.sh` line for `tank/zzz` stops the
  migration with the line printed
- results: the second of those fails against `HEAD~`

### Remaining risk

The recognised set is one entry long and hardcoded. A future host-level job type
would have to be added here by hand, and until it is, it stops a migration
rather than being carried — the loud direction, but it is a maintenance edge and
worth naming.

## Live evidence for the surrounding verb

Not requested by this review, but it happened in the same session and changes
what the reviewer can assume. Inside an owner-approved maintenance window on
metropolis pve1, `migrate-to-account` ran end to end against real crontabs using
a synthetic block on a test dataset:

- config MOVED to `/etc/zfs-snapshot-all/`, not copied;
- root's collector block removed, the digest kept in its own
  `# BEGIN zfs-backup-host` block;
- the account's block installed with the account's paths, the account's
  `cron.log`, no digest line, and the final config path in its `# Source:`;
- all four of the account's job lines executed as the account (`rc=0`, `0`, `0`,
  and `1` from the monitor line's trailing `[ $rc -ge 3 ]` test);
- then an injected-failure run with the account's crontab made immutable: root's
  crontab restored **byte-identical**, config moved back, exit 1.

That second run exposed a defect fixed in `d506361`: the rollback claimed "both
crontabs restored" one line after warning that the account's was not. It had
never been written, so there was nothing to restore. Both crontabs were
byte-identical to the pre-test capture after teardown, and the test dataset was
destroyed.

Phases 2–5 are therefore no longer stub-only. What remains untested live is this
review's own subject: a target that already runs a disjoint managed block.
