# Response to REV-20261021-160

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `hold_key()` was `tr '/@' '__'`, which is not one-to-one:
`tank/a_b` and `tank/a/b` both became `tank_a_b`. Both the origin record
(`orig.<key>`) and the holder markers (`hold.<pid>.<key>`) used that key. The
reviewer's four steps happen exactly as written: B reuses A's record without
reading its own property, A skips its restore because B "holds" the key, and
B restores B from A's value. The new test reproduces this on the old blob (see
Evidence).

There was a second, smaller hole in the same namespace. The holder glob
`hold.*.<key>` could also match another dataset's marker whose key ends in
`.<key>`, because a key could contain dots and the `*` absorbs them.

### Implemented change

`tui/browse.sh`:

- **Key.** `hold_key` is now the first 32 hex characters of `sha256sum` over
  the full dataset name. The key has no dots, so `hold2.*.<key>` can only match
  that key. If the key cannot be computed, nothing is changed.
- **Record names the dataset.** `orig2.<key>` holds three tab-separated
  fields: exact dataset name, value, source. ZFS names cannot contain a tab or
  a newline. An existing record that names another dataset is refused in
  `expose_snapdev`: no `zfs set` is run and the file is left untouched. The
  same mismatch in `restore_snapdev` becomes residue (snapdev left alone,
  record left alone, check command shown). So a hash collision is handled
  fail-closed rather than assumed away.
- **Holders.** Markers are `hold2.<pid>.<key>` and are scoped by the same key.
- **Legacy files.** A pre-REV-160 `orig.<old key>` for this dataset's old
  collided name, or a live pre-REV-160 `hold.<pid>.<old key>`, refuses the
  change. The message says that it is unknown which of the colliding datasets
  the old record belongs to, and names what to check (`zfs get -r snapdev`) and
  the file to remove after a manual restore. Nothing is guessed, and the file is
  never removed. The old key is computed only to detect such files
  (`legacy_key`).
- REV-159 behaviour is unchanged: residue reporting, a record kept on a failed
  restore, the second live holder of the same dataset, and validation of an
  empty or malformed record. Those cases now run under the new names.

### Remaining risk

- A browse session started by the pre-REV-160 script and still running during
  the upgrade keeps its old files. The new code refuses to touch that dataset
  until the old session ends, and refuses permanently while an old `orig.*`
  record remains. That record must then be checked and removed by hand, which
  is the intended fail-closed outcome.
- No live two-volume test on a lab host in this round. The stubbed entry-point
  test covers the namespace logic.
