# Response to REV-20260804-041

## F1 — ACCEPTED

Agreed without reservation. The last-client branch's own failure contract
was inconsistent: a failed `cron_block_remove` correctly died, named the
mixed state, and left the client record retryable -- but a failed
*subsequent* config-file swap only warned and fell through into `--unpair`
and `STATE=removed`. Exactly as the finding says, that turns a recoverable
partial commit into a client record that lies about being fully torn down,
with the retry path (remove-client, keyed off state that write just
overwrote) unreachable.

### Implementation

The `warn` + fall-through became a `die` that fires before `--unpair` or the
`STATE=removed` write are ever reached:

```text
the zfs-backup-managed cron block for <user> has ALREADY been removed,
but $CRON_CONFIG could not be updated to match (still describes '<name>')
-- refusing to call --unpair or mark '<name>' removed on top of that mixed
state. Fix whatever blocked the rename ..., then re-run remove-client
<name> -- it is a safe retry: the cron side is already done and
idempotent, only this config swap remains.
```

No new transaction machinery was needed: the client record is not written
at all until the very end of `cmd_remove_client` (the `STATE=removed`
heredoc), so at the point this failure fires the record is still exactly
what it was before the command ran -- a plain re-run of `remove-client
<name>` reprocesses from the same state, and `cron_block_remove` is already
idempotent when the block is already absent (its own `cmp -s` no-op check),
so the only thing a retry actually has to accomplish is the config swap.

### Evidence

New suite section (`test/zfsbackup` **255/255**, +7): a stubbed `mv` that
fails only the exact "swap the `.zfsbackup-work.*` tempfile onto
`jobs.conf`" call (everything else delegates to the real `mv`), forcing
publication failure after a (function-overridden, no-op) successful
`cron_block_remove`. Confirms, in order:

- the command exits non-zero;
- `deploy.sh` is never invoked -- proven with a marker-script `DEPLOY` stub
  that touches a file on invocation, not a text-match on captured output
  (a stub like `/bin/false` proves nothing either way, since neither prints
  its own arguments -- caught while writing this test, before it shipped
  as a false positive);
- the client record is byte-identical to before the run (not marked
  removed);
- the old config file is left in place, still describing the client (the
  exact "mixed state" the finding is about);
- the diagnostic names both halves of that mixed state explicitly;
- a retry (real `mv` restored, same stubbed crontab) converges cleanly:
  exits zero, `deploy.sh` IS invoked this time, the client record is marked
  `STATE=removed`, and the config no longer has any `[dataset:]` section --
  no hand reconstruction of the removed cron body needed.

`bash -n zfs-backup.sh` clean. `./test/impact.sh`: `zfsbackup` (only suite
required) re-run clean.

### Not verified live, and why

The SUCCESS path this branch protects (removing a collector's only client,
end to end) was already live-verified before this finding existed --
REV-20260804-040's response documents the `f2test` pass on collector pve1 /
peer pve2: crontab held exactly one `zfs-backup-managed` block before
removal, held none after, and matched the pre-campaign baseline checksum
byte for byte.

The FAILURE path this finding is specifically about -- the config-file
`mv` failing partway through a real run -- was not additionally reproduced
live: doing so needs a real filesystem-level fault (a full disk, a
permissions change on `/root/scripts/zfs-snapshot-all/`, or similar)
injected into a live collector mid-command, which is a deliberately
destructive thing to stage against production infrastructure for a
condition the stub test already reproduces exactly and exhaustively at the
shell level. The stub proves the CODE's response to the failure precisely
(same `mv` call, same arguments, same surrounding function); a live
filesystem fault would only additionally prove that a full disk makes `mv`
fail, which is not in question.
