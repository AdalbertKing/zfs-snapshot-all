## F1 — ACCEPTED (IMPLEMENTED)

### Analysis

`cmd_migrate_profile()` exists at `zfs-backup.sh:2311` and every one of the
twelve steps in the finding is in the code. I checked the two that would have
mattered most for pve0: the zero-client branch really is there
(`no active clients -- migrating the templates only`), and the install really
does go through `atomic_replace_and_install()` after the four guards, never an
in-place edit.

So my proposal was not a lighter path for a simple case. It was the same
migration with every guard removed, on a live config, on a host running twelve
dataset sections.

I want to name the failure mode rather than just fix the text, because it is the
second time in this project: **I proposed a mechanism without searching for the
existing one.** The first was claiming host configs "do not live on the hosts"
while `/etc/zfs-snapshot-all/` held all four of them. Both times the measurement
I did was sound and the search I did not do was the problem. Measuring pve0's
four dead sections told me the migration would be uneventful; it told me nothing
about whether a migration command already existed, and I did not ask.

The time-of-check objection is the sharper half, and I would have got it wrong
even holding the right verb. "Zero clients, zero references" are **mutable
live-host facts measured on 2026-08-09**. My plan would have carried a day-old
inventory as a precondition for a mutation. `migrate-profile` re-reads the
config, rebuilds from current client records, validates through the real
`gen-cron.sh` and previews the actual cron delta — it proves the state at
execution time, which is the property a migration needs and an inventory cannot
provide.

### Implemented change

`docs/design/slice-b1-plan.md`:

- the pve0 path is now `zfs-backup.sh migrate-profile`, preview read, confirmed;
- the 2026-08-09 inventory is demoted to *evidence the migration should be
  uneventful*, explicitly not a licence to skip the preview;
- option 3's fail-closed rule is restated: ordinary enrolment never silently
  treats a pre-GFS host as GFS.

### F1.2 — the incompatibility named in advance, as required

Two properties B1 must not break, since `migrate-profile` calls the function B1
rewrites:

1. **The removal list stays a LEGACY-name list.** It removes bare
   `standard_hourly|daily|weekly|monthly` — the names the pre-GFS *hardcode*
   wrote. If B1 re-derived that list from the loaded profile, then under the
   agreed namespacing the migration would remove the names it is about to write
   and leave the legacy ones in place: **a no-op that reports success**, which is
   the failure class this project keeps finding.
2. **`ensure_cron_config()` and `emit_client_sections()` must keep resolving the
   same names.** The comment at `:885` says they were extracted precisely so
   activation and migration cannot drift. B1 must not give the loader a second
   naming path.

If either cannot hold, F1.2 applies and I repair that path inside B1 rather than
migrating pve0 by hand.

## F2 — ACCEPTED (IMPLEMENTED)

### Analysis

The finding is right and the distinction is exact. The loop at
`zfs-backup.sh:599` tests `grep -q "^\[template:$t\]"` **per name**. It never
asks whether the config has other templates. A config carrying only
`local_daily`/`store_hourly` therefore does not suppress anything; the missing
built-in names would be appended if that path ran.

My sentence — "Hosts with their own never receive them" — was an inference from
pve2's observed state, presented as a rule. pve2's config is consistent with the
rule I invented *and* with that config simply never having gone through this
path, and I had no evidence separating the two.

What makes this worth more than a correction: I was about to write it as a **B1
acceptance criterion**. A test asserting "custom templates ⇒ emit nothing" would
have installed a semantic rule the code does not have, and done it under the
banner of extraction equivalence — the one thing an extraction slice must not do.
Green, and wrong in the direction the slice exists to prevent.

### Implemented change

The criterion is replaced by name-by-name idempotence: a present built-in is not
duplicated; a missing one is emitted per the applicable GFS/pre-GFS rule
**regardless of unrelated custom template names**; a pre-GFS config refuses
ordinary enrolment rather than converting. "Custom templates ⇒ never append" is
out of B1 entirely; if the product wants it, it is its own decision with its own
tests.

## Acceptance criterion, superseded

Recorded in the same commit: the byte-identity criterion is replaced by

retention/GFS, recursion, monitoring, source/target mapping, flags — not the
