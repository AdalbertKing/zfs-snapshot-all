# Response to REV-20260831-128

## F1 — IMPLEMENTED

### Analysis

The finding is correct and the diagnosis is exact: the helper was given no way to
know which of the two public forms it was serving.

The owner's grammar gives them different contracts -- with `--source`/`--target`
the `--onto` list is positional and equal-length; with no selection, one
`--onto` path rebases the whole relationship. Both call sites passed an array of
roots in exactly the same shape, so `restore_onto_plan()` had only the two
lengths to go on. `n_to -eq 1 && n_from -gt 1` therefore always meant "whole
relationship", and a selected list with a missing second destination silently
became a different, valid-looking mapping.

I wrote that branch to make the whole-relation form work and did not notice it
was also the catch-all for a cardinality mistake. The suite could not see it
either: `test/restore/onto.sh` exercises the helper, which by construction
cannot tell the two callers apart.

### How selection provenance reaches the planner

As an explicit first parameter, not as anything derivable from the data:

```
restore_onto_plan <selection given: 0|1> <onto list> <from root>...
```

- the `--source`/`--target` call site passes `1` -- those roots ARE the
  operator's selection;
- the whole-relation call site passes `0` -- those are the relationship's
  recorded roots.

With `1`, the lengths must match, and that includes the two-selected /
one-destination case; there is no fallback to the whole-relation branch. With
`0`, the single-path form and its common-root derivation are unchanged.

The refusal names the other form as well as the mismatch. A message that says
only "these must be equal" teaches an operator that one `--onto` path is never
allowed, and they stop using the form that exists for the disaster it was built
for.

### Against the acceptance criteria

1. **Provenance preserved through the boundary** -- explicit parameter.
2. **Equal length required with a selection, including two-to-one; refused before
   pause, pre-flight, preview or mutation** -- the call sits in `cmd_restore`
   after scope resolution and before `restore_scope_dest` and
   `restore_run_scope`, so nothing has been paused or touched.
3. **One `--onto` path still valid for the whole-relation form**, common-root
   derivation included.
4. **Public-CLI regression pair added** in `test/restore/run.sh`: the selected
   two-to-one form refuses; the identical bare form does not.
5. **Positional order, duplicate-destination refusal, longest-match child mapping
   and name-boundary common root** unchanged and still asserted.

### Negative control

Whole-file controls would be **contaminated**: this change alters the helper's
signature, so the previous file run against the new suite fails on argument
shift rather than on the defect. A control that fails for the wrong reason
proves nothing.

The control is therefore targeted at `8c870aca5b961cdaeead53f8c36ab47d660adcae`
and reproduces the reviewer's own measurement, calling the submitted planner with
the values the public selected-scope path supplies:

```
rc=0 pairs=1 from=rpool/data to=hdd/recovered
```

On this tree the same call refuses, naming both the cardinality and the form that
does take a single path.

## Remaining risk

The refusal depends on the call site passing the right provenance. That is one
literal per site, checked by the public-CLI pair rather than only by the helper
cases -- which is the level the defect lived at.

No live destructive campaign was run for this correction, and per the review none
was required.
