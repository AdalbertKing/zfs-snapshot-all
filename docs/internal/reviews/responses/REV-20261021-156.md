# Response to REV-20261021-156

## F1 — IMPLEMENTED

### Analysis

Accepted. `cap_of` was a `zpool | tr` pipeline, so a failing `zpool list`
was masked by `tr`, and the pool loop treated an empty or non-numeric value
with `continue` -- the pool was silently not evaluated and the run could end
with rc 0 and no alert.

### Planned or implemented change

`hostscripts/capacity-guard.sh`:

- `cap_of` captures `zpool list -H -o capacity <pool>` directly and returns
  failure on its nonzero exit (partial stdout included), on an empty or
  non-numeric value, or on a number outside 0-100.
- The pool loop: an unreadable capacity is never read as "below threshold".
  That pool is skipped with zero `zfs` calls, the run's status becomes 1, a
  pool-specific line is logged and an alert is sent; under `--plan` the pool
  is reported ("NIE da się odczytać zajętości") without an alert. Other pools
  are still evaluated.
- Readable capacities still follow `guard_at`; the post-destroy `zpool sync`
  and capacity hard stop from REV-20261021-155 are unchanged (it uses the same
  `cap_of`, whose failure keeps stopping the run).

### Evidence

- commit/PR: `1dac369e3acee5e1448fe05462bc00f1be1f695f` (branch
  `finisz/REV-156`).
- commands run: `bash test/alertmail/run.sh` on the pve9 clone (fixed tree);
  the same suite with `capacity-guard.sh` from `2bbdd15d` (main; blob
  `991ff29b`, the one the review inspected) as the negative control; `./test/impact.sh --verify`.
- results: fixed tree PASS=139 FAIL=0, of them 52 `PASS capacity-guard:`
  lines (the three-mode loop yields three). New F1 cases:
  capacity command failing with partial stdout (`95%`, rc 1), `NaN`, empty
  output -- each rc 1, zero `zfs` calls, alert naming the pool; `--plan` on a
  failing pool -- rc 1, report, no alert; two pools with the second
  unreadable -- the first cleaned, zero `zfs` calls on the second, rc 1,
  alert for the second. Control: readable 80 % under `guard_at` 89 -- no
  action, rc 0, no alert. On main the three unreadable cases, the `--plan`
  case and the two-pool case FAIL; the control passes on both.

### Remaining risk

None identified beyond the fake-command boundary: no live ZFS fault was
injected; the behaviour is decided entirely by the exit code and the value
of one `zpool list` call.

## F2 — IMPLEMENTED

### Analysis

Accepted. A failing pool discovery logged a line and exited 1 without
calling `alert()`, so an unattended guard could be blind to every pool with
no mail.

### Planned or implemented change

- `zpool list -H -o name` exiting nonzero (partial stdout included): log,
  alert ("bezpiecznik NIE działa -- zpool list zawodzi"), rc 1, zero `zfs`
  calls; under `--plan` the log line and rc 1 without an alert.
- A successful empty listing is documented as a host without ZFS pools:
  nothing to guard, rc 0, a log line ("brak pul ZFS"), no alert (`--plan`
  prints the same). Recorded in the script header and PROJECT_STATUS.

### Evidence

- commit/PR: as F1.
- results: discovery failing with partial stdout -- rc 1, zero `zfs` calls,
  alert; `--plan` -- rc 1, log, no alert; empty listing -- rc 0, zero `zfs`
  calls, no alert, log line. On main the failing-discovery case FAILS (no
  alert) and the empty-listing case FAILS (no log line); the `--plan` case
  passes on both (main already exited 1 without alerting).
- `./test/impact.sh origin/main` selects the suite `alertmail` and the manual
  obligations `deploy-check-only` and `project-status` (U35 entry updated);
  `./test/impact.sh --verify`: rc 0.

### Remaining risk

The empty-listing rule assumes `zpool list` reports an empty but valid
result only when the host truly has no imported pool; a host where pools are
expected but not imported gets a log line, not an alert.
