# Response to REV-20260920-144

## F1 — IMPLEMENTED

### Analysis

Accepted as written, including the reading of what the damage is. The composite
`delete-relation` treats its four steps as independent reports, so a source half
that did not complete was logged, recorded in `rc`, and then walked past. Step 3
purges the record — and that record is not a summary of the operation, it is its
**durable retry state**: `PEER_HOST`, `ACTIVE_ENDPOINT` (hence the port) and
`MANAGED_DATASETS` all live there and nowhere else reachable by name. Once it is
gone, the retry the run itself printed cannot be run: `delete-relation NAME
--yes` answers `no relationship 'NAME' on this host`. The printed manual
`deploy.sh --leave=` line is diagnostics for a human reading that terminal, not
state.

Step 4 is worse than unresumable. With `--destroy-copies` the same control flow
reached `zfs destroy -r` after the source failure — an irreversible action taken
in a run whose own output says a half of it failed. Measured on the code at
`main` `85f1b36dbf7…` with a stubbed 255 `ssh` and a `zfs` that records its
calls:

```text
>>> delete-relation: 3/4 purge the record of 'e'
>>> delete-relation: 4/4 zfs destroy -r tank/b/10.0.0.9/p/x
zfs calls: destroy -r tank/b/10.0.0.9/p/x | destroy tank/b/10.0.0.9/p | destroy tank/b/10.0.0.9
```

The reviewer's scoping is also accepted: this is the failure boundary of a
composite, not a redesign of teardown. Nothing about the successful path, the
plan-only path, or the skip decisions is changed.

### Implemented change

`cmd_delete_relation()`, `zfs-backup.sh`. The branch that already set `rc=1`
when the probe or `deploy.sh --leave` failed unexpectedly now also raises
`source_failed=1`, and a new gate between step 2 and step 3 returns 1 there:

```sh
if [ "$source_failed" -eq 1 ]; then
    log "!!! delete-relation: STOPPED before 3/4. The record of '$name' is KEPT so that the"
    log "!!!     same command can be run again once the source's half is done:"
    ...
    return 1
fi
```

The gate is on the *failure*, not on caution, so every case where there is
legitimately nothing to do on the source keeps its old behaviour and still
purges: `--keep-source`, a record naming no peer, a peer another live
relationship needs (`others`), a source positively proven to hold nothing of
ours (the probe's `[ -e manifest ] || id …` answering 1), and a successful
`--leave`. Those four set `do_source=0` or finish step 2 normally and never
touch `source_failed`. That is acceptance criteria 1–3.

The retry line printed is the exact command to re-run, with `--destroy-copies`
echoed back when it was asked for, so the operator does not have to reconstruct
it; and when it was asked for, the run says outright that the copies were **not**
destroyed.

### One consequence in the GUI, fixed in the same delivery

`tui/delete-relation.sh` (the `Del` window on F3) reported every nonzero result
as `USUNIĘTA Z POZOSTAŁOŚCIAMI` — "removed, with leftovers". After this change
that sentence is false for the new case: nothing was removed beyond the
collector's half, the name is still taken and the copies are still there. The
window now recognises the stop (the verb's own `STOPPED before 3/4` line, which
it tees) and says so: *stopped, the record is KEPT, run the same thing again*.
Leaving it as it was would have made the verb honest and the only surface the
operator actually uses dishonest.

### Remaining risk

Small and named. (1) A run that stops at the gate leaves the collector half
already done (`remove-client` ran, the record says `removed`) and the source
half not done — that is exactly the state the retry expects, and the retry is
idempotent on the collector side because `state=removed` makes it skip step 1.
(2) The gate does not distinguish "the peer is down" from "`deploy.sh --leave`
refused for a reason of its own"; both keep the record, which is the safe
direction, but the operator still has to read the `!!!` lines to know which. (3)
Unrelated to this finding and still open from the 2026-09-20 incident: when a
peer is *shared*, step 2 is skipped entirely, so `zfs allow` grants and the
source's scope entry for the removed datasets stay — there is no verb for "take
this dataset out of the source's scope" yet.
