### On point 4's last clause

Remote quiesce (`snapget -q`) contributes **no local requirement** and is not
silently passed either. The preflight states it:

```
[ plan ] blok uzywa quiesce ZDALNEGO (snapget -q) -- grant zyje na hoscie
         ZRODLOWYM i nie da sie go stad sprawdzic; potwierdza go
         'deploy.sh --join <pakiet> --allow-quiesce' wykonany tam
```

That is the enrolment proof the review asks to be named. Validating it from here
would mean this verb reaching into another host's sudoers, which it should not
do.

### The one shortcut, declared

`qscope_guest_id` is **copied** from `lib-zfs-snap.sh`'s `quiesce_guest_id`
rather than sourced — sourcing the library into this wrapper would drag its whole
runtime in. A copy can drift, so a test pins the two against each other on eight
dataset shapes (VM disk, container subvol, nested path, bare leaf, multi-digit
id, a parent, an ordinary dataset, a near-miss name). If they ever disagree, that
test fails rather than a migration passing on a stale mapping.

## Live validation on all four hosts

Run against the account blocks now installed everywhere. Every source that asks
for quiesce, checked through the real helper as the real account:

```
pve0 192.168.11.10   hdd/data/vm-101-disk-0 (101), hdd/lxc/subvol-102-disk-{0,1} (102)      all ok
pve1 192.168.11.11   rpool/data (-), vm-100-disk-0 (100), vm-101-disk-0 (101),
                     vm-106-disk-{0,1} (106)                                                all ok
pve1 192.168.28.9    subvol-101-disk-{0,1} (101), subvol-107-disk-0 (107),
                     vm-100-disk-0 (100), vm-106-disk-0 (106), rpool/ROOT/pve-1 (-)          all ok
pve2 192.168.28.8    subvol-103-disk-0 (103), rpool/ROOT/pve-1 (-)                           all ok
```

Two shapes worth pointing at, because they are the ones a weaker check gets
wrong in opposite directions:

- **pve1 192.168.11.11** runs `-q agent "rpool/data"` recursively. The named
  parent owns no guest at all; the four children do. Without the expansion the
  scope would have been one dataset with no guest — "nothing to quiesce" — and
  the check would have passed by looking at nothing.
- `rpool/data/vm-101-disk-0` on that host is a **pvesr replica**; guest 101 runs
  on pve0. The helper answers `kind=absent`, which is acceptable, not a gap. A
  check that only asked "is this id in the whitelist" would have failed a
  perfectly correct configuration.

`hdd/vm-disks/vm-102-disk-0` on metropolis pve1 is correctly **absent** from the
scope: it was added to the backup earlier the same evening with `quiesce = no`,
because its qemu-guest-agent is not running inside the guest.

## Product impact — AGREED

Agreed. After this the high-level operation proves the state that matters
("every `-q` job's guest is covered") rather than the one that is easy to
measure ("the helper is installed"). The administrator never has to know those
are different internal states, which was the review's point.

## Remaining risk

The scope is derived from `-q` on the rendered **snapsend** lines. A future job
type that quiesces through some other command would not be seen. That is the
same boundary `block_capabilities` has, it fails closed in the sense that the
unknown job simply is not checked — which is worth stating plainly, because it
is the one direction in this change that is not fail-closed.
