## F2 — four send cadences under one time-bucket ladder — ACCEPTED

This is the substantive one and the diagnosis is exactly right. I moved
retention onto the ladder and then left the four send cadences standing as if
they still meant something.

`delsnaps.sh -G` buckets by **creation time** and never reads the prefix. So
`standard_daily`, `standard_weekly` and `standard_monthly` defined no retention
tier at all — they produced additional snapshots and additional transfers whose
only effect was more work, plus the collision you describe: three of them fire at
00:00 against the same source and target while the hourly job follows a minute
later.

Taking your option 1. The profile is one send cadence and one client-level
ladder:

```
1 * * * *    snapget  ...                                    (one per dataset)
21 * * * *   delsnaps.sh -G -R "<target>/<label>" "automated_" -H24 -D7 -W4 -M12
*/15 * * * * check-snap-age.sh -R "<target>/<label>" "automated_hourly" 90m 150m
```

Two consequences worth naming because they are not obvious from the diff:

Every `keep_*` tier now matches `automated_hourly`, since that is the only
prefix that exists. The tiers still differ — each contributes its own count
letter to the ladder — but they no longer pretend to describe separate snapshot
families.

Only the finest tier carries monitor thresholds. Leaving them on `keep_daily`
would have pointed a staleness check at `automated_daily`, a pattern nothing
creates, which sits at CRITICAL forever. That is the same class of permanent
false alarm this estate has been bitten by before.

### Tests you specified

| requirement | assertion |
|---|---|
| one send job per dataset, one recursive GFS prune per client | both counted |
| no same-dataset send jobs share a minute | schedule fields deduplicated; 0 collisions |
| exactly one monitor, on a prefix that exists | counted **and** matched against `automated_hourly` |
| pre-GFS installations unchanged without an explicit action | the legacy guard, tested from both sides |

The "no two sends share a slot" case is structural now that there is one
cadence. It is in the suite anyway, as the thing that fails if a future second
tier quietly reintroduces the pile-up.

## F1 — an unreadable crontab read as an empty one — ACCEPTED

You are right that my previous answer under-rated this. I wrote it off as "a
noisy preview", but the operator is being asked to approve an exact live change,
and a failure that renders as "nothing is installed yet" is a guess in the
reassuring direction — the worst one available.

`crontab -l` is now captured with its status and stderr. The single benign case
is a user with no crontab, which cron reports on stderr; that yields an empty
left side, correctly. **Everything else aborts before the prompt** and installs
nothing.

The match on that message is deliberately loose, and the locale risk falls on the
safe side: a translated "no crontab" makes this refuse rather than invent an
answer.

## F3 — migration leaked internal template knowledge — ACCEPTED

Agreed, and the phrasing you quote was the tell. Telling an administrator that
migration is "a deliberate edit" hands them the `standard_*` / `keep_*` split —
precisely the thing the simplified workflow exists to keep out of their way.

`zfs-backup.sh migrate-profile [--yes]` now does it:

1. refuses if the host is already on the GFS profile (idempotent, says so);
2. removes the legacy templates — `ensure_cron_config` never rewrites a template
   that is present, so removal is what makes this a migration rather than an
   append that leaves dead schedules behind;
3. rebuilds every **active** client through `emit_client_sections()`;
4. validates with `gen-cron.sh` on the working copy;
5. shows the exact config and cron diff;
6. asks once, then installs atomically with the existing rollback.

Step 3 shares a function with `activate-client` on purpose. A migration that
produced *slightly* different sections than an activation would be the worst kind
of bug available here, because the difference would only ever appear as a cron
line nobody thought to compare. Extracting it was the point of the change, not a
tidy-up alongside it.

Clients that are not active are skipped and named. They have no cron sections to
rewrite, and inventing some for a half-enrolled client would be worse than
leaving them.
