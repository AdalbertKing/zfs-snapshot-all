# Response to REV-20261017-151

## F1 — IMPLEMENTED

### Analysis

Accepted as written. In `snapsend.sh`'s `process_dataset()`, the P-0 refusal
for an existing target with snapshots, no common snapshot by GUID and no
bookmark carried the extra condition `[ "$FULL_HISTORY_SEND" -ne 1 ]`. `-H`
therefore skipped the refusal. With no common base the same run then built
`zfs send ... -R <snap>` and received it with the default `-F -s`. That is a
destructive replication receive on an unrelated target, without the explicit
`-f` that the refusal message itself names. The pull twin has no such
exception.

I reproduced it with the new suite against `snapsend.sh` from `main`
`b5941292`. Push `-H` on the unrelated target produced `zfs send` and
`zfs recv` with no refusal, while plain push and pull `-H` refused.

### Implemented change

`snapsend.sh`, one condition in `process_dataset()`: the
`[ "$FULL_HISTORY_SEND" -ne 1 ]` term is removed from the no-common-base
refusal, with a comment that says why. The refusal now fires for `-H` exactly
as for a plain push and as in pull: the same message, `abort_held_snapshot`,
`return 1`, before any `zfs send` or `zfs recv`.

- `-H` keeps its meaning: what a full stream carries. On an absent target,
  and on a target with no snapshots, the refusal does not apply
  (`${#tgt_snaps[@]} -gt 0`), and the full-history `-R` stream is sent as
  before.
- With a common base the refusal does not apply either, so the D3 backup
  landing and its logged `recv -F` convergence are unchanged.
- `-f` remains the only decision for destructive recreation. Its branch is
  untouched (`FORCE_FULL_SEND -ne 1` still opens the condition).

snapsend stays v2.76. Refreeze done, and the freeze entry names this REV.

**Twin:** pull never had the exception, so this moves push to pull's
behaviour. `process_dataset` is a twinned function. `test/twins` failed as
designed ("changed in snapsend.sh ONLY"). The answer is that the pull
direction needs no change, so I blessed it. Only snapsend's hash moved. The row's
direction reason is unchanged and still true in substance, but its line
references (`snapsend.sh:1732`, `snapget.sh:1733`, `snapget.sh:1657`) have
drifted with earlier changes and point at the wrong lines. I did not refresh
them in this bounded change.

Also in this change, test-only: `test/twins` section M extracts
`mirror_target` and runs it against stubs. Since REV-20261017-150 that
function calls `guest_disk_is_live` first, and the extracted copy printed
"command not found" in every case. The cases passed, because the failed call
reads as "not live", but the output was misleading. The section now defines
a stub that returns "not live". That matches the shipped function's answer
for its target `t/x`, which names no guest.
