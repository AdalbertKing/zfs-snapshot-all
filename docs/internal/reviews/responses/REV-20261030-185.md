# Response to REV-20261030-185

## F1 — IMPLEMENTED

### Analysis

Accepted. The first §9.2 put `update-hold` on root's updater only. For the account it used a clock
window outside `:15`, which is not mutual exclusion: a `git pull` already running, or one that starts
late, could overlap `git gc --prune=now`.

Nothing was run on any host. No checkout was cleaned; the review came before execution.

Of the review's two options for the account, this takes the first: remove the pull cron line and
prove that the earlier invocation has exited. The shared lock is not used: it would change the
account's cron line, which needs a release and a redeploy on every host before a one-time cleanup.

Entry points are closed first, and only then does the wait start:

- root: `update-hold` is checked by `do_self_update` before it touches git (`update-control.sh`). This
  covers root's current cron line, `update-control.sh --self-update`, and `deploy.sh --self-update`.
  A manual `--rollback` does not check the hold (see Remaining risk).
- every repo owner, root included: a `cd <repo> && git pull --ff-only origin main` line is removed from
  its crontab, and the original crontab is saved first. For the account this is its updater. For root
  it is the old bare-pull form that `deploy.sh` still recognises on some hosts, and the hold does not
  gate that line. The removal is read back. `deploy.sh` knows other historical updater shapes as
  well. If any other line in the crontab runs `git` on a repo being cleaned, the tool stops before
  writing the crontab rather than guess at it.

Once both are closed, no scheduled updater can start until they are reopened. The wait then covers
whatever began earlier: it ends only when no such process is left.

### Implemented change

`release/clean-host-clone.sh <update-state-dir> <repo>...`, run as root on one host. It is not shipped:
`release/MANIFEST` is a whitelist. Design §9.2 is rewritten to describe it.

1. Close the entry points. Each of these steps is recorded in a `barrier` file in the run's directory
   *before* it is taken. A run that dies while closing them, or later, therefore leaves a record of
   what it changed in the entry points.
   - Record `created_hold=1`, then write `update-hold` atomically, if it is absent.
   - For every repo owner, root included, under lib-cron.sh's per-user lock:
     - `cron_read` the crontab; an unreadable crontab stops the run, "no crontab" counts as empty;
     - save the original and record it;
     - remove the pull line, stopping if the filter itself fails;
     - stop if another line still runs `git` on the repo;
     - `cron_write` the result.
       `cron_write` reads the crontab back and compares it.

   The crontab goes through lib-cron.sh, the project's single crontab writer (`test/deps.conf`,
   `[file:lib-cron.sh]`). The script sources `lib-cron.sh` from the checkout root above its own
   directory (`release/..`). Failing that, it uses the first given repo that carries one, or
   `CLEAN_LIB_CRON`.
2. Adopt a failed run. If an earlier run left a `barrier` file, the new run takes over that record.
   The original crontabs and the "created the hold" flag then come from the first run, so reopening
   restores what was there before the first run touched anything.
3. Wait (`CLEAN_WAIT`, default 1800 s) until no process does any of these:
   - has its cwd under a repo (paths resolved with `readlink -f`);
   - names a repo on its command line (for example `deploy.sh` run from root's checkout);
   - runs `update-control.sh` or `deploy.sh --self-update|--rollback|--resume-updates`. This is what
     catches root's cron entry, `<state>/update-control.sh --self-update`.

   On timeout: stop.
4. A leftover `*.lock` in `.git`: refuse.
5. Per repo, as its owner (`runuser`), refuse when:
   - HEAD is not the branch `main` (symbolic ref and commit);
   - tracked files are changed, or `git status` itself fails;
   - there is a stash, or listing `refs/stash` fails;
   - the rollback target (`previous-revision`, root's checkout) is not an ancestor of `origin/main`.

   Otherwise: delete every ref except `main`, `origin/main` and `origin/HEAD`; `reflog expire
   --expire=now --all`; `gc --prune=now`.
6. Validate:
   - `fsck --full`;
   - HEAD, `origin/main` and the rollback target are unchanged;
   - every path outside `.git` (ignored host config included) is unchanged: name, owner, group, mode
     and size, and the sha256 of each file.
7. Controlled update.
   - Account: the git command of its cron line, `git pull --ff-only origin main` in the repo, runs
     once, still under the barrier (without the cron line's log redirection).
   - Root: `fetch origin main` must still fast-forward from HEAD. Root's real update is
     `update-control.sh` at the next run after the hold is gone. The operator reads `git-pull.log`
     after it (design §9.2).
8. Reopen. The saved crontab is reinstalled with `cron_write`, under the lock, and read back. The hold
   is removed only if this run, or the failed run it adopted, created it. Every `barrier` record in the
   state directory is removed: a run that adopted a record and then failed left one that says the
   same.

`set -Eeuo pipefail` with an ERR trap. Any failure stops at once with the barrier in place: the hold
stays and the cron lines stay removed. The message names the run's directory. That directory holds
the before/after inventories and the barrier record, which names the saved crontabs (in the first run's
directory when this run adopted one). Rerunning the tool after the cause is fixed adopts that barrier and reopens
the entry points as they were.

### Remaining risk

- Nothing has been run on a host. Execution stays behind the Owner's gate: lab first (pve9, pve10,
  pve11; pve9b when it is reachable), then production one host at a time with consent.
- A manual `update-control.sh --rollback` does not check the hold. If one is already running when the
  wait starts, it is waited for. One an operator starts after the wait is not covered. Operator
  procedure: no manual update commands on the host while the tool runs.
- The process scan reads cwd and the command line. A git process that reaches a repo only through
  `GIT_DIR`, with its cwd elsewhere and no repo path in its arguments, would not be seen. No updater on
  the hosts works that way.
- The scan errs towards waiting: any command line naming `update-control.sh` counts, including an
  editor.

## F1 — IMPLEMENTED again, after the rejection of `680465bc`

### Analysis

Accepted. The process scan skips this tool by name, and nothing else serialised two runs. A second
run could adopt a live run's barrier record, reopen the entry points on success and delete every
record, while the first run was still before `gc`.

On the hosts every run so far was sequential; each finished before the next began:

- lab: pve10, pve11, pve9 and its recovery run;
- production: pve1 and pve2 (28.x), pve0 and pve1 (11.x), with the Owner's consent.

The interleaving did not happen there. The defect is real all the same.

### Implemented change

`release/clean-host-clone.sh`: before any barrier state is read, the run takes `flock -n` on two
kinds of lock and holds them until the process exits, on success or failure:

- `<state>/.clean-host-clone.lock`, one per state directory;
- `$CLEAN_LOCK_DIR/clean-host-clone.<first 16 hex of the path's sha256>.lock`, one per repository (default
  `/run/lock`). Two runs that name different state directories therefore still cannot share a
  repository.

A second run refuses with "another clean-host-clone is running". It never adopts a live record,
never reopens anything and never deletes a record. Adoption of a failed run (c8, c14, c15) is
unchanged: a failed run has exited and released its locks.

### Disputed point: the reproducer's exit status

On this fix the reproducer exits 1 even though it prints PASS. There are two causes:

1. `wait "$TWO"` runs under `set -Eeuo pipefail`. A second cleaner that refuses, which the acceptance
   delta allows, exits non-zero, so the script dies at `wait` before it prints anything. With
   `wait "$TWO" || echo "second_cleaner_rc=$?"` it prints `second_cleaner_rc=1` and then the PASS
   verdict above.
2. After PASS, the EXIT trap's `rm -rf "$T"` fails ("Directory not empty") because cleaner A is still
   alive and writing in the repo. The trap therefore ends with status 1.

Requested: the reviewer makes `wait` non-fatal and stops or waits for A before `rm -rf`, or accepts
the printed verdict.
