# Response to REV-20260813-119

## F1 — ACCEPTED and IMPLEMENTED. The ordering was wrong and the argument that shows it is my own.

I wrote the design with confirmation before capture, and REV-118 — my own finding,
three commits earlier — is the proof that cannot work. `written` on a live dataset
reflects the last committed txg, so the read-only preview cannot state the live
loss set exactly, so a confirmation resting on it is approval of a set nobody has
measured. Improving the after-the-fact measurement does not retroactively inform
a decision already taken.

### The capture comes first

The path now takes a technical snapshot of the source **before** it prints the
loss set. A snapshot is a committed point, so the delta it captures is a fact
rather than an estimate that may be a minute stale. The operator then sees:

```
  DO ZNISZCZENIA -- zbior ZMIERZONY, nie oszacowany:
    snapshot  s2                                       1024 B
    dane zapisane po ostatnim snapshocie zrodla:       7777 B
      (zamrozone w 'restore-preview-...' -- to POMIAR, nie kopia bezpieczenstwa:
       odtworzenie niszczy rowniez ten snapshot)
    RAZEM: 8801 B
```

This reverses my earlier "nothing mutates, not even the snapshot" rule. That rule
was right while the preview could not be informed; F1 shows it cannot be informed
without the snapshot, so the mutation is what buys the property. I would rather
name the reversal than let it look like drift.

Per R-017 the snapshot is never described as preservation — the rollback destroys
it. The output says measurement, and a test asserts the wording.

### The commit boundary

Your second point is the one I would have missed on my own: an accurate preview at
T1 does not stay true. After confirmation the path takes a **second** technical
snapshot and reads `written` on it. That is accounting between two committed
points, so unlike the live read it does not lag — a non-zero answer is proof of
arrival rather than a hint. It also lists any snapshot on the source that is
neither in the approved set nor its own.

Either signal means state arrived that the operator never approved, and the answer
is to destroy nothing:

```
  PO ZATWIERDZENIU stan zrodla sie ZMIENIL:
    nowe dane: 4096 B zapisane po podgladzie
  ... zatwierdziles zbior strat, ktory juz nie opisuje zrodla. NIC nie zniszczono.
```

An unreadable value counts as arrival. Fail-closed is the only defensible
direction when the question is "did something appear that I am about to destroy".

### Sufficiency, since you said the snapshot is not automatically enough

The claim I am making is narrow, so it can be checked: **no state created after
the preview snapshot can cross the destructive boundary unnoticed**, because
anything created after it is either (a) new data, which appears as non-zero
`written` on the commit snapshot — snapshot-to-snapshot accounting, no txg lag —
or (b) a new snapshot, which appears in the source's snapshot list after the
preview snapshot and is not the commit snapshot. There is no third way to add
state to a ZFS dataset. If you see one, that is the finding to raise.

### Round 2 — the write fence

You were right that the boundary snapshot only proves nothing arrived *through*
it, and I had named the same window in my own remaining-risk list without closing
it. Observing that nothing arrived is not the same as making arrival impossible.

The fence is `readonly=on` on the source. It is the ZFS mechanism that actually
refuses userland writes, for filesystems and ZVOLs alike, and it does not block
what this path needs — snapshot, rollback and receive are not userland writes.

Order is part of the property and is asserted, not just intended: **the fence goes
up before the boundary snapshot**. Raised after the check, it would leave the same
hole one step further along.

Restoring it is exact rather than convenient:

- a value that was **inherited** goes back via `zfs inherit`, not via a local `set`
  that happens to read the same today and diverges from the parent tomorrow;
- a source that was **already** `readonly=on` stays that way. Restoring "off"
  because it is the common case would silently erase a deliberate setting. That
  pair is the discriminating test for the restore logic.

Fail-closed both ways. A fence that cannot be raised refuses the run — proceeding
without it means destroying state that nothing prevented from arriving. A fence
that cannot be **lowered** is a loud fatal error naming the manual fix, because a
production dataset left read-only is a different outage from the one the operator
called this path to fix, and one they would otherwise debug blind.

No policy flag was added, per your instruction. The fence is a mechanism, not a
choice.

### Round 3 — the four residuals

All four accepted. Each was a case of the implementation being right about the
intent and wrong about the mechanism.

**F1.1 — ordering is not identity.** I decided what was new by position in a list
sorted by `creation`, and `creation` has one-second resolution, so it is not a
total order. Two snapshots made in the same second can come back either way round
and an intruder could sort *before* the preview snapshot, out of the "newer" set
entirely. Your point about the measurement interval is the sharper half: an
intervening snapshot also shortens the window `written` covers on the commit
snapshot, so the run could come back green having measured the wrong interval.
It is now a **set difference over snapshot names** — before-set captured right
after the preview snapshot, after-set read at the boundary, minus the commit
snapshot. There is no ordering left in it to get wrong.

**F1.2 — capture before mutation.** The old helper read the old state and changed
the property in one function, so a verification that came back unreadable returned
failure with nothing saved and could leave the source read-only. Split in two:
`restore_fence_capture` only reads, `restore_fence_raise` only mutates. Past the
capture line every path holds what it takes to undo, and after a failed raise the
undo is attempted unconditionally — because `set` may have gone through and only
the verification failed, which is precisely the case you named.

**F1.3 — provenance is part of the state.** A property that arrived with a
received stream has source `received`, and writing the same value back with
`zfs set` converts it to a local override: right value, wrong state. `received`
now goes back via `zfs inherit -S`, `local` via `set`, inherited via plain
`inherit`. The read-back also refuses a restoration that turned a non-local source
into a local one.

**F1.4 — cleanup that cannot admit failure launders a leftover.** It warned and
returned success, and the callers then told the operator the source was exactly as
they had left it while a run-owned snapshot sat on it. It now returns a status,
and every post-snapshot refusal goes through one exit that keeps two claims
separate: *nothing was destroyed* (always true on those paths) and *the source is
as you left it* (only when cleanup actually succeeded).

Six new assertions, including the control that makes F1.4 discriminating: on a
successful cleanup the path still **may** say the source is unchanged.

While wiring the F1.1 regression I hit the same class of defect in my own fixture.
The stub injected the intruder when the *preview* snapshot was taken, which under
the old ordering logic read as an intruder but under a set difference is simply
part of the before-set — correctly ignored. The test was named "arrived after the
approval" and modelled "was there all along"; it now injects at the boundary
snapshot. Changing the mechanism moved the moment the fixture had to act, and the
test had been passing for a reason that stopped being true.

### Round 4 — the F1.2 residual

Accepted, and it is the same defect I had just fixed one layer down, committed
again one layer up in the same change. Snapshot cleanup started reporting its
status honestly; the `readonly` restoration was still swallowed with `|| true` on
every post-mutation failure path, and the final helper — seeing the snapshots
gone — told the operator the source was exactly as they had left it while it sat
there read-only.

The exact-state claim now requires **both** facts. The fence outcome is a
**parameter** of the final helper rather than something it is left to assume, so
there is no exit that can forget it, and the leftover report names each thing
separately: one collective sentence would send the operator to fix half of it.

Four assertions, including the arrival path (the one an operator is most likely to
meet for real), both-leftovers-at-once, and the control that a clean run still
*does* make the exact-state claim — without which an implementation that simply
stopped claiming anything would pass the other three.

One older assertion went red and was **rewritten rather than loosened**. It pinned
a literal sentence that this change replaced with the shared final-status report;
it now pins the contract instead — nonzero, the `readonly` remediation named, no
exact-state claim. A literal-sentence assertion breaks on every rewording and
invites a loosening fix; a contract assertion breaks only when the property really
goes away.

### Cleanup

Every technical snapshot is removed on every exit path, including every refusal
and the unconfirmed case. Destroying them is safe in the sense REV-114 settled:
uniquely named, created by this run seconds earlier, so ownership is a fact rather
than an inference from ordering. A failed removal is reported, never swallowed.

## Remaining risk

1. **The fence is a ZFS-level refusal, not a lock.** Anything with `zfs` rights on
   that host can lower it — root, another tool, a second copy of this one. It
   closes the window against ordinary writers, which is what the finding was
   about; it is not an exclusion primitive and I am not claiming it is one.
2. **An in-flight write already accepted before the fence went up is not
   revoked.** It lands, and the commit-boundary check is what catches it — which
   is why both mechanisms exist rather than one.
3. **Fencing a ZVOL that a running guest has open will give that guest I/O
   errors.** For a recovery target that is usually stopped, but not always, and
   the operator is not warned about it yet. That warning belongs with the
   execution step, where the disruption actually happens.
4. The technical snapshots are extra objects on a production source for the
   duration of the run. They are removed on every path, but a hard kill between
   creation and cleanup leaves them behind. They are named distinctively for
   exactly that reason.

Not claiming closure.
