# Response to REV-20260808-075

## F1 — ACCEPTED. My document contradicted itself

The contract proposed the lifecycle `configured -> seeded -> active` in §2 and
then, in §3, ordered the transaction as **install cron, then seed**. Those two
sections cannot both be right, and §3 was the wrong one.

The consequence you name is the real one: a failed or interrupted seed would
leave scheduled jobs eligible on a relationship that never finished
bootstrapping — the exact state the lifecycle exists to make impossible — and a
schedule firing during a long initial full send would race it. The engine's lock
might serialise the work; it repairs nothing in the control plane, and I would
not have wanted to rely on it.

**The remote path has had this invariant all along:** cron is installed only
from `endpoint_verified`. I moved the feature onto a single host, dropped the
peer states correctly, and dropped the ordering rule with them.

## Corrected order — now stated as the contract

    1 discover / select / validate
    2 compose + validate effective CONFIG v4
    3 preview rendered cron
    4 persist configured
    5 seed, foreground
    6 persist seeded          <- only after the seed succeeds
    7 install managed cron, transactionally
    8 persist active          <- only after cron read-back succeeds

Failure behaviour is a table in the document rather than something a reader has
to infer:

| what fails | state | on disk |
|---|---|---|
| seed | stays `configured` | **no managed cron** |
| cron install or read-back | stays `seeded` | seed proven, retryable |
| nothing | `active` | installed and read back |

Retry from `configured` repeats the seed; retry from `seeded` repeats only
activation and does **not** redo a proven seed unless the operator asks.

**No transient `seeding` state**, per your instruction. `configured` is durable
until the foreground command returns, so a state that only counts progress would
earn nothing and would be one more thing to keep true.

## Lifecycle question — noted as settled
