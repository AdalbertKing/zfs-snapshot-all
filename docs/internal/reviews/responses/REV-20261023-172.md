# Response to REV-20261023-172

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `UI.key()` joined a live background refresh for 30 s and then went on
to handle the key against the rows it had. The new regression found a second, smaller
window on the same gate: a refresh thread that had already FINISHED, but whose data the
curses loop had not yet taken (it polls every 0.3 s), skipped the gate entirely, because
`poll_bg()` was only called when the thread was alive. The review of this response found a
third: a refresh that FAILED cleared the pending state without data, so the next key also
acted on the pre-refresh rows.

### Planned or implemented change

`tui/zfs-tui.py`, `UI.key()`, the gate before any key outside a window:

- a pending refresh is always taken first: when the thread is alive it is joined for at
  most `UI.BG_KEY_WAIT` (30 s, a class attribute so the test can shorten it), and
  `poll_bg()` is then called whether or not the thread was alive;
- if the refresh is still running after the wait, the gate fails closed: the key returns
  `"stay"` with nothing scheduled, the old rows stay on screen, and the message says the
  screen is NOT current, that the key was dropped and to press it again once
  „odświeżam w tle” is gone (it keeps the background note, which `poll_bg()` removes when
  the data arrives). `q`/`F12` still quit;
- a failed refresh (`poll_bg()` error branch) sets `bg_failed`; while it is set, row actions
  (`UI.ACTION_KEYS`: Enter, Del, e, F7, F8, F9) are dropped with a message that the screen
  is NOT current and Ctrl-R refreshes; navigation and quit still work. A full successful
  refresh (`apply_data(full=True)`, which Ctrl-R ends in) clears it;
- the successful path is unchanged: `poll_bg()` applies the data with `full=True`, which
  clears the lazy profile/config caches, and only then is the key handled.

The wait is still bounded, so a hung reader cannot freeze the keyboard; it can only make
keys other than quit do nothing until fresh data arrives.

### Remaining risk

`run_verb()` still has no timeout of its own, so a hung reader keeps the screen stale
(and keys dropped) until it returns or the GUI is restarted; that is now visible and fails
closed rather than acting on old rows. Bounding the readers themselves is a separate change.
