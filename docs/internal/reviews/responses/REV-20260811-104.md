# Response to REV-20260811-104

Both findings ACCEPTED.

## F1 — IMPLEMENTED — distinct source/target prune-template identities

Correct: two `[prune:]` scopes sharing one template family are not two policies.
Both prune sections resolved to the same `profile__default__keep_*` templates, so
editing `keep_monthly retain=-M12 → -M36` moved SOURCE and TARGET together.

Fixed at CREATE (`cmd_local_backup`): the target keeps the profile's `keep_*`
family (as `ensure_cron_config` already installs it); the SOURCE now gets its OWN
family, `profile__default__src_keep_*`, byte-copied from the same values but under
a distinct stable identity, and the source `[prune:]`'s `use_template` references
it. The rename is `__keep_` → `__src_keep_` (namespace-agnostic, so it works for
any `--profile`), and the source templates are extracted with
`awk '/^\[template:/{p=($0 ~ /__keep_/)} p'` (robust to template ordering). No
second configuration representation; native CONFIG v4 stays runtime truth, and
reactivation/profile drift cannot re-couple them (Phase 3's one-way handoff).

Evidence (`test/localbackup`, +4):
- `104 F1/... DISTINCT prune-template identities` — the candidate carries both a
  `__src_keep_*` and a `__keep_*` family, referenced by the source and target
  prune respectively;
- `104 F1/editing only SOURCE retention ...` — mutating `src_keep_monthly`
  `-M12→-M36` makes the source cron line `-M36` while the target stays `-M12`;
- `104 F1/editing only TARGET retention ...` — the converse (`-M60` target, `-M12`
  source);
- `104 F1/negctl: a SHARED template family couples both sides` — the load-bearing
  control: collapse the two families back to one (`__src_keep_→__keep_`, the
  `49d547ae` shape) and the same mutation moves BOTH sides, demonstrating why
  distinct identities are required.

The property applies equally to the remote-PULL source prune when it is added
(step 3): it will use the same distinct source family.

## F2 — IMPLEMENTED — recursive rationale reduced to the proven invariant

Accepted. The design no longer justifies allow-with-warning by "a recursive
relationship already takes a FULL on its first miss anyway." The note now states
only the established fact — recursive mode lacks bookmark fallback, so it needs a
FULL **when no usable ordinary common snapshot remains**, which is narrower than
"first miss" (a recursive transfer may still have a common snapshot after one
missed run) — and ties the recursive hard-refuse-vs-warn choice to a targeted
runtime test under REV-102 step 4 rather than a shorthand premise.
