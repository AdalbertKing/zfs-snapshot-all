# Response to REV-20261021-166

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. Since U62 the replayed `--host` is the active endpoint,
which may be `HOST:PORT`. In `cmd_import_relation()` the U45 probe passed that
whole value to `rux_root_ssh` as the host and hard-coded port 22. A relation
on a non-default SSH port therefore never got `--join-remotely`.

The same defect sat in the one-command path just above it ("source no longer
knows this collector"). It probed `"$peer_host" 22` and built
`--source="$peer_host:$_ds_list"`, which for `HOST:PORT` gives
`HOST:PORT:DATASETS`. The manifest lookup `peer_label "$peer_host"` also
labelled `HOST:PORT` rather than the host.

### Planned or implemented change

`cmd_import_relation()` now parses the replayed endpoint once, with the
canonical `parse_endpoint_arg`, into `peer_ep_host` and `peer_ep_port`. This
happens before any probe. An endpoint that does not parse is refused before
anything is called.

- Both probes of the one-command path and the U45 probe call
  `rux_root_ssh "$peer_ep_host" "$peer_ep_port" …`.
- The one-command path passes `--source=HOST:DATASETS` and, for a port other
  than 22, `--port=PORT` (`rux_entry` already takes `--port=`).
- The manifest check uses the label of the host.
- The replayed `--host=HOST[:PORT]` argument reaches `cmd_add_client` exactly
  as the file has it.

### Remaining risk

A live import on a non-default SSH port has not been run. The lab relations
all use port 22. The duplicate-peer guard above the probes compares
`PEER_HOST` with the raw `--host` value, and this change leaves it as it was.
With a `HOST:PORT` replay that comparison cannot match a record, so a second
relation to the same peer on a non-default port would not be refused at this
early point. It was not part of the finding. I have not changed it without
your view on whether `PEER_HOST` or `ACTIVE_ENDPOINT` is the right key there.
