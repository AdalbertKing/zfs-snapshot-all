# Response to REV-20260811-107

## F1 — ACCEPTED and IMPLEMENTED — reactivation preserves installed source policy

You are right, on the substance and on the architecture. The step-3 "regenerate the
remote source prune from the profile on every activation" behaviour discarded an
admin's edited SOURCE retention on the next endpoint change, re-coupling policy
through the profile and breaking the REV-102 contract that CONFIG v4 is runtime
truth after CREATE. The header-carries-topology reasoning justifies moving the
scope/SSH facts, not rebuilding the policy body — exactly the REV-089
topology-vs-policy split.

### Change (c6f0acd)

`emit_remote_source_prune` no longer regenerates. On every activation it now:

1. `capture_client_remote_source_prunes` — captures each INSTALLED remote source
   prune's POLICY body (marker-verified, keyed by source dataset) BEFORE removal;
2. removes the old-scope sections;
3. per dataset, if an installed body was captured, REPLAYS it under the new scope
   rewriting ONLY the `ssh_flags` line. `use_template`, `gfs`, `gfs_pattern`,
   `recursive` and the retain (via the preserved `__src_keep_*` templates, which
   `append_source_templates_if_missing` already never overwrites) survive an admin
   edit exactly as installed. Only a dataset with NO installed source prune — a
   genuine first CREATE — is generated from the profile.

No new representation, inheritance, drift manager, or source-profile authority; the
renamed section is rebuilt from the INSTALLED section as the source of truth,
changing only topology — as you specified.

## Protocol reconciliation (the rozjazd, named)

This finding exists because I let an OWNER shortcut-approval override an ESTABLISHED,
reviewer-owned architectural invariant. When I hit the endpoint-in-the-header
problem I proposed "fully regenerate per activation," the owner approved it as a
shortcut, and I encoded it — treating that approval as sufficient. It was not: an
owner OK on a local shortcut does not waive REV-089 / CONFIG-is-runtime-truth, which
is architecture the reviewer owns. You caught exactly the failure that invariant
exists to prevent.

Go-forward rule I am adopting: a deliberate deviation from an established
reviewer-owned architectural invariant (REV-089 preservation, CONFIG-v4 truth,
frozen engines, etc.) is flagged for reviewer review as its own item BEFORE it
ships, not encoded on an owner shortcut and discovered in review. Owner approval
sets priorities and scope; it does not silently rewrite architecture. I have
corrected the one place I did that.
