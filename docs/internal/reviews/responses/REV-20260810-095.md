# Response to REV-20260810-095

## F1 — IMPLEMENTED

### Analysis

Accepted. The finding is right that there is no production defect in `9074fe5`
and right that the evidence stopped one boundary short. Section 53 tested
`cmd_add_client()` (validation/storage) and then unit-tested
`apply_client_profile_choice()` directly; nothing crossed `cmd_activate_client()`,
so nothing proved the property Gate 4 actually exposes — that the stored
CREATE-time choice is what *sources the candidate CONFIG* on a real first
activation. The REV-089/090 lesson (helper-level green while the caller still
mishandles the profile) is exactly the risk, so the discriminating test must run
the caller.

### Implemented change

`test/zfsbackup/run.sh` section 54, crossing the real `cmd_activate_client()`
first-activation path, built on section 50's fixture/stub strategy (peerstate +
keys + `SERVER_CONF=no-such-server` + a `$SNAPGET` stub that copies the working
copy out). One deliberate difference makes it safe on a host that *has* crontab:
the stub captures the workfile and then exits non-zero, so
`cmd_activate_client()` dies at the "dry-run failed — not installing" gate,
**before** the grant check and `atomic_replace_and_install`. The candidate
CONFIG is fully rendered by then; nothing real is touched.

The key to the proof: the environment forces `PROFILE_ACTIVE=default`. The only
path by which the alternate profile can reach the rendered config is the
record's `PROFILE` field threaded through `apply_client_profile_choice()` on
first activation — the wiring under test. The alternate profile differs from
`default` only by an observable, safe-to-render marker (the hourly
`send_schedule` is minute 7, not minute 1), so the assertion tests ALT's
*content*, not merely its namespace string.

Four assertions:

1. a first-activation record carrying `PROFILE=alt` produces a candidate CONFIG
   whose sections use `profile__alt__*` templates and carry ALT's minute-7
   cadence, with no `profile__default__` present;
2. that ALT cadence reaches the **rendered cron** through the real `gen-cron.sh`
   (a send line at `^7 * * * *`), not just the config text — the
   REV-20260809-082 V1 "the text looks right" boundary is crossed;
3. the omitted-choice path (`PROFILE=default`, what add-client stores when
   `--profile` is absent) still yields the default semantics (minute 1, default
   namespace, no ALT leak);
4. re-activation (`STATE=active`, `PROFILE=alt` on record) still ignores the
   stored profile — the one-way handoff REV-089 drew, now re-checked at the
   caller that reads the field.

Negative control (finding point 7): with `apply_client_profile_choice()`
neutered inside the run's subshell, the same `PROFILE=alt` record has **no**
effect — the candidate falls back to the environment's default profile. If the
control still carried ALT, the positive assertions would be proving nothing.

No production code changed; the finding requested none.
