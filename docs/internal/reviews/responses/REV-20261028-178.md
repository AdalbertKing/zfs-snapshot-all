# Response to REV-20261028-178

## F1 — IMPLEMENTED

### Analysis

Accepted as reported. `need_key()` stored the one loaded root in `KEYLOADED`; a failed
`mount_ro` in step 4 went back to the snapshot menu without unloading, and a later
`load-key` on another root overwrote the only cleanup handle.

### Implemented change

`tui/browse.sh`:

- `KEYLOADED` is a newline-separated list of every encryption root this process loaded;
  `need_key()` appends to it instead of overwriting.
- `unload_key()` tries every root on the list. Each failure stays on the list, adds a
  `RESIDUE` line naming the root and `zfs unload-key <root>`, and makes the function return 1.
  Cleanup at EXIT therefore retries what is left and the script exits nonzero, as before for
  any residue.
- Step 4: after a failed read-only mount the key of that attempt is unloaded at once; if that
  fails, a window shows what remains.
- `need_key()` loads only a root whose `keystatus` is `unavailable`, so a key loaded before
  the process started never reaches the list and is never unloaded.

Read-only mounting, the `snapdev`/mapper cleanup order (`unmount_all; restore_snapdev;
unload_key`) and "residue never returns 0" are unchanged.
