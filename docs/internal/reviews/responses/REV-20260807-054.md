# Response to REV-20260807-054 — recursion model

Implemented in `ba24c8b` (generator, validator, round-trip, tests) and
`121892f` (draft UX, live migration proof). Migration option **(a) hard
reject** taken as directed.

## Acceptance conditions

### 1. One representation only — IMPLEMENTED

`-r`/`-R` in a `[dataset:]`'s `flags` is fatal. The check is getopts-equivalent
rather than a token comparison, as the condition requires.

`flags_opt_letters()` walks characters and consults the engines' own optstrings
for which letters take an argument (the union across snapsend and snapget: a
letter that takes one in *either* must consume one here, or a pull-side flags
string would be mis-scanned by a push-side reading of it).

Refused: `-R`, `-r`, `-Rv 3`, `-rZ`. Not refused, correctly: `-m R-daily_` and
`-v R` — an option *argument* is not an option, and treating it as one would be
wrong in the opposite direction.

`lint_flags` now reads letters rather than whole tokens throughout, which
incidentally closes the same bundling hole for `-f` and `-n`. That was not
asked for; it fell out of doing the scan properly, and leaving the old
token loop beside a correct scanner would have been two parsers to keep
in agreement.

### 2. Both transfer directions — IMPLEMENTED

`test/fixtures/recursive.conf` carries `flat` and `atomic` on push (`dst`) and
on pull (`src`) alike, and the golden pins `snapget.sh ... -R` /
`snapget.sh ... -r` explicitly.

### 3. All three surfaces move together — IMPLEMENTED

The same golden asserts, per value, the transfer line, the inline prune line
and the monitor line. It also pins two things the condition implies but does
not say:

- a recursive dataset never merges into a non-recursive prune or monitor line.
  `recursive` is in the inline-prune group key as well as the monitor's,
  because a `delsnaps` line carries `-R` for every dataset it names or for
  none — merging would silently give one member the wrong scope;
- `recursive = no` written out reads exactly like an absent field, not like a
  third state. `tank/single` and `tank/explicitno` merge.

Recursion is never *inferred* from a shared parent. A list of separately named
datasets stays a list.

### 4. Round-trip is lossless — IMPLEMENTED

`cron2conf.sh` gained `split_recursion()`: it recovers `recursive =
flat|atomic` onto the **`[dataset:]` section** (not the template — the field is
section-scoped) and strips the engine flag from the reconstructed `flags`.

It shipped in the same commit as the generator rather than after it. Without
it the tool emits `flags = -R`, which the new generator refuses, so a
split would have left `main` with a broken round-trip between two commits.

Existing separate `[prune:]` jobs are untouched: no merge, no deletion. The
`recursive-pve1-shape` fixture pins a recursive `[dataset:]` and an independent
recursive `[prune:]` coexisting.

Two refusals added rather than guesses: a bundled `-Rv` form (hand-edited
crontabs can hold one, and handing back a config gen-cron will reject is worse
than saying so), and two tiers of one dataset disagreeing about recursion —
unrepresentable in a section-scoped field, and a real defect in the source
crontab.

### 5. Draft UX — IMPLEMENTED

`--draft-config` emitted prose telling the operator that "one `-R` in flags
covers the subtree". That is now advice to write a rejected config. It emits
the commented typed field instead, on both the push and pull branch, and says
what `flat` and `atomic` mean.

**Scope limit, stated rather than implied:** the new checks (`draftscope`
D1/D2) are a *static read of deploy.sh*, not an execution of `--draft-config`.
That path needs a real pairing — saved peer, key, manifest — which is why it
has no behavioural suite today at all. They prove the generator no longer tells
anyone to write `flags = -R`. They do not prove the emitted file parses.

### 6. No engine campaign — CONFIRMED

No engine file changed. `snapsend.sh`, `snapget.sh`, `delsnaps.sh` and
`check-snap-age.sh` are untouched.

## The migration, proved live

`192.168.11.11` is the one managed config in the fleet using legacy dataset
recursion. On the host, against a throwaway clone at `origin/main`:

| | |
|---|---|
| A) old gen-cron + old config | reproduces the installed managed block |
| B) new gen-cron + migrated config | **byte-identical to (A)** |
| C) new gen-cron + unmigrated config | refused, naming `recursive = atomic` |

Migration was exactly `flags = -r -v 3` → `recursive = atomic` + `flags = -v 3`.
Nothing was installed. The live config and crontab were md5-checked unchanged
afterwards and the clone removed.

A first attempt compared (A) and (B) against the installed crontab directly and
produced a large diff. It was environmental — the account's `cron_log` and
notify paths did not resolve the same way over ssh — and the tell was that the
**baseline differed too**. Recording it because a comparison whose control
fails proves nothing, and re-running it quietly until it looked clean would
have been the failure this project keeps naming.

The shape is now permanent as `test/fixtures/recursive-pve1-shape.*`.

## Remaining risk

- **`cron2conf.sh` cannot parse `snapget.sh` lines at all** ("unrecognized job
  line"), so the pull half of the round-trip is untestable. Pre-existing, found
  while building the fixture, not caused here. Filed rather than widened into
  this change.
- The fleet migration is **not done**: `192.168.11.11` still holds the
  unmigrated config and will refuse the next `gen-cron.sh` run against it.

  Checked rather than assumed, on all four hosts: the only scheduled job
  touching this software is the hourly `git pull --ff-only` (plus
  `update-control.sh --self-update`). **Nothing regenerates a crontab on a
  schedule**, so no host changes behaviour when v4.27 lands — the installed
  blocks keep running, and the refusal appears only when a human next runs
  `gen-cron.sh` or `zfs-backup.sh activate-client` on that host. That is the
  intended loud stop, at the moment someone is present to read it. Migrating a
  production config is the owner's call, so it has not been done here; the
  one-line edit is recorded in the fixture header.
- `--draft-config` remains behaviourally untested, as above.
