# Response to REV-20260806-051

## F1 — `.` and `..` passed the identity check — IMPLEMENTED

Accepted; the analysis is exactly right and the impact is worse than a
missing refusal. Both labels contain only permitted characters, and
`"$RELATIONSHIPS_DIR/.."` resolves to a directory that normally exists — so
the unknown-relationship guard **succeeded** for an identity that is not a
relationship, and with no `disabled` file in that parent the gate fell
through to ACTIVE and executed `SSH_ORIGINAL_COMMAND`.

That is a fail-open in the one boundary whose entire purpose is to fail
closed, reachable from a stale, hand-edited or migrated `authorized_keys`
line.

### Reproduced before fixing

Against the reviewed head `4fecbc2`, with a state root containing an
ordinary relationship directory:

```text
LABEL=".."  SSH_ORIGINAL_COMMAND="touch <root>/PROOF"
-> rc=0, and <root>/PROOF was created
```

The gate ran the caller's command. Two characters.

### Implemented change (`8dd0c8a`)

Both sides now reject the dot segments before any path is constructed or any
forced-command line is rendered:

- **the gate** carries the rule inline. Deliberately duplicated rather than
  shared, for the reason the review itself gives: the gate is deployed
  standalone outside the checkout and must not depend on sourcing a file that
  could be missing or rolled back underneath it.
- **`deploy.sh`** gains `pair_label_valid`, called by `install_pair_gate` and
  `write_gated_key_line`.

The grammar refuses the empty string, `.`, `..`, and anything outside
`[A-Za-z0-9._-]` — which also excludes `/`. Every real label in this estate
(`pve1`, `site.a`, `a_b-1`, `10.0.0.9`) is unaffected.
