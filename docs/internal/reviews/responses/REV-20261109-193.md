# Response to REV-20261109-193

## F1 — IMPLEMENTED

### Analysis

Accepted. In `cmd_run_replicas`, with `--device`, `ins_known` became 1 only when `blkid`
returned a LABEL or a UUID. When both were empty, the ownership filter
(`oninsert=1 && ins_known=1`) was skipped and every `#on-insert` line ran. The 1.0.17
CHANGELOG described this fallback as "as before"; it contradicts the promise of the same
release that an unrelated disk starts nothing.

A partial identity was already safe and stays as it is:

- UUID only: a replica with a GUID list runs on a matching GUID;
- a replica that selects by pool name, with an empty LABEL: no match, not run;
- LABEL only, against a GUID list: no match, not run.

### Implemented change

`zfs-backup.sh`, `cmd_run_replicas`, the `--device` branch (commit d0a40f51). After the
LABEL/UUID probes: if both are empty, one log line ("... blkid read neither its pool name
nor its GUID -- running no replica ...") and `return 0`. That means no media gate, no
zfs-job record and no alert. The other paths are unchanged:

- `run-replicas` without `--device` (by hand, `--on-insert` without a device, or by
  schedule);
- the device-vanished and not-a-ZFS-member exits;
- GUID and pool-name matching;
- the `--collect` udev rule.

Docs: `docs/pl/WDROZENIE-KOLEKTOR-DWA-ZRODLA-REPLIKA.md`,
`docs/en/DEPLOYMENT-COLLECTOR-TWO-SOURCES-REPLICA.md` and `CHANGELOG.md` `[Unreleased]`.
