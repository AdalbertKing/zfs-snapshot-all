# Response to REV-20260809-087

## F1 — IMPLEMENTED

ACCEPTED. This is the same defect I found and fixed independently during
the REV-082/083/085/086 live campaign, already landed in
`67415a5795ad3d1cb659e3017c1485bc99b59a61` before this REV was filed. Per
the reviewer's own pre-inspection, no second fix is needed — this response
exists to give the defect its own protocol record rather than leaving it
only described inside REV-086's evidence.

`read_server_conf()` unconditionally resets `CRON_CONFIG=""` before
optionally refilling it from `$SERVER_CONF`. Both `cmd_remove_client()` and
`cmd_activate_client()` source the client's own record first — which
carries `CRON_CONFIG` from a prior activation — then call
`read_server_conf()` after. On a host with no `server.conf` (metropolis
pve1's exact shape), that reset was never undone, silently erasing the
relationship's authoritative recorded config path.

### Fix

Both functions now capture their own `CRON_CONFIG` immediately after
sourcing the client record, call `read_server_conf()` as before, then
restore the captured value only when it was non-empty:

```bash
. "$cpath"
local recorded_cron_config="${CRON_CONFIG:-}"
...
read_server_conf
[ -n "$recorded_cron_config" ] && CRON_CONFIG="$recorded_cron_config"
```

`read_server_conf()`'s own contract is unchanged for callers that
genuinely want the server default (`setup-server`, fresh `add-client`),
which never pre-load a client's `CRON_CONFIG` before calling it.

## Live corroboration

The removal half of this defect was hit directly, not just constructed:
during the live campaign's teardown of relationship `v3proofA`,
`remove-client` printed `"no managed dataset list on file (client was never
activated?)"` for a client whose record plainly showed
`STATE=active`/`MANAGED_DATASETS=...`. Teardown was completed by hand for
that session (documented in the REV-086 response); this fix is what makes
the automated path work correctly going forward.

The reactivation half was not separately hit live in this campaign (no
relationship was reactivated after an endpoint switch during it) — its
evidence is the targeted local regression above, which discriminates the
exact defect shape via a server.conf that does not exist and a recorded
`CRON_CONFIG` distinct from any recomputed default.
