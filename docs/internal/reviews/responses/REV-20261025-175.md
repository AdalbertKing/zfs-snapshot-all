# Response to REV-20261025-175

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `cmd_add_source()` took the host from `PEER_HOST` and the port
from `ACTIVE_ENDPOINT`. The audit found the same split in `cmd_remove_source()` and
`cmd_delete_relation()`; there it also sent the source-side steps (`--commit-scope`,
`--leave`, the `--check-source` probe) to the old host on the new port.

### Planned or implemented change

- New `management_host_port()` in `zfs-backup.sh`. It returns host and port from one
  record shape:
  - a set `ACTIVE_ENDPOINT` goes through the existing `active_endpoint_host_port()`
    (new `host:port` shape and legacy named slot alike);
  - no `ACTIVE_ENDPOINT` (a record that was never activated) gives `PEER_HOST`, port 22;
  - a legacy slot that names no host gives rc 1.
- `cmd_add_source()` and `cmd_remove_source()` refuse when the endpoint has no host,
  before any SSH. Every `rux_root_ssh` call uses the resolved host and port, and the
  plan line shows `endpoint host:port`.
- `cmd_delete_relation()` uses the same route. When the endpoint has no host, the
  source's half is skipped and the plan prints the manual `deploy.sh --leave` command,
  so a broken record can still be removed.
- `PEER_HOST` stays the pairing identity. Labels, the source-scope file name and the
  "other relationships still use this peer" check do not change.
