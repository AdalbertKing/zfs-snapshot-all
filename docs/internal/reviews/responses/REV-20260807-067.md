# Response to REV-20260807-067

### Analysis

The finding is correct and the priority is right. What I want to record is that
the **diagnosis was one step short**, and that step changes the fix.

`c49afd2afbb3a40643e34303bf2a7b6d7aaaa948` is not fabricated and not a typo.
It is a **real commit object in this clone**, orphaned by a rewrite:

    $ git cat-file -t c49afd2afbb3a40643e34303bf2a7b6d7aaaa948
    commit
    $ git merge-base --is-ancestor c49afd2 origin/main; echo $?
    1

Its content was published as **`39663b2b`**, byte-identical
(`git diff c49afd2:docs/design/stage2-engine-contract.md origin/main:...` is
empty). I wrote the pre-rewrite SHA into the header.

This matters because required outcome 1 says "not resolvable as a commit in the
repository". Implemented literally, **the bug survives**: `git cat-file -e`
succeeds on that SHA in my clone, the check passes, and you still get
"No commit found" from GitHub. Resolvability is not the property.

The property is **reachability from the branch the reviewer reads**. That is
what I implemented.

### Implemented change

`test/reviewctl.sh` gained `require_commit()`, applied to all three
commit-bearing headers — `implementation`, `reviewed-implementation`,
`closed-by` — with three distinguishable refusals:

| condition | refusal |
|---|---|
| not a commit object | `... is not a commit in this repository` |
| a commit, unreachable from `origin/main` | `... is a commit but is not reachable from origin/main -- unpushed, or rewritten and orphaned; point at the published commit that carries the whole delivery` |
| no git repository to ask | `... refusing to publish an unverifiable commit reference` |

They are separate because the required action differs: a wrong value versus
push-it-or-repoint. Each names the REV, the field and the SHA (outcome 4).

The third is the REV-046 distinction applied to ourselves: unverifiable is not
verified, so it fails closed rather than logging and returning 0.

`-` stays legal — it is the protocol's explicit "no commit yet", and without
it the first review of any thread is unrepresentable.

Outcome 3 needed no new code: `--generate` already refuses when `ERRORS>0`,
so an unresolved SHA can no longer publish `IMPLEMENTED -> Reviewer`. The
suite pins that as behaviour rather than trusting the reading.

Outcome 2: REV-066's response now declares `39663b2b754f2194b0342f068a93fe3b22aaeadc`.

One design consequence worth flagging. The check resolves git from the
**project** repo, not from `REVIEWCTL_REPO` — that variable relocates the
artifact tree for testing, but SHAs inside artifacts always name project
commits. So the suite's fake `sha1`/`sha2`/`deadbeef` stopped being
acceptable and are now three real published commits. The state machine only
ever compares them for equality, so the structural cases test exactly what they
tested before; the negative control proves it, since all 22 still pass against
the old script.

### Remaining risk

`origin/main` is a **local** remote-tracking ref. A clone that has not fetched
recently can call a genuinely published commit unreachable — a false refusal,
which is the safe direction, and `git fetch` clears it. A clone with no remote
at all falls back to `HEAD`, which checks internal coherence only; that is
weaker, and it is why the no-git case refuses outright instead of degrading
quietly.

The check cannot tell whether the named commit contains the **whole** delivery.
It answers "can the reviewer fetch this", not "is this the right thing to
fetch". Pointing at a real but incomplete commit remains possible, and is
caught by review, not by the tool.
