# Response to REV-20260920-145

## F1 — IMPLEMENTED

### Analysis

Accepted in full, including the severity. The finding is correct and it is the
same defect I had just written an error-log entry about: PR #403 added a call to
`install_quiesce_grant` and did not look at what it returned. `deploy.sh` runs
under `set -uo pipefail`, not `set -e`, so the failure was simply walked past.

What makes it P2 rather than cosmetic is the combination the reviewer names.
`install_quiesce_grant` is transactional and **restores the previous whitelist**
when it fails — so after a failed update the OLD, WIDER freeze permission is the
one in force, while the `zfs unallow` loop above has already narrowed the
replication grant. That is precisely the drift PR #403 existed to remove, now
with three aggravations: the durable `PEER_JOIN_GRANTED_DATASETS` had already
been rewritten to the new list, the scope hash had been written, and the command
returned 0. Nothing was left to retry from and nothing said anything was wrong.

Reproduced against merged `main` `7dff3038` with the shipped function, stubs for
`zfs`/`id`/the installer, and the installer forced to fail:

```text
rc=0
PEER_JOIN_GRANTED_DATASETS="pool/a"
hash: WRITTEN
>>> commit-scope complete for 'peer': 1 dataset(s) granted to backup, 1 revoked
```

### Implemented change

`deploy.sh`. Both branches now check the status:

```sh
install_quiesce_grant "$account" "${still_granted[*]}" || quiesce_update_failed "$account" "$label"
```

`quiesce_update_failed()` is a new function rather than an inline `die` because
what it does is a **decision**, not a message, and both branches need the same
one. By the time it runs, two facts are already true and cannot be wished away:
the replication grant has been narrowed, and the failed installer has put the
previous (wider) whitelist back. Only two coherent states remain — undo the
revoke, or remove the freeze permission — and it takes the second, which is
acceptance criterion 4's own second option:

1. it says plainly what happened and that the restored whitelist is wider than
   the replication grant that accompanies it;
2. it calls `revoke_quiesce_grant` so the freeze permission is never left wider,
   and names the one command that restores it
   (`--commit-scope=LABEL --allow-quiesce`); if that revoke *also* fails it says
   so and hands the operator the exact manual command instead of pretending;
3. it `die`s — **before** the manifest rewrite and **before** the hash write. So
   the prior `PEER_JOIN_GRANTED_DATASETS` stays, no new hash is written, neither
   "whitelist now matches this scope exactly" nor "commit-scope complete" is
   printed, and re-running the same `--commit-scope` retries from a record that
   is still true. Criteria 1, 2 and 3.

The successful path, the no-grant path and the explicit `--allow-quiesce` path
are unchanged; the guard is on the failure, not on caution.

### Remaining risk

Named rather than hidden. (1) The chosen boundary takes the freeze permission
away on failure; an operator who never reads the output could be left without
remote quiesce until the retry, which is why the run says so twice and prints
the restoring command. (2) `revoke_quiesce_grant` can itself fail (a read-only
`/etc`, for instance); that case is reported with the manual command, but the
host is then genuinely inconsistent until a human acts — there is no third state
the process can reach on its own. (3) The live half of this path was not
re-measured on a host: the injected failure is a stub, because making the real
installer fail on pve9b would mean breaking `/etc/sudoers.d` on a live machine.
The success path of the same code was measured live on pve9b earlier today (PR
#403's evidence).

## F1 follow-up (reviewer, 2026-09-26: criteria 6 and 7) — IMPLEMENTED

### Analysis

Accepted. The reviewer's reading is exact. `revoke_quiesce_grant()` counted
only **successful** removals. When both `rm`s failed, `removed` stayed 0, the
function printed "no quiesce grant found … nothing to revoke" and returned 0
while both files still stood. So `quiesce_update_failed()` always took its
first branch ("the freeze permission was taken away entirely"). Its second
branch, the one with the manual emergency command, could not be reached by the
very failure it was written for. The test I shipped in `773b955d` stubbed
`revoke_quiesce_grant()` to return 0, so it measured the caller and never
measured the function the caller depends on.

Reproduced **live** on pve9b at `main` `2702d89c`, with the reviewer's
discriminator. The account is a throwaway (`rev145test`), its sudoers file is a
single comment, and both files are made undeletable with `chattr +i`:

```text
!!! could not remove /etc/zfs-quiesce-allow/rev145test -- rev145test may still be able to quiesce guests here
!!! could not remove /etc/sudoers.d/zfs-quiesce-rev145test -- rev145test may still reach the helper through sudo
>>> no quiesce grant found for 'rev145test' on this host -- nothing to revoke
rc=0
```

### Implemented change

`deploy.sh`, `revoke_quiesce_grant()` only. The rollback/order boundary chosen
in the first round is unchanged: on a failed whitelist update the freeze
permission is taken away, and nothing durable is written. This round makes the
status of "taken away" true.

- Each managed file that existed is removed with `rm -f "$f" && [ ! -e "$f" ]`.
  If it is still there, the function warns as before and sets `stuck=1`.
- If nothing existed, the output is "nothing to revoke", rc=0, as before.
- If something existed and **nothing** could be removed, it prints "the quiesce
  grant for '<account>' is still in place -- remove the files named above by
  hand" and returns 1. "Nothing to revoke" is never printed in this case.
- If one half was removed and the other is stuck, the rest of the function runs
  as before (`visudo -c`, the shared-helper note) and it returns 1. Without one
  half, the helper already refuses the account. A file of the grant is still on
  disk, though, so the status says so.
- `--revoke-quiesce` already did `exit $?`, so it now exits nonzero in both
  failure cases.
- `quiesce_update_failed()` is unchanged. Its `else` branch ("could not be
  taken away either … `deploy.sh --revoke-quiesce=<account>`") is now the one
  that runs when the files stay, and `die` follows it as before.
