## A defect found AFTER this review's scope, in the code it accepts

`54c1ead`. Running the real remote-quiesce path on a real host exposed a bug that
every local suite had been passing over for days.

`thaw_all` runs from the EXIT trap. **In a trap handler, bash resolves a bare
`return` against the status the shell was exiting with, not against the last
command in the function.** So

```bash
gq_thaw() { ... sudo -n "$QHELPER" thaw "$1" >/dev/null 2>&1; return; }
```

returned 0 while sudo had exited 3, and the consequences chain exactly as
REV-006 F3 described — in the code written to fix F3:

- `thaw_all` took the success branch and logged `QLOG thawed VM 104`
- the id was dropped from the recovery list
- `on_exit` saw an empty file, deleted it and **killed the deadman**
- the run exited 0

Measured on pve0 with a wrapper logging every helper call: wrapper `exit 3`, run
`EXIT=0`, guest left `frozen`, nothing remaining that would ever thaw it.

**Why no suite caught it, and why the new guard is textual.** bash 5.1.4
(Debian 11 / PVE 7 — every real host here) reproduces this; bash 5.3.9 (the
development box) does not. Verified both ways with a minimal reproducer. The
existing err4 case ("a failed thaw fails the run (6)") therefore passed on the
BROKEN code locally and would keep passing. A behavioural test on this machine
cannot distinguish fixed from broken, so `test/quiesce` now asserts textually
that no bare `return` exists in the embedded script — it fails on the pre-fix
library and passes after. Every `return` there now carries its status explicitly.

So §1's "no longer fail-open in the reviewed paths" was true of the source text
and false of the behaviour on the hosts. It is now true of both, and verified on
the platform where it failed.

## F1 — final catch-up record can become stale — ACCEPTED, IMPLEMENTED

Correct on both counts, and the second example (same endpoint name, different
host) is the one that would have been hardest to notice afterwards.

`final-catchup` now records the transport it actually proved:

```
FINAL_CATCHUP_ENDPOINT=lan
FINAL_CATCHUP_HOST=192.168.11.11
FINAL_CATCHUP_PORT=22
FINAL_CATCHUP_EPOCH=1753...
FINAL_CATCHUP_AT="2026-07-31 15:12:03"
```

`set-endpoint` requires all three to match the endpoint being LEFT — name, host
and port — plus an age within `CATCHUP_MAX_AGE`, default **1800s (30 min)** as
recommended. `--allow-stale-catchup` overrides only the age, warns, and names
what it costs ("everything written since <time> will cross the slow link").
`--skip-final-catchup` is unchanged for the already-disconnected case.

Two additions beyond the letter of the requirement:

- **Moving an endpoint invalidates a catch-up recorded against it**, at the
  moment of the move rather than silently later, with a warning naming the old
  and new address.
- **A record with no `FINAL_CATCHUP_EPOCH` is refused rather than treated as
  fresh.** Configs written by the previous version have no epoch; defaulting a
  missing timestamp to "recent" would silently grandfather in exactly the stale
  state this finding is about.

Tests (7 new, `test/zfsbackup`): stale refuses and names the age; different host
refuses; different port refuses; a fresh catch-up against the exact endpoint
passes; the override proceeds with a warning; a legacy record without an epoch is
not treated as fresh; moving the LAN endpoint invalidates the record. The
pre-existing case that asserted the weaker "name matches" contract was updated
rather than worked around — that contract changed deliberately.

## F2 — grant installation is not transactional — ACCEPTED, IMPLEMENTED

Correct. The old order created the helper and whitelist first and only then
discovered that sudo was missing or the rule would not validate.

`install_quiesce_grant` is now staged:

1. dependencies resolved first (visudo located, `sudo` package installed if
   absent) — before anything is created;
2. whitelist and sudoers rule written to temporary files;
3. the rule validated with `visudo -cf` while still in `/tmp`;
4. one short install phase;
5. on ANY failure, every artifact **this run** created is removed and the
   rollback is reported by name.

The shared helper is handled as the review allows: if this run installed it and
no account holds a grant after rollback, it is removed; if another account still
has one, it stays and the message says so explicitly rather than leaving the
operator to work out which artifacts are shared.

Tests (6 new, `test/quiescehelper`), each injecting a failure at one stage and
asserting **zero** orphaned per-account artifacts: clean run installs both; a
failed `sudo` install leaves nothing; a rejected sudoers rule leaves no
whitelist; a failed whitelist install rolls back; a failed rule install rolls the
whitelist back too (the case the old code got wrong); a retry after a failure
succeeds cleanly.

Two notes on test mechanism, since they affect how much the results are worth:
the dependency-failure case removes the `visudo`/`sudo` stubs entirely, because
with a stub on PATH that branch is never reached and the case would pass while
testing nothing; and the `install` stub strips `-o`/`-g` because this box has no
`root` user, which would otherwise fail for reasons unrelated to the test.

## Addendum, 2026-07-31 evening: two more defects in `writers`, both from live use

Running the deferred vsql2 verification turned up two defects in the `writers`
verb. Neither was in this review's scope; both were in code it accepted.

### 1. The verb rendered a health verdict that the evidence does not support

The header of `zfs-quiesce-helper.sh` claimed a `Failed` SqlServerWriter proves
the snapshot was not application-consistent, and the awk emitted `class=FAILED`
plus a `failed=N` summary on that basis. **The claim is wrong.**

Measured on vsql2 (VM 100, pve1): the writer read `[1] Stable` immediately before
a manual `qm guest cmd 100 fsfreeze-freeze` + `fsfreeze-thaw`, and `[10] Failed /
Timed out` immediately after — **same writer instance id**, so nothing crashed or
re-registered; the successful freeze itself put it there. A freeze-only requester
(qemu-ga) drives SQL through `BACKUP DATABASE` to a VDI device and calls
AbortBackup at thaw; SQL logs 3013/3271/4035 with Windows error 995
(`ERROR_OPERATION_ABORTED`) and the writer ends failed. That is the aftermath of
success.

Application event 24583, grouped over seven days, shows SQL engaged at **every**
quiesce including the nightly `00:12` job, both before and after an unrelated
registry repair earlier that day. So the earlier conclusion that nightly backups
were not application-consistent is **retracted** — it was built on reading writer
state as a verdict.

Consequence: a caller alerting on `class=FAILED` would have fired after every
successful backup. The verb now reports the state machine (`stable` /
`transient` / `failed`, lowercase) and ships a `WRITERS-NOTE` line with the data
saying it is not a backup verdict. Corroborating datapoint: metropolis pve1
VM 106, an English guest nobody froze, currently reads `failed=1 transient=2`.

Honest limit: whether SQL's participation yields a **recoverable** image is a
different question and only a restore test answers it. Not done.

### 2. The parser was locale-dependent and failed silently

`vssadmin` is translated. On VM 106 (pve1, Polish Windows) it prints
`Nazwa modulu zapisujacego:` / `Stan: [1] Stabilne` / `Ostatni blad:`. The parser
keyed on `/^Writer name:/`, `/State:/`, `/Last error:/` and matched nothing —
while `vssadmin` had succeeded, so the empty-output guard did not fire either.
Result: `total=0`, which reads as "this guest has no VSS writers". No Windows
install has none.

Fixed by parsing structure and numbers instead of labels: the writer name is the
only single-quoted string in its block, the state line always carries `[N]`, and
`N` is `VSS_WRITER_STATE` (1 stable, 2–5 transient, ≥6 failed). Labels ahead of
the first colon are stripped so values read alike in any language. A reply that
parses to nothing now says `WRITERS-UNREADABLE` instead of reporting an empty
but healthy-looking set.

### 3. New verb `sqlfreeze` — the signal `writers` could not give (owner-requested)

Removing the writer-state verdict left a real hole: nothing could tell whether a
Windows application quiesce actually happened. Investigating vsql2 turned up a
signal that can, and it is a positive one rather than an inference from an error.

SQL Server logs, per database, on every snapshot-style backup:

```
3197  "I/O is frozen on database <db>."
3198  "I/O was resumed on database <db>."
```

Measured on vsql2, grouped over 20 hours: **both ids appear at every single
quiesce** — the 2-hourly pvesr replication runs, the nightly `snapsend -q agent`
job at 00:12, and the manual test at 16:48 — perfectly balanced, 227/227 on
`MSSQLSERVER` and 187/187 on `MSSQL$SQL2019`. A balanced pair is the documented
proof that SQL flushed and held its I/O for the snapshot.

This also settles the original question that started the investigation: the
nightly backup of vsql2 **is** application-consistent for SQL Server.

> **Corrected by REV-20260731-010 §2, and the correction is right.** That
> sentence claims more than the evidence carries. `sqlfreeze` reads a WINDOW, and
> nothing in an event ties it to a caller — on vsql2, pvesr, snapsend and a human
> all quiesce the same guest, so events from a neighbouring operation inside the
> window read the same way. What is actually supported: SQL participated in
> freeze/resume repeatedly across that period, including at 00:12, with no
> unbalanced pair anywhere. What is not: that the 00:12 events belong to the
> snapsend run rather than to something else running near it. Correlating a
> specific run needs the read to happen inside the same operation as the freeze
> (highest `EventRecordID` first, then freeze/snapshot/thaw, then read only what
> is newer). See the response to REV-010.

`sqlfreeze <id> [seconds]` reports per instance and summarises with
`verdict=engaged` / `unbalanced` / `no-freeze-seen`, plus a `SQLFREEZE-NOTE`
saying what it does not prove (that the snapshot restores). Matching is on the
numeric event ids — the `writers` locale bug above is exactly why.

Boundary notes, since this verb is new privileged surface:

- The command remains a CONSTANT in the root-owned file. The look-back window is
  the only caller-influenced part; it is validated to digits only and bounded to
  1..86400 **before** interpolation, so it cannot become an argument, a flag or a
  second statement. Tests drive `abc`, `3600; whoami`, `-1`, empty and `99999`
  and require rc=2 for all five.
- An absent window defaults to 900; an **empty** one is refused (`${2-900}`, not
  `${2:-900}`) — an empty argument is nearly always an unset variable in the
  caller, and answering about a window nobody chose is the wrong kindness.
- `qm guest exec` on Windows joins argv back into a command line, so a
  multi-line `-Command` argument arrives as nothing at all ("A command must
  follow -Command"). The command is therefore one physical line, deliberately.
- When a guest is still working at the timeout, `qm` exits **0** with only a
  `pid` and no `out-data`. Reporting that as "nothing found" would be a false
  all-clear, so it fails (3) and says the guest never answered. This is not
  theoretical: on the Server 2008 guest here even `$PSVersionTable` exceeds a
  120s timeout, which makes every PowerShell-based verb unusable there.

Tests: 12 new in `test/quiescehelper` (balanced, unbalanced, none, timeout-pid,
window validation ×5, whitelist refusal, and that a refused call never reaches
the guest). Live on vsql2: `verdict=engaged frozen=414 resumed=414`, the 300s
window correctly `no-freeze-seen`, both rejections rc=2, default window 900s.

Not verified: no restore test. `engaged` proves SQL participated, not that the
image recovers.
