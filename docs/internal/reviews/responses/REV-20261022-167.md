# Response to REV-20261022-167

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. Verdict 3 in `cmd_import_relation()` compared each record's
`PEER_HOST` with the raw replayed `--host`. Since U62 that argument is the active
endpoint, which may be `HOST:PORT` or another address of the same peer. A second
mode-based relationship to a peer that is already covered therefore reached
`add-client`, `seed` and `activate`. This is the risk I left open in the
REV-166 response.

The export already carries the durable identity. `cmd_export_relation()` writes
the record's own `PEER_HOST` into `declarations`; only the replayed `--host` in
`argv` is replaced by the active endpoint.

### Planned or implemented change

- `peer_id` is read from `PEER_HOST` in the file's `declarations` object. JSON
  whitespace is allowed. The object holds only the `EXPORT_RELATION_MAP` fields,
  with `PEER_HOST` first: a host, a target dataset, a landing label, a recursion
  word, a mode, profile names, an account name and a bandwidth figure. None of
  those value sets admits a brace (ZFS dataset names and the validated host,
  label, profile and account names do not), so the `{[^}]*}` match cannot be cut
  short.
- Verdict 3 compares each record's `PEER_HOST` with `peer_id`, not with the
  transport endpoint. The refusal message names that identity.
- Fail closed: a mode-based file with a peer (`--host` present) but without a
  valid `PEER_HOST` (`endpoint_host_valid`) is refused before anything is
  called. Local mode-based files have no `--host` and no peer, so verdict 3 does
  not apply to them, as before.
- The REV-166 behaviour is unchanged. SSH probes use `peer_ep_host` and
  `peer_ep_port`, and the replayed `--host=HOST[:PORT]` reaches the creation
  paths as the file has it.
- The "already paired?" lookup (`prepaired`) used `peer_label` of the raw
  `--host`, which for `HOST:PORT` is a label no manifest has. It now uses
  `peer_ep_host`. That is the host the record `add-client` is about to write
  takes as its `PEER_HOST`, and the label `seed` looks the manifest up by.
  It is the same rule as the REV-166 probe.

### Remaining risk

Address aliases (a DNS name and an IP for the same host) are not canonicalised,
as the review scopes out. A peer re-paired under a different `PEER_HOST` is
therefore a different peer for this check.
