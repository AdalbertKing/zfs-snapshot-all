## F4 — IMPLEMENTED

### Analysis

Accepted. The two producer-status losses the review names were real for
local reads too: `check_one` read the snapshot list through
`done < <(zfs list ...)`, and the `-R` walk used the same construction. A
failed snapshot list after a successful existence probe therefore became "no
matching snapshot" and was judged by the dataset's age. A failed walk checked
no children and said nothing. The fix is the same for local and remote reads.

### Implemented change

`check-snap-age.sh` (v2.3 → v2.4), within the `authorizes-frozen` marker:

1. **Remote entries.** A dataset entry may be `[user@]host:dataset`. It is
   parsed by `delsnaps.sh`'s `parse_remote` rule (remote only when nothing
   before the `:` looks like a path). The five options are the same as in
   `delsnaps.sh`: `-p -k -c -K -O`. The ssh options are built the same way:
   `-k` pins with `StrictHostKeyChecking=yes`, otherwise `accept-new`;
   `-K`/`-O` go at the front, because OpenSSH keeps the first value. The run is
   non-interactive and bounded: `ssh -n`, `BatchMode=yes`,
   `ConnectTimeout=15`, `ServerAliveInterval=15`, `ServerAliveCountMax=4`,
   and a wall-clock `timeout -k 10 120` around each remote read when
   `timeout(1)` exists. Keepalive alone only notices a dead link, because sshd
   keeps answering while a zfs on the far side hangs. A timeout (124/137) is
   UNKNOWN "timed out".
   `zfs` is required only when a local entry exists, and `ssh` only when a
   remote one does.
2. **Validation before any read.** A remote host must be a plain host name and
   the user a plain account name. A remote dataset name must match
   `[A-Za-z0-9][A-Za-z0-9_.:/-]*`. Anything else is UNKNOWN before ssh starts,
   so no quote and no shell syntax reaches the far shell. The arguments are
   single-quoted there, and `--` precedes the dataset name, as in
   `delsnaps.sh`'s `run_zfs`. Received data is never evaluated.
3. **One read path, `zread`.** It covers existence, the snapshot list,
   creation and the `-R` walk, and runs on the entry's own host. There is no
   local fallback. It runs `zfs list` and `zfs get` only.
4. **Every status and shape is checked before use**, locally and remotely:
   - existence: non-zero means UNKNOWN. Exit 1 (zfs's own answer) is "does
     not exist". Every other status says why: 255 is ssh (connection,
     authentication, host key), 93 is the pair gate refusing, 124/137 is a
     timeout, 127 means zfs was not found on that host, anything else is the
     zfs exit status. An answer other than the dataset name is UNKNOWN;
   - snapshot list: read whole, then its status is checked. A failure is
     UNKNOWN "snapshot list could not be read", also when lines were printed
     before the failure. A line that is not `<dataset>@…` is UNKNOWN, not
     trusted;
   - creation: the existing numeric validation, now on the right host;
   - `-R` walk: read whole and its status checked. A failure is UNKNOWN
     "descendants could not be listed; none of them was checked". A line
     that is neither the root nor under it is UNKNOWN.
5. **Unchanged:** the local CLI and its output for successful reads, the
   pause wording, `-x`, the thresholds, the no-match dataset-age rule (now
   only after successful reads), the container leniency under `-R`, and the
   severity order CRITICAL > UNKNOWN > WARNING > OK. Every UNKNOWN is still
   printed when CRITICAL decides the exit status. Status lines name a remote
   dataset with its `user@host:` prefix.

`gen-cron.sh` (not frozen):

6. A `[prune:user@host:dataset]` section with `monitor_warn`/`monitor_crit` is
   no longer refused. Its monitor line carries the section's `ssh_flags`, the
   same string its `delsnaps.sh` prune line already carries. `lint_ssh_flags`
   restricts the OPTIONS to `-p/-k/-c/-K/-O`; it does not validate their
   values, which is the same exposure the prune line has had and is not
   widened here. A local scope's `ssh_flags` only draw a warning and are not
   passed to its monitor, so a local line is byte-identical to before.
7. **The monitor group key includes the ssh identity and the remote host**
   (the review: "Current MONITOR_GROUPS key has no SSH field"). Two remote
   scopes with a different key, alias or host never share a line.
8. The negative case `prune-remote-monitor` (the old refusal) becomes a golden
   case with three remote scopes. Two on hostA with one identity give ONE
   line. One on hostB with another identity gives its OWN line.

Not changed: `lib-zfs-snap.sh`, the engines, the pair gate and its grants. The
gate is the existing active/disabled gate. It passes `zfs list`/`zfs get` while
active, and nothing here widens it. `zfs-backup.sh`'s remote source retention
still drops monitor fields from a remote source template. Wiring the monitor
into a `snaponly` relationship is round 1.

### Remaining risk

- The gate passes active read commands through. It is not a per-command
  sandbox, as the review notes, and this change does not make it one.
- The wall-clock bound needs `timeout(1)`, which coreutils provides on every
  supported Linux host. Without it the read relies on ssh keepalive alone.
- `ssh_flags` values are not validated by the lint (see item 6). This is
  unchanged from the prune line, and it is the operator's own config.
