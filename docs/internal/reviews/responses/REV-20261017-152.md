## F1 — IMPLEMENTED (round 1)

### Analysis

Accepted as written. The mode is a fact of the record, never an inference
from an empty target, and every path that assumes a collector-side copy must
refuse it or not apply.

### Implemented change

- `add-client --snaponly --host=H --datasets=DS[,DS]` and the facade
  `--source=H:DS --mode=snaponly` write `RUX_MODE=snaponly` (`lib-record.sh`
  already allowed the field; `MANAGED_SOURCES` was added to the client
  allow-list). Records without `RUX_MODE` keep their old meaning.
- `add-client --snaponly` refuses `--target` given at all (an empty
  `--target=` included), `--mode=`, a missing `--datasets`, and
  `--passive/--raw/--bandwidth/--exclude-*`. `DEFAULT_TARGET` is not applied.
  `activate_snaponly` refuses a snaponly record that names a target.
- Lifecycle: `add-client` -> `--join` on the source -> `verify-endpoint`
  (`snapget.sh -n -s`, read-only) -> `activate-client` (`--plan` previews).
  `seed` refuses. The facade and `cmd_activate` skip the seed for snaponly.
- Refused by name, before anything changes: `seed`, `restore`,
  `edit-relation`, `add-source`, `remove-source`, `set-tiers`,
  `export-relation`, `import-relation` (a file declaring snaponly),
  `delete-relation --destroy-copies`. `snapget_local_base` dies for snaponly
  instead of building `<target>/<label>` from an empty target.
- Pairing uses the sync package shape (`--mode=sync --peer-requested=DS`),
  the only shape with no target on either side; measured, `deploy.sh --pair`
  and `--join` both refuse a package without a target otherwise. The record
  keeps `RUX_MODE=snaponly`; the pairing's "sync" only means "no target root".
- Removal: `remove-client`/`delete-relation` remove the relationship's
  `[snaponly:]`/`[prune:]` sections and templates by their marker
  (`snaponly_strip`) and its cron lines; the source dataset and its snapshots
  are not touched. The delete plan says "copies: none".
- Status: its own text view; `status --json` reports `mode: snaponly`.
- Activation writes the record (`STATE=active`, `MANAGED_SOURCES`, empty
  `MANAGED_DATASETS`) only after the atomic install succeeded; every refusal
  before that leaves the record in `endpoint_verified`.

### Evidence

- `test/zfsbackup --section snaponly`: the `add-client --snaponly` refusals
  (`--target=` empty included, `--mode`, missing `--datasets`) with no record
  created; `snaponly_refuse` for restore, edit-relation, add-source,
  export-relation and set-tiers on a snaponly record, and the same verbs
  passing for a copy record; `snapget_local_base` refusing.
- Legacy backup/sync/local behaviour: the whole CI battery (50 checks) was
  green on PR #592 and PR #596 exact heads, unchanged suites included.
- Live (F3 below): add-client -> join -> verify-endpoint -> activate ->
  status -> delete-relation on pve9 -> pve10; the record and crontab after
  removal are as before.

### Remaining gap (stated, not hidden)

- No test interrupts an activation between the install and the record write;
  the order (install first, record after, every refusal before the install)
  is the evidence.
- The `seed` refusal for snaponly has no dedicated test (the other refused
  verbs do).

Changing a snaponly relationship in place (edit, add-source, set-tiers) and
export/import replay are REFUSED, not implemented. The relationship is
deleted and created again. An unknown `RUX_MODE` value is not refused by the
record loader (it was not before either); the snaponly paths test for the
exact value.

## F2 — IMPLEMENTED (round 1)

### Implemented change

- `gen-cron.sh` section kind `[snaponly:<[user@]host:dataset>]`: the mode is
  the section kind, carried into `SNAPONLY_ENTITIES`, never grouped with a
  pull (no destination to group by) and emitted by its own `emit_snaponly`:
  `snapget.sh -s -m "<prefix>" [-R|-r] [-q ...] <ssh_flags> -L <pair_label>
  "<scope>"`. No destination argument, no transfer flag.
- Refused by name per tier: `dst`, `src`, `flags`, `autotune`,
  `prune_schedule`, `keep`, `retain`, `gfs` (there is no target). Link fields
  (compression, cipher, history, raw, bandwidth), `passive` and `media` are
  not in the section's allow-list and are refused as unknown. `pair_label`
  and a non-reserved prefix are required; the name must be a plain
  `[user@]host:dataset`.
- Overlap, at activation (`snaponly_assert_source_free`): by enrolled source
  identity (peer label) plus dataset, parent and child included, against every
  other record of THIS collector; another source host with the same path, and
  other collectors, are allowed. An unreadable record or manifest is a refusal.
- `zfs-backup.sh` writes the sections from the profile; the monitor rides the
  round-2 remote monitor with the section's `ssh_flags` (identity and host in
  the group key).

  negatives (`snaponly-target-prune`, `-dst`, `-flags`, `-no-label`,
  `-local-name`, `-compression`, `-reserved-prefix`, `-shell-name`).

  parent) and allowed cases (another peer, a disjoint dataset).

### Remaining gap

- Grouping: snaponly lines live in their own entity list and emitter, so an
  ordinary pull with the same scope cannot coalesce with them; there is no
  shared group key to extend. No golden places a snaponly section next to a

  same source host are two labels and are not detected as one source.
- No dedicated gen-cron reconcile test for snaponly lines; the installed

### Implemented change

- Family `<label>_<prefix>`, `<label>` the pairing label the source knows
  (from the peer account `zfsbackup-<label>`; case kept; a label containing
  `_` is refused). Its uniqueness per source is enforced by `deploy.sh --join`:
  the package carries the collector's machine identity (16 hex of
  sha256(`/etc/machine-id`)) and `--join` refuses another machine under a
  label it already pairs, and a package without identity once the manifest has
  one. Before, a second collector with the same short hostname was taken for a
  key rotation and shared the first one's account, scope and family.
- Creation, prune and monitor use the same family and scope. The prefix must
  be non-empty and not Proxmox-reserved; a profile with no prefix is refused.
  A profile with a per-tier GFS ladder (the built-in `default` included) is
  refused: a source `[prune:]` carries one section-level ladder, and a flat
  count would be a different policy.
- Source retention is a `[prune:]` section on the source scope with the
  relationship's pinned key, `-L <label>` (pause/disable) and the existing
  grant checks (`assert_source_prune_grant` fails closed). No `-F`, no target
  prune, no hold release, no grant widening.
- Another collector holding `destroy` on the source (the owner allows
  independent collectors) is NAMED in a warning, not refused, for snaponly
  only: no other collector's family can match `<label>_*`. A failed `zfs allow`
  read refuses. Backup relationships keep the existing refusal.
- Failure to prune is visible: the source prune runs under `zfs-job.sh` like
  every prune line, and a failed destroy is rc 1 with the notify (live: a held
  and a clone-origin snapshot gave rc 1 with both errors named).
- Create and prune keep the existing semantics: independent cron jobs on their
  own schedules (prune offset from the snapshot minute), no coupling between
  them.
- Minutes written are never multiples of 5. Activation takes the first
  snapshot of every tier; rc 8 (quiesce degraded) is reported as a
  crash-consistent snapshot.

### F1.2 — the record kind is validated at load

*Change.* `record_load client` validates the kind read from THAT file
(`record_client_mode_ok`, `lib-record.sh`). Absent means the legacy meaning.
`backup`, `sync`, `local` and `snaponly` are accepted, and snaponly must not
name a target (in either field order). Anything else ends the load with a
die, the same treatment as an unknown field name, before any lifecycle,
status or target-path dispatch. Values set by the caller are not judged, only
what the file says.

Present-but-empty `RUX_MODE=''` is accepted on purpose. It is not garbage:
it is what the facade writes for its default kind (`rux_remote_install` writes
`RUX_MODE "$mode"` with `mode` empty for backup, reported as
`mode='${mode:-backup}'`), and `test/rux` records carry it. Refusing it would
stop existing backup relationships.

*Evidence.* The suite tests `snaponyl`, `Snaponly`, and snaponly with a target
before and after the mode, all refused. Absent, empty, `backup`, `sync`,
`local`, and snaponly with an empty target all load. `seed`,
`activate-client`, `remove-client`, `status` and `delete-relation` on a
`snaponyl` record all stop at the load, with ssh and zfs as recording stubs:
no call, record unchanged. `snapget_local_base` is never reached for a
`snaponyl` record with a sync-shaped pairing (before, it answered `''`, the
sync meaning).

### F2.1 — the overlap check reads every other record whole

*Change.* `snaponly_assert_source_free` loads each other record with
`record_load client` in a confined subshell. A bad line, an unclosed quote, an
unknown field or kind, or an unreadable file is a refusal. Every field it
relies on must also be present: a missing STATE, a missing PEER_HOST, or no
dataset list (record or manifest) is a refusal. A same-peer relationship's
manifest is loaded the same way. Fields travel through `\x1f`, not a tab,
because a tab is IFS whitespace and an empty legacy `RUX_MODE` would shift the
fields. Removed and local records are skipped, as before.

*Evidence.* The suite tests an unterminated `REQUESTED_DATASETS` quote, no
STATE, an unknown mode, no PEER_HOST, snaponly with no datasets, a non-record
line, a malformed STATE and a malformed PEER_HOST (unclosed quotes),
`REQUESTED_DATASETS=''`, a field this package does not write, a same-peer
backup with a malformed manifest, and one with an overlapping manifest. All
are refused. The controls (removed, local, disjoint,
another peer, a legacy record without `RUX_MODE` and a disjoint manifest, a
facade-written `RUX_MODE=''` and a disjoint manifest) keep their behaviour.
An unreadable file is the `record_load` rc 1 path, refused the same way; it is
not exercised (file modes do not bind on the Windows test box).

## F4 — IMPLEMENTED

### Analysis

Accepted. The two producer-status losses the review names were real for
local reads too: `check_one` read the snapshot list through
`done < <(zfs list ...)`, and the `-R` walk used the same construction. A
failed snapshot list after a successful existence probe therefore became "no
matching snapshot" and was judged by the dataset's age. A failed walk checked
no children and said nothing. The fix is the same for local and remote reads.

### Implemented change

`check-snap-age.sh` (v2.3 → v2.4), within the `authorizes-frozen` marker:

1. **Remote entries.** A dataset entry may be `[user@]host:dataset`. It is
   parsed by `delsnaps.sh`'s `parse_remote` rule (remote only when nothing
   before the `:` looks like a path). The five options are the same as in
   `delsnaps.sh`: `-p -k -c -K -O`. The ssh options are built the same way:
   `-k` pins with `StrictHostKeyChecking=yes`, otherwise `accept-new`;
   `-K`/`-O` go at the front, because OpenSSH keeps the first value. The run is
   non-interactive and bounded: `ssh -n`, `BatchMode=yes`,
   `ConnectTimeout=15`, `ServerAliveInterval=15`, `ServerAliveCountMax=4`,
   and a wall-clock `timeout -k 10 120` around each remote read when
   `timeout(1)` exists. Keepalive alone only notices a dead link, because sshd
   keeps answering while a zfs on the far side hangs. A timeout (124/137) is
   UNKNOWN "timed out".
   `zfs` is required only when a local entry exists, and `ssh` only when a
   remote one does.
2. **Validation before any read.** A remote host must be a plain host name and
   the user a plain account name. A remote dataset name must match
   `[A-Za-z0-9][A-Za-z0-9_.:/-]*`. Anything else is UNKNOWN before ssh starts,
   so no quote and no shell syntax reaches the far shell. The arguments are
   single-quoted there, and `--` precedes the dataset name, as in
   `delsnaps.sh`'s `run_zfs`. Received data is never evaluated.
3. **One read path, `zread`.** It covers existence, the snapshot list,
   creation and the `-R` walk, and runs on the entry's own host. There is no
   local fallback. It runs `zfs list` and `zfs get` only.
4. **Every status and shape is checked before use**, locally and remotely:
   - existence: non-zero means UNKNOWN. Exit 1 (zfs's own answer) is "does
     not exist". Every other status says why: 255 is ssh (connection,
     authentication, host key), 93 is the pair gate refusing, 124/137 is a
     timeout, 127 means zfs was not found on that host, anything else is the
     zfs exit status. An answer other than the dataset name is UNKNOWN;
   - snapshot list: read whole, then its status is checked. A failure is
     UNKNOWN "snapshot list could not be read", also when lines were printed
     before the failure. A line that is not `<dataset>@…` is UNKNOWN, not
     trusted;
   - creation: the existing numeric validation, now on the right host;
   - `-R` walk: read whole and its status checked. A failure is UNKNOWN
     "descendants could not be listed; none of them was checked". A line
     that is neither the root nor under it is UNKNOWN.
5. **Unchanged:** the local CLI and its output for successful reads, the
   pause wording, `-x`, the thresholds, the no-match dataset-age rule (now
   only after successful reads), the container leniency under `-R`, and the
   severity order CRITICAL > UNKNOWN > WARNING > OK. Every UNKNOWN is still
   printed when CRITICAL decides the exit status. Status lines name a remote
   dataset with its `user@host:` prefix.

`gen-cron.sh` (not frozen):

6. A `[prune:user@host:dataset]` section with `monitor_warn`/`monitor_crit` is
   no longer refused. Its monitor line carries the section's `ssh_flags`, the
   same string its `delsnaps.sh` prune line already carries. `lint_ssh_flags`
   restricts the OPTIONS to `-p/-k/-c/-K/-O`; it does not validate their
   values, which is the same exposure the prune line has had and is not
   widened here. A local scope's `ssh_flags` only draw a warning and are not
   passed to its monitor, so a local line is byte-identical to before.
7. **The monitor group key includes the ssh identity and the remote host**
   (the review: "Current MONITOR_GROUPS key has no SSH field"). Two remote
   scopes with a different key, alias or host never share a line.
8. The negative case `prune-remote-monitor` (the old refusal) becomes a golden
   case with three remote scopes. Two on hostA with one identity give ONE
   line. One on hostB with another identity gives its OWN line.

Not changed: `lib-zfs-snap.sh`, the engines, the pair gate and its grants. The
gate is the existing active/disabled gate. It passes `zfs list`/`zfs get` while
active, and nothing here widens it. `zfs-backup.sh`'s remote source retention
still drops monitor fields from a remote source template. Wiring the monitor
into a `snaponly` relationship is round 1.

### Remaining risk

- The gate passes active read commands through. It is not a per-command
  sandbox, as the review notes, and this change does not make it one.
- The wall-clock bound needs `timeout(1)`, which coreutils provides on every

### Implemented change

`check-snap-age.sh` v2.4 -> v2.5, inside the same `authorizes-frozen` marker:

1. `name_from_zfs_ok`: before any follow-up read, a returned snapshot must be
   `<ds>@<component>` and a returned descendant `<ds>/<path>`, where the part
   after the root holds only what a ZFS name component carries: letters,
   digits, `_ - : .` and space (it stays inside quotes); a descendant's path
   may also hold `/`, but not a trailing `/` or `//`.
   A quote, `;`, `$(`, a backtick or anything else is UNKNOWN ("not a
   well-formed snapshot/dataset ... not trusted"), and that name is never read
   with. A bad snapshot line makes the dataset UNKNOWN; a bad descendant line is
   UNKNOWN and not checked, the other descendants still are.
2. `zread` escapes an embedded single quote POSIX-style (`'` -> `'\''`) for
   every remote argument. That is the second wall: every name reaching it is
   already validated, so for every valid name the command text is
   byte-identical to v2.4 (the pair gate sees the same strings).
3. `-R`: the walk output must contain the root's own line. Empty or root-less
   rc-0 output is UNKNOWN "does not contain the root itself, so it is not a
   complete walk; none of the descendants was checked". A valid root-only walk
   still applies the container rule, and CRITICAL still outranks UNKNOWN with
   every UNKNOWN printed.

Unchanged: the CLI, thresholds, pause wording, `-x`, the no-match rule, the
severity order, read-only `zfs list`/`zfs get`.
