## F1 — IMPLEMENTED

### Analysis

Confirmed. Both engines built the protected-snapshot list as
`zfs list ... -r <tgt> 2>/dev/null | grep ... || true` (snapsend local and over ssh, snapget
local): a failed listing and "nothing reserved by Proxmox VE" were the same empty string, and
`zfs destroy -R` followed.

### Planned or implemented change

`lib-zfs-snap.sh` `list_protected_snaps <ds> [user] [host]`, called by both engines before the
force-full destroy, for both entry paths (`-f` and the `-F` upgrade, which share the block):
existence is asked with the new `dataset_presence` (exists / does not exist only when zfs itself
says "dataset does not exist" / unknown -- `probe_dataset`'s local branch read every failure as
absent, which the first version of this fix inherited; text-checker caught it before submission);
absent = nothing to protect, unknown = refuse;
the listing's status is checked (stderr captured, shown in the refusal); every line must be a
snapshot under the target; only then the reserved prefixes are matched. Any failure logs
"Refusing the destructive full transfer ..." and returns before any destroy. The policy (the three
reserved prefixes) is unchanged.

### Evidence

## Round 3 (Reviewer verification of 92c81fcf, 2026-11-05) — F5 IMPLEMENTED

### Analysis

Accepted, both points.
- (1) In both engines `get_sorted_snapshots` assigned `snaps=$(printf ... | awk ...)` without
  checking it and ended with `echo`, so a failed local filter returned success with an empty
  or partial list.
- (2) `find_conflicting_snapshots` collected its lists with `local a=($(get_sorted_snapshots
  ...))`, which returns the status of `local`. The `-n` branch of `process_dataset` ignored the
  status of `find_common_snapshot` and of the scan, and the `-n` main loop ignored the status of
  `process_dataset`. A failed discovery therefore ended as a complete-looking answer.
  Measured on `main`'s engines with the new tests (below): a failed filter or a failed target
  listing gave rc 0 with `PLAN=INCREMENTAL`; a failed source listing in the scan gave rc 1 with
  the healthy target snapshot listed as a conflict.

### Implemented change

Both engines change in the same way (the pull engine asks its source over ssh, the push
engine locally):
- `get_sorted_snapshots`:
  - the filter runs as `snaps=$(awk ... <<< "$_out") || { log; return 1; }`;
  - a failed LOCAL listing is now logged, as the remote one already was.
- `find_conflicting_snapshots`:
  - each list is assigned apart from `local` and checked;
  - the target and, in `-r`, each source child are asked with `dataset_presence` (lib, REV-186
    F1): "absent" only on zfs's own "does not exist". `target_exists`/`probe_dataset` read
    every failed LOCAL `zfs list` as absent, so a "permission denied" looked like a first copy.
    An absent target means nothing can conflict (the first copy, as before); unknown is a
    failure;
  - in `-r`, the children listing is checked;
  - an unanswerable source child fails the scan. Before, snapget.sh skipped it and went on
    (a hole in the list), and snapsend.sh's plain `zfs list` read it as gone (its target
    snapshots listed as conflicts);
  - `find_common_snapshot` and the recursive call propagate their status.
- `find_common_snapshot` asks the target with `dataset_presence` as well: absent gives "null"
  (the first copy, as before), unknown is a failure. Before, `target_exists` read a failed
  local `zfs list` as absent. This function also runs on the real (non-`-n`) path, which
  therefore no longer treats an unanswerable target as a first copy. There the caller now
  checks the status: the dataset is refused ("could not be compared -- NO transfer for this
  dataset"), and the reconcile (`-F`) branch counts it as an incomplete collision scan (no
  upgrade). Without that check, the empty answer reached the send as `-I <src>@` (found by CI
  on 6b5c5fc4, below).
- `process_dataset -n`:
  - a failed `find_common_snapshot`, conflict scan or bookmark-base target listing logs
    "-n: ... could not be listed -- no plan and no conflict list for this dataset" and returns 1
    before any `PLAN=` line;
  - the bookmark-base branch asks the target with `dataset_presence` as well; unknown is a
    failure, not "no target".
- The `-n` main loop records the dataset. The run then exits **2** with `INCOMPLETE: <dataset>`
  on stderr. Exit 1 keeps its meaning "conflict list on stdout". Conflicts found for OTHER
  datasets of the same run are still printed. The failed dataset prints none: the loop cuts
  `CONFLICT_SNAPSHOTS` back to its length before that dataset, because a `-r` scan that fails
  in a child has already added the parent's conflicts (a partial list).
- Every `-n` caller in zfs-backup.sh fails on a nonzero status: `activate_dryrun_snapget`,
  verify-endpoint, the snapshot-only rehearsal, the seed and verify loops. The history-only
  exception (`probe_conflicts_are_history`) applies to rc 1 only.

## Round 4 (Reviewer verification of a3cb5309, 2026-11-05) — F5 IMPLEMENTED

### Analysis

Accepted. `lib-zfs-snap.sh:get_snapshot_guids` piped `zfs list -o name,guid` (local, or the
remote one over ssh) into `awk` and returned awk's status. Both engines' `find_common_snapshot`
read it with `done <<< "$(get_snapshot_guids ...)"` and did not check it. The GUID fallback
runs when the name scan finds no common snapshot (a base renamed on one side). A failed
listing or transport was therefore an empty list, and the fallback answered "null": no common
base. Measured on `main`'s code with the new tests (below).

### Implemented change

- `get_snapshot_guids` (lib), the same shape as `get_sorted_snapshots`:
  - the listing is captured and its status checked: a remote 255 is logged as a
    connection-level failure, any other nonzero (local or remote) as "could not list the
    snapshot GUIDs";
  - every line must be `snapshot<TAB>guid`, otherwise a failure;
  - the awk filter runs on the checked list and its own status is checked;
  - a failure is rc 1; an empty successful list is rc 0 with no rows, as before.
- `find_common_snapshot`, both engines, both calls (target and source): the list is assigned
  apart from `local` and a failure returns 1. Round 3's callers then act on it: the real run
  refuses the dataset ("could not be compared -- NO transfer"), the reconcile branch (`-r -F`)
  logs "the collision scan ... could not complete -- NOT upgrading", and `-n` ends rc 2 with
  `INCOMPLETE:`. On `main` the failure was the answer "null", which the reconcile branch took as
  a base for its collision scan.
