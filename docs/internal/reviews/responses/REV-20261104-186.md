## F1 — IMPLEMENTED

### Analysis

Confirmed. Both engines built the protected-snapshot list as
`zfs list ... -r <tgt> 2>/dev/null | grep ... || true` (snapsend local and over ssh, snapget
local): a failed listing and "nothing reserved by Proxmox VE" were the same empty string, and
`zfs destroy -R` followed.

### Planned or implemented change

`lib-zfs-snap.sh` `list_protected_snaps <ds> [user] [host]`, called by both engines before the
force-full destroy, for both entry paths (`-f` and the `-F` upgrade, which share the block):
existence is asked with the new `dataset_presence` (exists / does not exist only when zfs itself
says "dataset does not exist" / unknown -- `probe_dataset`'s local branch read every failure as
absent, which the first version of this fix inherited; text-checker caught it before submission);
absent = nothing to protect, unknown = refuse;
the listing's status is checked (stderr captured, shown in the refusal); every line must be a
snapshot under the target; only then the reserved prefixes are matched. Any failure logs
"Refusing the destructive full transfer ..." and returns before any destroy. The policy (the three
reserved prefixes) is unchanged.

### Evidence

- commit: see `implementation` header (branch `fix/rev186-delsnaps`).
- `test/snapsend/run.sh` section "REV-20261104-186", send and get: (a) the protected listing
  fails; (b) the existence check of the target fails with "permission denied" (not "does not
  exist"); send: (c) the listing answers rc 0 with a line that is not a snapshot. Each: rc != 0,
  zero destroys, target snapshots unchanged, refusal named. Control through the same shim with
  nothing broken: `-f` rebuilds the target (the existing PVE-reserved refusal cases stay green).
- pve9: `test/snapsend` 329/0. Negative control (snapsend.sh, snapget.sh, lib-zfs-snap.sh,
  delsnaps.sh from `origin/main`, same suite): 295/34 -- every F1 failure case fails, the controls
  pass.

### Remaining risk

The destroy command itself (`zfs list -r | tac | xargs zfs destroy -R ... || true`) still does
not report a partial destroy; out of F1's scope (discovery), noted for a later review.

## F3 — IMPLEMENTED

### Analysis

Confirmed. The `-R` walk discarded the status of `zfs list -r`; a failed or truncated walk pruned
the root and whatever children were printed, rc 0.

### Planned or implemented change

The tree is listed BEFORE anything is pruned. The listing must succeed, contain the root itself and
only lines under it; otherwise nothing in the tree is pruned and EXIT_CODE=1, with the reason.

### Evidence

  the tree, and over ssh (a fake ssh, transport exit 255 before output) -- rc 1, nothing deleted on
  root or child; controls (local and remote) with the walk intact prune both.
- pve9 numbers as F2 (one suite).

## F4 — IMPLEMENTED

### Analysis

Confirmed in both engines: the loop ran over the whole `zfs list -r` output and mapped
`tgt/a/b` to `src/b` (basename), so a nested tree produced a false collision and `-F` upgraded to
a destroying full transfer. snapget also discarded the listing status.

### Planned or implemented change

`lib-zfs-snap.sh` `collision_scan_pairs`: every target descendant maps to the source by its full
relative path; a listing without the root, a line outside the root or a malformed path ends the
scan. The redundant recursive call is gone (the `-r` listing already covers the tree). The source
peer is asked with `dataset_presence`: absent (zfs says so) = mismatch as before, unknown = scan
incomplete -- local and remote alike. In
both callers an incomplete scan never upgrades: "NOT upgrading to a full ...". Send and get
symmetric.

### Evidence

- `test/snapsend/run.sh`: depth-2 tree with equal GUIDs under `-r -F` (the scan is gated on
  `RECURSIVE`, i.e. `-r`, not `-R`): rc 0, no upgrade, the increment reaches the depth-2 child;
  duplicate leaf names (`root/a/x`, `root/b/x`, equal GUIDs): no upgrade; the source child's
  existence check denied: "could not complete -- NOT upgrading"; control: a different `@base` on the
  target child is still upgraded.
- Negative control: every "NOT upgraded" / "could not complete" check fails on `origin/main`;
  controls pass.

### Remaining risk

None known.

## F5 — IMPLEMENTED

### Analysis

Confirmed: the remote command ended in `| awk`, so ssh returned awk's status and a failed remote
`zfs list` came back as an empty list. The local branch relied on the global `pipefail`.

### Planned or implemented change

Both engines' `get_sorted_snapshots`: the remote list comes back raw and its status is checked; on
a remote failure other than ssh 255 a dataset that genuinely does not exist (`dataset_presence`) is
still an empty success, as before. The local branch keeps its behaviour (absent = rc 1, as on
`main`). Every line must be a snapshot; the `awk` filter then runs locally on the already checked
list (a local `printf | awk`, no status left to lose).

### Evidence

- `test/snapsend/run.sh` F5 (function-level, both engines, ssh shim running the remote side
  locally): existing dataset + remote list exit 1 / exit 77 -> rc 1; ssh exit 255 -> rc 1; absent
  dataset -> rc 0, empty; normal -> names oldest first.
- Negative control: the exit 1 and exit 77 cases fail on `origin/main` for both engines (255 was
  already handled there).

### Remaining risk

None known.

## F6 — IMPLEMENTED

### Analysis

Confirmed: `grep "^$MESSAGE"` in both engines.

### Planned or implemented change

Literal prefix: `[[ "$s" == "$MESSAGE"* ]]` (quoted right side: no regex, no glob, no locale, no
option parsing).

### Evidence

- `test/snapsend/run.sh` F6, send and get: `-m daily.2026` takes `daily.2026_a`, never the newer
  `dailyX2026_b`, and `-m d.x` only `d.x_1` -- both fail on `origin/main`. Measured grammar (the
  suite tries each character on the pve9 pool): ZFS refuses `+ * ? ^ $ \ [ ] ( ) | { } %` in snapshot
  names, accepts `. : -`. Of the regex metacharacters only `.` can occur in a family, and it is
  covered; `:` and `-` select literally (cases pass on both).

### Remaining risk

The other metacharacters cannot occur in a ZFS snapshot name (measured above), so a `-m` holding
them selects nothing on either engine.
