## §2 — a requested quiesce can fail and the snapshot is taken anyway — ACCEPTED, FIXED (blocker)

Correct, and this was the worst of the three: the flag exists specifically to
prevent a silently crash-consistent snapshot, and the code delivered exactly
that. `freeze_one()` printed `QERR` and returned 0, and the calling loop
discarded the result, so a failed freeze, an already-frozen guest, a mode that
did not fit the guest type, or a failed `pct exec ... sync` all continued into
the atomic `zfs snapshot` and exited 0.

`freeze_one()` now returns non-zero for every case where a **discovered,
running** guest in scope could not be quiesced, the loop counts those, and a
non-zero count skips the snapshot entirely and exits 5. The EXIT trap still thaws
whatever did get frozen, so a partial freeze does not leave guests frozen.

Two cases deliberately stay non-failures, because nothing needed quiescing:

- a dataset whose guest does not exist on this host (a replica leaf parses the
  same as the original — that is a known and tested property);
- a guest that is not running.

`auto` needed no special definition after all: it selects the method from the
guest kind, so it cannot produce a mode mismatch. The mismatch cases are only
reachable when the operator named `agent` or `sync` explicitly, and those now
fail — the quiesce that was asked for is not going to happen.

The already-frozen case ends the run before the snapshot and leaves the guest
untouched, as required. The message says why in those terms: this run did not
establish the freeze and must not claim it did.

## §3 — a missing `setsid` only warned — ACCEPTED, FIXED (blocker)

Correct. The check now happens **before** anything is frozen and is fatal
(exit 3). Additionally the deadman is verified to be actually alive
(`kill -0`) after being started — a pid that has already exited is not a safety
net either, and only checking `command -v setsid` would have missed that.

## §4 — a failed thaw destroyed the deadman's state — ACCEPTED, FIXED (blocker)

Correct, and this is the one that would have hurt most in production: the
unconditional `: > "$frozen_file"` removed the last automatic rescue path in
precisely the case it exists for.

- `thaw_all()` now removes **only** ids it actually thawed; the rest stay in the
  file and it returns non-zero.
- Thawing, stopping the deadman and deciding whether the file may be removed all
  moved into one `on_exit` trap, so every exit path goes through it. The file is
  kept whenever a guest is still frozen — that file **is** the deadman's mandate,
  and removing it would be the same bug in a different place. The deadman is only
  killed once nothing is left frozen.
- The run exits 6 and the message carries the exact manual command, which differs
  by route: a delegated account has no `qm`, so telling it to run one would be
  useless advice at the worst possible moment.
- The deadman **retries** — up to 12 passes, 5s apart, dropping each id as it
  succeeds — and logs either a per-attempt line or an explicit `GAVE UP ... STILL
  FROZEN ... manual thaw required`. It no longer stops after one failed attempt.

New exit codes: 5 = quiesce preparation failed (no snapshot taken), 6 = a guest
is still frozen. `quiesce_remote_run()` maps both to specific operator-facing
messages.

## §5 — error-branch tests — ACCEPTED, DONE

All seven are in `test/quiesce/run.sh`, driving the real
`$ZFS_REMOTE_QUIESCE_SCRIPT` under `qm`/`pct`/`zfs`/`setsid`/`sudo` stubs, and
each asserts on the trace as well as the exit code — whether `zfs snapshot` was
reached at all is the point, not just what was returned.

1. freeze fails → no snapshot, exit 5
2. already frozen → no snapshot, exit 5, and the reason is stated
3. no setsid → nothing frozen, exit 3
4. thaw fails → exit 6, id stays for the deadman, manual command named
5. snapshot fails → exit 4, the trap still thaws
6. a mode the guest cannot honour → no snapshot, exit 5
7. two guests, second freeze fails → no snapshot, and the first is thawed

**These were run against the pre-fix library and 12 of them fail there**
(`LIB=<HEAD's lib> ./test/quiesce/run.sh` → PASS=33 FAIL=12), which is the
property that makes them regression tests rather than descriptions of the new
code. Case 5 passes on both, deliberately kept as a guard.

Two test-mechanism defects found while writing them, both noted in place:
an empty file used as the helper stub is not `-x` on MSYS (so the case would have
passed for the wrong reason on Linux and failed for the wrong reason here), and
making `setsid` absent needs different tricks on MSYS and Linux — emptying PATH
only proves `mktemp` is missing.

## §6 — permission model UX — ADDRESSED by work this review predates

`1ed60d7` / `a59c4cc` add `zfs-quiesce-helper` plus
`deploy.sh --join --allow-quiesce`, which is the single supported deployment path
this section asks for. The administrator does not write a sudo rule: `--join`
generates it, validates it with `visudo -c` before installing (a broken file in
`/etc/sudoers.d` breaks `sudo` for every user including root), and the audit
surface is explicit — one script, four verbs, guests scoped to the datasets the
same run delegated via `zfs allow`.

Two points worth the reviewer's attention:

- The grant is a **local flag on the joining host**, not a field in the pairing
  package. Freezing is real power — whoever can freeze can cause an outage by
  never thawing — and the script that performs the thaw is streamed by the
  collector. So the source host's owner decides, and a package cannot ask.
- `writers <id>` was added after measuring qemu's source. On Linux a failing
  `/etc/qemu/fsfreeze-hook` aborts the freeze; on Windows `requester.cpp` calls
  `GatherWriterStatus()` and never inspects individual writer state — no
  `GetWriterStatus` or `VSS_WRITER_STATE` appears in that file in v7.2.0, v8.2.0
  or master. A dead `SqlServerWriter` therefore yields a snapshot that reports
  success and is not application-consistent, and no version of qemu will say so.
  This is not hypothetical: it is what happened on a production SQL guest here
  for months. `writers` is the only way to see it from the host.

Agreed and unchanged: `-q` is **not** enabled in `zfs-backup.sh`'s `standard`
profile, and will not be until the live checks below are done.
