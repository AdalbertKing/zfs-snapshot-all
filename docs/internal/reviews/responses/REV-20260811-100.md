# Response to REV-20260811-100

## F1 — IMPLEMENTED

Accepted. The critique is exactly right: my REV-099 d8/d9 asserted the lifecycle
only in its FINAL shape — it opened the review directly at `$sha2` and appended
`reviewed-by: $sha1` by hand, so nothing ever named `$sha1` as a review state and
no pointer advance was performed. A fixture that starts already-retired stays
green even if the transition that produces the resurface, or its retirement,
regresses. The historical failure is temporal, so the proof has to be temporal.

### Change

d8 now walks the states in order, generating and asserting at each step (`test/
reviewctl`, using the existing helpers, no `reviewctl` redesign):

1. `deliver $sha1` -> generate -> assert `$sha1` is present as DELIVERED
   (reviewer-owned);
2. open `REV $R` AT `$sha1` -> generate -> assert the DELIVERED row is gone and
   the REV row stands in its place;
3. **advance the same review to `$sha2`** (`review $R APPROVED $sha2` +
   `respond ... $sha2`) -> generate -> assert `$sha1` **RESURFACES as DELIVERED**
   — this is the exact historical failure, now executed rather than described,
   and it is the load-bearing step the old fixture skipped;
4. record the durable `reviewed-by: $sha1 $R`;
5. `close $R` at `$sha2` -> generate -> assert BOTH the original `$sha1` delivery
   and the closed REV are absent.

The genuinely-unreviewed `$sha3` negative control is kept, in the same
post-closure world, so it still proves the retirement is the `reviewed-by` fact
and not "closing a REV silences every delivery".

The step-3 assertion is what makes the regression load-bearing: if a future
change broke the advance-then-retire bookkeeping, step 3 (resurface) or step 5
(stays absent) would fail rather than a pre-populated final marker passing
silently.
