# Response to REV-20260731-012

Delivery: direct to `main`, per the owner-approved exception.

## F1 — the update commit order can widen an active grant — ACCEPTED, and the reasoning was mine

The finding is correct. This is a defect in the design I argued for, not a
misreading of it, and the argument I used to justify it was false in a way I can
point at exactly.

I wrote that the whitelist could be committed first "because it is a
RESTRICTION, so a crash between the two leaves the narrower of the two lists in
force". That sentence is wrong twice.

It is wrong about the mechanism: what is in force after that rename is the **new**
list, whatever its width. There is no sense in which a rename leaves "the
narrower" of two files behind. I was reasoning about the case where the OLD list
is wider — the narrowing update — and generalised it to both directions without
checking the other one.

And it is wrong about the state: "the rule is last because it is the switch —
until it lands nothing is granted" is true **only on a first install**. On an
update the final rule already exists and stays active through every rename, so
the switch was never off. The moment a wider whitelist lands, the old rule and
the old helper read it, and a crash there leaves the grant permanently widened by
a transaction that never completed.

That is the re-enrol path — the one REV-009 opened — so it is also the path most
likely to be exercised.

## Implemented change

The commit order now starts by switching the live grant **off**:

```
0. mv  <rule>            <rule>.zqg-bak      suspend the active grant   (update only)
1. mv  <allow>.zqg-new   <allow>             whitelist
2. mv  <helper>.zqg-new  <helper>            helper
3. mv  <rule>.zqg-new    <rule>              re-arm with the new grant
```

Step 0 is skipped when no rule exists, so a **first** enrolment never sees an
outage and its ordering is unchanged — which is the part §Decyzja accepted.

Two details worth stating because they are not free choices:

**Suspending is itself a rename**, onto the `.zqg-bak` name that sudoers.d
ignores. So the disable is atomic — there is no instant where the rule is
half-present — and it doubles as the preservation step for the rule.

**The rule therefore gets no hard-linked backup**, unlike the helper and the
whitelist. This matters more than it looks: POSIX `rename()` on two names for the
same inode "shall return successfully and perform no other action". Had I left
the hard link in place, `mv <rule> <rule>.zqg-bak` would have succeeded, changed
nothing, and left the grant live for the whole update — a silent reintroduction
of exactly this finding, with a green suite.

The cost is a window during an update where the account cannot quiesce at all. I
agree with §Wymagana poprawka that this is the right trade: a job that fails
during an update is visible and gets retried, a silently widened grant is
neither.

### Recovery of a suspended grant

A crash between step 0 and step 3 leaves the host with no active rule and its
only copy under `.zqg-bak`. The sweep used to delete leftovers unconditionally,
which would have turned an interrupted update into permanent loss of the grant.
It now distinguishes:

- destination present → the `.zqg-bak` is spare, remove it;
- destination **missing** → that copy is the only one left, so it is renamed
  back, and the run says so.

So an interrupted update is fail-closed while it lasts and self-heals on the next
run, without replaying a half-finished intent.

## Tests

The cases you asked for measure the **effective boundary**, not the files. The
boundary is open only when both hold: an active (dotless, therefore
sudo-readable) rule exists, **and** the whitelist names the newly added dataset.
Until the whole commit succeeds that combination must not appear.

Fixture: a live grant on `rpool/data/vm-106-disk-0`, updated to
`vm-106 + vm-107`.

| SIGKILL at | result |
|---|---|
| suspending the old rule | not widened |
| switching the whitelist | not widened |
| switching the helper | not widened |
| — completed update | **is** widened, i.e. the update actually took effect |
| — narrowing update | completes, `vm-107` gone, rule active |
| interrupted, then re-run | left OFF while interrupted, restored and completed by the next run |

The "completed update does grant the new dataset" case is there deliberately: a
function that did nothing at all would satisfy "never widens" perfectly.

Two older crash cases asserted the **previous** contract — "rule unchanged" and
"the whitelist commits first" — which is precisely the widening window. They are
rewritten rather than extended, and now assert that the rule is suspended first
and that its preserved copy is byte-identical to what was live.

```
bash test/quiescehelper/run.sh   PASS=87 FAIL=0   (81 + 6)
bash test/join/run.sh            PASS=42 FAIL=0
bash test/impact/run.sh          PASS=21 FAIL=0
bash test/selfupdate/run.sh      PASS=28 FAIL=0 SKIP=7
./test/impact.sh --verify        graph is consistent with the tree
```

Against the previous ordering (`9ab1440`), 5 cases fail — including
"a crash while switching the helper must not widen the grant", which is the
finding reproduced mechanically.

One case passes on both and is worth naming so the number is not read as more
than it is: crashing **at** the whitelist rename cannot widen anything under
either design, because the rename has not happened yet. The old design's window
opens immediately after it, which is what the helper-step case catches.

the first-install wording, correct because no rule pre-existed.

**The `env_reset` fence, with a load-bearing control.** The whole design rests on

| | |

| same variable exported by the account and passed **through sudo** | **rc=0, unchanged** — the lever is broken by `env_reset` |
| variable given in sudo's *argument* form | `sudo: a password is required` — it does not even match the rule, so it never runs |

`sudo -l -U zfsbackup-pve2` confirms the configuration side: `env_reset`,
`secure_path`, exactly one permitted command, and zero `SETENV`.
