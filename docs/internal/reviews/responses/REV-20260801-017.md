## F1 — `gencron_as_target()` built a shell sentence — IMPLEMENTED

### Analysis

Accepted without reservation. The old form was

```bash
su -s /bin/bash - "$u" -c "NOTIFY_SCRIPT='…' … bash '$GENCRON' $*"
```

`$*` flattens argv into one string and hands it to the target account's shell to
re-parse. A config path containing a space arrives as two arguments; one
containing a metacharacter arrives as something else entirely. The reviewer's
sharpest point is the one about consent rather than about injection: the preview
validates the file the wrapper thinks it passed, and the install would then act
on a different one.

### Implemented change

`runuser --user "$u" -- env "${envv[@]}" bash "$account_gencron" "$@"` — the
argv form, which the review lists first and calls easier to audit. No `-c`, no
`printf %q`, nothing re-parsed.

### Evidence

- commit: `0c08f54`
- test: `test/zfsbackup/run.sh` section 15, which is the closing test the review
  specifies. The config path used is `"$WORK/con fig's.conf"` — a space **and**
  an apostrophe, both legal in a filename and both fatal to a re-parsed string.
  A stub `runuser` records its own argv one item per line, so "exactly one
  argument" is asserted rather than assumed.
- three checks: the path arrives as one argument with the space and quote
  intact; the account's alert paths ride along with `DIGEST_SCRIPT=none`;
  `--install` is still its own argument and was not merged or re-split.
- results: `PASS=134 FAIL=0` at `1d5a8c4`.

### Remaining risk

`runuser` is assumed present. It is part of util-linux on Debian and Proxmox, so
on the hosts this project targets that assumption holds, but there is no
fallback and no probe. A host without `runuser` fails at the first delegated
render with a "command not found" rather than a diagnosis.

## F2 — `--local-user` had no live pass — IMPLEMENTED

### Analysis

Accepted. The reviewer's list of what moves at once — crontab owner, key owner,
pinned host key, HOME, logs, alert scripts, and the identity of the installing
process — is exactly right, and a golden suite cannot speak to any of it.

### Implemented change

Pass B was run end to end on metropolis pve1 with a dedicated account, on a
separate config root does not use, with both crontabs captured first and the
whole thing torn down afterwards. It found five defects that no suite had:

| commit | defect |
|---|---|
| `3b53bfd`/`b6ae542` | the account cannot read root's config **or** root's scripts (`/root` is 0700) |
| `1be9234` | the preview rendered as root while the install ran as the account |
| `2b29db1` | `mktemp`+`mv` re-moded the config to 0600 on every section removal |
| `4738708` | the pinned host key was written root-owned inside the account's `~/.ssh` |
| `9af0003`/`39e610f` | `remove-client` did not load the server config and targeted root's crontab |

Three of those were caught by existing guards turning a defect into a message
rather than an incident; root's 15 production lines were never modified, and the
final crontab was byte-identical to the pre-test capture.

### Evidence

- commits: `0c08f54`, `7b3fb0e`, `adb7e0d`, `3b53bfd`, `b6ae542`, `1be9234`,
  `cf755f3`, `2b29db1`, `4738708`, `9af0003`, `39e610f`
- live: activation installed the block into the account's crontab with the
  account's paths and no digest line; the account's `snapget`, `delsnaps -G` and
  `check-snap-age` lines were each executed as the account and returned 0;
  root's crontab held 15 lines throughout
- teardown verified: `pve1 root=15 (identical), account=0, test datasets=0`;
  `pve2 root=14, account=0, test datasets=0`

### Remaining risk

`test/scenarios` still has not been run under `--local-user`; the live pass
exercised the wrapper's own path, not the generated lines under the scenario
harness. And the pass covered a **new** client on a separate config — not the
migration of an existing block, which is REV-018/-019/-020 and is still held.

## F3 — pve2's config is missing — NEEDS-DISCUSSION (owner)

### Analysis

Agreed, including that this is not something a tool should repair on its own.
Confirmed directly: 14 production job lines whose `# Source:` names
`/root/gfs-install-tmp/jobs.pve2.v4.conf`, and a full-filesystem search finds no
copy anywhere on the host.

### Change made

None to the jobs, which is the point. Two things were done around them:

1. the guard from `c6c98c2` refuses to **create** the file an installed block
   names as its source — an empty config plus `--install` would replace 14 live
   lines with nothing, and `assert_cron_config_matches_installed` would have
   approved it because that check compares identity, not content;
2. `migrate-to-account` refuses outright when the source config is absent,
   rather than inventing one (`1d5a8c4`).

### Evidence

- commits: `c6c98c2`, `1d5a8c4`
- recorded for the owner in `docs/PROJECT_STATUS.md` §6 (`4f4271e`), which is
  where this had been missing: until then it existed only in session notes, so
  the reviewer could not see it.

### Remaining risk

Unchanged and by design: pve2 cannot be regenerated. The installed block is the
only remaining record of what belongs in that config. `activate-client`,
`migrate-profile`, `migrate-to-account` and a direct `gen-cron --install` all
stay off that host until the owner decides between rebuilding from `crontab -l`
and a controlled migration with a full diff.
