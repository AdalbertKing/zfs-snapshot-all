# Response to REV-20260812-111

## A — IMPLEMENTED — verify the bookmark capability, not just `destroy`

ACCEPTED, no dispute. The finding is correct and the failure mode is the one my own
REV-102 campaign measured (leg A6): a source delegated everything except `bookmark`
logged `cannot create bookmark …: permission denied` plus a non-fatal warning and
still exited **0**. Activation looked healthy, the insurance was absent, and the
relationship would have stopped permanently the first time retention outran the
target.

### Implementation

`assert_source_prune_grant()` now requires `bookmark` alongside `destroy`, read off
the **same** `zfs allow` output already fetched over the relationship's pinned SSH
identity — no extra round trip, same fail-closed discipline, same verify-never-widen
rule. It fires at all three points that can install managed source retention:
`activate-client`, `migrate-profile` and the narrow `--apply` retrofit.

Why that function rather than a new one: the identity that prunes the source and the
identity that writes the bookmark are the same pinned identity, on the same host, for
the same dataset, and the capability list arrives in one query. A second checker would
have been a second ssh round trip to learn something already on screen.

### Compatibility — checked live, not assumed

`deploy.sh --commit-scope` already delegates `bookmark`
(`deploy.sh:4543`, `snapshot,destroy,send,hold,release,bookmark`), and the comment at
`deploy.sh:140` describes exactly this failure mode. So a correctly paired host is
unaffected.

Verified read-only across both live metropolis hosts, 2026-08-12: every dataset on
which `zfsbackup` holds any grant also holds `bookmark` — including every real backup
target and source. The single exception in the entire estate is `hdd/rev102nobm`, the
lab dataset I deliberately delegated without it. That sweep is therefore both the
compatibility proof (no production relationship would be refused) and a live positive
control (the condition is detectable where it genuinely exists — see
[Controls can be contaminated]; a green sweep with nothing red would have proven only
that I was grepping wrong).

## B — IMPLEMENTED — hard refuse, and specifically NOT a silent switch to `-R`

### Which option, and why

The finding offered two: prefer a recursive mode that has bookmark insurance, or
refuse. I chose **refuse**, on a fact established before choosing:

**The high-level layer never emits atomic recursion.** Every `[dataset:]` section
`zfs-backup.sh` generates carries `recursive = no` (`zfs-backup.sh:874`, `:1943`); the
only `recursive = yes` it writes are on `[prune:]` sections, which is a delsnaps scope
flag, not a transfer mode. The legacy spelling (`-r` inside `flags`) is a hard `die`
in `gen-cron.sh:692` outside `--migrate-recursion`. So the unsafe combination cannot
be produced by the package — it can only arrive from a hand-edited CONFIG.

Given that, switching the operator's `atomic` to `flat` would not be "preferring a
supported mode", it would be **overriding a deliberate human edit with a different
transfer mode** — different ordering and crash semantics — to make a safety check pass.
The finding itself says not to substitute silently if semantics change. They do.

### Implementation

`assert_no_atomic_with_source_retention()` refuses when a relationship about to receive
managed source retention declares `recursive = atomic`. It reads the **candidate** —
the workfile about to be installed — rather than what this run generated, precisely
because the dangerous value comes from outside the generator. Placed *before* the grant
gate at each of the three sites: a file read is cheaper than an ssh round trip per
source.

The refusal names the conflict, names both resolutions (`recursive = flat` with the
explicit warning that it is a different mode, or leave source retention off), and
changes nothing.

## Remaining risk

The gates cover the three paths that **install** source retention. A relationship
whose CONFIG is hand-edited to `recursive = atomic` *after* source retention is already
installed is not re-checked, because nothing re-validates an installed CONFIG on a
schedule. That is a pre-existing property of the design — CONFIG is runtime truth and
is not continuously audited — not something these changes introduce or worsen. If the
reviewer wants it closed, the natural home is `audit-source-retention`, which already
walks installed relationships read-only; say so and I will add it there rather than
inventing a new checker.

Not claiming closure.
