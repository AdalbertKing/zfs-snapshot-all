# Response to REV-20260809-080

## F1 — ACCEPTED (IMPLEMENTED)

I reported this defect after hitting it, so there is nothing to dispute. What
follows is what the fix actually covers and where it went further than the
finding.

### Analysis

Resolvability and canonical form are different properties. `require_commit()`
asked only the first — git resolves an unambiguous abbreviation — and
`state_of_raw()` then decided state with `[ "$ri" = "$im" ]`, a string
comparison. So one commit written two ways became two submissions.

The severity is in the **quiet**, not the wrongness. Nothing was malformed
enough to complain about: the generator produced a normal derived state, exit 0,
a well-formed ledger. The only signal was a routing table telling a reviewer to
do work he had already done.

### Implemented change

`canonical_sha()` in `test/reviewctl.sh`, called from `require_commit()` before
the reachability check: a commit-bearing value must be 40 lowercase hex
characters, and `-` stays legal where the protocol defines it.

**Rejection, not canonicalisation** — the review's stated preference and I agree
with the reason. These artifacts are durable audit facts, not interactive git
input; an abbreviation that is unambiguous today can become ambiguous as the
repository grows. Canonicalising would also silently rewrite what an artifact
says, which is the opposite of what a durable fact is for.

### Requirement 4 turned up a worse instance than the one reported

Applying one rule everywhere, rather than only to `implementation:`, found that
`no-review-required` and `reviewed-by` **were not commit-checked at all**. They
clear a delivery by matching its sha as an array key, so an abbreviated or
malformed value there clears nothing — and unlike the reported case there is no
later comparison to go wrong, no state to derive incorrectly, and no error. The
delivery simply stays open forever while the file looks like it was waived.

Both now go through `require_commit()`.

### Evidence

- commit: `004b4662efed7254997f99e2f301218b653ceaf9`
- `./test/reviewctl/run.sh` — **47/47** (was 36/36)
- negative control against `origin/main`'s `reviewctl.sh`, copied **inside** the
  repository as the suite header requires: **8 fail, 39 pass**
- `./test/impact.sh` selected `reviewctl` only; `./test/impact.sh --verify` clean
- frozen engine files untouched; no live ZFS/SSH/cron work, none required

### The case that actually discriminates

Not "a bad sha is refused" — the suite already had that. The new case is **a sha
that IS the same commit, written short, must not silently mean a different one**,
and the abbreviation's resolution to that exact commit is **asserted as a
premise** first. Without that assertion the case would pass on a build that
merely failed to resolve it, proving nothing — the contaminated-control mistake
this project has made six times.

Also covered: symmetric abbreviated `reviewed-implementation`, abbreviated
`closed-by`, a 40-character value that is not lowercase hex, all three delivery
markers, and `-` still legal.

### Remaining risk

The rule is enforced where commit-bearing values enter `reviewctl`. It does not
prevent a human writing a short SHA into an artifact — it makes that a loud
refusal instead of a quiet mis-derivation. That is the property the review asked
for, and I am not claiming more.
