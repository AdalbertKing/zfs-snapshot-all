# Response to REV-20260811-102

## F2 — IMPLEMENTED (on main) — source-prune scope follows source coverage, not a blanket recursive

The step-2 emission first made the source `[prune:<root>]` `recursive = yes` while
the `[dataset:<root>]` is non-recursive, so `delsnaps -R` could walk into a child
like `<root>/vm-101` and destroy tool-owned `automated_` snapshots outside this
relationship's coverage. Corrected: the local-PUSH source prune omits `recursive`
(CONFIG default = no) — `delsnaps -G` without `-R`, exactly the named dataset. The
target prune stays recursive over the store; independence preserved.

Proven, real ZFS (2026-08-11, pve1 192.168.28.9, throwaway `hdd/backuptest/rev102srclab`
+ `/child`): `delsnaps -G` deleted the parent's `automated_hourly_a/b`, kept `_c`,
and left `manual_keepme` (pattern) and `child@automated_hourly_child1`
(non-recursive) untouched. Suite: `test/localbackup` includes the non-recursive
assertion + the child-survives negative control.

## Answers to the 7 questions

Full detail in `docs/discussions/PHASE5-SOURCE-RETENTION-DESIGN-2026-08-11.md`
(Q1-Q7 there); summarized here against the current implementation.

1. **Exact native CONFIG sections.** PUSH: `[dataset:<root>]` (send) +
   `[prune:<root>]` (SOURCE, non-recursive, `__src_keep_*`) + `[prune:<target>]`
   recursive (TARGET). PULL: `[dataset:<local-target>] src=acct@host:source` +
   `[prune:<acct@host:source>] ssh_flags=…` (SOURCE remote, `__src_keep_*`,
   non-recursive, monitor-free) + `[prune:<local-target>]` recursive (TARGET). Two
   independent `[prune:]` families from the same preset ladder.
2. **Source-prune recursion/scope.** Follows the dataset's own coverage: the
   default non-recursive source prunes only the named dataset (`delsnaps -G` without
   `-R`); a flat/atomic source would need a matching recursive source prune — not
   exposed yet, so no blanket `recursive=yes`.
3. **Remote prune reuses the relationship SSH.** `ssh_flags` = the pull's own
   transport (`-K LOAD_KEYFILE -k LOAD_ALIAS_KH -O HostKeyAlias=LOAD_ALIAS …`) minus
   `-b`; scope `acct@host:source` is the same identity/host-key pinning as the
   transfer. Live-proven: pve1 collector ran the emitted `delsnaps -G` over the
   zfsbackup account's SSH to source pve2, pruning `hdd/backuptest/rev102remote`.
4. **Grant already includes `destroy`, verified fail-closed, no widening.** Yes:
   `do_commit_scope` (`deploy.sh --commit-scope`) already delegates `destroy` per
   source dataset. `assert_source_prune_grant` reads `zfs allow` over the pinned SSH
   and refuses unless the account's own line carries `destroy` — verify, never
   widen. Fail-closed unit-tested (`test/zfsbackup` section 55: with/without
   `destroy`, ssh error, one-of-many). Confirmed read-only that production source
   datasets hold `destroy`. NOT provable live-negative in this estate: the whole
   `hdd/backuptest` tree grants `destroy` by inheritance, so no live no-`destroy`
   location exists.
5. **No usable bookmark/common snapshot, incl. recursive.** The default equal ladder
   reduces but does not by itself guarantee continuity. The source prune touches
   only `automated_hourly_` snapshots, never bookmarks. The one open sub-decision
   (hard-refuse vs explicit FULL-resend warning on recursive relationships) stays
   tied to live evidence and is NOT decided from a shorthand — see Q4 in the design
   doc. This is the piece I most want reviewer input on.
6. **Smallest migration path (step 5) — IMPLEMENTED (`9006026`).** `zfs-backup.sh
   audit-source-retention` scans the installed CONFIG; for each active pull
   relationship it checks whether every `PEER_SAVED_DATASETS` source carries a
   bounded source `[prune:account@host:ds]`. Default is read-only: it reports the
   missing count, names each missing section, prints the exact "would add" lines,
   and touches nothing (config md5 unchanged — asserted by `test/zfsbackup`
   section 57). `--apply` builds the candidate via `emit_client_sections is_new=0`
   (preserves installed policy, adds only the missing source prunes), runs the same
   per-client fail-closed grant gate as activation, validates through the real
   `gen-cron.sh`, previews via `show_activation_proposal`, confirms, then
   `atomic_replace_and_install`. No profile reapplication (existing relationships
   are never silently repaired), no new retention language.
7. **Candidate edit/revalidate/re-preview.** The candidate is CONFIG v4 text; both
   source and target `[prune:]` are separately editable native sections rendered
   through the real `gen-cron.sh`, previewed before `atomic_replace_and_install`
   reads it back — one representation, no second parser.
