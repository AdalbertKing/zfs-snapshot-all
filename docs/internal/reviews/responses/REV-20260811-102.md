## F3 residual — IMPLEMENTED — bound THIS relationship's managed family, not any prune on the scope

ACCEPTED. `8cb28f3`'s `source_scope_is_bounded` matched **any** `delsnaps` line
naming the exact scope. That is stronger than a header but still false-green in two
valid CONFIGs the reviewer named: a `[prune-bookmarks:<scope>]` renders
`delsnaps -B … "scope" …` (deletes bookmarks, never `automated_hourly_*` snapshots),
and a `[prune:<scope>]` may prune an unrelated prefix — both satisfy the old grep
while this relationship's managed snapshots stay unbounded.

Fix: `source_scope_is_bounded` now discriminates the rendered command's snapshot-prune
semantics (still no second CONFIG parser — it reads gen-cron's own output):

- a bookmark cleanup (`delsnaps -B`) is excluded — it does not delete snapshots;
- the prune's pattern argument must COVER the managed source family: the managed
  prefix must begin with the pattern, so every `<managed-prefix>*` snapshot matches.
  The managed prefix is read back from the relationship's own `snapget -m` transfer
  line in the render (`managed_source_prefix_for_scope`), falling back to the
  high-level default `automated_hourly_`;
- the line must carry a finite count/GFS retention flag (`-H24`/`-c 24`/`-d 30`).

Negative controls (`test/zfsbackup` section 57): same scope + `prune-bookmarks` only
→ still reported missing; same scope + snapshot prune of an unrelated prefix → still
missing; same scope + managed-prefix bounded prune → bounded. Plus the earlier F3
controls (header that renders no delsnaps → missing).

## F4 — IMPLEMENTED — `--apply` adds only missing source retention, no topology repair

ACCEPTED. The first cut called `emit_client_sections … is_new=0` (the ordinary
reactivation path), which refreshes `[dataset:]` `src`/`flags` to the currently-loaded
endpoint and can move an existing source-prune endpoint — so a retention retrofit
could perform an unrelated topology refresh, especially when client state and the
installed CONFIG disagree.

Fix: `--apply` no longer calls `emit_client_sections`. A new NARROW emitter
(`emit_missing_source_prune`) appends ONLY the missing source `[prune:]` sections and
their `__src_` templates; existing `[dataset:]`, target prune, and existing bounded
source prunes are left byte-identical. The source scope is read from the INSTALLED
`[dataset:]` `src` (`installed_dataset_src`) — CONFIG is truth, not client state. If
the client's current endpoint DISAGREES with the installed `src`, the retrofit
REFUSES and tells the operator to reconcile (re-activate) first: no opportunistic
endpoint repair, and no grant-checking/pruning the wrong host.

Discriminating regression (section 57): a client whose current endpoint (10.9.9.9)
differs from the installed `src` (10.7.7.1) → `--apply` refuses, config byte-identical.
With agreeing endpoints → `--apply` adds a bounded source prune at the installed
endpoint and the `[dataset:]` `src` line is byte-identical (topology not rewritten).

## Answers to the 7 questions

Full detail in `docs/discussions/PHASE5-SOURCE-RETENTION-DESIGN-2026-08-11.md`
(Q1-Q7 there); summarized here against the current implementation.

1. **Exact native CONFIG sections.** PUSH: `[dataset:<root>]` (send) +
   `[prune:<root>]` (SOURCE, non-recursive, `__src_keep_*`) + `[prune:<target>]`
   recursive (TARGET). PULL: `[dataset:<local-target>] src=acct@host:source` +
   `[prune:<acct@host:source>] ssh_flags=…` (SOURCE remote, `__src_keep_*`,
   non-recursive, monitor-free) + `[prune:<local-target>]` recursive (TARGET). Two
   independent `[prune:]` families from the same preset ladder.
2. **Source-prune recursion/scope.** Follows the dataset's own coverage: the
   default non-recursive source prunes only the named dataset (`delsnaps -G` without
   `-R`); a flat/atomic source would need a matching recursive source prune — not
   exposed yet, so no blanket `recursive=yes`.
3. **Remote prune reuses the relationship SSH.** `ssh_flags` = the pull's own
   transport (`-K LOAD_KEYFILE -k LOAD_ALIAS_KH -O HostKeyAlias=LOAD_ALIAS …`) minus
   `-b`; scope `acct@host:source` is the same identity/host-key pinning as the
   transfer. Live-proven: pve1 collector ran the emitted `delsnaps -G` over the
   zfsbackup account's SSH to source pve2, pruning `hdd/backuptest/rev102remote`.
4. **Grant already includes `destroy`, verified fail-closed, no widening.** Yes:
   `do_commit_scope` (`deploy.sh --commit-scope`) already delegates `destroy` per
   source dataset. `assert_source_prune_grant` reads `zfs allow` over the pinned SSH
   and refuses unless the account's own line carries `destroy` — verify, never
   widen. Fail-closed unit-tested (`test/zfsbackup` section 55: with/without
   `destroy`, ssh error, one-of-many). Confirmed read-only that production source
   datasets hold `destroy`. NOT provable live-negative in this estate: the whole
   `hdd/backuptest` tree grants `destroy` by inheritance, so no live no-`destroy`
   location exists.
5. **No usable bookmark/common snapshot, incl. recursive.** The default equal ladder
   reduces but does not by itself guarantee continuity. The source prune touches
   only `automated_hourly_` snapshots, never bookmarks. The one open sub-decision
   (hard-refuse vs explicit FULL-resend warning on recursive relationships) stays
   tied to live evidence and is NOT decided from a shorthand — see Q4 in the design
   doc. This is the piece I most want reviewer input on.
6. **Smallest migration path (step 5) — IMPLEMENTED.** `zfs-backup.sh
   audit-source-retention` scans the installed CONFIG; for each active pull
   relationship it reads the source scope from the installed `[dataset:]` `src` and
   checks whether the config rendered through `gen-cron.sh` bounds it (F3 — effective
   retention, not a header). Default is read-only: it reports the missing count,
   names each missing section, prints the exact "would add" lines, and touches
   nothing (config md5 unchanged — asserted by `test/zfsbackup` section 57).
   `--apply` appends ONLY the missing source prune(s) via `emit_missing_source_prune`
   (F4 — never `emit_client_sections`, so no topology refresh; refuses on a
   client/CONFIG endpoint disagreement), runs the same per-client fail-closed grant
   gate as activation, validates through the real `gen-cron.sh`, previews via
   `show_activation_proposal`, confirms, then `atomic_replace_and_install` (F5 —
   transaction tested end-to-end). No profile reapplication, no new retention language.
7. **Candidate edit/revalidate/re-preview.** The candidate is CONFIG v4 text; both
   source and target `[prune:]` are separately editable native sections rendered
   through the real `gen-cron.sh`, previewed before `atomic_replace_and_install`
   reads it back — one representation, no second parser.
