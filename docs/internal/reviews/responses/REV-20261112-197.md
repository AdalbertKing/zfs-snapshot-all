## F1 — IMPLEMENTED

### Analysis

The reproduction is correct. `prune_source_family` used the exact family (`-m`) plus
"older than the head just sent" as its whole authority. Medium B therefore deleted
medium A's last common snapshot whenever A's bookmark was missing. A bookmark refresh is
best-effort by design (`record_send_bookmark` destroys the old bookmark first, logs a
warning and continues), so a missing bookmark is a normal outcome, not a fault the
pruner could rely on never seeing. The race in the hold-to-bookmark window is the same
defect: B's prune does not wait for A's proof.

The authority to prune must come from the target that was just written. It must not
depend on anything other media are expected to keep.

How this meets the required outcome ("preserve a validated usable source snapshot or
matching per-target bookmark for every affected completed copy"): the repair keeps
the **source snapshot**, not the bookmark. B's run cannot remove A's remaining base,
because that base is never on B (points 1 and 2 below). So A's base survives whatever
happened to A's bookmark and whenever B runs. The bookmark stays best-effort and is
no longer part of the pruning decision. No lock across jobs is needed for the
hold-to-bookmark window: B never has a candidate that is A's.

### Implemented change

1. **Prune only what this target holds** (`snapget.sh` `prune_source_family`, commit
   `6624cdf1`). The function now receives the target dataset. It reads the target's
   snapshot GUIDs (`zfs list -H -o guid -t snapshot -d 1 <tgt>`). A source snapshot
   of the family is a prune candidate only if its GUID is among them. The source is
   listed as `name,guid`, locally or over the same ssh path as before. If either
   listing fails or the target list is empty, the run logs a warning and prunes
   nothing; the copy itself stays successful.
2. **`--source-keep` requires `-i`** (same commit). With `-i` a run sends only the
   snapshot it has just made, so a snapshot made for medium A never reaches medium B.
   Every source snapshot B holds is therefore B's own base, and B can never prune A's
   base. This holds whether or not A has a bookmark, and whether or not A's run is
   still between hold release and bookmark creation. Without `-i` a run sends all
   intermediates, so a GUID could sit on two media at once, and the rule in point 1
   alone would let B remove A's only base. That combination is refused before any
   snapshot is made (`Error: --source-keep needs -i: ...`).
3. **gen-cron** (`bc6e5c05`): an active keep replica gets `--source-keep=1` only when its
   history is `-i`. A keep replica with history "all" (no `-i`) has no source
   pruning, as before W5; `delsnaps` still prunes by age.
   W5 is not released (1.0.20 does not contain it), so no installed job changes.
4. Docs (`af2e8f39`): CHANGELOG [Unreleased], REFERENCE (EN) / REFERENCJA (PL),
   PROJECT_STATUS, ENGINE-FREEZE refreeze, PROTOCOL heading.

The remaining source retention is bounded: each medium of the family keeps its own
newest snapshot on the source. That is one snapshot per medium, as the retention case
shows (three media, three own snapshots). It is not one per family. Shared-prefix
configurations keep working; nothing is reseeded and no `-f` is chosen for the
operator.

## F1 round 2 — IMPLEMENTED

### Analysis

Both findings are correct. Round 1 proved ownership by "this target holds the GUID" and
argued that `-i` keeps the media disjoint. That argument covers only snapshots the
`--source-keep` runs themselves send:

- **F1a:** B can already hold A's head from history copied before (a history-all run, an
  `-H` seed, an import);
- **F1b:** `-H` with `-i` sends the full history on the first run, so a fresh C gets A's head.

In both cases round 1's pruner deleted A's only base whenever A's bookmark was missing.
The claim in round 1 ("A's base is never on B") was wrong.

Holding a GUID is not ownership, and nothing on the target can prove ownership. So
ownership is recorded where the snapshot is created.

### Implemented change

- `snapget.sh` `mark_source_owner`: in a `--source-keep` run, the snapshot the run has
  just made is stamped on the source with the user property `zfsbackup:srckeep-owner=<tag>`,
  where `<tag>` is `bookmark_target_tag` of the target dataset and `-j`, the same tag as
  the `#tgt-` bookmark. A remote source gets the stamp over the same ssh path. If the
  stamp cannot be set (e.g. no `userprop` delegation), the run logs a warning and goes
  on; that snapshot is then never prunable.
- `prune_source_family`: a snapshot is a prune candidate only if it is in the family
  (unchanged), carries **this** target's stamp, and the target holds its GUID (round 1).
  The sent snapshot must itself be a candidate, or nothing is pruned (unchanged rule).
- What stays on the source:
  - unstamped snapshots: earlier history, `-H` seeds of older points, snapshots made by
    hand or by another job;
  - snapshots stamped by another target.

  This is the conservative choice the review asks for: an ambiguous base is kept, no
  reseed is chosen for the operator.
- Each medium's head is the snapshot its own last run made and stamped. Only that
  medium's later runs may prune it, and never its newest, so every medium keeps its base
  on the source whatever happened to its bookmark.
- `-H` is not refused: with the stamp it cannot hurt another medium (F1b test). Existing
  overlap is handled by the same rule (F1a test): it is unstamped, so it stays.
- `--source-keep` still needs `-i` (unchanged since round 1). It keeps one snapshot per
  run on each medium; it is no longer the safety argument.
- Unchanged: `gen-cron.sh`, `lib-zfs-snap.sh`, `snapsend.sh`.
- Docs: `snapget.sh` help, CHANGELOG, REFERENCE (EN) / REFERENCJA (PL), ENGINE-FREEZE
  (refrozen, with a correction of round 1's claim), twins reason and baseline,
  PROJECT_STATUS.

Cost, stated: snapshots of the family made before W5, or sent by an `-H` run as history, are never removed by
`--source-keep`; they need `delsnaps` or a manual destroy. W5 is unreleased, so no
installed job has stamped snapshots yet.

### Remaining risk

- Someone can set or copy `zfsbackup:srckeep-owner` by hand onto a snapshot. Then that
  snapshot counts as the named target's own. That is an explicit operator act, not
  something history or seeding produces.

  that copy is later the source of another `--source-keep` job, the stamp names the

## F1 round 4 — IMPLEMENTED

### Analysis

ACCEPTED. F1d is real, and the round-3 serial tests could not catch it, as the Reviewer
says. After a successful quiesce window, `process_dataset` still picked `src_snaps[-1]`,
the newest snapshot of the `-m` family. The round-3 guard only decided whether to stamp
that snapshot, not whether to copy it. Locks are per source+target+`-j`, so job B on another
target can make a newer snapshot of the family between A's window and A's selection. A
then copies B's point and depends on it; B owns that point and prunes it.

The root of the defect is the selection, not the stamp. The window always names its
snapshots `${SNAP_MESSAGE}${RUN_SUFFIX}`: local quiesce at `snapget.sh:3361`
(`quiesce_snap_suffix="$RUN_SUFFIX"`), remote at `snapget.sh:3431`
(`quiesce_suffix="$RUN_SUFFIX"`), and the push twin at `snapsend.sh:2911`. So "the
snapshot proved created by that window" is that exact name, on every quiesce entry path.

### Implemented change

- `snapget.sh` `process_dataset` (from line 1911): when `QUIESCE_SNAPPED=1`, the run
  selects exactly `${SNAP_MESSAGE}${RUN_SUFFIX}` from the family list. If that name is
  not on the source, the run logs "refusing to copy another snapshot in its place" and
  returns 1. It never substitutes another snapshot. A newer foreign snapshot is named in
  a level-1 log line and left alone (not copied, not stamped, not pruned by this job).
  The stamp is still set only in this branch, on the selected own snapshot.
- `snapsend.sh` `process_dataset` (from line 1585): the same selection rule (shared
  logic, twins row 16 says so). The push twin has no `--source-keep`, but copying another
  job's point after its own quiesce window was the same defect there.
- Docs: CHANGELOG, `docs/en/REFERENCE.md` and `docs/pl/REFERENCJA.md` (the Quiescing
  section), ENGINE-FREEZE entry with its `twin:` line, refrozen. Twins reason and
