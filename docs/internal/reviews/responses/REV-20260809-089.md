#### The topology-owned field set, justified rather than guessed

The review requires the set be derived from current runtime contracts. It is
derivable mechanically: `emit_client_sections()` writes exactly four fields of
its own beyond the profile fragment, and each is a function of one input.

| field | value written | depends on | changes on reactivation? |
|---|---|---|---|
| `src` | `${LOAD_ACCOUNT}@${LOAD_HOST}:${ds}` | `LOAD_ACCOUNT`, `LOAD_HOST` — set by `load_client_and_connection()` from the client record's `ACTIVE_ENDPOINT`/`ENDPOINT_*_HOST` | **yes** — `set-endpoint` writes exactly these |
| `flags` | `$LOAD_FLAGS` | `LOAD_FLAGS` — transport options (`-K`, port, cipher) from the same loader | **yes** — same command, same reason |
| `pair_label` | `$name` | the relationship name | no |
| `notify` | `${name}-$(basename "$ds")`, or `${name}` for the backup ladder | `$name` and `$ds` | no |

`src` and `flags` are therefore the topology-owned pair, and they are also
precisely the reason the unconditional remove-then-add existed at all — the
comment at the old call site says so in as many words ("that is what makes a
re-run after an endpoint switch actually pick up the new host/port/alias").

#### `pair_label`/`notify` are left untouched, and why that is safe

The review asks for proof in the direction of *rewriting* them. The
implementation does the opposite — it does not rewrite them — so the obligation
is to show that not rewriting them cannot leave a stale value:

- `$name` is the relationship identity. It is the client record's file name
  (`client_conf_path "$name"`) and its `CLIENT_NAME` field. There is no rename
  command in `zfs-backup.sh` (`grep -n 'rename' zfs-backup.sh` returns
  nothing); a differently-named relationship is a different client record with
  its own sections and its own ownership marker. So `$name` cannot differ
  between two activations of the same relationship.
- `$ds` is the dataset path. A dataset whose path changed is not the same
  dataset: it fails the `section_owned_by` lookup for its new path and lands in
  the regeneration branch, where the section is written fresh from scratch
  including `notify`.

Both fields are therefore pure functions of inputs that are invariant across
the reactivation of an existing dataset. Rewriting them could only ever write
back the identical string. Leaving them alone is that same result, plus it
preserves an operator edit — strictly the safer of two semantically identical
choices, which is why the implementation takes it.

#### `[prune:]` sections carry no topology-owned field at all

Neither prune shape contains `src` or `flags` — a prune section is profile
policy plus `recursive` plus the two name-derived labels. So the correct
reactivation action for an owned prune section is not "refresh some fields", it
is "do not touch it". Both shapes are handled that way:

- **backup mode**, one recursive GFS ladder at `$PEER_SAVED_TARGET/$LOAD_LABEL`:
  a dataset newly in scope lands *under* that ladder without the section needing
  to change, so an already-owned ladder is left alone even when some datasets
  are regenerated. (`LOAD_LABEL` is `peer_label "$PEER_HOST"`, and `PEER_HOST`
  is the pairing peer, not the endpoint address — `set-endpoint` does not move
  it, so the ladder's own path is stable across an endpoint switch.)
- **sync mode**, one `[prune:]` per dataset at the *same path* as its
  `[dataset:]`: preserving the dataset section means never calling
  `remove_managed_sections` on that path, which would let the prune half escape
  the ownership check. So sync mode requires **both** halves to be owned before
  either is preserved; otherwise the pair is regenerated and the existing
  fail-closed refusal still fires.

#### Fail-closed behaviour is preserved, not relaxed

`section_owned_by()` applies the *same two tests* `remove_managed_sections()`
applies — the marker as the section's first content line, or the path already
recorded in this client's own `MANAGED_DATASETS`/`MANAGED_PRUNE_SCOPE` — and
nothing else. A header match alone is still not ownership (REV-20260802-033
U11). An unowned header therefore does not get preserved; it falls through to
the regeneration branch, where `remove_managed_sections()` refuses it with its
existing "looks hand-written" message, unchanged.

One new refusal was added rather than a silent no-op: if an owned section has
no `src` (or no `flags`) line to refresh, `update_section_field()` returns 3 and
activation dies. Writing nothing would leave the relationship pointing at the
*old* endpoint with a successful exit status — the exact failure mode this
change exists to prevent, reintroduced at a different layer.

#### `migrate-profile` is the one caller that must keep regenerating

`cmd_migrate_profile()` also calls `emit_client_sections()`, and its entire
purpose is to re-derive policy from the new profile. It now passes `1`
explicitly, with a comment saying why. Defaulting the parameter to `0` and
letting that call site inherit it would have silently turned migrate-profile
into a no-op — this is the REV-088 F1 lesson (ask which call sites reach the
new code and whether *each* wants the property) applied in the opposite
direction.

### Planned or implemented change

`zfs-backup.sh`:

- new `section_owned_by()` — non-mutating form of `remove_managed_sections()`'s
  ownership test;
- new `update_section_field()` — replaces one field's value inside one section,
  keeping everything up to and including the original `=` so hand formatting
  survives; returns 3 when the field is absent;
- `emit_client_sections()` gains a third parameter `is_new_relationship`
  (default `0`), and splits its dataset list into a preserved set and a
  regenerated set instead of removing everything;
- `cmd_activate_client()` passes the `is_new_relationship` it already computes
  for REV-088;
- `cmd_migrate_profile()` passes `1` explicitly.

`test/zfsbackup/run.sh`: new section 49, eleven assertions.

Step 6 deliberately expresses the profile drift in **valid** profile fields
(`recursive` in `dataset.inc`, a changed `gfs_pattern` in `prune.inc`). A first
attempt used an invented field name; the profile boundary refused it, so the
call died and the test would have "passed" for the wrong reason — a green
result proving only that an invalid profile is rejected. Recorded because it is
the same class of contaminated control this project has hit before.

The suite drives `emit_client_sections()` with `MANAGED_DATASETS` and
`MANAGED_PRUNE_SCOPE` deliberately **empty**, so ownership must be proven by the
marker the function itself wrote on the previous call rather than by the client
record — the harder of the two ownership tests, and the one a freshly written
record relies on.

### Remaining risk

- **`zfsbackup-live-pair` not run here.** The change is a deterministic
  CONFIG-composition change: no host-state mutation, no crontab install
  semantics, no dataset-set reconciliation, no transfer behaviour. Per the
  review's own boundary no new live campaign is required, and `89 step 6b`
  crosses the real `gen-cron.sh` boundary locally. Left `IMPLEMENTED`, not
  `CLOSED`.
- **Deferred, unchanged:** a dataset that *disappears* from the peer's committed
  scope still keeps its stale section. That is the pre-existing deferred
  source-removal/dataset-set reconciliation item in `ACTIVE-WORK-PLAN.md`; per
  the review's scope note it is not solved here, and nothing in this change made
  it worse — the stale section was orphaned before and is orphaned now.
- **A prune scope whose path changes** (a different `LOAD_LABEL`) would orphan
  the old ladder. Also pre-existing: the old code removed only the *new* scope's
  path too. Not reachable by `set-endpoint`, which does not move `PEER_HOST`.
