# Response to REV-20260908-138

## F1 — IMPLEMENTED

### Analysis

The finding is correct and the discriminator is better than the one I shipped.

`list-jobs` checked `[ -f "$cfg" ]` and then consumed `config_section_dump`
through process substitution. `-f` proves the path is a regular file; it does
not prove the file can be OPENED, and a producer inside `< <( )` has no exit
status the loop can reach. So awk's refusal went to stderr, the `while` loop saw
no lines, and an empty parse was indistinguishable from a config with no
sections. Reproduced here against the reviewed implementation
`1f6a1b38454824d9bf73bfbf6e017f0fc160f856`, with a parser failing the way awk
fails on a file it cannot open:

```text
{"host":"","jobs":[],"count":0,"unreadable":[]}
```

That is this verb recreating, for a different reason, the exact failure it was
written to prevent: a managed block running an engine line while the window
reports no work and no diagnostic. The review is also right that this is not an
exotic path — an ordinary root-owned config read by a delegated account has the
same shape, and my own negative fixture could never reach it, because a
nonexistent path fails the `-f` check one line earlier.

### Planned or implemented change

**The parse is the readability test, and it is buffered before anything is
published.** `config_section_dump` now writes to a temporary file and its exit
status is checked; only then is that file iterated. A failure is routed to the
same "cannot explain these lines" diagnostic as a missing `# Source:` header:

```sh
if [ -n "$cfg" ] && [ -f "$cfg" ]; then
    dump=$(mktemp) || die "list-jobs: mktemp failed"
    if ! config_section_dump "$cfg" > "$dump" 2>/dev/null; then
        rm -f "$dump"; dump=""
    fi
fi
[ -n "$dump" ] || { jobs_note_unreadable "$acct" "$cfg" "$nlines" "$as_json"; continue; }
```

Buffering before publication is the discipline REV-20260907-136 imposed on the
other readers, applied here to the producer rather than to the record: nothing
is emitted for a source that was refused.

The two ways of reaching that diagnostic — no readable header, and a header
whose parse fails — now share one emitter, `jobs_note_unreadable`. Two copies of
a diagnostic drift the moment one of them learns a field the other does not
have, which is the shape this tree kills with contracts.

`rc=0` is retained, per criterion 3: this verb reports, it does not judge the
host. The `unreadable` element carries `account`, `config`, `lines_in_block` and
a sentence, which is what a front end needs to paint a non-green state without
reading stderr.

### Remaining risk

One adjacent case is **not** covered by this change, and I am naming it rather
than quietly widening the scope of the finding: a config that opens and parses
cleanly but declares **no** `[dataset:]`/`[prune:]` section for an account whose
block is running engine lines. Today that account contributes no job row and no
diagnostic — the same "window shows nothing" shape, from a third cause.
Measured while building this fix: an account with a one-line block and a config
containing no sections produces `jobs:[]` for it and no entry anywhere.

It is not "unreadable", so widening that array would be the wrong word, and
inventing a third category is a design decision rather than a defect fix. If the
Reviewer wants it in this REV, the cheapest honest shape is a per-account
`declared`/`lines_in_block` pair a front end can compare; I would rather be told
than guess.

**A second thing the lab surfaced, and it is NOT mine to fix in this REV.**
Running as the delegated account, every row is attributed to `root` while the
lines live in that account's own crontab. Measured on pve10:

* the account cannot list `/var/spool/cron/crontabs` (mode `1730 root:crontab`),
  so `cron_known_accounts` enumerates only `root`;
* `cron_is_self()` in `lib-cron.sh` is `[ "$1" = "$(id -un)" ] || [ "$1" = root ]`,
  so asking for `root` runs a bare `crontab -l` -- the CALLER's crontab -- and
  the rows are then labelled `root`.

The rows themselves are right; the account label is not, and it points an
operator at a crontab that does not hold those lines. This is pre-existing
shared machinery: `cmd_monitor` walks the same loop and mislabels the same way.
Changing `cron_is_self` touches every writer path (deploy, gen-cron install), so
it belongs in its own review rather than inside a P2 fix -- reported here
because this REV's verification is where it was measured.
