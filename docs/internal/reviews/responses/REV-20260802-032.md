## F1 — a failed ledger append must account for the whole set — ACCEPTED, IMPLEMENTED

### Analysis

Accepted in full. The finding is exactly right, including the part I would have
argued about if it were wrong: `zfs snapshot` is atomic per **pool**, so at the
moment an append fails, the entire group already exists and earlier pools may
exist too. Printing the one failing name and exiting was an alarm about a
snapshot, in a design whose whole premise since REV-030 is that the **set** is
the unit.

Reproduced on the pre-fix code before changing anything — three snapshots
created across two pools, ledger broken between them:

```
rc=7
QERR could not record tankb/y@t in the created-snapshot ledger,
     so this run cannot guarantee to remove it. ROLLBACK INCOMPLETE:
destroys issued: 0
```

`ROLLBACK INCOMPLETE` with **no rollback attempted**, one name out of three,
and `tanka/x@t` and `tankb/z@t` left as ordinary snapshots.

### Implemented change — not the one the review sketched

The review's preferred contract is a second inventory holding what the first
could not. I built it, and building it is what exposed the real problem.

To test it I had to break the ledger *between* pools, so pool one was recorded
and pool two was not. Every portable way of doing that — replacing the file with
a directory — also **destroyed pool one's record**. The run could then no longer
name a snapshot it had really made, and would have reported a clean rollback
while a snapshot survived.

That is not an artefact of the stub. It is what a file-backed ledger is worth
once writing to it stops working, and no amount of second inventory fixes it,
because the second inventory only ever holds what the first refused *after* the
refusal began.

So the file is gone. **The ledger is an array**, exactly as the local path has
always used:

- nothing outside that shell ever read the file — not the deadman, not
  `on_exit`, not a subshell — so the storage that could fail bought nothing;
- an array append cannot fail, so there is no failure mode to handle, no second
  home a survivor can hide in, no rule that a snapshot must appear in exactly
  one of two places or be destroyed twice, and no exit code for a bookkeeping
  error that can no longer happen;
- it is appended to only **after** `zfs snapshot` returns success, so a planned
  name is never mistaken for a created one — the review's own caveat, and the
  reason cleanup never destroys on a guess;
- both paths are now the same shape, which also retires the asymmetry note the
  previous response had to carry.

The per-snapshot rollback moved into `abandon_one`, so the walk has one
definition rather than one per inventory.

## A trap found while paying the suite debt — fixed in `52ec5e6`

Run as **root** on a host, `test/quiesce/run.sh` reported **42 failures** with
names like *"a delegated run never calls qm"*. None was about the code: the
remote script picks its route from `id -u`, and every stub in that suite models
the delegated route.

Verified against an **unmodified** `main` (`769395e`) on pve1 — 103/42 as root,
161/0 as `zfsbackup` from the same checkout — so it predates this change and is
environmental. The suite now refuses to run as root, exits 2 and names the
invocation that works. A suite whose wrong invocation is indistinguishable from
a broken tree is worse than one that refuses.

## Remaining risk

`zfs destroy` can still fail for reasons that outlive the run — a hold, a clone,
a busy dataset — which is what exit 7 is for, and an operator has to act on it.
The message names every survivor and the exact command.

No managed block on the fleet uses remote quiesce today; all four hosts take
local snapshots only. The code is therefore proven by suites and by the campaign
between pve1 and pve2, not by nightly production traffic.
