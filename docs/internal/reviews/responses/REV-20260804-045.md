# Response to REV-20260804-045

## Scope declaration (required before coding)

**Logical pause only** — `pause-client` / `resume-client` / `status`, owner
decision 2026-08-06 confirming the leaning recorded 2026-08-04. The peer-side
SSH hard-disable gate (`disable-pair`/`enable-pair`) is NOT part of this
implementation; those verbs are not created, not aliased, and not simulated.

The documented limitation is retained verbatim and repeated everywhere the
feature surfaces (CLI help, status output, PROJECT_STATUS, this file):

> Local logical pause is an **orchestration feature, not a security
> boundary**. A managed cron job or a manual command carrying the
> relationship label is blocked; a raw manual `snapget.sh`/`snapsend.sh`
> that omits the label is NOT blocked. Nothing in this stage claims that
> manual transfers are impossible while paused.

Nothing here is named `allow`/`unallow`, and no routine toggle touches
`zfs allow`, key material, cron content, or relationship identity.

## Design decisions (mapped to the review's boundaries)

1. **Cron is not edited** (boundary 1). The generated transfer command
   carries the relationship identity as a new short option `-L LABEL` on
   both `snapget.sh` and `snapsend.sh` (both parse single-letter `getopts`
   only; `-L` is unused in both, and is not part of the five-flag
   ssh-flag-parity contract). The preflight runs after argument parsing and
   before any lock, snapshot, hold, SSH, or stream setup, and exits 0 with:

   ```text
   SKIPPED: relationship LABEL is paused
   ```

2. **Stable identity** (boundary 2). `-L` carries the client NAME from the
   `/etc/zfs-snapshot-all/clients/NAME.conf` record — the durable enrolment
   identity the review names, not an endpoint. All of a client's datasets
   and endpoint candidates emit the same label; an endpoint switch rewrites
   `src`/aliases but never the label.

3. **State storage** (boundary 3).
   `/var/lib/zfs-snapshot-all/relationships/LABEL/paused` — a marker file
   holding timestamp + optional reason, written by root's CLI via the
   stage-then-rename pattern already used for grants, readable by the
   delegated accounts that run the jobs. Strict label validation (the
   existing `peer_label` character class, plus "must resolve to an existing
   client record" for pause; resume also accepts a stale label to allow
   cleanup). Idempotent both ways; `remove-client` clears the exact
   relationship's state directory; `add-client` refuses to inherit a
   pre-existing marker silently — it reports and clears it, so a reused
   label cannot import an old pause.

4. **In-flight behavior** (boundary 4): pause blocks the NEXT run's
   preflight; a transfer already past preflight finishes. `pause-client`
   reports when the relationship's lock/process is currently held and says
   the current run will finish. No kill, no abort.

5. **Monitoring** (result-shape requirement). A paused relationship must
   neither report as a fresh success nor produce ordinary staleness noise:
   - the skip is logged as its own distinct state (`SKIPPED_PAUSED`) in the
     stats log, never as a completed transfer;
   - `check-snap-age.sh` gains the same `-L LABEL`; while the label is
     paused it exits OK with wording naming the pause (`OK -- relationship
     LABEL is paused; staleness is expected`), so expected staleness does
     not page, and resume restores normal thresholds with no other change;
   - `zfs-backup.sh status NAME` shows `PAUSED_LOCAL` with the timestamp
     and reason.

6. **Config carriage**: `emit_client_sections` writes one new optional
   field `pair_label = NAME` into its generated `[dataset:]` sections;
   `gen-cron.sh` forwards it as `-L NAME` on the emitted
   `snapget.sh`/`snapsend.sh` line and on that dataset's
   `check-snap-age.sh` monitor lines. Hand-written configs without the
   field behave exactly as today (absence = no label = no gate).

## Found live during slice 4 (metropolis)

1. **lib-cron lock file unshareable after a root-first touch** (fixed,
   `62e190d`): root-side `activate-client` created
   `locks/lib-cron.zfsbackup.lock` 0644 root-owned; the account's own
   `gen-cron --install` then failed "could not open the lock file" --
   permanently. REV-035 fixed the lock PATH; this was the same failure one
   level down (the FILE's mode). `cron_lock_acquire` now chmods 664 after
   create, refusal names the one-line fix, test/cron section V pins both.
   One-time live remediation applied on pve1 (`chmod 664` both lock files).
2. **One relationship per host pair is a hard design constraint.** Enrolling
   two clients against the SAME peer address entangles them at both ends
   (shared peer manifest keyed by address on the collector, shared state
   keyed by the collector's label on the peer): the second join overwrote
   the first client's dataset list, and its activation was then refused by
   the U11 ownership marker (the guard worked). This matches the owner's
   production driver (several DIFFERENT-site peers per collector) and is
   recorded here as a documented constraint, not changed. The live
   isolation test uses a throwaway LXC as a genuine second peer
   (the Gate G pattern) for relationship B.
3. **pve1's account cron block had drifted behind its config** (the
   reserved-prefix -P protections were in the config since setup-server
   added the [excluded:] sections, but the installed block predated them);
   activate-client's deletion guard refused to install over the drift --
   correctly. Reconciled with a plain account-side `gen-cron --install`
   (diff reviewed first: only the four prune lines gained -P flags).
