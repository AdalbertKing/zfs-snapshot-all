# Response to REV-20260729-003

Delivery: direct to `main`, per the owner-approved exception this review records.

## F1 — hourly rollback point is not durable — ACCEPTED, IMPLEMENTED

Correct on all three counts, and I had claimed durable rollback on the strength
of a mechanism that did not provide it.

- the cron line wrote the CURRENT revision every hour whether anything had
  changed or not, so an hour after a bad update the recorded "rollback point"
  was the bad revision itself;
- a `git reset --hard` was undone by the next hourly pull, so the rollback
  lasted until the next `:15` unless the operator also disabled cron;
- nothing established that anything was good, while the file was called
  `last-known-good`.

### Implemented change

`d5c96d6`, fixed up in `656a09b`. Three modes replace the inline cron command:

| | |
|---|---|
| `--self-update` | what cron runs hourly |
| `--rollback` | reset to the recorded revision **and hold** |
| `--resume-updates` | drop the hold and update deliberately |

State lives in `$ALERT_SHARED_DIR`, renamed to say what it is:
`previous-revision` (not `last-known-good` — no health gate establishes good)
and `update-hold`.

Behaviour against each acceptance criterion:

- **a no-op run does not overwrite the pointer** — the revisions are compared
  first and the function returns before touching anything;
- **a real A → B records A before activating B** — and if the fast-forward then
  fails, the prior pointer is restored, so a failed update does not consume the
  rollback point either;
- **rollback prevents the next hourly run from restoring B** — that is what the
  hold is for; the hourly run logs that it is held and does nothing;
- **an explicit resume command exists** — `--resume-updates`, printed by
  `--rollback` itself at the moment it is needed;
- **failure leaves the active revision usable** — verified as its own case;
- **honest naming** — `previous-revision`;
- **no duplicate cron jobs** — every shape the line has ever had is matched and
  removed before one is appended.

The three modes are dispatched **before** the root check and before every
deployment phase. Cron runs the first hourly, and a rollback has to work when
the thing being rolled back is what broke, so it must not drag apt and alerting
along behind it. There is deliberately no `id` check: what protects these is the
filesystem — `$REPO_DIR` is root-owned — and an id check would have made the
whole path untestable without root, which is how the previous version shipped
untested. One caveat is named in the code rather than hidden: the state
directory is group-writable by `zfsalert`, so that account can create a hold.
It already runs the backups, so this is not a new privilege, but it is not
nothing either.

### Three mistakes of my own in getting here, all found by running it

1. **The first version of the suite scored itself on nothing.** The modes were
   still behind the root check, so two cases reported PASS while nothing had
   executed. There is now a canary that aborts the run instead of scoring it.
2. **I broke `deploy.sh` and pushed it** (`d5c96d6`): the self-update block is
   dispatched near the top of the file and read `ALERT_SHARED_DIR`, which was
   defined two hundred lines lower, so every plain invocation died on `unbound
   variable`. Nothing caught it because every case in the new suite passes that
   variable in the environment, `bash -n` cannot see it, and no suite runs
   `deploy.sh` without overrides. The suite now ends with two canaries asserting
   the absence of `unbound variable` — verified to fail 2/13 against the broken
   version. Blast radius was limited by luck, not design: no cron runs
   `deploy.sh`, and backups run other scripts.
3. **Silencing a CRLF warning in the fixture** by setting `core.autocrlf` after
   cloning left the test's worktree permanently modified, so every `--ff-only`
   failed. Set at clone time now.

Separately, `test/selfupdate/run.sh` shipped as `100644` — a `chmod` on Windows
does not reach git, the second time in a day. `impact.sh --verify` already
checked the tracked mode but fell back to the filesystem for a file that was not
staged yet; that fallback now only applies outside a checkout.

### Remaining risk

- No **health gate**: `previous-revision` is honestly named, but nothing proves
  the current revision works. A smoke gate before activating a revision is not
  implemented and is a larger change than this finding asked for.
- If a bad update breaks `deploy.sh` itself, `--rollback` is also broken. The
  fallback is two plain git commands, named in the code comment; that is why
  rollback is deliberately not clever.
- The hold is a file, not a lock. Two operators racing `--rollback` and
  `--resume-updates` can interleave; on a four-host fleet with one operator this
  is not worth a lock.
