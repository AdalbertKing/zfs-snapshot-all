# Response to REV-20260810-097

All three findings ACCEPTED and IMPLEMENTED. They are tightly coupled in
`cmd_local_backup()` (F1 gates before the candidate build that F2 restructures,
F3 is the dispatch onto it), so they land as one coherent commit with the code
and this response; each finding's evidence is separated below.

## F1 — IMPLEMENTED — explicit source must exist

Accepted. A syntactically plain but nonexistent `--source` was planned as if real
— the EXPLICIT-SOURCE contract requires the opposite. `cmd_local_backup()` now
runs `zfs list -H -o name -- "$source"` before anything is rendered; a miss
hard-refuses the whole operation with no fallback and no partial plan. Read-only,
no install.

Regression (`test/localbackup`): a stubbed `zfs` marks a known set of datasets as
existing; `F1/missing-source hard-refuses` proves a typo refuses, `F1/existing-
source proceeds` and `F1/another existing source also proceeds` prove the gate
keys on the ZFS verdict for the same code path — the negative control the finding
asked for (the only difference between refuse and proceed is the stub's answer).

## F2 — IMPLEMENTED — plan is additive over the installed CONFIG

Accepted, and the most important fix. Planning no longer builds `$cand` from
scratch. It now:

- copies the existing target CONFIG into the working copy when one exists, so the
  preview shows old jobs **A** alongside new job **B**;
- when the CONFIG is missing, applies the **same** fail-closed guard the installer
  uses — extracted from `ensure_cron_config` into
  `assert_config_not_claimed_if_missing()` and called from both, so this is one
  safety model, not a second one (the finding's explicit constraint). A missing
  file that an installed crontab block still claims refuses; a genuinely unclaimed
  missing file gets a fresh candidate;
- runs `ensure_cron_config "$cand" 1 1` — the same primitive `activate-client`
  uses — to add profile templates/floors idempotently, exercise template
  reuse/collision, and inherit `[excluded:]` global policy against the real file;
- refuses via `config_section_overlap()` (built on the existing `path_overlaps`)
  when the new source/target overlaps any section already in the file, before
  anything is written;
- previews the **complete** candidate CONFIG and the **complete** rendered cron.

Regressions: `F2/additive: existing A is byte-unchanged and B is added`,
`F2/rendered cron carries both A and B send lines`, `F2/the real target config
file is not mutated by planning`, `F2/overlap with existing coverage refuses`,
`F2/missing config claimed by an installed block refuses`, `F2/missing unclaimed
config gets a fresh candidate`. The guard extraction is behaviour-preserving:
`test/zfsbackup` (which pins `ensure_cron_config`'s missing-file refusal) stays
**363/363**.

## F3 — IMPLEMENTED — bare public entrypoint

Accepted. The dispatch now routes `zfs-backup.sh --source=… --target=…` (bare,
the ACTIVE-WORK-PLAN Phase 5 form) to the same `cmd_local_backup` logic;
`local-backup` remains as an alias, never the required workflow. Usage documents
the bare form as canonical. Regressions: `F3/bare --source/--target reaches the
planning logic` (drives the real script's dispatch, not the function) and
`F3/local-backup alias still reaches the same logic`.
