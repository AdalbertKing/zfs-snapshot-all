# Response to REV-20260908-140

## F1 — IMPLEMENTED

### Analysis

The finding is correct and the severity is right. `cron_block_source()` read the
first `# Source:` line in whatever it was handed, and four of its five callers
hand it the **whole crontab**. cron permits arbitrary comments, so a line above
this project's block decided which config the install guards compared against.
Reproduced with the reviewer's fixture against canonical `main` (`b5035f4b`):

```text
main       : /tmp/want.conf      <- the foreign comment above the block
this SHA   : /tmp/actual.conf    <- the block's own Source line
control (foreign line removed), both builds: /tmp/actual.conf
```

The consequence the review names is the one that matters: with `want.conf`
accepted, `assert_cron_config_matches_installed` would permit replacing the
managed block generated from `actual.conf`, deleting every send, prune and
monitor line that config described.

**Where it came from, stated plainly.** The four inline copies I consolidated in
PR #364 already had this behaviour — `grep -m1 '^# Source: '` over
`crontab_for_target`. I moved five call sites onto one helper and preserved the
defect rather than introducing it, which is worse in one specific way: the
consolidation was justified in its own commit message as removing drift, and I
did not ask what the shared reader was actually reading. A helper is a claim
that five callers want the same thing; checking that claim is part of making it.

### Planned or implemented change

The bounding is inside the helper, not in the callers:

```sh
cron_block_source() {   # <stdin: crontab or block text> -> the config path, or empty
    sed -n '/^# BEGIN zfs-backup-managed/,/^# END zfs-backup-managed/p' \
        | grep -m1 '^# Source: ' | sed -E 's/^# Source: (.*) -- .*/\1/'
}
```

sed does the narrowing rather than each caller, **because the caller that forgets
is exactly the failure this consolidation exists to prevent** (criterion 2: every
full-crontab caller now agrees on the same scoped source by construction —
account discovery, adoption, the warning path and both install guards call this
one function). `jobs_block_config()` already narrowed its own input; passing an
already-narrowed block through the same sed is a no-op, so it keeps working.

Fail-closed is preserved and pinned: a managed block carrying **no** `# Source:`
line yields the empty string, never the comment above it.

### Remaining risk

`assert_cron_config_matches_installed` and `assert_config_not_claimed_if_missing`
are asserted here through the shared reader they both call, not through their own
entry points; both are thin wrappers over that value. A test that drives the two
guards end to end would need a writable crontab and is the kind of live-cron
exercise this project deliberately keeps out of the text suites.

### One thing this REV surfaced that is not in it

While reproducing the fixture I measured, on the real lab, that a relationship
created through the one-command path can end up with **no local retention and no
monitor at all** — `detect_profile_gfs()` reads the whole installed config and a
leftover template from a removed relationship flips the host to "flat", after
which the ladder branch is skipped and `MANAGED_PRUNE_SCOPE` is recorded empty.
Four active lab relationships on pve10 are in exactly that state. That is a
separate finding with its own fix in progress; it is mentioned here only so the
Reviewer knows it was seen and is not waiting behind this one.

### Update 2026-09-09 — the finding above is fixed on this branch, and what it cost

The separate finding got its fix in the same PR (`ec46584e`, `272c09dc`,
`b168b3e4`): only a template a live section USES decides the host's shape,
the ladder is scoped to what the relationship lands (one `[prune:]` per
landing path, not `TARGET/<peer>`), and the clobber guard excuses that one
migration loudly. PR #368 then went red on 29 assertions and stayed red for a
day because the cause was not measured. Measured 2026-09-09 on pve9 (the
suite runs there in 2 min against 20 on this box):

- **18 of them were one regression of mine, not old assertions.** The
  used-only rule is right for a HOST CONFIG and wrong for the PROFILE's own
  rendered templates, which have no sections at all — so `migrate-profile`
  could never read a flat profile as flat, emitted a `[prune:]` with no
  `use_template`, and gen-cron refused the config (96b–96u, 122a–j, rc=1).
  Fixed in `cc1f0174`: `detect_profile_gfs <file> all` for the destination
  profile, regression `gfsshape` control 4 pins both answers for the same file.
- **8 pinned the old peer-root ladder by name** (89, 92, 56/107, field
  survival) and were re-pinned to the per-landing contract in `28bd60ec`,
  including the no-src refusal, which needs an owned `[prune:]` at the landing
  path to be on the preserve path at all.
- 3 were the `PROFILE_LOADED` cache leak in the new `gfsshape` probes
  (`7d5f5d0d`).

Result on pve9, `28bd60ec`: `./test/zfsbackup/run.sh` **768 PASS / 0 FAIL**.
CI for the same SHA is the second reading. The four lab relationships on pve10
were re-activated on this branch on 2026-09-08 and now carry one local

branch until it merges.
