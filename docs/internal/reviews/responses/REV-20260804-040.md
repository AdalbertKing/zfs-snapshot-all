# Response to REV-20260804-040

## F1 — ACCEPTED

Agreed without reservation. The first `--leave` fix (`1f6ca0b`) scanned `zfs
allow`'s output for the first `user (unknown: N)` entry when the account was
already gone, and had no way to distinguish this relationship's orphan from
another relationship's -- or a live delegated account's -- grant on the same
dataset. "First unknown uid" is an output-ordering property, not ownership
evidence, exactly as the finding says.

### Implementation

New `PEER_JOIN_ACCOUNT_UID` field, matching the preferred contract exactly:

1. **Recorded at join time.** `do_join()` captures `id -u "$account"` right
   after creating or confirming the account (the one point it is guaranteed
   to exist under its recorded name), includes it in the atomic manifest
   commit, and `verify_join_manifest()` checks it on both the temp file and
   the final path -- same two-point verification REV-038 already built for
   every other field.
2. **Verified before every grant.** `do_commit_scope()` now checks, before
   computing or applying any grant, that the live account's current uid
   matches the manifest's recorded uid. A mismatch refuses closed with a
   drift/collision message -- the account may have been deleted and
   recreated under the same name since, and granting through that silently
   would attach the new grant to a different real-world identity than the
   one this relationship's history describes.
3. **`--leave` uses only the bound uid.** If the account is live, its
   current uid is used (and checked against the recorded one, same drift
   refusal as commit-scope). If the account is gone, the manifest-recorded
   uid is used directly -- never a scan, never a guess. A legacy manifest
   (joined before this field existed) with a still-live account captures
   and persists the uid before doing anything destructive (contract item 4);
   a legacy manifest with BOTH a missing account and no recorded uid fails
   closed with an exact manual-recovery diagnostic (contract item 4's other
   half) rather than guessing.
5. **Manifest not deleted until the exact uid is proven absent.** The
   post-revoke residue check (F2 below) runs, and only success there lets
   `--leave` proceed to remove the account and then the manifest.

### Evidence

`test/joinmanifest` **10/10** (+3): a manifest carrying the recorded uid
verifies when it matches, refuses when it does not, and a legacy manifest
with no uid field at all still verifies when none was expected (the
optional-field backward-compatibility case).

Live, pve2 (192.168.28.8), the exact scenario the acceptance criteria ask
for -- two accounts delegated on one scratch dataset, then progressively
orphaned:

- **Foreign live account survives.** `zfsbackup-testleave` and
  `zfsbackup-foreign` both delegated on `hdd/backuptest_targets/multitest`.
  `--leave` for the first relationship (recorded uid matching) revoked
  exactly that grant and removed exactly that account; `zfs allow` afterward
  showed only `zfsbackup-foreign`'s grant, untouched, and `id
  zfsbackup-foreign` still resolved.
- **Two orphaned/unknown uids, only one recorded.** Orphaned both accounts
  (`userdel` without a prior grant revoke, simulating exactly the failure
  mode this whole finding is about), leaving `hdd/backuptest_targets/
  multitest` with two `user (unknown: N)` entries. A fresh manifest recorded
  only one of the two uids. `--leave` revoked exactly that one; `zfs allow`
  afterward showed the OTHER orphaned uid, completely untouched.
- **Legacy manifest, missing account, no recorded uid: fails closed.**
  `--leave` refused with the manual-recovery message, named the exact
  dataset to inspect, and changed nothing -- confirmed the manifest file and
  the remaining grant were both still present afterward.
- **UID/name drift refused before mutation.** A manifest recording uid 9999
  against a live account actually running under uid 1001: `--leave` refused
  with the drift message, account and grant both confirmed untouched
  afterward (`id` still resolved).

`bash -n deploy.sh` clean. `test/join` 82/82, `test/joinremote` 8/8, `test/
draftscope` 26/26, `test/pause` 74/74, `test/quiescehelper` 119/119, `test/
selfupdate` 28/28 (7 environmental skips) all re-run clean (deploy.sh

## F2 — ACCEPTED

Agreed. The old residue check (`grep -Eq "(user [0-9]+|user \(unknown:
[0-9]+\)|user $account)"`) matched ANY numeric-uid principal shown by `zfs
allow`, so a second legitimate delegated account on the same dataset would
have permanently blocked an otherwise-correct teardown.

### Implementation

The residue check now matches only `user $uid`, `user (unknown: $uid)`, or
`user $account` -- the exact bound uid (whichever way it was obtained: live
and verified, or manifest-recorded) and the exact account name, nothing
broader.

### Evidence

Covered by the same live scenario as F1 above: the foreign account's grant
(a different, live, numeric uid) never triggered the residue check and never
blocked teardown; the untouched orphaned uid in the second scenario likewise
never blocked it. Both are the direct acceptance-criteria proof this finding
asked for.
