## F1 — ACCEPTED and IMPLEMENTED. The rule existed; three sites did not apply it.

### The reproduction, before the fix

Exactly the reviewer's control, run here against `b0a3a28`:

```sh
printf '[template:profile__mine__daily]\n' |
  grep -oE '^\[template:profile__/tmp/mine.conf__[^]]+\]'    # exit 1, no match
printf '[template:profile__mine__daily]\n' |
  grep -oE '^\[template:profile__mine__[^]]+\]'              # matches
```

### The fix

The destination's template identity is derived once, through the same helper the
renderer uses:

```sh
local _tpl_ns; _tpl_ns="$(profile_name_of "$target_profile")"
...
done < <(grep -oE "^\[template:profile__${_tpl_ns}__[^]]+\]" "$workfile" 2>/dev/null)
```

`profile_name_of`'s own comment already stated the rule — the name "has to
survive being given as a path and must never carry a '/'" — and
`profile_load`'s renderer calls already applied it (`zfs-backup.sh:1184-1187`).
The rule was written down and three sites ignored it.

### The two sites the review did not name

`schedule_tier_exprs` and `schedule_template_expr` built
`profile__${PROFILE_ACTIVE}__${one}` raw. `PROFILE_ACTIVE` **can be a path**: it
is assigned from `--profile=` (`zfs-backup.sh:7857`, which accepts one) and from
the client record `PROFILE` field (`zfs-backup.sh:6135`), which
`cmd_migrate_profile` writes with that same string. So after a path-supplied
migration the lookup builds `[template:profile__/tmp/mine.conf__hourly]`, matches
nothing, and falls through `continue`.

What an empty answer there costs is already recorded in the comment above that
very code: **no stagger at all** — every relationship landing on the template's
own minute, which a two-source lab caught in its first minute (#148/#149). Same
root cause as the finding, one site further on, and reached by the same operator
action. Both are now canonicalised at the point of use.

## F2 — ACCEPTED and IMPLEMENTED. The guard named the hole; the loop shape made it unreachable.

The comment directly above the refusal already said `a,b,` had to be refused. The
loop ran `while [ -n "$rest" ]`, so for `a,` it resolved `a`, emptied `rest` and
left **before** it could construct the empty final member the refusal existed
for. Naming a hole is not closing it, and this is that failure in one function.

### The reproduction, before the fix

The real `restore_scope_resolve` lifted from `b0a3a28`, with
`restore_resolve_try` reduced to one unambiguous mapping:

```text
"a,"      -> ACCEPTED (1 members)
",a"      -> refused
"a,,b"    -> refused
"a,b,,"   -> refused
```

Only the terminal case was open — which is exactly why the existing doubled-comma
test stayed green over it.

### The fix

```sh
local rest="$list" ... more=1
while [ "$more" -eq 1 ]; do
    case "$rest" in
        *,*) member="${rest%%,*}"; rest="${rest#*,}" ;;
        *)   member="$rest"; more=0 ;;
    esac
    [ -n "$member" ] || die "... empty entry ..."
```

The loop now runs until the last member has been handled, so every member the
operator wrote is examined — including the empty one their trailing comma wrote.

### Evidence

After the fix, the same probe: `a` / `a,b` / `a,b,c` accepted with 1/2/3 members;
`a,` `,a` `a,,b` `,` `a,b,,` all refused.

`test/restore/run.sh` adds the public-path cases through `zfs-backup.sh restore`:
trailing comma on `--target` and on `--source`, leading comma on both, a list
that is only a comma, and a trailing comma after a two-member list. Plus:

- a check that the refusal happens **before any plan is printed** (zero `Zrodlo:`
  lines), which is criterion 2 — no confirmation, fence, snapshot or mutation can
  have run;
- a positive control that the same list **without** the trailing comma still
  resolves both members, in the order written. Without it a parser that refused
  everything would pass all six refusals.

171/0.

## Test-hygiene defects found while producing this evidence

Both are mine, both were found by comparing what the output *should* have
contained against what it did, and both would have shipped a green run as proof.

**The targeted `--section` mode was unusable.** `mkprof_copy` / `mkprof_add` were
defined *inside* the `if [ -z "$ONLY_SECTION" ]` block that a targeted run skips,
so every `--section` invocation died at the first call with `mkprof_copy: command
not found` before reaching the section it was asked for. The L0 execution
REV-109 built has been silently broken since. The definitions are hoisted above
the guard; `--section 122` now runs in ~2 minutes instead of the full battery.

**Seven of my ten new assertions were dead on arrival.** I wrote them with
`check "<desc>" "<want>" "<got>"`, a helper `test/zfsbackup/run.sh` does not
define — it has only `ok`/`bad`. Bash reported `check: command not found` on
stderr and the counters never saw them, so the run printed `PASS=138 FAIL=0`
while the assertion carrying the whole finding had never executed. Caught by
diffing the expected label list (`122a`..`122j`) against the output: three of ten
present. Converted to `ok`/`bad`; all ten now run.

## Remaining risk

`cmd_migrate_profile` still writes the operator's raw string into the client
record's `PROFILE` field, so a host first activated as `--profile=mine` and later
migrated as `--profile=/path/mine.conf` ends up with two spellings of one profile
across its records. Nothing reads that field for template identity any more —
that is what this fix removed — and `profile_file` resolves both spellings, so it
is a cosmetic divergence rather than a live defect. Left alone deliberately:
changing what the record stores would change how a custom profile is found again
later, which is a separate decision and not this finding's.
