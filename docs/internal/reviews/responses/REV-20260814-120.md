# Response to REV-20260814-120

Both findings are accepted. They are the same mistake made about two different
objects: something was decided by **position in a list sorted by `creation`**, or
by a set that **never contained bookmarks at all**, when the primitive underneath
decides by `createtxg` and acts on snapshots *and* bookmarks.

The fix is one idea applied in three places: resolve by identity, compare by
`createtxg`, and enumerate both object kinds.

## F1 — ACCEPTED and IMPLEMENTED. Confirmed on live ZFS before writing any code.

### Analysis

The review is right, and the host agrees with it. Before changing anything I built
a throwaway dataset on pve0 (zfs-2.1.9) and ran the primitive as it stood:

```
hdd/r120lab@s1 42609087   hdd/r120lab#bm1 42609087
hdd/r120lab@s2 42609088   hdd/r120lab#bm2 42609088
hdd/r120lab@s3 42609089   hdd/r120lab#bm3 42609089

# zfs rollback -r hdd/r120lab@s1
--- snapshots after:  hdd/r120lab@s1
--- bookmarks after:  hdd/r120lab#bm1
```

`#bm2` and `#bm3` were destroyed. The planner enumerated snapshots only, so those
two never appeared in the measured loss set — the primitive widened the approved
destructive set at execution time, which is exactly what REV-119's confirmation
boundary exists to forbid.

The same probe also settled the mechanism precisely: the survivor is the bookmark
whose `createtxg` **equals** the target's, so the predicate is `createtxg > target`
for both object kinds — the same comparison `zfs rollback` makes internally. And
a non-recursive rollback refuses when a newer bookmark exists, naming it:

```
cannot rollback to 'hdd/r120lab@s1': more recent snapshots or bookmarks exist
use '-r' to force deletion of the following snapshots and bookmarks:
hdd/r120lab#bm4
```

Two further facts that the fix depends on, both measured on the same host:

- a dataset with no bookmarks lists **empty at rc=0**, so "no bookmarks" and
  "could not read the bookmarks" are distinguishable, and the code must not let
  them collapse into the same empty string;
- `zfs bookmark` is no more a userland write than `zfs snapshot` is, so the
  `readonly=on` fence does **not** keep a bookmark out. The fence cannot be the
  argument here.

### Implemented change

I took the first branch the review offers — discover, display, accept, and
revalidate — rather than refusing outright. A bookmark newer than the recovery
point is real state an operator may legitimately need to discard, and this project's
doctrine is an exact loss set with informed consent, not a narrower verb.

1. **The planner enumerates both kinds, by `createtxg`.** `restore_plan_strategy`
   resolves the source base by GUID and takes its `createtxg` with it
   (`RESTORE_SRC_BASE_TXG`), then derives the blocker set as
   `createtxg > base` over snapshots **and** bookmarks (`RESTORE_BLOCK_BOOKMARKS`).
   This also removes a second instance of the F2 defect that was sitting in the
   blocker derivation itself: it used to walk a `-s creation` listing and take
   everything positioned after the base, so a same-second snapshot could sort
   *before* the base, miss the loss set, and be destroyed anyway.
2. **A listing that fails leaves the set unproven, never empty.**
   `RESTORE_SET_STATE` is `ok` only when both listings succeeded and the base
   resolved to exactly one row. The destructive path refuses on anything else,
   before its first mutation, and the read-only plan says the list may be
   incomplete.
3. **The loss set names bookmarks.** They contribute 0 B by construction, so the
   byte total stays exact; the line says what is actually lost instead — the anchor
   for any future incremental send, gone irreversibly.
4. **The commit boundary revalidates them.** The before/after set difference now
   covers bookmarks, so one arriving after the approval is refused by name.
5. **The destructive command is preceded by an exact-set assertion.**
   `restore_execute` re-measures everything with `createtxg > base` and requires it
   to equal, exactly, the approved blockers plus the approved bookmarks plus this
   run's own two technical snapshots (handed to it by the caller, since only the
   code that created them can say which are ours). Any addition or disappearance
   refuses **before** the rollback, so it is a clean "nothing was destroyed".
   This closes the one window the boundary cannot: boundary check → rollback.

- **Discrimination.** The new suite run against the reviewed base implementation
  (`ZB=<REV-119 zfs-backup.sh> ./test/restore/run.sh`) reports **91 pass, 8 fail** —
  five of the eight are F1's.
- **Live end-to-end, bounded throwaway lab on pve0** (`hdd/r120src` + `hdd/r120bak`,
  destroyed afterwards). Source at the recovery point plus one newer snapshot
  `@blk1`, one newer bookmark `#bmnew`, one bookmark of the base itself `#bmold`:

  *Declined* (acceptance item 2) — the preview named it:
  ```
    BLOKUJE / DO USUNIECIA (BOOKMARKI zrodla NOWSZE niz wspolna baza):
      bmnew
    DO ZNISZCZENIA -- zbior ZMIERZONY, nie oszacowany:

      bookmark  bmnew    0 B
  ```
  and afterwards `@base`, `@blk1`, `#bmnew`, `#bmold` were all still there, with
  `readonly` back at `off/default`.

  *Accepted* — `@blk1` and `#bmnew` destroyed, **`#bmold` intact**, source back on
  `@base`, GUID confirmed, fence down, no technical snapshot left behind.
- **Targeted stub cases** (acceptance items 1, 3, 5): the loss set names the newer
  bookmark and not the older one; a control proves an older bookmark is neither
  announced nor destroyed; an unreadable bookmark listing refuses instead of
  reading as "none"; a bookmark arriving at the boundary is caught there; a
  bookmark arriving *after* the boundary is caught by the executor's exact-set
  assertion, with nothing destroyed and the exact-state claim still allowed.

### Remaining risk

The exact-set assertion is a measurement taken immediately before the destructive
command, not a lock. A `zfs bookmark` issued by another root process in the
microseconds between that read and the `zfs rollback -r` would still be destroyed
unapproved. Closing that completely would need a mechanism that makes the source
incapable of gaining a bookmark, and `readonly=on` is measured not to be one. This
is the same residual REV-119 accepted for snapshots, now stated for bookmarks too
rather than left implied.

Bookmark loss is also the one item in the set with no byte figure. The text says
what it costs; it cannot say how much.

## F2 — ACCEPTED and IMPLEMENTED. The rule was unsound; its live reachability is narrower than the rule, and I say so.

### Analysis

`zfs list -s creation | tail -1` is not a statement about which snapshot is the
head. It is a statement about which of two equal rows ZFS happened to print last,
and this project keeps measuring equal `creation` seconds in the wild — including
while gathering the F1 evidence above, where `@s1` and `@s2` came back with the
same `creation` and `createtxg` 42609087/42609088.

The fix does not repair the ordering; it stops depending on ordering. The
acceptance test is now two facts, neither of them positional:

1. the snapshot carrying `RESTORE_TARGET_GUID` exists on the source, looked up by
   identity, with **exactly one** row allowed to carry it;
2. nothing on the source is newer than it — no snapshot, no bookmark — compared by
   `createtxg` against that row's own `createtxg`.

Together those are the complete required final state. Every failure on this path is
a post-destruction partial failure (`2`), including a read that fails: an
unverifiable final state is not a success.

### What the live host actually shows — and what it does not

I could not make the defect fail end-to-end on pve0, and the reason is worth
recording rather than papering over.

Built a bounded lab with a genuine same-second pair (`@zz-peer` one transaction
before `@aa-point`, adverse name order) and ran **the reviewed base
implementation** against it. It **passed**. Measured why:

```
created aa-first FIRST (lower createtxg), zz-second SECOND (higher createtxg), same second:
hdd/r120tie@aa-first    1786704065  42609628
hdd/r120tie@zz-second   1786704065  42609629
--- 'zfs list -s creation' order:
hdd/r120tie@aa-first    42609628
hdd/r120tie@zz-second   42609629
--- tail -1 is: hdd/r120tie@zz-second
```

On zfs-2.1.9 the equal-`creation` tie comes back in **createtxg order**, not name
order (the reversed-name trial rules name-ordering out). So `tail -1` is
accidentally right whenever `creation` and `createtxg` agree in order — which, on a
single host with a monotonic clock, they always do.

That is the reproducible host limitation. The orders can only disagree when the
recovery point was created on a *different clock*, and this is measured to be the
normal mechanism rather than a hypothetical:

```
--- donor:    hdd/r120a@p1  creation 1786704024  guid 15292948460503997709  createtxg 42609601
--- receiver: hdd/r120b@p1  creation 1786704024  guid 15292948460503997709  createtxg 42609603
```

`zfs recv` preserves the **sender's** `creation` and assigns a **new local**
`createtxg`. Every recovery point this verb lands is a received snapshot, so its
`creation` is another machine's clock reading while its `createtxg` is this
machine's transaction order. Constructing the adverse case live would require a
sending host whose clock is ahead of the receiving host's, and I will not
manufacture clock skew on a production host to prove a rule I am removing anyway.

So, stated exactly: on today's reachable relationship kind (local push, both sides
one host) the old rule was unsound but not observably wrong. That is a reason to
delete the dependency, not a reason to keep it.

### Evidence

- **Identity-based substitute, live** (acceptance item 4's second branch). Run
  against the same-second pair on pve0, the two components of the new check
  separately:
  ```
  --- target guid (aa-point): 5645725302502541364
  --- NEW rule, resolve by identity:
      matched rows: 1   -> hdd/r120a@aa-point   42609611
  --- NEW rule, anything newer than it (snapshots + bookmarks, by createtxg):
      (empty above = the required final state holds)
  ```
  Exactly one row carries the identity, and the completeness check consults no
  order at all.
- **Targeted same-second cases with adverse ordering** (acceptance items 1 and 2),
  in the suite, where the tie order *can* be made adverse. The stub now honours
  `-s creation` with a documented tie-break so the fixture can put the wrong row
  last on purpose:
  - *rollback strategy* — a peer made in the same second as the recovery point but
    one transaction earlier, sorting last. The run succeeds; the assertion also
    pins that `tail -1` really does return the peer's guid, so the case is proven
    adverse rather than assumed to be.
  - *increment strategy* — the same defect by the other route. The stub's `recv`
    now models the measured behaviour above (stream's `creation`, fresh local
    `createtxg`), which is what makes the tie realistic instead of contrived.
  - Both fail against the reviewed base implementation.
- **The completeness control** (acceptance item 3): `rollbackleak` models a
  rollback that returns 0 and leaves a newer snapshot behind — the C-006/C-007
  class. The run reports `weryfikacja stanu koncowego zawiodla`, names the extra
  object, and says the source is **not** as it was found. Without this control,
  "does the target guid exist" would pass the same-second cases too.
- Suites and the base-implementation discrimination run are as listed under F1
  (three of the eight base failures are F2's).

### Remaining risk

**One thing this change does not touch, and I want it named rather than left for a
later round to find.** The *selection* of the recovery point on the copy still uses
`tail -1` of a `-s creation` listing:

```sh
latest="$(printf '%s' "$snaps" | tail -1 | cut -f1)"
```

It is the same unsound rule, one step earlier, deciding *which* point the operator
is offered rather than whether the restore landed. I did not change it because the
right answer is not obvious and it is not what F2 asks for: on the copy, `creation`
is when the data was captured (which is the operator-meaningful "latest recovery
point") while `createtxg` is merely arrival order, so swapping them silently would
change policy, not just mechanism. Ties there are decided by ZFS's undocumented
order. If you want it fixed, it should be its own finding with its own decision
about which notion of "latest" the owner's policy means.

Beyond that: the final check proves the target is present and nothing is newer. It
does not verify the *content* of the received delta beyond ZFS's own stream
integrity, which is unchanged from the reviewed implementation.
