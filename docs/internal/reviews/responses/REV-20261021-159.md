# Response to REV-20261021-159

## F1 — IMPLEMENTED

### Analysis

Accepted. `unmount_all()` discarded the status of `umount`, `umount -l`,
`rmdir` and `cryptsetup close` and cleared `MNT`/`MAPPED` regardless;
`browse_and_exit()` then printed "Odmontowane" and exited 0, leaving the EXIT
trap nothing to retry.

### Planned or implemented change

`tui/browse.sh`:

- `is_mounted` (via `mountpoint -q`, `/proc/self/mounts` as fallback) decides
  whether the mount is gone. `MNT` is cleared, and the directory removed, only
  when it is no longer mounted; otherwise the residue is recorded with the
  manual command (`umount <dir>`).
- A failed `rmdir` of the mount directory is residue too (reported, retried).
- A lazy detach is never reported as a clean unmount: with or without a
  mapper it is listed as residue ("odłączona leniwie", with `lsof +D`/`fuser`
  as the check), exit 1.
- Cleanup order: the mapper is closed only after the filesystem on it is
  really unmounted. If the mount is still there, or it went away only through
  `umount -l` (a lazy detach does not prove that nothing uses it), the mapper
  stays open and is reported with `cryptsetup close <name>`. A failed `close`
  keeps `MAPPED` and is reported as residue (decrypted data still reachable).
- `browse_and_exit()` prints "=== Odmontowane" and exits 0 only with no
  residue; otherwise "=== NIE wszystko posprzątane" with each residue line and
  exits 1. The EXIT trap retries with the state preserved, reports what is
  still left on stderr and exits 1 whenever residue remains -- also when the
  user went back to the menus after a failed step and cancelled there (which
  previously ended with `exit 0`).
- Found while testing: `is_mounted` ended with a bare `return`. Inside a
  function called from an EXIT trap, a bare `return` returns the status of the
  last command before the trap (bash manual: "If return is executed by a
  trap handler, the last command used to determine the status is the last
  command executed before the trap handler"), so the exit-time retry took a
  mounted copy for unmounted and removed its directory -- measured: the
  both-umounts-fail case showed two umount calls instead of four until it
  was changed to `return $?`.

### Evidence

- commit/PR: `de953d0706ce4f926fcf7306cab995ab3673c61f` (branch
  `finisz/REV-159`).
- commands run: `bash test/browse/run.sh` (new suite) and `bash
  test/tui/run.sh` on the pve9 clone; the browse suite with `tui/browse.sh`
  from `origin/main` (blob `fa383785`) as the negative control;
  `./test/impact.sh --verify`.
- results: fixed tree browse 14/0, tui 362/0. The suite runs the shipped
  `tui/browse.sh --any` with fake whiptail, zfs, mount, umount, mountpoint,
  cryptsetup, lsblk and mc. F1 cases: normal success; ordinary umount fails,
  lazy succeeds (no mapper) -- detached but reported, no "Odmontowane",
  exit 1; both umounts fail -- exit 1, residue
  and manual command shown, no "Odmontowane", umount attempted again at exit;
  LUKS `cryptsetup close` fails -- exit 1, mapper kept, command shown, close
  retried at exit; residue followed by a return to the menus and Cancel --
  exit status still nonzero; close
  succeeds -- success, mapper gone, snapdev restored; lazy detach with a
  mapper -- exit 1, mapper kept open, no `cryptsetup close` at all. On the old

### Remaining risk

The fakes model `mountpoint` from a marker file; a real kernel can report a
mount as gone while a lazy-detached filesystem is still referenced, which is
why the mapper is never closed after `umount -l`.

## F2 — IMPLEMENTED

### Analysis

Accepted. `expose_snapdev()` wrote the origin record from unchecked
`zfs get` substitutions; `restore_snapdev()` ignored the status of
`zfs set`/`zfs inherit`, then removed `orig.<dataset>` and cleared its state,
and the caller said "Nic nie zostało zmienione w kopii".

### Planned or implemented change

- `expose_snapdev()` changes nothing unless both `zfs get` calls succeed and
  the value is `hidden|visible` and the source `local|default|received|
  inherited from ...`; reasons go to stderr (shown in the dialog).
- The origin record is written only when it does not exist (atomically via a
  temp file and `mv`); an existing record -- from another live session or a
  failed restore -- is read and validated before `snapdev=visible` is set,
  and an empty or malformed one refuses the change instead of being
  overwritten; it is removed only after a successful restore.
- `restore_snapdev()`: another live holder -> drop only this session's hold,
  keep the record; otherwise restore by source (`local` -> `zfs set
  snapdev=<was>`, `default`/inherited -> `zfs inherit`, `received` -> `zfs
  inherit -S`); any failure or an unreadable/unknown record keeps the record
  and `SNAPDEV_DS`, adds a residue line with the manual command, returns 1
  (the EXIT trap retries).
- Every early-exit path of the zvol step now goes through `undo_or_warn`: the
  "Nic nie zostało zmienione" text is shown only when unmount and restore
  both succeeded; otherwise the residue is shown.

### Evidence

- New F2 cases: original `hidden`/`local` restored with `zfs set`, record
  removed; original `inherited from tank` restored with `zfs inherit`; failed
  initial `get` -- no `set snapdev=visible` at all, reason shown; failed `set
  visible` -- no mount, value unchanged; device does not appear and the
  restore fails -- no "Nic nie zostało zmienione", "NIE przywrócony" shown,
  `orig.tank_vol` kept; a second live holder -- no restore call, record kept;
  an existing but empty record -- no `set snapdev=visible`, record untouched.
  On the old blob the failed-get, failed-restore and empty-record cases FAIL
  (and the `local` case, through the changed wording); the inherited,
  failed-set and two-holder cases pass on both.
- `./test/impact.sh` selects the suites `browse`, `tui`, `impact` and the
  manual obligation `project-status`; `./test/impact.sh --verify`: rc 0.

### Remaining risk

No live browse with a real zvol/LUKS device was repeated for this change; the
behaviour is decided by exit codes of the same commands, proven with
injected failures. BitLocker remains unmeasured live (U6).
