# Response to REV-20260831-129

## F1 — IMPLEMENTED

### Analysis

The finding is correct, and calling it a category error is the right description
rather than a harsh one. A snapshot's guid identifies that dataset's snapshot.
Comparing a child's guid with its parent's does not make the check stricter; it
makes it ask a question that has no true answer.

The consequence is the one the correction it belongs to was written to remove.
`restore_one()` turns any non-empty result into "the engine reported success but
the target is NOT at $point" and returns the changed/incomplete status -- so
every successful recursive restore ended as a report that a completed recovery
needs manual intervention. That is the same shape as the `written@point` defect
this verifier replaced, arriving one layer further in: a check that cannot pass.

The focused suite could not see it because its fixture held a single dataset. A
one-dataset fixture makes "the root's guid" and "each dataset's guid" the same
value, so the distinction the code gets wrong never arises.

### How each recursive dataset receives its own expected identity

The caller builds a table from the COPY side, where the recovery point's
identities actually live, and keys it by each dataset's position under the copy
root:

```
<relative path><TAB><guid>
```

The far side enumerates the target subtree, derives the same relative position
under the target root, and looks up that dataset's own expected guid. Nothing is
compared against the root's identity any more.

A dataset with no entry in the table was not part of this recovery -- it was
never in the copy -- so it is skipped rather than reported. Reporting it would be
a false alarm about something the run did not touch, and criterion 4 scopes the
guarantees to the datasets that were included in the send.

### A defect in the table itself, caught while writing it

The first version keyed the table with `index($1, c) == 1`, which also matches a
dataset that merely STARTS with the copy's name -- `hdd/copyOTHER` under
`hdd/copy` -- entering the table under a nonsense relative path. `zfs list -r`
would not return such a dataset, so it could not bite in practice, but a table
keyed by position must not depend on that. It is the same name-boundary mistake
corrected earlier the same day in the `--onto` common root, which is why it was
tested rather than assumed.

### Against the acceptance criteria

1. **Each enumerated dataset verified against its own copy-side snapshot guid**,
   never against the root's.
2. **A root and child at their respective valid recovery points produce no
   off-point report** -- the carrying case.
3. **Right name, wrong guid still refused**, measured against that dataset's own
   expected identity.
4. **Missing recovery snapshot and any newer snapshot still detected** for every
   dataset in the table.
5. **Parent-plus-child regression added**; the existing single-dataset identity
   cases are unchanged.

Against `4cb82baead4ecaa05b4b4bd8ba0521e4c5622562`, with the reviewer's own

```
rpool/data/child has a snapshot NAMED p but a DIFFERENT one -- guid 222, expected 111
```

On this tree the same call is silent: parent and child are each judged against
their own identity.

## Remaining risk

The table is built from the copy at the moment of verification. If the copy
changed between the send and the check, the expected identity would come from the
newer state -- the same time-of-check window every remote probe in this file has,
and narrower than the transfer it follows.

No live destructive campaign was run for this correction, and per the review none
was required.
