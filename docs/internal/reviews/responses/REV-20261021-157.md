# Response to REV-20261021-157

## F1 — IMPLEMENTED

### Analysis

Accepted. `exec 9>LOCK && flock -n 9 || exit 0` merged two different states:
another run holding the lock (a reasonable skip) and the lock file not being
openable at all (the guard never runs). The second exited 0 with no message
of ours and no alert.

### Planned or implemented change

`hostscripts/capacity-guard.sh`, start-up, before the crontab read and before
any `zpool`/`zfs` call:

- `{ exec 9>"$LOCKF"; } 2>/dev/null` failing (missing parent, permissions,
  read-only filesystem, invalid path): log with the path, alert
  ("bezpiecznik NIE działa -- blokada", path in the body), exit 1. Under
  `--plan`: the log line and exit 1, no alert. (Measured on pve9: bash does
  not exit on a failed `exec` redirection, so the handler runs.)
- `flock -n -E 75 9`: 75 = held by another run -> skip, exit 0, no alert
  (documented policy: that run is guarding the pools); under `--plan` the
  read-only plan continues without the lock and says so. Any other nonzero
  flock status -> the same error path as an open failure.
- There is no path to `zfs destroy` without the lock held (`--plan` never
  destroys).

### Evidence

- commit/PR: `0c8a4bb47c37cd881f61e7c7f8c7361c647bdfd2` (branch
  `finisz/REV-157`).
- commands run: `bash test/alertmail/run.sh` on the pve9 clone (fixed tree);
  the same suite with `capacity-guard.sh` from `origin/main` (blob
  `e46050b5`, the one the review inspected) as the negative control;
  `./test/impact.sh --verify`.
- results: fixed tree PASS=144 FAIL=0, of them 57 `PASS capacity-guard:`
  lines. The fake `zpool` now logs every call, so "zero pool discovery" is
  asserted, not assumed. New F1 cases: lock parent missing, `guard=on` --
  rc 1, no `zpool`/`zfs` call at all, alert with the path; the same under
  `--plan` -- rc 1, log line, no alert; lock held by a real `flock` process --
  rc 0, no destroy, no alert, no `zpool` call, "pomijam" logged. Control:
  valid uncontended lock -- normal run, three destroys. On the old blob the
  three lock cases FAIL; the control passes on both.

### Remaining risk

A read-only lock directory was not injected separately (the suite runs as
root, which ignores permission bits); it takes the same `exec` failure path
as the missing parent.

## F2 — IMPLEMENTED

### Analysis

Accepted. A failed `mktemp -d` logged a line and exited 1 without an alert.

### Planned or implemented change

`mktemp -d` failing: log with the effective `TMPDIR`, alert ("bezpiecznik NIE
działa -- katalog tymczasowy", `TMPDIR` in the body), exit 1 -- after the lock
is taken and before the crontab read, so zero `zpool`/`zfs` calls. `--plan`:
no alert. The cleanup trap is set only after `WORK` exists, as before; the
lock is released by process exit (fd 9).

`alert()` is unchanged: it calls the notifier once (`$ZFS_NOTIFY_SCRIPT`, by
default `/root/scripts/notify-fail.sh`, installed from
`hostscripts/notify-fail.sh`, which only queues) and falls back to `mail`;
it returns 0 either way and never re-enters the guard, so a broken queue
cannot recurse, and no deletion follows a failed preflight (both paths exit).

### Evidence

- New case: `TMPDIR` pointing to a missing directory -- rc 1, no `zpool`/`zfs`
  call, alert naming the directory. Healthy control as in F1. On the old blob
  the case FAILS (no alert).
- `./test/impact.sh origin/main` selects the suite `alertmail` and the manual
  obligations `deploy-check-only` and `project-status` (U35 entry updated);
  `./test/impact.sh --verify`: rc 0.

### Remaining risk

None beyond the fake-command boundary.
