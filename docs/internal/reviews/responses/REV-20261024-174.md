# Response to REV-20261024-174

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `foreign_normalized_identity()` removes every `-P "..."` token from
both the installed and the proposed `delsnaps.sh` line. The intended U4 transition only
ADDS protections, in the two shapes gen-cron's `apply_foreign_prune` generates:
`-P "<other family>:all"` for each other family on the scope and `-P "<replica prefix>:2"`.
Erasing every `-P` therefore also erased the pre-existing floors (`[excluded:]` ->
`-P "vzdump:2"`), so a floor lowered or dropped in the same proposal rode along with the
allowed rewrite and the seventh exception returned success. The reviewer's reproducer
shows exactly that on main (`combined_foreign_and_protection_change_rc=0`).

### Planned or implemented change

`zfs-backup.sh`: a new `foreign_protections_kept <installed line> <proposed line>`, required
by the seventh exception in addition to the pattern-normalized identity:

- every `-P` token of the installed line must be present in the proposed line, unchanged
  (a removed prefix or a changed count fails);
- a token only in the proposed line must be one of the generated shapes (`:all`, `:2`),
  and must not name a prefix the installed line already protects (a changed floor written
  as a new token fails).

When it fails, the line is not exempted; it stays in the lost set and the ordinary
destructive guard refuses the install ("would be DELETED"). The other refusals are
untouched: a changed retention count, a changed non-empty pattern, a remote line and an
unrelated lost job still go through the same checks as before.

### Remaining risk

- Acceptance criterion 1 is met in a narrower form than written, and I am flagging it for
  review rather than claiming it. The guard recognises the generated protections by their
  form (`:all`, `:2`, for a prefix the installed line did not already protect); it does not
  recompute `apply_foreign_prune`'s exact set for the proposal (that needs gen-cron's
  scope-pattern and replica state, which the installer does not hold). So an added
  `-P "<x>:2"` or `-P "<x>:all"` for a new prefix is accepted. That only ever ADDS
  protection (fewer deletions), which is the direction the guard does not need to stop;
  every weakening -- a lowered count, a removed floor, a new token re-stating an already
  protected prefix -- is refused. If the reviewer wants the exact generated set compared,
  the place is a gen-cron-provided list of the tokens it added, and I would add it here.
- The U4 generator cases in `test/cron` and the full battery run in CI on the PR; not run
  locally on this Windows box (CLAUDE.md, "Which executor").
