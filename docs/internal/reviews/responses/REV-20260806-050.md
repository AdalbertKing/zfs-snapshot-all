# Response to REV-20260806-050

## F1 — the group-write test examined the whole mode string — IMPLEMENTED

Accepted; the finding is exact, including the worked example. `stat -c %a`
renders 0755 as `755`, and my pattern looked for a `7` anywhere in that
string — so it matched the **owner's** digit and pronounced a directory
writable that the account could not touch. `2755` and `1755` passed for the
same wrong reason.

The consequence is the one the review names: `chown` succeeds, `chmod 0775`
does not take, enrolment finishes without a warning, and remote
`PAIR-CONTROL enable` can never remove the marker. That is exactly the
degraded state the verification was added to catch — accepted by the check
meant to catch it.

Worth noting why it survived my own testing: the live campaign that motivated
the check had a directory whose group was `zfsalert` (wrong group), so the
first condition failed and the second was never reached. The mode arm had no
coverage at all.

### Implemented change (`fe2209b`)

The check is now its own function, `gate_state_dir_ok`, taking the `stat`
output **by value** — so it is tested directly rather than through a stubbed
filesystem. It requires:

- the group to equal the account, and
- the **group digit** — second from the right, since modes may be three or
  four digits — to be `2`, `3`, `6` or `7`.

Non-numeric, empty or truncated `stat` output is a refusal, not a guess.
