# Response to REV-20260809-082

All three findings ACCEPTED.

## F1 — ACCEPTED (IMPLEMENTED)

The finding is right and it names the shape correctly: a generic validated
fragment followed by a hand-maintained key-to-key extractor is more machinery,
not less. `profile_emit()` now copies the rendered fragment through. The
relationship still writes what it owns — prune `recursive`, `pair_label`,
`notify`, `src` — and cannot collide, because `lib-profile.sh` refuses exactly
those fields inside a profile.

The owner'''s preinstall-preset direction and this finding agree, which is why I
implemented it without waiting: both say the high-level layer should stop
translating a contract `gen-cron.sh` already owns.

### What writing the test found, which is worse than the finding

Mid-edit, `profile_emit` was referenced by all three call sites and **not yet
defined**. Client sections were losing their entire policy reference.

**The suite reported 295/295.**

Nothing in it asserted that a generated `[dataset:]` carries a `use_template`
line at all. So the false green F1 describes was not limited to unknown fields —
the *known* field was unasserted too, and a runtime that emitted policy-free
sections would have shipped green.

I caught it only because the number did not move where it had to move. The new
block therefore pins both: the field that was always there, and the field the
extractor dropped.

## F2 — ACCEPTED (IMPLEMENTED)

`lib-profile.sh` declares `suites = profiles zfsbackup`. B1 made
`zfs-backup.sh` source it, so a profile-boundary change can break the runtime,
and the graph was routing such a change only to `profiles`.

The regression asserts the **real** graph rather than a fixture, deliberately: a
fixture would prove the resolver can follow an edge, which was never in doubt.
Whether *this* edge is declared is what was, and only the real file can answer.

## Remaining risk

`profile_emit` copies whatever the boundary accepted. That is the intent, and it
moves the question entirely onto `lib-profile.sh`'''s field rules — which is where
the contract says it belongs, but it does mean a mistake in the forbidden-field
list now reaches a config directly rather than being filtered by a narrow
extractor. I consider that correct rather than risky, and state it so the trade
is on the record.
