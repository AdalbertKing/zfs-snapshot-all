# Response to REV-20261023-170

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `restore_grant_namespaces` maps every scope on a pool to the same
`<pool>/restore`, and ZFS stores one permission set per `(dataset, account)`. Two
relationships to one peer normally share its `zfsbackup-<peer>` account, so two grants on
disjoint scopes of one pool hold the same tuple. `do_deny_restore` ran the namespace
`zfs unallow` unconditionally. Withdrawing the first grant therefore removed the
capability the second, still active grant needed, and it returned 0, so nothing
revealed the break.

### Planned or implemented change

`deploy.sh` only. The REV-147 order (record moved first, unallow, resume only
after a proven revocation) is unchanged.

- **New `restore_ns_other_owners <label> <account> <namespace>`.** It lists every
  OTHER grant that still needs the namespace: those standing in `RESTORE_GRANT_DIR`
  and those still being revoked in `RESTORE_REVOKE_DIR`. A grant counts when it
  has the same account and its scope maps to that namespace.
  - Its account comes from its record (`RESTORE_GRANT_ACCOUNT`, or
    `RESTORE_REVOKE_ACCOUNT` on a pending revocation), otherwise from its
    pairing manifest.
  - A grant whose account cannot be told keeps nothing alive. Another account's
    tuple is neither retained nor revoked by guesswork.
- **The namespace loop in `do_deny_restore`** skips the `unallow` while another
  owner remains, and logs `kept: … still needed by grant(s): <labels>`. The last
  owner unallows as before, and before its grant-owned writers resume. A failed
  unallow keeps the REV-147 fail-closed retry.
- **New grants record their account.** `do_allow_restore` writes
  `RESTORE_GRANT_ACCOUNT`, so the accounting does not depend on a manifest that
  may change later. Grants written before this fall back to the manifest.
- Different accounts and different pools stay isolated, because the tuple
  compared is `(namespace, account)`.

## R1 — IMPLEMENTED (the reviewer rejected implementation 0843461a, 2026-10-23)

### Analysis

Accepted. With records moved per label and no lock, two concurrent withdrawals each saw
the other as a pending owner. Both skipped the namespace `unallow`, both returned 0 and
both removed their record, so the capability stayed delegated with nothing on disk to
retry from. The regression in #780 denied serially and could not see it. Point 4 is
accepted as well: a grant whose account or scope cannot be read was treated as "not an
owner", which is a silent guess about a capability that may still be in use.

### Implemented change

`deploy.sh`:

- **`restore_grant_lock`.** One `flock` on `${RESTORE_GRANT_DIR}.lock`, held on fd 9 to
  process exit. Both `do_allow_restore` and `do_deny_restore` take it before they read or
  move any record, so a grant's recording, the ownership decision, the ZFS
  allow/unallow, the cleanup and the resume of writers all run inside it.
  - It is one lock for all labels, because the namespace is shared across labels.
  - If `flock` is missing, or the lock is not free within `RESTORE_GRANT_LOCK_WAIT`
    (300 s), the command dies with "nothing was changed".
  - A holder that dies releases the lock through the kernel. Its pending record stays in
    `grants.revoking`, and the next `--deny-restore` retries from it (REV-147).
- **Point 4, fail closed.** `restore_ns_other_owners` marks another grant `?<label>` when
  its account or scope is unknown and it may share the namespace. When it is known to be
  another account, or its scope is on another pool, it is not an owner.
  - On a `?` the withdrawal does NOT unallow the namespace and is NOT reported done:
    `_rd_open=1`, rc 1, the record stays pending, and the writers stay paused.
  - The warning names the grant(s) and the two ways out: withdraw them, or add
    `RESTORE_GRANT_ACCOUNT`/`RESTORE_GRANT_DATASETS` to their records.

## R2 — IMPLEMENTED (the reviewer rejected implementation a3379138, 2026-10-23)

### Analysis

Accepted. `do_allow_restore` records `RESTORE_GRANT_ACCOUNT`, but `do_deny_restore` read
the account for its OWN grant only from `RESTORE_REVOKE_ACCOUNT`. It appended that line at
the first withdrawal, from the CURRENT pairing manifest. After an import or rejoin the
manifest named another account, so the withdrawal unallowed that account's scope, left the
real one delegated, and returned 0. That contradicted my own claim in F1, and the
different-account criterion.

### Implemented change

`deploy.sh`, `do_deny_restore`:
- **Reading the account.** For the grant being withdrawn it is read from
  `RESTORE_GRANT_ACCOUNT` in the record first. `RESTORE_REVOKE_ACCOUNT` is used only
  when that line is absent. The manifest fills only a field the record does not carry.
- **Writing at withdrawal.** `RESTORE_REVOKE_ACCOUNT` is written only for a LEGACY
  record, one with no `RESTORE_GRANT_ACCOUNT`. A record that names its account keeps that
  account. A later manifest cannot add a second, different one.
- `restore_ns_other_owners` now reads `RESTORE_GRANT_ACCOUNT` by name first, then
  `RESTORE_REVOKE_ACCOUNT`. Before, it took whichever of the two lines came first in the
  file, which was right only because the grant line is written first.
