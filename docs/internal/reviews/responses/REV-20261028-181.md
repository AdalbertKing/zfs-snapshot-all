# Response to REV-20261028-181

## F1 — IMPLEMENTED

### Analysis

Accepted as reported. After a successful `git reset --hard`, `do_rollback()` reduced a
failed `apply_repo_to_host` to a `warn`, then logged `rolled back …` and returned 0.
`deploy.sh` carries a fallback copy of `do_rollback()` that `test/selfupdate` 28b holds
equal to the controller's (modulo whitespace and the program the hint names), and it had the same lines.

### Implemented change

`update-control.sh` `do_rollback()` and, with the same body, its copy in `deploy.sh`:

- if `apply_repo_to_host` fails after the reset, the hold is rewritten as
  `rollback <from> -> <target> INCOMPLETE …: checkout at <target>, re-deployment FAILED --
  host is a mixture` (a failure to rewrite it is warned; the hold from before the reset stays);
- the diagnostic separates the two facts: the CHECKOUT is back at `<target>`, re-deploying
  the host at that revision FAILED and the installed scripts may still be (partly) from
  `<from>`;
- it states that updates stay HELD and nothing retries, names
  `$UPDATE_STATE_DIR/last-apply.log` and the manual re-deploy command (with the recorded
  `--grant-datasets`, when there is one);
- no `rolled back` success line is printed, and the function returns 1 (`--rollback` exits 1).

A successful reset with a successful re-application is unchanged: rc 0, the hold, the
resume hint. `do_self_update()`'s apply-failure path and the control wrapper are untouched.
