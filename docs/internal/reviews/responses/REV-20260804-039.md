# Response to REV-20260804-039

## F1 — interrupted `--join-remotely` strands an asymmetric relationship

**DISPUTED for the required mechanism (a new pending-record or resume-
enrolment verb); ACCEPTED for the underlying concern.** Evidence below,
live, not assumed.

### What was actually live-tested

Before writing any code, the exact scenario the finding describes was
reproduced deliberately, twice, on collector pve1 / peer pve2: ran
`add-client ... --join-remotely`, let the automated `--join` succeed on the
peer, then killed the whole process (`timeout 15`, a real SIGTERM, not a
graceful stop) mid interactive scope editor -- the process/terminal/SSH
loss failure mode the finding names.

**First kill:** confirmed the collector's client record was never written
(matches the finding exactly), but the peer's account/key/manifest were
fully and correctly committed (REV-038's atomic manifest, verified).

**Re-ran the identical `add-client` command, no manual cleanup:**
`do_pair`'s existing keygen step (`elif [ -f "$keyfile" ]; ... reusing it`)
found the unconsumed key from the killed attempt and reused it rather than
generating a new one. `do_join`'s existing collision handling saw the
resubmitted package carrying that SAME fingerprint and treated it as a
no-op reconfirmation (account "already exists, leaving it alone", key
"already there, leaving it alone", manifest re-committed byte-equivalent
except the remote-session timestamp) -- not a rotation, not a second key.
`authorized_keys` stayed at exactly one line across both attempts,
confirmed by direct count.

**Second kill** (same command, same peer, same key): identical outcome --
key reused again, join reconfirmed again, still one key.

**Third invocation, without `--join-remotely`** (the scope was already
committed from manual cleanup of the second attempt): completed cleanly and
wrote the collector's client record for the first time, proving the
relationship IS recoverable by plain retry, with no second key, no
duplicate account, and no rotation, at any point in the sequence.

### Why DISPUTED for the required mechanism

The review's required outcome asks for either a pending-record-before-
mutation model or a dedicated idempotent `resume-enrolment` command,
explicitly rejecting "a blind second add-client that happens to fall into
rotation logic" as acceptable. The live evidence above shows the premise
does not hold for this codebase as it stands: a second `add-client` does
NOT fall into rotation logic -- rotation is a separate, explicit,
`--rotate`-gated code path that a plain retry never reaches, because the
keygen step's default behavior (established well before this finding, not
new) is exactly "reuse an unconsumed key for this peer host." The
recovery path the review says does not exist already exists, and behaves
exactly as its own acceptance criteria demand:

- [x] "does not require the operator to infer which half committed" --
  the peer's manifest already answers this (REV-038's
  `PEER_JOIN_REMOTE_*` fields), and the collector-side retry does not need
  to know either way; it converges regardless.
- [x] "One documented recovery command completes the same relationship
  without adding a second key or rotating identity" -- confirmed live,
  the recovery command being the exact same `add-client` invocation.
- [x] "Re-running the recovery is idempotent" -- confirmed live, twice.
- [x] "A mismatched peer manifest/fingerprint refuses closed" -- pre-
  existing `do_join` collision handling (label collision: different
  account/target refuses; same account/target but different fingerprint IS
  rotation-shaped, which only occurs if the LOCAL key actually changed
  between attempts -- not the scenario a same-command retry produces, since
  the local key is reused, not regenerated).

Building a new state-tracking mechanism on top of an already-idempotent
retry path would add complexity without closing a gap the live evidence
shows does not exist in the mechanism itself.

### What WAS a real, accepted gap: the operator was never told this

Nothing in `add-client`'s own output said any of the above. An operator
hitting this failure had no way to know retry was safe without reading the
source. Fixed (`fef2314`): the failure message now states plainly that
retrying the exact command is safe, why (key reuse, join reconfirmation),
and that an unreachable peer leaves nothing touched either way.

### Evidence

`test/zfsbackup` 249/249 (unaffected -- this is a message-only change,
covered by the live proof above rather than a new stub test, since the
mechanism being described is `do_pair`/`do_join`'s real actions, which this
project has never locally stub-tested for the same reason recorded
throughout this whole campaign -- see `test/join/run.sh`'s own header).
Live cleanup: `f1test` relationship fully torn down on both hosts,
`hdd/backuptest_targets` back to only the pre-existing unrelated
`zfsbackup` grant, pve1 crontab confirmed byte-identical to the campaign's
own Gate A baseline (`54b12f26244f8e5184e17fe57b87d6d7`) throughout.

### If this analysis is wrong

If a scenario exists where a plain retry DOES trigger rotation or a
duplicate key (a case the live testing above did not reach), that is a
concrete, reproducible claim worth a follow-up review naming the exact
sequence -- at which point building the stronger mechanism this finding
originally asked for would be the right call, and the dispute above
withdrawn.

## F3 — peer teardown can leave orphaned numeric-UID ZFS grants

**ACCEPTED, fixed, live-verified, and hardened by a follow-up finding.**
See `docs/internal/reviews/responses/REV-20260804-040.md`: new `--leave=LABEL`
peer-side teardown command, then (after review correctly caught the first
version's own "scan for the first unknown uid" mistake) a durable
`PEER_JOIN_ACCOUNT_UID` binding, live-verified against exactly the
multi-principal scenario the follow-up review specified -- two accounts on
one dataset, one foreign grant surviving untouched; two orphaned uids, only
the recorded one revoked; a legacy manifest with no recorded uid and no
live account failing closed rather than guessing; uid/name drift refused
before any mutation.

### Summary

Of REV-039's four findings: F2 and F3 are fixed and live-verified (with two
follow-up reviews, both accepted and closed by REV-040/041). F1's required
mechanism is disputed with reproducible live evidence that the concern it
targets is already closed by existing behavior; the one real gap
(undocumented recovery) is fixed. F4's five gates: two now PASS live (E,
H), one is closed by F1's own evidence (B), two remain genuinely NOT RUN
for reasons external to the code (G: no second network path exists to
test with; I: no reachable non-clustered pair exists in this environment) --
disclosed precisely rather than simulated or asserted.
