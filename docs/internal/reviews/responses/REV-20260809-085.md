# Response to REV-20260809-085

## F1 — IMPLEMENTED, and it corrects a claim I made in the live-proof discussion

ACCEPTED, including the correction to my own reasoning. In
`docs/discussions/V3-LIVE-PROOF-NEXT-STEPS-2026-08-09.md` I argued that
backup-mode parent/child overlap between two different relationships was
"structurally unreachable" because I believed `LOAD_LABEL` was the client's
own name. It is not: `load_client_and_connection()` sets
`LOAD_LABEL="$(peer_label "$PEER_HOST")"` — derived from the PEER's address,
not this relationship's identity. I verified this by reading the function
directly before writing any fix, rather than trusting my own prior claim.

That means two differently-named relationships pairing with the same peer
share the same `target/label` namespace, and `cmd_seed()` performed a real,
non-dry-run `snapget.sh` receive with no coverage check anywhere in its path
— the only guard (`assert_no_coverage_overlap`, REV-083/084) lived inside
`emit_client_sections()`, reached only at `activate-client` time, after seed
had already moved real data.

### Fix

`cmd_seed()` now computes each candidate's local destination path for every
dataset in `$PEER_SAVED_DATASETS` — right after `load_client_and_connection()`
returns, so mode-based clients' resolved list (via `resolve_mode_datasets()`,
called inside that same function) is already final — and calls the same
`assert_no_coverage_overlap()` before the transfer loop. No second overlap
implementation; the activate-time check in `emit_client_sections()` is
unchanged and remains as defense in depth, per the finding's own guidance not
to remove it without a proven single-boundary replacement.

### What writing the test found, which changed the test itself

Section 47's original "disjoint" case reused the SAME peer as the overlap
cases, with a different dataset (`rpool/other`). It failed — refused, when it
should have succeeded. The reason is a real, pre-existing property I hadn't
accounted for: a GFS relationship's `MANAGED_PRUNE_SCOPE` is the WHOLE
`target/label` subtree (`prune_scope="$PEER_SAVED_TARGET/$LOAD_LABEL"`,
`recursive = yes`), and `coverage_conflicts()` checks a candidate against both
`MANAGED_DATASETS` and `MANAGED_PRUNE_SCOPE` of every other active
relationship. So once one GFS relationship exists for a given peer+target,
EVERY dataset under that same peer+target is already covered — there is no
such thing as a "disjoint second dataset" under the same peer once GFS is on;
that is one relationship per peer+target namespace, by design, not something
this finding should route around. The regression's disjoint case now uses a
different peer host, which is the actually-disjoint shape.

## Remaining risk

`emit_client_sections()`'s activate-time check and `cmd_seed()`'s new
seed-time check are now two call sites for one canonical guard, which is the
finding's own required shape ("reuse... or extract a single canonical
helper"). I did not extract a separate helper because both call sites already
call the exact same `assert_no_coverage_overlap()` function directly — there
is no duplicated logic to extract, only two callers of one function, which I
believe satisfies "no duplicate overlap semantics" without adding an
unnecessary layer.
