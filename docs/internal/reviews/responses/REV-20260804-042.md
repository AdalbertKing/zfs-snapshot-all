### The defect this gate found

`assert_target_block_not_clobbered()` diffs the installed managed cron
block against the newly rendered one and refuses to install if any
installed line would disappear. A legitimate endpoint switch changes
the literal `-A "acct@host:path"` text of a client's pull line, which
made it indistinguishable from a foreign job silently disappearing —
the guard FATAL-refused step 5 above on the first attempt. This is the
documented, advertised relocation flow (the same "Wariant B" walked
through with the owner earlier this session); it had never actually
run against this guard before, because Gate G had never run live
before.

Fixed once (`2e02a7d`, HostKeyAlias-based carve-out), found too coarse
by an independent review before it reached this stage
(`REV-20260804-043`, P1: a client with two datasets could have one
silently dropped as long as the other still rendered), corrected
(`3a89892`, endpoint-normalized per-job identity — see that finding's
own response for the full defect/fix narrative and acceptance-criteria
mapping). Step 5 above is the *corrected* guard's live run — clean,
no FATAL, real subsequent incremental confirmed.

## F2 — Gate I

**PASS, live**, after a methodology correction made mid-gate and
disclosed in full below rather than smoothed over.

### First attempt: LXC, mechanism proof only — and a real isolation gap found

The first attempt reused the same privileged-LXC design as Gate G. Two
live findings came out of it, both disclosed to the owner as they were
found, before continuing:

1. **A UID collision with the real production `zfsbackup` account.**
   `useradd` inside a fresh privileged container allocates UIDs from
   its own `/etc/passwd`, independent of the host's — the first
   container's peer account (`zfsbackup-pve1`) landed on **UID 1000**,
   the *exact* UID of the host's real, production `zfsbackup` delegated
   account. Because a privileged container shares the host's kernel and
   therefore its UID-keyed `zfs allow` state, that container account
   had de facto access to every dataset genuinely delegated to UID 1000
   on the real host — `rpool/data`, `rpool/ROOT/pve-1` — for as long as
   the container existed. Found live, the container destroyed
   immediately, `zfs allow` on both real datasets confirmed unchanged
   (still exactly the documented `rpool/data`/`rpool/ROOT/pve-1`
   delegation, nothing added or removed). The rebuilt container used an
   explicit `UID_MIN 5000` in `/etc/login.defs` before any account was
   created, confirmed live (new account landed on UID 5000, not 1000).
2. **Sync mode's own `do_pair` had no code path for a `sync`-mode pull
   at all.** `--mode=sync` deliberately has no `--target` (source paths
   are reproduced 1:1), so `PEER_TARGET` is empty; `do_pair`'s
   target-pre-creation step built `"$PEER_TARGET/$label"` unconditionally
   for every pull role, which collapses to a bare `/$label` for sync —
   `zfs create -p` correctly refused it. Sync mode had never actually
   paired against live infrastructure before this gate ran. Fixed
   (`d58e847`): skip pre-creation entirely when there is no target;
   whatever path a sync relationship eventually receives into is
   created on demand at receive time, same as a brand-new multi-level
   backup-mode target already is.

With that fixed, the LXC-based `add-client --mode=sync` pairing,
scope-restriction, seed and activation all completed cleanly — but
inspecting the result showed `zfs list -r hdd/backuptest_targets` on
the **real pve1 host** listing the "received" dataset exactly **once**,
not twice. Because the container shares the host's kernel and zpool
import table, and sync mode reproduces the source's own path with no
prefix, the "source" (as seen through the container) and the
"destination" (as seen on the host) were the literal same dataset
object the whole time. The seed/sync commands succeeded, but proved
nothing about cross-host data movement — this was disclosed to the
owner as a genuine architectural limit of privileged LXC (pool names
are a single global namespace shared with the host kernel; two
same-named, genuinely independent pools cannot coexist under one
kernel), not something a container flag can fix.

### Second attempt: a real VM, genuine storage independence

The owner chose to close the gap properly rather than accept partial
evidence. Built:

- A real Debian 12 KVM guest (`labvm`, cloud-init, own boot disk) on
  metropolis pve1 — **its own kernel** (`6.1.0-51-cloud-amd64`,
  independent of pve1's `5.15.102-1-pve`), not a shared one.
- `zfsutils-linux`/`zfs-dkms` built genuinely from source against that
  kernel (required installing the matching `linux-headers-*-cloud-amd64`
  package after a first DKMS build silently targeted the wrong kernel
  flavor and produced a module that would not load — caught by
  `modprobe zfs` failing, not assumed to have worked because `apt-get`
  returned 0).
- A second virtual disk, a fresh `zpool create testsync` on it —
  **pool GUID `7174827982115380259`**, wholly independent of the
  matching file-backed `testsync` pool created separately on pve1
  itself (**pool GUID `6403485474931656966`**) purely for the naming
  match sync mode requires (same pool name on both sides; the two
  underlying pools are provably different objects).

### Sequence and evidence

1. `zfs create testsync/gatei_src` on the VM, one file, one snapshot
   (`@seed0`, GUID `11286747257047800743`, recorded before any transfer).
2. `add-client labgatei2 --lan=192.168.28.153 --mode=sync`, `--join` on
   the VM, scope drafted (one dataset from one pool — nothing to hand-restrict
   this time, the VM has no other data at all) and committed.
3. `seed` — real transfer. Verified on **pve1's own, separately-created**
   `testsync` pool: the received snapshot's GUID (`2466882639255399635`)
   matches a snapshot the VM's *own* listing shows under that same GUID
   (seed's own auto-snapshot, not `@seed0` literally — a real ZFS
   send/receive, not a name copy); content byte-identical
   (`gate i real sync test v1`).
4. `verify-endpoint`, `activate-client` — cron installed.
5. A controlled change on the VM source (appended a line, new snapshot),
   the installed cron line run by hand. First run correctly refused
   (`written@` > 0 — because inspecting the *previous* step's result had
   involved manually mounting the pull target, which itself writes;
   the pre-existing safety gate from the original campaign caught it
   exactly as designed). Re-run with `-f`, understanding precisely why
   the divergence existed and that it was safe to discard: full resend,
   content verified afterward as `v1` + `v2` both present.
