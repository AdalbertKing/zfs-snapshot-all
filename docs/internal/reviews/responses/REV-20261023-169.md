# Response to REV-20261023-169

## F1 — IMPLEMENTED

### Analysis

Accepted as stated, with a second cause of the same class found while proving the
root run.

1. **The record directory (the finding).** The suite sourced `zfs-backup.sh`
   first, so `lib-backup-common.sh` had already set
   `CLIENTS_DIR=/etc/zfs-snapshot-all/clients`. The helpers' `${CLIENTS_DIR:-$(mktemp -d)}`
   therefore never took the `mktemp` arm. A root run wrote `lb.conf` into the host's
   real `/etc`, and every later one-shot `--name=lb` case met "relationship 'lb'
   already exists".
2. **The cron spool (found while proving the root run).** `cron_known_accounts`
   also lists every account in the host's cron spool (`CRON_SPOOL_DIRS`). Root can
   read the spool; an ordinary user cannot. On pve9, root saw the real `bkp` and
   `zfsbackup` crontabs. The crontab stub "claims" `claimed.conf` for every account,
   so with only fix 1 applied a root run was 134/29, failing on "config ... already
   drives bkp's managed crontab block, and this run resolves to account 'root'".
   This is also why the reviewer's evidence script, run as root on pve9, gives 1/2
   instead of the 156/5 signature. Run as an ordinary user it gives the reviewer's
   3/0.

Both causes are the suite consulting host state it does not own, so the fix covers
both.

### Planned or implemented change

`test/localbackup/run.sh` only. No production code changed, and name-collision
behaviour is untouched.

- **Before `source "$ZB"`**, every product path that defaults to `/etc` or `/var` is
  exported to a directory under `$WORK/host`: `CLIENTS_DIR`, `RELATIONSHIPS_DIR`,
  `PEER_STATE_DIR`, `PROFILE_USER_ROOT`, `ZFS_MEDIA_KEY_DIR`, `SETTINGS_FILE`,
  `SERVER_CONF` and `ZFS_PROGRESS_DIR`. `CRON_LOCK_DIR` was already there. Because they are exported,
  `bash "$ZB"` children inherit them.
- **After sourcing**, `CRON_SPOOL_DIRS` is set to an empty fixture directory. It is a
  plain array assigned at source time, so it cannot be set before.
- **One-shot cases** get a fresh directory. `lb_clients()` returns a new
  `mktemp -d "$WORK/clients.XXXXXX"` when `CLIENTS_DIR` is still the suite default
  (`LB_DEFAULT_CLIENTS`); otherwise it returns the caller's directory. `run()`,
  `runi()` and `runp()` use it.
- **Shared-state cases keep one explicit shared directory.** The `LC`, `RL`, `LN` and
  similar cases already pass one. KROK 5 still sets `CLIENTS_DIR="$K5C"` for its
  series. After KROK 5, the old `unset CLIENTS_DIR` becomes
  `CLIENTS_DIR="$LB_DEFAULT_CLIENTS"`, so the one-shot cases that follow get fresh
  directories, and direct `cmd_*` calls never see an empty `CLIENTS_DIR`.
- **Negative control** (two new cases):
  - two one-shot `--name=lb` installs in a row both install; the second does not
    see the first's record, and the suite default directory stays empty;
  - every host path the sourced product resolved (the nine above plus the cron
    spool) is under `$WORK`.

### Remaining risk

- `bash "$ZB"` children re-source the product and so read the real cron spool
  again. That array cannot be exported. The child cases use their own unclaimed
  configs (`bare.conf`, `alias.conf`, `nocopy-*.conf`, `tgt-*.conf`), so the
  stub's claim cannot match them. The root run above includes these cases.
- `QUIESCE_PVE_DIR` still defaults to `/etc/pve` and is only read. It is outside
  `/etc/zfs-snapshot-all` and outside this finding.
