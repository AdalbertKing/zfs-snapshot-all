# Response to REV-20260809-084

## F1 — IMPLEMENTED, and the fix itself hid two more bugs before any test ran

ACCEPTED. `coverage_conflicts()`'s `. "$f" 2>/dev/null || exit 0` is exactly
the fail-open the finding describes: a damaged record read as "no conflict",
and `assert_no_coverage_overlap()`'s own diagnostic ("could not check ...
refusing rather than guessing") was unreachable for that class of failure.

The per-record subshell now exits 2 — distinct from the normal 0/1 the caller
never sees — for three cases: the file is not readable, `.` fails to source
it, or it sources cleanly but leaves `CLIENT_NAME` empty (a record that names
no relationship could own anything). `coverage_conflicts()` turns any of those
into an overall `return 2` and prints a line identifying the file. All three
are still evaluated inside the existing per-record subshell, so isolation
between records is unchanged.

### What writing the test found, twice, before the first green run

I did not trust the one-line diff. Running the suite immediately after the
minimal fix surfaced two more defects, both worse than F1 in isolation:

**1. A false fail-closed on every disjoint record.** The per-record subshell's
exit status, once consumed by `... ) || { ...; return 2; }`, is whatever its
LAST command returned — and the last command in the ordinary path is
`path_overlaps "$owned" "$req" && printf ...`. For any record whose *final*
dataset/path pair does not overlap, `path_overlaps` returns 1, so the whole
`&&` chain returns 1, and the new fail-closed line reported a perfectly valid,
successfully-read, non-conflicting record as "unreadable or unparseable". The
first full run of `test/zfsbackup/run.sh` went from PASS=304/FAIL=6 straight
to a REAL regression: every disjoint-append, parent/child overlap, and
removed-relationship case failed with the new fail-closed message, because
the code path could no longer tell "read fine, found nothing to report" apart
from "could not read at all". The fix adds an explicit `exit 0` as the last
statement of the subshell, after the scan loop, so a record that was
successfully read and scanned always exits 0 regardless of what the scan
found — conflicts travel through the printed lines, not through the exit
status.

**2. The diagnostic naming the bad record never reached the operator.**
`coverage_conflicts()` prints a line identifying the file (`!<TAB>path<TAB>
reason`), but `assert_no_coverage_overlap()` discarded `$conflicts` entirely
on the `rc != 0` path and always died with the same generic sentence. REV-084
is explicit: "The diagnostic should name the record that could not be
checked." `assert_no_coverage_overlap()` now parses the `!`-tagged line(s)
out of `$conflicts` and appends the file and reason to the refusal message.

Neither of these was visible from reading the one-line diff in isolation —
both were only visible once the same suite that exercises ordinary,
successful overlap detection was run against the "fixed" code and produced
the wrong kind of red.

## Remaining risk

The overlap guard is now fail-closed for the three failure shapes this REV
named (unreadable, unparseable, nameless). It is deliberately still a
conservative path-prefix rule, not the full recursion/coverage model — that
scope boundary is REV-083's, not this one's, and is unchanged here.
