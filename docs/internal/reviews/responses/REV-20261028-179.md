# Response to REV-20261028-179

## F1 — IMPLEMENTED

### Analysis

Accepted as reported. `deploy.sh` (top-level `REPO_URL` resolution) and
`cmd_prepare_source()` in `zfs-backup.sh` fell back to
`https://github.com/AdalbertKing/zfs-snapshot-all.git` when the checkout had no `origin`.
Both feed a clone whose hourly self-update then follows that URL. Since 2026-10-28 the
development repository is also private, so the same fallback now makes an anonymous clone
fail instead of silently switching channel; either way it is wrong for the release.

Of the two remedies the review allows, the stock fallback is changed rather than refusing:
a tree without Git metadata that came from the release (archive, copied tree) is the
ordinary case, and the release repository is the only channel the package publishes.

### Implemented change

- `deploy.sh`: no `origin` -> `REPO_URL=https://github.com/AdalbertKing/zfsbackup.git`.
  An explicit `REPO_URL` still wins, then any `origin` the checkout has (a fork), then the stock URL.
- `zfs-backup.sh cmd_prepare_source()`: the same fallback. The URL is used for the
  `git clone` and, on the bundle path, for the `remote add origin` of the unpacked
  checkout, so both paths end with the release origin and the updater keeps that channel.
- `test/release` 3b: no shipped `*.sh`/`*.py` code line (comments excluded) names
  `AdalbertKing/zfs-snapshot-all`.
