# Response to REV-20261106-189

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. In `zfs-media-gate.sh attach`, the one-run lock was taken only when its
file could be created, and the run record was written with `|| :`. A lock that could not be
created, or a record that could not be written (for example a directory at `rep.running`),
did not stop the import. A second run then found no live holder, imported or found the pool,
and its `detach --engine-rc 75` exported the pool the first run was writing to.

The lock was fail-open to keep the REV-20260829-123 F2 outcome: with an unwritable state
directory, the refusal came later, from the imported-by-us marker write, after an import and a
compensating export. Refusing at the claim gives the same result ("will not proceed",
nothing left imported) without importing first.

### Planned or implemented change

`zfs-media-gate.sh`, attach (before any import):

- the lock file cannot be created or opened → `claim_refuse`, rc 2, `emit failed`, the medium
  is not touched;
- the start time of `$PPID` cannot be read from `/proc` → the same refusal (without it the
  record could never name this run);
- the claim is written to `$RUNNING.tmp.$$` and renamed with `mv -fT` (atomic; with a
  directory at the record path `mv -T` fails instead of moving the file into it -- measured
  with GNU coreutils 8.32: "cannot overwrite directory ... with non-directory", rc 1); a write
  failure → refusal;
- the record is read back and must equal `"$PPID <start time>"`, otherwise → refusal.

`zfs-media-gate.sh`, detach. The ownership rule for every exit:

- the record names another live run → leave the medium alone (unchanged, A11/A13);
- a record exists (file, directory or symlink) but is not exactly three numeric fields → do not
  export. rc 2. If the pool is imported, the message says DO NOT UNPLUG and how to clear the
  record. A run whose own attach refused at the claim ends here without touching the medium;
- no record at all → the medium is unclaimed (a manual detach, or a run that started before
  this guard). The imported-by-us marker decides, as before;
- the record names this run, or a run that is dead → proceed. `clear_running` removes only this
  run's record.

An early exit in attach after a successful claim (absent medium, quiet source, lineage
refusal) leaves the record naming this run's subshell. The same bracket's detach sees it as its
own and clears it. If the bracket dies, the record names a dead process and blocks nothing
(RU5).

Tests, `test/mediagate/run.sh`:

- F2 (unwritable state dir): rc 2, "will not proceed", nothing imported;
- F2 with a directory at `rep.imported-by-us` (claim fine, marker write fails): the original
  compensating export and its DO NOT UNPLUG variant stay covered;
- RU6: a directory at `rep.running` → attach rc 2, nothing imported;
- RU7: the other run's pool is imported and its marker matches, the record is unreadable →
  detach does not export, rc 2, DO NOT UNPLUG;
- RU8: a garbage record, and a one-field numeric record → detach does not export;
- RU9: a directory at `rep.running.lock` → attach rc 2, nothing imported;
- RU10 control: a sound state directory → attach imports; with no record, detach exports as
  before;
- the existing RU1-RU5 (live holder, overlap, age, dead holder) and the absent-medium and
  quiet-source sections are unchanged.

### Remaining risk

- A record deleted by hand while a copy runs makes the medium look unclaimed. The next run's
  claim succeeds, and its attach meets the pool already imported by the first run. That is the
  existing imported-by-us path, not a new one. Removing the record is an operator act, and the
  detach message names it only for the unreadable case.
- Not run on a real ZFS host or with a real USB medium. No production test is authorised by the
  review.
