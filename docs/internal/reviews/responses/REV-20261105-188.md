# Response to REV-20261105-188

## F1 — IMPLEMENTED

### Analysis

Accepted as stated. `quiesce_whitelist_gaps` read both enumerations (the dataset of each
local `-q` line, and every root of `/etc/zfs-quiesce-allow/<account>`) through
`while ... done < <(zfs list ... 2>/dev/null)`. The producer's status was never seen, so a
listing that failed before any row read as "this line freezes no guest", and one that failed
after some rows read as a complete set. The caller warned only on non-empty output, so a
failed check was silent. The U149-c test fed a healthy listing only.

### Planned or implemented change

`zfs-backup.sh`:

- Each listing runs into a variable, `out=$(zfs list ... 2>"$ef"); rc=$?`, and its status
  is checked. stderr goes to a temporary file, so it never mixes into the rows.
- **A failed listing** is `? <dataset> zfs list rc=<n>: <last stderr line>`. This applies to
  the job side and the whitelist side, whether the failure comes before or after rows. Its
  rows are dropped: no guest set and no coverage set is built from a listing that did not
  finish.
- **A whitelist file that exists but cannot be read** is `? <file> the whitelist cannot be
  read`. An absent whitelist is still a known answer: every guest is uncovered, as before.
- **The install-time warnings** move from `atomic_replace_and_install` into
  `quiesce_whitelist_warn <account> <block>`, which the install path calls at the same place.
  When any `?` line exists, it warns that coverage is UNKNOWN and names each dataset with its
  reason. In that case it also says that the list of uncovered guests, if one follows, may be
  incomplete or name covered guests. A failure on the whitelist side can turn a covered guest
  into an apparent gap, so the two warnings stay separate and the first one qualifies the
  second.
- If the temporary file for stderr cannot be made, the answer is `? <block> mktemp failed`,
  which also reads as UNKNOWN (not tested; same guard shape).
- Advisory as designed: nothing is refused, and nothing is granted. `quiesce_whitelist_warn`
  returns 0 in every case.

Kept unchanged: root (nothing to check), lines without `-q`, a healthy listing with no gap,
and the known gap (CT 105 in the pve0 shape).

### Remaining risk

- The unreadable-whitelist branch has no automated case. Where the suite runs as root (pve9),
  a mode-000 file is still readable, so the case cannot be built that way; it is a two-line
  `[ -e ] && [ ! -r ]` guard, read rather than measured. The `mktemp` failure branch is
  untested for the same kind of reason.
- REV-188 asks for "final status". The function and its caller are asserted to return 0. The
  install path's own status was not exercised in a test: it is unchanged, and the warning
  cannot refuse.
- No live host was used. The change only reads (`zfs list`), and this review authorizes no
  production test. A throwaway-host check would be an install of a `-q` relation for a
  delegated account with a whitelisted root that does not exist. The diff adds no new host
  interaction and does not require one.
