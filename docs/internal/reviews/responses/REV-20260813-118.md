## F1 round 1 — ACCEPTED and IMPLEMENTED. The preview was blind to state that lives in no snapshot.

*Kept for the record. Round 2 above supersedes the `written=0` row of the table
below — that state is now unproven, not clean.*

The finding is correct and the reasoning is the part worth repeating: my blocker set
was a set of **snapshot names**, so by construction it could only see state that had
already been captured. Data written after the source's newest snapshot is in no
snapshot at all, and it is the one class of state a destructive recovery destroys
*irrecoverably* — a rolled-back snapshot at least existed; those bytes never did.
The preview answered `Nic po stronie zrodla nie blokuje` for exactly that state.

### The fact used, and why that one

`written` — ZFS's own accounting of the space written to a dataset since its most
recent snapshot, read as `zfs get -Hp -o value written <src>`. It is a native
property, not a second state authority, and it works for ZVOLs as well as
filesystems. `zfs diff` was rejected: it needs the snapshot mounted, does not apply
to volumes, and walks the whole dataset — an expensive read to answer a question a
property already answers.

Three states, treated distinctly:

| `written` | verdict |
|---|---|
| `0` | the **only** state permitted to read as `NIC DO ZROBIENIA` or as "nothing blocks" |
| `> 0` | the byte count is printed, the loss is stated, the operation is declared destructive **even when no snapshot blocks** |
| unreadable / non-numeric | classified destructive — your option 2. A failed read is not a clean source |

The `unknown` branch matters more than it looks. `written="$(zfs get ... 2>/dev/null)"`
returning empty on a permission or naming failure would otherwise have fallen into
whichever branch the code checked last, and the fail-open direction here is silence.

### What the lab caught

Between B's `dd` and B's measurement I ran `sync`, and `written` still read **0**.
It only became `4268032` after `zpool sync hdd`. `written` reflects the last
**committed txg**, and this pool commits roughly once a minute rather than the 5 s
default (`/proc/spl/kstat/zfs/hdd/txgs` showed ~61 s between commits). A write made
seconds before the preview can therefore be invisible to it.

I did not paper over this:

- the clean wording no longer promises an idle source. It says `written=0 wedlug
  ostatniego zatwierdzonego txg` and, in the "nothing blocks" branch, tells the
  operator to confirm the source is idle before anything destructive;
- forcing the window shut with `zpool sync` was rejected — that is a pool-wide
  write, and this verb advertises itself as read-only in its own closing line;
- the measurement and the rejected alternative are in the code comment, not only
  here, because the next person to read `written` will have the same idea I did.

Had I written this from the property's documentation, I would have claimed
`written=0` means "nothing was written". It does not; it means "nothing is
accounted yet".
