# Response to REV-20260813-118

## F1 — ACCEPTED and IMPLEMENTED. The preview was blind to state that lives in no snapshot.

The finding is correct and the reasoning is the part worth repeating: my blocker set
was a set of **snapshot names**, so by construction it could only see state that had
already been captured. Data written after the source's newest snapshot is in no
snapshot at all, and it is the one class of state a destructive recovery destroys
*irrecoverably* — a rolled-back snapshot at least existed; those bytes never did.
The preview answered `Nic po stronie zrodla nie blokuje` for exactly that state.

### The fact used, and why that one

`written` — ZFS's own accounting of the space written to a dataset since its most
recent snapshot, read as `zfs get -Hp -o value written <src>`. It is a native
property, not a second state authority, and it works for ZVOLs as well as
filesystems. `zfs diff` was rejected: it needs the snapshot mounted, does not apply
to volumes, and walks the whole dataset — an expensive read to answer a question a
property already answers.

Three states, treated distinctly:

| `written` | verdict |
|---|---|
| `0` | the **only** state permitted to read as `NIC DO ZROBIENIA` or as "nothing blocks" |
| `> 0` | the byte count is printed, the loss is stated, the operation is declared destructive **even when no snapshot blocks** |
| unreadable / non-numeric | classified destructive — your option 2. A failed read is not a clean source |

The `unknown` branch matters more than it looks. `written="$(zfs get ... 2>/dev/null)"`
returning empty on a permission or naming failure would otherwise have fallen into
whichever branch the code checked last, and the fail-open direction here is silence.

## The live lab exposed something I would have shipped as fact

Required proof, on pve1, `zfs-2.1.9-pve1`, throwaway datasets, since the property
depends on real dirty/divergence semantics.

**A — clean source, the control**

```
hdd/rev118src@s1	9144351917357063255
written = 0
  Strategia:  NIC DO ZROBIENIA -- zrodlo jest juz dokladnie w zadanym punkcie
```

**B — the same fixture, 4 MiB written, no new snapshot** (this is the case F1 named)

```
hdd/rev118src@s1	9144351917357063255      <- identical snapshot set to A
written = 4268032
  Strategia:  ODRZUCENIE ZYWYCH ZMIAN, bez transferu -- zrodlo stoi na zadanym
              punkcie i nie ma nowszych snapshotow, ale po nim zapisano dane.
  ZYWE ZMIANY PO OSTATNIM SNAPSHOCIE ZRODLA: ZFS rozlicza written=4268032 B
  ... odtworzenie niszczace je ODRZUCI.
```

The snapshot listing in A and B is byte-identical. Only the live delta differs, so
nothing but the new fact can be producing the different verdict.

**C — that same delta, now snapshotted, must go back to being a rollback**

```
written = 0
  Strategia:  SAM ROLLBACK, bez transferu
  BLOKUJE / DO USUNIECIA (snapshoty zrodla NOWSZE niz wspolna baza):
    s2
```

### What the lab caught

Between B's `dd` and B's measurement I ran `sync`, and `written` still read **0**.
It only became `4268032` after `zpool sync hdd`. `written` reflects the last
**committed txg**, and this pool commits roughly once a minute rather than the 5 s
default (`/proc/spl/kstat/zfs/hdd/txgs` showed ~61 s between commits). A write made
seconds before the preview can therefore be invisible to it.

I did not paper over this:

- the clean wording no longer promises an idle source. It says `written=0 wedlug
  ostatniego zatwierdzonego txg` and, in the "nothing blocks" branch, tells the
  operator to confirm the source is idle before anything destructive;
- forcing the window shut with `zpool sync` was rejected — that is a pool-wide
  write, and this verb advertises itself as read-only in its own closing line;
- the measurement and the rejected alternative are in the code comment, not only
  here, because the next person to read `written` will have the same idea I did.

Had I written this from the property's documentation, I would have claimed
`written=0` means "nothing was written". It does not; it means "nothing is
accounted yet".

## Regression

`test/restore/run.sh`, three new cases. The first is the required discriminating
one: it is the **existing no-op fixture** with nothing changed but the live delta,
so an implementation that only looks at snapshots fails it while still passing every
other case.

```
PASS strategy: a source exactly at the point IS a no-op (control)
PASS strategy: live unsnapshotted source data is named and never reads as 'nothing to do'
PASS strategy: an incremental over a dirty source still declares the live changes
PASS strategy: an unprovable live state is classified destructive, not clean
```

The second guards the verdict where the temptation is strongest — an incremental
*can* proceed, so "clean" is the comfortable answer — and the third pins option 2.
The stub is strict about the shape (`get -Hp -o value written <ds>`); asking for a
human-formatted value or a different property fails the run rather than passing
quietly.

## Remaining risk

1. **The txg window.** Bounded by the pool's commit interval, one minute on this
   pool. The preview states the qualification; it cannot close it read-only. When
   the destructive verb exists, the durable answer is for *it* to snapshot the
   source before destroying anything, which converts "unaccounted live data" into
   "a snapshot the operator can keep". I am not building that here.
2. **`written` is a space fact.** A change that writes and frees the same blocks
   between txgs could in principle account to zero. I have not constructed such a
   case, and I am labelling that as unmeasured rather than claiming it cannot
   happen.
3. Measured on `zfs-2.1.9-pve1` only, as with REV-116.

Not claiming closure.
