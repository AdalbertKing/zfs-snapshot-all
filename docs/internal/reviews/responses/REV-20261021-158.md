# Response to REV-20261021-158

## F1 — IMPLEMENTED

### Analysis

Accepted and reproduced through the shipped script. `tag()` spliced the
landing path (built from a crontab destination) and the `-j` identifier into
a shell string run by `awk ... | getline`; an apostrophe ended the intended
quoting. With blob `2f6c301c` and a line whose destination and `-j` contain
`'; touch <marker>; echo '`, the suite's marker file was created -- the
injected command ran, under `--plan` too.

### Planned or implemented change

`hostscripts/capacity-guard.sh`:

- `tag()` and `landing()` are gone from awk; awk runs no command at all.
- Before the candidate awk, bash computes every needed tag: for each local
  transfer line (in `facts` order) and each dataset under its root, the
  landing path is built with parameter expansion only (host:base -> base/ds,
  bare user@host -> ds, local -> dst/ds) and passed with `-j` as BYTES:
  `printf '%s\0%s' "$L" "$id" | md5sum | cut -c1-8` -- the same bytes as
  `lib-zfs-snap.sh:bookmark_target_tag`. The result table
  (`ds<TAB>line<TAB>tgt-xxxxxxxx`) is read by awk as data.
- A missing tag for a needed target blocks the dataset (fail closed), as a
  missing bookmark already did.
- The tokenizer refuses a tab inside a quoted token (the tag table is TSV);
  the loop over `facts` reads with a non-whitespace separator (`\037`):
  bash `read` collapses consecutive tabs, so an empty `-j` shifted the fields
  -- found by the existing bookmark tests during this change.

  `finisz/REV-158`).

  the marker is never created, no destroy in that dataset, the dataset is

  equals the engine's byte for byte (bookmark found, cleaning below the base

### Remaining risk

None identified for this sink. The growth guard on its own branch (U50,
alarm only, not merged) computes no tags and passes crontab data only as
quoted `zfs list` arguments; it will be moved to the same trusted source
before it merges.

## F2 — IMPLEMENTED

### Analysis

Accepted. A `# BEGIN zfs-backup-managed` marker in any account's crontab was
taken as destructive authority, and the reserved Proxmox families were
protected only by trusting ownership patterns.

### Planned or implemented change

- Ownership no longer comes from crontabs. The guard renders the host's own
  configs, `$CONFDIR/jobs.<host>.conf` and `jobs.<host>.<account>.conf`
  (default `/etc/zfs-snapshot-all`), with `gen-cron.sh -c` as root -- the
  same files deploy and zfs-backup install cron from -- and parses only that
  output. A config without rules ("no send/prune/monitor rules resolved") is
  empty, not an error; any other render failure fails closed.
- Trust check (`trusted_path`): each config, its directory, each peer scope
  and `gen-cron.sh` (taken from the deploy-installed
  `/usr/local/bin/zfs-backup` link, fallback the usual checkout path) must be
  owned by uid 0 and not group/other-writable; otherwise nothing is
  destroyed, rc 1, alert naming the file. `ZFS_GUARD_TRUST_UID` exists only so
  the non-root CI suite can own its fixtures; root's cron environment is not
  writable by other accounts. Measured on the lab: every config and scope is
  `root:root` 644/755.
- No config at all, unreadable config directory, malformed facts: fail
  closed as before.
- `__replicate_`, `__migration__` and `vzdump` are skipped at the
  destructive decision point before any ownership match, independent of
  holds and `guard_min_keep`.

### Evidence

- New cases: a marker-wrapped block in another account's crontab
  (`cron/mallory`) targeting `tank/c` -- zero destroys there while the
  registered relationships still clean; config group-writable, `gen-cron.sh`
  other-writable, no host config -- each rc 1, zero `zfs destroy`, alert
  naming the file; reserved families with explicit `__replicate_`, `vzdump`
  and `__migration__` retention patterns -- none destroyed, ordinary
  families still cleaned. On blob `2f6c301c`: the forged crontab case FAILS
  (`tank/c` destroyed), the reserved-families case FAILS, the trust cases
  FAIL.
- Live, read-only (`--plan`, real configs, no destroy): pve10 renders its
  config and lists the collector's daily copies as candidates; pve9b (a pure
  pull source) reports "nie wiem, które migawki są nasze" and fails closed.
- `./test/impact.sh origin/main` selects the suite `alertmail` and the manual
  obligations `deploy-check-only` and `project-status`; `./test/impact.sh
  --verify`: rc 0.

### Remaining risk

The guard now trusts what root's configs say even if the installed crontab
was hand-edited differently; that is the intended authority (root's own
files). Rendering costs about 1.5 s per config on the lab.
