# Response to REV-20260809-083

## F1 — IMPLEMENTED (in two commits: `90bb026` then `57deecb`, the latter closes REV-084's gap in the former)

ACCEPTED. Overlap that is not an exact section-header collision was not
refused before `90bb026e2c9273ce0bd9d7f87f429bf732476883`: a relationship
owning `rpool/data` and a later one taking `rpool/data/vm-101` produced
different generated section headers, so the existing marker check never
fired, and both would then send and prune the same snapshots under different
policy.

`90bb026` added the required preflight: `coverage_conflicts()` reads every
other client record's `MANAGED_DATASETS`/`MANAGED_PRUNE_SCOPE` and
`path_overlaps()` refuses a candidate whose requested path is a parent,
child, or exact match of anything another active relationship already owns.
`assert_no_coverage_overlap()` calls it from `emit_client_sections()` before
`remove_managed_sections()` — the first mutation of the working config — so
the refusal happens before any write, matching the required "fail closed
before mutation" property.

This response was not written when `90bb026` landed. The reviewer
independently found, and REV-20260809-084 records, that `90bb026`'s guard was
not actually fail-closed: its per-record subshell converted an unreadable or
unparseable existing record into "no conflict" via `|| exit 0`, so a
corrupted record — not merely a disjoint one — would have been silently
skipped and the candidate addition allowed. `57deecb23d8962e5ad47fc9312141e248776f3f5`
corrects that (full evidence in the REV-084 response), and is the SHA this
response cites as the implementation, because it is the
first commit where the fail-closed property REV-083 asked for actually holds
for damaged as well as absent-conflict records.

### Required properties, and where each is proven

- **disjoint existing CONFIG remains appendable** — `test/zfsbackup/run.sh`
  section 45 case 3 ("a disjoint source is still appendable").
- **exact-path collision remains refused** — section 45 case 4, and the
  pre-existing marker-collision path this preflight sits in front of.
- **parent→child and child→parent overlap are both refused** — section 45
  cases 1 (sync-mode child of an owned parent) and 2 (parent of an owned
  child, the other direction).
- **refusal occurs before CONFIG or crontab changes** — section 45 case 5
  asserts the candidate working file is empty (byte-identical to before the
  call) after a refusal; the crontab is never reached because
  `emit_client_sections()` calls the guard before it writes anything.
- **unrelated hand-written/native CONFIG remains untouched** — not separately
  re-tested here; unaffected by this preflight, which only reads other
  clients' records and only refuses before any write to the CANDIDATE
  working file.
- **a removed relationship reserves nothing** — section 45 case 6, so a
  torn-down pair does not block its own replacement forever.
- **fail-closed on a damaged record, not just an absent conflict** —
  REV-20260809-084's own three new cases (unreadable, unparseable, nameless),
  now section 46.
