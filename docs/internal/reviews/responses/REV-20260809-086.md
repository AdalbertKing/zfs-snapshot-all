### Corrected campaign design

Per the required shape: a candidate with a **different `CLIENT_NAME`**,
resolving to the **same peer-derived label**, requesting coverage that
conflicts with an already-active relationship, driven far enough to reach
`cmd_seed()`.

Investigating the real peer-manifest mechanics found the simplest possible
valid case: `peer_manifest_path(label)` is keyed by `peer_label(PEER_HOST)`
only — one manifest per peer, not per relationship — and it carries
`PEER_SAVED_DATASETS` itself. Two relationships sharing a peer therefore
share not just the label namespace but the literal recorded dataset list.
This means:

- the second relationship does not need its own `add-client`/pairing at
  all — it can be a hand-written client record (`STATE=pending_enroll`,
  same `PEER_HOST`) that reuses the first relationship's already-established
  peer manifest directly;
- calling `seed` on it reaches `load_client_and_connection()`, which loads
  that shared manifest, computes the exact same destination path as the
  active relationship, and hits `assert_no_coverage_overlap()` — an
  **exact-path** overlap, the simplest discriminating case, requiring no
  extra dataset to be created;
- critically, this candidate never touches `add-client` at all, so the
  name-uniqueness guard REV-086 flagged is structurally not in the path —
  the refusal can only come from the coverage guard.

This also avoids the exact risk REV-086 asked to be checked: a fresh
`add-client`/pairing dance for the second relationship could have mutated
shared peer-state relevant to the first. Skipping it removes that risk
rather than merely verifying around it.

### A third, independent defect found and fixed along the way

`remove-client`'s automated cron cleanup silently no-ops whenever no
`server.conf` exists (metropolis pve1's exact situation): `read_server_conf()`
unconditionally clears `CRON_CONFIG` and only restores it from
`$SERVER_CONF`, clobbering the value the client's own record had just
supplied. The same defect exists in `activate-client`'s re-activation path,
which is more serious — a re-activation would silently target a
freshly-recomputed default cronfile instead of the one actually installed.
Fixed in `67415a5795ad3d1cb659e3017c1485bc99b59a61` with regression coverage (`test/zfsbackup/run.sh` section
48) and a negative control against the pre-fix code. Full detail in that
commit and in the project memory entry for this campaign.
