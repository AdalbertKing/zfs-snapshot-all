# Response to REV-20260907-137

## F1 — IMPLEMENTED

### Analysis

The finding is correct, reproduced here, and the diagnosis in it is better than
the one I would have written: the defect is not a missing rule, it is a gate
aimed at the wrong boundary.

`save-profile` advertised two gates and both of them are real:

* `profile_validate_file` answers **who may own this field** — it is why
  `--pair_label=mine` is refused;
* `load_active_profile` answers **does the renderer survive this value** — it is
  why `keep = xyz` is refused, which dies inside the translation.

Neither of them has an opinion about what a value **means**. `send_schedule` is
copied through the renderer verbatim: nothing between the operator's keystroke
and the saved file ever asks whether those five fields are five fields. So the
reviewer's repro is exactly right, and it reproduces here on the reviewed head:

```text
save-profile --from=d7h24 --as=badcron --tier=hourly --send_schedule='not a cron'
rc=0, badcron.conf written, list-profiles says "valid":true
```

while the generator a future `add-client` actually runs says:

```text
gen-cron.sh: error: [dataset:...] tier=profile__badcron__hourly:
send_schedule = 'not a cron' -- a crontab time specification is exactly 5 fields
```

`--force` makes it worse in the way the review says: the working copy is built,
both gates pass, and the atomic rename lands over a known-good operator profile.
The transaction is honest — it never leaves a partial file — and it publishes an
unusable one.

The class matters more to me than the instance. This is the third time in this
package that a gate proved *a* property rather than *the* property (E39, E41),
and the shape is the same each time: a check written next to the code being
changed instead of at the boundary the value must survive. That is now E45.

### Planned or implemented change

**A third gate: the real `gen-cron.sh`.** Deliberately not a longer list of
rules here — a hand-copied cron/duration parser inside `zfs-backup.sh` would be
a second implementation of the generator's semantics, which is the shape
`test/deps.conf`'s contracts exist to kill, and it would drift the first time
`gen-cron.sh` learns a rule.

`profile_downstream_gate()` renders the candidate profile into the **same
minimal CONFIG v4 shape a relationship is built from** —

```text
[defaults]                     host_label only, as write_fresh_config_defaults does
<the profile's rendered [template:profile__<name>__<tier>] sections, whole>
[dataset:rpool/save-profile-downstream-check]   the rendered [dataset] fragment
[prune:rpool/save-profile-downstream-check]     the rendered [prune] fragment,
                                                emitted only when
                                                profile_declares_ladder says so
```

— and hands that file to `bash "$GENCRON" -c`. No `--install`, no crontab, no
dataset: the path is a name, not a place. On refusal the destination is not
touched and the generator's own message is quoted verbatim into the refusal.

The `[prune:]` half is conditional on the existing `profile_declares_ladder`,
not on a new predicate: emitting an empty ladder for a flat profile is the
defect measured on pve9 2026-08-25, and reproducing it inside a validation gate
would have refused every flat profile in the catalogue.

**What the gate does not cover, stated rather than papered over.**
`gen-cron.sh` lints per *referenced* tier (`lint_cron_schedule` is called from
the `[dataset:]` and `[prune:]` emitters, not from the `[template:]` parser), so
a tier that neither fragment references is judged by nobody. That is not a hole
below the boundary — it *is* the boundary: a tier no fragment names is a tier no
relationship built from this profile would ever use.

### Remaining risk

Cost: one `gen-cron.sh` invocation per `save-profile` call, on top of the render
the second gate already does. `save-profile` is an interactive, one-at-a-time
verb — this is not `list-profiles`, where the same cost per row was measured at
~500 ms and had to be made optional. Measured here at roughly a third of a
second on this box; on a Linux host it is a fraction of that.

The gate proves the candidate against the generator **as it is on this host at
this moment**. A profile saved today and used after a `gen-cron.sh` that has
learned a stricter rule can still be refused at create time — the same exposure
every installed config already has, and the reason the refusal quotes the
generator instead of paraphrasing it.
