# Response to REV-20260907-137

## F1 — IMPLEMENTED

### Analysis

Accepted in full. `save-profile` had two gates and both are this program's own
reading of the profile: `profile_validate_file` (ownership, field membership)
and `load_active_profile` (it renders). The generator that every future
relationship is built through was never consulted, and a value the renderer
merely copies -- `send_schedule`, `monitor_warn`, `prune_schedule`, anything
`gen-cron.sh` judges by its own grammar or its own reasoning -- passed both
gates untouched. Reproduced on `6498652` before the change, exactly as the
review describes: `--send_schedule='not a cron'` returned 0 and published
`badcron.conf`; the same with `--force` replaced a known-good file.

The review's reading of *why* is also right: the existing `keep = xyz` control
covers a value rejected during translation (`profile_keep_to_retain`), which is
the one place the renderer has an opinion. Everything it copies through was
unguarded.

### Implemented change

**GATE 3, after the render gate and before staging.** `profile_downstream_candidate`
(`zfs-backup.sh`, beside `profile_template_section`) composes the relationship
the generator would see, the way `emit_client_sections` composes a real one:

- the rendered `[template:profile__NAME__tier]` sections verbatim (the same
  text add-client appends via `profile_template_section`);
- the `[excluded:]` floors verbatim;
- one `[dataset:zfs-backup/save-profile-gate]` carrying the profile's own
  rendered `use_template` line (`profile_emit "$PROFILE_DS_FILE"`, as add-client);
- a `[prune:...]` only when `profile_declares_ladder`, carrying the rendered
  prune fragment (as add-client);
- `[defaults] host_label` as a placeholder -- the generator does not resolve
  it, and a real relationship carries its own.

Then the **real** `bash "$GENCRON" -c "$cand"` renders it. Non-zero refuses
with the generator's first `error` line quoted, before any file is staged,
so acceptance criterion 2 (no new destination) and 3 (`--force` target
byte-identical) follow from where the gate sits, not from cleanup. On rc=0 the
verb logs `gen-cron.sh accepted a relationship rendered from this profile`,
which exists only on that path. One composer, so the gate and any control of
it judge the same shape; no copied list of the generator's rules (criterion 1).

Not changed: confinement to `PROFILE_USER_ROOT`, the atomic rename, the
package-directory refusal, the two earlier gates, and the rule that nothing
installed is touched (criterion 6; the suite still asserts the installed
config byte-identical after every case, the gate-3 cases included).

Cost: one generator run per save, ~1.6 s measured (16 shipped profiles in
25.8 s). A save verb can afford it; `list-profiles` cannot, and was
deliberately left alone -- see Remaining risk.

### Remaining risk

- `list-profiles --json` still reports `"valid":true` from the two earlier
  gates only; a profile file hand-edited into the user directory with a
  generator-refused value will be listed valid and refused at add-client.
  Not changed here: PR #352 (`perf/list-profiles-no-render`) just removed
  rendering from that verb for cost reasons, and a generator run per profile
  would put ~1.6 s × N back. `save-profile` is the only writer of that
  directory, so after this change a generator-refused file gets there only by
  hand. If the catalogue's `valid` is to mean "usable", that is a separate
  decision with a cost; raised, not decided.
- The candidate uses placeholder identities. A refusal that depends on the
  REAL relationship (a `[template:]` collision with an installed config, a
  `use_template` that the installed config's other datasets contradict) is
  add-client's to make and stays there; this gate proves the profile alone.
