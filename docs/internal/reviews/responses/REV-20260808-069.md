# Response to REV-20260808-069

## F1 — IMPLEMENTED

### Analysis

Correct. The pre-pass claimed getopts-equivalence and implemented one case of it:

```bash
if [ "${#a}" -eq 2 ] && opt_takes_arg "$last" ...
```

"The last letter of a two-character token" is not the getopts grammar. `-em` is
`-e` then `-m`, and since `m:` takes an argument with nothing following it
inside the token, the next argv is that argument. The old code left it to be
inspected as a long option, so the MESSAGE became a recursion declaration.

I want to name the reasoning error rather than just the line. I wrote the
two-character check while thinking about the case I was testing (`-m X`),
and then described the result as "getopts-equivalent" in a comment. The comment
made the claim; the code never did. That is the same shape as the contract
premise corrected in Stage 2.2 — an assertion in prose that no test held.

### Implemented change

`cluster_needs_next()` walks the cluster left to right, as getopts does:

| token | next argv is | why |
|---|---|---|
| `-m` | the argument | `m:` takes one, nothing follows it |
| `-em` | the argument | `e` takes none, `m:` does, token ends |
| `-mfoo` | an option | `foo` **is** the value |
| `-mfooe` | an option | everything after `m` is the value, including `e` |
| `-ez` | an option | no letter in the cluster takes an argument |

### The probe, because two earlier ones were blind

My first probe compared "does it error". It could not discriminate: a **valid**
mode produces no output whether the token is data or a declaration.

My second probe appended a second declaration (`-em --recursive=flat -r`)
expecting a duplicate-declaration refusal. Also blind, and more subtly: on the
old code the long form was consumed, so `-m` took **`-r`** as its argument and
there was no second declaration to count. Both readings accepted; the difference
was invisible from outside.

The probe that works is a deliberately **invalid** mode. If the token is data,
nobody validates it; if it is parsed as an option, it is refused by value. That
asymmetry is the only externally visible difference, and the suite comment says
so, because the next person will reach for "does it error" first as I did.

### Remaining risk

The pre-pass now models option-argument boundaries correctly, but it still does
not know which letters are **valid** — an unknown letter inside a cluster is
passed through for getopts to reject. That is deliberate (one place decides what
is a legal option) and it means the pre-pass can consume a next argv for a
cluster getopts will reject anyway. The refusal still happens, one step later.
