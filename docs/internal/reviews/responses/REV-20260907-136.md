# Response to REV-20260907-136

## F1 — IMPLEMENTED

### Analysis

The finding is correct in all three of its forms, and it is mine in a way worth
naming: the fix it asks for is one I had already written, on the same day, one
function away.

`list_profiles_record` buffers its row and emits it only when complete. That
buffering exists because a profile that VALIDATES and then dies while rendering
left half an object in the middle of the array and made the whole catalogue
unparseable. Having found that shape, I fixed it at the site and did not ask the
question the shape deserved: *which other reader publishes a record it did not
itself validate?* Both of them did — `status --json` and `show-config` — and both
were merged with the defect intact.

The two halves the review separates are real and different:

* `record_load` **dies** for a field outside the per-record allowlist. In
  `status_json_record` that die arrived after `cmd_status_json` had already
  written `{"relations":[` and, for a second record, a comma. The command
  correctly refused and exited non-zero, and a front end reading stdout got 448
  bytes of truncated document. Reproduced here against `59b54452` byte for byte.
* `record_load` **returns non-zero** for a malformed value without dying. Nothing
  read that status, so the fields assigned before the bad line were published as
  state: `status --json` answered `rc=0` with a row named `broken` and an empty
  state, and `show-config` answered `rc=0` with a plausible `config_readable`.

The ordering observation in the review is the sharpest statement of the defect
and I reproduced it as a number: `show-config` on the same broken record printed
**155 bytes with `CRON_CONFIG` above the malformed line and 163 with it below**.
The reader was reporting whatever the parser had managed to assign before giving
up — the parser's partial state, published as the product's answer.

### Planned or implemented change

Three changes, no schema change (acceptance 5).

1. **`status_json_record`**: `record_load client "$1" || exit 1`. The load is a
   gate, not a step. A refusal ends that record instead of decorating it.
2. **`cmd_status_json`**: the publication boundary is buffered. Records are
   collected into a variable and the document is printed once, at the end, only
   if every selected record produced a complete object. A refused record dies
   with the parser's own message on stderr and stdout stays empty. stdout is one
   parseable response or nothing; there is no third outcome (acceptance 3).
3. **`cmd_show_config`**: the same gate on its single `record_load`, with a
   refusal naming the file.

The successful two-client contract is unchanged, and `list-profiles`'
per-profile buffering is untouched (acceptance 5).

Controls added, per acceptance 4 — both failure forms, the command status
asserted, and stdout measured rather than sampled:

| control | what it discriminates |
|---|---|
| disallowed field in the SECOND of two records | non-zero status |
| ...and stdout is 0 bytes | no prefix, no delimiter, no partial object |
| ...and the parser's refusal is on stderr | the message is the parser's, not a new one |
| unterminated quoted value | non-zero status instead of a plausible row |
| ...and stdout is 0 bytes | the rc-2 half of the boundary |
| `show-config` on the same record | refuses instead of describing |
| ...and prints no object | the partial-assignment leak |
| the malformed line ABOVE vs BELOW a valid field | the answer no longer depends on where it sits |
| two VALID records | the complete answer, both rows, still published |
| a NAMED read of a valid relationship with a broken one beside it | a neighbour's bad file is not collateral damage |

The suite runs these through the **real `zfs-backup.sh` entrypoint as a
subprocess**, not through the sourced functions. That is required rather than
tidy: this suite sources the program, so `die` there is a bare `exit 1` and the
fatal-die machinery that makes the worst form visible is armed only when the file
is the program. The reviewer's reproduction used the entrypoint for the same
reason.

### Remaining risk

The other two readers were checked for the same shape rather than assumed clean.
`monitor --json` loads no client record; it reads the installed crontab and runs
the frozen engine, and its own fail-closed path was already asserted.
`list-profiles` buffers per row already. `cmd_status`'s TEXT view still calls
`record_load` inside a per-record subshell without reading its status: a refused
record there prints its refusal and an empty column rather than a wrong value,
and no JSON boundary is involved — out of this finding's scope and named here
rather than left to be found.
