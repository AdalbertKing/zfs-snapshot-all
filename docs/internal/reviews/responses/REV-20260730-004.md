## Update: the IP-vs-hostname gap above has now been closed live

The user asked directly whether this had been tested with a genuinely different address (not just
the same IP twice), which was the right question -- it had not. A real second network path (VPN)
still isn't available in this environment, but a genuinely different ADDRESS STRING for the same
host is a valid, honest substitute for the specific claim under test (identity survives an address
change) and doesn't require fabricating a VPN: added a temporary `/etc/hosts` entry on pve0
(`192.168.11.11 pve1-vpn-test`, removed after), then ran the full cycle with `--lan=192.168.11.11`
first and `set-endpoint --vpn=pve1-vpn-test:22` second.

**This immediately found two more real bugs, neither hypothetical:**

1. **`verify-endpoint` failed outright** the first time: `Offending key for IP in
   /etc/ssh/ssh_known_hosts:4` / `Host key verification failed` -- even though the alias-keyed
   known_hosts file matched correctly. Root cause: OpenSSH also consults
   `/etc/ssh/ssh_known_hosts` (`GlobalKnownHostsFile`, on by default) keyed by the literal connected
   address, not the alias -- and pve0's system-wide file already had an unrelated, pre-existing RSA
   entry for `192.168.11.11` (nothing to do with this project) that conflicted with the real ED25519
   key and aborted the connection. Fixed with `-O GlobalKnownHostsFile=/dev/null` everywhere this
   file builds ssh flags.
2. After that fix, the connection succeeded, but OpenSSH's `CheckHostIP` (also on by default) then
   **silently wrote a second, hashed-hostname entry into the alias-keyed known_hosts file** as an
   anti-spoofing courtesy record -- harmless (it only recorded a key already proven trusted via the
   alias) but defeated the point of a file meant to contain exactly and only what this script
   generates. Fixed with `-O CheckHostIP=no`.

**Re-verified clean after both fixes**: `verify-endpoint` succeeded through the hostname endpoint
with zero warnings and no stray writes to the alias file; `activate-client` regenerated exactly the
4 lines for this client, connecting via `zfsbackup-pve0@pve1-vpn-test` (the hostname) with
`-O HostKeyAlias=zfs-client-zfsbktest` UNCHANGED from the IP-based run -- the actual claim under
test, now proven, not just simulated. `crontab -l` diff showed exactly those 4 lines changed
(address + the two new `-O` flags), target/alias/everything else identical. Full cleanup done
(`remove-client`, peer-side unallow/userdel, both throwaway datasets destroyed, temporary
`/etc/hosts` entry removed, crontab confirmed content-identical to baseline).

**Still not tested**: a real VPN tunnel specifically (WireGuard/etc. adding actual latency, MTU,
and route-flap characteristics a plain hostname substitution doesn't exercise) -- the identity/
address-independence mechanism itself is now proven, but the specific transport is not.
