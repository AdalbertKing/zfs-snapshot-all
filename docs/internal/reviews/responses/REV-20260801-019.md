### Point 4 — DISPUTED on ordering, not on the requirement

The end state required is one block or the other, never both. That is
implemented. The review's sketch reaches it by installing the account's block
first and then removing root's; I remove root's first.

Installing first leaves both blocks live for the width of the second step. These
blocks contain prune lines, so "both live" means two `delsnaps` runs over one
dataset set, concurrently, each thinking it owns the retention. Removing first
can only lose a tick.

I am not asking for the requirement to change — the end state is the same, and
this order also never passes *through* the state the requirement forbids.

### Point 5 — the fail-closed rule found a fail-open bug in its own guard

Worth reporting because the test caught something I had written wrong that same
hour. `crontab_of_or_die()` originally returned the crontab on stdout and called
`die` on an unreadable one. `die` is an exit, and an exit inside `$(…)` or a
pipeline element ends only the subshell: the caller carried on with an empty
string, and for an overlap check an empty string reads as *nothing overlaps*.

The guard designed to fail closed was failing open, and it was the new
fail-closed test that said so — not review, not reading. The helper now writes
to a file the caller names, so `die` runs in the caller's shell.
