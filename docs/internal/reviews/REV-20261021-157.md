# REV-20261021-157 — U35 can silently fail before capacity protection starts

Reviewer: ChatGPT. Date: 2026-10-21.
Canonical published `main` inspected: `c989ece676b9684e42433356f45b8a39f2db3ea2`.
Affected: `hostscripts/capacity-guard.sh`, current blob `e46050b595d29037b837b2e7c4982d314c9383fd`.
This is a **new** preflight observability failure after the independently approved and closed REV-20261021-156. It does not reopen F1/F2 of that REV.

## F1 — P1: lock file open failure silently disables enabled guard with status 0

- Severity: **P1** (disabled unattended safety control misreported as successful)
- Blocking: **yes for production enablement of `[capacity] guard=on`**
- Affected: startup/locking, around line 97.

### Evidence

Current statement:

```bash
exec 9>"${ZFS_GUARD_LOCK:-/run/lock/zfs-capacity-guard.lock}" 2>/dev/null && flock -n 9 2>/dev/null || { [ "$PLAN" -eq 1 ] || exit 0; }
```

Two different conditions collapse into the same silent success: (a) another guard holds an otherwise valid lock (a reasonable skip), and (b) this process **cannot create/open** the lock file at all (missing parent, permission denied, read-only filesystem, invalid path). With `PLAN=0`, condition (b) exits 0, without a diagnostic or a call to `alert()`, before any pool is checked, even when `GUARD=on`. The setting `ZFS_GUARD_LOCK` is overridable by the environment; a misconfigured or newly read-only lock directory can keep the guard disabled indefinitely.

Isolated execution of the exact expression on Linux with an existing temporary directory `$t` and `ZFS_GUARD_LOCK="$t/missing/guard.lock"` (where `missing` does not exist) returned **rc 0** without reaching the subsequent statement. This is an isolated shell-expression reproduction, not a full live ZFS test.

### Required outcome

Separate **failure to open/create the lock file** from **normal nonblocking contention**. Open failure (and genuine `flock` system error) is a guard startup error: nonzero rc, explicit diagnostic containing the lock path and a best-effort alert. Contention while a valid guard is already active may remain a skip without an alert; document that policy. Never enter the destructive path without holding the lock.

### Acceptance criteria

- [ ] `guard=on` and nonexistent/non-writable lock parent: zero pool discovery or `zfs destroy`, nonzero rc, explicit error/alert.
- [ ] Valid, uncontended lock: normal behavior unchanged.
- [ ] Valid lock already held by another guard: no duplicate destructive run and clearly defined exit behavior, without treating it as lock-open failure.
- [ ] `--plan` has no destructive side effects; invalid lock path must at minimum report the error, rather than silently pretending locking succeeded.
- [ ] Isolated regression executes the actual `capacity-guard.sh` with a fake `zpool`/`zfs`, includes negative control against the reviewed old script.

## F2 — P2: temporary workspace creation failure also cannot alert

- Severity: **P2** (missing operational alarm)
- Blocking: **yes for production enablement of unattended U35**, because the workspace is needed before any capacity/retention decision.
- Affected: temporary directory initialization, around line 109.

### Evidence

```bash
WORK="$(mktemp -d 2>/dev/null)" || { say "brak katalogu tymczasowego -- nic nie robię"; exit 1; }
```

Failure to create the workdir returns rc 1 and prints a line but **does not call `alert()`**; this is an unattended 15-minute cron guard whose purpose is to warn and react as space becomes scarce. A full or read-only `TMPDIR` may make the guard inoperable precisely when alerting matters. In a shell-isolated reproduction, `TMPDIR` pointed to a nonexistent directory, `mktemp -d` failed, and the branch exited rc 1 without invoking any alert.

### Required outcome / acceptance criteria

- [ ] Failed `mktemp -d` means zero destructive calls, nonzero exit and best-effort `alert()` with reason (including the effective temp directory if safely available).
- [ ] Preserve safe cleanup of successfully created `WORK` and lock release.
- [ ] Fake-command regression with `TMPDIR` pointed to a missing directory, a healthy temporary-directory control, and an old-tree negative control.
- [ ] Confirm new startup alerts do not recurse through a broken queue, pretend notification succeeded, or start deletion despite unmet preflight requirements.
