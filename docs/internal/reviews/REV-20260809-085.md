# REV-20260809-085 — overlap refusal happens after seed can already write overlapping ZFS paths

Review time: 2026-08-09 18:05 CEST
Reviewed implementation: `f1c4b9607a4d5e86351538aa71675a2d619c73af`
Response path: `docs/internal/reviews/responses/REV-20260809-085.md`

## Verdict

**CHANGES REQUIRED.** REV-083's overlap algorithm is correct at the point where it runs, but the production call order does not protect the first destructive/data-plane boundary. A second relationship can reach `cmd_seed()` and perform a real `snapget.sh` receive before `assert_no_coverage_overlap()` is ever called.

This is a new finding, not a restatement of REV-083. REV-083 proved/refined the CONFIG/crontab preflight inside `emit_client_sections()`. This finding concerns the earlier ZFS mutation performed by `seed`.

## F1 — P1 — coverage preflight is after the first real transfer

- Severity: P1
- Blocking: yes
- Affected: `zfs-backup.sh` — `cmd_add_client()`, `cmd_seed()`, `load_client_and_connection()`, `snapget_local_base()`, `client_local_path()`, `emit_client_sections()`

### Evidence

The current production path has these relevant properties:

1. `cmd_add_client()` rejects only reuse of the same `CLIENT_NAME` by checking whether `clients/<name>.conf` already exists. It does not compare the new peer/dataset coverage against other client records before pairing/writing the client record.
2. `load_client_and_connection()` derives `LOAD_LABEL` from `peer_label($PEER_HOST)`, not from `CLIENT_NAME`.
3. In backup mode, `client_local_path(ds)` is therefore:

   `PEER_SAVED_TARGET / peer_label(PEER_HOST) / ds`

4. `cmd_seed()` loads the client/peer state, computes that base/path and then performs a **real non-dry-run** `snapget.sh` for every selected dataset.
5. The REV-083 guard `assert_no_coverage_overlap()` is called from `emit_client_sections()`, i.e. on the later CONFIG-generation/activation path, not before the seed transfer.

The latest discussion claiming that backup-mode parent/child overlap is structurally unreachable on the agreed host pair relies on the premise that the namespace label is the client name. That premise is false in the current code: the label is derived from the original `PEER_HOST`. `CLIENT_NAME` is deliberately a separate, address-independent relationship identity.

`cmd_add_client()` also does not reject a different client name merely because it names the same `--lan` peer. Thus two client records with different `CLIENT_NAME` values can share the same `PEER_HOST`/label namespace unless another independent guard rejects that topology.

### Concrete failure shape

A representative path is:

```text
existing relationship A:
  CLIENT_NAME = alpha
  PEER_HOST   = 192.0.2.10
  target      = tank/backups
  dataset     = rpool/data

new relationship B:
  CLIENT_NAME = beta
  PEER_HOST   = 192.0.2.10
  target      = tank/backups
  dataset     = rpool/data/vm-101
```

Both relationships derive the same backup namespace base:

```text
tank/backups/192.0.2.10
```

so B's seed destination is below A's managed destination. The current high-level sequence allows:

```text
add-client beta ...   # different name, so name-existence guard does not fire
seed beta             # REAL snapget receive happens here
...
activate-client beta  # only here emit_client_sections() reaches overlap guard
```

The system can therefore write into overlapping ZFS coverage before the guard intended to prevent overlapping ownership runs.

### Failure mode

This is not merely a CONFIG duplication issue. The unsafe mutation can occur during the initial real receive. Depending on dataset state, the result can be duplicate/competing ownership, an unexpected receive into an already-managed subtree, or a failed/partial seed that has already modified ZFS state before the later activation refusal.

The existing REV-083 invariant "refusal occurs before CONFIG or crontab changes" remains true but is too late to protect the earlier data-plane mutation.

### Required outcome

Move or reuse the same fail-closed coverage decision at the earliest high-level boundary where the final local destination paths are known **and before any real ZFS receive**.

Do not create a second overlap implementation. Reuse `coverage_conflicts()` / `assert_no_coverage_overlap()` or extract a single canonical helper that both seed-time and config-time paths call.

The required property is:

```text
no real snapget/snapreceive for a candidate relationship
until all candidate local managed paths are proven disjoint
from active relationship-owned coverage
```

If dataset resolution for mode-based clients is only available during `seed`, then the check belongs in `cmd_seed()` immediately after `load_client_and_connection()`/dataset resolution and before state/data mutation that authorizes the transfer. The later `emit_client_sections()` check should remain as defense in depth unless there is a clearly proven single-boundary replacement.

The checker must stay fail-closed on unreadable/unparseable/nameless active records as fixed by REV-084.

### Acceptance criteria

- [ ] Same-peer, different-client-name parent→child overlap is refused before invoking real `snapget.sh`.
- [ ] Same-peer, different-client-name child→parent overlap is refused before invoking real `snapget.sh`.
- [ ] Exact-path overlap is refused before invoking real `snapget.sh`.
- [ ] Disjoint coverage still reaches the seed transfer path.
- [ ] Damaged/nameless active client state still fails closed before transfer.
- [ ] The CONFIG-time guard remains effective or is replaced by one demonstrably equivalent canonical boundary.
- [ ] No duplicate overlap semantics/list is introduced.

### Minimal verification

Use targeted evidence only:

1. Stub `snapget.sh` with a recorder that makes invocation observable but performs no ZFS mutation.
2. Construct two client records that differ in `CLIENT_NAME` but share the same `PEER_HOST`/label namespace.
3. Parent→child, child→parent and exact-overlap cases must refuse with **zero recorder invocations**.
4. A disjoint case must reach exactly the expected recorder invocation(s).
5. Negative control against current reviewed implementation `f1c4b960...`: at least one same-peer prefix-overlap case must reach the recorder, proving the test distinguishes the defect.
6. Run the dependency-driven suites selected by the changed files and `./test/impact.sh --verify` with its real exit status.

No broad ZFS/SSH campaign is needed to prove the code correction. After the local negative control closes the ordering defect, one bounded live-host proof is still required because this boundary controls whether a real receive is allowed: on a controlled relationship, the overlap attempt must refuse before any new dataset/snapshot/receive-side state appears. Read back CONFIG/crontab as already required by REV-083, but additionally prove the candidate destination subtree was not created or changed by the refused attempt.

## Impact on REV-082 / REV-083 live plan

Do **not** treat the current `f1c4b960...` discussion as proof that REV-083's backup-mode overlap is structurally unreachable merely because client names differ. The current code namespaces backup targets by `peer_label(PEER_HOST)`, not by `CLIENT_NAME`.

Before running the already-authorized live campaign, fix/prove this ordering defect. Afterward the same-peer/different-client-name topology may provide a bounded real overlap refusal case on the existing host pair without introducing an outside-cluster sync peer, provided the setup itself does not overwrite shared pairing state in a way that invalidates the test. That pairing-state question should be checked before live execution; do not infer safety from client-name separation.

REV-082's positive live create/seed/activate proof remains independently useful, but it should not be used to close REV-083/085 until the overlap attempt is guaranteed to refuse before the real transfer boundary.
