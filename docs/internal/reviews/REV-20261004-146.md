# REV-20261004-146 — verify-endpoint mistakes retained history for an unavailable source

Review date: 2026-10-04  
Reviewer: ChatGPT  
Fresh canonical main checked: `fae77a339ce5f1b31c94b528968833409765d2e5`

## Verdict

**CHANGES REQUIRED — P2 blocking.**

## F1 — P2 BLOCKING — longer target retention prevents relationship activation

- Severity: P2
- Blocking: yes
- Affected path: `zfs-backup.sh`, `probe_snapget_endpoint()`

`probe_snapget_endpoint()` treats every nonzero `snapget -n` result as an
endpoint failure before it reads the emitted `PLAN=` verdicts. That is too
broad for exit status 1: `snapget` also uses it when the target has snapshots
which the source no longer has. A collector that intentionally retains history
longer than its source therefore cannot pass `verify-endpoint`, even when every
dataset has a valid incremental plan and every target-only snapshot is older
than the common base. The normal pull would preserve that history.

This blocks re-creating the `pve9-synchro` relationship required after the
Profiles/R5-2 change in PR #448. It is fail-closed, so it does not risk data
loss, but it incorrectly reports a healthy reachable endpoint as unavailable
and prevents activation.

### Minimal reproduction

At canonical main `fae77a339ce5f1b31c94b528968833409765d2e5`, make the
endpoint probe receive this successful incremental plan and conflict list from
`snapget -n`, with exit status 1:

```text
PLAN=INCREMENTAL base=b2 src=s/x tgt=t/x
t/x@old1
t/x@old2
```

On the target, `createtxg` values are:

```text
t/x@old1  10
t/x@old2  20
t/x@b2    30
```

Observed: the current probe increments `failed`, records
`FAILED (rc=1): s/x`, skips the plan parser, and rejects the endpoint.

The focused discriminator supplied in PR #451 was independently run against
both trees. Candidate `5f7a3bb128cc28523521c28b9e9951fe4e9bf1e8` passed
`6/6`. The same tests against canonical-main production code passed `4/6`:
the history case was not accepted and the endpoint probe did not consult any
history discriminator. Exact-head CI for that candidate is green ([run
37237321860](https://github.com/AdalbertKing/zfs-snapshot-all/actions/runs/37237321860)).

### Safety boundary

Exit status 1 must not be accepted merely because a `PLAN=INCREMENTAL` line is
present. A target-only snapshot newer than or equal to the common base is
divergence, and missing/malformed plan data or an unreadable transaction group
must remain a hard failure. Other nonzero exit statuses must retain their
current fail-closed behavior.

## Acceptance criteria

1. For `snapget -n` exit status 1, accept the probe only when every non-plan
   output line is a target snapshot named by a plan's target dataset, that plan
   has a non-null common base, and every listed snapshot has `createtxg`
   strictly lower than the target's copy of the common base.
2. Keep the probe failing when any listed snapshot is newer than or equal to
   the base, the relevant plan/base is absent or malformed, an output line is
   not a recognised snapshot, or either `createtxg` cannot be read.
3. Keep all nonzero statuses other than 1 fail-closed and preserve the existing
   handling of clean status 0 plans.
4. Add an executing focused regression covering: history-only acceptance;
   newer divergence; null base; foreign output; missing plan; and the rule that
   only exit status 1 may enter the history check.
5. Report the number of target-only historical snapshots in the successful
   diagnostic so the operator can distinguish this exception from a clean
   no-conflict probe.
