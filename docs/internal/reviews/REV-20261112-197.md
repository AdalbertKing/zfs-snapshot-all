## F1 — best-effort bookmark refresh is insufficient authority to prune shared source history

- Severity: **P1**. Blocking: **yes for safe incremental continuity of active keep replicas**.
- Contract: W5's `--source-keep=N` removes source snapshots only after a successful copy while the per-target bookmark preserves the next increment. Multiple removable targets may share the source/family; the new function's own comment explicitly relies on each target's bookmark. A completed copy must not become impossible to update merely because a later ordinary copy to another medium prunes its only surviving base.
- Entry path: generated active keep replicas add `--source-keep=1` (`gen-cron.sh:4724–4734`). Direct CLI and flat-recursive pulls reach `prune_source_family`; atomic `-r` intentionally skips pruning. The local and remote branches have the same bookmark/prune ordering. No hidden profile/template read is introduced by this delta.
- Mechanism: `snapget.sh:2529–2530` releases the sent snapshot's hold and clears the in-flight record. At `2554` it calls `record_send_bookmark` without proving that the target-specific replacement exists with the sent identity, then `2556–2561` enables source pruning. `lib-zfs-snap.sh:3397–3418` deliberately treats bookmark refresh as best-effort: it destroys the old bookmark first, tries to create the new one, and only logs a nonfatal warning on failure. New `prune_source_family` deletes older exact-family source snapshots up to its sent head without preserving another target's now-unbookmarked base.

### Reproduction and actual impact

**EXECUTED — deterministic Reviewer stub proof using the actual W5 functions**, not a full suite or real ZFS run. Extract `prune_source_family` from the exact PR head and `record_send_bookmark` from its unchanged library. Source has `rep_2026-11-12_01-00-00` (A) and `rep_2026-11-12_02-00-00` (B); each medium has its own target tag and the same source family. External ZFS calls are stubbed and state is kept in a temporary directory; no host, pool or package is touched.

1. Medium A has successfully received snapshot A. Simulate failure when creating A's refreshed bookmark after its previous bookmark was removed. Actual function logs `Warning: failed to refresh bookmark tank#tgt-A (non-fatal)`.
2. Medium B receives B and creates its own bookmark normally. Run the actual pruning function with `SOURCE_KEEP=1`, sent B. It destroys source A and reports one older snapshot removed.
3. Result: **A incremental anchor=none** — A's latest target snapshot has neither a common surviving source snapshot nor its target-specific source bookmark. Positive control: with successful A bookmark refresh, the identical B pruning leaves **A incremental anchor=bookmark**. Both observations were executed by Terra and repeated by lead Sol.

The next actual engine path refuses an existing target without common GUID or matching bookmark (`snapget.sh:2170–2174`): a full resend needs explicit `-f`, which destroys/recreates the target. This refusal follows from inspected engine control flow; the fixture does not execute a real next transfer. Existing A data and recovery points are not claimed destroyed. The defect is loss of normal incremental continuity and a forced repair/reseed decision after apparently successful copies. A non-root account can have snapshot/destroy capability without working bookmark capability; treating the old best-effort warning as sufficient is therefore consequential.

There is also a concrete concurrency window: after A's hold is released but before its bookmark is created, B may prune A. A's later bookmark creation then fails because its source snapshot is gone. This interleaving is established by code order; it was not scheduled against real concurrent processes in the fixture. Holds do protect snapshots still held, so the finding concerns this released-before-proof window, not a claim that destroy ignores ZFS holds.
