## F1 — `-I` sends the intermediate snapshots that `-E` filtered out

- Severity: **P1**.
- Blocking: **yes for release of the PR #1111 first-copy history claim**.
- Affected: `snapget.sh` `process_dataset` first-copy mirror path and ordinary
  incremental mirror path; `test/scenarios/run.sh` S8.

### Contract and evidence

The public `-E` option promises to omit snapshot families by prefix. In
`snapget.sh`, `process_dataset` filters `src_snaps` for `-E` at lines 1619–1631,
then optionally filters by `-m` at 1643–1651. PR #1111 chooses the oldest
remaining snapshot for the first full mirror send, then builds
`zfs send ... -I oldest newest` at 2104–2115. The ordinary common-base path
also selects `-I` by default at 2049–2064. OpenZFS specifies that `zfs send
-I` sends **all** intermediary snapshots between the two endpoints; the
filtered array has no effect on that stream. This is an inference from the
exact command and the [OpenZFS `zfs-send(8)` definition](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html),
not a claim of a live ZFS run.

S8 constructs precisely this case: `automated_daily_1`,
`automated_daily_2`, `__replicate_100-0_1__`, `automated_daily_3`,
`__replicate_100-0_2__`, then invokes `snapget -e -M -E __replicate_`.
Its inventory assertion removes `__replicate_` from the *observed target*
with `grep -v` before comparing, so it passes even if the excluded snapshot
was copied. The source contains an excluded snapshot between the first and
last eligible endpoints. The later `__replicate_100-0_2__` is outside the
interval and is not proof either way.

### Failure mode and required outcome

The first copy promises to carry eligible history without copying Proxmox's
reserved `__replicate_` snapshots. The new `-I` stream includes the reserved
snapshot inside the interval, contrary to the `-E` contract. The same
endpoint-only filtering can recur after a common snapshot on later runs.
Copy only eligible snapshots while preserving the intended data and history
semantics, or explicitly obtain an Owner decision to change the public `-E`
contract before publication. Do not treat a filtered assertion as evidence of
an unfiltered target inventory.

## Reviewer verdict on d37d50445cec3fa83b83b5b301b96c9abd9cf13e — CHANGES-REQUIRED

The unfiltered inventory tests on the nonrecursive S8 and S9 paths now pass
on pve9, and the old engines fail four new assertions. The new stepwise path
still has an untested public `-r` case in **both** engines. Under `-r`,
`get_sorted_snapshots` removes `-d 1`, so `src_all` contains snapshot names
from the root and every child. It strips the dataset path, leaving only the
name. The stepwise block deduplicates by name and uses each remaining name
as an endpoint of `zfs send -R -i ${src_dataset}@previous
${src_dataset}@next`. A child-only snapshot can therefore be selected as
`next` even though `${src_dataset}@next` does not exist.

For a concrete input, let the root have `@a`, `@skip`, `@c`, and a child
have `@a`, `@b`, `@skip`, `@c`, in that creation order, with `-e -r -E skip`.
The exact selection loop on this main, given `src_all=(a a b skip skip c c)`,
produces `hidden=1`, `steps=(b c)`, then tries
`zfs send -R -i root@a root@b`. The root has no `@b`. The old single
`-I root@a root@c` at least used endpoints that exist; the new path can
fail a copy that previously ran. This is a code-path inference, not a claim
of a live ZFS failure. [OpenZFS `zfs-send(8)`](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html)
requires the target snapshot to exist on the named dataset. S8 and S9 use
only nonrecursive datasets, so their 45/0 lab result cannot cover this case.

Preserve the exclusion contract for `-r` without constructing an endpoint
from a child's snapshot name. Add a disposable-ZFS regression with the root
and child snapshots above, check the full target inventory, and include a
negative control against `b382467d` or the first submitted fix as appropriate.
Also cover `-R` flat recursion if its traversal reaches the same case. Do not
touch production hosts. Exact-head CI for PR #1117 passed all 54 checks, but
the scenario suite runs on pve9 outside CI. The impact graph requires remote
and ZFS suites and reports nonroot-account and force-full obligations; those
are not discharged by the nonrecursive S8/S9 evidence. Release repository
`main` has meanwhile advanced to `e5fff9f5a9613ef069590cbc6c51fc45e6a1c06a`
with `RELEASE-OF` pointing to `c15e6f8b517d5031fa6ea1a648c2a867e3398944`.
That release contains this unapproved implementation. The release workflow
needs a gate on reviewer-owned approval; a successful release build is not
