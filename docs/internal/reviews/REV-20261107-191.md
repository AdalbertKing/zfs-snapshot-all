## F1 — `-I` sends the intermediate snapshots that `-E` filtered out

- Severity: **P1**.
- Blocking: **yes for release of the PR #1111 first-copy history claim**.
- Affected: `snapget.sh` `process_dataset` first-copy mirror path and ordinary
  incremental mirror path; `test/scenarios/run.sh` S8.

### Contract and evidence

The public `-E` option promises to omit snapshot families by prefix. In
`snapget.sh`, `process_dataset` filters `src_snaps` for `-E` at lines 1619–1631,
then optionally filters by `-m` at 1643–1651. PR #1111 chooses the oldest
remaining snapshot for the first full mirror send, then builds
`zfs send ... -I oldest newest` at 2104–2115. The ordinary common-base path
also selects `-I` by default at 2049–2064. OpenZFS specifies that `zfs send
-I` sends **all** intermediary snapshots between the two endpoints; the
filtered array has no effect on that stream. This is an inference from the
exact command and the [OpenZFS `zfs-send(8)` definition](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html),
not a claim of a live ZFS run.

S8 constructs precisely this case: `automated_daily_1`,
`automated_daily_2`, `__replicate_100-0_1__`, `automated_daily_3`,
`__replicate_100-0_2__`, then invokes `snapget -e -M -E __replicate_`.
Its inventory assertion removes `__replicate_` from the *observed target*
with `grep -v` before comparing, so it passes even if the excluded snapshot
was copied. The source contains an excluded snapshot between the first and
last eligible endpoints. The later `__replicate_100-0_2__` is outside the
interval and is not proof either way.

### Failure mode and required outcome

The first copy promises to carry eligible history without copying Proxmox's
reserved `__replicate_` snapshots. The new `-I` stream includes the reserved
snapshot inside the interval, contrary to the `-E` contract. The same
endpoint-only filtering can recur after a common snapshot on later runs.
Copy only eligible snapshots while preserving the intended data and history
semantics, or explicitly obtain an Owner decision to change the public `-E`
contract before publication. Do not treat a filtered assertion as evidence of
an unfiltered target inventory.

- Severity: **P1**. Blocking: **yes, for release of recursive `-e -r -E` behavior**.
- Evidence: `snapget.sh` constructs the first full send while `common_snapshot=null` (the `Performing standard full pull` branch); `snapsend.sh` does the analogous `Performing standard full send`. In both engines the new `exclusion_step_plan` is invoked **only** if `common_snapshot != null` and the send command ends in `-I root@common root@latest`. Therefore the first full replication never examines excluded child snapshots.
- OpenZFS specifies that `zfs send -R root@latest` replicates the descendant snapshots up to the named snapshot: https://openzfs.github.io/openzfs-docs/man/master/8/zfs-send.8.html. A child-only excluded snapshot taken **before** `root@latest` is included despite `-E`. This is a code-path plus documented-stream-semantics finding, **not** a claim that I ran a ZFS transfer.
- Minimal scenario on a disposable pool: `zfs snapshot -r root@a`; `zfs snapshot root/ch@skip_x`; `zfs snapshot -r root@b`; then the **first** `snapget -e -r -E skip` (or `snapsend -e -r -E skip`) into an empty target. Expected: target root `@a/@b` as applicable, target child **no `@skip_x`**. Actual command path: unfiltered full `-R root@b`, which preserves `ch@skip_x`.
- The new S10 and S11 create the first copy **before** adding any excluded snapshot. They prove subsequent `-I/-i` behavior, not first-copy exclusion. Exact-head CI of #1129 passed 54/54 checks, but cannot substitute for this missing privileged scenario. Its pve9 report was S10/S11 `PASS=55 FAIL=0`, negative control `PASS=52 FAIL=3` on the already-covered incremental path.

If the existing `-R` replication stream cannot honor snapshot-by-prefix exclusion without sacrificing another documented backup guarantee, **fail closed before transfer** with a clear diagnostic and request an Owner contract decision. Never silently publish a stream that violates `-E`. Keep ordinary `-R` flat and the already-correct incremental paths working.

Then run only the impacted suite on pve9, `impact.sh --verify`, and exact-head CI; provide the SHA and test results. No production system is authorized.

## Reviewer verdict on 8d767ffde0d32bd4ad1d0e674cde183d39bf88b1 — CHANGES-REQUIRED (round 4)

**F1 — The first `-e -H -E` copy stops replicating child datasets after the safe base**

- Severity: **P1**. Blocking: **yes for release of the submitted recursive/full-history exclusion fix**.
- **Exact code path:** `snapget.sh:~2126–2152` and `snapsend.sh:~1950–1975` call `exclusion_full_base` when `FULL_HISTORY_SEND=1`. If an excluded snapshot precedes the latest root snapshot, they correctly start with a full `zfs send -R root@safe_base`. But they then rebuild the continuation as `zfs send $recursive_send_flag ... -I root@safe_base root@latest`. `recursive_send_flag` is set to `-R` **only when `RECURSIVE=1`** (`snapget.sh:1846–1847`, `snapsend.sh:1785–1786`). The public `-H` flag sets `FULL_HISTORY_SEND=1`, not `RECURSIVE=1` (`snapget.sh:2472`, `snapsend.sh:2278`). Hence plain `-H` sends the first full subtree correctly but the remainder is a **root-only** `-I` stream. An `-I` without `-R` does not carry updates/snapshots for descendants, contrary to the original full `-R root@latest` stream.
- **Minimal, bounded reproducer:** create root with child; `zfs snapshot -r root@a`; `zfs snapshot root@skip_root` (excluded only at root); change child data; `zfs snapshot -r root@b`; first copy to an empty target using `snapget -e -H -E skip root dest` and separately `snapsend -e -H -E skip root dest`. Expected: root and child reach `@b` with matching GUID/content, no `@skip_root`. Actual path on this implementation: full `-R root@a` followed by nonrecursive `-I root@a root@b`; the child can remain at `@a`. **Code-path inference only:** no live ZFS command was executed by this Reviewer.
- **Coverage hole:** S12 tests `-H` only on a single dataset (`S12H`), not on a root with descendants. S12 does cover atomic `-r` with child snapshots, which correctly retains `-R` on the follow-up. The submitted pve9 result `PASS=60 FAIL=0` and discriminating r4 negative control `PASS=55 FAIL=5` are credible for the tested paths, but not evidence for this `-H` regression. GitHub exact-head CI was **54/54 green**.

**Required outcome:** preserve the original `-H` full-history subtree semantics when splitting a full `-R` stream to honor `-E`. Every follow-up step must carry the descendant changes/snapshots that the original stream promised, while no excluded snapshot reaches the target. If not possible, fail closed rather than declare a partial child backup successful. Do not alter the already covered `-r`, `-R` flat, or ordinary incremental contracts.

**Focused acceptance:** extend S12 with a multi-dataset first-copy `-e -H -E` case for **pull and push**, inspect complete child/root inventories and latest GUID/content; run the **new case against r4 code without its fix** as the negative control, with the intended failure; then execute only `scenarios` on pve9, `impact.sh --verify`, and exact-head CI. No production host or destructive production operation.
