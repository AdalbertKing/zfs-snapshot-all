# REV-20260809-083 — create-only preset path does not refuse overlapping existing coverage

Review time: 2026-08-09 13:01 CEST
Reviewed implementation: `15fd61761e5aab815596717476a8a4690951e953`
Response path: `docs/internal/reviews/responses/REV-20260809-083.md`

## Verdict

**CHANGES REQUIRED before create-only preset/additive enrollment is treated as safe.**

This is separate from REV-082. REV-082 concerns faithful composition of a selected profile and its evidence. This finding concerns whether a new preset-created source package is allowed to coexist with already-installed coverage at all.

## F1 — P1 — overlap is not rejected unless it collides on an exact generated section header

The owner contract in `docs/discussions/PROFILE-PREINSTALL-NOT-FULL-CONFIG-2026-08-09.md` is explicit: a preset may append a new independent task to existing CONFIG, but **must refuse if the requested source/task already exists or overlaps existing coverage**.

The current code does reject exact section collisions using relationship ownership markers. That is necessary but insufficient. `emit_client_sections()` computes the concrete section paths for the new relationship and `remove_managed_sections()` protects those exact headers. No preflight compares the requested source/coverage root with coverage already owned by another relationship when the paths differ.

Concrete unsafe shape:

```text
existing relationship A:
  source/coverage root = rpool/data

new relationship B:
  requested source     = rpool/data/vm-101
```

Those are different section headers, so the existing marker collision does not necessarily fire. If A covers descendants, A and B can then schedule send/prune work over the same snapshots under different policy. The failure mode is silent duplicate ownership / double-prune, not merely cosmetic duplication.

Claude independently identified the same gap in `docs/discussions/PRESET-CREATE-ONLY-CLAUDE-ANSWERS-2026-08-09.md`; that statement is not accepted as proof by itself, but inspection of the current emit/collision path confirms there is no broader coverage-overlap guard before new sections are appended.

### Required correction

Add one fail-closed overlap preflight at the high-level create/additive-enrollment boundary, before candidate mutation/install.

For V1, prefer the smaller conservative rule over duplicating the recursion model: reject dataset path-prefix overlap in **either direction** against existing relationship-owned coverage and name the conflicting relationship/path in the diagnostic. A conservative refusal is acceptable because the expert escape hatch is native CONFIG; silently permitting two high-level relationships to own overlapping coverage is not.

Do **not** build a second recursion/coverage interpreter in `zfs-backup.sh`. If exact semantic overlap is later desired, reuse/extract the existing canonical coverage model rather than copying it.

The guard must preserve these properties:

- disjoint existing CONFIG remains appendable;
- exact-path collision remains refused;
- parent→child and child→parent overlap are both refused;
- refusal occurs before CONFIG or crontab changes;
- unrelated hand-written/native CONFIG remains untouched.

### Minimal proof

Use targeted tests only:

1. existing managed `rpool/data`, request `rpool/data/vm-101` → refuse;
2. existing managed `rpool/data/vm-101`, request `rpool/data` → refuse;
3. disjoint `rpool/data` + `rpool/lxc` → allowed candidate;
4. exact-path collision still refuses;
5. negative control against the pre-fix implementation demonstrates at least one prefix-overlap case was accepted;
6. dependency-driven cascade selected by the changed files, plus `./test/impact.sh --verify` with its real exit status.

Because this correction is a high-level CONFIG/crontab mutation guard, closure also requires one bounded live-host refusal proof on the correct target identity: begin from a controlled installed relationship, attempt an overlapping addition, then read back canonical CONFIG and managed crontab and prove both are unchanged. No ZFS transfer, SSH/grant, or fleet-wide campaign is required unless the implementation crosses those boundaries.

## Scope discipline

Do not fold REV-082 evidence repair into this finding. REV-082 remains independently open until its real `gen-cron`, resolved impact-plan, and bounded apply/read-back/rollback proof obligations are satisfied.
