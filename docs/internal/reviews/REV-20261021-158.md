# REV-20261021-158 — U35 root shell execution via crontab-derived bookmark tag and forged ownership

Reviewer: ChatGPT. Date: 2026-10-21.
Canonical inspected `main`: `90602e5e0561ea81a7524ec17b50f6ee070994c6`.
Affected: `hostscripts/capacity-guard.sh`, blob `2f6c301c950eb91efe30530913ef8407c0c8a325`, especially `read_managed()`, `candidates()` AWK functions `tok`, `tag`, `landing`, `source_state`; and `deploy.sh` root scheduling around lines 5606–5619.

**Urgent security review.** This is a new trust-boundary finding after the completed REV-157. It does not undo the verified functional fixes in REV-155–157. The severity is conditional on the caller's privileges and whether a modified crontab is consumed.

## F1 — P0: crontab-supplied destination is interpolated into an AWK shell command

- Severity: **P0** (credible path to elevated code execution on hosts that run the guard as root).
- Blocking: **yes**, guard **must stay OFF in production**, and the read-only `--plan` path must not be treated as safe for untrusted crontabs until this is fixed.
- Trust boundary: `read_managed()` scans files from `/var/spool/cron/crontabs/*`. A comment marker `# BEGIN zfs-backup-managed` is not an authenticated ownership proof; an account with its own editable crontab may inject plausible `snapsend.sh`/retention lines.
- The tokenizer accepts single quotes and shell metacharacters inside a double-quoted crontab argument (it rejects backslashes there, not apostrophes). That argument is used as destination/identifier data and reaches `tag(landing(ds, SDst[k]), SId[k])`.
- `tag()` constructs a shell command by concatenating destination and identifier **inside single quotes**, then executes the resulting string through AWK `c | getline h`. This is an execution sink, not a hashing API taking data as literal bytes. An apostrophe in a parsed input can terminate the intended shell quote and change what the shell executes.
- `deploy.sh` installs `/root/scripts/capacity-guard.sh` in **root's** crontab every 15 minutes. Thus a user-editable crontab used as an input to the root guard crosses a privilege boundary. The same AWK path is reachable in `--plan` even if `guard=off` (the plan intentionally still enumerates candidates).

### Independent evidence and limits

The reviewer reproduced this with the guard's actual `tok()`, `landing()` and `tag()` algorithms, using an **isolated AWK test process** and a harmless temporary-file marker. Normal quoted destination: parsed successfully, no marker; a crafted quoted destination containing a quote boundary and shell separators: parsed successfully and created the marker when `tag()` invoked AWK's shell pipeline. No real ZFS, crontab, root privileges or host was touched.

The full production script was **not** dynamically run with an injected crontab in this reviewer environment; the implementer must reproduce the complete dataflow with fake binaries as specified below. This is a credible code-execution path, not a claim of an observed compromise.

### Required outcome / acceptance criteria

1. Remove execution of shell-command **strings** containing crontab-derived data. Do not use `awk c | getline`, `system()`, `eval`, `sh -c` or unsafe shell interpolation to compute per-target MD5. Use a bounded, argument/byte-safe mechanism and prove its digest matches `lib-zfs-snap.sh:bookmark_target_tag` for normal destinations and `-j` identifiers.
2. A malicious or malformed destination/identifier supplied by any parsed crontab must **never execute an additional command** under guard or `--plan` — even when guard is otherwise disabled. Unknown/unsafe data => skip destruction/fail closed; no reinterpretation as a shell program.
3. Exercise the **actual installed script** with fake `zpool`, fake `zfs`, isolated temp paths, synthetic root/untrusted-user crontabs and a benign marker as the negative control. Prove prior blob behavior differs and fixed code never creates that marker. No real root escalation, ZFS destruction or production hosts.
4. Preserve byte-exact bookmark matching for valid remote/local targets, multiple distinct `-j` identifiers, and the missing-bookmark fail-closed behavior. Cover ordinary targets and inputs containing shell-sensitive characters.

## F2 — P1: any cron account can forge the guard's ownership authority

- Severity: **P1** (destructive cross-account trust-boundary bypass).
- Blocking: **yes** for production guard enablement.
- `read_managed()` loops over `"$CRONDIR"/*`, trusts only textual BEGIN/END markers, then treats a `delsnaps.sh` row containing a local scope and any nonempty explicit pattern as `OWN`. This is treated as permission to destroy matching snapshots; it is **not verified** against root-controlled deployment/relationship registration or the real owner of that crontab.
- A user permitted to install their **own** crontab can add marker-wrapped fictitious retention rows targeting someone else's dataset/family. Once the capacity threshold is exceeded, guard executes `zfs destroy` under its host-root schedule against anything admitted by that forged pattern, subject only to generic holds/head/keep/bookmark protections. The current candidate algorithm has **no independent unconditional exclusion** for the Proxmox-reserved snapshot-name families; earlier assertions that `__replicate_`/migrations are never deleted rely on trusted ownership patterns.

### Required outcome / acceptance criteria

1. Never infer destructive authority solely from a managed-marker-looking block in **arbitrary** local-user crontabs. Establish and validate the allowed actor/relationship/scope set from trusted deployment metadata; allow legitimate delegated-account flows without giving every cron user that authority.
2. Verify that an untrusted user's marker + invented `delsnaps.sh` pattern cannot authorize **any** `zfs destroy` in unrelated datasets or in protected Proxmox families. Include a negative control demonstrating the old code's candidate authorization and a legitimate control confirming actual registered relationships still work.
3. Explicitly protect Proxmox-reserved `__replicate_`, `__migration__`, `vzdump` families at the destructive decision boundary, regardless of a misleading matching pattern. Do not reduce protected snapshots to `guard_min_keep` or assume that all instances carry ZFS holds.
4. Ambiguous/missing registry, unsafe crontab ownership, malformed metadata or privilege discrepancy => fail closed, report/alert, no deletion.
