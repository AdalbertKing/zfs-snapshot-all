## Verdict

**CHANGES REQUIRED before local-relation implementation starts.**

The proposed placement in `zfs-backup.sh`, reuse of existing mechanisms, rejection of a fake localhost peer, and the shorter local lifecycle are directionally correct. The lifecycle question is settled in favour of a local-specific short lifecycle rather than reusing peer-only states as N/A.

One ordering defect remains in the written contract and should be fixed before code makes it persistent.

## F1 — P1 — cron is installed before the first seed succeeds

- Severity: P1
- Blocking: yes
- Affected: `docs/design/local-relation-contract.md`, §3 `add-local` transaction

### Evidence

The contract currently orders the second high-level invocation as:

```text
render config
preview
install cron
seed in foreground
```

But the proposed persistent lifecycle is:

```text
configured -> seeded -> active
```

and the project already uses activation as the boundary after which scheduled jobs may run.

### Failure mode

If cron is installed first and the foreground seed then fails, is interrupted, or the process crashes, scheduled jobs are already eligible to run even though the relationship has never reached the `seeded` boundary. That creates exactly the state the lifecycle is supposed to make impossible: operationally active scheduling with incomplete/retryable bootstrap state.

It also creates a race if the schedule fires during a long initial full send. The engine's locking may serialize individual work, but relying on that would not repair the control-plane invariant: activation must follow successful bootstrap, not precede it.

### Required outcome

Make the local transaction fail closed around the same boundary as the lifecycle:

```text
1. discover/select/validate
2. compose + validate effective CONFIG v4
3. preview rendered cron
4. persist relation as configured
5. run first seed in foreground
6. only after successful seed, persist seeded
7. install managed cron transactionally
8. only after successful cron read-back, persist active
```

If seed fails, relation remains `configured` and no managed local job cron is installed. If cron installation/read-back fails after a successful seed, relation remains `seeded` and is retryable; it must not claim `active`.

A separate transient `seeding` state is not required if `configured` is durable until the foreground command returns success; do not add state merely to count progress.

### Acceptance criteria

- [ ] no local managed job cron exists before the first seed succeeds;
- [ ] failed/interrupted seed leaves the relation visibly non-active and retryable;
- [ ] successful seed followed by failed cron install leaves `seeded`, not `active`;
- [ ] `active` is written only after transactional cron install + read-back succeeds;
- [ ] re-running from `configured` retries seed without duplicating state/jobs;
- [ ] re-running from `seeded` retries activation without repeating a proven seed unless the operator explicitly requests it.

### Required verification

Automated, smallest useful set:

- state-transition tests for seed failure and cron-install failure;
- a regression proving cron writer is not called on failed seed;
- a regression proving `active` is not persisted before cron read-back;
- idempotent retry from `configured` and `seeded`;
- dependency-selected cascade + `impact.sh --verify`.

Live proof when implementation exists:

- one scratch local cross-pool relation on a real ZFS host;
- force/induce one seed failure and prove no managed job cron was installed;
- successful seed + activation, then read back actual crontab and relationship state;
- destroy scratch state afterwards.

No transfer-engine modification or broad engine campaign is required.

## Reviewer decisions on the open design questions

1. **Lifecycle:** approve a local-specific short lifecycle: `configured -> seeded -> active`. Do not carry `pending_enroll`, `endpoint_verified`, keys or peer states as N/A.
2. **Same-pool target:** do not reject it, consistent with the Owner's ruling that this layer does not judge protection sufficiency. A special warning is not required; preview should simply show source pool and target pool/path factually. Avoid encoding a policy judgement through warning severity.
3. **Public UX:** keep the two-invocation `zfs-backup.sh` boundary. No third public wrapper.

## Cost discipline

This is a contract-order correction, not a request for code now. Fixing the document before implementation is sufficient for this review attempt. Once code arrives, prove only the state/side-effect boundary above plus one real-host scratch run; do not expand into a four-host campaign unless the dependency graph later justifies it.
