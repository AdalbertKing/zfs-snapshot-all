# REV-20260808-069 — Stage 2.3 long-option pre-pass misclassifies an argument after a short-option cluster

**Review time:** 2026-08-08 03:00 CEST

**Reviewed head:** `46b96b47c0f1a5b2ff0785992aae697d84889b22` (2026-08-08 02:33:35 CEST).

**Verdict:** **CHANGES REQUIRED**

Stage 2.3 is directionally correct: long recursion spellings are kept out of generated cron, recursion declaration conflicts are explicit, and the parser tests correctly distinguish a recognised spelling from an unrelated later failure. The remaining defect is narrower but real: the new `snapsend.sh` / `snapget.sh` pre-pass claims getopts-equivalence but does not preserve one legal getopts case.

## F1 — an option argument after a clustered short option is reinterpreted as a long option

- Severity: **P2**
- Blocking: **yes, for Stage 2.3 acceptance**
- Affected: `snapsend.sh::translate_long_options`, `snapget.sh::translate_long_options`, `test/recursion/run.sh`

### Evidence

The pre-pass correctly derives which short letters take an argument from `OPTSTRING`, but it skips the following argv only when the token length is exactly two:

```bash
last="${a: -1}"
if [ "${#a}" -eq 2 ] && opt_takes_arg "$last" && [ $# -gt 0 ]; then
    out+=("$1"); shift
fi
```

That handles:

```text
-m --recursive=flat
```

because `-m` is length 2 and the next argv is correctly preserved as MESSAGE data.

It does **not** handle the legal clustered equivalent:

```text
-em --recursive=flat
```

`getopts` parses that as `-e` followed by `-m`, with the **next argv** as the argument of `-m`. The pre-pass instead sees `-em`, does not consume the next argv because the token length is 3, and then interprets `--recursive=flat` as a recursion declaration.

The same class applies to any cluster whose final option consumes the following argv.

This violates the stated Stage-2.3 invariant that the pre-pass is getopts-equivalent and that option arguments which merely look like long options remain data.

### Why the current test does not catch it

`test/recursion/run.sh` pins only the unclustered case:

```text
-m --recursive=flat
```

There is no case where a no-argument short flag is clustered immediately before a short option that takes its value from the next argv.

The existing 54/54 therefore demonstrates the simple two-argv case, but not the actual getopts grammar the implementation claims to preserve.

### Required outcome

The long-option pre-pass must preserve exactly the same option-argument boundary as the subsequent `getopts` invocation for short-option clusters.

In particular, a token such as `-em` must be recognised as ending in `m`, where `m:` in `OPTSTRING` means that the next argv belongs to the short option and must not be inspected as a long option.

Do not fix this by adding another hand-maintained list of clustered forms. The existing design choice — derive argument-taking letters from `OPTSTRING` — is good; the scan of the short-option token must simply honour it for clustered options as well.

### Minimal acceptance evidence

No ZFS, SSH, root, delegated account or live-host campaign is required for this finding. It is pure argv normalisation.

Add a targetted regression for **both transfer engines**:

```text
-em --recursive=flat
```

where `--recursive=flat` must remain the argument of `-m` and must **not** count as a recursion declaration.

Also add one discriminating mixed case, for example:

```text
-em --recursive=flat -r
```

which must be accepted as MESSAGE=`--recursive=flat` plus exactly one real recursion declaration (`-r`).

Run the new cases as a negative control against `46b96b47...`; at least the clustered-argument property must fail there while the existing unclustered `-m --recursive=flat` control remains green.

Then run only the graph-selected local cascade and `./test/impact.sh --verify`. Do not spend a delegated/live-host run on this parser defect; the already-planned single delegated Stage-2.3 proof should be performed only after the parser implementation is final.

## Other Stage 2.3 assessment

No additional finding is opened on the `delsnaps.sh` / `check-snap-age.sh` bare `--recursive` alias in this pass. Their runtime loop keeps the same positional-stop semantics as the existing short `-R` parser, and the new alias does not expand that boundary.

The Stage-2 contract still correctly requires one delegated-account invocation on the **installed final copy** after local parser acceptance; that proof remains owed and should not be substituted with local PASS counts.
