## F1 — P1: transport endpoint is compared with pairing identity

- Severity: **P1**
- Blocking: **yes** for mode-based relation import on a peer that is already
  represented on the collector
- Affected: `zfs-backup.sh`, `cmd_import_relation()`, verdict 3 (one scope per
  collector and peer)

### Evidence

The import contract distinguishes two values:

- `PEER_HOST` is the durable pairing/peer identity used by existing records;
- replayed `--host=HOST[:PORT]` is the current transport endpoint and, since
  U62, may contain a port or even a different active address.

REV-166 correctly parses the replay endpoint into `peer_ep_host` and
`peer_ep_port` for network operations. The earlier duplicate-peer guard still
compares every stored `PEER_HOST` with the raw replay argument:

```bash
[ "$(record_get "$f" PEER_HOST)" = "$peer_host" ] || continue
```

For an existing `PEER_HOST=10.0.0.11` and a valid exported replay argument
`--host=10.0.0.11:2222`, the strings cannot match although they identify the
same peer. The guard is therefore skipped.

The reviewer exercised the shipped `cmd_import_relation()` through the existing
isolated `exportrel` harness. Only a temporary reviewer assertion was added;
network and change boundaries remained stubbed. The current focused suite is
green without that assertion: **68 PASS / 0 FAIL**. With the exact same-peer
`HOST:PORT` assertion it becomes **68 PASS / 1 FAIL** and records:

```text
add-client|nowaport|--host=10.0.0.11:2222|--mode=sync|...
seed|nowaport|--yes
activate|nowaport|--yes
```

Expected behavior is a refusal naming the already active relationship `inna`,
with no `add-client`, `seed`, `activate`, record creation or remote action. The
existing no-port positive control does refuse the same pair before any action,
so the reproduction isolates endpoint/identity comparison rather than the
general verdict path.

### Failure mode and impact

An exported mode-based relationship can be imported under another name on a
collector that already has a relationship to that peer whenever the replayed
transport endpoint differs textually from stored `PEER_HOST` — at minimum by a
non-default port, and potentially by U62's alternate active address. Import
then proceeds through creation, seed and activation even though the code's own
contract says a peer has one scope per collector. Two relationships can
therefore contend for the same peer-side scope and overlapping datasets,
creating inconsistent grants, duplicate work or pruning-policy conflicts. The
reviewer demonstrated the bypass and three attempted lifecycle calls, not live
ZFS damage.

### Required outcome / acceptance criteria

- [ ] Decide verdict 3 using the exported durable peer identity (`PEER_HOST`),
  not the replay transport endpoint or its port.
- [ ] Refuse before any mutation when an active/non-removed mode-based record
  has the same peer identity, including replay through `HOST:PORT`.
- [ ] Preserve REV-166 behavior: use the parsed transport host and port for SSH
  probes and preserve the replayed `--host=HOST[:PORT]` for creation paths.
- [ ] Fail closed before mutation when a mode-based export does not provide a
  valid peer identity sufficient to perform the one-scope check.
- [ ] Do not treat a genuinely different exported `PEER_HOST` as a duplicate
  merely because its transport endpoint happens to be textually similar.

### Required verification

- automated: extend the actual `cmd_import_relation()` `exportrel` harness with
  a same-peer `HOST:PORT` case; require refusal and zero calls to
  `add-client`, `seed`, `activate` and `rux_entry`;
- automated: cover an U62-style export where declarations retain the pairing
  `PEER_HOST` but replay uses a different `ACTIVE_ENDPOINT=HOST:PORT`;
- automated: keep the present no-port same-peer positive control and add a
  different-peer negative control that still reaches the intended import path;
- automated: run `bash test/zfsbackup/run.sh --section exportrel`,
  `bash test/impact.sh --verify`, `bash test/reviewctl.sh --verify` and CI on
  the exact submitted SHA;
- manual: no live host or ZFS operation is required to decide this string-domain
  and pre-mutation ordering defect.

### Notes and uncertainty

The evidence proves bypass of the promised pre-change refusal and invocation of
the import lifecycle. It does not prove that every real second import completes:
later checks may still fail depending on scope, manifests and remote state. That
does not make the early safety guard effective. Address alias canonicalisation
(DNS/IP equivalence) is outside this finding; acceptance requires correct use of
the already exported durable identity.
