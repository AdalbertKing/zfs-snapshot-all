## F1 — P1 — `zfs rollback -r` can destroy unapproved bookmarks

### Evidence

The planner's accepted loss set is derived from source rows returned by `zfs list ... -t snapshot`; it therefore enumerates newer snapshots and live bytes, but no bookmarks. The executor then runs:

```sh
zfs rollback -r "$RESTORE_SRC_BASE_SNAP"
```

OpenZFS's rollback implementation applies its newer-object check to both snapshots and bookmarks; with recursive rollback enabled those newer bookmarks are eligible for destruction. See the upstream [`zfs_do_rollback` implementation](https://github.com/openzfs/zfs/blob/master/cmd/zfs/zfs_main.c), which invokes both `zfs_iter_snapshots_sorted_v2(..., rollback_check, ...)` and `zfs_iter_bookmarks_v2(..., rollback_check, ...)`.

Thus an operator can approve the displayed measured loss set and the primitive can delete an additional, undisclosed newer bookmark. That violates REV-119's exact-loss confirmation boundary.

### Required change

Make the approved destructive set equal the actual set:

- either discover, display, accept, and boundary-revalidate every newer bookmark that rollback will remove;
- or use a mechanism that provably preserves bookmarks or refuses the operation when such a bookmark exists.

Do not silently widen the accepted loss set at execution time.

### Acceptance evidence

1. A targeted model/stub case with a newer bookmark and no newer source snapshot proves the bookmark is represented before confirmation, or proves fail-closed preservation/refusal.
2. Declining confirmation leaves it intact.
3. A bookmark appearing after confirmation but before the destructive command is detected and refused, unless an equivalent fence proves it cannot occur.
4. A bounded throwaway-dataset live-ZFS transcript proves the chosen behavior on the supported OpenZFS host.
5. Failure/cleanup text remains exact about whether destruction began and what may have changed.

## F2 — P1 — final GUID verification relies on a non-total creation-time order

### Evidence

After execution the primitive selects a supposed source head with:

```sh
zfs list -H -p -t snapshot -o guid -s creation -d 1 "$src" | tail -1
```

The project already treats equal-second snapshot creation times as a real boundary condition. Sorting only by `creation` does not establish a unique order for equal-valued rows, so `tail -1` is not proof that the selected GUID is the actual final target. A correct restore can consequently be reported as partial/failed, or final-state acceptance can depend on incidental tie ordering.

### Required change

Verify the exact expected target snapshot identity and the complete required final state without inferring “head” from `creation | tail -1`. Keep the check GUID-anchored and fail closed on ambiguity.

### Acceptance evidence

1. A targeted same-second case with deliberately adverse snapshot names/order discriminates the target from its peer and reports the correct result.
2. Both incremental and rollback strategies exercise the corrected final check.
3. A mismatch remains a post-destruction partial-failure result and names the exact uncertainty.
4. A bounded live-ZFS proof covers the same-second boundary, or records a reproducible host limitation and a stronger identity-based substitute.
