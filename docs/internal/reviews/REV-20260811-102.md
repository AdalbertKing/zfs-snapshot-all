# REV-20260811-102 — default backup policy leaves source snapshots unbounded

## Acceptance property

Every high-level backup relationship that creates tool-owned source snapshots must have a bounded, ownership-safe source cleanup policy. SOURCE and TARGET retention are separate native CONFIG v4 policies, initialized from the same preset values at CREATE but independently editable thereafter. For remote PULL the collector owns the cron/config and executes source prune through the relationship's existing pinned SSH/delegated identity; no autonomous source cron is introduced.

Existing CONFIGs are runtime truth. They must not be silently regenerated from a profile. Any retrofit must be explicit, previewed, add only missing source-retention policy, and preserve unrelated installed policy/topology.

Incremental continuity may only be claimed while a usable ordinary common snapshot or proven usable bookmark remains. Source-prune failure/outage behaviour must be explicit and safe.

## Accepted progress

The following pieces are accepted and remain part of REV-102's eventual closure proof:

- local PUSH emits a bounded SOURCE prune and an independent TARGET prune;
- SOURCE and TARGET use distinct template authorities after CREATE;
- default non-recursive source prune no longer uses `-R`, so matching snapshots on out-of-coverage children survive;
- real local ZFS proof showed managed source snapshots aging out while a manual snapshot and child snapshot survived;
- remote PULL emits a collector-scheduled `[prune:<account@host:source>]` over the existing pinned SSH path;
- the existing delegated `destroy` capability is verified fail-closed rather than widened;
- real pve1 -> pve2 source-prune proof exercised the delegated identity, prefix selectivity and non-recursive scope;
- REV-107 corrected reactivation so installed source-retention policy is preserved while endpoint topology moves.

## Review of implementation `8cb28f3337a4697c89d61d6d170075caa75f8d0b`

This submission addresses the previous step-5 findings F3/F4/F5.

### F4 — narrow retrofit, no topology refresh — ACCEPTED

`audit-source-retention --apply` no longer calls `emit_client_sections(..., is_new=0)`. It uses a narrow `emit_missing_source_prune` path, derives the source scope from installed CONFIG, leaves existing dataset/target/source-policy sections alone, and refuses if current client endpoint state disagrees with the installed `src` instead of opportunistically repairing topology.

The discriminating regression with mismatched current endpoint versus installed `src` is the right negative control. This satisfies the migration boundary: retention retrofit is not reactivation.

### F5 — direct `--apply` orchestration test — ACCEPTED

The new fixture directly drives the `audit-source-retention --apply` command path with a real profile and real `gen-cron`, and proves both successful narrow addition and unchanged-on-grant-refusal. Stubbing the already-tested external grant/install boundary is acceptable here because the test is aimed at the new orchestration and the atomic install/rollback helper has independent coverage.

### F3 residual — any `delsnaps` for the scope is not proof that the managed source snapshots are bounded

The new helper is:

```bash
source_scope_is_bounded() {
    grep -F 'delsnaps' "$1" 2>/dev/null | grep -qF "\"$2\""
}
```

This is stronger than header existence, but still proves only that **some** `delsnaps.sh` command mentions the exact remote scope. It does not prove that command prunes the snapshot family created by this backup relationship.

Concrete false-green examples are valid CONFIG v4:

1. `[prune-bookmarks:<same remote scope>]` renders `delsnaps.sh -B ... "account@host:dataset" ...`. The helper sees `delsnaps` + the exact scope and reports the source bounded, although bookmark cleanup does not delete any `automated_hourly_*` snapshots.
2. A standalone `[prune:<same remote scope>]` may legitimately prune a different snapshot prefix. That command also satisfies the helper while this relationship's `automated_hourly_*` snapshots remain unbounded.

Therefore the audit can still print `nic do dodania` while the original REV-102 production-safety property is false.

#### Required correction

Reuse the rendered `gen-cron` result, but discriminate the **snapshot-prune semantics** that bound this relationship's managed source snapshots. At minimum the proof must exclude bookmark-only `-B` jobs and must establish that the prune pattern actually covers the generated managed snapshot prefix (`automated_hourly_` for the current high-level default), with finite retention. Do not add a second CONFIG parser if the rendered command already exposes the needed semantics.

Add negative controls for at least:

- same scope + `prune-bookmarks` only -> audit must still report source retention missing;
- same scope + snapshot prune of an unrelated prefix -> audit must still report source retention missing;
- same scope + actual bounded managed-prefix prune -> audit reports bounded.
