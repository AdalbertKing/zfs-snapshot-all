# REV-20260811-102 — default backup policy leaves source snapshots unbounded

## Acceptance property

Every high-level backup relationship that creates tool-owned source snapshots must have a bounded, ownership-safe source cleanup policy. SOURCE and TARGET retention are separate native CONFIG v4 policies, initialized from the same preset values at CREATE but independently editable thereafter. For remote PULL the collector owns the cron/config and executes source prune through the relationship's existing pinned SSH/delegated identity; no autonomous source cron is introduced.

Existing CONFIGs are runtime truth. Retrofit must be explicit, previewed, add only missing source-retention policy, and preserve unrelated installed policy/topology.

Incremental continuity may only be claimed while a usable ordinary common snapshot or proven usable bookmark remains. Behaviour after that base is lost must be explicit and safe.

## Sole remaining blocker — continuity after loss of the ordinary common base

The implementer response itself still explicitly leaves this evidence open. No later commit or proof found during the 2026-08-12 fresh review supplies it.

Before REV-102 can close, run the targeted runtime case that establishes what actually happens when source retention removes the last ordinary common snapshot.

Minimum evidence:

1. **Non-recursive / bookmark path:** demonstrate a successful transfer, then make the ordinary common snapshot unavailable while exercising the real bookmark behaviour (including the case where bookmark creation/refresh is unavailable or fails), create later source snapshots, run source prune, and show the next transfer behaviour explicitly.
2. **Recursive path:** lose the last ordinary common snapshot in a controlled throwaway relationship and run the real transfer path. Record whether it performs a controlled FULL resend or fails/refuses.
3. **TARGET preservation:** existing older TARGET snapshots/history must survive SOURCE prune and any recovery/FULL path unless TARGET's own independent retention removes them.
4. **Successful incremental-after-prune where continuity is claimed:** if an ordinary common snapshot or usable bookmark remains, prove the next transfer is genuinely incremental after source prune.
5. **No-base degraded behaviour:** if neither common snapshot nor usable bookmark remains, the operator-visible result must be explicit. No silent claim of incremental continuity.

### Decision rule already agreed

Do not decide this from prose before the runtime case.

- If recursive loss of the last common snapshot produces a controlled successful FULL resend, preserves TARGET history, and clearly surfaces the degradation, **allow + warning/status** is acceptable and simpler.
- If the path fails ambiguously, silently loses protection, or cannot expose the FULL boundary safely, **hard refuse** source-prune activation/migration for that recursive case until a safe mechanism exists.

Do not modify frozen transfer engines merely to manufacture a recursive bookmark solution unless the runtime proof shows it is necessary.
