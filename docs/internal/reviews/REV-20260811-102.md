# REV-20260811-102 — default backup policy leaves source snapshots unbounded

## Scope

Default/high-level backup policy, both the Phase 5 local path and the existing remote PULL activation path. This is not a request to couple source and target retention; the defect is precisely that the default currently bounds only the target side.

## Finding F1 — managed hourly snapshots on the source have no default prune

Fresh reviewed `main`: `542351826dfeede59ddbaf57851e17684853c127`.

The current built-in `default` profile renders:

- `dataset.inc` -> `use_template = standard_hourly`;
- `standard_hourly` -> `send_schedule` + `prefix = automated_hourly_`, but **no `prune_schedule` / `retain`**;
- `prune.inc` -> `keep_hourly,keep_daily,keep_weekly,keep_monthly` with GFS `-H24 -D7 -W4 -M12`.

That target-retention fragment is emitted only into standalone `[prune:<target>]` sections. In the local Phase 5 planner the generated `[dataset:<source>]` gets `standard_hourly`, while the GFS fragment is emitted as `[prune:<target>]`. In remote PULL, `emit_client_sections()` writes `[dataset:<local-target-path>]` with `src = account@host:<source>` and again writes the GFS `[prune:]` over the **local collector target**. There is no generated source-side `[prune:host:source]` equivalent.

`gen-cron.sh` only self-prunes a `[dataset:]` when its resolved template carries a prune schedule. `snapget.sh`/`snapsend.sh` do not perform an implicit source snapshot destroy after transfer. Therefore a default hourly job creates `automated_hourly_*` snapshots continuously on the source and, absent a hand-written/external cleanup rule, never removes them.

This is not merely cosmetic. A source pool with little free space can fill because the backup product itself accumulates its managed snapshots. That can impact the production workload the backup is supposed to protect.

The repository already documents the correct product model in `docs/examples/short-local-long-store.conf`: source retention and store retention are independent, and a short source window with long store history is a first-class supported shape. The default high-level workflow currently fails to provide any bounded source side of that model.

## Required correction

Preserve the architecture: **source retention and target/store retention remain independent policies.** Do not make target pruning delete source history, and do not force the same retention numbers on both sides.

The default high-level backup created from a preset must, however, have an explicit bounded retention for the snapshots that this tool creates on the source. The implementation must cover both:

1. local source -> local target (`snapsend` path), and
2. remote source -> collector target (`snapget` PULL path), where source cleanup is necessarily a source-side/remote prune operation rather than pruning the local `[dataset:]` destination.

Only the tool-owned snapshot pattern should be affected; manual/foreign snapshots must remain outside this cleanup rule. Do not invent a general retention framework or profile inheritance layer.

The exact default source window is a product-policy choice; keep it explicit and visible in the generated CONFIG/preview. A short operational window (distinct from the longer store GFS) is the intended shape, but do not silently equate it with the target ladder.

## Required evidence

Because this adds destructive pruning on a production/source boundary, local parser tests are not sufficient.

At minimum require:

- deterministic generation tests proving the default candidate contains **both** bounded source retention and independent target/store retention;
- negative control proving the reviewed base leaves source retention absent/unbounded;
- proof that manual/non-matching snapshots on source survive;
- proof that target-only old snapshots survive after the corresponding source snapshots are pruned;
- real-ZFS end-to-end evidence for short-source / long-target retention, including a subsequent incremental transfer after source pruning;
- for remote PULL, evidence that the source-side cleanup actually runs against the remote source identity/grant boundary and not accidentally against the local target;
- dependency-selected cascade + `./test/impact.sh --verify`.

## Verdict

CHANGES REQUIRED (P1). This should be resolved before Phase 5 gains transactional installation: a one-command installer must not make the default path capable of silently filling its source pool.
