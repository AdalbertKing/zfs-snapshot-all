# REV-20260811-102 — default backup policy leaves source snapshots unbounded

## Acceptance property

Every high-level backup relationship that creates tool-owned source snapshots must have a bounded, ownership-safe source cleanup policy. SOURCE and TARGET retention are separate native CONFIG v4 policies, initialized from the same preset values at CREATE but independently editable thereafter. For remote PULL the collector owns the cron/config and executes source prune through the relationship's existing pinned SSH/delegated identity; no autonomous source cron is introduced.

Existing CONFIGs are runtime truth. They must not be silently regenerated from a profile. Any retrofit must be explicit, previewed, add only missing source-retention policy, and preserve unrelated installed policy/topology.

Incremental continuity may only be claimed while a usable ordinary common snapshot or proven usable bookmark remains. Source-prune failure/outage behaviour must be explicit and safe.

## Accepted progress before current submission

The following pieces are directionally accepted and remain part of REV-102's eventual closure proof:

- local PUSH now emits a bounded SOURCE prune and an independent TARGET prune;
- SOURCE and TARGET use distinct template authorities after CREATE;
- default non-recursive source prune no longer uses `-R`, so matching snapshots on out-of-coverage children survive;
- real local ZFS proof showed managed source snapshots aging out while a manual snapshot and child snapshot survived;
- remote PULL emits a collector-scheduled `[prune:<account@host:source>]` over the existing pinned SSH path;
- the existing delegated `destroy` capability is verified fail-closed rather than widened;
- real pve1 -> pve2 source-prune proof exercised the delegated identity, prefix selectivity and non-recursive scope;
- REV-107 corrected reactivation so installed source-retention policy is preserved while endpoint topology moves.

These accepted pieces do not by themselves close REV-102.

## F3 — audit false-green: header presence is not proof of bounded source retention

`cmd_audit_source_retention()` currently decides that a source is bounded with only:

```bash
grep -qxF "[prune:$scope]" "$cronfile"
```

That proves only that a section header exists. It does not prove that the section actually schedules bounded destruction.

A valid/native CONFIG can contain the exact header while still being effectively unbounded or non-pruning, for example a section that:

- has `prune = no`;
- references a template family with no `prune_schedule`/`retain`;
- has been hand-edited so the effective generated cron contains no bounded `delsnaps` retention;
- otherwise exists structurally but does not produce a finite retention ladder.

In those cases the audit reports `nic do dodania` even though REV-102's production safety property remains false.

### Required correction

Audit the effective retention semantics, not header existence. The smallest acceptable proof is implementation-defined, but it must distinguish:

1. missing source prune;
2. present and genuinely bounded source prune;
3. present but unbounded/disabled/invalid source prune.

Prefer reusing the existing CONFIG/gen-cron semantics rather than adding a second retention parser. Add a negative control where the exact `[prune:<remote-source>]` header exists but does not produce bounded prune; the audit must not report that source as safe.

## F4 — `--apply` is not "add only missing source retention" because it refreshes unrelated topology

The migration contract says `--apply` preserves installed policy/topology and adds only missing source retention. The implementation instead calls:

```bash
emit_client_sections "$workfile" "$name" 0
```

for every active client.

`emit_client_sections(..., is_new=0)` is the ordinary reactivation path. For preserved dataset sections it intentionally rewrites topology-owned `src` and `flags` to the currently loaded endpoint. Its remote-source-prune path can also move source-prune scope/SSH topology when the endpoint differs.

Therefore `audit-source-retention --apply` can perform an unrelated endpoint/topology refresh while supposedly doing only a retention retrofit. This is especially visible if client state/current endpoint and the installed CONFIG do not match exactly: the migration can change more than the missing `[prune:]` sections.

That violates the explicit REV-102 migration boundary and the established one-way CONFIG-v4 handoff.

### Required correction

The retrofit path must be narrower than reactivation:

- identify only relationships/datasets whose effective source retention is missing/unbounded;
- add or repair only the source-retention material explicitly previewed for those entries;
- leave existing `[dataset:]` `src`/`flags`, target prune, existing bounded source prune, templates and unrelated client topology byte/semantically unchanged;
- no profile-wide regeneration or opportunistic endpoint repair.

Add a discriminating regression: arrange a client record whose current endpoint/topology differs from the installed CONFIG, run the source-retention migration, and prove the only semantic change is the intended source-retention addition/repair.

## F5 — new persistent `--apply` orchestration has no direct transaction test

Section 57 currently proves only:

- read-only audit names a missing source prune and leaves CONFIG byte-identical;
- once an exact source-prune header exists, audit reports nothing to add.

It does not execute the new `--apply` path through workfile creation, grant gate, gen-cron validation, preview/confirmation boundary and atomic install/rollback/read-back.

Reusing lower-level helpers is useful but does not prove the new orchestration connects them correctly. Because `--apply` modifies persistent CONFIG and crontab state and installs a destructive source-prune job, at least one targeted end-to-end fixture of this command boundary is required, including an unchanged-on-refusal/failure case.

## Reviewer direction on recursive refuse-vs-warn

Do not choose from prose. Run the targeted runtime case first.

Preferred minimal decision rule after the test:

- if loss of the last ordinary common snapshot in recursive mode results in a controlled, successful FULL resend, keeps existing TARGET history, and surfaces that degradation clearly, **allow-with-warning/status** is acceptable and simpler;
- if the path can fail ambiguously, silently lose protection, or otherwise cannot make the FULL boundary explicit and safe, **hard-refuse source-prune activation/migration for that recursive case** until a safe mechanism exists.

Do not modify frozen transfer engines merely to force a recursive bookmark solution unless the runtime proof shows that is actually necessary.

## Required evidence before closure

At minimum, the final submission must prove:

- separate bounded SOURCE/TARGET defaults and independent editing;
- source-prune scope equals owned source coverage;
- manual/foreign/out-of-coverage snapshots survive;

- migration changes only intended source-retention semantics and has a direct apply/refusal transaction test;
- bookmark-unavailable and recursive cases have explicit, tested safe/degraded behaviour;
- real incremental-after-prune succeeds where continuity is claimed;
- dependency-selected cascade + `./test/impact.sh --verify` are clean for the final implementation.
