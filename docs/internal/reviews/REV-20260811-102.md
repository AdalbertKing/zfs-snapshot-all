# REV-20260811-102 — default backup policy leaves source snapshots unbounded

## Scope

Default/high-level backup policy, both the Phase 5 local path and the existing remote PULL activation path. The defect is that the default currently bounds only the target/store side while tool-owned snapshots on the production source are unbounded.

Design discussion / owner direction:
`docs/discussions/SOURCE-TARGET-RETENTION-2026-08-11.md`

## Finding F1 — managed hourly snapshots on the source have no default prune

Fresh originally reviewed `main`: `542351826dfeede59ddbaf57851e17684853c127`.

The current built-in `default` profile renders:

- `dataset.inc` -> `use_template = standard_hourly`;
- `standard_hourly` -> `send_schedule` + `prefix = automated_hourly_`, but **no `prune_schedule` / `retain`**;
- `prune.inc` -> `keep_hourly,keep_daily,keep_weekly,keep_monthly` with GFS `-H24 -D7 -W4 -M12`.

That target-retention fragment is emitted only into standalone `[prune:<target>]` sections. In the local Phase 5 planner the generated `[dataset:<source>]` gets `standard_hourly`, while the GFS fragment is emitted as `[prune:<target>]`. In remote PULL, `emit_client_sections()` writes `[dataset:<local-target-path>]` with `src = account@host:<source>` and again writes the GFS `[prune:]` over the **local collector target**. There is no generated source-side remote `[prune:<host:source>]` equivalent.

`gen-cron.sh` only self-prunes a `[dataset:]` when its resolved template carries a prune schedule. `snapget.sh`/`snapsend.sh` do not perform an implicit source snapshot destroy after transfer. Therefore a default hourly job creates `automated_hourly_*` snapshots continuously on the source and, absent a hand-written/external cleanup rule, never removes them.

This is not merely cosmetic. A source pool with little free space can fill because the backup product itself accumulates its managed snapshots. That can impact the production workload the backup is supposed to protect.

The repository already documents the correct underlying model in `docs/examples/short-local-long-store.conf`: source retention and store retention are independent policies. The high-level default currently fails to provide any bounded source policy at all.

## Owner direction — one scheduler, two independent policies

Owner decisions recorded 2026-08-11:

1. **The collector (`pve1`) owns the cron and CONFIG for source retention as well as transfer/store retention.** A remote source must not acquire a second autonomous scheduler merely to clean these snapshots.
2. **The default preset should initially propose the SAME retention values for source and target/store.** This is the zero-surprise safe starting point: both sides are bounded and the operator sees one familiar policy rather than a hidden asymmetric default.
3. Equality is only a CREATE-time proposal. Once rendered, CONFIG v4 must hold **two separate native policies** that the administrator can edit independently before acceptance and later by normal CONFIG editing. There is no runtime linkage, inheritance, drift authority or automatic re-synchronisation between them.

For the current `default`, the simplest baseline proposal is therefore the same current ladder on both sides (24 hourly / 7 daily / 4 weekly / 12 monthly), unless the owner later chooses different default numbers. An administrator may then deliberately shorten the source or lengthen the store in the candidate CONFIG before install, for example:

- source: `24H / 7D`, target/store: `24H / 30D / 12M / 3Y`; or
- source: `24H / 7D / 4W / 12M`, target/store: a longer archive ladder.

This does **not** turn source and target into one policy. It means the preset copies the same initial values into two independently owned CONFIG rules.

For a remote PULL relationship the collector schedules the source-prune operation and executes it on the source through the relationship's existing SSH / authorization boundary:

`collector cron + canonical CONFIG -> remote source prune over SSH`

not:

`collector schedules backup` + `source has a separate local cleanup cron/config`.

CONFIG v4/gen-cron already supports remote standalone `[prune:<host:dataset>]` with `ssh_flags`; prefer composing that existing primitive rather than inventing another retention language or scheduler.

Reasons this boundary matters:

- one canonical place describes the relationship and both independent retentions;
- pause/disable/removal/lifecycle do not leave behind a forgotten source-side cron;
- source retention cannot drift independently from the relationship CONFIG on the collector;
- the destructive remote operation can reuse the pinned relationship identity/key and exact accepted/granted scope;
- no retention side effect has to be hidden inside the frozen transfer engines.

For local source -> local target the same ownership rule is trivial: the one local CONFIG and cron generate both source-prune and target-prune jobs.

## Required correction

Preserve the architecture: **source retention and target/store retention are separate policies in native CONFIG v4.**

The default high-level CREATE path must:

1. propose bounded source retention and bounded target/store retention;
2. initialize both sides from the same preset retention values;
3. render them as separate CONFIG rules, so changing one does not change the other;
4. expose both clearly in the candidate/preview before install;
5. after any operator edit, revalidate the candidate and show the final CONFIG + cron diff before confirmation;
6. after installation, treat CONFIG v4 as runtime truth and never re-couple the two through the profile.

The implementation must cover both:

- local source -> local target (`snapsend` path), and
- remote source -> collector target (`snapget` PULL path), where source cleanup is a collector-scheduled remote prune over the existing relationship SSH/grant boundary.

Only tool-owned snapshot patterns may be affected; manual/foreign snapshots must remain outside this cleanup rule. Do not invent profile inheritance, source-vs-target profile variants, a second scheduler, or a new retention framework.

For remote PULL, do not install an independent source-side cron/config. If the existing remote-prune grammar/SSH gate cannot express the required operation safely, expose that as the narrow implementation gap instead of creating another control plane.

## Timing / phase gate

REV-102 is a prerequisite to the Phase 5 transactional installer.

The required order is:

1. keep Phase 5 install/commit slice blocked;
2. correct CREATE-time composition for independent bounded SOURCE + TARGET retention;
3. wire remote PULL source retention from collector cron using the existing remote-prune primitive;
4. prove local and remote destructive behavior on real ZFS;

6. close REV-102;
7. only then resume Phase 5 transactional install (`preview/edit -> seed -> atomic CONFIG -> cron install/read-back -> active`).

This is not deferred to restore or a later convenience phase. A one-command installer must not knowingly install an unbounded production-source policy.

## Existing CONFIGs — no silent profile reapplication

Changing the default preset fixes NEW CREATE only. Existing relationships have already crossed the one-way handoff from profile to CONFIG v4 and may contain deliberate native edits. Ordinary reactivation must therefore NOT add source retention as a hidden repair.

Before REV-102 closes, the implementation/design must provide the smallest explicit migration/audit boundary that can:

- identify managed sources creating tool-owned snapshots without matching bounded source retention;
- show the exact source-prune CONFIG/cron additions;
- require explicit operator acceptance;
- leave unrelated installed policy byte/semantically intact;
- leave already-customized source retention untouched;
- be idempotent.

Avoid adding a permanent new public verb unless no smaller safe migration boundary exists.

## Incremental-base safety

Source retention must not destroy the transfer chain. The implementation must prove that after source pruning:

- old target-only snapshots remain;
- the required common base/bookmark survives;
- the next transfer remains incremental;
- a long outage/paused relationship has explicit safe behavior rather than silently losing the only useful base.

The repository already has per-target bookmark machinery; use and prove it if it provides the property rather than adding a parallel mechanism.

## Required evidence

Because this adds destructive pruning on a production/source boundary, parser/unit tests alone are not sufficient.

At minimum require:

- deterministic generation tests proving NEW default candidates contain separate bounded SOURCE and TARGET policies initialized from the same preset values;
- a test proving an operator can change only SOURCE or only TARGET in the candidate without the other being regenerated/coupled;
- negative control proving the reviewed base leaves source retention absent/unbounded;
- proof that manual/non-matching snapshots on source survive;
- proof that target-only old snapshots survive after corresponding source snapshots are pruned;
- real-ZFS end-to-end proof for short-source / long-target retention, including a subsequent incremental transfer after source pruning;
- remote PULL proof that collector-issued cleanup executes against the remote source identity/grant boundary, never the local target;
- proof that no autonomous source-side cron is installed or left behind;
- proof of the chosen explicit migration/audit behavior for an existing CONFIG lacking source retention;
- dependency-selected cascade + `./test/impact.sh --verify`.
