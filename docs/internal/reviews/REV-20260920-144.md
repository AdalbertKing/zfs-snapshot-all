## F1 — P2 BLOCKING — a failed source cleanup does not stop record purge

- Severity: P2
- Blocking: yes
- Affected path: `zfs-backup.sh`, `cmd_delete_relation()`

`delete-relation --yes` correctly records a failed source-side presence probe or
`deploy.sh --leave` as `rc=1`, but it then continues into
`clean-relationships.sh --purge=NAME`. The relationship record is therefore
deleted even though the source may still contain the pairing manifest, account
and ZFS grants. A later `delete-relation NAME --yes` cannot retry the failed
half because the command now refuses with `no relationship 'NAME'`.

The same control flow also reaches `--destroy-copies` after the source failure.
Thus the composite reports failure while discarding its durable retry state and,
when explicitly requested, may continue with irreversible copy destruction.
The printed manual command is useful diagnostics, but it is not a durable,
machine-readable relationship record and does not make the operation resumable.

### Minimal reproduction

## Acceptance criteria

1. If the source presence probe or `deploy.sh --leave` fails unexpectedly,
   return nonzero and stop before record purge and before any
   `--destroy-copies` action.
2. Preserve the removed relationship record, including peer/endpoint metadata,
   so the same `delete-relation NAME --yes` command can safely retry.
3. Permit record purge only after source cleanup succeeds, the source is
   positively proven already clean, another live relation proves the shared
   source side must stay, or the operator explicitly selected `--keep-source`.
4. Add the focused discriminator above and assert all three properties:
   nonzero result, record still present, and neither purge nor copy destruction
   invoked after the injected source failure.
5. Preserve the existing successful, already-clean, shared-peer and plan-only
   paths; report the full implementation SHA, focused result, `delrel` result,
   `impact.sh --verify`, and exact-head CI.
