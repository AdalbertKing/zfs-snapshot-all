# REV-20260809-089 — reactivation rebuilds managed sections from the current profile and discards installed policy

Review time: 2026-08-09 23:11 CEST
Reviewed state: `8d0dc243f519243a67ae06c64e0822abe021bf7d`
Response path: `docs/internal/reviews/responses/REV-20260809-089.md`

## Verdict

**CHANGES REQUIRED — Phase 3 finding confirmed independently.**

Claude's discussion note correctly identifies a production defect in the current reactivation path. `cmd_activate_client()` already distinguishes first activation (`STATE=endpoint_verified`) from reactivation (`STATE=active`) for REV-088's template-collision check, but `emit_client_sections()` receives no such distinction. It always removes the relationship-owned sections and reconstructs them from the CURRENT active profile before writing fresh topology fields.

That violates the canonical one-way handoff:

```text
PROFILE/PRESET -> generate once -> CONFIG v4 -> runtime truth
```

and Phase 3's required property that endpoint/topology maintenance preserves installed policy.

## F1 — P1 — ordinary reactivation destroys relationship-local CONFIG policy

Current `emit_client_sections()` does, on every call:

1. `load_active_profile`;
2. compute managed paths;
3. `remove_managed_sections` for those paths;
4. recreate `[dataset:]` bodies with `profile_emit "$PROFILE_DS_FILE"`;
5. recreate `[prune:]` bodies with `profile_emit "$PROFILE_PRUNE_FILE"`.

Therefore an operator's deliberate post-generation customization inside a relationship-owned section is silently deleted on the next reactivation. A later edit to the shipped/current profile can also silently change `use_template`, `recursive`, `gfs`, `gfs_pattern` or any other profile-owned field during what should be a topology-only operation.

The fact that `src`/`flags` correctly refresh to the new endpoint does not justify regenerating the entire policy section.

## Required correction

Reuse the existing first-activation/reactivation distinction; do not build a merge framework.

- **First activation:** keep today's full generation from the selected/default profile.
- **Reactivation:** use the installed relationship-owned section as the base and update only fields whose values are relationship/topology facts that actually changed.
- At minimum, endpoint reactivation must refresh `src` and transport `flags` without changing profile/policy fields or hand-added fields.
- Preserve current ownership-marker checks and fail-closed behavior; do not adopt foreign sections by header alone.
- Do not solve deferred source-removal/dataset-set reconciliation here unless a concrete correctness dependency makes it unavoidable.

The exact topology-owned field set must be justified from current runtime contracts rather than guessed. `pair_label`/`notify` appear stable/name-derived; if the implementation elects to rewrite them, prove that doing so is semantically invariant and cannot erase operator intent.

## Minimal discriminating proof

Use the real activation/composition boundary, not a helper-only tautology:

1. first activation creates the normal managed `[dataset:]`/`[prune:]` sections;
2. deliberately customize policy in an installed relationship-owned section;
3. change endpoint facts and run the real reactivation path;
4. prove endpoint-owned fields (`src`, transport flags) change as required;
5. prove customized/policy fields remain byte/semantically unchanged;
6. edit the active profile fragments between activation and reactivation and prove installed relationship policy is still not regenerated from them;
7. cover backup-mode GFS prune shape and sync-mode per-dataset prune shape at the smallest boundary that actually exercises the reactivation branch;
8. negative control against current main must show the customization is lost/regenerated;
9. run dependency-selected cascade and `./test/impact.sh --verify` with real exit status.

No new ZFS payload/SSH/live-host campaign is required if the implementation remains a deterministic CONFIG-composition change. If the fix changes host-state mutation, real crontab install semantics, dataset-set reconciliation, or transfer behavior, reassess evidence at that boundary.
