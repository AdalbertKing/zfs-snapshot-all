# REV-20261112-196 — mirror pruning removes a recovery point whose GUID remains on the source

Reviewer: ChatGPT / GPT-6.1 Sol. Date: 2026-11-12.

Target: canonical development main `1d4cbdd8f7577d1eedee830eb5b00b65a3430d68`. The candidate-bound live evidence was committed by Claude for REV-194 at PR #1184 and executed on `c63b500cf870bf5d3bf0064933054cd6c31682b8`. Reviewer independently checked its four dependency hashes against current main. This new REV concerns destructive mirror-history behavior after a successful transfer; it neither reopens the repaired attach preflight nor adds another attempt to REV-195's release gate.

## F1 — source rename is mistaken for source deletion during mirror pruning

- Severity: **P1**. Blocking: **yes for safe preservation of the source's existing mirror history**.
- Contract: `snapget.sh:231–237` describes `-M` as removing target snapshots the source no longer has, older than the common base. The engine already recognizes snapshot identity by GUID across names (`find_common_snapshot`, `snapget.sh:1025–1055`). The Owner's mirror-history direction is recorded in `docs/project/ENGINE-FREEZE.md:1321–1327`: the replica carries the collector's history. Renaming a source snapshot preserves its GUID and recovery point.
- Affected path: generated replica jobs select `snapget.sh -e -M` or `snapget.sh -m PREFIX -M` (`gen-cron.sh:4709–4728`); direct `snapget.sh -M` reaches the same post-success `mirror_target` at `snapget.sh:3313`. That function lists source and target snapshots and finds a valid common base, but builds `on_src` from **names** (`1358–1359`), skips only matching names (`1364`), then destroys an older target snapshot (`1366`). This downstream check forgets the GUID identity the transfer accepted. Source-list reads support local and remote sources; the demonstrated live case is local.

### Evidence and expected versus actual

**EXECUTED — real ZFS, independently reviewed committed evidence:** [live log](evidence/REV-20261112-194-mediagate-live.log), scenario 3, lines 45–80; [fixture/command](evidence/REV-20261112-194-mediagate-live.sh). Host pve9, ZFS 2.1.11, isolated file-backed pool. The log's `snapget.sh` SHA256 is `67eb9b02164afc3b39af6e36f391a2ec7d9a1fedd3e15bf59a3dbb6cae8cb76b`, identical to the reviewed main tree. This is Claude-executed lab evidence which Reviewer read and bound to code, not a Reviewer-executed host test.

1. Source renames `@replica_2026-11-12_13-51-41` to `@replica_renamed`, preserving GUID **12128216800917772009**. The source bookmark and another common-name snapshot are removed to make this identity the sole old common point. The log prints source `replica_renamed` and the medium's old-name snapshot with this same GUID.
2. The candidate gate accepts the common GUID. The engine finds `replica_renamed` as the valid common snapshot and successfully sends an increment to the new newest snapshot.
3. Mirror pruning then logs `destroyed ...@replica_2026-11-12_13-51-41 -- no longer on the source`. Final target listing contains only the new snapshot (GUID **16585132537459466547**). The run returns engine rc 0 and exports the medium successfully.

**Expected:** the older recovery point still present on the source by GUID survives on the mirror, either retained under its existing name or safely synchronized to the new name. **Actual:** its only snapshot on this medium is destroyed, although the source still holds that recovery point. Removal of `replica_collector2` in the same log is a legitimate true-deletion control and must remain possible; the renamed point is different.

Impact: the medium loses an older restore point and reports successful mirror completion. This is not loss of the latest copy or destruction of the source snapshot. A normal later incremental run starts from the newer common state and does not recreate the older missing point; the already-up-to-date transfer path (`snapget.sh:1838–1843`) also does not backfill old history. A deliberate reseed/history-repair operation may restore it, but normal successful replication is not such a repair.

### Acceptance and required evidence

- Decide snapshot presence using validated identity evidence before a destructive mirror decision, consistently with GUID-based transfer lineage. Preserve an older source point when its name differs on the target. Do not loosen the existing common-base/order, reserved-name, live-guest or unknown-read guards.
- Cover source renamed / target old name, target renamed / source old name, ordinary matching names and genuine source removal. Cover same name / different GUID so name equality alone cannot prove identity. Failed, incomplete or unparsable identity evidence must not establish absence and authorize deletion.
- Trace all public `-M` entry paths affected by the chosen repair, including generated replica jobs, direct CLI and local/remote source evidence. Do not add a profile/template dependency: the relationship config remains authoritative after creation. This finding does not request a retention-setting redesign or changes to unrelated non-mirror `keep` jobs.

Run an isolated real-ZFS rename case through successful transfer and mirror pruning; list source/target GUIDs before and after, demonstrate the older recovery point remains usable, and repeat with no new work. Include a true-deletion positive control and bind logs/commands/dependencies to the submission SHA. No physical unplug or production-host modification is required for this bounded proof.
