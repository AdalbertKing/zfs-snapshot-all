## F1 — `git gc --prune=now` has no mutual exclusion with the account cron

- Severity: **P1**
- Blocking: **yes for the proposed cleanup on every root/account checkout**
- Affected: `docs/project/DESIGN-REPO-WYDAN-2026-10-24.md` section 9.2 and
  the delegated-account auto-update installed by `deploy.sh`

### Evidence

Section 9.2 correctly places `update-hold` for the root updater, but explicitly
states that the delegated account has no hold. It substitutes a clock window
outside minute `:15`, then expires every reflog and runs:

```text
git reflog expire --expire=now --all
git gc --prune=now
```

The exact production release installs the account's independent cron as:

```text
15 * * * * cd <account-repo> && git pull --ff-only origin main >>.../git-pull.log 2>&1
```

That line has no `flock`, hold check, or other lock shared with the proposed
maintenance. Selecting `:20..:10` is not mutual exclusion: an already-running
pull can overlap the cleanup, and there is a race between any point-in-time
process/lock check and the destructive prune.

Git's own `git-gc` documentation says that `--prune=now` “increases the risk
of corruption if another process is writing to the repository concurrently”
and explains that the other process may later add a reference to an object
which GC deleted:
https://git-scm.com/docs/git-gc

Safe exact-state negative control (read-only; no host, object or ref mutation):

```bash
DEV_REPO=/path/to/zfs-snapshot-all
REL_REPO=/path/to/zfsbackup
DEV_SHA=f6bb2b7476532516eadb3851ea8136ff890b1b77
DESIGN_SHA=41c06623e2f9258fddb994ea88d7ac0466e70e09
REL_SHA=3d15bc4296a175a08d408315af801be697ac8726

test "$(git -C "$DEV_REPO" rev-parse HEAD)" = "$DEV_SHA"
test "$(git -C "$REL_REPO" rev-parse HEAD)" = "$REL_SHA"
git -C "$DEV_REPO" show "$DESIGN_SHA:docs/project/DESIGN-REPO-WYDAN-2026-10-24.md" > /tmp/rev185.design
git -C "$REL_REPO" show "$REL_SHA:deploy.sh" > /tmp/rev185.deploy

grep -F 'git gc --prune=now' /tmp/rev185.design
grep -F 'Konto nie ma holdu' /tmp/rev185.design
grep -E 'PULL_LINE=.*git pull --ff-only origin main' /tmp/rev185.deploy
if grep -E 'PULL_LINE=.*(flock|update-hold)' /tmp/rev185.deploy; then
    echo 'PASS: updater and cleanup share exclusion'
    exit 0
fi
echo 'FAIL: prune=now can overlap the delegated-account git pull'
exit 1
```

Expected and observed on the named states: all three contract lines are present,
no shared exclusion is present, and the control exits 1.

### Failure mode and impact

A delegated-account `git pull` can be fetching or creating objects while the
cleanup expires all reflogs and immediately prunes unreachable objects. The
normal age grace which mitigates concurrent writers is intentionally disabled.
The pull may fail, or it may later reference a deleted object and leave the
checkout corrupt. That checkout supplies the delegated backup account's
executables and hourly updates, so the failure can silently strand future
security and correctness updates until repaired manually.

The same concurrency rule applies independently to each root and account
repository. A root-only hold cannot serialize operations in the account clone.

### Acceptance criteria

- Before any `--prune=now` maintenance, establish enforceable mutual exclusion
  in the exact repository being cleaned. Clock selection or a one-time
  `ps`/`.git/index.lock` observation is not sufficient.
- For the delegated account, either temporarily remove/disable its pull cron and
  prove any previous invocation has exited, or make both the updater and cleanup
  acquire the same per-repository lock. Restore the cron only after validation.
- Apply the same explicit quiescence rule to the root checkout in addition to
  `update-hold`; wait for any updater already in progress before GC begins.
- Preserve ignored host configuration byte-for-byte. Preserve `HEAD`,
  `origin/main`, the intended rollback target, ownership and executable modes.
- Every destructive ref deletion, reflog expiry and GC step must stop on the
  first failure. Do not remove the hold/lock on failed validation.
- Validate `git fsck`, exact `HEAD`, exact ignored/config inventory and a
  subsequent controlled update before considering one checkout complete.
- Keep the Owner gate and the lab-first, one-host-at-a-time rollout. This review
  does not authorize execution on any host.

### Required verification

- Add a hermetic temporary-repository test in which a delegated-style updater
  holds the shared lock; cleanup must refuse or wait without deleting refs.
- Add the converse control: maintenance holds the lock and the updater cannot
  enter. Verify cleanup failure leaves the hold and repository recoverable.
- Test a pre-existing updater which began before the maintenance request.
- Test root and delegated clones separately, including ignored configuration,
  rollback reachability and post-cleanup `git pull --ff-only`.
- Run shell syntax, `git diff --check`, the focused installer/update tests,
  `test/impact.sh --verify`, and exact-head CI.

### Boundaries and confidence

The concurrency defect is established from the exact merged proposal, exact
production cron, and the upstream Git contract. No race was attempted against a
live host because the proposal is explicitly pre-execution and host mutation is
outside reviewer authority. This finding does not claim that corruption has
already occurred; it establishes that the proposed procedure lacks the required
barrier before a command whose documented risk is repository corruption.
