# REV-20260811-104 — REV-103 correction is internally inconsistent and still carries the stale source-grant premise

## Scope

Independent follow-up review of the REV-103 design correction at implementation `2e4853d8eff104d1d9854cc3c58aa529248d1fb2`, read from fresh main `c37fb3624d0612500ba9b12ecf4c767fbf83dfb2`.

REV-103 correctly fixes its Q3 and Q4 prose near the top of `docs/discussions/PHASE5-SOURCE-RETENTION-DESIGN-2026-08-11.md`, but the same document still contains downstream sequencing/progress statements that contradict the correction and can drive the next implementation step from the old premise.

## F1 — corrected Q3 says no grant gap, but sequencing still says to add `destroy,mount`

Current `deploy.sh` defines one delegated `ZFS_PERMS` set containing:

`snapshot,destroy,send,receive,create,mount,rollback,hold,release,canmount,bookmark`

The corrected Q3 therefore properly says the default plain source prune needs `destroy`, which is already granted, and that no privilege widening is required.

However, the same design note's **Sequencing step 3** still says:

`Remote grant: deploy.sh --join destroy,mount on source + fail-closed activation check.`

That is the exact stale action REV-103 F1 rejected. If followed literally, the next slice can still widen/alter the pairing/grant path despite the corrected analysis saying not to.

Required correction: remove the stale grant-addition step. Step 3 should be framed as **remote source-prune composition + fail-closed verification of the already-required delegated capability and pinned SSH path**, with a negative control proving failure when `destroy` is absent/revoked. No new `destroy,mount` grant should be introduced unless a real command-path test proves a new permission is actually needed.

## F2 — progress text repeats the false reason for deferring remote PULL

The **Progress — step 2** section says remote PULL was deferred because composing it "before the source `destroy` grant exists" would install a failing job, and says it will land "with the grant" in step 3.

That premise is also false on current code: `destroy` already exists in the delegated set. The safe deferral reason is narrower: remote PULL is destructive and must not be installed until the existing delegated identity/SSH path is explicitly verified for the exact prune operation and activation fails closed when that verification fails.

Required correction: rewrite the progress/defer text so the implementation plan has one consistent source of truth. Do not leave historical false premises in an ACTIVE design section that governs the next slice.

## F3 — recursive FULL-resend recommendation must remain a decision pending evidence, not an assumed runtime fact

The corrected Q4 properly states that recursive bookmark fallback is unsupported and that pruning past the last common snapshot can force a FULL resend. That is supported by `lib-zfs-snap.sh`.

But the recommendation rationale says a recursive relationship "already takes a FULL on its first miss anyway." The reviewed code proves only that **bookmark fallback** is skipped for recursive mode; it does not, from the evidence reviewed here, prove that every first missed schedule/transfer necessarily lacks a usable common snapshot. A recursive transfer can still have an ordinary common snapshot until retention removes it.

Required correction: do not use "first miss => FULL" as a product premise unless a targeted test/runtime path proves that exact property. Keep the actual invariant: recursive mode has no bookmark-backed fallback, so once source retention removes the last usable common snapshot a FULL resend may be required. The owner/reviewer choice between hard-refuse versus allow-with-warning may remain open until the live recursive case is exercised.
