# REV-20260811-104 — source and target retention still share one prune-template authority

## Scope

Independent review of current `main` `49d547aeb444259225a9aa4f9bae721ca6bf21f4`, following REV-102/103 and the owner decision that SOURCE and TARGET retention must be independently editable after the CREATE-time preset proposal.

The `49d547ae` change correctly fixes REV-102 F2's destructive recursion over-reach for the current non-recursive local source: the generated source `[prune:<root>]` now omits `recursive=yes`, while the target remains recursive. That narrow correction is accepted as directionally correct.

## F1 — two `[prune:]` sections are not two independent policies while they reference the same template identities

The current local candidate emits two different scopes:

- `[prune:<source>]`
- `[prune:<target>]`

but both are populated from the same `PROFILE_PRUNE_FILE`, whose `use_template` resolves to the same namespaced template identities (`profile__default__keep_hourly`, `keep_daily`, `keep_weekly`, `keep_monthly`). The retention counts (`-H24/-D7/-W4/-M12`) live in those shared template definitions.

Therefore an operator editing the candidate in the obvious native way, e.g. changing `profile__default__keep_monthly retain=-M12` to `-M36`, changes BOTH source and target retention at once. Separate section scopes alone do not provide the product property agreed with the owner: CREATE may initialize both sides from the same values, but after rendering they must be independently editable runtime policies.

This matters especially for the real constrained-source case: a source may intentionally keep only a short operational window (e.g. `H48`) while the target retains a long GFS history. The candidate must allow that without inventing ad-hoc duplicate templates by hand or relying on hidden coupling.

### Required correction

Render distinct prune-template authorities for SOURCE and TARGET at CREATE time, initialized from the same preset values but with different stable names/identities. The exact naming is an implementation detail; the required property is structural:

- editing SOURCE retention changes only SOURCE cron semantics;
- editing TARGET retention changes only TARGET cron semantics;
- reactivation/profile drift cannot re-couple them after install;
- remote PULL must use the same independence property when its source-prune is added.

Do not solve this by keeping shared templates and adding a second configuration representation. Native CONFIG v4 remains runtime truth.

### Minimum evidence

Use the smallest discriminating proof:

1. generation test: default candidate starts with equal SOURCE/TARGET values but references distinct source-vs-target prune template identities;
2. mutate only SOURCE retention in the candidate and render cron: SOURCE line changes, TARGET line is byte/semantically unchanged;
3. mutate only TARGET retention and prove the converse;
4. negative control against `49d547ae`: the same template mutation changes both sides, demonstrating why the new test is load-bearing;
5. dependency-selected cascade for files actually changed. No live-ZFS campaign is required solely for template identity; the destructive live proof remains REV-102's obligation once remote/source pruning is complete.

## F2 — active design still contains the unproven `recursive first miss => FULL` shorthand

The `49d547ae` design correction properly replaces the false claim that the equal default ladder guarantees a surviving incremental base. However the same active design still recommends allow-with-warning for recursive source pruning because a recursive relationship "already takes a FULL on its first miss anyway."

That statement remains stronger than the proven runtime property. The established fact is narrower: recursive mode lacks bookmark fallback. A recursive transfer may still have an ordinary common snapshot after a missed run; FULL becomes necessary when no usable common snapshot remains. Do not use `first miss => FULL` as a product premise unless a targeted runtime test proves exactly that behavior.

Required correction: state only the proven invariant and keep the recursive hard-refuse vs allow-with-warning choice tied to live evidence under REV-102.

## Verdict

CHANGES REQUIRED (P1). REV-102 remains OPEN and Phase 5 transactional install remains blocked. The local `-R` over-reach fix in `49d547ae` is accepted, but source/target retention is not yet structurally independent and the active recursive rationale is still overstated.
