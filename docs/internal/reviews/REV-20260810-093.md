## Remaining proof gap

This delivery newly exposes ZFS-dependent runtime behavior through supported CONFIG/generator paths. The implementation note explicitly says the relevant real-ZFS tests were not run in this delivery. Under the standing review contract, a local green generator suite is not final proof for behavior whose correctness crosses the ZFS/runtime boundary.

The missing proof is small and targeted; a broad campaign is not required.

### Required live-host proof

On a disposable real-ZFS dataset, on the identity that would actually execute the generated jobs:

1. **prefixless create** — execute the generated `snapsend` shape with `-m ""`; prove a new source snapshot is created with the engine's timestamp-only naming and transferred successfully.
2. **bare passive** — create at least two differently named source snapshots with a known newest one, execute the generated `-m "" -e` shape, and prove no new source snapshot is created and the newest existing snapshot is the one transferred. Include a meaningful negative/control observation (for example the older snapshot is not selected).
3. **prefixless GFS** — on an isolated disposable dataset containing a controlled hourly snapshot population, first run the exact generated `delsnaps.sh -G <dataset> "" -H... -D... -W... -M...` shape in dry-run and verify the intended survivor/deletion set; then, if safe, execute it and verify the resulting set. The essential property is that the empty pattern selects the intended all-name population and the GFS buckets operate on that population without argument shifting.

Use a reduced ladder/population if that proves the same dependency; there is no value in manufacturing months of data merely to increase PASS count. Synthetic creation timestamps may be used only if the engine/test harness already has a trustworthy way to establish them; otherwise prove representative H/D bucket boundaries sufficient to validate the runtime contract and rely on the existing deterministic GFS unit coverage for the remaining tiers.

## Scope discipline

No engine thaw is requested. No production-code change is requested unless the live proof exposes one. Do not run a fleet-wide campaign. This is a targeted runtime proof for the newly exposed generator-to-engine contract.

Once the transcript records commands, executing identity, ZFS before/after state, and the three outcomes above, REV-093 can be closed and Phase 3.5 approved.
