## F1 — P1 — client-recorded CRON_CONFIG is lost when server.conf is absent

Both `cmd_activate_client()` (reactivation path) and `cmd_remove_client()` source the client record first, then call `read_server_conf()`. `read_server_conf()` resets `CRON_CONFIG=""` before optionally sourcing `$SERVER_CONF`. On a host with no server.conf, the relationship's already-recorded authoritative cron config path is therefore silently erased.

Consequences observed/derived:

- `remove-client` can skip managed cron/config cleanup for an actually activated relationship;
- reactivation can fall back to a freshly computed default config path and write managed sections into the wrong file, orphaning the installed authoritative CONFIG.

The live campaign on metropolis pve1 exposed the removal half directly.

## Required outcome

Preserve a non-empty relationship-recorded `CRON_CONFIG` across the server-config read for operations that have already sourced a client record. Do not change `read_server_conf()` semantics for callers that genuinely want server defaults (`setup-server`, fresh `add-client`).

## Acceptance criteria

- [ ] With no server.conf, `remove-client` uses the client's recorded `CRON_CONFIG` and engages normal managed cleanup instead of treating it as never activated.
- [ ] Reactivation keeps using the relationship's recorded `CRON_CONFIG`, not `$SCRIPT_DIR/jobs.<host>.conf` or another recomputed default.
- [ ] Existing fresh-enrolment/setup callers retain their current server-default behavior.
