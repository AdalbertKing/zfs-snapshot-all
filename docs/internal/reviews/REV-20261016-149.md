## F1 — P1 blocking — local quiesce loses recursive listing status

- Affected: `snapsend.sh`, main quiesce scope loop around
  `done < <(quiesce_scope "$dataset" "$RECURSIVE")`;
  `lib-zfs-snap.sh:quiesce_scope` supplies the listing.
- Severity P1; blocking acceptance of recursive push/local snapshots as
  quiesced when source discovery failed.
- Independently reproduced after Claude disclosed this remaining risk in the
  REV-148 F2 response. It predates that fix and is not introduced by PR #572.
  REV-148 covers remote pull/snapshot-only; this finding covers the distinct
  local push path and gives the bounded authorisation it previously lacked.

### Cause and impact

`quiesce_scope` calls `zfs list -H -o name -r` with stderr suppressed. Its
nonzero status is lost by the caller's process substitution. The caller still
adds the parent to `QUIESCE_SNAPS_BY_POOL`, so failure (including after partial
stdout) becomes an empty or incomplete guest-discovery scope followed by a
recursive snapshot under the ordinary run name. Even `agent,strict` returns
0 with a success statistic. Descendant guests omitted by the failed listing
were never checked, flushed or frozen. The strict consistency request is not
fulfilled, and the operator receives no listing-failure diagnostic.

### Minimal actual-CLI reproduction

From the repository root, run this bash snippet. It reuses disposable external
command stubs from the existing snaponly harness, but executes the real
`snapsend.sh` and local quiesce code. No host is contacted, no real ZFS command
is executed, and no tracked file is changed. Each case uses its own lock
directory to avoid fixture process inheritance affecting the next case.

```bash
set -u
REPO=$PWD
SCRIPT_DIR="$REPO/test/snaponly"
source <(awk '/^# ---- 1\./{exit} /^SCRIPT_DIR=|^REPO=/{next} {print}' \
    "$SCRIPT_DIR/run.sh")
for listing_failure in 1 partial 0; do
    reset_world
    mkdir -p "$WORK/lock/$listing_failure"
    out=$(env ZFS_LIST_FAIL="$listing_failure" PATH="$STUB:$PATH" \
        RELATIONSHIPS_DIR="$WORK/rel" STATS_LOG="$WORK/stats.log" \
        LOCKDIR="$WORK/lock/$listing_failure" NOTIFY_SCRIPT=/bin/true \
        bash "$REPO/snapsend.sh" -r -q agent,strict -v 1 -m lab_ tank 2>&1)
    rc=$?
    printf 'listing_failure=%s rc=%s\n%s\n' "$listing_failure" "$rc" "$out"
    cat "$TRACE"
    cat "$WORK/stats.log" 2>/dev/null || :
done
```

Observed for both `listing_failure=1` (no output, rc 2) and `partial`
(root printed, then rc 2), with the snapshot suffix abbreviated:

```text
rc=0
Quiesce: taking 1 atomic snapshot(s), one per pool, covering 1 dataset(s)
All datasets processed successfully
QM list
ZFS list -H -o name -r tank
ZFS snapshot -r tank@lab_<run>
ZPOOL list -H -o health tank
{"status":"success", ...}
```

The good-listing control also returns 0 with exactly one recursive snapshot.
This fixture has no actual guest configuration: it proves the unsafe control
flow and misleading success, not live guest inconsistency or agent operation.
The reproduction uses local snapshot-only execution so it stops before any
send/receive; the faulty discovery loop is shared by push transfer jobs.

### Bounded correction authorised

Only `snapsend.sh` is opened by the marker above. Retain/check the helper's
exit status at the call site, reject unsuccessful or empty recursive scope,
and issue a source-specific diagnostic. `quiesce_scope` already returns the
underlying listing's nonzero status, so changing the shared library is not
needed for this finding. Higher layers cannot reliably detect the failure
once the engine converts it to success; the engine call site owns this guard.

Do not refactor freeze/thaw, delegation, transfer, P-0, snapshot naming or
successful source discovery. If implementation evidence shows that a library
change is necessary, explain that boundary in the response before touching
the still-frozen library. Update the normal freeze/twin record for the actual
diff. No production fix was made in this review; no deployment or live lab
campaign is authorised here.

### Acceptance and smallest verification

1. Under `-r -q agent,strict`, failed listing with no output, failed listing
   after partial output, and a successful but empty answer all refuse
   nonzero before any snapshot or transfer. Never report ordinary success or
   an ordinary clean snapshot for unknown scope. If earlier selected roots
   prepared guest state, exit through the existing safe cleanup path.
2. Keep the successful-listing control: full scope, existing guest handling,
   exactly one recursive snapshot per intended pool, established status.
   Check both the no-target route and a push job that would otherwise send.
3. Add an actual-CLI regression with external command stubs; assert command
   trace and final status. The current code must fail its refusal cases while
   passing the positive control. Avoid false coverage through a lock refusal
   or replacing quiesce with a chosen success code.
4. Inspect actual-diff impact obligations; run the smallest selected checks,
   twin checks and `impact.sh --verify`. Record exact SHA/CI and any unavailable
   live obligations honestly. No full-cluster campaign is needed merely to
   prove that failure exits before snapshot/transfer.

Extend the canonical response for this REV with the fixing full SHA and
evidence. This is a concrete defect to fix, not a request for the owner to
accept degraded safety or redesign the engine.
