# REV-20260907-137 — save-profile accepts profiles the downstream generator refuses

Review date: 2026-09-07
Reviewer: ChatGPT
Reviewed delivery: PR #347, head `0fa5bcfebec728913375531dd9d54eec3568875f`
Canonical merge checked: `7e78b314a4633fc90b2c5464898cd5b32f3732af`

## Verdict

**CHANGES REQUIRED — P2: `save-profile` reports success and publishes a
profile as valid even when the real downstream `gen-cron.sh` rejects a value
that the profile renderer merely copies through. With `--force`, this can
replace a usable operator profile with one that cannot be applied.**

The boundary that confines writes to `PROFILE_USER_ROOT`, the atomic final
rename, and the valid edit path are not rejected. The blocking issue is that
the advertised second gate proves only that `load_active_profile` can render
intermediate fragments, not that those fragments satisfy the generator that
future relationship creation actually invokes.

## F1 — P2 BLOCKING — the render gate does not prove downstream usability

- Severity: P2
- Blocking: yes
- Affected: `cmd_save_profile()` in `zfs-backup.sh` and the `saveprof`
  controls in `test/zfsbackup/run.sh`.

### Evidence

On exact implementation `0fa5bcfebec728913375531dd9d54eec3568875f`:

```sh
PROFILE_USER_ROOT="$D/user" PROFILE_ROOT="$PWD/profiles" \
  ./zfs-backup.sh save-profile \
    --from=d7h24 --as=badcron --tier=hourly \
    --send_schedule='not a cron'
```

Observed: `rc=0`, and `$D/user/badcron.conf` was written. The catalogue then
returned `rc=0` and described the row as `"valid":true`, carrying
`"send_schedule":"not a cron"`.

Rendering that saved profile into the same minimal CONFIG v4 shape used for a
future relationship and passing it to the real generator produced:

```text
gen_rc=1
gen-cron.sh: error: [dataset:rpool/test] tier=profile__badcron__hourly:
send_schedule = 'not a cron' -- a crontab time specification is exactly 5 fields
```

The two current gates both pass because `profile_validate_file` validates
ownership and field membership, while `load_active_profile` translates and
copies profile values into intermediate fragments. Neither asks
`gen-cron.sh` to validate the resulting effective section. The existing
`keep = xyz` control covers a value rejected during translation; it does not
cover values copied through and rejected only at the downstream generator.

A second reproduction first saved a valid `mine.conf`, recorded its SHA-256,
and then ran the command above as `--as=mine --force`. The forced call returned
`rc=0`, changed the file hash, and left `send_schedule = not a cron` in place.
Thus the defect is not limited to creating a disposable new file: the command
can replace the operator's known-good profile while claiming both gates passed.

### Failure mode and impact

The profile editor can accept an answer and present it as a valid saved
template, but the next `add-client`/activation path refuses when it reaches the
real generator. No installed relationship is mutated by `save-profile` itself,
so this is P2 rather than a data-safety P1. It is blocking for the GUI profile
editor because its save-success result is currently not a reliable statement
that the saved object can be used.

### Existing verification and why it missed the defect

- The focused `saveprof` invocation on current main completed

- The suite checks a value rejected by `load_active_profile` (`keep = xyz`),

- Independent `reviewctl --verify` and `impact.sh --verify` passed while
  closing REV-136; they do not exercise profile value semantics.

### Acceptance criteria

1. Before publishing or replacing a user profile, `save-profile` must prove
   that its rendered policy is accepted by the real downstream generator, or
   by one authoritative validation boundary shared with that generator. A
   copied, hand-maintained list of cron/value rules is not sufficient.
2. `--send_schedule='not a cron'` must return nonzero, name the downstream
   validation failure, and leave no new destination profile.
3. The same invalid edit with `--force` over an existing valid profile must
   leave the existing file byte-identical.
4. Add a positive discriminator showing that a valid schedule edit is still
   saved and is accepted through the same downstream boundary.
5. Cover at least one non-schedule value that is copied through profile
   rendering but validated by `gen-cron.sh`, so the remedy proves the general
   publication boundary rather than a special-case cron parser.
6. Preserve the current confinement to `PROFILE_USER_ROOT`, the atomic rename,
   and the rule that installed configs and relationships remain untouched.

### Required verification

- the focused `saveprof` controls, including the negative/positive
  discriminators above;
- `./test/impact.sh --verify`;
- exact-head CI.

No ZFS, fleet, destructive, or full product campaign is required. A temporary
profile directory, a minimal generated CONFIG v4 candidate, and the real
`gen-cron.sh` decide the defect.

## Required response

Publish one exact implementation SHA reachable from canonical `main`, explain
how the saved profile is checked at the same semantic boundary used by future
relationship creation, and report the focused controls, impact verification,
and exact-head CI.
