# REV-20261028-179 — P1: no-origin fallbacks leave the release channel

Reviewer: ChatGPT. Date: 2026-10-28.

Source release: `AdalbertKing/zfsbackup` main
`8143775b415bc400e6a554bdac2bed396196f839`, with
`RELEASE-OF=901e8e4b7ba5a2871ef59e29e6356b9762f2bb2f`.

## F1 — archive/bundle installs can silently adopt development `main`

- Severity: **P1**
- Blocking: **yes**
- Affected: `deploy.sh` repository selection and `zfs-backup.sh prepare-source`

### Evidence

The shipped guides and READMEs now correctly clone
`https://github.com/AdalbertKing/zfsbackup.git`. Ordinary clones therefore keep
their release `origin`. Two executable fallbacks disagree:

- `deploy.sh` uses `AdalbertKing/zfs-snapshot-all.git` when the checkout has no
  `origin`;
- `zfs-backup.sh prepare-source` uses that same development URL when its local
  checkout has no `origin`.

A checkout made from a GitHub archive, copied tree or bundle without an origin
is a supported operational shape in the package itself: `prepare-source`
explicitly has a bundle fallback. In that shape deployment clones the
development repository for a delegated account or source host. Its hourly
self-update then follows development `main`, bypassing the release export,
scrub, `RELEASE-OF` checkpoint and release-only publication decision.

Executable exact-blob negative control (read-only; no clone, host or install):

```bash
bash docs/internal/reviews/evidence/REV-20261028-179-release-channel-fallback.sh
```

On the exact development `RELEASE-OF` SHA it reports:

```text
sha=901e8e4b7ba5a2871ef59e29e6356b9762f2bb2f deploy_dev=1 prepare_dev=1 deploy_release=0 prepare_release=0
FAIL: a no-origin install/prepare-source fallback crosses from the release channel to the development repository
```

Running the same script with `TARGET_REPO` pointing at the release checkout and
`TARGET_SHA=8143775b415bc400e6a554bdac2bed396196f839` produces the same discriminator.
The exact release export was independently verified byte-for-byte against its
`RELEASE-OF`, so this is shipped behavior rather than export drift.

### Failure mode and impact

The operator starts from the production repository but an installation path
without Git metadata silently enrolls another host in the development channel.
Future hourly pulls may deliver unexported code and internal files without the
release checkpoint or release-repository review boundary. The visible install
can succeed, so the channel change is not an obvious failure.

### Acceptance criteria

- Every executable default used by the released package selects
  `AdalbertKing/zfsbackup`, never `AdalbertKing/zfs-snapshot-all`.
- If provenance cannot be established safely, fail closed before cloning or
  installing and name an explicit `REPO_URL`/origin remedy; do not guess the
  development repository.
- Preserve fork behavior: a valid `origin` continues to win over the stock
  fallback, and an explicit `REPO_URL` continues to win for deployment.
- A source prepared through clone and through the bundle fallback must finish
  with the intended release/fork origin and its updater must retain that exact
  channel.
- Add a release/export guard that rejects executable install/update references
  to `AdalbertKing/zfs-snapshot-all`; historical/internal documentation outside
  the shipped product is not the target of this rule.

### Required verification

- The reproducer above must change from FAIL to PASS and still fail against both
