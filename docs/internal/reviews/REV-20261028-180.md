## F1 — missing or failing `qm`/`pct status` is treated as a stopped guest

- Severity: **P1**
- Blocking: **yes**
- Affected: `zfs-restore.sh`, `restore_live_guard()`, local Proxmox disk path

### Evidence

For a local dataset whose basename matches `vm-*-disk-*` or
`subvol-*-disk-*`, `restore_live_guard()` obtains the guest state with:

```bash
st="$(command -v "$kind" >/dev/null 2>&1 && "$kind" status "$id" 2>/dev/null)"
```

It refuses only when the resulting text contains `running`. An empty result is
diagnosed only in the remote branch (`[ -n "$host" ]`), so all of these local
outcomes fall through with return code 0 and an empty verdict:

- `qm`/`pct` is absent from `PATH`;
- the command exists but exits nonzero;
- the command exits zero without a readable state.

This is not covered by the current local live-dataset test: that harness always
defines successful `qm()` and `pct()` functions. The remote path already treats
an unclassifiable `pgrep` result as a refusal, so the local and remote safety
boundaries disagree.

Executable exact-blob negative control (stubs only; no ZFS, guest, host or
network operation):

```bash
bash docs/internal/reviews/evidence/REV-20261028-180-local-guest-status.sh
```

On the exact `RELEASE-OF` commit it reports:

```text
qm-missing rc=0 verdict=<>
qm-error rc=0 verdict=<>
pct-missing rc=0 verdict=<>
pct-error rc=0 verdict=<>
FAIL: an unavailable local Proxmox guest-state probe is accepted as safe
```

Running the same control against the exact release commit produces the same four

comment, so the whole-file blob IDs differ; the executable guard is unchanged.

### Failure mode and impact

A zvol normally reports mountpoint/mounted as `-`, so neither the mounted-root
nor the `fuser` filesystem guard classifies it. The guest-state probe is then
the guard that prevents `rewind`/`replace` from rolling back or replacing a
disk while its VM or container may be running. If the Proxmox CLI is missing
from `PATH`, broken, denied or otherwise returns no state, the guard currently
claims success. A destructive recovery can proceed on an unclassified live
guest disk, risking concurrent writes and guest/filesystem corruption.

### Acceptance criteria

- For a local Proxmox-shaped dataset, absence of `qm`/`pct`, any nonzero status
  result, an empty result or an unrecognised result must refuse before the
  restore engine or any mutating ZFS command runs.
- The refusal must name the guest ID, the failed probe and the operational
  remedy; unknown is never equivalent to stopped.
- Only a successful, explicitly parsed `stopped` state may pass this guard.
  A successful `running` state must continue to refuse.
- Preserve the existing remote `pgrep` fail-closed behavior, the mounted-root
  and `fuser` guards, and ordinary non-Proxmox dataset behavior.

### Required verification

- Add actual-`restore_live_guard` tests for both `qm` and `pct`: missing
  command, nonzero command, empty/unknown output, stopped, and running.
- Every negative case must assert nonzero/refusal and that the trace contains
  reads only: no restore engine, `zfs rollback`, `zfs destroy`, receive or
  snapshot mutation.
- The reproducer above must change from FAIL to PASS and remain failing against
  both exact affected SHAs named here.
- Run `test/restore`, shell syntax, `git diff --check`,
  `test/impact.sh --verify` and exact-head CI. A live destructive test is not
  requested; if live evidence is supplied, it must be a read-only status probe.
