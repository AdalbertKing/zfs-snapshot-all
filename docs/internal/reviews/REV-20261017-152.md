## F1 — Explicit mode must survive the complete relationship lifecycle

- Severity: P1; Blocking: yes, implementation acceptance condition.
- Affected: `zfs-backup.sh` record readers, add-client, activation, seed,
  edit/add-source, status/JSON, import/export, cleanup; `lib-record.sh`.
- Evidence: `CLIENT_TARGET` currently encodes backup versus sync;
  `snapget_local_base()` derives a collector path. `RUX_MODE` is already an
  allowed client field in `lib-record.sh`; a parser redesign is unnecessary.
- Failure mode: a no-target record falls into mirror/receive/target cleanup,
  or a source is misrepresented as a local copy.
- Required outcome: resolve snaponly before all empty-target inference;
  preserve legacy records without RUX_MODE; reject unknown/inconsistent modes
  and an explicitly supplied target (including an empty spelling). Do not
  apply DEFAULT_TARGET. Seed/receive/target restore and target cleanup must
  refuse or be inapplicable, never fabricate a local base. Removing a
  relationship removes its jobs/state, not the source dataset. Export/import,
  reactivation and add-source preserve this distinction. Keep records as data.
- Verification: CLI/record round trips, legacy backup/sync/local regressions,
  target rejection, no seed/receive/target-delete call, interrupted activation
  does not leave a misleading active record or partial installed policy.
- Uncertainty: no Round 1 implementation exists; these are acceptance criteria,
  not claims that the future feature already contains these defects.

## F2 — Source ownership and generated mode need their own identity

- Severity: P1; Blocking: yes.
- Affected: source coverage check; `gen-cron.sh` validation, entity grouping,
  emission and reconciliation; configuration written by `zfs-backup.sh`.
- Evidence: `coverage_conflicts()` compares LOCAL owned paths and includes
  REQUESTED_DATASETS only for RUX_MODE=local. `pull_check()` requires a local
  path; both validate_transfer_semantics and emit_send invoke it.
- Failure mode: different hosts with identical dataset names conflict, aliases
  bypass duplicate detection, or a no-copy job is emitted as an ordinary pull.
- Required outcome: record mode must be carried explicitly into generated
  configuration/entities, not inferred from missing fields. Check overlap by
  enrolled source identity plus dataset scope on this collector, including
  recursive parent/child overlap and later add-source edits. Different source
  hosts may use identical paths; different collectors remain allowed. Refuse
  malformed/unreadable relevant records instead of treating them as no overlap.
  Bypass local target checks only for explicit snaponly. Include mode and SSH
  identity in grouping/reconcile identity so ordinary pulls cannot coalesce
  with snaponly. Emit -s, source, prefix, recursion, label and applicable
  supported snapshot/quiesce/SSH options; no destination or transfer flags.
  Reject incompatible policy rather than silently discarding it.
- Verification: duplicate source, recursive overlaps, same path on different
  sources, existing peer aliases, malformed record, add-source, grouping with
  normal pull, golden cron and reconcile tests. Golden checks the whole job,
  not merely the presence of -s.
- Assumption: existing enrolled peer identity is reused; no network-wide
  collector registry or VM discovery is requested.

## F3 — Source retention is the destructive boundary

- Severity: P1; Blocking: yes.
- Affected: source policy generation and existing delsnaps invocation.
- Evidence: existing append_source_prune_create carries recursion, pinned SSH
  and pair_label; delsnaps destroy_one uses ordinary destroy by default but -F
  selects destroy -R and can destroy dependent clones.
- Failure mode: a broad family or scope deletes another relationship's recovery
  points; clear-cut deletes dependent VM/CT clones; missing retention fills A.
- Required outcome: creation, pruning and monitoring agree on source scope and
  owned family. Separate collectors' prefixes must actually be disjoint,
  including prefix matching (one family must not subsume another). Never use
  an empty/any-snapshot retention pattern or Proxmox-reserved families. Use the
  existing approved source retention and delegated/pinned SSH checks, honour
  pause/disable, and emit no target prune. Do not introduce automatic -F,
  recursive destruction of dependents, hold release or permission widening.
  Failure to prune is visible; an unsuccessful snapshot must not be represented
  as fresh. Preserve existing retention semantics rather than inventing a
  new coupling between independently scheduled create/prune jobs.
- Verification: dry-run then disposable lab dataset with this relation's old
  and fresh snapshots, another collector's family, __replicate_*, vzdump and a
  held/clone-dependent point: only eligible owned snapshots are removed, and
  protected/dependent objects survive. Check recursive children and delegated
  account failures. Confirm source prune exists and no B dataset is created.
- Assumption: preserving selected snapshots consumes space on A; the existing
  source/pool capacity monitoring remains operational. Snapshot creation itself
  does not overwrite the live dataset, but retained blocks can exhaust a pool.

## F4 — Remote monitor must preserve failures, not just output

- Severity: P1; Blocking: yes, condition of frozen authorisation.
- Affected: `check-snap-age.sh` parsing, ZFS read boundary, recursion and result
  aggregation; generator's remote-monitor validation and grouping.
- Evidence: check_one reads snapshots through `done < <(zfs list ...)`; the
  recursive main loop uses the same construction. Producer failure does not
  reach the loop status. A successful existence probe followed by a failed
  snapshot list could fall back to dataset creation age, or skip an empty
  discovered subtree. That is unsafe as the remote-read implementation.
- Required outcome: reuse the existing SSH option meanings -p/-k/-c/-K/-O,
  pinned host identity and enrolled key/gate. All reads (existence, snapshots,
  creation, recursive enumeration) use the chosen host; never fall back locally.
  Capture and check each command's status explicitly before consuming its
  output, including partial output with nonzero status. Transport/auth/gate
  failure, timeout, unavailable remote zfs and invalid output yield UNKNOWN,
  never empty-success, dataset-age fallback or silent recursion omission.
  Use bounded noninteractive SSH with stdin detached, safe argument quoting
  and no evaluation of received data. Read-only means list/get only: no
  snapshot/destroy/hold/rollback/receive or remote script installation.
- Preserve current local CLI, pause wording, prefix/exclusions, thresholds and
  severity order (CRITICAL > UNKNOWN > WARNING > OK). In a mixed result,
  every UNKNOWN remains in diagnostics even when CRITICAL determines rc.
  Preserve no-match dataset-age semantics only after successful reads; a
  missing explicit dataset is UNKNOWN. Use each dataset's own family, not the
  newest snapshot anywhere in a subtree. No opportunistic refactor of engines.
- Generator must remove the remote rejection only for supported remote mode,
  propagate complete SSH identity to all monitors, and include it and the
  remote endpoint in grouping. Current MONITOR_GROUPS key has no SSH field.
- Verification: fake SSH OK/stale/no-match, absent dataset, denial, disconnect,
  timeout, failure after successful probe, partial stdout plus failure,
  recursive enumeration failure and malformed epoch; multiple endpoints/keys;
  quotes/metacharacters; assert no mutations. Run existing monitor regressions,
  generator goldens and required impact suites; provide negative controls.
- Uncertainty: existing pairing gate is an active/disabled gate and passes
  active commands through; it must not be described as a new dataset-command
  sandbox. This change must not broaden it or the account's grants.

## F5 — End-to-end alarm evidence and precise protection claim

- Severity: P1; Blocking: yes, production acceptance condition.
- Affected: generator schedules, monitor notifications, design wording/lab.
- Evidence: design says incoming pvesr recv -F removes tool snapshots after
  migration. A snapshot-age check samples existence/freshness, not VM location.
- Required outcome: use matching relation-specific prefix and actual profile
  cadence, with warn/crit allowing the longest scheduled gap. Default generated
  snapshot minutes remain outside multiples of five after tier staggering and
  hour wrap; explicit admin override remains allowed. This reduces collisions,
  but does not promise exclusion while a pvesr cycle runs for multiple minutes.
- Verification: existing proposed CLI/cron/source-snapshot/no-B-copy lab, plus
  stop snapshot job and observe real alert delivery at the normal threshold;
  connection/gate failure delivers monitor BROKEN. Exercise a real migration
  with the intended monitor/pvesr schedules and observe the alert. Include the
  ordering where a new snapshot on the old node is sampled before pvesr removes
  it: do not claim all monitor timings necessarily detect migration. Document
  the measured timing limitation without adding VM-location detection.
- Explicit limitation: the alarm detects stale/missing snapshots or a broken
  read; it does not prevent migration, recover snapshots removed by recv -F,
  or prove that A is currently the active VM node. While B is down, its own
  monitor cannot send alerts either. These are scope facts, not a request to
  reopen the owner's architecture.

## Source data safety conclusion

No inherent live-data overwrite path is required by this design: snapget -s
creates snapshots and the remote monitor only reads. The principal destructive
operation is deliberate source snapshot retention; F3 bounds it to the owned
history and preserves dependent live datasets. Remaining operational risks are
pool space retained by snapshots, temporary pvesr contention, and loss of local
snapshot history after migration/recv -F. The age alarm reports a condition;
it does not protect or restore the deleted points. No independent copy exists
on B in this mode. Chained passive collection remains separately unvalidated.

### F4.1 — P1 blocking: returned names can become remote shell commands

- Affected: `check-snap-age.sh`, `zread()` (lines 338–349), snapshot parsing
  in `check_one()` (428–442), recursive child parsing (523–530).
- Evidence: only CLI dataset entries are validated by the name regex.
  A returned snapshot is checked only for the `<dataset>@` prefix; a returned
  child only for `<dataset>/`. Both later reach `zread`, which surrounds the
  name with literal single quotes without escaping embedded quotes. The
  comment that all names were validated is therefore false for read-back data.
- Reproduced: an SSH/ZFS stub returns
  `tank/vm@automated_'; printf executed > '<temporary marker>'; #` from the
  snapshot-list read. It passes both prefix checks. The following creation
  read executes the injected printf in the simulated REMOTE shell, creates
  the marker, and the monitor returns OK / rc 0.
- Scope/uncertainty: this is a synthetic malformed remote response, not a
  claim that ordinary ZFS produces illegal snapshot names or that a live host
  was attacked. Execution is on the source under the selected SSH account,
  not on the collector. Nonetheless F4 explicitly treats received data as
  untrusted and promises a read-only mode: output must never supply shell code.
- Required outcome: validate every returned snapshot/descendant before any
  follow-up call, and make remote argument serialization safe for every string
  accepted by the read boundary. Malformed names are UNKNOWN. Do not execute
  or evaluate output. Keep valid local/remote datasets and pause semantics.
- Required tests: matching-prefix malformed snapshots AND descendants with a
  quote, command separator and command substitution; assert UNKNOWN and no
  marker/unexpected command. Pair with valid-name controls. The tests must
  fail on the submitted implementation, not only inspect source text.

### F4.2 — P1 blocking: an empty successful recursive read can report OK

- Affected: `check-snap-age.sh`, recursive main loop (515–531).
- Evidence: only the return code and prefixes of nonempty lines are checked.
  A successful `zfs list -r -t filesystem,volume <root>` must contain the
  already-probed filesystem/volume root. An empty answer is not a valid
  complete walk, but passes without any finding.
- Reproduced: existence probe returns `tank/root`; snapshot list succeeds
  empty (allowed for the container); recursive list succeeds with no output.
  `-R -v root@srcA:tank/root automated_ 2h 4h` prints only
  `SKIP ... no snapshots at all ... likely a container node` and exits 0.
  No child was checked, and no UNKNOWN is recorded. A fresh root snapshot
  would also allow this incomplete walk to paint the subtree green.
- Required outcome: validate recursive-list completeness before accepting the
  walk: empty output or a missing required root is UNKNOWN, even with rc 0.
  Keep CRITICAL > UNKNOWN result aggregation and the legitimate no-snapshot
  container rule for a VALID walk. Do not infer nonexistence from an unreadable
  or malformed listing.
- Required tests: empty rc-0 listing, nonempty listing missing root, valid
  root-only empty container, valid root with stale child, and mixed CRITICAL /
  UNKNOWN. Negative controls against the submitted SHA.
- Uncertainty: this tests a malformed-success channel response, not a normal
  empty subtree (normal root-only output remains a valid positive control).
