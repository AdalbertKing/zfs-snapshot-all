# REV-20260811-098 — local-backup overlap guard does not expand comma-separated CONFIG scopes

Review time: 2026-08-11 00:02 CEST
Reviewed implementation: `a41ba7a686431e48334b2b0e10288ca45a5ffd0d`
Response path: `docs/internal/reviews/responses/REV-20260811-098.md`

## Verdict

**CHANGES REQUIRED — P1 safety contract gap in the REV-097 F2 fix.**

REV-097 F1 and F3 are satisfied by the current implementation: the explicit local source crosses a real/stubbed `zfs list` existence boundary, and the bare `zfs-backup.sh --source=... --target=...` public form reaches the same planner. The additive candidate also correctly copies the installed CONFIG and preserves the existing single-scope job used by the new regression.

However, the new overlap guard is not equivalent to CONFIG v4's actual section grammar.

## Finding — comma-separated `[dataset:]` / `[prune:]` scopes are treated as one path

`config_section_overlap()` extracts the text after `dataset:` / `prune:` and passes it directly to `path_overlaps`:

```bash
owned="${hdr#\[}"; owned="${owned%\]}"; owned="${owned#*:}"
for req in "$@"; do
    path_overlaps "$owned" "$req" && ...
done
```

But this repository explicitly supports comma-separated section scopes. Existing production-facing code already has to split `[prune:a,b,c]` before treating those values as dataset names (`config_datasets()` documents and implements that split), and the comment there records that real configs contain such multi-dataset prune sections.

Therefore a legal existing section such as:

```ini
[prune:rpool/data,rpool/other]
```

is seen by `config_section_overlap()` as the single string `rpool/data,rpool/other`. A new local plan for `--source=rpool/data/...` or a target overlapping either member can fail to match `path_overlaps`, so the planner may accept B even though installed policy A already covers that path. That violates the exact REV-097 F2 requirement: overlap with existing coverage must refuse before slice 2 turns this plan into an installer.

The current `test/localbackup` fixture only exercises one-path section headers, so its 19/19 result does not discriminate this failure mode.

## Required correction — keep it narrow

Do not redesign CONFIG parsing and do not broaden the live campaign.

1. Make `config_section_overlap()` evaluate every comma-separated member of each `[dataset:]` / `[prune:]` header independently, with surrounding whitespace normalized consistently with the existing CONFIG consumers.
2. Add one targeted regression fixture containing a multi-path section, preferably `[prune:rpool/other,rpool/data]`, and prove a requested source or target overlapping the second member refuses.
3. Add a negative/control case proving a genuinely disjoint request beside the same multi-path section still proceeds; this prevents a conservative "any comma means conflict" implementation from passing.
4. Run the dependency-selected cascade and `./test/impact.sh --verify`.

No real ZFS transfer, SSH, seed, or crontab install is required for this finding: the defect is entirely in read-only CONFIG-scope parsing/planning. The existing stubbed `zfs list` boundary remains sufficient for F1.

## Scope / routing

This REV blocks approval of Phase 5 slice 1 / REV-097 F2 and therefore slice 2 installation work that relies on this overlap guard. It does not require changes to the transfer engines.
