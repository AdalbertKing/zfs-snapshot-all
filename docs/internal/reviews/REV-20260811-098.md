# REV-20260811-098 — local-backup overlap guard does not expand comma-separated CONFIG scopes

Review time: 2026-08-11 00:02 CEST
Reviewed implementation: `9b4a6e5a9c4dcd9c0a2f12159872dad9227dd0bd`
Response path: `docs/internal/reviews/responses/REV-20260811-098.md`

## Verdict

**APPROVED.** The submitted correction expands every comma-separated `[dataset:]` / `[prune:]` scope member independently with whitespace normalization before applying `path_overlaps`. The targeted regression exercises the exact former false-negative on the second member of `[prune:rpool/other,rpool/data]`, while a disjoint request beside the same section remains allowed.

The proof is proportionate to the changed behavior: this is read-only CONFIG parsing/planning. No ZFS mutation, SSH, seed, crontab install, UID/grant or host-state boundary changed, so no live-host campaign is required for this finding.

## Verified correction

`config_section_overlap()` now splits the extracted scope on commas, trims each member, skips empty members and evaluates every requested source/target path against each member independently. This matches the existing CONFIG-v4 multi-dataset scope grammar rather than treating the comma-joined scope as one filesystem path.

The regression fixture contains `[prune:rpool/other,rpool/data]` and proves that a request for `rpool/data` — the non-first member — refuses with overlap. The negative control requests the disjoint `rpool/db` / `hdd/disjoint` pair and proves the implementation is not merely refusing every multi-path section.

The dependency graph already routes `zfs-backup.sh` changes to both `zfsbackup` and `localbackup`, and `gen-cron.sh` includes `localbackup`; no missing impact edge was found for this fix.
