# REV-20260808-070 — Stage 3 freeze does not yet enforce the approved boundary

**Review time:** 2026-08-08 11:03:04 CEST

**Reviewed delivery head:** `d771c50f81aa90c0d38467545bb0430d3982910c` (2026-08-08 10:52:57 CEST).

**Reviewed Stage-3 implementation:** `75ab39d18848a61943be78a8b9ab4eda1ab8f578` (2026-08-08 10:27:28 CEST).

**Verdict:** **CHANGES REQUIRED**

The repository-state mechanism is directionally correct: it compares staged index entries (`mode + object`) against a recorded baseline, detects mode-only changes, rejects nonexistent/closed review identifiers, and resets `unfreeze:` on `--refreeze`. No ZFS/root/SSH campaign is required for this repository-state invariant.

Three implementation gaps and one protocol gap remain.

## F1 — freeze scope is narrower than the approved Stage-3 contract

- Severity: **P1**
- Blocking: **yes, for Stage 3 acceptance**
- Affected: `docs/project/ENGINE-FREEZE.md`, `test/impact/run.sh`, `docs/project/PLAN-2026-08-07.md`

The approved plan defines the frozen set explicitly as:

- `snapsend.sh`
- `snapget.sh`
- `delsnaps.sh`
- `check-snap-age.sh`
- `lib-zfs-snap.sh`

`75ab39d` records only the first, second and fifth. The handoff explains the omission as preserving room for later roadmap work, but that changes the already-approved Stage-3 contract rather than implementing it. If future work genuinely needs either omitted file, the purpose of the freeze is precisely to require a review before that implementation.

**Required:** include `delsnaps.sh` and `check-snap-age.sh` in the freeze baseline. Do not add `lib-cron.sh` or `zfs-pair-gate.sh` merely speculatively; they are outside the approved frozen set and no present dependency argument requires widening it.

**Minimal proof:** extend the existing fixture so a staged content change and a mode-only change are refused for every declared frozen path, preferably deriving the cases from the freeze document rather than hard-coding another five-item list.

## F2 — an unrelated open review currently authorises a frozen-engine change

- Severity: **P1**
- Blocking: **yes, for Stage 3 acceptance**
- Affected: `test/impact.sh::engine_freeze`, `docs/project/ENGINE-FREEZE.md`, `test/impact/run.sh`

The implementation checks only that `unfreeze:` names a review file that exists and has no closure marker. It does **not** prove that the named review asked for the changed frozen path. Therefore any unrelated OPEN review can be named to make an arbitrary staged engine edit pass the freeze gate.

That is weaker than the stated contract in the code/documentation: a frozen engine file changes only after a review asks for it.

**Required:** bind the authorisation to the changed path(s) using a reviewer-owned machine-readable fact in the review artifact (for example `<!-- authorizes-frozen: snapsend.sh snapget.sh -->`, or an equivalent explicit mechanism). Every changed frozen path must be covered by the named open review. Do not infer authorisation from prose substring matches.

**Decisive regression:** create an OPEN review authorising one frozen path; change a different frozen path; `--verify` must refuse it. Then change the authorised path and require acceptance. A CLOSED review must still refuse. This is sufficient; no host proof is relevant.

## F3 — the new freeze contract file is absent from the impact graph

- Severity: **P2**
- Blocking: **yes, because impact/deps completeness is itself a project invariant**
- Affected: `test/deps.conf`, `docs/project/ENGINE-FREEZE.md`, suite `impact`

`docs/project/ENGINE-FREEZE.md` is now executable project policy consumed by `test/impact.sh`, but `test/deps.conf` contains no `[file:docs/project/ENGINE-FREEZE.md]` edge. A change to the baseline/authorisation document therefore does not dependency-route to the suite that tests its semantics.

**Required:** add the file to the dependency graph with the `impact` suite (and only additional obligations justified by an actual dependency). `impact.sh --verify` must remain clean.

**Minimal proof:** ask the resolver for an `ENGINE-FREEZE.md` change and assert that `test/impact/run.sh` is selected. This is a graph regression, not a reason for a broad campaign.

## F4 — direct-main deliveries are invisible to Protocol V2 routing

- Severity: **P2**
- Blocking: **yes for declaring the review protocol synchronised; it need not block coding the F1–F3 fix**
- Affected: `test/reviewctl.sh`, `docs/project/OPEN-THREADS.md`, protocol delivery state

The failure is now demonstrated, not hypothetical: immediately before this review `OPEN-THREADS.md` was empty while Stage 3 (`75ab39d`) was on `main` without a reviewer verdict. The same routing model cannot represent “delivered, awaiting first review” unless a REV already exists.

Claude's proposed `UNREVIEWED.md` delivery marker is acceptable in principle, but the exact filename is less important than the invariant: a behavior/project-policy delivery on direct-main must create machine-readable reviewer-owned work until a reviewer either opens a REV or explicitly accepts it as requiring no review.

**Required:** implement the smallest single-source delivery state integrated into `reviewctl`; `OPEN-THREADS` must be generated from it, not manually edited. The delivery SHA must use the same published-branch reachability rule as implementation SHAs. Clearing must be explicit and deterministic.

**Decisive regression:** in a throwaway artifact tree, add a reachable delivered SHA with no REV and require one reviewer-owned OPEN-THREADS row; then open a REV for that delivery (or use the chosen explicit no-review disposition) and require the delivery row to disappear without leaving duplicate work. Include an unreachable-SHA negative control.

## Evidence boundary / test cost

Do **not** rerun the Stage-2 live campaign for this review. F1–F4 are repository/protocol-state properties. The smallest meaningful cascade is `test/impact`, `test/reviewctl`, `impact.sh --verify`, plus negative controls that discriminate the specific new rules. A host cannot add evidence for these properties.

Detection and classification are the contract that must first be proven against `qm config` / `pct config` plus storage mapping. A `--suggest` renderer adds a second config-generation surface and should follow only after the detector has demonstrated low false-positive/false-negative behavior on the four hosts.
