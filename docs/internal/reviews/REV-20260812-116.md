# REV-20260812-116 — Phase 7 planner map: live GUID evidence is asserted, not independently auditable

Date: 2026-08-12

Severity: P1 evidence gap
Routing: Claude

## Scope reviewed

Delivery `306cdba58628b49e2e4d203a80360b487facb154` extends `restore --plan` so the planner emits `{dataset -> snapshot, guid, creation, consistency}`. The code change is narrow and the targeted regression tests are directionally strong: GUID is read in the same `zfs list` call and the CONFIG-vs-snapshot trap correctly discriminates INDEPENDENT from ATOMIC without inferring from matching names.

## F1 — the new environment-dependent GUID read lacks independently verifiable live-host evidence

The implementation now depends on this exact OpenZFS interface:

```text
zfs list -H -p -t snapshot -o name,creation,guid -s creation -d 1 <dataset>
```

The stubbed `test/restore` proves parsing and control flow, but it cannot prove that the deployed OpenZFS version exposes `guid` through that exact `zfs list -o` shape, with the expected tab-separated field order and usable values. The commit message says this was verified live on zfs-2.1.9 and that a real pve2 planner run showed GUIDs, but no raw transcript/evidence artifact for that new dependency is present in the reviewed tree. Under the review contract, an implementer claim is not independent evidence.

This is intentionally an evidence-only finding unless the live command disproves the assumption.

## Minimal required proof

Do **not** run a broad campaign. Provide a compact, durable transcript from a real project host using the actual installed ZFS identity/context that shows:

1. `zfs --version` (or equivalent version identity);
2. one real dataset with at least one snapshot;
3. the exact `zfs list -H -p -t snapshot -o name,creation,guid -s creation -d 1 <dataset>` command and raw output demonstrating three fields and a non-empty GUID;
4. the corresponding `zfs-backup.sh restore --plan ...` output for that relationship showing the same snapshot GUID;
5. one negative/control observation sufficient to show the parser is not fabricating a GUID (for example a second snapshot with a different GUID, or direct comparison of the planner GUID to the exact row returned by `zfs list`).

Store that evidence in the response or a referenced durable evidence file. If the exact command fails on the real host, fix only the selector/output shape required by the real interface and add the smallest regression assertion that would fail on the old shape.

No real crontab, SSH/grant, restore write, or full suite is required for this finding: this boundary is a read-only ZFS property lookup.

## Verdict

CHANGES REQUIRED only because the new live dependency is not yet independently auditable. Product logic is otherwise not rejected by this review.
