# REV-20260810-095 — Phase 4 preset selection is not yet proved through the real first-activation boundary

Review time: 2026-08-10 20:12 CEST
Reviewed implementation: `9074fe5543fa1077aa871b135c721232a2cdf0b5`

## Verdict

**CHANGES REQUIRED — production wiring looks correct by inspection, but Gate 4 evidence stops one boundary too early.**

The Phase 4 slice adds the right small surface: `add-client --profile=NAME`, early profile validation, storing the CREATE-time choice, and applying it only for a genuinely new relationship. Re-activation deliberately ignores the stored profile, preserving the one-way handoff established by Phase 3.

I do not currently find a production-code defect in the `9074fe5` diff.

The remaining problem is the proof. `test/zfsbackup/run.sh` section 53 tests `cmd_add_client()` for validation/storage, then unit-tests `apply_client_profile_choice()` directly. It never crosses the real `cmd_activate_client()` first-activation path and therefore never proves the property Gate 4 actually exposes to the operator:

```text
add-client --profile=ALT
        -> stored CREATE-time choice
        -> real first activate-client
        -> ALT profile is the policy source for the candidate CONFIG
        -> rendered cron reflects ALT semantics
        -> install preview/transaction boundary is the existing one
```

That distinction matters in this repository. REV-089/090 already demonstrated that helper-level evidence can be green while the caller still loads or mutates policy incorrectly. The same lesson applies here: if the property is "the selected preset actually drives first activation", the discriminating test must cross `cmd_activate_client()` rather than only test the setter helper.

## Required outcome

Keep the current reduction-oriented implementation. Do not add a profile manager, second runtime policy field, or new preview framework.

Add one focused automated proof using the real `cmd_activate_client()` boundary with deterministic fixtures:

1. Build a valid alternate profile whose semantics are observably different from `default` (for example a unique namespaced template/prefix/schedule value that is safe to render).
2. Build a first-activation client fixture with `PROFILE=<alt>` and the minimum existing manifest/key/config fixtures needed by the current `cmd_activate_client()` harness pattern.
3. Run the real first-activation path (`STATE=endpoint_verified`, `--yes` or equivalent test-safe invocation).
4. Prove the resulting candidate/installed CONFIG and rendered cron contain the alternate profile's semantic marker, not the default profile's value.
5. Prove the omitted `--profile` path still resolves to the existing default semantics.
6. Reuse the existing Phase-3 reactivation assertions rather than duplicating a new drift framework; it is sufficient to show this new test does not weaken the rule that reactivation ignores profile state.
7. Include a meaningful negative control: the test must fail if the first-activation wiring from stored `PROFILE` to `PROFILE_ACTIVE` is removed/bypassed. A temporary test mutation or control against the pre-Phase-4 implementation is acceptable.
8. Run the focused `zfsbackup` suite, dependency-selected cascade, and `./test/impact.sh --verify` with actual exit status.

## Live-host requirement

No new live ZFS/SSH campaign is required merely for this finding if the real `cmd_activate_client()` composition can be exercised deterministically with the same fixture/stub strategy already used elsewhere in `test/zfsbackup`.

The existing `zfsbackup-live-pair` manual obligation may remain as a broader deployment obligation, but it is not necessary to prove this specific profile-selection wiring unless the implementation changes pairing, host state, or installation semantics.
