# REV-20261021-160 — browse snapdev holder/restore key collision across distinct ZFS datasets

Reviewer: ChatGPT. Date: 2026-10-21.
Published `main` inspected: `ffa6bc1a05cc1d19a06664114c456b8e5c9f1cb6`.
Affected: `tui/browse.sh`, blob `b3f6c598638f3f3e6075d8f2f594312200ab2f9c`; `hold_key()`, `other_holders()`, `expose_snapdev()`, `restore_snapdev()`. Follows **REV-159**, whose independently submitted F1/F2 cleanup fixes are accepted separately; this is a new, distinct namespace-integrity failure.

## F1 — P1: lossy dataset-to-record mapping mixes original snapdev state between volumes

```bash
hold_key() { printf '%s' "$1" | tr '/@' '__'; }
```

This mapping is **not one-to-one** because dataset underscores are legal and `/` becomes the same `_`. Both of these legal, distinct paths are possible *within the same ZFS pool*:

```text
tank/a_b   -> tank_a_b
tank/a/b   -> tank_a_b
```

The reviewer independently ran the exact shell expression with both values and confirmed identical results. This is an isolated identity-key reproduction; an end-to-end live ZFS collision was not attempted.

The shared key is then used for:
- `$BROOT/orig.$key` (original snapdev value **and its inheritance source**);
- `$BROOT/hold.$pid.$key` (concurrent session ownership).

### Concrete failure scenario

1. Browse of **dataset A** (`tank/a_b`, initially `snapdev=hidden`) creates `orig.tank_a_b` and hold A, then sets A visible.
2. Browse of **different dataset B** (`tank/a/b`, initially `snapdev=visible`) sees the same `orig.tank_a_b`. It does **not read B's original property**, treats A's record as its own, creates hold B and sets B visible.
3. A exits first. `other_holders(A)` observes B under the collided key, so A **skips restoring A**.
4. B exits last. It restores **B** from **A's** original record, setting B hidden even though B was originally visible; A can remain visible. The shared original record is removed.

That violates the specific property-state preservation and multi-session assumptions in the browse path. A prior failed restoration for A can likewise poison a later browse of B. It can leave a VM snapshot device exposed or hide another VM's device without an honest per-dataset recovery record.

### Required correction and acceptance

- [ ] Replace `hold_key` with a collision-free, deterministic, filesystem-safe representation of the **full exact dataset name** (e.g. reversible escape of `/` and `_` or bounded cryptographic digest with collision-handling). Do not use lossy `tr`.
- [ ] Tag persistent origin metadata with the **exact dataset identity** and refuse reuse if it does not match; preserve exact original value and source. No other dataset may consume or remove its record.
- [ ] A and B above must get distinct origin files and holder namespaces. End-to-end actual-entry-point fake-ZFS test should verify independent `hidden/local` and `visible/local` original values, cross-dataset interleaved sessions, cleanup in both finish orders, and no spurious `zfs inherit` or snapdev mutation on the wrong dataset.
- [ ] Regression negative control on blob `b3f6c598...` must prove the old collision in a *harmless stubbed environment*, not on a live VM.
- [ ] A crash/retry with legacy `orig.tank_a_b` files must be handled **fail-closed**, without guessing which of the colliding datasets owned the legacy record and without silently erasing evidence.
- [ ] Preserve REV-159 cleanup/residue reporting and same-dataset concurrent-holder behavior. Run focused `test/browse`, `test/tui`, impact verification, and CI.

**Blocking:** P1 for exposing/browsing distinct zvol datasets concurrently on production. No current evidence of an observed production leak. No destructive ZFS or live mounted volume was touched in this review.
