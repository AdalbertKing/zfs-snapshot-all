# REV-20260907-135 — idempotent close accepts damaged derived review state

Review date: 2026-09-07
Reviewer: ChatGPT
Reviewed delivery: `cf668df5486342ad9c3604cef801ff668c3b5ce6`
Canonical descendant checked: `e9a97bbed1eacf313e333563b787de2e62fc573f`

## Verdict

**CHANGES REQUIRED — P2: replaying an already-published `reviewctl close`
returns success before regenerating or verifying the ledger and routing view.**

The transactional writers, including the fixes already approved under
REV-20260829-125, are otherwise not rejected by this review. The remaining
defect is the closure replay path: it is weaker than the equivalent approval
replay and can bless a damaged derived state with exit status zero.

## F1 — P2 BLOCKING — closure replay returns before checking derived views

- Severity: P2
- Blocking: yes
- Affected: `tx_close()` in `test/reviewctl.sh` and the focused controls in
  `test/reviewctl/run.sh`.

### Evidence

`tx_approve()` treats an idempotent replay as a transaction: it snapshots the
derived views, regenerates and verifies them, reconfirms the publication parent,
and only then returns success. `tx_close()` instead contains an early return:

```sh
if [ -f "$cfile" ] && [ "$(hdr "$cfile" closed-by)" = "$acommit" ]; then
    echo "reviewctl: $rev is already closed by $acommit -- nothing to do"
    return 0
fi
```

That branch does not guard, regenerate, verify, or reconfirm the derived state.
The suite has a discriminating replay-repair test for approval, but no symmetric
test for closure.

Reviewer-only reproduction on fresh canonical `main` copied the current review
artifacts to a throwaway directory, appended `TAMPERED` to
`REVIEW_LEDGER.md`, and replayed the real published closure of REV-20260904-134:

```sh
REVIEWCTL_REPO="$W" REVIEWCTL_PUBREF=HEAD ./test/reviewctl.sh close \
  REV-20260904-134 \
  --approval-commit=9bd319775b1a881d8a3c096cf5f3216eb060e653 \
  --expected-parent=e9a97bbed1eacf313e333563b787de2e62fc573f
```

Observed:

```text
rc=0
reviewctl: REV-20260904-134 is already closed by 9bd319775b1a881d8a3c096cf5f3216eb060e653 -- nothing to do
last ledger line: TAMPERED
```

The canonical review and closure facts were valid and unchanged; only the
generated view was damaged. A successful replay therefore claims a healthy
publication while leaving the routing/ledger representation inconsistent.

### Failure mode and impact

After a partial manual edit, merge conflict, or interrupted publication damages
one generated review view, an operator can safely replay `approve` to repair and
verify it. Replaying the matching `close` appears equally successful but does
nothing. Downstream automation reads these generated files, so a zero exit can
leave a review missing, duplicated, or incorrectly routed until a separate
explicit verification is run.

This does not change backup or ZFS data. It is a review-protocol integrity fault,
which is why the severity is P2 rather than a product-data P1.

### Acceptance criteria

1. An idempotent `close` replay must not return before validating the state it
   reports as successful. Guard `REVIEW_LEDGER.md` and `OPEN-THREADS.md`,
   regenerate and verify both, and reconfirm `--expected-parent`, mirroring the
   already-correct approval replay semantics.
2. If either derived view was changed but canonical facts remain valid, the
   replay must repair it and finish with both `reviewctl --verify` and the
   expected-parent check passing.
3. If regeneration or verification fails, the transaction must return nonzero
   and restore every guarded byte under the existing rollback guarantees.
4. Add a focused closure-replay control symmetric to the approval replay test:
   damage at least one derived view after a successful close, replay the same
   close, assert that the damage is gone, and run `--verify`. The control must
   fail against `e9a97bbed1eacf313e333563b787de2e62fc573f` for the reason shown
   above.
5. Preserve the existing proof that the named approval commit carried APPROVED
   for the response's current implementation and preserve the rule that a
   different existing closure is never overwritten.

### Required verification

- `bash test/reviewctl/run.sh` including the discriminating replay control;
- `./test/impact.sh --verify`;
- exact-head CI.

No ZFS, fleet, GUI, or full product campaign is required: the defect is fully
decided in a throwaway review-artifact directory with the real writer.
