# REV-20260812-111 — managed source retention can strand a relationship without bookmark insurance

## Finding

The real-ZFS continuity campaign that closes REV-102 proved an important operational boundary that was not previously demonstrated.

Managed SOURCE retention is safe for TARGET history, but continuity is not self-healing once the last ordinary common snapshot is aged out. The campaign shows two concrete configurations with no usable bookmark insurance:

1. a non-recursive delegated relationship whose account lacks the `bookmark` permission: the transfer still returns rc=0 and only emits a non-fatal bookmark warning; once source retention removes the ordinary common base, subsequent transfers explicitly refuse and the relationship stops until a human intervenes;
2. an atomic recursive `-r` relationship: the engine deliberately creates/consults no bookmarks for this mode, so after source retention removes the last ordinary common base the relationship likewise refuses permanently until manual recovery.

This is not a silent data-loss bug: REV-102 proves TARGET history is preserved and the failure is explicit. It is nevertheless a P1 operational-resilience defect in the high-level managed-backup contract. The package now automatically owns and enforces bounded SOURCE retention, so it must not knowingly create a default relationship whose continuity insurance is absent while presenting activation as successful.

For a destination outage longer than the source-retention horizon, this state is predictable rather than exceptional: the source cleanup can legally age out the last common snapshot, after which the backup relationship stops and requires destructive/manual recovery (`-f` or equivalent operator action).

## Required correction

Keep the solution small and at the high-level orchestration layer. Do not invent a new ownership model and do not modify frozen transfer engines unless unavoidable.

### A. Relationships that can use bookmarks

When managed SOURCE retention is enabled and continuity relies on bookmark fallback, activation/migration must verify that the production transfer identity can actually create/refresh the required bookmark. A warning after an otherwise successful transfer is not sufficient for a newly activated managed relationship.

Reuse the existing grant-verification style used for `destroy`; do not widen permissions automatically. If the required bookmark capability is absent, fail closed with a precise operator message before installing/activating source retention.

Passive `snapget -e` remains outside package SOURCE-retention ownership and must not be pulled into this rule.

### B. Atomic recursive `-r`

The measured engine semantics show that `-r` has no bookmark insurance at all. Therefore managed SOURCE retention plus `-r` needs an explicit high-level policy instead of relying on eventual runtime refusal.

Claude should choose the smallest safe option after checking the existing recursion contract:

- prefer an already-supported recursive mode that preserves the required relationship semantics and has usable bookmark insurance (the campaign measured flat `-R` bookmarks), **or**
- refuse activation/migration of managed SOURCE retention for the unsupported `-r` combination with a clear reason.

Do not add a background keeper, hidden anchor snapshot, automatic destructive reseed, or new framework merely to preserve `-r`.

If `-R` changes required atomic/recursive semantics, do not substitute it silently; use the hard-refuse option instead.

## Minimum discriminating evidence

Use the smallest evidence set that proves the orchestration contract:

1. **bookmark-capable managed relationship:** activation succeeds when the delegated production identity has the needed bookmark capability;
2. **negative control:** same relationship without bookmark capability is rejected before managed SOURCE retention is installed/activated, and existing CONFIG remains unchanged;
3. **passive `-e` control:** remains accepted without a bookmark/source-retention grant requirement;
4. **recursive `-r` control:** prove the selected policy — either the high-level configuration no longer emits the unsafe managed-retention + `-r` combination, or activation refuses it deterministically;
5. if choosing `-R`, add one targetted runtime proof that its bookmark-backed continuity actually preserves the intended recursive coverage/semantics. If choosing hard-refuse for `-r`, no new destructive live campaign is needed beyond the already-recorded REV-102 evidence.

During iteration use targeted L0 tests around activation/grant/recursion composition. Run dependency-driven affected suites once on resubmission. Do not run a broad campaign merely because this finding is P1.

## Interaction with REV-102

REV-102 is CLOSED by the real-ZFS evidence at `b9fcd402594ed2e989b773f437b513c4e759d8e2`: its acceptance property was safety and explicit behaviour after base loss, and that property is proven.

REV-111 is a separate follow-up about preventing a predictable managed-backup outage at activation/configuration time. It must not reopen accepted REV-102 source-retention implementation, F3/F4/F5, passive ownership, or the already-proven TARGET-preservation behaviour.
