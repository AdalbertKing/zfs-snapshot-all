# REV-20260812-111 — managed source retention can strand a relationship without bookmark insurance

## Finding

The real-ZFS continuity campaign that closed REV-102 proved two predictable outage modes for managed SOURCE retention: a delegated non-recursive relationship without `bookmark`, and atomic recursive `-r`, which deliberately has no bookmark fallback. TARGET history remains safe, but once ordinary common-base snapshots age out, either relationship can stop until manual recovery.

## Required correction

Keep the correction at the high-level orchestration layer. For managed SOURCE retention, verify bookmark capability without widening grants; passive `snapget -e` remains outside package SOURCE-retention ownership. For atomic `-r`, either use an already-supported bookmark-backed recursive mode only if semantics are preserved, or refuse the unsafe combination explicitly rather than silently changing transfer semantics.

## Independent verification of implementation

Reviewed implementation: `58c1cfea756b998f4f7d4bd1f50e1319ba89f682`, with part A introduced at `5e28f5f6a503c7b8ee0727482484e3a32ea25b3c`.

Part A is correct and narrow: `assert_source_prune_grant()` now verifies `bookmark` alongside `destroy` from the same `zfs allow` result on the production transfer identity, without another SSH round trip and without widening permissions. The discriminating control differs only by the missing bookmark capability and fails closed before installation. Existing deploy scope already grants bookmark, and the submitted live read-only sweep confirms compatibility on the real estate while preserving a deliberately negative lab dataset.

Part B is also correct and narrow: `assert_no_atomic_with_source_retention()` reads the candidate CONFIG and refuses `recursive = atomic` before managed source retention can be installed through activate-client, migrate-profile, or the narrow audit `--apply` path. It deliberately does not rewrite atomic to flat because their ordering/crash semantics differ. The regression includes the important negative control: `recursive = flat` must continue to pass, so the guard is not merely rejecting all recursion.

The response reports the dependency-driven affected suites on pve1 (`test/zfsbackup` 401/401 and `test/localbackup` 42/42). No new destructive live campaign is required for part B because the runtime property that atomic `-r` has no bookmark continuity and fails after base loss was already measured in the accepted REV-102 campaign; this change is an orchestration refusal built directly on that measured property.

The remaining risk named by the implementer — an administrator hand-editing an already installed CONFIG to atomic after source retention was installed — is outside this finding's activation/migration/install contract and is not newly introduced by the patch. CONFIG is runtime truth and is not continuously revalidated. It does not justify extending REV-111 or adding a background checker.
