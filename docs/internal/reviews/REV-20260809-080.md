# REV-20260809-080 — `reviewctl` accepts abbreviated commit IDs, then silently compares them as unequal strings

Review time: 2026-08-09 02:18 CEST
Reviewed implementation: `f497f25a6d6bf26982b39cad9aff829e00aa0f88`

## Original verdict

**CHANGES REQUIRED.**

This is an independent REVIEW PROTOCOL V2 correctness defect found while closing REV-078. It is not a B1/profile finding and does not touch production backup engines.

## F1 — P1 — a valid abbreviated SHA passes validation but can park a thread in the wrong state with rc=0

The failure happened on REV-078, not only in a synthetic example.

Claude's response originally carried:

```text
<!-- implementation: dc1c038 -->
```

while the reviewer approval correctly carried the full commit:

```text
<!-- reviewed-implementation: dc1c038e262fb4a5965e3161a79f916b510b9d76 -->
```

`reviewctl` accepted the abbreviated response commit because `require_commit()` asks Git whether `${sha}^{commit}` resolves and is reachable. Git accepts an unambiguous abbreviation.

Later, however, `state_of_raw()` does not compare commit identity. It compares the two header strings literally:

```bash
[ "$ri" = "$im" ]
```

Therefore the same commit expressed once as a full SHA and once as an abbreviation is treated as two different submissions. REV-078 remained `IMPLEMENTED` after reviewer approval and advanced to `APPROVED` only after commit `7a2febc034f3e0b3341370d52631f5b40145681f` rewrote the response header to the full 40-character SHA.

The dangerous property is **fail-quiet**: the generator returned a normal derived state rather than reporting malformed/noncanonical machine facts. A human looking only at `OPEN-THREADS` was routed back to the reviewer even though the reviewer had already approved the exact submitted commit.

## Required correction

Commit-bearing protocol facts must have one canonical identity before any equality decision.

Preferred contract for durable review artifacts:

1. `reviewed-implementation`, `implementation`, `closed-by`, `delivered`, `reviewed-by` and `no-review-required` commit identifiers must be the full 40-character lowercase hexadecimal object ID when they name a commit; `-` remains legal where the protocol explicitly permits it.
2. `reviewctl` must reject an abbreviated/noncanonical commit-bearing header **explicitly and non-zero**, naming the REV/delivery, field and supplied value. Do not allow it through reachability validation and later reinterpret it as a different commit by string comparison.
3. If implementation instead chooses canonicalisation rather than rejection, every commit-bearing value must be resolved to the same full object ID **before it is stored/compared/rendered**, and ambiguity/unresolvability must fail closed. No raw-string equality may decide protocol state after successful commit validation.
4. Use one rule consistently for reviews, responses, closures and delivery bookkeeping. Do not fix only `implementation:` while leaving the same class in `closed-by` or delivery markers.
5. Existing canonical artifacts on `main` must remain valid. The B1 delivery marker has already been rewritten to the full SHA while being marked reviewed.

## Required proof

Add targeted `test/reviewctl/run.sh` cases that discriminate this exact failure mode. No live ZFS/SSH/cron campaign is required.

**Verdict: APPROVED.**

Independent diff inspection confirms the implementation enforces canonical 40-character lowercase hexadecimal commit IDs in `require_commit()` before reachability/state handling, while preserving the explicit `-` sentinel. The same path now covers review/response/closure commit fields and all three delivery bookkeeping forms, including the previously unchecked `no-review-required` and `reviewed-by` markers.

The regression matrix is discriminating rather than merely broad: it first proves that a 7-character abbreviation resolves to the same real commit, then requires the new implementation to reject that representation instead of silently deriving the wrong state. Symmetric reviewed-implementation, closed-by, delivery markers, uppercase/noncanonical input and the canonical happy path are covered. The reported old-code negative control (8 failures, 39 passes) is consistent with the exact delta and is meaningful because the old implementation lacks this canonical-form rule rather than merely lacking the new helper symbol.

No environment-dependent behaviour changed. Live ZFS, crontab, UID/account, SSH or grant proof would add no evidence for this protocol-only parser/state-machine correction. `test/reviewctl` plus dependency-selected impact/verify is the appropriate proof boundary.
