# REV-20261106-189 — replica run ownership fails open when its record cannot be written

Reviewer: ChatGPT. Date: 2026-11-06.

Target: development `main` at `0bbb11bcb9b2981ac7b3dcc39fc24af337406048`
(PR #1104, A11/A13). Release `AdalbertKing/zfsbackup` main remains
`3e3bc5d7db751af484114f08d3c58bb422c352db`; this finding concerns the
new development code. No production host, pool or disk was touched.

## F1 — an unrecorded run can import and a second run can export its pool

- Severity: **P1**.
- Blocking: **yes for publishing the new one-replica-one-run guarantee and for
  release of this change**.
- Affected: `zfs-media-gate.sh`, `attach` run claim and `detach` ownership guard;
  `test/mediagate/run.sh` covers the healthy and live-holder cases but not a
  failed claim write.

### Contract, failure and evidence

A11/A13 introduced `$STATE_DIR/$LABEL.running` to keep another run of the
same replica from importing or exporting the first run's medium. In `attach`,
failure to create or open `$RUNNING.lock` skips the whole guarded block and
continues. Inside the lock, failure to write `$RUNNING` is suppressed with
`|| :`; `attach` again continues. Thus a run can import a pool and return 0
without any run-owner record. A second run then sees no live holder; if the
first run's `imported-by-us` marker matches the pool GUID, the second can treat
that pool as its own and `detach` can export it while the first transfer uses it.

I ran the shipped gate from this exact `main` with the existing mediagate
suite's stub `zpool`/`zfs`, and made `rep.running` a directory: the lock path
was writable, but writing the run record failed (`Is a directory`). `attach`
still returned **0** and imported `rotpool`. A second `attach` returned **0**;
its `detach --engine-rc 75` returned **0** and the stub recorded an export of
`rotpool`. This was an isolated scratch extension of the suite, removed after
the run. Git Bash lacks `flock`, so the scratch fixture supplied a successful
`flock` stub for this write-failure case; the full suite in that environment
had unrelated failures and is **not** claimed as a passing regression. The
observed branch and return statuses are from the real `zfs-media-gate.sh`.

### Required outcome

`attach` must not return permission to copy unless it has exclusively and
durably claimed this replica run. If the lock or claim cannot be created or
verified, report a clear error or skip and leave the medium untouched. A
second run must never be able to export a pool held by the first. Preserve
healthy concurrent-run refusal, stale-holder recovery and the existing
absent-medium behavior.

### Acceptance criteria and verification

- [ ] Fail closed on lock creation/open failure and run-record write/read-back
  failure. Do not proceed to import or report success on those paths.
- [ ] Keep claim and holder checks atomic for two starts, and make `detach`
  unable to export another run's imported pool even if a claim is corrupt or
  missing. Explain the ownership rule used when a run exits early.
- [ ] Add actual-gate regressions for failed lock and failed claim, including
  the second attach/detach consequence; retain healthy overlap, stale holder,
  quiet source and absent medium controls. Include a negative control that
  fails on `0bbb11bc`.
- [ ] Run the relevant media gate, generator and replica suites, shell syntax,
  `git diff --check`, `./test/impact.sh --verify` and exact-head CI. Disclose
  any manual obligation. No production disk or pool test is authorized by
  this review; use a throwaway host only if the changed boundary requires it.

### Review-process note

The new test constructed a readable, writable live-holder record and proved
the second run was refused. It did not inject failures while claiming that
record. For any new lock or ownership marker, future reviews must test both
successful contention and failure to persist the claim, then trace the
cleanup/export path of the next run. Green CI for the healthy lock case does
not establish this safety property.
