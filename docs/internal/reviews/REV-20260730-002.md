## F1 — external rollback controller — CLOSED

`update-control.sh` now contains the self-update, rollback and resume control plane. `deploy.sh` installs a root-private copy at:

```text
/root/.zfs-snapshot-all-update-state/update-control.sh
```

This path is outside `$REPO_DIR`, so `git reset --hard` of the managed checkout cannot revert the code that enforces `update-hold`.

The installed cron line invokes the external wrapper directly. Current `deploy.sh --self-update`, `--rollback` and `--resume-updates` also delegate to the wrapper when it is present; the in-tree implementation remains only as first-deployment bootstrap fallback.

### Verification accepted

The live pve0 test reproduced the exact version boundary that previously failed:

1. current controller deployed outside the checkout;
2. rollback to `feaf0ab`, whose in-tree `deploy.sh` predates the safe state location;
3. scheduled entry point invoked while the old checkout was active;
4. external wrapper observed the hold and left HEAD unchanged;
5. explicit resume through the wrapper removed the hold and advanced deliberately.

The deliberately invoked old `deploy.sh` ignored the new hold and reproduced the original defect, confirming that the external wrapper — not an accidental difference in the fixture — is what closes the gap.

All four hosts were migrated to one wrapper-shaped cron line without duplicate updater jobs.

## F2 — emergency fail-closed control — CLOSED WITH TEST DEBT

When a safety-critical hold write fails, `emergency_disable(reason)` now escalates through independent controls:

1. write the ordinary root-private hold;
2. if that fails, remove execute permission from the external update wrapper;
3. if that fails, remove the cron line invoking that exact wrapper;
4. if every circuit breaker fails, return non-zero with a critical diagnostic.

The affected failure branches now use this escalation:

- rollback-pointer restoration failure after a failed fast-forward;
- rollback reset failure;
- hold restoration failure after a failed explicit resume.

Initial pointer-write failure remains correctly fail-closed before checkout activation. Hold-removal failure remains correctly fail-closed because execution stops while the hold still exists.

### Live defect found and corrected

The first `emergency_disable()` implementation used `$0` as its own path. A sourced test invocation made `$0` equal `bash`, causing the cron fallback to remove an unrelated `SHELL=/bin/bash` line on pve0. The line was restored immediately and the implementation was corrected in `764ddef` to use `${BASH_SOURCE[0]}` through the stable `SELF` variable.

This is accepted because the corrected path was re-tested in isolation, the full suite then passed on every host, and before/after crontab comparisons showed no further unintended modifications.

### Verification accepted

Reported live result on each of the four Linux hosts:

```text
PASS=34 FAIL=0 SKIP=0
```

The live suite exercised real symlinks, POSIX permission bits, immutable-directory write failure, the external-wrapper hold/resume/rollback flow and the emergency wrapper-disable path.

### Non-blocking test debt

The literal eight-item fault-injection matrix requested in `REV-20260730-001` is not complete. In particular, the suite does not independently construct:

- an atomic-rename-only failure distinct from temp-file creation/write failure;
- every individual caller of the shared hold/remove primitives as a separate scenario;
- an explicit update failure after resume combined with a simultaneous failure to restore the hold.

Code inspection shows these paths converge on the tested primitives and `emergency_disable()`, and the live circuit-breaker test verifies the fail-closed mechanism on real Linux. Therefore this is retained as **P2 test coverage debt**, not an open P1 production defect.

Before materially changing `write_state_file()`, `remove_state_file()`, `emergency_disable()`, `do_self_update()`, `do_rollback()` or `do_resume_updates()`, extend the suite with injectable operations or command hooks so the remaining failure combinations can be tested deterministically.

## Operational constraint: external wrapper release step

The hourly updater intentionally updates only the Git checkout. It does not replace the external controller that is currently executing it.

Therefore any future change to `update-control.sh` is not fully deployed merely by pushing it to `main`. Each host must subsequently run:

```sh
bash /root/scripts/zfs-snapshot-all/deploy.sh
```

That full deploy atomically refreshes the copy under `/root/.zfs-snapshot-all-update-state/` and normalizes the cron line. This is an accepted consequence of keeping the rollback controller outside the tree it manages.

At the reviewed state all four hosts have already completed that migration and are reported clean, un-held and on one current updater cron entry.
