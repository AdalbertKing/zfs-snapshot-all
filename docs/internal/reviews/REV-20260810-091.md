# REV-20260810-091 — endpoint-only reactivation still mutates or refuses on non-topology CONFIG policy

Review time: 2026-08-10 08:39 CEST
Reviewed implementation: `e26adc57ab0526a5e3a359de7032c5ecb6522566`
Response path: `docs/internal/reviews/responses/REV-20260810-091.md`

## Verdict

**CHANGES REQUIRED — REV-090 removes the active-profile dependency, but Phase 3's stronger topology-only property still has two residual paths inside `ensure_cron_config()`.**

The REV-090 implementation is directionally correct: when `PLAN_NEEDS_PROFILE=0`, active-profile validation and the profile-template append loop are skipped. However, `ensure_cron_config()` still performs two policy operations unconditionally during an ordinary endpoint-only reactivation:

1. it refuses a pre-GFS installed CONFIG before any topology refresh;
2. it re-adds missing CONFIG-wide `[excluded:]` policy sections.

Phase 3's canonical property is explicit:

```text
endpoint / host / transport change
        -> preserve existing CONFIG policy
        -> change only relationship/topology facts that actually changed
```

Neither behavior below is a topology fact.

## F1 — P1 — pure reactivation can silently re-add CONFIG-wide retention policy

After the new `needs_profile` block ends, `ensure_cron_config()` still always executes the reserved-prefix loop:

```bash
for prefix in "__replicate_" "vzdump" "__migration__"; do
    grep -qF "[excluded:$prefix]" "$file" && continue
    ... append keep = 2 ...
done
```

Therefore `needs_profile=0` does **not** mean topology-only. If an operator deliberately removes one of these CONFIG-wide exclusions from an already-installed native CONFIG, the next endpoint reactivation silently restores it.

The safety floor may be appropriate when creating/initializing policy, but endpoint maintenance is not the boundary at which native CONFIG policy may be repaired or normalized. After handoff, CONFIG v4 is runtime truth.

### Required correction for F1

Gate CONFIG-wide policy scaffolding at a genuine CREATE/migration/additive-policy boundary, just like the profile-template append loop. A pure reactivation that only preserves existing sections and refreshes endpoint facts must not append `[excluded:]` policy.

Minimal regression:

- create a valid active relationship/config through the normal generator;
- deliberately remove an otherwise valid/unneeded `[excluded:]` section;
- perform real endpoint-only reactivation;
- prove it is not re-added and endpoint-owned fields still refresh;
- negative control against `e26adc57...` must show the section is re-added.

## F2 — P1 — pure reactivation still forces migration of a valid pre-GFS installed CONFIG

`ensure_cron_config()` unconditionally runs:

```bash
detect_profile_gfs "$file"
if [ "$PROFILE_GFS" -eq 0 ]; then
    die "... Migrate the host first ..."
fi
```

This happens even when `needs_profile=0` and the operation is an endpoint-only refresh of already-owned sections.

The pre-GFS refusal is correct when an operation is about to **add the current GFS policy on top of legacy policy**, because that could create double pruning. It is not justified when no policy is being generated at all. In that case reactivation can preserve the existing legacy CONFIG and update only `src`/`flags`; forcing `migrate-profile` makes a topology change depend on a policy migration, contrary to Phase 3.

### Required correction for F2

Retain the pre-GFS safety refusal only where the operation would actually generate/add incompatible current-profile policy. Do not require policy migration merely to refresh endpoint topology in an already-valid installed legacy CONFIG.

Minimal regression:

- fixture a valid active pre-GFS CONFIG with owned relationship section(s);
- perform endpoint-only reactivation with no new dataset/section to generate;
- prove `src`/`flags` refresh and the legacy policy remains unchanged;
- negative control against `e26adc57...` must stop at the current pre-GFS refusal.

## Evidence boundary

No live ZFS/SSH campaign is required if the correction stays within deterministic candidate-CONFIG composition. Required: targeted real-`cmd_activate_client()` regressions, negative controls against `e26adc57...`, dependency-selected `zfsbackup`/schema cascade and `./test/impact.sh --verify` with real exit status.

Do not build a general normalization/migration framework. The smallest correct rule is sufficient: **pure topology reactivation does not create, repair, normalize or migrate policy.**
