## Decision and scope

**The design direction is accepted for a bounded implementation in
`snapget.sh`, subject to the contract below.** The marker above authorises
only that frozen file. It is pre-implementation authorisation, not an
APPROVED verdict on code that does not exist. The machine state remains OPEN
until an implementation is submitted and independently verified.

`snapsend.sh`, `lib-zfs-snap.sh`, `delsnaps.sh` and `check-snap-age.sh` remain
outside this authorisation. Existing backup/mirror/receive behaviour must not
be refactored as part of this change. Record the intentional pull-only twin
difference and update only affected twin pins after inspecting the diff.

REV-147's active Restore P1 retains priority. This pre-review does not
authorise deployment, further changes on Metropolis, or skipping the
owner's per-step lab approvals.

### Why this is the smallest useful boundary

The requested new contract is source-side snapshot creation with no receive
side. `create_snapshot()` already supports remote SSH; the main flow already
owns `-L`, identity options, one run suffix, recursion and remote quiesce.
A separate SSH snapshot implementation in the CLI/generator would duplicate
those semantics. An explicit mode in this engine reuses them and removes
the currently inseparable receive phase. The generator and GUI may select
the mode later; their implementation is not approved by this engine review.

Leaving `snapsend.sh` unchanged is justified: its existing no-target mode
already creates local snapshots, while remote source execution is the pull
engine's responsibility. This is a deliberate directional capability, not
permission for the existing twins to drift.

## F1 — P2 blocking acceptance contract — snapshot-only must cover the whole execution path

- Severity: P2
- Blocking: yes, for acceptance of the forthcoming feature
- Affected: `snapget.sh` option validation, dependencies, main quiesce block,
  `process_dataset()`, main result/mirror loop and stats/logging.
- No current implementation of `-s` exists; these are conditions on the
  proposed change, not a claim of a shipped `-s` defect.

### Observations from the current tree

An early `process_dataset()` return is necessary but insufficient:

1. After that function returns success, the main loop still calls
   `mirror_target()` when `MIRROR=1`. Accepting `-s -M` and only returning
   early could therefore delete local snapshots in a no-transfer mode.
2. `adopt_legacy_state()` currently runs at the very start of the function,
   before the proposed insertion point. The new mode must bypass target-side
   state adoption too, not just the pool check and stream planner.
3. The remote quiesce block runs before the per-dataset function. It already
   distinguishes `QUIESCE_SNAPPED=1` from safe degradation. Neither a second
   snapshot nor bypassing the established nonzero degradation result is valid.
4. Mandatory `mbuffer`/compressor checks, remote compression defaults and
   optional autotuning are outside the function. None is needed to take a
   snapshot, and their absence must not prevent a valid `-s` run.
5. The current main result loop emits ordinary copy success and a target
   identity even after a local snapshot-only return. The new remote mode
   must not imply that a backup was transferred or that its collector-side
   copy was refreshed.
6. The proposed `test/snapget` suite does not exist in this tree. Use an
   existing suitable engine harness or explicitly register a small focused
   suite in the dependency graph/CI; do not leave the new tests unselected.

### Required behaviour

1. `snapget -s [user@host:]dataset` accepts exactly the source positional
   argument (including the existing source-list grammar). Reject an extra
   target argument and contradictions `-e`, `-t`, `-M`, `-f` and `-F` before
   any SSH, quiesce or snapshot side effect. Other transfer-only flags must
   have an explicit documented policy; they may not activate transfer work.
2. `-n -s` emits `PLAN=SNAPSHOT-ONLY src=...` for each selected dataset and
   makes no snapshot, quiesce, hold, bookmark, receive, destroy, rollback or
   target-state mutation. Read-only source discovery/SSH may be required for
   `-R` and identity validation; a claim that dry-run invokes literally
   nothing must not hide that distinction. No target probe is allowed.
3. The real `-s` path does source work only: no local target probe, legacy
   target-state adoption, resume operation, hold, stream, mirror cleanup,
   bookmark or progress watcher. It must not require `mbuffer` or a
   compressor, or run transfer autotuning. Existing no-`-s` runs retain their
   dependency and execution contracts.
4. Preserve `-L` pause and the peer's disabled-gate refusal, existing SSH key,
   port/known-host/options handling, source validation and lock exclusion.
   A denied/unreachable source must not yield a success plan for executed
   work. Do not relax existing identity/security guards to make the mode run.
5. Preserve the remote quiesce implementation: a successful freeze/snapshot/
   thaw window supplies the one snapshot set; `QUIESCE_SNAPPED=1` must prevent
   a second snapshot. An explicitly permitted safe degradation creates the
   crash-labelled set and retains the established exit 8; a strict or
   unsafe failure remains nonzero without an unquiesced fallback. A local
   source with requested quiesce must refuse as unsupported by this engine.
6. Preserve the existing recursion grammar: `-r` snapshots atomically;
   `-R` uses the actual discovered/deduplicated selected descendants with one
   run suffix and honours `-X`/`-S`. Source listing failure must not become a
   successful empty or partial snapshot set. Snapshot failure makes the run
   fail with the source diagnostic; per-member failures must reach the final
   exit status. Existing no-`-s` behaviour remains unchanged.
7. Logs and existing stats must identify source-side snapshot success/failure
   without claiming a stream/received copy. Do not redesign the stats schema
   or shared library for this feature. Document the new mode, rejection rules
   and its failure/degradation statuses in the same delivery.

### Smallest decisive verification

Drive the actual CLI with stubbed SSH/ZFS, not just an extracted helper or
source-text assertions. Cover source-only success, `-r`, filtered `-R`,
paused `-L`, peer refusal, remote failure and a failed source listing. Assert
the command trace contains no target/transfer/destructive operations.
Exercise `-n -s` and rejected combinations above, including `-s -M`; check
the trace, not only rc. Hide `mbuffer` and the compressor in a source-only
positive case. Run successful quiesce and one safe-degradation/strict-failure
case, checking ordering, snapshot count and final status. The baseline must
fail the new supported-mode assertions because `-s` is unsupported; an
unsupported-option error is not evidence that a refusal guard works.

Use the actual-diff `impact.sh` obligations and `impact.sh --verify`, preserving
existing engine/twin tests. For live proof, reuse one bounded delegated-account
lab case through the actual pairing key/gate: create one source snapshot,
verify it exists there and no target dataset was created, then demonstrate
disabled-gate refusal. Do not run a new full-cluster campaign just to verify
this mode. Additional quiesce live obligations remain those selected by the
affected contract; never infer delegated/live proof from stubs alone.

## Integration boundary: the cluster design is a separate acceptance

The owner has recorded acceptance of no new snapshots on A while collector B
is down, and stop+alarm when the guest moves to B. No further owner question
is needed to repeat those choices. An emergency fallback on A is merely a
possible later design, not part of this authorisation.

Before the new mode is selected by the cluster relationship, the higher layer
must prove guest/replication-source ownership and refuse or stop+alarm when
ownership is wrong or cannot be determined. A stopped guest alone is not
proof that the dataset is the source rather than a pvesr target. Source prune
needs the same direction guard; an engine-only `-s` flag cannot protect a
separate prune cron line. Recheck ownership before each mutating job, not
only at relationship creation. Do not claim this removes migration races
without measuring the chosen guard.
