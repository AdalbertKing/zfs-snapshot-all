# REV-20261104-187 — editing remote snapshot retention still uses a hidden relation template

Reviewer: ChatGPT. Date: 2026-11-04.

Target: development `main` at `12e25e6848a30cffa56d98d1372212b984e0c857`.
This is a new finding, separate from REV-20261104-186 F1–F6. It records the
Owner's observation that the package still uses hidden templates while setting
and changing retention despite the relation config being the sole source of
truth after creation.

## F1 — the snaponly retention editor re-renders from `profiles/relacja-<name>.conf`

- Severity: **P1**
- Blocking: **yes for claiming config-only retention editing for snaponly relations**
- Affected: `tui/edit-relation.sh` snaponly `harm` flow and
  `zfs-backup.sh` `cmd_edit_relation` / snaponly regeneration; related
  creation-time flow in `tui/new-relation.sh`.

### Contract and evidence

The Owner's decision in
`docs/project/DESIGN-SZABLON-TYLKO-PRZY-TWORZENIU-2026-10-22.md` says that
profile files are read only when creating a relation or deliberately choosing
"Use template". Other edits of an existing relation must use its block and
sections in config. The older review backlog also records removal of hidden
relation templates and reconciliation in #521–#525.

The ordinary copy-retention editor already follows that model:
`tui/edit-relation.sh` `harm_flow()` reads `show-tiers` from config and applies
`set-tiers` once. But the snaponly branch explicitly exits that flow (near
line 891). Its `harm` path instead takes `CUR_P` as the table base, invokes
`tui/template.sh`, writes `relacja-$NAME` through `save-profile --hidden
--force` (near line 1054), then builds `edit-relation "$NAME"
"--profile=$PROFILE"` (near line 1094). `zfs-backup.sh` rejects per-tier
words for snaponly and directs the user to `--profile=` or direct config editing
(near line 12979). Thus the GUI's normal retention action reuses a profile
file as policy input after the relation already exists. A hidden file is also
created for "Manual" in the creation wizard (`tui/new-relation.sh` near line
829); the concern is its continuing authority after creation, not the use of
a draft helper before the first config is committed.

### Failure mode and impact

If the installed config was edited independently, or the hidden template is
missing or stale, the next GUI retention change can fail or regenerate policy
from that separate file instead of the current relation sections. The old code
even computes a warning about manual config edits before this replacement
(near line 1165). Because the affected policy controls deletion of snapshots,
an unnoticed revert or stale retention value is operationally significant.

This is a static control-flow finding. I have not yet reproduced a concrete
overwrite or deletion on a live host, and the exact behavior for every snaponly
shape remains to be established by the regression below.

### Required outcome

For an existing snaponly relation, the ordinary "Harmonogram i retencja" and
source-retention actions must read the current relation config and apply the
chosen change to that config atomically. A profile may be consulted only for
explicit "Use template". The creation wizard may use a draft template as an
input mechanism, but after creation the installed relation must not require
that hidden file to remain available or synchronized.

### Acceptance criteria

- [ ] The snaponly retention editor starts from the installed config's actual
      tiers, values, schedules, prefixes and method, including manual config
      changes, without consulting `relacja-<name>.conf`.
- [ ] Its preview and commit use the same config-derived plan; cancellation,
      failure and interruption leave the original config and jobs intact.
- [ ] A missing, stale or deliberately altered hidden template cannot change
      the result of a normal retention edit. Do not regenerate unrelated
      relation fields or overwrite manually maintained values.
- [ ] Explicit "Use template" remains a separate, named action which previews
      the fields it will replace.
- [ ] Creation and import produce a relation whose subsequent editing works
      without the hidden template; remove or demote any persisted helper that
      otherwise competes with config.
- [ ] Preserve existing snaponly and other relation semantics, including
      source-side pruning and job activation safeguards.

### Required verification

- Automated: actual CLI/GUI-path regression on an installed snaponly relation:
  mutate a supported retention value in config, remove or stale the hidden
  template, then edit another retention value. Assert the preview, final config
  and cron derive from the edited config; the first value remains intact.
- Automated: missing-template, stale-template, cancel, failed generator and
  explicit "Use template" controls; show the old path fails at least one
  distinguishing case.
- Automated: cover ordinary copy and local relation editors as controls;
  run `test/impact.sh` obligations, `./test/impact.sh --verify`, syntax,

- Manual: if the affected path depends on real ZFS or delegated-account state,
  perform the required throwaway lab check and report any unavailable obligation

### F1 — a tier-set edit replaces each dataset's own template membership

`snaponly_tiers_apply_ops()` now handles `--add-tier` and `--drop-tier` by
calling `snaponly_use_template_set()` for both `snaponly` and `prune` sections.
That helper builds one comma-separated list from **all** relation tiers, then
uses `set_or_remove_section_field()` to write that same list into **every**
managed `[snaponly:]` or `[prune:]` section (near lines 7505-7533). Its input
does not include the section's current `use_template` list. If the installed
config deliberately omits a tier on one dataset, adding or dropping another
tier re-enables the omitted tier on that dataset. This changes which snapshot
families are taken or pruned without the user selecting that change. The
generic config and generator represent membership per section; it is not a
relation-wide value that can be reconstructed from the tier definitions.

The new regression and reported lab run use uniform membership across their
sources, so they cannot distinguish this overwrite. Their stale-profile and
hand-edited count/schedule controls demonstrate the fixed read path, but do
not test preservation of an installed per-dataset tier choice. This is a
static data-flow finding; I did not run a live ZFS deletion or claim that a
particular production relation has divergent membership.

### F1 — "Krótka retencja źródła" still re-renders from a hidden profile

`tui/edit-relation.sh` presents **Krótka retencja źródła** as an edit action
beside the schedule/retention table (near lines 839-843). Its `fastprune`
path selects a base from the current profile (`FP_CUR_BASE` or `CUR_P`), calls
`fp_save` to write `relacja-<NAME>-fastprune` (near lines 990-1026), and then
executes `edit-relation NAME --profile=$PROFILE` (near line 1057).
`tui/fastprune-lib.sh` `fp_save()` derives each tier from `list-profiles --json`
and uses `save-profile --from=$base --hidden --force`; the generated profile
is then the policy input. The action's user-facing name does not say
**Use template**. A missing or stale base profile can therefore fail or
re-render unrelated, manually maintained values in the installed config
when the user only changes the short source-retention period.

This is directly within this REV's required outcome: ordinary source-retention
actions on an existing snaponly relation must read its config and apply only
the selected change; profiles may be consulted for deliberate **Use template**.
The response explicitly lists fast prune as residual work, but classifying
it as a separate explicit action does not satisfy the Owner's narrower
exception. I have traced the call chain; I have not run a live short-retention
edit or observed actual snapshot deletion.

### Acceptance delta and reviewer process correction

- Make the fast-prune edit read the installed relation's tiers and source
  retention from config, and update the selected policy there without an
  implicit `save-profile`/`edit-relation --profile` round trip. Preserve
  unrelated hand edits, dataset membership, jobs and rollback semantics.
- Add an actual GUI-to-CLI regression on an installed snaponly relation with

  Future verification of the config-authority rule must trace every such
