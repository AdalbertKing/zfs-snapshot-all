# REV-20261021-159 — Browse cleanup discards failures and reports resources closed

Reviewer: ChatGPT. Date: 2026-10-21.
Canonical inspected `main`: `b0c04c1ceb355677d1b05615b042b93f37d380f0`.
Affected: `tui/browse.sh`, blob `fa38378589381135107c4421ef20250c79b4da00`, introduced across PRs #611, #615 and #617; specifically `unmount_all()` at lines 33–43 and `restore_snapdev()` at lines 70–82.

This review is independent of open REV-158. It covers the already-landed read-only browse/recovery path and does not reopen any closed capacity-guard finding.

## F1 — P1: failed unmount or mapper close is erased and shown as success

- Severity: **P1**.
- Blocking: **yes** for claiming the browse session has cleaned up successfully.
- `unmount_all()` tries ordinary and lazy `umount`, but ignores failure of both calls, attempts `rmdir`, then clears `MNT` unconditionally. It likewise ignores `cryptsetup close` failure and clears `MAPPED` unconditionally.
- `browse_and_exit()` then prints `=== Odmontowane` and exits zero. The EXIT trap sees empty state and cannot retry.
- Consequence: a snapshot can remain mounted after the UI says it was unmounted. An unlocked LUKS/BitLocker mapper can remain open, exposing decrypted data and preventing later cleanup, while the only in-process recovery handles have been discarded. If the mount is still active, attempting to close its backing mapper is also the wrong cleanup order.

### Independent reproduction

The reviewer ran the shipped `tui/browse.sh --any` entry point with fake `zfs`, `mount`, `umount`, `rmdir`, `whiptail` and `mc`; no real mount, mapper, ZFS pool or host was touched. `mount` succeeded, both ordinary and lazy `umount` returned failure, and `rmdir` returned failure. Observed result:

```text
rc=0 umount_calls=2 rmdir_calls=1 success_banner=1
```

The call log showed both failed unmount attempts followed by the success banner. Static inspection confirms the same discarded-status pattern for `cryptsetup close` immediately before `MAPPED=""`.

### Required outcome / acceptance criteria

1. Cleanup must preserve state until the mount or mapper is demonstrably gone. A failed operation must remain retryable by the EXIT path or an explicit recovery action.
2. Do not print `Odmontowane` or return success while any mount or mapper remains. Report the exact residual resource and a safe manual recovery command; return nonzero when automatic cleanup cannot complete.
3. Maintain cleanup order: verify the filesystem is no longer mounted before closing its mapper. Do not treat a requested lazy detach as proof that all references are gone.
4. Exercise the actual shipped entry point with fake commands for: normal success, ordinary-unmount failure with lazy success, both unmounts failing, `cryptsetup close` failing, and mapper close succeeding. Assert final status, diagnostics, retry behavior and absence/presence of residual state.

## F2 — P1: failed `snapdev` restoration deletes the only recovery record

- Severity: **P1**.
- Blocking: **yes** for the zvol browse path.
- `restore_snapdev()` discards the status from `zfs set`/`zfs inherit`, then removes `orig.<dataset>` and clears `SNAPDEV_DS` regardless. The EXIT trap therefore cannot retry and the original value/source is lost.
- `expose_snapdev()` also writes an origin record from unchecked `zfs get` substitutions; inability to read the original property is not distinguished from an empty value before mutation.
- Consequence: `snapdev=visible` can remain enabled after the UI says nothing was changed, and the process deletes the evidence needed to restore the previous local/inherited state safely.

### Independent reproduction

The reviewer ran the actual entry point for a fake volume. `zfs get` returned `hidden`/`local`, `zfs set snapdev=visible` succeeded, the fake snapshot device deliberately did not appear, and restoration `zfs set snapdev=hidden` failed. Observed result:

```text
rc=0 restore_attempts=1 orig_files=0 hold_files=0 misleading_msg=1
```

The script removed both marker types, cleared its state and exited zero after displaying `Nic nie zostało zmienione w kopii`; no second restoration attempt occurred.

### Required outcome / acceptance criteria

1. Refuse to change `snapdev` unless both original value and source were read successfully and validated.
2. A failed restoration must retain sufficient root-owned recovery metadata, keep the failure visible, retry where safe, and return nonzero rather than claim no change. Do not silently replace an unknown original source with `inherit`.
3. Preserve the existing multi-browser contract: one session must not hide the device while another live session uses it, and a stale marker must not cause loss of the original property record.
4. Add actual-entry-point tests for local original value, inherited original value, failed initial `get`, failed `set visible`, failed restoration and two holders. The regression test must fail on blob `fa38378589381135107c4421ef20250c79b4da00` for the reproduced failure cases.
