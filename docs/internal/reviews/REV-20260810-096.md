# REV-20260810-096 — configexamples does not require semantic coverage for newly added runnable examples

Review time: 2026-08-10 22:07 CEST
Reviewed implementation: `58f67f69dc3ac8225c93b58d5b643758c3284978`

## Verdict

**CHANGES REQUIRED — current examples are protected, but the regression edge is not yet durable for future additions.**

REV-094 is closed for the four examples that triggered it: the new suite runs the real generator, pins their intended semantics, has the right dependency edges, and includes a useful drift control.

A smaller follow-up remains in the suite's own contract. Layer 1 deliberately discovers every future `docs/examples/*.conf`, but only requires that an unknown/new example render with exit 0. Layer 2 hard-codes semantic assertions for the four names that existed when the suite was written. Therefore this sequence can still go green:

1. add `docs/examples/new-policy.conf`;
2. impact correctly selects `configexamples` through the directory edge;
3. the new file parses successfully;
4. no semantic assertion exists for what `new-policy.conf` is supposed to teach;
5. the suite passes anyway.

That leaves exactly one part of the original durable-contract goal dependent on reviewer memory: remembering to extend Layer 2 whenever a runnable example is added. The graph catches the file change, but the suite does not yet prove that every runnable example has semantic coverage.

This is a test-hygiene defect only. I do not find a production-runtime defect and no current example loses coverage.

## Required outcome

Add the smallest meta-guard that makes semantic coverage total over the runnable example set.

Acceptable shapes include either:

- a checked-in/inline list of example basenames that have semantic assertions, with the suite comparing that list exactly to `docs/examples/*.conf`; or
- a compact per-example dispatcher/manifest where discovery of an unknown basename is a FAIL until its semantic checks are registered.

Acceptance criteria:

1. every current example remains rendered by the real `gen-cron.sh` and keeps its existing semantic assertions;
2. adding a fifth runnable `.conf` without registering semantic coverage makes `test/configexamples/run.sh` fail;
3. deleting/renaming an example without updating the semantic registry also fails, so stale assertions cannot silently remain detached;
4. include one deterministic negative control for the new meta-property (for example, introduce a temporary extra `.conf` in a temporary examples directory/fixture and prove the registry check rejects it); do not mutate the real repository tree during the committed test run if a fixture can prove the same property;
5. run only `configexamples`, the dependency-selected cascade caused by the test/graph change, and `./test/impact.sh --verify`.

No live ZFS, SSH, UID/account, crontab, grant, or deploy proof is required. No production-code change is requested.

## Phase impact

This finding is scoped to Phase 6 runnable-example hygiene. It does **not** reopen REV-094 for the current four examples and does **not** block Phase 5, whose Gate 4 proof is independently closed by REV-095.

It blocks only the next Phase 6 slice that adds or materially changes runnable examples until the total semantic-coverage guard exists.
