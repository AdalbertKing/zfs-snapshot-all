## F1 — P1: JSON export is escape-aware but `[relation:]` restore is not

- Severity: **P1**
- Blocking: **yes** for the advertised exact export/delete/import round trip
- Affected: `zfs-backup.sh`, `import_restore_relblock()` and the U28 relation
  settings replay

### Evidence

`cmd_export_relation()` serializes every `[relation:NAME]` key/value with
`json_escape()`. `json_value_of()` also walks JSON strings while respecting
escapes. The final U28 restore step discards that parser and extracts the
`relation` object with:

```awk
while (match(s, /"[^"]*":"[^"]*"/)) { ... }
```

That expression treats an escaped quote as the end of a JSON string and never
JSON-decodes the recovered values. A relation value containing a backslash is
likewise restored in its JSON-escaped form.

The executable reproduction is:

```bash
bash docs/internal/reviews/evidence/REV-20261022-168-config-roundtrip.sh
```

It uses a temporary local relationship with the legal field:

```ini
hourly.notify_word = snap"shot
```

The shipped `gen-cron.sh` accepts the configuration, and `export-relation
--json` correctly writes `"snap\"shot"`. Calling the shipped
`import_restore_relblock --check` against the unchanged source config returns
1 instead of identifying it as equal. Calling the real restore function with
only cron installation boundaries stubbed returns success but changes the
value:

```text
before=[snap"shot]
after=[snap\]
```

The evidence script ends **2 PASS / 2 FAIL**. It touches no network, ZFS,
account, installed cron or live host.

The current focused suite remains green:

- `bash test/zfsbackup/run.sh --section exportrel`: **73 PASS / 0 FAIL**;
- `bash test/run.sh`: **123 PASS / 0 FAIL**;
- `bash test/zfsbackup/run.sh --section snaponly`: **31 PASS / 0 FAIL**;
- U28 PR-head GitHub Actions run `39313874955`: success.

The gap is direct: the U28 test stubs `import_restore_relblock()` and verifies
only that it was called. It does not execute the parser/rewriter on an exported
block containing JSON escapes.

### Failure mode and impact

An operator can export a valid relationship, delete it, and import the exact
document successfully, yet receive different relationship settings. The
demonstrated field changes notification wording; the same parser handles all
relation values, including prefixes, patterns, schedules, retention and engine
settings. Some corruptions may be rejected by `gen-cron`, but accepted output
such as the demonstrated `snap\` is installed with a success result. This
violates the promised exact round trip and makes the export unsafe as a sole
configuration recovery artifact. No ZFS data loss was demonstrated.

### Required outcome / acceptance criteria

- [ ] Parse the `relation` object with the same escape-aware JSON contract used
  by the rest of import; do not recover JSON key/value strings with a regular
  expression that stops at escaped quotes.
- [ ] JSON-decode keys and values exactly once before rendering the temporary
  `[relation:NAME]` block; preserve literal quotes and backslashes byte for byte.
- [ ] Add an end-to-end focused regression that performs real export followed
  by the real `import_restore_relblock()` on values containing at least `"` and
  `\`, then compares `relblock_dump` before and after.
- [ ] Prove that `--check` reports equality for the unchanged exported block
  and reports a difference for a genuinely changed setting.
- [ ] Keep whole-config `gen-cron` validation and atomic replacement; malformed
  or unsupported JSON must fail before installation rather than silently omit
  or truncate fields.
- [ ] Run `bash test/zfsbackup/run.sh --section exportrel`, `bash test/run.sh`,
  `bash test/impact.sh --verify`, `bash test/reviewctl.sh --verify` and CI on
  the exact submitted SHA.

### Evidence boundary

The reproduction executes the production export and restore functions while
stubbing only record-to-cron resolution and final installation into temporary
files. It proves false inequality and accepted value corruption. It does not
claim that every relation field accepts arbitrary punctuation or that live ZFS
state was modified. The reviewer made no production-code change.
