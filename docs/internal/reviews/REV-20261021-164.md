# REV-20261021-164 — U42: --leave fails open when post-revoke ZFS reads fail

Reviewer: ChatGPT, 2026-10-21. Published `main`: `99c7ebd524bd7f4deb075b6fc49e73febc865ae8`. Affected `deploy.sh` blob `8391798ad0ecefb8b7b38884482993c9659d44bb`, `do_leave()` around lines 4400–4455. Discovered while independently reviewing the already implemented REV-163 *new account* guard. The REV-163 fix is approved **within its new-account boundary**; this is a distinct **existing-account teardown** bug.

## F1 — P1: failed `zfs allow` read is treated as a successfully empty post-revoke inventory

### Evidence in the published code

After the loop attempting to revoke the relationship's recorded dataset grants, `do_leave()` verifies residual permissions with:

```bash
local -a residual=()
for ds in "${datasets[@]}"; do
    [ -n "$ds" ] || continue
    zfs list -H -o name -- "$ds" >/dev/null 2>&1 || continue
    zfs allow "$ds" 2>/dev/null | grep -Eq "(^|[[:space:]])user (${uid}|\\(unknown: ${uid}\\)|${account})([[:space:],]|$)" \\
        && residual+=("$ds")
done
if [ "${#residual[@]}" -gt 0 ]; then die ...; fi
# ... passwd -l, userdel -r, remove manifest ...
```

Both read-error cases are disguised as absence:
1. `zfs list ... || continue` does not distinguish *dataset does not exist* from *dataset exists but enumeration failed* (permissions, ZFS CLI error, transient unavailable pool). The earlier hold check and revoke loop do the same.
2. `zfs allow ... | grep -Eq` checks only `grep` status; a `zfs allow` command failing with nonzero and no output is interpreted as `no residual grants`. The script may then run `userdel -r` and delete the relationship manifest and keys, even if the earlier `zfs unallow` also failed and merely warned. The numerical UID can be recycled with its grants remaining on-disk — exactly the U42 isolation failure the project is fixing.

The reviewer independently reproduced the **exact pipeline and conditional** from `do_leave()` using harmless shell function stubs. When `zfs allow` emitted the remaining grant, `residual=1` and `userdel` was blocked; with `zfs allow` returning rc 42, `residual=0` and the `userdel` decision gate opened. No live account, ZFS, dataset or manifest was modified. This is a partial path reproduction; the full `do_leave()` call boundary remains for the implementer to verify.

### Severity and boundary

**P1 — BLOCKS `--leave` account deletion until proven fail-closed.** This is not a claim that every ordinary teardown loses grants; normal successful reads and revocations can work correctly. The risk is specifically a failed verification or inventory. A successful `userdel` under uncertainty releases the UID for reuse while potentially leaving delegated `destroy`, `mount`, `send`, `snapshot`, etc. on ZFS datasets.

### Required outcome

- [ ] A nonzero `zfs list` for each dataset during hold checking, revocation and post-revoke verification must **not** silently mean absent. If absence needs distinguishing, use a reliable explicit distinction or fail closed with a diagnostic; allow documented successful absence only on solid evidence.
- [ ] Capture and check `zfs allow` status directly for each dataset. No masked pipelines; unreadable permissions => nonzero `--leave`, no `userdel`, no key/manifest/scope deletion, and clear message with dataset and exact UID. Never conclude `no grants` from an unreadable ACL.
- [ ] If `zfs unallow` fails and ACL re-read fails, do not continue teardown. If `zfs unallow` reports success but ACL read fails, also do not continue. A definitive remaining grant still blocks as before.
- [ ] Preserve the existing *exact UID bound by the manifest*, no guessing other accounts' anonymous/numeric principals or revoking their grants.
- [ ] Add deterministic fake-ZFS/fake-account tests at the `do_leave()` call boundary: clean removal, still-present grant, `zfs list` failure at each relevant stage, `zfs allow` failure, `unallow` failure plus read failure, documented missing dataset. Assert account/key/manifest unchanged on uncertain results. Distinguishing old-version negative control mandatory.
- [ ] Run `test/draftscope`, `test/join`, `test/joinremote`, `test/joinmanifest`, any `leave` suites and `bash test/impact.sh --verify`. Supply exact SHA and manual obligations in `docs/internal/reviews/responses/REV-20261021-164.md`.

No production system was touched in this review. Keep the scope narrow: do not loosen the relation UID binding or convert read failures into guessed cleanup. `--leave` on delegated relationships should not be considered fully safe until this issue is implemented and independently verified.

### R1 (P1) — scope narrowing revokes access on an unreadable hold

The shipped do_commit_scope() contains:

```bash
if ! zfs list -H -o name -- "$p" >/dev/null 2>&1; then
    revoke_gone+=("$p")
elif commit_scope_dataset_held "$p"; then
    revoke_held+=("$p")
else
    revoke_clean+=("$p")
fi
```

Bash treats both return 1 (no hold) and the new return 2 (read error) as false. Return 2 therefore adds the dataset to revoke_clean. The later zfs unallow loop can revoke a relationship's permissions while a transfer hold cannot be read; this violates the claimed fail-closed behavior. Independently executed the exact branching structure with a stub returning 2: revoke_clean=tank/a and revoke_held empty. No live ZFS tests.

Acceptance for this SAME REV: handle status 0/1/2 explicitly in do_commit_scope, with 2 failing closed before any revocation or persistent mutation (preferred). Also distinguish its initial failed zfs list check from a verifiably absent dataset; today any error becomes revoke_gone. Add fake-ZFS regression for failed snapshot listing and failed holds with previous grants: no unallow, no lost manifest grant, nonzero exit and useful diagnosis. Confirm normal held and unheld paths. Run joinmanifest, join/scope-related tests, impact --verify and CI. Update the existing response with a new full implementation SHA and old-tree negative evidence.
