# REV-20260908-139 — show-scope turns failed auxiliary ZFS reads into zeros

Review date: 2026-09-08
Reviewer: ChatGPT
Reviewed delivery: PR #362, implementation `adda72f134138068c04a7fd15c1371f3e49600b5`
Canonical merge checked: `84d27f0370c17296b70046a08133bc74b54b6d4c`

## Verdict

**CHANGES REQUIRED — P2: `show-scope --json` checks the snapshot-list read,
but silently converts failures of the bookmark and `usedbysnapshots` reads to
successful zero values. A GUI therefore cannot distinguish an empty result
from data the current account was unable to read.**

The literal-prefix family grouping, `other` bucket, recursion switch and
creation-time tie breaker are not rejected. The blocker is confined to the two
unchecked auxiliary ZFS boundaries after the main snapshot list succeeds.

## F1 — P2 BLOCKING — failed auxiliary producers are published as measured zeros

- Severity: P2
- Blocking: yes
- Affected: `cmd_show_scope()` in `zfs-backup.sh` and the `showscope` controls in
  `test/zfsbackup/run.sh`.

### Evidence

On exact implementation `adda72f134138068c04a7fd15c1371f3e49600b5`, the
reviewer used a minimal ZFS stub with three independently controlled results:

- `zfs list ... -t snapshot` succeeds and returns one snapshot using 4096 B;
- `zfs get ... usedbysnapshots` prints a permission error and exits 1;
- `zfs list ... -t bookmark` prints a permission error and exits 1.

Observed:

```text
rc=0
stdout={"dataset":"pool/fs","exists":true,"error":"",...,"total_snapshots":1,"bookmarks":0,"used_by_snapshots":0}
stderr=
```

The snapshot row proves this is not the already-tested failure of the primary
snapshot list. The two later commands redirect diagnostics away, never retain
their exit status, and normalize nonnumeric/empty output to zero. `grep -c` in
the bookmark pipeline also masks the producer's failure.

### Failure mode and impact

`0` is a valid measurement for both fields. The response therefore asserts
that there are no bookmarks and snapshots occupy no space when neither fact
was measured. On the GUI detail screen this can conceal retained bookmarks or
the storage pressure the command was introduced to explain. The verb is
read-only and the primary snapshot inventory remains available, so the finding
is P2 rather than a mutation/data-loss severity.

### Existing verification and why it missed the defect

- PR #362 exact-head CI is green: run `34256740900`.
- Independent focused run: `18 PASS / 0 FAIL`.
- The suite covers primary snapshot-list refusal, but its successful fixture
  makes both auxiliary producers succeed. It has no discriminator where the
  primary list succeeds and either later producer fails.

### Acceptance criteria

1. Check the exit status of `zfs get ... usedbysnapshots` before publishing its
   value; a refusal must not become numeric zero.
2. Check the exit status of the bookmark-list producer itself, not only the
   count produced downstream; a refusal must not become `bookmarks:0`.
3. Define one explicit machine-readable partial-read policy: either return a
   nonzero complete error document, or retain the available snapshot families
   while marking each unavailable metric as unavailable. In both cases a GUI
   must be able to distinguish refusal from a measured zero.
4. Add two focused discriminators with a successful snapshot list: one failing
   `usedbysnapshots` read and one failing bookmark list. Each must prove the
   response does not publish a healthy zero for the failed metric.
5. Preserve the existing family counts, `other` bucket, flat/recursive ZFS
   arguments, tie breaking and complete JSON shape.

### Required verification

- focused: `./test/zfsbackup/run.sh --section showscope`;
- negative control: the auxiliary-failure fixture above must demonstrate the
  current false zeros against `adda72f134138068c04a7fd15c1371f3e49600b5`;
- consistency: `./test/impact.sh --verify` and exact-head CI.

No real pool, destructive operation or full product campaign is required. A
three-branch ZFS stub decides the defect.
