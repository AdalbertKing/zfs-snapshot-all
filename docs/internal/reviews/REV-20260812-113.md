# REV-20260812-113 — Phase 7 slice 1 restore planner

## Verdict

CHANGES REQUIRED. The planner's central promise — enumerate the recovery points that actually exist on the copy dataset — is not yet proven against real ZFS, and the current command shape is suspect at exactly that boundary.

## Verified scope

The slice is otherwise appropriately narrow: `restore --plan` derives relationship locations from installed CONFIG, refuses the write verb, reports ZFS `creation` rather than trusting a timestamp encoded in the snapshot name, and declares a dedicated `restore` suite in the impact graph. The stubbed suite has useful discriminating controls for creation-vs-name and records that only `zfs list` is invoked.

The local-push copy-path derivation is consistent with the already-recorded Phase 5 live seed topology; I am not reopening that contract here.

## F1 — snapshot enumeration is environment-dependent and the stub does not prove the real `zfs list` selector semantics

Implementation currently executes:

```sh
zfs list -H -p -t snapshot -o name,creation -s creation "${copy[$i]}"
```

The test stub is intentionally permissive: it treats the final argument as a key and returns fixture snapshots for that dataset. That proves the parser and presentation logic, but not that real OpenZFS interprets this exact invocation as "list snapshots belonging to this dataset". This is the core runtime dependency of the planner. If real `zfs list -t snapshot DATASET` requires a depth/recursive selector to enumerate snapshots below the filesystem, the current planner reports `BRAK` on a healthy backup and therefore fails its primary recovery contract.

This is precisely an environment boundary where a green local stub suite is a filter, not final proof.

### Required correction / proof

Use the smallest proof that resolves the real selector semantics:

1. On a real ZFS host, create or reuse a disposable dataset with at least one snapshot.
2. Run the exact planner enumeration command shape against that dataset and record whether it returns the snapshot(s).
3. Include a negative control using a dataset with no snapshots (or otherwise demonstrate that the selector distinguishes present from absent recovery points).
4. If the current command is wrong, fix only the selector and update `test/restore` so its stub requires the correct option shape; do not broaden the restore implementation.
5. Re-run `test/restore` plus only dependency-driven suites required by the changed files. No full campaign unless the impact graph demands it.

The live proof must show the exact command and output/return status, not merely state that a snapshot existed.
