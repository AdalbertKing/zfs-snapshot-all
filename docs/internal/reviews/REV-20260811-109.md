# REV-20260811-109 — iterative review is paying for monolithic test suites too often

## Finding

The repository has a sound risk-based test policy, but the current execution granularity does not let the implementer follow it efficiently.

`test/zfsbackup/run.sh` has grown into a large sequential suite (currently hundreds of assertions). A small correction inside one late section — for example the REV-102 audit-source-retention checks — still naturally leads to re-running the whole `zfsbackup` suite. Repeating that after each reviewer OPEN/revision cycle is not proportional to the risk of the individual correction and is now a project-delivery problem.

The defect is not "too many tests". Coverage is valuable. The defect is that the smallest convenient execution unit is too large.

This contradicts the existing owner policy in `docs/project/TEST-CAMPAIGN-POLICY.md`: during implementation use fast local feedback, group related changes, and pay for the expensive campaign once at the end of the package.

## Owner direction

This is the next required infrastructure step. Keep it simple.

Do NOT invent a new testing framework and do NOT delete broad regression coverage merely to make the counter smaller.

The target model is:

- **L0 — targeted iteration:** run the exact defect reproducer / changed test section (seconds, not the entire suite);
- **L1 — formal resubmission:** when a REV is genuinely ready for reviewer verification, run the full affected suite(s) selected by the dependency graph;
- **L2 — gate/phase campaign:** expensive integration/live/destructive campaign once at the relevant REV/Gate/Phase boundary, according to risk;
- `./test/impact.sh --verify` remains a cheap consistency check and may be run frequently.

A reviewer returning the SAME REV OPEN for a narrow residual must not, by itself, force another L1/L2 run before the implementer has finished the next submission.

## Required correction

### 1. Measure before changing

Perform one short cost audit of the current test tree and record it in `docs/discussions/TEST-SUITE-COST-AUDIT-2026-08-11.md`.

At minimum record for the main repeatedly-used suites:

- assertion count;
- wall-clock runtime on the implementation environment;
- why/when the suite is selected;
- whether it already has a useful targeted execution boundary;
- the largest obvious cost/redundancy contributors.

This is a one-pass engineering measurement, not a benchmarking project. Identify the few biggest offenders first.

### 2. Give `test/zfsbackup` a real targeted boundary

Implement the smallest maintainable way to run one logical section (or one named focused group) without executing all unrelated earlier/later assertions.

A shape such as:

```text
./test/zfsbackup/run.sh --section 57
```

or an equally simple named form is acceptable. Exact CLI spelling is implementation detail.

Critical property: targeted execution must not false-green because the selected section secretly depends on state produced by skipped sections. A targetable section must either be self-contained or declare/use the minimal shared setup it really needs.

Do not wrap the entire file in a complex dispatcher merely for aesthetics. Extracting a high-churn section into a small independently runnable helper is acceptable if that is the smaller change.

### 3. Preserve the full-suite gate

No-argument `./test/zfsbackup/run.sh` must remain the full regression suite and retain equivalent coverage. L0 is an additional fast path, not a replacement for L1.

### 4. Prove the selector discriminates

Minimum evidence:

1. targeted run executes the intended REV-102/retention section and catches a deliberate negative control;
2. unrelated sections are demonstrably not executed in targeted mode;
3. target setup is self-contained / has no hidden dependence on skipped test state;
4. full no-argument suite still passes with the same substantive assertions;
5. `./test/impact.sh --verify` remains clean.

### 5. Apply the execution policy immediately

For ongoing REV-102/REV-108 iteration after this lands:

- intermediate fixes: L0 targeted test + any directly touched shared-boundary checkpoint;
- full affected suite(s): once when Claude marks the complete REV IMPLEMENTED for reviewer verification;
- live/destructive proof: only when the acceptance property actually requires it, not on every textual review round.

## Explicit non-goals

- no new test orchestration framework;
- no CI platform migration;
- no mass splitting of every existing suite in this REV;
- no deleting tests merely because they are slow;
- no weakening `impact.sh` dependency coverage;
- no rerunning the full campaign just to prove this documentation/process change.

If the cost audit finds an obvious exact duplicate, record it; removal can be proposed separately with proof. First priority is granularity, not coverage reduction.

## Interaction with active product work

REV-102 and REV-108 remain product-correctness work. REV-109 is an independent delivery/tooling defect and is routed to Claude in parallel, but it should be treated as the next infrastructure priority before another long sequence of narrow REV-102/108 iterations.

Reviewer should accept targeted evidence for intermediate corrections once the selector exists; L1 remains required on the final resubmission.

The change is intentionally small and preserves dependency-driven L1/L2 gates.
