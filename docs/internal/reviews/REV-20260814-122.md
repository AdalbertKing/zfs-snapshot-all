## F2 — P1 — closure proof checks APPROVED but not what was approved

`tx_close()` reads the review file at `--approval-commit`, but extracts only
`verdict`:

```sh
shown="$(git show "$acommit:.../$rev.md" |
         sed ... verdict ...)"
[ "$shown" = "APPROVED" ] || refuse
```

It does not read and compare that commit's `reviewed-implementation` with the
current response implementation. Therefore commit A that approved implementation
X can be supplied while current hand-edited facts say APPROVED for Y. If current
review and response both name Y, generation derives CLOSED even though
`closed-by=A` proves approval only of X.

That violates the consensus requirement that the closure commit provably carried
approval of the exact implementation being closed.

### Required

At construction time, require all of:

- approval commit carries `verdict: APPROVED`;
- its `reviewed-implementation` is canonical and equals the exact current response
  implementation;
- current reviewer header still names the same implementation;
- the closure cannot be produced when any of those values differ.

Add a discriminator where the named commit approved X but the current response and
review header name Y; `close` must refuse and leave no closure/view change.

## F3 — P1 — `--expected-parent` is a preflight read, not publication CAS

`tx_expect_parent()` compares `origin/main` with the supplied SHA before editing
the working tree. The tool then returns and instructs the caller to commit the
result later. A peer can advance `main` after the comparison and before commit or
push. The writer neither creates the commit nor advances a ref with compare-and-
swap, so the published transition is not atomic with the check.

The current claim that `--expected-parent` “is the compare-and-swap” is therefore
stronger than the implementation. It detects an already-stale request, but not a
race after the check.

### Required

Choose and prove one coherent boundary:

1. the publication wrapper owns commit/ref advancement and uses an atomic expected-
   old-SHA update/push lease; or
2. the core describes this only as a preflight and the Profile-A PR/branch-
   protection adapter supplies the real publication CAS, including an up-to-date-
   branch requirement and a race negative control.

Do not describe the invariant as enforced until the selected publication boundary
has been measured.

## F4 — P2 — idempotent replay returns before verification and repair

Both writers return success immediately when the target header/artifact already
matches. Those paths do not regenerate or verify the derived views. `approve`
also returns before ensuring the permanent `reviewed-by` fact exists.

A partially published or manually damaged state can therefore receive a successful
“already APPROVED/CLOSED” result while ledger/routing or delivery acknowledgement
remains inconsistent.

### Required

An idempotent replay must either:

- prove the complete postcondition, including permanent delivery acknowledgement,
  regenerated views and `--verify`; or
- refuse and name the inconsistent residual.

Add replay controls starting from matching approval/closure headers with stale
views and, for approval, a missing `reviewed-by` marker.
