## F1 — P1 blocking: supported `dst = user@host` pushes stop after cron regeneration

Affected: `gen-cron.sh:emit_send`, engine selection near line 3806;
`test/fixtures/sync-mode.expected`.

U49 correctly moves local copies to snapget, but selects that engine for every
nonempty destination without a colon. The supported bare `user@host` spelling
is a REMOTE push in sync mode, not a local path. `snapsend.sh` explicitly parses
this spelling and keeps the source dataset's path on the remote host. The
generator itself recognizes `*@*` as remote in its compression/autotune logic.
U22 retains remote CLI push support for existing fleets; this is not a request
to introduce push into the GUI or change that owner decision.

### Reproduction and impact

On the exact main above, using the existing shipped fixture:

```sh
bash gen-cron.sh -c test/fixtures/sync-mode.conf
```

returns 0, but its push-sync job ends with:

```text
snapget.sh -m "automated_" -A "tank/push-sync" "user@far"
```

The correct engine is `snapsend.sh` with those same source/destination arguments.
`snapget.sh` always interprets the second argument as a LOCAL base and refuses
`@` there. Running its actual CLI with `-n -N tank/push-sync user@far`, with
temporary command stubs that return 99 if invoked, returns 1 and reports:

```text
Second argument must be a plain local path, no host
```

Thus regenerating/installing cron for an existing bare-address push disables
every subsequent transfer until corrected. The generator accepts the config;
the runtime refusal is not a generator validation error. No data corruption is
claimed. Existing installed cron is unaffected until regeneration/install.

The U49 fixture change replaced push-sync's snapsend with snapget alongside the
intended push-local replacement. A green golden suite therefore cannot prove
this transport contract; the expected output itself includes the regression.

Reviewer evidence: `evidence/REV-20261020-154-routing.py` runs the real generator
and asserts each emitted engine against the transport contract, without
installing cron or invoking SSH/ZFS. On inspected main: **3 PASS / 1 FAIL**
(only push-sync fails). Pre-U49 `639b3848e527c5ff8dfcbe460c66a4f853944b37` emits
snapsend for push-sync; its local-copy engine is also snapsend, as expected
before U49. The comparator therefore also rejects that old local-copy mapping;
that is intentional and is not another old bug.

### Acceptance criteria and verification

1. Select snapget only for an actual local destination. Both `[user@]host:path`
   and bare `user@host` must remain on snapsend; absent destination must also
   remain on snapsend for snapshot-only operation.
2. Correct the sync-mode golden fixture and add a semantic assertion that
   distinguishes remote push-sync from local copy. Demonstrate that the new
   regression check fails on this inspected U49 main and passes with the fix.
3. Preserve local-copy snapget selection, remote base push, pull, and local
   snapshot-only behavior, including relevant generator/cron tests.
4. Run the selected impact suites and `bash test/impact.sh --verify`; submit
   the exact fixing SHA in the canonical response for this REV.

A generator/fixture fix is sufficient; no frozen engine change is requested
or authorized. This review does not approve the rest of U49 or the 1.0 release.
Independent current mirrorguest regression: **11 PASS / 0 FAIL**, including the
local-copy exception and retained remote live-guest refusal. Its success does
not exercise this generator routing bug. No live hosts were contacted and no
production jobs were changed. Remaining uncertainty is deployment prevalence:
the number of fleets using bare-address pushes was not measured.
