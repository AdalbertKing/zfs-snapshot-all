# REV-20261021-161 — Browse: unprotected holder registration vs last-session restore (same zvol)

Reviewer: ChatGPT, 2026-10-21.
Published code base: `809a14c1574ec58f2b62423ebd4c0a191c001948`; `tui/browse.sh` blob `2decbde1ac74ce35c6e43acfbd80b6a191138dcb`.
This is a **new P1 concurrency race** after REV-159 cleanup and REV-160 cross-dataset key fixes, which remain accepted within their scoped boundaries.

## F1 — P1: a last holder can delete the origin record while another session is starting

In `expose_snapdev()`, an entrant B validates or creates `orig2.<key>` but does not register `hold2.<pid>.<key>` until **after** that check:

```bash
if [ -e "$BROOT/orig2.$k" ]; then
    IFS=$'\t' read -r d v s <"$BROOT/orig2.$k" ...
    ...
else
    ... zfs get ... ; printf ... > "$BROOT/orig2.$k.$$" && mv -f ... "$BROOT/orig2.$k"
fi
: >"$BROOT/hold2.$$.$k"
SNAPDEV_DS="$ds"
zfs set snapdev=visible "$ds"
```

In `restore_snapdev()`, an exiting A does the following **without an interprocess lock**:

```bash
rm -f "$BROOT/hold2.$$.$k"
if other_holders "$SNAPDEV_DS"; then SNAPDEV_DS=""; return 0; fi
... zfs set snapdev="$was" "$SNAPDEV_DS" ...
rm -f "$BROOT/orig2.$k"; SNAPDEV_DS=""; return 0
```

The new key prevents **different datasets** from sharing records, but it does not serialize **multiple simultaneous sessions on the same dataset**.

### Concrete valid interleaving

1. A is browsing `tank/vol` (original `snapdev=hidden`), with `orig2.<key>` and its `hold2.A.<key>` record; snapdev is temporarily visible.
2. B enters `expose_snapdev(tank/vol)`, reads and validates `orig2.<key>`, then is preempted **before** writing its hold.
3. A exits: removes `hold2.A`, sees zero other holders, restores `snapdev=hidden`, then removes `orig2.<key>`.
4. B resumes, writes `hold2.B` and sets `snapdev=visible`. Eventually B exits, but `orig2` is missing. `restore_snapdev()` returns failure, **cannot restore the original state**, and can leave `snapdev=visible` with no recovery metadata.

There is also a race on the absence check + `mv -f` used to create the origin record. A simple `sha256` key and checked records cannot make either check/modify group atomic.

### Independent evidence boundary

The reviewer directly inspected the shipped source and executed a **deterministic isolated shell state-transition simulation** with a temporary `orig2` record and two holder markers. It produced:

```text
B_restore=FAIL missing_orig
final_snapdev=visible expected=hidden
```

This simulation exercises the sequence of the shipped read/check/create/delete operations, but it is **not** a full `browse.sh` entry-point test and used no real ZFS/mount/VM. The full race and its timing must be validated with test-controlled pauses in the actual shipped entry point.

### Required correction / acceptance criteria

- [ ] Protect the **per-exact-dataset** transition covering origin validation/creation, holder registration, and `snapdev=visible` from the terminal exit transition covering holder removal, checking remaining holders, restoring `snapdev`, and deleting the original record. Use a robust cross-process synchronization design (e.g. a trusted per-dataset `flock` / transaction lock), not a non-atomic existence test.
- [ ] Never drop the final known-good `orig2` metadata while an entrant has passed validation but not registered. Lock errors must fail closed, not silently proceed.
- [ ] Keep failure metadata and emit nonzero/residue when restoration fails; preserve graceful cleanup, SIGTERM handling and controlled stale holder recovery.
- [ ] Add deterministic **actual-entry-point** two-session same-dataset regression with fault-injection pause after entrant origin validation and before holder registration; let exiting A complete, then resume B. Check original `hidden/local` is restored, both sessions finish safely, no orphan exposed snapdev or discarded origin record. Negative control on `2decbde1` should demonstrate old failure.
- [ ] Repeat with entrant/exit reversal, original inherited `snapdev`, and stale/malformed origin record; preserve REV-159 cleanup and REV-160 cross-dataset cases (15–18) without introducing lock deadlocks.
- [ ] Run `test/browse`, `test/tui`, `test/impact.sh --verify` and CI; publish exact implementation SHA, regression evidence and any manual deployment obligations in `docs/internal/reviews/responses/REV-20261021-161.md`.

**Blocking:** P1 for unrestricted parallel browsing of the same zvol on production. This does not reopen REV-160's different-name identity fix and does not imply a general 1.0 release veto outside the affected browse workflow.
