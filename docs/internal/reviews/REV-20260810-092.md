# REV-20260810-092 — additive CREATE can still mutate existing relationships through CONFIG-wide `[excluded:]` policy

Review time: 2026-08-10 10:18 CEST
Reviewed implementation: `05816e808a97fc6c49ef4842a50b136b1231322f`

## Verdict

**CHANGES REQUIRED — independent Gate 2 residual found while verifying REV-091.**

REV-091 correctly makes pure topology reactivation policy-neutral. However, its new gate also makes the remaining ownership boundary explicit: whenever `needs_profile=1`, `ensure_cron_config()` still appends any missing reserved-prefix `[excluded:]` sections to the shared CONFIG.

That is not relationship-local scaffolding. `gen-cron.sh` resolves `[excluded:]` first into one CONFIG-wide `PROTECT_FLAGS` fragment and pastes it onto **every** generated snapshot-prune line, including prune lines belonging to relationships/tasks that existed before the new relationship was added.

Therefore the Phase-2 CREATE-only invariant is still false for this case:

```text
add one new independent relationship
        -> old relationships/policy must remain unchanged
```

A new relationship can currently cause old prune jobs to receive new/different `-P` protection semantics merely because the new relationship crossed a policy-generating boundary.

## F1 — P1 — new additive relationship may silently rewrite effective retention policy of old relationships

Current shape after REV-091:

```bash
if [ "$needs_profile" -eq 1 ]; then
    ... append profile templates ...
fi
...
if [ "$needs_profile" -eq 1 ]; then
    for prefix in "__replicate_" "vzdump" "__migration__"; do
        missing -> append [excluded:<prefix>] keep = 2
    done
fi
```

For a first relationship in a new CONFIG, installing initial CONFIG-wide defaults is reasonable.

For an additive CREATE into an **already-populated native CONFIG**, it is not. If the administrator deliberately removed or customized one of these global sections after the original CREATE, adding a disjoint new relationship must not silently restore it. Because `gen-cron.sh` applies `PROTECT_FLAGS` globally, that restoration changes the effective prune command of pre-existing relationships as well as the new one.

This is exactly the class Gate 2 promises to forbid: **preset may add new but cannot mutate old**.

REV-091's section-51 positive guard proves only that a policy-creating call on a newly initialized fixture installs the floors. It does not exercise additive CREATE into an existing config containing an unrelated established task, so it cannot distinguish initial-config scaffolding from forbidden shared-policy mutation.

## Required correction

Keep the reduction-oriented architecture. Do not invent per-relationship exclusion policy or a merge framework.

The smallest acceptable property is:

- initializing a genuinely new CONFIG may install the standard CONFIG-wide safety defaults;
- explicit migration may deliberately change global policy with preview/confirmation;
- adding a new independent relationship/task into an already-populated CONFIG must **reuse the installed CONFIG-wide `[excluded:]` state exactly as it exists** and must not repair, normalize or restore it as a side effect;
- if a new relationship cannot be safely created under the installed global policy, REFUSE clearly rather than mutating old policy silently.

## Minimal discriminating proof

Use the real additive activation/composition boundary:

1. build/install relationship A into a shared CONFIG through the normal CREATE path;
2. customize the installed global `[excluded:]` state (e.g. remove or change one standard entry) while keeping CONFIG valid;
3. record/render A's prune line before the second CREATE;
4. create disjoint relationship B in the **same CONFIG** through the normal first-activation path;
5. prove A's effective rendered prune command/policy is unchanged and the customized global `[excluded:]` state was not silently repaired;
6. prove B is added successfully if the existing global policy is acceptable;
7. negative control against `05816e808a97fc6c49ef4842a50b136b1231322f` must show the missing standard `[excluded:]` is restored and A's rendered prune semantics change;
8. dependency-selected cascade + `./test/impact.sh --verify` with real exit status.

No live ZFS/SSH campaign is required if the correction remains deterministic CONFIG composition. If the proposed fix changes actual install/rollback semantics, reassess at that boundary.

## Phase impact

REV-091 itself remains correctly APPROVED/CLOSED: pure topology reactivation is fixed.

This is a separate defect in **Phase 2 / additive CREATE**. Gate 2 must be treated as reopened until this property is proved. By the canonical sequencing rule, later functional expansion (including Phase 4 public preset UX) remains blocked until REV-092 is resolved.
