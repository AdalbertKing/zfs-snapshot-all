## F1 — P1 — same-client-name refusal stops before `cmd_seed()` and therefore cannot prove seed-time refusal

- Severity: P1
- Blocking: yes, for closing REV-083/085 and Gate 1
- Affected: `docs/project/ACTIVE-WORK-PLAN.md`, `docs/internal/reviews/responses/REV-20260809-085.md`, Phase 1 live-proof acceptance

### Evidence

The active plan says Phase 1 should create one real relationship and then:

```text
Make one real second-add refusal using the existing client name
```

It also still states that genuine cross-client parent/child overlap is structurally unreachable because distinct relationship names create distinct LABEL namespaces.

Both statements are now incompatible with the code and with Claude's own corrected REV-085 response:

1. `load_client_and_connection()` derives `LOAD_LABEL` from `peer_label(PEER_HOST)`, not from `CLIENT_NAME`.
2. Therefore two differently named relationships using the same peer can share the same target/label namespace.
3. REV-085 exists precisely because such a second relationship could previously enter `cmd_seed()` and perform a real receive before the activate-time overlap guard.
4. A second `add-client` using the **same client name** is rejected by the existing client-name uniqueness check before the candidate can reach `cmd_seed()`.

The REV-085 response explicitly proposes the same-name refusal as the live proof and says this "also exercise[s] this exact boundary" because the second add is refused before `seed`. That conclusion is backwards: refusal before `seed` proves that an earlier name-uniqueness guard works; it does **not** execute or prove the new seed-time `assert_no_coverage_overlap()` call at all.

A test cannot prove a boundary that it never reaches.

### Consequence

If Phase 1 is executed exactly as currently written, it can produce a green transcript while leaving the only environment-dependent part of REV-085 untested:

```text
add-client SAME_NAME -> name-existence refusal
                       -> cmd_seed() never entered
                       -> seed-time overlap guard never evaluated
                       -> no evidence about real receive boundary
```

The same transcript also cannot be treated as a live `path_overlaps()` refusal for REV-083, because it fails on identity uniqueness rather than coverage overlap.

This is especially important because the stale "distinct names -> distinct LABEL" premise in `ACTIVE-WORK-PLAN.md` is exactly the premise disproved by REV-085.
