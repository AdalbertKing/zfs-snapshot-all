## F1 — P2: a relationship moved to another host cannot add a source through its active endpoint

- Severity: **P2**
- Blocking: **yes for `add-source` on a relationship whose active endpoint host
  differs from its original pairing host**
- Affected: `zfs-backup.sh`, `cmd_add_source()`, construction of the
  `rux_root_ssh` destination for steps 1 and 2.

### Evidence

`ACTIVE_ENDPOINT` is the address currently verified and used by the installed
relationship. The repository already has the canonical parser
`active_endpoint_host_port()`, which returns the host and port as one tuple.
`cmd_add_source()` instead builds another tuple:

```bash
local peer="${PEER_HOST:-}" state="${STATE:-}" port=22
case "${ACTIVE_ENDPOINT:-}" in *:*) port="${ACTIVE_ENDPOINT##*:}" ;; esac
...
rux_root_ssh "$peer" "$port" ...
```

After `set-endpoint` changes `lan.example:22` to `vpn.example:2222`, this sends
both remote management calls to `lan.example:2222`. The helper used by the
rest of the endpoint state machine returns `vpn.example 2222` for the same
record.

Safe reproducer using the production command with only client-record and SSH
functions stubbed:

```bash
bash docs/internal/reviews/evidence/REV-20261025-175-add-source-endpoint.sh \
  ./zfs-backup.sh
```

Result on exact PR head and inspected current main:

```text
active_endpoint=vpn.example:2222
attempted_endpoint=lan.example:2222
command_rc=1
REPRODUCED: add-source mixed the original host with the active endpoint port
```

The exact-head focused suite passes 7/7. Running those head tests against the
exact base yields 0/8 because the command and scope mutator do not exist there.
Neither set exercises a changed endpoint. Exact-head CI run `37745914631`,
`impact --verify`, and exact-range `diff --check` pass, so green CI does not
cover F1.

### Failure mode and impact

The first `zfs list` probe normally fails against the nonexistent mixed
address, and the command stops before changing the source scope. Fail-closed
data safety is preserved, but the advertised operation is unavailable after a
supported endpoint migration. If the old hostname still resolves, the attempt
is also directed at an endpoint the relationship did not verify. Strict host
key checking normally limits that case to another refusal; this review does not
claim that a wrong host accepted the command.

The same tuple-construction pattern exists in adjacent older lifecycle verbs.
F1 is proven for the new `add-source` path introduced by PR #476. The
implementation should audit those sibling call sites rather than copy another
mixed tuple, but this finding does not assert an unmeasured destructive effect
in them.

### Acceptance criteria

- [ ] Both remote `add-source` steps use one coherent, parsed management
  endpoint. Host and port must come from the same authoritative record shape.
- [ ] A new-shape record with `PEER_HOST=lan.example` and
  `ACTIVE_ENDPOINT=vpn.example:2222` calls the SSH wrapper with
  `vpn.example`, `2222`.
- [ ] Preserve compatibility for the legacy named-slot endpoint shape and the
  ordinary same-host/default-port case.
- [ ] Keep the original pairing identity for record/label ownership; changing
  the connection tuple must not rename the relationship or its source scope.
- [ ] Add a negative control proving that no remote write or local record/config
  change occurs when the coherent active endpoint is unreachable.
- [ ] Audit `remove-source` and `delete-relation` for the same mixed tuple and
  either use the shared endpoint resolver or document, with a test, why a
  different management route is authoritative.

### Required verification

- Automated: focused `addsource` tests including changed host+port, same host
  with changed port, legacy slot, and unreachable endpoint; this evidence
  reproducer against old and fixed code; all suites selected by
  `./test/impact.sh <range>`; `./test/impact.sh --verify`; `git diff --check`;
  exact-head CI.
- Manual: no live-host test is required to prove tuple selection. If the
  implementer supplies operational evidence, use a disposable dataset and
  report the exact route without changing production relationships.

### Notes and uncertainty

The reproducer does not open a socket, edit a scope, install cron, or touch ZFS.
It proves the arguments passed to the production SSH wrapper and the early
fail-closed result. It does not prove availability or root access on either
address. The reviewer made no production-code fix.
