# REV-20260812-114 — Phase 7 slice 2 SAFE restore cleanup ownership race

## Verdict

CHANGES REQUIRED. The slice is directionally correct and the live/stub evidence found several important defects before delivery, but the central failed-attempt ownership claim is still not durable. The current implementation can destroy a dataset created by another actor after the initial collision check.

## Verified scope

The following parts are accepted as the right shape and are not being reopened by this finding:

- safe restore is `restore --dataset=X --snapshot=S`, while destructive replacement remains a separate later verb;
- the final landing path is derived and never the production source path;
- acceptance requires BOTH successful `zfs send | zfs recv` and GUID equality;
- the source GUID is read before the transfer and the restored GUID is checked afterwards;
- a pre-existing landing dataset found by the initial collision check refuses;
- the cleanup root is clamped so an ancestor-listing failure cannot walk destruction outside the restore namespace;
- the targeted suite covers receive failure, GUID mismatch, failed cleanup, collision refusal, and namespace derivation;
- the reported live pve1 end-to-end proof is useful evidence for real `zfs recv` parent requirements and the successful send/receive/GUID path.

## F1 — collision-first does not prove later cleanup ownership (TOCTOU)

The implementation makes this inference:

> collision refusal runs first -> therefore anything present after a failed attempt was created by this run

That implication is only true if nobody can create the landing path between the check and the later receive/cleanup. The code does not establish such exclusivity.

A concrete destructive race remains:

1. restore A checks `zfs list LANDING`; LANDING is absent;
2. before A's receive, restore B or an administrator creates LANDING;
3. A reaches `zfs recv -u LANDING`; the receive fails because the destination now exists or otherwise fails;
4. A enters the failure path;
5. with no newly-created ancestor recorded, A chooses `victim=LANDING` and executes `zfs destroy -r "$victim"`;
6. the dataset created by B/the administrator can be destroyed even though A never owned it.

The same class of race applies to inferred ownership of newly-created restore-namespace ancestors. Temporal ordering is not an ownership proof.

This violates the slice's safety contract: a SAFE restore may clean up only artifacts it can prove were created by that attempt.

## Required correction

Use the smallest mechanism that makes cleanup ownership durable rather than inferred from a one-time absence check.

Acceptable shapes include a per-attempt unique staging dataset followed by verified promotion to the predictable final landing, or another design that provides equivalent proof. A cooperative lock by itself is insufficient if an unrelated administrator can still create/replace the ZFS path while the run is in progress; if locking is part of the solution, destructive cleanup still needs a fact tying the victim to this attempt.

Required properties:

1. The predictable final landing path remains the public result on success.
2. A failed receive or GUID mismatch can clean up only an artifact demonstrably owned by this attempt.
3. A dataset created after the initial collision check by another actor must survive untouched.
4. A concurrent final-landing collision must fail closed rather than overwrite, adopt, rename around, or destroy the competing dataset.
5. Retry after an ordinary failed attempt remains clean; no new lifecycle/state machine is required.
6. Cleanup must remain clamped away from the pool/production namespace.

## Required evidence

Add a discriminating negative control that injects a dataset at the final landing **after** the initial collision check but before receive/promotion, then proves:

- the restore fails;
- the injected dataset still exists;
- no destroy targets that dataset or any ancestor that contains it.

Keep the existing receive-failure, GUID-mismatch, cleanup-failure and happy-path tests.

If the correction introduces a real-ZFS primitive whose semantics the stubs cannot prove (for example rename/promotion behavior), add one focused disposable-dataset live proof of that primitive. Then run `test/restore` plus only dependency-selected suites and `./test/impact.sh --verify`; no broad campaign is requested unless the graph requires it.
