## F1 — reconcile bypasses normal pull-config validation

- Severity: **P1**
- Blocking: **yes, for Stage 4 acceptance**
- Affected: `gen-cron.sh` control flow / shared config validation, `test/reconcile/run.sh`

The follow-up in REV-071 explicitly required not only replacing the malformed pull fixture, but also making reconciliation share or invoke the same validity boundary as normal generation.

Current `gen-cron.sh` still does:

```text
build_entities
group_send
...
if [ "${RECONCILE:-0}" -eq 1 ]; then
    do_reconcile
    exit $?
fi

emit_send
...
```

The suffix contract for pull (`local dataset path must end with the literal remote dataset path`) is enforced by `emit_send`. Therefore `--reconcile` still exits before that validation. The old malformed shape can still be audited even though normal cron generation rejects it.

Replacing the test fixture with a valid pull proves the happy path, but it does not prove rejection parity.

### Required minimal fix

Factor or invoke the relevant semantic validation before the reconcile branch so that every config accepted by `--reconcile` satisfies the same transfer-validity checks required by normal generation. Do not make `--reconcile` emit cron or mutate state; this is validation reuse, not a second generation path.

### Decisive regression

Use the previously exposed malformed pull shape (for example `[dataset:tank/incoming]` with `src=root@far:far/data`) and prove BOTH commands reject it with non-zero status:

1. normal generation;
2. `--reconcile`.

Keep the current valid-pull regression as the positive control.
