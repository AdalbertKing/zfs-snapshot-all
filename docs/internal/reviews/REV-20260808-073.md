# REV-20260808-073 — Stage 5 ownership boundary: profile policy must not own dataset selection

Review time: 2026-08-08 16:32:45 CEST
Reviewed main: `f26d20feacd9602df00d47a15b62cbe57c7a6652`
Response path: `docs/internal/reviews/responses/REV-20260808-073.md`

## Verdict

**CHANGES REQUIRED before Stage 5 runtime implementation.**

This is a pre-implementation contract correction, not a request to change the frozen transfer engines.

## F1 — P1 — `PLAN-2026-08-07.md` assigns dataset selection to the wrong layer

The Stage 5 plan currently says that the profile "trzyma selektor" and then defines `effective = selektor ∩ grant`.

That wording conflicts with the more precise architecture already agreed elsewhere and with the Owner's clarification on 2026-08-08:

- `docs/discussions/DEPLOY-UX-AGREED-POSITION.md` says that after enroll the collector connects to pve2, obtains the available datasets, the deployment/relationship selects the data, and pve1 builds the final local CONFIG v4;
- the same document says pve2 only exposes selected datasets while pve1 owns target, schedule, retention and transfer policy;
- `docs/discussions/AI-BRAINSTORM-SYNTHESIS-2026-08-07.md` separates `CONFIG v4 / profile policy` from `Relationship / endpoint`, where concrete deployment facts include source/target and granted scope;
- that synthesis defines profile policy as reusable **how-to-back-up** intent: cadence/schedule baseline, retention/GFS, recursion, monitoring, consistency/quiesce and autotune, while explicitly excluding topology, source/target mapping and grant authority.

The Owner has now made the intended UX boundary explicit:

> The dataset list is discovered during `zfsbackup -> deploy` from pve2 and the deployment process decides **what** is backed up. A profile defines **how** it is backed up and **how long** it is retained.

Those two concerns must not be collapsed in Stage 5.

### Required contract

Use this ownership split:

```text
DEPLOY / RELATIONSHIP
    discovers datasets on pve2
    selects what is in scope
    owns source/target mapping
    owns granted scope / endpoint facts
                |
                +-------------------+
                                    |
PROFILE                             |
    defines how to back up          |
    cadence / retention / GFS       |
    recursion / monitoring          |
    quiesce / autotune              |
                |                   |
                +---------+---------+
                          |
                    effective CONFIG v4
                          |
                      gen-cron.sh
```

A built-in or custom profile must therefore **not contain or select concrete dataset names** and must not become the authority for dataset/grant scope.

Stage 4 reconciliation may compare discovered, selected, granted and effective scope, but that does not transfer ownership of the selector into the profile.

## Acceptance criteria

1. Correct the Stage 5 planning/contract documentation so it no longer says or implies that the profile owns the dataset selector.
2. State explicitly that dataset discovery and selection belong to `zfsbackup -> deploy` / relationship state.
3. State explicitly that the profile owns reusable backup policy only: how/when/retention/recursion/monitoring/consistency/autotune as supported by native CONFIG v4 fields.
4. Preserve the existing prohibition on profile-owned relation fields (`src`, `dst`, topology, grants, endpoint/key material, raw flags).
5. Show the intended `default` profile without concrete datasets, and show separately how deploy-selected datasets are combined with that profile into effective CONFIG v4.
6. Do not begin a runtime selector/profile implementation based on the old wording.

## Proof required

This is primarily a contract/documentation correction. The smallest sufficient proof is:

- exact documentation diff establishing the ownership boundary above;
- existing `test/profiles` still green, including rejection of relationship-owned fields;
- `./test/reviewctl.sh --verify` / normal review protocol verification;
- if code is changed beyond documentation, run only the dependency-selected tests implied by that diff.

No ZFS/live-host campaign is required for this contract correction alone.

## Reviewer note

This finding is intentionally raised **before** Stage 5 implementation because correcting ownership after profile runtime exists would be substantially more expensive and could create a second source of truth for backup scope.
