# REV-20260908-138 — list-jobs hides an installed block when its config cannot be opened

Review date: 2026-09-08
Reviewer: ChatGPT
Reviewed delivery: PR #357, implementation `1f6a1b38454824d9bf73bfbf6e017f0fc160f856`
Canonical merge checked: `edccdce28938ed25c7bcd1fc715de46026d168d4`

## Verdict

**CHANGES REQUIRED — P2: `list-jobs --json` returns success and an empty,
healthy-looking result when an installed managed block points at a regular
config file that the parser cannot open. The parser error reaches stderr, but
the promised `unreadable` record is empty.**

The source-header design, the four direction labels and the separation between
job rows and unreadable diagnostics are not rejected. The blocker is confined
to checking the config-reading boundary before publishing the JSON document.

## F1 — P2 BLOCKING — config_section_dump failure is lost behind process substitution

- Severity: P2
- Blocking: yes
- Affected: `cmd_list_jobs()` and its `config_section_dump` loop in
  `zfs-backup.sh`; the `listjobs` controls in `test/zfsbackup/run.sh`.

### Evidence

On exact implementation `1f6a1b38454824d9bf73bfbf6e017f0fc160f856`,
the reviewer installed a fixture block containing one engine line and this
source header:

```text
# BEGIN zfs-backup-managed -- Source: /proc/1/mem
5 * * * * /r/snapsend.sh x y
# END zfs-backup-managed
```

On this Linux runner `/proc/1/mem` is a regular file (`test -f` succeeds) but
opening it is refused. It therefore exercises the distinction the command's
own contract promises: the block is present and running a line, while its
declaration cannot be read.

Observed:

```text
rc=0
stdout={"host":"localhost","jobs":[],"count":0,"unreadable":[]}
stderr=awk: cannot open "/proc/1/mem" (Permission denied)
```

`cmd_list_jobs()` checks only `[ -f "$cfg" ]`, then consumes
`config_section_dump "$cfg"` through process substitution. The exit status of
the producer is not checked, so the failed read looks exactly like a config
containing no sections. The existing negative fixture uses a nonexistent path;
that fails the earlier `-f` check and therefore cannot cover this boundary.

The same failure shape applies to an ordinary root-owned config read by a
delegated account: existence is not readability, and stderr is not part of the
JSON contract a front end iterates.

### Failure mode and impact

The verb was added specifically to prevent an active host from appearing empty
when relationship records are absent. In this case it recreates that exact
failure: a managed block has a running engine line, yet a GUI trusting `rc=0`,
`count` and `unreadable` sees no work and no diagnostic. It does not itself
mutate cron or ZFS, so the finding is P2 rather than a data-safety P1.

### Existing verification and why it missed the defect

- PR #357 CI is green; merge run `34213892873`.
- The submitted focused suite reports `365 PASS / 0 FAIL`.
- Its unreadable-config case names a file that does not exist. That exercises
  the path-presence check, not a parser/open failure after `-f` succeeds.

### Acceptance criteria

1. Buffer and check the complete config parse before emitting any job rows for
   that block; do not infer an empty config from a failed parser.
2. A regular config that cannot be opened must produce no element in `jobs`,
   must produce one `unreadable` element naming the account/config and
   `lines_in_block`, and must not leave a partial JSON document.
3. Keep the command's reporting exit policy explicit. If `rc=0` is retained,
   the machine-readable `unreadable` entry must be complete and sufficient for
   the GUI to show a non-green state.
4. Add a discriminator in which the source path passes the regular-file check
   but `config_section_dump` fails. A nonexistent-path test alone is not
   sufficient.
5. Preserve the five valid job rows, the push/pull/local/snapshot/prune
   classification, source-header lookup and exclusion of foreign cron lines.

### Required verification

- automated: focused `listjobs` controls with the failed-open discriminator;
- negative control: the discriminator above must fail against
  `1f6a1b38454824d9bf73bfbf6e017f0fc160f856` with `unreadable:[]`;
- consistency: `./test/impact.sh --verify` and exact-head CI.

No ZFS, fleet, destructive or full product campaign is required. A synthetic
cron block and a regular path whose open fails decide the issue.

## Required response

Publish one exact implementation SHA reachable from canonical `main`, explain
how the parser result is buffered and checked before JSON publication, and
report only the focused controls, impact verification and exact-head CI.
