## F1 — P1: a `prune_foreign` rewrite can silently weaken an existing protected family

- Severity: **P1**
- Blocking: **yes for relying on the install guard before a destructive
  `prune_foreign` reactivation**
- Affected: `zfs-backup.sh`, `foreign_normalized_identity()` and the seventh
  exception in `assert_target_block_not_clobbered()`.

### Evidence

The seventh exception must recognize one intended transition: the finest
`delsnaps.sh` tier changes from its family pattern to an empty pattern and gains
generated `-P "<other-family>:all"` / `-P "<replica>:2"` protections. Its
normalizer currently removes **every** `-P` token from both installed and
proposed lines:

```bash
sed -E -e '/delsnaps\.sh/ s/ -P "[^"]*"//g' \
       -e '/delsnaps\.sh/ s/ "[^"]*"( -[HDWMYhdwmy][0-9 ])/ "<PAT>"\1/'
```

That also removes pre-existing, independent `[excluded:]` floors. The shipped
guard therefore distinguishes `vzdump:2 -> vzdump:0` when it is the only
change, but accepts the same weakening when it accompanies the empty-pattern
U4 rewrite.

Safe reproducer using the actual shipped guard, a stub read-only `crontab`, and
no ZFS or installation:

```bash
bash docs/internal/reviews/evidence/REV-20261024-174-prune-foreign-guard.sh \
  ./zfs-backup.sh
```

Result on inspected main:

```text
plain_protection_change_rc=1
combined_foreign_and_protection_change_rc=0
u4_only_rc=0
REPRODUCED: prune_foreign exception hides an unrelated -P protection change
```

The exact-head U4 tests are otherwise useful and pass: historical
`test/cron` 165/165, `test/cron2conf` 35/35, `passivepick` 12/12 and
`mirrorguard` 8/8. Replacing the three production files with exact base
versions produces the advertised 7, 4, 1 and 1 failures. Current main also
passes generator 123/123, cron 230/230, passivepick 15/15 and mirrorguard 8/8.
The hole remains because mirrorguard tests changed retention count and pattern,
but never changes an existing `-P` floor during the U4 transition. PR #465
exact-head CI run `37522116804` succeeded and therefore does not cover F1.

### Failure mode and impact

An installed line can protect the two newest `vzdump` snapshots while the
proposal simultaneously enables the empty-pattern foreign carrier and changes
that floor to zero. The guard reports only the named, allowed U4 conversion and
returns success. On the next real retention run, `delsnaps.sh` matches every
unprotected family because the pattern is empty; older `vzdump` snapshots now
compete in the finest tier and can be deleted. The same bypass applies to any
unrelated explicit `-P` prefix/count change hidden beside the U4 rewrite.

This evidence proves the fail-open installation decision and the resulting
destructive command shape. The reviewer did not install cron or run ZFS and
does not claim a live snapshot was deleted.

### Acceptance criteria

- [ ] The `prune_foreign` exception accepts the intended pattern rewrite and
  only the protections deterministically added by that rewrite.
- [ ] Every pre-existing explicit `-P prefix:keep` protection remains equal in
  the proposed line, or the install is refused by the ordinary destructive
  guard. A changed count, removed prefix, or newly relaxed unrelated prefix
  must not be erased by normalization.
- [ ] Add regression cases for `vzdump:2 -> vzdump:0` and removal of an
  unrelated protection during the empty-pattern transition; both must fail
  closed. Keep a positive control for the exact U4-only transition.
- [ ] Preserve existing refusal of changed retention count, changed non-empty
  pattern, remote `prune_foreign`, and unrelated lost jobs.
- [ ] Run the focused guard suite, U4 generator cases, the evidence reproducer
  against old and fixed code, `bash test/impact.sh --verify`, `git diff
  --check`, and exact-head CI.

production-code fix.

## Reviewer verification of PR #849 — 2026-10-25

Exact submitted PR head inspected: `096c9433e07dbf4f74e54b7947b844571c62fcdb`;
implementation commit declared by the response:
`084aabef741e6865aa8a24ab9d87ca80011e153c`. The response correctly fixes the
confirmed weakening/removal cases, but **F1 remains CHANGES-REQUIRED** because
the first acceptance criterion is not met.

`foreign_protections_kept()` permits every newly-added token whose suffix is
`:all` or `:2` and whose prefix was not already present. It has no input that
identifies the protections deterministically emitted by `apply_foreign_prune`.
A proposed line that keeps `-P "vzdump:2"` but also adds an unrelated
`-P "manual:all"` therefore follows this path:

1. the installed token is still present;
2. `manual` was not an installed protected prefix;
3. the suffix `all` passes the shape-only case;
4. the function returns success, while `foreign_normalized_identity()` erases
   both protections and the seventh exception accepts the line as the same job.

This is a direct counterexample to “only the protections deterministically
added by that rewrite”. It can silently add an unrelated permanent protection,
prevent expected pruning of a real family and create unbounded capacity
pressure. It is not the original deletion direction, but it is still an
independent retention-policy change hidden by the same exception and therefore
continues F1 rather than opening a new REV.

Required continuation:

- carry the exact generated protection set (or equivalent provenance) from
  gen-cron into the comparison, so shape alone is insufficient;
- add negative controls for an ungenerated new `:all` and `:2` token, while
  retaining the exact U4 positive control and the weakening/removal controls;
- rebase the implementation onto current `main` and provide exact-head CI.

Evidence boundary: this verdict is a static, line-by-line counterexample against
the submitted production function. GitHub reports no pull-request workflow run
