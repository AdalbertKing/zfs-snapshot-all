## F1 — P1: `new_account_drop_inherited_grants` fails open when ZFS inventory or ACL reads fail

- Severity: **P1**
- Blocking: **yes** for creating delegated relationship accounts
- Affected: `deploy.sh`, `new_account_drop_inherited_grants()`, and both post-`useradd` call sites in join and standalone account creation

### Evidence

The U42 guard is meant to ensure that a newly created account starts with no inherited destructive ZFS rights when Linux reuses an old UID. The shipped function enumerates datasets through process substitution and suppresses its status:

```bash
while IFS= read -r ds; do
    ...
done < <(zfs list -H -o name -t filesystem,volume 2>/dev/null)
```

For every dataset it also suppresses the permission-read error and pipes it into `grep`:

```bash
zfs allow "$ds" 2>/dev/null | grep -qE "^[[:space:]]+user $account " || continue
```

Consequently, a failed inventory is indistinguishable from an empty inventory, and a failed ACL read is indistinguishable from an ACL without the account. The later `zfs unallow` path does abort on failure, but it is never reached when discovery fails.

The reviewer extracted the exact function from published `deploy.sh` and invoked it with deterministic `zfs` stubs. No production file or live ZFS host was modified:

```text
listfail rc=0 out=''
allowfail rc=0 out=''
clean rc=0 out=''
```

`listfail` made `zfs list` return 41. `allowfail` returned one dataset from `zfs list` and made `zfs allow` return 42. Both failure cases incorrectly returned success, exactly like the clean no-grants control.

The existing U42 draftscope test covers matching output and successful/failed `unallow`, but it does not inject either read failure. `bash test/draftscope/run.sh` reported **54 PASS / 1 FAIL** locally: the U42 case passed; the sole failure is an unrelated runner-local `su: System error` in the pre-existing execution-reaches-past-validation case. `bash test/impact.sh --verify` passed. GitHub Actions on final PR #639 head `8f1b5f625ba6fc5032ff71461529ec2c01239de5`, run `39443794866`, was green, but contains no negative control for these reads.

### Failure mode and impact

If either read fails after `useradd`, deployment continues as though the recycled UID had no inherited grants. An old dataset delegation can therefore survive account creation and cross relationship boundaries before the new relationship adds its intended permissions. Depending on the stale grant, this can include destructive ZFS operations. The guard's core safety postcondition — a new delegated account starts with no pre-existing rights — is not established.

### Required outcome / acceptance criteria

- [ ] A nonzero `zfs list` used for this inventory aborts the account setup with a clear diagnostic; it must not mean “no datasets”.
- [ ] A nonzero `zfs allow <dataset>` aborts the account setup; it must not mean “no matching grant”.
- [ ] Capture and check command output/status explicitly. Do not rely on the exit status of a process-substitution loop or a pipeline that collapses read failure into a negative match.
- [ ] Add deterministic tests on the shipped function or its actual call boundary for: inventory failure, ACL-read failure, clean no-grants inventory, matching grant with successful revoke, and matching grant with failed revoke. Negative controls against `990e265409adf010fc7b27fccf440fe5308a5bb8` must demonstrate that the two read failures return success.
- [ ] Preserve both post-`useradd` call sites and prove the guard finishes successfully before any new ZFS delegation, relationship manifest, or key/state mutation is created.
- [ ] Run `test/draftscope`, affected deployment tests, `test/impact.sh --verify`, and CI; publish the exact implementation SHA and any unperformed manual obligations in `docs/internal/reviews/responses/REV-20261021-163.md`.

### Notes and uncertainty

The reproducer uses the exact published shell function with mocked command results. It proves the exit-status defect and indistinguishable outcomes, but does not create a real user, change a real ZFS delegation, or operate on a live host. Those actions are neither required nor authorised for this finding.
