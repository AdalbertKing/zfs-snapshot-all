# REV-20261023-172 — limit oczekiwania pozwala wykonać akcję na starym wierszu

Reviewer: ChatGPT/Codex. Date: 2026-10-23.

This is new executable evidence against the H-3 safety promise recorded in
`docs/PROJECT_STATUS.md`: after a child window, every key is supposed to wait
for fresh data before acting. It does not re-adjudicate REV-20261023-171's

## F1 — P1: after 30 seconds an action is dispatched against stale GUI data

- Severity: **P1**
- Blocking: **yes for treating post-dialog actions as freshly targeted**
- Affected: `tui/zfs-tui.py`, `UI.key()` background-refresh gate and
  `run_verb()`.

### Evidence

The background collector runs the six read-only verbs in threads. `run_verb()`
uses `subprocess.run()` without a timeout, so a reader can remain alive for an
unbounded time. Before handling a key, `UI.key()` waits only 30 seconds:

```python
if bg is not None and bg[0].is_alive():
    bg[0].join(30)
    self.poll_bg()
```

If the thread is still alive, `poll_bg()` returns false and key processing
continues on the old rows. The safe reproducer blocks only the substituted
read-only collector, presses `del`, observes the scheduled command, and never
executes it:

```bash
python3 docs/internal/reviews/evidence/REV-20261023-172-stale-bg-timeout.py \
  tui/zfs-tui.py
```

Result on the inspected main:

```text
elapsed=30.00 result=shell alive=True row=stale-relation
scheduled=... /tmp/zfs-backup.sh delete-relation stale-relation --ask
after_release_row=fresh-relation
```

A shorter positive control with the same production methods released the
collector after 0.15 seconds: `UI.key()` waited, applied `after-save`, cleared
the lazy config cache, and only then moved the cursor. Therefore normal
post-save readback works; the failure is specifically the reachable timeout
boundary.

### Failure mode and impact

After a successful edit, creation or deletion, the GUI immediately returns
with explicitly stale rows while refreshing. If any reader takes more than 30
seconds, the next navigation or action continues against that stale snapshot.
The reproducer schedules deletion of the old relation; the same gate precedes
immediate actions such as F7, matching the class of wrong-row execution H-3
was intended to prevent. The dialog or command may still add its own checks,
but the TUI's asserted fresh-target guarantee has already failed.

This proves stale command selection without executing a command. It does not
claim that a live reader hung or that data was deleted.

### Acceptance criteria

- [ ] While a full background refresh is alive, no navigation or action may be
  dispatched against the pre-refresh rows, regardless of elapsed time.
- [ ] If waiting is bounded, expiry must fail closed: keep the old screen
  visibly marked stale, report that refresh is still pending or failed, and
  schedule no action from that key.
- [ ] Preserve the immediate return to the GUI and the normal successful path:
  once fresh data is applied, the user's next action targets the refreshed
  row and the full refresh invalidates lazy profile/config caches.
- [ ] Add a deterministic regression whose collector remains alive beyond the
  action-wait boundary and assert that no stale relation/replica/job command is
  scheduled; then complete the collector and assert the next action uses the
  fresh identity.
- [ ] Cover at least one immediate action (F7) and one dialog action (Del or
  edit). Run focused TUI tests, `bash test/impact.sh --verify`,
  `git diff --check`, and exact-head CI.

### Evidence boundary

The reproducer imports the shipped TUI and replaces only its collector with
two in-memory snapshots plus an event. It performs no ZFS, network, account,
cron, configuration, subprocess or live-host operation. It inspects a command
that `UI.key()` prepares but does not execute. The reviewer changed no
production code.
