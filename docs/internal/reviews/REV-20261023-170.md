## F1 — P1: `<pool>/restore` permission has no owner/reference accounting

- Severity: **P1**
- Blocking: **yes for treating concurrent Restore grants to one peer/pool as
  independently valid**
- Affected: `deploy.sh`, `restore_grant_namespace_delegate()` and the namespace
  loop in `do_deny_restore()`.

### Evidence

PR #553 maps every dataset scope on a pool to the same object,
`<pool>/restore`. Issuing a grant executes:

```text
zfs allow -u <account> <restore-perms> -- <pool>/restore
```

Revoking that label later executes the matching `zfs unallow` unconditionally.
ZFS stores a delegated permission set for `(dataset, account)`, not one copy per
BackUpAll relationship label. Two relationships to the same peer normally use
the same `zfsbackup-<peer>` account; disjoint scopes on one pool are permitted.
Their namespace capability therefore collapses to one tuple.

The safe executable reproducer runs current `deploy.sh` with two disposable
relationship manifests and a stateful fake ZFS permission set:

```bash
bash docs/internal/reviews/evidence/REV-20261023-170-shared-restore-namespace.sh
```

Result on the reviewed main:

```text
PASS both grants are issued
PASS their shared namespace capability exists
PASS revoking the first grant reports success
PASS the second grant file is still active
PASS but its shared namespace capability is gone (reproduced)
PASS=5 FAIL=0
```

The discriminating trace contains two identical `allow` calls followed by one
identical `unallow`:

```text
allow -u backup-shared receive,rollback,create,canmount,mountpoint,mount -- tank/restore
allow -u backup-shared receive,rollback,create,canmount,mountpoint,mount -- tank/restore
unallow -u backup-shared receive,rollback,create,canmount,mountpoint,mount -- tank/restore
```

After `--deny-restore=one`, grant `two` remains on disk and its scope delegation
remains, but it can no longer create/receive a recovery beside the original.
The first revocation returns 0 and resumes its writers, so neither status nor
exit code reveals that the other active permission promise was broken.

PR #553's section 13 tests cover one grant only: allow, re-allow, then deny.
They correctly prove creation, delegation, idempotent re-application and final
revocation, but cannot distinguish an unconditional revoke from a last-owner
revoke. Its exact-head GitHub Actions run `38787893215` is completed/success.
Later REV-147 changes preserve the same namespace `unallow` loop and do not add
cross-label ownership accounting.

### Impact

During recovery, withdrawing one relationship can silently make another
visible, active grant unusable for the owner-selected “beside the original”
path. The remaining grant and pair gate still say the operation is authorized,
so the fault appears only when ZFS refuses creation/receive at incident time.
No data destruction was executed or observed in this review.

### R1 — P1 BLOCKER: two concurrent `--deny-restore` calls leave the shared ZFS capability delegated forever

**Exact affected code** in `deploy.sh`:
- `do_deny_restore()` atomically moves its **own** `grants/<label>` to `grants.revoking/<label>`, not a transaction covering all labels that share `(account, <pool>/restore)`.
- `restore_ns_other_owners(self, account, namespace)` enumerates OTHER labels in both `grants/` and `grants.revoking/`. It treats a pending revocation as a reason to **skip** the shared namespace `zfs unallow`.
- The caller does `_rd_others="$(restore_ns_other_owners ...)"`, and if nonempty, `continue` past `zfs unallow`. Later it unlinks its own pending record and resumes its writers.
- No `flock` or equivalent cross-process lock exists around this permission/record transition; the `--deny-restore` command dispatch directly enters `do_deny_restore`. The full published `deploy.sh` was checked for locking.

**Reachable counterexample with two active labels `one`, `two` using the same account `backup-shared` on `tank`:**

1. Process A moves `grants/one` to `grants.revoking/one`.
2. Process B moves `grants/two` to `grants.revoking/two`.
3. A asks for other owners of `(backup-shared, tank/restore)`: sees `two` (pending); **skips namespace unallow**.
4. B asks: sees `one` (pending); **also skips namespace unallow**.
5. A and B both report successful withdrawal and remove their respective pending records. Neither call executed `zfs unallow` for the shared namespace.

Final state: **zero active and pending grant records, but `backup-shared` still has `create,receive,rollback,canmount,mountpoint,mount` on `tank/restore`.** Subsequent `--deny-restore=one` or `two` takes the no-grant no-op branch and cannot recover the leaked capability automatically. This is more serious than a temporary inability to restore: revocation is falsely reported complete while permissions remain delegated.

**Independent verification boundary:** I executed a deterministic disposable state-transition simulation with two labels moved into `grants.revoking` before either checks `restore_ns_other_owners`. It returned `other_owners_seen={one:[two],two:[one]}`, `remaining_records=[]`, `shared_permission_still_active=true`. This demonstrates the exact interleaving of the published transitions; it was not an end-to-end invocation of `deploy.sh` or a live ZFS privilege test. The regression in PR #780 serially denies one, then two and therefore does not cover this ordering.

### Required correction **in the same REV-170**

1. Serialize grant and revoke transactions sharing a namespace/account, including their recording, ownership decisions, ZFS allow/unallow, and cleanup, under a trusted **interprocess** lock; or implement a provably atomic equivalent. A same-label lock alone is insufficient when two labels share a namespace. If acquiring the lock fails, stop, retain durable retry state and do not claim a successful revocation.
2. Deterministic **actual `deploy.sh`** fake-ZFS test: grant one and two; launch two `--deny-restore` processes with barriers that force both transitions to compete; assert exact shared namespace `unallow` once by the last owner, zero remaining grant/pending records, absent effective capability, no premature writers resume, and rc0 only after capability removal. Negative-control test against the PR #780 code must demonstrate the orphaned capability, not merely a sequential test.
3. A pending revocation that remains due to a real failed `unallow` must continue blocking teardown appropriately (REV-147), and different account/pool isolation must survive. Include a crash and restart/retry case where the lock holder dies.
4. A pre-existing grant with an unreadable/unknown account or datasets **must not be silently disregarded as "not an owner"** when deciding whether to remove a capability that may still be in use. Preserve clear diagnostics and fail closed under that ambiguity; new grant records carrying account info are helpful but do not repair old recorded state.
5. Run `test/restoregrant/run.sh` under its supported non-root environment, the new injected race/legacy controls, `test/impact.sh --verify`, `test/reviewctl.sh --verify`, and CI on exact submitted SHA. Update the existing `responses/REV-20261023-170.md`; **no new REV identity**.
