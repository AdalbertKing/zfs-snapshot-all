# REV-20260907-136 — GUI readers publish success from malformed client records

Review date: 2026-09-07
Reviewer: ChatGPT
Reviewed delivery: PR #341, head `59b544526d269d91599ebabac569d437be458e90`
Canonical merge checked: `819c3a8c0e40d9ada5103fcaac687abdb22a5426`

## Verdict

**CHANGES REQUIRED — P2: the new JSON readers ignore a failed
`record_load client`, so malformed state can be reported as a successful,
plausible answer; `status --json` can additionally leave truncated JSON on
stdout.**

The four-reader package and its live monitor correction are otherwise not
rejected by this review. The blocking issue is the error boundary between the
existing fail-closed record parser and the new front-end contract.

## F1 — P2 BLOCKING — failed record loads are treated as reader data

- Severity: P2
- Blocking: yes
- Affected: `status_json_record()`, `cmd_status_json()` and
  `cmd_show_config()` in `zfs-backup.sh`; focused `statusjson` and `showconfig`
  controls in `test/zfsbackup/run.sh`.

### Evidence

`record_load` returns 2 for a malformed record value and calls `die` for a
field outside the per-record allowlist. Neither `status_json_record` nor
`cmd_show_config` checks the return status. `cmd_status_json` also writes the
array prefix and delimiter before the record has completed.

Reviewer-only reproduction on the exact PR head used two client records. The
first was valid; the second contained a field the package refuses:

```sh
printf '%s\n' 'CLIENT_NAME=good' 'STATE=active' > "$D/clients/a.conf"
printf '%s\n' 'CLIENT_NAME=broken' 'DIE_MAIN_PID=payload' > "$D/clients/b.conf"
CLIENTS_DIR="$D/clients" CRON_CONFIG="$D/missing.conf" \
  ./zfs-backup.sh status --json >"$D/out" 2>"$D/err"
```

Observed: `rc=1`, the refusal was present on stderr, but stdout ended after the
first complete object and a comma. Parsing it produced `JSONDecodeError` at
column 448. Thus the command correctly refuses the bad record only after it has
published an invalid partial response.

A second discriminator used a syntactically malformed but allowlisted value:

```text
CLIENT_NAME=broken
STATE='unterminated
```

`status --json` returned `rc=0` with a row named `broken` and an empty state.
The same shape under `show-config broken --json` returned `rc=0` and a
plausible `config_readable` answer derived only from the fields preceding the
malformed line. Reordering `CRON_CONFIG` before or after the bad line changed
that answer, proving that the reader exposed the parser's partial assignments
as if they were valid state.

### Failure mode and impact

A truncated write, manual edit, or damaged relationship record is no longer a
fail-closed input to the GUI data layer. Depending on the malformed line, a
front end receives either invalid JSON after a nonzero exit or valid JSON with
exit zero that silently describes only the prefix of the record. It may then
show a relationship as unconfigured or omit its state even though the product
has explicitly refused that record as data.

This is read-only and does not mutate ZFS or configuration, so it is P2 rather
than a data-safety P1. It is blocking because these commands are the API being
introduced for the configurator.

### Existing verification and why it missed the defect

- Exact-head PR #341 CI is green: run `34129011913`.
- The reader-focused invocation completed `285 PASS / 0 FAIL`, including the
  `statusjson`, `showconfig`, `listprofiles` and `monitorjson` sections.
- `./test/impact.sh --verify` is green on the canonical merge.
- Existing record tests prove that malformed or unknown fields are refused by
  `record_load`; the new reader fixtures contain only valid records, so they do
  not prove that the readers preserve that refusal or keep stdout atomic.

### Acceptance criteria

1. `status --json` and `show-config --json` must check the result of every
   `record_load client` before treating any assigned field as valid.
2. A malformed allowlisted value must not produce `rc=0` or a plausible row
   assembled from assignments made before the bad line.
3. `status --json` must not leave a prefix, delimiter or partial object on
   stdout when any selected client record is refused. Buffer the publication
   boundary so stdout is either one complete parseable response or empty, and
   return nonzero with the record refusal on stderr.
4. Add discriminating controls for both failure forms above: an unclosed quoted
   value and a disallowed field in the second of two records. Parse stdout in
   the tests and assert the command status; the controls must fail against
   `59b544526d269d91599ebabac569d437be458e90` for the observed reasons.
5. Preserve the successful two-client output contract and the existing
   per-profile buffering behaviour; no redesign of the four JSON schemas is
   requested.

### Required verification

- the focused `statusjson` and `showconfig` controls in
  `test/zfsbackup/run.sh`;
- `./test/impact.sh --verify`;
- exact-head CI.

No ZFS, fleet, destructive, or full product campaign is required. Temporary
client records and the real `zfs-backup.sh` entrypoint decide the defect.
