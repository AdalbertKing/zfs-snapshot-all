# REV-20261028-178 — P1: failed encrypted browse can orphan a loaded ZFS key

Reviewer: ChatGPT. Date: 2026-10-28.

Source release: `AdalbertKing/zfsbackup` main

`RELEASE-OF=901e8e4b7ba5a2871ef59e29e6356b9762f2bb2f`. The affected development

## F1 — a second encryption root overwrites cleanup ownership after a failed mount

- Severity: **P1**
- Blocking: **yes**
- Affected: `tui/browse.sh`, `need_key()`, filesystem step 4 and `KEYLOADED`

### Evidence

`need_key()` loads an unavailable encryption root and stores the single root in
`KEYLOADED`. If the immediately following read-only `mount_ro` fails, step 4
returns to the snapshot menu without calling `unload_key()`. The operator can
cancel back to the dataset tree and choose a dataset under a different
unavailable encryption root. Its successful `load-key` overwrites
`KEYLOADED`; final cleanup unloads only the second root. The first root remains
loaded after the process exits, contrary to the UI promise that the key is
loaded only for browsing and removed on exit.

Executable isolated negative control:

```bash
bash docs/internal/reviews/evidence/REV-20261028-178-encrypted-key-cleanup.sh
```

It invokes the actual `tui/browse.sh --any` entry point with executable stubs;
it does not access ZFS or a production host. On exact affected development SHA
`901e8e4b7ba5a2871ef59e29e6356b9762f2bb2f` it reports:

```text
zfs load-key -L prompt -- tank/key1
zfs load-key -L prompt -- tank/key2
zfs unload-key -- tank/key2
FAIL: tank/key1 remains loaded after exit
```

The existing focused suite passes `43/43`, including the ordinary successful
load/mount/unmount/unload path, raw keys and incorrect passwords. It has no
mount-failure-after-load or multiple-encryption-root case. Exact release export
verification passes, so this is the behavior actually shipped in `8143775…`,
not a dev/release mismatch.

### Failure mode and impact

A routine read-only mount error (unsupported state, transient mount failure or
bad snapshot) extends key lifetime beyond the attempted browse. Visiting a
second encrypted copy can make the first key permanently untracked by this
process, leaving encrypted data unlocked until an operator discovers and
manually unloads it or the host reboots. This is a broken security promise and
a fail-open cleanup path.

### Acceptance criteria

- Every encryption root loaded by this process is unloaded before the flow
  leaves that browse attempt, including mount failure, cancellation, signal and
  ordinary exit paths.
- Cleanup tracking must not be lossy when more than one encryption root is
  encountered. Either unload before another selection or track every root
  loaded by this process; never overwrite the only cleanup handle.
- A failed unload returns nonzero and names every remaining root with an exact
  manual remediation command. Never unload a key that was already loaded before
  this process started.
- Preserve read-only mounting, existing snapdev/mapper cleanup ordering and the
  rule that cleanup failures cannot return success.
