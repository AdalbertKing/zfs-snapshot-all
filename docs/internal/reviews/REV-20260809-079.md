# REV-20260809-079 — Slice B1 scope plan: migration bypasses the existing safe path and one acceptance premise is false

Review time: 2026-08-09 02:07 CEST
Reviewed delivery: `8505601d39b79e931a357cf81c4595b833550b78`

## Original verdict

**CHANGES REQUIRED before Slice B1 runtime implementation.**

The owner's option-3 decision stands: B1 targets the GFS shape, pre-GFS is frozen rather than silently reinterpreted, and pve0 needs a migration path. The problems are in the proposed migration mechanism and in one inference used to define B1 acceptance.

No frozen transfer engine needs to change for either finding.

## F1 — P1 — the pve0 migration plan bypasses an existing transactional migration command

The plan says pve0 should be migrated by manually deleting four supposedly unreferenced sections from the live file:

`/etc/zfs-snapshot-all/jobs.pve0.v4.conf`

That is the wrong safety boundary for this project, especially because `zfs-backup.sh` already has `migrate-profile` for exactly this transition.

Current `cmd_migrate_profile()` already:

1. reads the authoritative cron config;
2. refuses if it is not pre-GFS;
3. copies the real config to a working file;
4. removes `standard_hourly`, `standard_daily`, `standard_weekly`, `standard_monthly` from the working copy;
5. calls `ensure_cron_config()` to construct the GFS shape;
6. rebuilds active managed clients through the same `emit_client_sections()` used by activation;
7. explicitly handles the zero-client case with `no active clients -- migrating the templates only`;
8. validates the working config through the real `gen-cron.sh`;
9. shows the exact config and live-crontab proposal;
10. requires confirmation;
11. runs the existing config-source / foreign-block / clobber / readability guards;
12. installs through `atomic_replace_and_install()` rather than editing the live file in place.

The measured pve0 state in the delivery — zero active clients and four dead legacy template sections — is therefore not an argument for a hand edit. It is almost the simplest case the existing migration verb already supports.

There is also a time-of-check problem in the written plan. "Zero jobs reference them" and "zero clients are enrolled" are mutable live-host facts measured on 2026-08-09. A migration path must prove the relevant state at execution time, not rely on an earlier observation. The existing migration path is materially better because it rebuilds/validates the current working copy and previews the actual cron delta before mutation.

### Required correction for F1

1. Make the normal pve0 migration path use the existing high-level migration machinery, preferably `zfs-backup.sh migrate-profile`, not manual deletion from the live CONFIG.
2. If the B1 loader change makes the existing verb unsuitable, name the exact incompatibility and repair that path as part of B1 before migrating pve0. Do not fall back to a manual edit merely because the host currently has zero clients.
3. At migration time, prove from the then-current config/preview that pve0's legacy template sections are unreferenced / that the rendered production job set does not change unexpectedly. The 2026-08-09 measurement is useful evidence, not a permanent precondition.
4. Preserve the option-3 fail-closed rule: a pre-GFS host is never silently treated as GFS by ordinary enrolment/activation.

## F2 — P1 — "a host with its own template names receives no built-ins" is not the current `ensure_cron_config()` contract

The plan adds this B1 acceptance criterion:

> a host with its own template names (the pve2 case) still receives nothing

and explains that built-ins are appended "only when missing", concluding that hosts with their own template names never receive them.

The first clause is true only name-by-name; the conclusion is false.

Current `ensure_cron_config()` does not ask whether the config has *some other* templates. It loops over each built-in name and does:

```bash
grep -q "^\[template:$t\]" "$file" && continue
# otherwise append this built-in template
```

and does the same for `keep_*` when `PROFILE_GFS=1`.

Therefore a config containing only `local_daily`, `store_hourly`, etc. does **not** suppress the built-ins. If `ensure_cron_config()` runs on such a config, the missing built-in names are appended. The fact that the measured pve2 config contains custom templates and no built-ins does not establish a suppression rule; it is also consistent with that config simply never having gone through this path.

This matters because B1 is supposed to extract hardcoded policy without changing behaviour. A test asserting "custom templates => emit nothing" would bless a new semantic rule that the current code does not have.

### Required correction for F2

1. Remove the claim that the mere presence of custom template names suppresses built-in template emission.
2. Reframe the pve2 observation as a host-state measurement unless there is separate evidence proving which code path produced it.
3. Make B1 acceptance preserve the actual name-by-name idempotence contract:
   - a built-in section already present is not duplicated;
   - a missing built-in section is emitted according to the applicable GFS/pre-GFS rules, regardless of unrelated custom template names, unless a separately reviewed behaviour change intentionally says otherwise.
4. If the product actually wants "custom template config => never append built-ins", split that into a separate behaviour/design decision with its own tests; do not smuggle it into B1 as extraction-equivalence.

## Proof required for eventual B1 runtime

Before B1 code is accepted, targeted proof must include:

- a fixture proving the post-B1 profile loader preserves the current name-by-name append/idempotence semantics;
- a pre-GFS fixture proving ordinary enrolment/activation refuses rather than silently converting;
- a migration test covering **zero active clients**, proving the established migration path removes legacy templates on a working copy, loads the GFS profile through the new production loader, validates, previews and installs without requiring a manual live-config edit;
- negative control showing the relevant new assertions fail against the wrong B1 implementation;
- dependency-selected cascade and `impact.sh --verify` as required by the normal policy.

For the eventual pve0 migration, the live proof is the migration command's current-state preview/read-back at execution time. Do not treat the 2026-08-09 inventory as immutable host state.

**APPROVED.**

Independent inspection of the exact docs implementation confirms both findings are corrected.

F1: the plan now makes `zfs-backup.sh migrate-profile` the normal pve0 path, treats the 2026-08-09 live inventory only as evidence, and explicitly preserves the legacy-name removal list plus the shared naming path between `ensure_cron_config()` and `emit_client_sections()`. The pre-GFS fail-closed rule remains intact.

F2: the invented "custom templates suppress built-ins" rule is removed. Acceptance now preserves the actual per-name idempotence contract: each missing applicable built-in is emitted irrespective of unrelated custom template names.

The plan also incorporates the separately resolved deterministic profile-template namespace. That changes representation, not rendered job semantics; the eventual B1 runtime proof must therefore compare schedules, prefixes, retention/GFS, recursion, monitoring, source/target mapping and flags rather than requiring byte-identical CONFIG text.

This submission is documentation-only. The runtime loader, migration and negative-control proof obligations listed above are intentionally **not** claimed as discharged; they remain gates on the future B1 implementation.

No REV-079 finding remains open.
