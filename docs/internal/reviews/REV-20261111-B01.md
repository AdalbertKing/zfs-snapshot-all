## F1 — A terminated replica still leaves live transfer records

- Severity: **P1**. Blocking: **yes**, within submitted U182.
- Affected: `gen-cron.sh:4137`, `snapsend.sh:1223-1229` (and the equivalent send arms at 1235-1271), `lib-zfs-snap.sh:175-184,211-295`, `hostscripts/check-pool-capacity.sh:150-165`.
- Invariant: U182's accepted backlog outcome requires the interrupted replica to detach its medium **and mark that run's transfer records interrupted**. The new outer signal trap calls the media gate's `detach --engine-rc 143`; it does not close progress records. A `progress_watch` writer stores `"state":"running"`. Only `progress_done`, reached after the send pipeline returns normally to its caller, changes that state. A TERM to the whole process group exits the inner shell and kills the watcher before this call. `progress_reap` expressly leaves `running` records alone. After 30 minutes `check-pool-capacity.sh` classifies them as orphaned and emits the same false alarm that U182 set out to remove.
- Evidence: the U182 test added in `test/cron/run.sh` checks only that `detach` receives 143. There is no assertion about `progress/*.json`. The submitted live claim says `detach` ran on pve11, but supplies no post-signal progress-record state. This is a code-path proof; I have not interrupted a live transfer.
- Required outcome: after a terminated replica, each transfer record owned by that run has a terminal interrupted/dead state without overwriting another run's record. The medium is exported and gate state is cleaned as already intended. A deliberate kill must not generate a later orphan/hang alarm for that run.
- Acceptance: add a discriminating group-TERM test that creates a running progress record, proves the submitted implementation leaves it running, then proves the fix marks it terminal and does not affect unrelated records. Repeat a bounded disposable-pool interruption on the lab host and record the gate, pool and progress states before and after. Run the affected focused suites and exact-head CI.
