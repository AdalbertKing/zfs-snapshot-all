## F1 — P1 BLOCKING — `move-to-client` publishes the config before its ownership records

### Evidence

`zfs-backup.sh:9294-9345` first commits the config and both crontabs through
`atomic_replace_and_install`. Only afterwards it appends the destination and
source client records. Either append failure is reduced to `warn`; execution
continues into pausing the old relationship and finally prints `done` plus the
claim that the destination carries the schedule.

This recreates the exact inconsistency the new record block says it fixes. If
the destination append fails, the installed sections belong to the new
relationship while its record says it owns nothing. If the source append fails,
both records may claim the same datasets. `status`, a second move and
`remove-client` read those records, so the next administrative action operates
on false ownership state. The command can additionally pause the old
relationship after either failure.

`test/moveclient/run.sh` tests transforms, GUID proof and early CLI refusals. It
does not execute the publication sequence and has no injected failure for
either record write.

### Acceptance criteria

1. The config, both crontabs and both client-record transitions share one
   rollback boundary, or all record replacements are prepared and proven
   installable before any live config/crontab replacement.
2. Failure of either record transition cannot leave the new config installed,
   pause the old relationship, or print the successful final state.
3. Add discriminating cases for failure of the first and second record update.
   Each must prove byte restoration of config, both client records and both
   crontabs, and prove that the pause state is unchanged.

## F2 — P1 BLOCKING — a successfully imported medium can lose its ownership marker and still return success

### Evidence

`zfs-media-gate.sh:145-159` imports the pool and validates the dataset. It then
creates `$SEEN` and `$OURS`, but the entire state write ends in `|| :`. A
missing/unwritable state directory therefore produces exit 0 and the message
that this run will export the pool again even though no `imported-by-us` marker
exists.

The later `detach` branch at lines 162-166 sees the missing marker, reports that
this run did not import the pool, leaves it imported and also exits 0. This
defeats the script's loudest safety promise: a successful bracket may leave a
pool active while the job reports success, exactly when an operator may assume
the removable disk is safe to unplug.

The suite covers failed `zpool export`, but not failure to persist ownership
after a successful import.

### Acceptance criteria

1. After importing a pool, failure to durably record ownership is a hard error,
   never success.
2. The error path immediately tries to restore the pre-run state by exporting.
   Whether that export succeeds or fails, return a loud nonzero result; on
   failure explicitly retain the `DO NOT UNPLUG` warning.
3. Add pure/stub cases using an unusable state path for both successful and
   failed compensating export. They must fail on this reviewed SHA.
