# REV-20260904-134 — a record field can disable fatal propagation

Review date: 2026-09-04
Reviewer: ChatGPT
Reviewed delivery: PR #295, head `ac05727800acd7052dec73405dacbfbc53cf9e21`
Canonical base checked: `09769beebe95c9fffd310f21778d8394c52155cf`

## Verdict

**CHANGES REQUIRED — P2: `record_load` accepts arbitrary uppercase variable
names, so a record can overwrite `DIE_MAIN_PID` and disable the new fail-closed
behaviour of `die` inside command substitutions.**

The large records-as-data refactor and its focused suites are otherwise not
rejected by this review. The blocking issue is the boundary between record data
and the reader's own control variables.

## F1 — P2 BLOCKING — an accepted record field restores fail-open control flow

- Severity: P2
- Blocking: yes
- Affected: `lib-record.sh`, `lib-backup-common.sh`, and the record controls in
  `test/zfsbackup/run.sh`.

### Evidence

`record_field_name_ok` says it accepts fields the package writes, but the
implementation accepts every name matching `[A-Z][A-Z0-9_]*` except a short
deny-list. `DIE_MAIN_PID` is not on that list. `record_load client` therefore
assigns it in the main shell after `die_arm_fatal` has stored the process id.

Reviewer-only reproducer on fresh canonical `main`:

```sh
mkdir -p "$D/clients" "$D/rel"
printf '%s\n' \
  'CLIENT_NAME=pve2' \
  'PEER_HOST=192.168.28.8' \
  'ACTIVE_ENDPOINT=192.168.28.8:22' \
  'STATE=seed_complete' \
  'DIE_MAIN_PID=' > "$D/clients/pve2.conf"
CLIENTS_DIR="$D/clients" RELATIONSHIPS_DIR="$D/rel" \
  bash ./zfs-backup.sh set-endpoint pve2 --host='bad host'
```

Observed:

```text
rc=1, FATAL lines=2
FATAL: invalid endpoint host 'bad host' ...
FATAL: refusing to switch 'pve2' from '192.168.28.8:22' to ':' ...
```

Without `DIE_MAIN_PID=`, the existing focused control produces exactly one
FATAL and stops before the second refusal. The record stays byte-identical in
both runs, but the safety property is lost: the first `die` exits only the
subshell, the caller receives an empty host and continues.

This is not limited to one misspelled data field. Other uppercase internal
variables are accepted by the same rule, so extending the deny-list by this one
name would leave the data/control boundary open.

### Existing verification and why it missed the defect

- Exact-head PR #295 CI is green (run `33787518606`).
- Fresh-main focused suites are green: `zfsbackup 556/0`, `evalfree 16/0`,
  `selfupdate 63/0` (3 skips), `rux 45/0`, `restore 300/0`,
  `joinmanifest 32/0`, `cron2conf 29/0`, `deadcode 7/0`, `twins 72/0`.
- The existing hostile-record test covers `PATH`, which is explicitly denied.
  It does not exercise an uppercase control variable absent from the deny-list.

### Acceptance criteria

1. A client record containing `DIE_MAIN_PID=` is refused before that name is
   assigned; record data must not be able to assign the reader's control
   variables.
2. Close the class, not only this spelling: use per-record-set allowed fields or
   an equivalently bounded mechanism proving that unknown uppercase fields
   cannot mutate program control state.
3. Add the reproducer above to the focused record tests. On the fixed head it
   must return `rc=1`, print only the `invalid endpoint host` FATAL, never print
   `refusing to switch`, and leave the record unchanged. The same control must
   fail on `ac05727800acd7052dec73405dacbfbc53cf9e21`.
4. Preserve round-trip parsing of every legitimate client, manifest, pause and
   server field, including `%q` values and literal command-substitution text.

### Required verification

- `bash test/zfsbackup/run.sh` including the discriminating control;
- `./test/impact.sh --verify`;
- exact-head CI.

No live ZFS or fleet campaign is required: the defect is fully decided with a
temporary record and the real `zfs-backup.sh` entrypoint.

## Follow-up — 2026-09-04, candidate implementation in PR #328

**CHANGES REQUIRED remains unchanged.** I reviewed the response on PR #328,
branch head `bbf21cc3fcc1728b61a78ad1a7131af69ffcd98a`, which identifies
implementation commit `65b01a911d4f9d1c4d6b178278368d5bcb78600b`.

The per-record-set gate fixes the original `DIE_MAIN_PID=` reproducer and is
the right mechanism. The submitted client allowlist is nevertheless still
open-ended:

```sh
case "$2" in
    EXCLUDE_FAMILY_*|EXCLUDE_CHILD_*|EXCLUDE_SNAP_*|EXCLUDE_*)
        case "${2##*_}" in ''|*[!0-9]*) return 1 ;; esac
        return 0 ;;
esac
```

The final alternative, intended to retain the historical exact family
`EXCLUDE_<n>`, accepts every uppercase name beginning with `EXCLUDE_` whenever
its final underscore-separated component is numeric. It therefore also admits
names the package has never written, for example `EXCLUDE_FOO_1` and
`EXCLUDE_FOO_BAR_1`.

Reviewer-only probe on the exact PR head:

```sh
. ./lib-backup-common.sh
printf 'EXCLUDE_FOO_1=payload\n' > "$record"
record_load client "$record"
printf 'rc=%s value=%s\n' "$?" "$EXCLUDE_FOO_1"
```

Observed:

```text
rc=0 value=payload
```

The package writers on that head produce only `EXCLUDE_FAMILY_<n>` and
`EXCLUDE_CHILD_<n>` today; the two compatibility forms are exactly
`EXCLUDE_SNAP_<n>` and `EXCLUDE_<n>`. Thus `EXCLUDE_FOO_1` is neither a current
nor a legacy package field, but it is assigned into the reader shell. This is
the same undelimited-name class as F1, not a new finding.

The submitted records suite passes, but its negative probe is
`EXCLUDE_FOO=x`; that value has no numeric suffix and does not exercise the
broad alternative. Exact-head CI run `33880680184` is green and the focused
records assertions pass, so neither currently distinguishes this residual
opening.

### Remaining acceptance delta

1. Match the four numbered families independently: `EXCLUDE_FAMILY_<digits>`,
   `EXCLUDE_CHILD_<digits>`, `EXCLUDE_SNAP_<digits>` and the legacy exact shape
   `EXCLUDE_<digits>`. Do not accept arbitrary intermediate components.
2. Add negative controls for at least `EXCLUDE_FOO_1` and
   `EXCLUDE_FOO_BAR_1`; both must be refused before assignment. Keep positive
   controls for all four legitimate families.
3. Re-run only the focused record control, `./test/impact.sh --verify`, and
   exact-head CI. No wider campaign is required.
4. Update the existing response with the new exact implementation SHA. The
   same REV continues; do not create another response or REV.
