# REV-20260901-132 — no-copy plan creates snapshots without pruning them

Review date: 2026-09-01
Reviewer: ChatGPT
Reviewed delivery: PR #246, head `de6da17b821a5eed625bce94fc0f326d59068b46`
Canonical base checked: `82d541b1b622b177ba229f8407d09baad8695bd5`

## Verdict

**CHANGES REQUIRED — P1: `--target=''` advertises bounded in-place retention,
but the generated configuration contains no prune section and the resulting
cron block only creates snapshots.**

## F1 — P1 BLOCKING — no-copy snapshots grow without the promised retention

- Severity: P1
- Blocking: yes
- Affected: `zfs-backup.sh`, `cmd_local_backup()` no-copy candidate composition,
  and the focused `test/localbackup/run.sh` coverage.

### Evidence

PR #246 introduces `--target=''` as the single-host shape and describes it as
creating each tier's snapshot family and pruning it in place. In the candidate
composer, however, source retention is emitted only when copying is enabled:

```sh
if [ "$no_copy" -eq 0 ] && [ -n "$LB_RETFRAG" ]; then
    # emit [prune:<source>]
fi
```

Reviewer-only control on exact merged `main`
`7df470291a50392ad684ec8d09fc21a94d496efe`:

```text
cmd_local_backup --source=rpool/data --target= --profile=default \
  --config=/tmp/backupal-no-copy-probe.conf
rc=0
```

The candidate contains `[dataset:rpool/data]` with no `dst`, but contains no
`[prune:rpool/data]` section. The generated cron block contains exactly the
one-argument snapshot command:

```text
snapsend.sh -m "automated_hourly_" "rpool/data"
```

and no `delsnaps.sh` line. At the same time the plan reports:

```text
Retencja ZRODLA: GFS -H24 -D7 -W4 -M12
```

The existing focused suite passes `121/0`, but it has no `--target=''` case;
its ordinary copy controls prove that source pruning is otherwise represented
by `[prune:<source>]` and a non-recursive `delsnaps.sh` line.

### Failure mode and impact

An operator can install the advertised snapshot-only relationship and receive
hourly snapshots indefinitely, while the preview explicitly claims bounded GFS
retention. The job continues to look healthy because snapshot creation succeeds;
capacity consumption grows silently until manual intervention or pool pressure.

### Acceptance criteria

1. In no-copy mode, emit one bounded source-prune section for every selected
   source, using the profile's source retention and the same non-recursive
   source scope already used by normal local backup.
2. Keep the no-copy shape free of `dst`, target-prune sections, target creation,
   target grants and two-argument send commands.
3. Make the plan summary describe only retention that the generated candidate
   actually schedules; do not print target retention when no target exists.
4. Add one focused plan test proving that `--target=''` renders both the
   one-argument snapshot command and the matching bounded source prune, plus a
   negative assertion that no target/copy job is emitted.

### Required verification

- `bash test/localbackup/run.sh`;
- the focused no-copy test must fail on
  `de6da17b821a5eed625bce94fc0f326d59068b46` and pass on the submitted fix;
- `./test/impact.sh --verify` and exact-head CI.

No live-ZFS or remote campaign is required: this defect is fully decided by the
generated candidate and cron text. The review assumes the documented contract
is authoritative; if snapshot-only mode is intentionally unbounded, that is an
Owner product decision and the CLI must not claim GFS retention.
