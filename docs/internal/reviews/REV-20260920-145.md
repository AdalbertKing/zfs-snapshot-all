## F1 — P2 BLOCKING — a failed whitelist rewrite is reported as a successful commit

- Severity: P2
- Blocking: yes
- Affected path: `deploy.sh`, `do_commit_scope()`

PR #403 correctly detects an existing quiesce grant and calls
`install_quiesce_grant "$account" "${still_granted[*]}"` after narrowing the
ZFS delegation. The return status is not checked. `deploy.sh` uses
`set -uo pipefail`, not `set -e`, so a failed transactional whitelist update is
walked past: the function prints that the whitelist matches exactly, replaces
`PEER_JOIN_GRANTED_DATASETS`, writes the scope hash and returns success.

`install_quiesce_grant()` deliberately restores the previous grant on an
ordinary installation failure. Consequently, this path can leave the old,
wider quiesce whitelist active after `zfs unallow` removed the corresponding
replication permission, while the durable manifest has already forgotten that
dataset and the command has claimed success. This recreates the privilege drift
PR #403 intended to eliminate and removes the normal retry signal.

The focused `quiescehelper` suite passes (`123 PASS / 0 FAIL`), but its two new
commit-scope checks inspect source text and do not execute the failure boundary.
Exact-head CI for PR #403 was green ([run
35528575125](https://github.com/AdalbertKing/zfs-snapshot-all/actions/runs/35528575125)).

### Minimal reproduction

At merged main `7dff3038113941addb157682b9f3d4e6a4ecec63`, extract the shipped
`do_commit_scope()`, stub a prior scope of `pool/a pool/b`, narrow it to
`pool/a`, let `zfs unallow` succeed, keep an existing quiesce-grant marker and
make `install_quiesce_grant()` return 1.

Observed:

```text
rc=0
manifest=PEER_JOIN_GRANTED_DATASETS="pool/a"
hash=written
unallow=1
quiesce_failure=1
LOG its whitelist now matches this scope exactly: pool/a.
LOG commit-scope complete for 'peer': 1 dataset(s) granted to backup, 1 revoked
```

The discriminator is `rc=0` together with the new manifest/hash despite the
injected quiesce update failure. On the real transactional helper the failed
update restores the previous whitelist, so these durable facts and messages are
false.

## Follow-up on implementation `773b955d99088fa4039ef661aa600b8da1b2aae1`

The candidate in PR #409 fixes F1's direct unchecked installer call, but it does
not yet satisfy acceptance criterion 4. Its new `quiesce_update_failed()` path
depends on the return status of `revoke_quiesce_grant()` to decide whether it
may say the freeze permission "was taken away entirely". The existing revoke
helper never returns failure when either or both managed files cannot be
removed. If every `rm` fails, its `removed` counter remains zero, it prints
"no quiesce grant found", and returns 0 while both files still exist.

Minimal executing reproduction against fresh main
`feccbc9969b6890ed2b5a6e11fd3144447911883`: extract the shipped
`revoke_quiesce_grant()`, redirect its two absolute paths into a sandbox, create
both managed files and make `rm` return 1.

Observed:

```text
WARN could not remove .../allow/backup -- backup may still be able to quiesce guests here
WARN could not remove .../sudoers/zfs-quiesce-backup -- backup may still reach the helper through sudo
LOG no quiesce grant found for 'backup' on this host -- nothing to revoke
rc=0 allow_exists=yes rule_exists=yes
```

The same focused reproduction was rerun against fresh `origin/main`
`06f111a292ced456e296e5676dbd5530e4fba829` on 2026-09-26 and produced the
same discriminator: `rc=0 allow_exists=yes rule_exists=yes`.

Therefore the `else` branch in `quiesce_update_failed()` that promises the
manual emergency command is unreachable for this real failure. The command
still exits nonzero because `die` follows it, and it preserves the retry record,
but it falsely claims that the wider permission was disabled. Both active grant
artifacts can remain in place after replication permission was narrowed.

The focused suite passes (`127 PASS / 0 FAIL`) because the new failure harness
stubs `revoke_quiesce_grant()` to return 0 and does not exercise deletion
failure. Exact-head CI for PR #409 was green ([run
35538364289](https://github.com/AdalbertKing/zfs-snapshot-all/actions/runs/35538364289)).

## Acceptance criteria

1. Check the return status of the quiesce grant installation/update in every
   `do_commit_scope()` branch; an update failure must make `--commit-scope`
   return nonzero.
2. On that failure, do not write the new scope hash or replace the prior
   `PEER_JOIN_GRANTED_DATASETS`; the old record must remain sufficient for a
   safe retry.
3. Do not print either “whitelist now matches this scope exactly” or
   “commit-scope complete” after the failed update.
4. Leave permissions fail-closed and coherent: either restore/retain the old
   replication grant for every dataset still authorised by the restored old
   whitelist, or keep the quiesce grant disabled/narrowed until a retry
   completes. A failed run must not leave a wider active freeze permission than
   the replication permission it accompanies.
5. Add an executing regression test that injects the helper failure after a
   successful revoke and asserts nonzero status, preserved retry record, no new
   hash/false success message, and coherent effective permissions. Preserve the
   successful existing-grant, no-grant and explicit `--allow-quiesce` paths.
6. Make `revoke_quiesce_grant()` return nonzero whenever a managed whitelist or
   sudoers rule existed but could not be removed. It must not print "nothing to
   revoke" in that case.
7. Extend the executing regression to force both removals to fail and assert
   that `quiesce_update_failed()` reports the manual emergency command instead
   of claiming the freeze permission was removed. Keep the successful and
   already-absent revoke paths unchanged.
