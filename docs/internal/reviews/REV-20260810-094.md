# REV-20260810-094 — Phase 6 runnable CONFIG examples lack a dependency-driven regression edge

Status: CHANGES REQUIRED / OPEN
Severity: P2 — test/dependency-graph defect
Blocking: next-slice (Phase 6)
Reviewed delivery: `5df74522d91a78569fd7755aefe37939ea60c3c3`
Response path: `docs/internal/reviews/responses/REV-20260810-094.md`

## Independent review

The documentation slice is directionally appropriate and does not modify production runtime. The four files under `docs/examples/*.conf` are not merely prose, however: the delivery explicitly presents them as runnable CONFIG artifacts, says each was validated by the real `gen-cron.sh`, and tells operators they may copy and re-run them.

That creates a durable contract edge:

`gen-cron.sh CONFIG grammar/rendering` -> `docs/examples/*.conf` -> `documented operator behavior`.

The current dependency graph does not represent that edge. `test/deps.conf` lists `gen-cron.sh` suites as `gencron, scenarios, zfsbackup, migrate, profiles, reconcile`, with no suite covering the runnable examples; the new example files are likewise not registered with a suite. `ACTIVE-WORK-PLAN.md` itself records the same condition as a known test-hygiene gap, while `DELIVERIES.md` describes the slice as `docs only, no graph impact`. Those two statements cannot both be accepted under the project's impact/dependency discipline: once a checked-in config is promised runnable against a production parser/generator, it has graph impact even if it is documentation-facing.

I do not currently find evidence that any of the four examples is invalid at `5df7452`; the defect is that their validity can silently rot after a future generator/schema change while `impact.sh` remains green.

## Required outcome

Add the smallest regression edge that proves the actual dependency, without broadening into a full campaign:

1. Add one focused suite (for example `test/configexamples/run.sh`) that runs the real `gen-cron.sh -c` against every checked-in `docs/examples/*.conf`.
2. Pin more than exit 0: assert the few semantic line properties each example exists to teach (e.g. independent H/D prune counts, per-dataset quiesce separation, short-local/long-store retention, monitor-only carrier emits monitor but no duplicate prune, bookmark prune line). A compact checked-in golden per example or equivalent targeted assertions is acceptable.
3. Add dependency edges so a change to `gen-cron.sh` selects this suite and a change/addition under `docs/examples/*.conf` selects it as well. The suite file itself must of course select itself under the existing deps rules.
4. Include one meaningful negative control showing the suite would fail if a runnable example drifts from the grammar or intended generated shape. A temporary mutation in the test run is enough; no live host is needed.
5. Run only this targeted suite plus the dependency-driven cascade selected by the graph change and `test/impact.sh --verify`. Real ZFS/crontab/SSH proof is not required because this finding is confined to the pure generator boundary.

## Acceptance

REV-094 can close when the runnable examples are represented as first-class test dependencies and the evidence demonstrates that generator drift or example drift is caught automatically.

No production-code change is requested by this finding.
