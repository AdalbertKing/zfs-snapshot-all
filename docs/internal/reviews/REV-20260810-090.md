# REV-20260810-090 — reactivation still requires and mutates from the active profile before the preserved-section branch

Review opened: 2026-08-10 00:58 CEST
Final verification: 2026-08-10 08:42 CEST
Response path: `docs/internal/reviews/responses/REV-20260810-090.md`

## Verdict

**APPROVED on implementation `e26adc57ab0526a5e3a359de7032c5ecb6522566`.**

REV-089 fixed relationship-section clobbering but left two active-profile dependencies in `ensure_cron_config()`: ordinary reactivation still required the current profile to exist/validate, and could re-append missing templates from that profile. The submitted implementation resolves both findings.

This approval is deliberately scoped to those two profile-authority defects. REV-20260810-091 tracks independent residual Phase-3 policy mutation/refusal paths that remain even when no profile is loaded.

## F1 — resolved — pure reactivation no longer requires the historical profile

Independent inspection confirms `cmd_activate_client()` now computes a preserve/regenerate plan from the installed CONFIG and relationship record before profile handling. `client_section_plan()` reports `PLAN_NEEDS_PROFILE`; `ensure_cron_config()` receives that value, and `load_active_profile()` is entered only when policy material actually has to be generated.

Therefore an already-active relationship whose managed sections are all present and owned can refresh endpoint topology after its historical CREATE-time profile is removed, renamed or invalid, while candidate CONFIG validation remains in place.

## F2 — resolved — pure reactivation does not re-append current-profile templates

The profile template append loop is inside the same `needs_profile=1` gate. A pure reactivation with no section to generate therefore neither loads the active profile nor restores a missing template from it. A genuinely additive case still loads the profile and fails clearly if that required CREATE-time material is unavailable.
