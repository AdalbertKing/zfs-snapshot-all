# REV-20260810-090 — reactivation still requires and mutates from the active profile before the preserved-section branch

Review time: 2026-08-10 00:58 CEST
Reviewed implementation: `c5f04ab0bf9c06ef4faa9e10d605aeb2cd552fc5`
Response path: `docs/internal/reviews/responses/REV-20260810-090.md`

## Verdict

**CHANGES REQUIRED — REV-089 fixes relationship-section clobbering, but Gate 3 is not yet proved.**

The submitted correction is directionally right and the targeted tests are discriminating for the specific defect REV-089 filed: an already-owned `[dataset:]` section is now used as the reactivation base, only `src`/`flags` are refreshed, and owned `[prune:]` policy is preserved.

However, the real `cmd_activate_client()` path still consults the current active profile unconditionally *before* it reaches that preservation logic. This leaves a residual runtime dependency on the profile after the supposed one-way handoff and also leaves a mutation path that can append current-profile templates during ordinary reactivation.

The canonical contract is stronger than “do not rewrite the relationship-local section body”:

```text
PROFILE/PRESET -> generate once -> CONFIG v4 -> runtime truth
```

An endpoint-only reactivation of an already-active relationship must not require the CREATE-time profile to still exist, validate, or supply missing policy content unless the operation is genuinely creating new policy.

## F1 — P1 — `ensure_cron_config()` still loads the active profile on every reactivation

`cmd_activate_client()` correctly derives `is_new_relationship` from state and calls:

```bash
ensure_cron_config "$workfile" "$is_new_relationship"
...
emit_client_sections "$workfile" "$name" "$is_new_relationship"
```

REV-088 narrowed only the *template collision comparison* inside `ensure_cron_config()` to first CREATE. But `ensure_cron_config()` itself still executes `load_active_profile` unconditionally after the pre-GFS check, even when `check_new_template_collision=0`.

`load_active_profile()` validates and renders `profiles/$PROFILE_ACTIVE` and dies if that profile is missing or invalid.

Therefore this valid lifecycle still fails:

1. relationship is created successfully from profile `P`;
2. native CONFIG v4 is now the execution truth;
3. `P` is later removed, renamed, or becomes invalid (none of which should matter to already-installed policy under the one-way handoff);
4. endpoint changes;
5. ordinary reactivation fails before installed policy can be preserved, solely because the historical CREATE-time profile can no longer be loaded.

That is still persistent profile authority, now as an availability dependency rather than a content-drift comparison.

## F2 — P1 — ordinary reactivation can still append policy from the current profile

After that unconditional `load_active_profile`, `ensure_cron_config()` iterates every `PROFILE_TEMPLATE_NAMES` entry. If a namespaced template from the current profile is absent from the installed CONFIG, it appends it regardless of `check_new_template_collision`.

So reactivation is not strictly topology-only even after REV-089: it can mutate CONFIG by adding current-profile template sections. The collision flag controls whether an existing name is compared; it does not control whether missing profile content is appended.

A reactivation that is merely refreshing an endpoint must not silently restore or introduce policy/template material from the current preset. If an installed CONFIG is intentionally customized and a no-longer-needed generated template was removed, endpoint maintenance must not re-create it as a side effect.

If a genuinely new dataset/task appears during the operation and therefore requires new policy material, that is a distinct CREATE/additive boundary and may legitimately need a profile; the implementation should make that dependency explicit rather than loading a profile for every active relationship unconditionally.

## Why the current evidence misses this

`test/zfsbackup/run.sh` section 49 drives `emit_client_sections()` directly for its key reactivation assertions. It edits the active profile between calls, but keeps the profile directory present and valid. That proves “changed profile content is not copied into preserved relationship sections”; it does **not** prove “reactivation is independent of the profile after CREATE.”

Step 6b then feeds the resulting CONFIG through real `gen-cron.sh`, which is useful for command rendering but still bypasses `cmd_activate_client()`'s earlier unconditional `ensure_cron_config -> load_active_profile` path.

The reported negative control (328/333 against `8d0dc243…`) is therefore valid for REV-089's local section-clobber defect, but not sufficient for Gate 3 as a whole.

## Required correction

Keep the narrow architecture. Do not build profile versioning or a merge framework.

For an ordinary reactivation of an already-active relationship whose installed managed sections already exist:

- do not require `load_active_profile()` merely to refresh endpoint/topology facts;
- do not append current-profile templates as a side effect;
- preserve installed CONFIG as the source of policy truth;
- continue to validate the candidate CONFIG with real `gen-cron.sh` before install;
- retain the explicit CREATE/migration paths where profile loading is genuinely required.

If the implementation needs profile material only when a newly-added dataset or missing managed section must be generated, gate that dependency at that exact additive boundary and fail clearly there rather than making every reactivation depend on the profile.
