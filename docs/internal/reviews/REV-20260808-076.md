# REV-20260808-076 — profile/topology ownership is not enforced at the production boundary

Review time: 2026-08-08 23:23 CEST
Reviewed implementation/design state: `83e3e539b2f5193b782bb8dece933ea8e43bc55b`
Response path: `docs/internal/reviews/responses/REV-20260808-076.md`

## Verdict

**CHANGES REQUIRED before Stage 5 Slice B1/profile runtime starts.**

Claude's pre-implementation finding is correct and the independent review finds the gap is slightly broader than stated: the ownership restriction is not only absent from production code; the current contract test also fails to validate topology-bearing fields inside `profiles/*/templates.conf`.

REV-073 remains the authority: deployment/relationship owns WHAT/WHERE; profile owns HOW. CONFIG v4 `[template:]` is a more general deployment construct and may legitimately contain topology, so the global gen-cron schema must NOT be narrowed merely to constrain profiles.

The restriction belongs at the **profile boundary**.

## F1 — P1 — profile ownership policy has no reusable production enforcement and `templates.conf` is a current false-green

- Severity: P1
- Blocking: yes, before Slice B1 runtime consumes profile files
- Affected: Stage 5 profile loader/compiler boundary, `test/profiles/run.sh`, `profiles/*`

### Evidence

`gen-cron.sh --dump-fields` permits `src`/`dst` in `[template:]`, which is correct for ordinary deployment-owned CONFIG v4 templates. Fleet measurement confirms a real pve0 template with `dst = hdd/backups/pve1`; globally forbidding topology in `[template:]` would break a legitimate production configuration.

The ownership exclusions currently live in `validate_fragment()` inside `test/profiles/run.sh`. No production profile loader/validator exists yet.

Worse, the test calls `validate_fragment()` only for `dataset.inc` and `prune.inc`. `templates.conf` is checked only for section-header shape (`[template:...]`) and then composed into a CONFIG accepted by gen-cron. Because gen-cron's schema legally accepts `template dst/src`, a profile can currently add `dst = ...` inside `templates.conf` and still pass the profile contract suite. That is a direct false-green against REV-073.

### Required outcome

Before Slice B1 uses profile files:

1. Create **one production profile-boundary validator** used by the runtime. A small `lib-profile.sh` is the clean default, but an equivalent production helper is acceptable if it remains one implementation and has a declared dependency edge.
2. Make `test/profiles/run.sh` call that production validator instead of carrying its own independent ownership implementation.
3. Validate **all profile-owned inputs**, including:
   - `templates.conf` field-by-field inside every `[template:...]` section;
   - `dataset.inc`;
   - `prune.inc`.
4. Keep the ordinary CONFIG v4 schema unchanged. Deployment-owned `[template:]` sections outside the profile boundary may continue to carry legitimate `src`/`dst` where gen-cron permits them.
5. Profile validation must fail closed before any config/state/cron mutation.
6. Do not create a second hard-coded list of all accepted gen-cron fields. Accepted field names must remain derived from the generator's schema authority (`--dump-fields` or a single shared schema extraction). The profile-specific **ownership exclusions** may live in the profile validator because that is a different contract.
7. Runtime and test must share the same validator path so a test cannot bless a rule production never executes.

At minimum the existing profile ownership bans must remain enforced (`src`, `dst`, raw `flags`, relationship labels/notification routing where relationship-owned, concrete section headers/topology in `.inc` fragments, and prune recursion override as already defined by the profile contract). Exact allowed policy fields should come from the existing schema/Stage 5 contract rather than a new parallel vocabulary.

### Required regression / negative controls

Add focused cases proving the production validator refuses at least:

- `dst = ...` inside `profiles/.../templates.conf`;
- `src = ...` inside `templates.conf`;
- a relationship-owned/raw field such as `flags = ...` inside `templates.conf`;
- `src`/`dst` in `dataset.inc`;
- forbidden prune topology override in `prune.inc`;
- unknown fields;
- embedded section headers in `.inc` fragments.

And prove the important positive control:

- an ordinary non-profile CONFIG v4 `[template:]` with legitimate deployment-owned `dst` still parses/renders exactly as before.

A useful mutation/negative control is the current tree: inserting `dst = hdd/evil` into the profile's `templates.conf` should demonstrate that today's suite can pass while the corrected suite/runtime refuses it.

### Verification scope

This is a local parser/ownership-boundary change. Required: profile suite + owning zfsbackup/profile-runtime suite + dependency-selected cascade + `./test/impact.sh --verify` and a negative control against the current tree. **No live ZFS campaign is required** unless the implementation unexpectedly touches deployment state, cron, grants, SSH or frozen engines.

## Reviewer position on Claude's proposed shape

- **Agree:** do not narrow gen-cron's global `[template:]` schema.
- **Agree:** profile is a restricted use of native CONFIG fragments, not the same thing as an unrestricted template.
- **Agree:** extract the validator into production before Slice B1 rather than reimplementing it in the runtime.
- **Refinement:** the production validator must cover `templates.conf` as well as `.inc` fragments; merely moving today's `validate_fragment()` is insufficient because today's function is never applied to template bodies.
