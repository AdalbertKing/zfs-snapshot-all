`lib-backup-common.sh` blob `c52a825906c9a77628b62d336bbcb51bef296d5d`.

This was found while completing the release-audit batch for Profiles PR #756.
It is a test-isolation finding, not a defect in the five-profile catalog or its

## F1 — P2: the suite's one-shot helpers inherit one writable `CLIENTS_DIR`

- Severity: **P2**
- Blocking: **yes for treating `test/localbackup` as portable release evidence**;
  this does not by itself block the Profiles product behavior or authorize a
  production change.
- Affected: `test/localbackup/run.sh`, the initial `source "$ZB"`, `run()`,
  `runi()` and `runp()` fixture helpers.

### Evidence

The suite sources `zfs-backup.sh` before defining its helpers. That source loads
`lib-backup-common.sh`, which assigns:

```bash
CLIENTS_DIR="${CLIENTS_DIR:-/etc/zfs-snapshot-all/clients}"
```

The helpers later claim that a missing caller override gives every one-shot a
fresh directory, but use:

```bash
CLIENTS_DIR="${CLIENTS_DIR:-$(mktemp -d)}"
```

Because sourcing the product has already made the variable nonempty, the
`mktemp` arm is not evaluated. A root-capable run therefore used
`/etc/zfs-snapshot-all/clients`, wrote the test relationship `lb.conf` there,
and later cases collided with that record. Moving that exact test artifact out
of `/etc` and rerunning with one explicit temporary `CLIENTS_DIR` kept the host
clean but reproduced the same shared-state failure: **156 PASS / 5 FAIL**.

The five failures are the cases after the first successful `lb` install:

- recursive flat and atomic seed checks;
- two-source seed/install check;
- explicit `--local-user=root` acceptance;
- the proposed-source `--yes` refusal.

Each receives `relationship 'lb' already exists on this host` instead of
testing its own property. The safe executable reproduction is:

```bash
bash docs/internal/reviews/evidence/REV-20261023-169-localbackup-isolation.sh
```

It forces the suite into a disposable record directory, requires the exact
**156/5** signature and checks that `lb.conf` leaked between nominal one-shot
cases. The reproduction itself is **3 PASS / 0 FAIL**. It touches no live ZFS,
network or installed cron and never writes `/etc`.

The discriminating historical control is structural: PR #756 changed only
flat/GFS retention expectations in this test; it did not change the helper
isolation expressions. CI run `39832544369` executes the identical test blob and
passes 161/0, proving the result depends on environment/state rather than the
Profiles assertions. The direct Profiles checks remain green:

- `bash test/profiles/run.sh`: **93 PASS / 0 FAIL**;
- `bash test/zfsbackup/run.sh --section listprofiles`: **23 PASS / 0 FAIL**;
- `bash test/zfsbackup/run.sh --section saveprof`: **45 PASS / 0 FAIL**;
- real planner with stubs for profile `full`: five snapshot and five flat-prune
  jobs (H24/D7/W4/M12/Y5), rc 0.

### Failure mode and impact

The suite can mutate host-level relationship state when run with sufficient
privilege, contrary to its `needs = nothing`/fixture-only contract. On a host
where the default directory is writable, later checks become false negatives;
on a runner where it is not writable, the missing record can make the same
checks appear green. A stale `lb.conf` can also poison a later invocation.
This makes green/red results non-portable and risks leaving test metadata in an
administrator's real `/etc` tree. No ZFS data or production cron was changed in
this review.

- [ ] Set the suite's default `CLIENTS_DIR` to a directory below its own
  disposable `$WORK` **before** sourcing production code; never consult or
  write `/etc/zfs-snapshot-all` in this suite.
- [ ] Give every case documented as one-shot a fresh relationship-record
  directory, while cases intentionally testing repeated/shared state keep one
  explicit shared directory.
- [ ] Add a negative control that runs two nominal one-shot `--name=lb` cases
  and proves the first record is invisible to the second.
- [ ] Run as a root-capable user and prove **161 PASS / 0 FAIL**, no path under
  `/etc/zfs-snapshot-all` was created or modified, and no test record survives
  outside the suite fixture.
- [ ] Preserve the existing shared-state KROK 5, local-relationship and
  remove/edit assertions; do not weaken name-collision behavior in production
  to make the test pass.
- [ ] Run `bash test/localbackup/run.sh`, `bash test/impact.sh --verify`,
  `bash test/reviewctl.sh --verify` and CI on the exact submitted SHA. Report

  the discriminating negative control; it is intentionally expected to stop
  reproducing after the fix.

### Evidence boundary

The reviewer reproduced fixture leakage in a disposable `CLIENTS_DIR` and once
observed the suite-created `lb.conf` under `/etc` before moving it to a
recoverable temporary location. The review did not exercise live ZFS, network,
accounts or an installed cron. The reviewer made no production-code or test
harness fix.
