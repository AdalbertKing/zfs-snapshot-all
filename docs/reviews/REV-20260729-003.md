## F1 — hourly rollback point is not durable

- Severity: **P1**
- Blocking: **no for continued test-fleet operation; yes for claiming one-command durable rollback**
- Status: `OPEN`
- Affected: `deploy.sh`, Phase 7 `PULL_LINE`, commit `75bf956`

### Evidence

The installed cron command performs, every hour:

```sh
cd "$REPO_DIR" && git rev-parse HEAD > "$LAST_GOOD"; git pull --ff-only origin main
```

This has two consequences.

First, after an update from revision A to revision B, the next hourly no-op run writes B over A even when no new revision exists. The useful rollback target therefore survives for at most one hour.

Second, the displayed rollback command is only:

```sh
git -C "$REPO_DIR" reset --hard "$(cat "$LAST_GOOD")"
```

The next hourly cron run pulls `main` again and reapplies the revision that was rolled back. The rollback is therefore temporary unless the operator also disables auto-update.

The file is named `last-known-good`, but no health gate establishes that the current revision is good. At most it records a previous revision.

### Required outcome

Provide a rollback point that survives no-op cron executions and a one-command rollback that remains in effect until the owner explicitly resumes updates.

### Acceptance criteria

- [ ] A no-op hourly update does not overwrite the previous revision.
- [ ] A real A → B update records A before activating B.
- [ ] Rollback to A prevents the next hourly run from immediately restoring B.
- [ ] There is an explicit command to resume automatic updates.
- [ ] The state is named honestly: use `previous-revision` unless a real health gate proves `known-good`.
- [ ] Update failure leaves the active revision and prior rollback state usable.
- [ ] Existing four-host cron lines are migrated without creating duplicate pull jobs.

A suitable design is a small update helper invoked by cron, with a persistent hold file:

- normal mode: fetch, compare revisions, record the old SHA only when a change exists, then fast-forward;
- rollback mode: reset to the recorded SHA and create an update hold;
- resume mode: remove the hold and update explicitly.

The exact interface may differ, but the behavior above is required.

### Required verification

Automated or shell-stubbed cases:

1. A == origin/main: rollback pointer unchanged;
2. A → B: pointer contains A and checkout becomes B;
3. failed fetch/fast-forward: checkout stays A;
4. rollback B → A: hold is created;
5. next hourly invocation while held: checkout remains A;
6. resume: hold removed and checkout advances deliberately;
7. repeated deployment leaves exactly one update cron line.

Live verification on one test server should then confirm the same cycle before propagating it to all four.
