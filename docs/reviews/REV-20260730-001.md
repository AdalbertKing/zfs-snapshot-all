## F1 — rollback can revert the controller that enforces the hold

- Severity: **P1**
- Blocking: **yes for claiming durable rollback**
- Status: `OPEN`
- Affected: `deploy.sh --rollback`, `deploy.sh --self-update`, Phase 7 cron line

### Evidence

The update controller lives inside the same Git checkout it resets:

```sh
git -C "$REPO_DIR" reset --hard "$target"
```

The response reports the resulting failure on both clusters. A rollback from a post-fix revision to a pre-fix revision checked out the old `deploy.sh`, which looked for the hold in the old group-writable location. The next invocation therefore did not see the new root-private hold and updated the checkout back to `main` without an explicit resume.

This was reproduced on:

- pve0 and pve1 in the 192.168.11.x cluster;
- pve1 and pve2 in the metropolis 192.168.28.x cluster.

The response calls this a transitional artifact, but it directly violates the required behavior: **rollback must remain in effect until the owner explicitly resumes updates**. A rollback mechanism must remain effective precisely when the checked-out revision contains an older or broken updater.

### Required outcome

The automatic-update hold must be enforced by code or configuration that is not reverted by `git reset --hard` of the managed checkout.

A suitable design is either:

1. a small root-owned update wrapper outside the repository, responsible for hold, previous revision, fetch, fast-forward, rollback and resume; or
2. at minimum, a cron-level root-private hold guard that prevents invoking any version of the repository updater while the hold exists.

The first design is preferred because it also gives `--resume-updates` stable semantics after rolling back to an older repository revision.

### Acceptance criteria

- [ ] Rolling back to a commit that predates the current hold implementation remains held across every hourly cron invocation.
- [ ] The enforcement point is outside the Git tree being reset, or the cron line independently checks the root-private hold before invoking repository code.
- [ ] An explicit resume operation works while the checkout is on the rolled-back revision.
- [ ] Automatic update cannot bypass the hold merely because the rolled-back `deploy.sh` uses an older state path or older implementation.
- [ ] The existing four hosts are migrated without duplicate updater jobs.

### Required verification

- Build a test fixture with a current updater and an older checked-out `deploy.sh` that ignores the new hold.
- Perform current → old rollback.
- Invoke the exact scheduled update entry point at least twice.
- Assert that HEAD remains old and the hold remains intact.
- Run explicit resume and assert that the hold is removed and the checkout advances deliberately.
- Repeat the cycle on one live test host before fleet propagation.

## F2 — some failed state transitions still leave hourly retries enabled

- Severity: **P1**
- Blocking: **yes for closing REV-20260729-004 F2**
- Status: `OPEN`
- Affected: `do_self_update()`, `do_resume_updates()`, failure-injection coverage

### Evidence

The implementation correctly prevents activating B when the initial write of A fails. However, two later failure branches still fail open:

1. When fast-forward fails and restoration of the previous pointer also fails, the script attempts to write an automatic hold. If that hold write fails, it only warns that the state needs manual attention and returns. The hourly cron entry remains installed and will retry.
2. When `--resume-updates` removes a hold, the explicit update fails, and restoration of the hold also fails, the script warns that automatic updates may retry hourly. This is the opposite of the required safe default.

The response and test suite provide one injected write-failure case: an immutable state directory proves that failure to record A prevents activation of B. The original required verification also called for pointer-restoration failure, atomic-rename failure, hold-write failure, reset failure and failed update after resume. Those paths are not exercised by the current 30-test suite.

### Required outcome

Any state transition whose final safety state is uncertain must make the next scheduled updater invocation unable to advance the checkout. Logging a warning while leaving the cron retry path active is insufficient.

The exact emergency control may be a secondary root-private sentinel, disabling/removing the updater cron entry, or an external wrapper with its own fail-closed state. It must not depend solely on the same write operation that has just failed.

### Acceptance criteria

- [ ] Pointer-restoration failure leaves scheduled updates disabled or held.
- [ ] Failure to write the emergency hold cannot leave the updater eligible for an hourly retry.
- [ ] Failed `--resume-updates` restores a hold or independently disables scheduled updates.
- [ ] Rollback reset failure remains held and reports the real checkout state.
- [ ] Every failure path returns non-zero with a precise diagnostic.
- [ ] A later successful administrative recovery can re-enable updates explicitly.

### Required verification

Inject and assert each of the following independently:

1. initial pointer write failure;
2. atomic rename failure;
3. pointer restoration failure after failed fast-forward;
4. automatic-hold write failure;
5. rollback reset failure;
6. hold removal failure;
7. update failure after resume;
8. hold restoration failure after failed resume.

For every case record:

- active checkout SHA;
- `previous-revision` content/type;
- hold state;
- whether the scheduled updater remains enabled;
- exit code and diagnostic.

## Verified closure detail

### REV-20260729-004 F1 — closed

The default update state moved to `/root/.zfs-snapshot-all-update-state`. Live verification shows `700 root:root`; new state files are root-owned and the delegated `zfsbackup` account was unable to read, remove or replace the hold on both metropolis hosts. Symlinked directory/file and group/world-writable directory cases pass on Linux.

Residual note: `ensure_update_state_dir()` does not explicitly compare directory ownership with the effective updater UID, but the production default is directly under `/root` and live ownership is correct. This is not kept open as a practical production defect under the current fixed default.

### REV-20260729-004 F3 — closed

A real update is refused when `git status --porcelain` is non-empty. Tests cover an untracked file and a modification to a tracked file untouched by the incoming commit. SHA and rollback pointer stay unchanged.

### REV-20260729-004 F4 — closed

Known updater forms are scoped to this repository, counted and normalized to exactly one current line. Mixed current/old, duplicate-current and unrelated `--self-update` cases are covered by deterministic tests. Live hosts retain one current updater line.
