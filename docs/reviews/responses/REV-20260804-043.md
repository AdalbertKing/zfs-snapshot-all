# Response to REV-20260804-043

## F1 — ACCEPTED

Agreed without reservation. The counterexample is correct and the first
fix (`2e02a7d`) genuinely had this gap: `assert_target_block_not_clobbered`
excused any "lost" cron line whose `-O HostKeyAlias=zfs-client-<name>`
also appeared anywhere in the newly rendered block. That alias is
shared by every job a single client owns. A client with two datasets
could have one silently deleted by an install as long as the *other*
one still rendered under the endpoint being switched to — exactly the
class of defect this guard exists to catch, reproduced precisely by the
finding's own `alpha`/`tank/a`/`tank/b` example.

### Implementation

Replaced the alias-only carve-out with `endpoint_normalized_identity()`:
normalizes *only* the mutable host between `"acct@` and the following
`:` in a pull line's `-A "acct@host:path"` argument, to a fixed
placeholder, and leaves everything else in the line untouched. A "lost"
line is excused only if its normalized form matches a normalized
proposed line exactly — account, source dataset, target dataset,
schedule, retention flags and `HostKeyAlias` all still have to match.

Anchored specifically to the `-A "...@` prefix, not a bare
"first colon in the line" search, because dataset names may legally
contain a colon (`pc_is_dataset`'s own character class allows it) —
matching anywhere would risk normalizing part of a path instead of the
host.

A line with no `-A "acct@host:..."` shape at all (`delsnaps.sh`,
`check-snap-age.sh` — no remote connection to switch) passes through
the normalizer unchanged. Such a line can only be excused by being
byte-identical to a proposed line already, which the strict `comm(1)`
diff upstream of this carve-out would not have called "lost" in the
first place — fail-closed by construction, matching acceptance
criterion 6 without a special case for it.

### Acceptance criteria

1. **One-job endpoint change passes** — `test/zfsbackup`: "a one-job
   endpoint change for the same relationship passes".
2. **Two jobs, one dropped under the new endpoint, refuses** — the
   finding's own counterexample, reproduced as a test case: "same
   client, one of two datasets dropped under the new endpoint still
   refuses". This is the case the first fix missed; it now fails
   correctly.
3. **Two jobs, both retained, endpoint-only change on both, passes** —
   "same client, both datasets survive an endpoint switch, passes".
4. **A source/target/schedule change is not disguised as endpoint-only** —
   "a source dataset change alongside the endpoint is not disguised as
   endpoint-only": same account, same `HostKeyAlias`, same schedule,
   different `-A` source path — refuses, because normalizing only the
   host leaves the differing source path in the compared string.
5. **A different client's removed job still refuses** — "a different
   client's removed job continues to refuse" (retained from the first
   fix's own test, still correct under the new logic).
6. **Fail-closed on unparseable lines** — by construction, see above;
   no dedicated test needed beyond the existing "unrenderable proposal
   fails closed" case, which exercises the same code path from the
   other direction.
7. **Regression tests added, impacted suites re-run** — `test/zfsbackup`
   grew by 3 net (two cases rewritten to the reviewer's own acceptance
   language, three new ones for the counterexample and the source-change
   case): **263/263**. `bash -n` clean on both changed files.
8. **Gate G re-run live under the corrected guard** — done; see
   `docs/reviews/responses/REV-20260804-042.md`'s Gate G section for
   the full sequence. Summary: real route switch (LAN address →
   isolated bridge address) for a live throwaway client, corrected
   guard let the re-activation through cleanly (no FATAL), a real
   subsequent incremental over the new route confirmed byte-identical,
   `authorized_keys` unchanged at one line, old address retained as a
   known candidate.

### Evidence the tests actually catch the regression, not just pass

Before restoring the corrected fix, the fix alone (not the tests) was
stashed and the suite re-run against the prior (`2e02a7d`) logic:
exactly the two cases targeting this defect fail
(`FAIL clobber: same client, one of two datasets dropped under the new
endpoint still refuses`, `FAIL clobber: a source dataset change
alongside the endpoint is not disguised as endpoint-only`), everything
else stays green (258/260). Fix restored, re-run: 263/263. Same
methodology used for the original Gate G fix's own regression proof.

### Remaining risk

None identified. The corrected guard has both a live re-run (real
route switch, real incremental) and full local coverage of the
counterexample shape; the fix is narrowly scoped to the one field that
legitimately varies across an endpoint switch and leaves every other
part of job identity as a strict, literal match.
