## F1 — ACCEPTED

### Analysis

Confirmed exactly as described. The old remote command:

```bash
"./deploy.sh --draft-scope=$my_label 2>/dev/null; \${VISUAL:-\${EDITOR:-vi}} $(peer_scope_path "$my_label")"
```

joined draft and editor with a bare `;` (the editor opened regardless of the
draft's exit status), discarded the draft's stderr, and set `remote_ok=1`
right after `--join` -- never revisited for whatever happened in the editor
stage. A failed editor only `warn`ed; the final summary still printed "Zakres
zredagowany zdalnie" unconditionally whenever `remote_ok=1` and `$PEER_MODE`
was set. No disagreement with any part of the finding.

### Planned or implemented change

Extracted the draft/edit/check substage into its own function,
`remote_scope_stage()` (deploy.sh, next to `peer_scope_path()`), so it is
independently testable by the same sed-range technique
`test/draftscope/run.sh` already uses for `do_draft_scope` -- not incidental:
this is exactly what let the required regression tests exist without needing
root, which `do_pair()` itself still requires before reaching this code.

The function stages the four substeps explicitly and returns a distinct exit
code per stage reached:

- `0` -- scope exists (or was freshly drafted), edited, and passes
  `--commit-scope-check` -- the ONLY code that may be called "ready".
- `2` -- `--draft-scope` failed; stops before the editor; no file created;
  the draft's own stderr is no longer discarded.
- `3` -- the editor itself exited non-zero.
- `4` -- `--commit-scope-check` failed on the file the editor produced (the
  exact "false success" shape F1 named: a file that looks edited but does
  not parse).

`do_pair()` now keeps `scope_rc` separately from `remote_ok` and prints a
distinct recovery instruction for each of 0/2/3/4 (plus a fallback case for
an unexpected/transport-level ssh failure): a state-2 or state-3 failure
explicitly says "join already ran, do not repeat it" and gives only the
draft/edit/check commands, not the whole relationship again. `--commit-scope`
is never invoked automatically in any branch -- unchanged, U10 condition 1.

The scope path is now quoted (`"$SCOPE"` inside the generated remote script,
built from a local variable rather than an inline unquoted
`$(peer_scope_path ...)` expansion).

Covers, against the acceptance criteria:

## A defect the campaign found before F1 was read: `PEER_CONF_MODE: unbound variable`

Not a review finding -- found live, during Gate B's first real attempt,
before this response file's F1 section above was even written.

### What happened

The very first live `deploy.sh --join` ever run against a `--mode=backup`
package (this exact live campaign, collector=pve1, peer/source=pve2, client
label `pve2b`) crashed twice with `deploy.sh: line 3691: PEER_CONF_MODE:
unbound variable`, once during the manifest-write heredoc and once again in
the closing summary's `[ -n "$PEER_CONF_MODE" ]` check. `do_join()` still
printed "Join zakonczony" (the error came from a failing `cat > "$mpath"
<<EOF` heredoc under `set -u`, which aborts that statement but not the whole
function) and exited 1.

### Root cause

`do_join()` declares local aliases from the validated `PC[...]` array for
every `PEER_CONF_*` field it uses:

```bash
local PEER_CONF_ROLE="${PC[PEER_CONF_ROLE]}"
local PEER_CONF_TARGET="${PC[PEER_CONF_TARGET]}"
local PEER_CONF_ACCOUNT="${PC[PEER_CONF_ACCOUNT]}"
local PEER_CONF_AS="${PC[PEER_CONF_AS]}"
local PEER_CONF_DATASETS="${PC[PEER_CONF_DATASETS]:-}"
local PEER_CONF_INITIATOR_LABEL="${PC[PEER_CONF_INITIATOR_LABEL]}"
local PEER_CONF_REMOTE_JOIN="${PC[PEER_CONF_REMOTE_JOIN]:-}"
```

`PEER_CONF_MODE` is missing from this list entirely, even though it is read
twice further down (`PEER_JOIN_MODE="$PEER_CONF_MODE"` in the manifest
heredoc, and `[ -n "$PEER_CONF_MODE" ]` in the closing log block). Under
`set -uo pipefail` (line 28), referencing that undeclared local scalar is
fatal. This is a plain missing line from REV-20260802-033 slice 5/6 (when
`PEER_CONF_MODE` was introduced) -- every local test of `--mode=` packages
went through `--join-check` only (validation, never real `do_join()`
execution -- see `test/join/run.sh`'s own header on why), so nothing local
could have caught a bug that lives exclusively in `do_join()`'s real
execution path.

### Fix

Added the missing line, matching the sibling pattern (`:-` default, since
`PEER_CONF_MODE` is optional -- absent for a legacy pre-slice-5 package):

```bash
local PEER_CONF_MODE="${PC[PEER_CONF_MODE]:-}"
```

While there, hardened `PEER_CONF_TARGET` the same way (`:-` added) as a
consistency fix, not a new finding: a freshly-produced package always writes
that line (even empty, for `--mode=sync`), so it was not observed to crash
live, but a genuinely old package missing the line entirely would hit the
identical unbound-variable shape -- the same reasoning `PEER_CONF_DATASETS`
and `PEER_CONF_REMOTE_JOIN` already use `:-` for.

### Evidence

Live, not stubbed -- this is exactly the class of bug (`do_join()`'s real
execution) this project has never had a local test path for, by established
choice (`test/join/run.sh` header: "a test that has to run as root is a test
where a mistake creates a real account on a real host"), and this class of
bug (a plain bash scoping omission) only manifests under real execution,
never under `--join-check`'s validation-only path. Re-verified by redoing
the same relationship from a clean state after the fix -- see Gate B below.

### Remaining risk

None identified beyond the standing gap already named above (`do_join()`'s
real actions have no local regression test of any kind, for any field, by
design). If another `PEER_CONF_*` field is ever added to the wsad grammar in
the future, the same "declare it as a `local` alias in `do_join()`" step is
easy to forget again, since nothing local exercises that path -- worth a
`grep 'PEER_CONF_' | wc -l` sanity comparison between `parse_peer_conf`'s
allow-list (line 745-747) and `do_join()`'s local-alias block the next time
either changes.
