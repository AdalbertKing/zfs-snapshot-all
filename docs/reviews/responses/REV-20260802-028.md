## F1 — the remediation command must not rewrite unrelated grants — ACCEPTED, IMPLEMENTED

### Analysis

The review is right, and it is right about the distinction that matters: my
previous fix (`0d48103`, changing the printed list from GAPS to the full set of
the migrated block) addressed **the case that was observed** and left **the
primitive** untouched.

`--allow-quiesce` rewrites `/etc/zfs-quiesce-allow/<account>` wholesale from the
list it is handed. `CAP_ALL` is derived from one rendered block. So on a host
whose account also carries grants from another config, an older deployment or a
manual job, the generated command still revoked them — while presenting itself
as the safe, generated fix. Printing a wider list does not make a destructive
primitive additive; it only moves the boundary of what gets destroyed.

### Implemented change

Option 2, the explicit additive operation, as the review preferred:

- **`--add-quiesce`** provisions exactly like `--allow-quiesce` but **merges**:
  existing entries are read, the required ones are added, the result is
  `sort -u`'d. Idempotent — a second identical merge is a no-op, and an entry
  present in both lists is not duplicated.
- **`--allow-quiesce` keeps replacing.** That is the correct behaviour for
  *enrolment*: re-running `--join` with a narrower dataset list is supposed to
  drop what was removed, and the suite already pinned that (`tx-widen`). The two
  behaviours have to coexist, which is why this is a new flag and not a change
  of meaning for the old one.
- **Fail closed.** An existing whitelist that cannot be *read* stops the grant
  instead of being treated as empty. "Unreadable" is not "obsolete" — and
  neither is "absent from the caller's list", which is the whole finding.
- The migration remediation block now prints `--add-quiesce`.

### The documentation half

The remediation text still said the whitelist is *PRZEPISYWANA* (rewritten) from
the printed list. True of the old command, false of the new one, and exactly the
sentence that would make an operator believe unrelated grants are at risk — the
opposite of what `--add-quiesce` guarantees. It now says the command adds the
required datasets and **preserves** what is already there, including entries
from another config, an older deployment or a peer relationship, and names the
difference from `--allow-quiesce` explicitly. (That correction is also described
in the response to REV-20260802-029, which is where it was carried.)

## Remaining risk

The unreadable-whitelist case **SKIPs on this workstation**: MSYS ignores mode
`0000` for the owner, so the file stays readable and a check that passed here
would have passed for the wrong reason. It is skipped loudly rather than
weakened, and it needs a Linux host to actually execute. It has since run on the
fleet as part of the suite, but the skip is a property of the environment, not
of the commit, so it will keep skipping on Windows.

`--add-quiesce` merges what it can read. A whitelist that is readable but has
been hand-edited into something the parser drops (the header comment is
preserved, anything else non-blank is kept verbatim) is out of scope: the file
is declared managed-by-tool at its head, and the tool does not attempt to
interpret hand edits beyond preserving them.
