## A defect found AFTER this review's scope, in the code it accepts

`54c1ead`. Running the real remote-quiesce path on a real host exposed a bug that
every local suite had been passing over for days.

`thaw_all` runs from the EXIT trap. **In a trap handler, bash resolves a bare
`return` against the status the shell was exiting with, not against the last
command in the function.** So

```bash
gq_thaw() { ... sudo -n "$QHELPER" thaw "$1" >/dev/null 2>&1; return; }
```

returned 0 while sudo had exited 3, and the consequences chain exactly as
REV-006 F3 described — in the code written to fix F3:

- `thaw_all` took the success branch and logged `QLOG thawed VM 104`
- the id was dropped from the recovery list
- `on_exit` saw an empty file, deleted it and **killed the deadman**
- the run exited 0

Measured on pve0 with a wrapper logging every helper call: wrapper `exit 3`, run
`EXIT=0`, guest left `frozen`, nothing remaining that would ever thaw it.

**Why no suite caught it, and why the new guard is textual.** bash 5.1.4
(Debian 11 / PVE 7 — every real host here) reproduces this; bash 5.3.9 (the
development box) does not. Verified both ways with a minimal reproducer. The
existing err4 case ("a failed thaw fails the run (6)") therefore passed on the
BROKEN code locally and would keep passing. A behavioural test on this machine
cannot distinguish fixed from broken, so `test/quiesce` now asserts textually
that no bare `return` exists in the embedded script — it fails on the pre-fix
library and passes after. Every `return` there now carries its status explicitly.

So §1's "no longer fail-open in the reviewed paths" was true of the source text
and false of the behaviour on the hosts. It is now true of both, and verified on
the platform where it failed.

## F1 — final catch-up record can become stale — ACCEPTED, IMPLEMENTED

Correct on both counts, and the second example (same endpoint name, different
host) is the one that would have been hardest to notice afterwards.

`final-catchup` now records the transport it actually proved:

```
FINAL_CATCHUP_ENDPOINT=lan
FINAL_CATCHUP_HOST=192.168.11.11
FINAL_CATCHUP_PORT=22
FINAL_CATCHUP_EPOCH=1753...
FINAL_CATCHUP_AT="2026-07-31 15:12:03"
```

`set-endpoint` requires all three to match the endpoint being LEFT — name, host
and port — plus an age within `CATCHUP_MAX_AGE`, default **1800s (30 min)** as
recommended. `--allow-stale-catchup` overrides only the age, warns, and names
what it costs ("everything written since <time> will cross the slow link").
`--skip-final-catchup` is unchanged for the already-disconnected case.

Two additions beyond the letter of the requirement:

- **Moving an endpoint invalidates a catch-up recorded against it**, at the
  moment of the move rather than silently later, with a warning naming the old
  and new address.
- **A record with no `FINAL_CATCHUP_EPOCH` is refused rather than treated as
  fresh.** Configs written by the previous version have no epoch; defaulting a
  missing timestamp to "recent" would silently grandfather in exactly the stale
  state this finding is about.

Tests (7 new, `test/zfsbackup`): stale refuses and names the age; different host
refuses; different port refuses; a fresh catch-up against the exact endpoint
passes; the override proceeds with a warning; a legacy record without an epoch is
not treated as fresh; moving the LAN endpoint invalidates the record. The
pre-existing case that asserted the weaker "name matches" contract was updated
rather than worked around — that contract changed deliberately.

## F2 — grant installation is not transactional — ACCEPTED, IMPLEMENTED

Correct. The old order created the helper and whitelist first and only then
discovered that sudo was missing or the rule would not validate.

`install_quiesce_grant` is now staged:

1. dependencies resolved first (visudo located, `sudo` package installed if
   absent) — before anything is created;
2. whitelist and sudoers rule written to temporary files;
3. the rule validated with `visudo -cf` while still in `/tmp`;
4. one short install phase;
5. on ANY failure, every artifact **this run** created is removed and the
   rollback is reported by name.

The shared helper is handled as the review allows: if this run installed it and
no account holds a grant after rollback, it is removed; if another account still
has one, it stays and the message says so explicitly rather than leaving the
operator to work out which artifacts are shared.

Tests (6 new, `test/quiescehelper`), each injecting a failure at one stage and
asserting **zero** orphaned per-account artifacts: clean run installs both; a
failed `sudo` install leaves nothing; a rejected sudoers rule leaves no
whitelist; a failed whitelist install rolls back; a failed rule install rolls the
whitelist back too (the case the old code got wrong); a retry after a failure
succeeds cleanly.

Two notes on test mechanism, since they affect how much the results are worth:
the dependency-failure case removes the `visudo`/`sudo` stubs entirely, because
with a stub on PATH that branch is never reached and the case would pass while
testing nothing; and the `install` stub strips `-o`/`-g` because this box has no
`root` user, which would otherwise fail for reasons unrelated to the test.
