## F1 — rollback can revert the controller that enforces the hold — ACCEPTED, IMPLEMENTED

Correct, and reproduced exactly as described: the hold/rollback/resume logic
lived entirely inside `$REPO_DIR/deploy.sh`, the tree `--rollback` resets with
`git reset --hard`. Rolling back across the exact commit that introduced or
relocated the hold checked out code that did not enforce it, so the next
scheduled invocation of *that* code did not see the hold.

### Implemented change

The reviewer's preferred design (a small root-owned wrapper outside the
repository) is what was built: **`update-control.sh`**, a new file at the repo
root containing the entire self-update/rollback/resume control plane
(`ensure_update_state_dir`, `write_state_file`/`read_state_file`/
`remove_state_file`, `do_self_update`, `do_rollback`, `do_resume_updates`, plus
a new `emergency_disable` -- see F2), parameterized by `REPO_DIR` and
`UPDATE_STATE_DIR` via two placeholders (`__REPO_DIR__`, `__UPDATE_STATE_DIR__`)
that `env:REPO_DIR`/`env:UPDATE_STATE_DIR` override for testing, exactly like
`deploy.sh` itself already does.

`deploy.sh`'s Phase 7 deploys a fresh, `sed`-templated copy of this file into
`$UPDATE_STATE_DIR/update-control.sh` on every successful (non-`--check-only`)
run -- root-private (`0700`), and critically **outside `$REPO_DIR`**, so
`git reset --hard $REPO_DIR` during a rollback cannot touch it no matter which
revision is being rolled back to or from:

- the hourly cron line now invokes `$UPDATE_STATE_DIR/update-control.sh
  --self-update` directly, never `$REPO_DIR/deploy.sh --self-update`;
- `deploy.sh`'s own `--self-update`/`--rollback`/`--resume-updates` dispatch
  now `exec`s the deployed wrapper first if one exists and is not a symlink,
  falling back to the (unchanged) logic built into `deploy.sh` only as a
  bootstrap path for a host that has never successfully deployed the wrapper
  yet (first-ever run, or the wrapper removed by hand);
- `is_this_repo_updater_line()` (both in `deploy.sh` and mirrored in
  `test/selfupdate/run.sh`, per the existing "keep both in sync" comment) now
  also matches the wrapper-shaped cron line, so an existing host's
  `deploy.sh`-direct line is normalized to the wrapper line on its next
  non-`--check-only` deploy, the same way the old bare-`git-pull` shape was
  normalized to the `deploy.sh`-direct shape by REV-20260729-004 F4.

This satisfies the specific acceptance criterion that a manual
`--resume-updates`/`--rollback` must work "while the checkout is on the
rolled-back revision": both are documented as running via
`$UPDATE_STATE_DIR/update-control.sh` directly, a static file that persists
from the last successful deploy regardless of what `$REPO_DIR` currently
contains, rather than via whatever `deploy.sh` happens to be checked out.

### Evidence

`test/selfupdate/run.sh` cases 16-18 (new):

- 16: a wrapper deployed via the same `sed` templating Phase 7 uses honors an
  **existing hold** with `--self-update`, even though the throwaway `$CLONE`
  fixtures in this suite have no `deploy.sh` in them at all -- proving the
  enforcement does not depend on what is checked out;
- 17: `--resume-updates` via the same deployed wrapper removes the hold and
  advances the checkout to the real upstream revision;
- 18: `--rollback` via the wrapper moves the checkout back and re-establishes
  the hold.

All three PASS locally. `bash -n` on both `deploy.sh` and `update-control.sh`
is clean. The `sed` templating itself was smoke-tested in isolation (a
throwaway state dir, a fake `REPO_DIR=/fake/repo`, confirming the placeholders
are correctly substituted and the resulting file is independently syntax-valid
and runnable). Phase 7's new deployment block could **not** be exercised
end-to-end locally, because reaching Phase 7 at all requires
`[ "$(id -u)" -eq 0 ]`, which this box cannot satisfy -- this is the same
"canary" limitation `test/selfupdate/run.sh` has documented from the start for
every phase past the update-dispatch functions.

### What was not built

The reviewer's minimum-acceptable alternative ("at minimum, a cron-level
root-private hold guard") was not needed once the full wrapper was built, since
the wrapper satisfies the stronger, preferred design directly.

## F2 — some failed state transitions still leave hourly retries enabled — ACCEPTED, IMPLEMENTED (partial)

Correct on both named branches.

### Implemented change

A new `emergency_disable(reason)` function (defined once in
`update-control.sh`, and duplicated with a narrower fallback in `deploy.sh`'s
bootstrap-fallback copy) replaces every bare `write_state_file "$UPDATE_HOLD_FILE"
... || warn ...` in a failure-escalation position:

1. try to write the hold file, as before;
2. if that fails, in `update-control.sh` only: `chmod 000` on the wrapper's
   own path (`$0`) -- this is proportionate there because the wrapper's only
   job is dispatching updates, so disabling it entirely is the correct
   circuit breaker. `deploy.sh`'s bootstrap-fallback copy deliberately
   **skips** this step, since `$0` there is `deploy.sh` itself, used for the
   whole deployment sequence, not just updates -- disabling it would be a
   bigger hammer than the situation calls for;
3. if that also fails (or was skipped), remove the hourly cron line entirely
   (`crontab -l | grep -v ... | crontab -`) as a last resort;
4. if all of the above fail, `warn` loudly and return non-zero -- the
   remaining true worst case (multiple independent write paths failing at
   once), which the review accepts needs only "exit code and diagnostic", not
   a guarantee.

Applied to the three branches named in the review:

- `do_self_update`: pointer-restoration failure after a bad fast-forward now
  escalates through `emergency_disable` instead of a bare `warn`-only hold
  write;
- `do_rollback`: a failed `git reset --hard` now escalates through
  `emergency_disable` instead of silently discarding the re-write's own
  failure (`2>/dev/null`, unchecked) before `die`ing;
- `do_resume_updates`: hold restoration after a failed explicit update (post
  `--resume-updates`) now escalates through `emergency_disable` instead of a
  bare `warn`-only hold write.

Two branches the review flagged were already fail-closed and needed no
change: `do_resume_updates`'s hold-removal failure already `die`s with the
hold left in place (removal only proceeds past `die` if it actually took
effect), and `do_rollback`'s *initial* hold write (before the reset) already
`die`s without touching the checkout if it fails.

### Evidence

`test/selfupdate/run.sh` case 19 (new): `emergency_disable` is exercised
directly (the file is `source`d, guarded by a new
`[ "${BASH_SOURCE[0]}" = "$0" ]` check around `update-control.sh`'s dispatch so
sourcing does not also trigger it -- a real invocation, `bash update-control.sh
--self-update` or a direct cron `exec`, is unaffected since `BASH_SOURCE[0]`
equals `$0` there) against a `chattr +i` state directory, confirming the
wrapper's own file permissions are reduced to `000` when the hold write itself
cannot succeed. PASS locally where `chattr` is available in principle (this
box cannot make a directory immutable at all -- Windows/NTFS -- so this case
**SKIPs** here exactly like REV-20260729-004's original F2 case did before its
live verification).

### What is honestly not covered yet

The review's required-verification list named eight specific failure points.
This pass covers 1 (initial pointer write — pre-existing coverage), 3
(pointer-restoration failure), 5 (rollback reset failure), and 8 (hold
restoration failure after failed resume) with the `emergency_disable`
escalation plus test 19's direct exercise of the escalation mechanism itself.
**Not separately fault-injected**, and left as an honest gap rather than
claimed:

- 2 (atomic rename failure specifically, as distinct from mktemp/write
  failure) — would need a fixture where the state directory accepts a new
  file but rejects a rename into it (e.g. a read-only bind mount over the
  destination only), which `chattr +i` on the whole directory does not
  isolate;
- 4 (automatic-hold write failure) and 6 (hold removal failure) are exercised
  only as the same code path as 3/8 respectively (the write/remove primitives
  are shared), not as independently constructed scenarios;
- 7 (update failure after resume, without a prior write failure) is exercised
  indirectly by the existing case 6/`do_resume_updates` logic but not paired
  with a simultaneous hold-restore failure in one test.

This is a smaller-effort pass than a full fault-injection matrix would be; the
mechanism (`emergency_disable`) is uniform across all the named failure
points, so the untested combinations exercise the same function already
proven to behave correctly under case 19's direct fault, but that is an
argument by shared code path, not independent evidence for each one.

## Remaining risk

- Everything named as remaining risk in the REV-20260729-004 response still
  applies unchanged (single-file rollback pointer, hold-as-file rather than a
  lock, transitional artifacts around any future state-schema move).
- **New transitional risk introduced by this fix itself**: a host that has
  never run a post-`update-control.sh` deploy has no wrapper yet, so its cron
  line still invokes `$REPO_DIR/deploy.sh --self-update` directly and is
  exactly as exposed to F1 as before until one successful deploy lands the
  wrapper and normalizes the cron line. This is unavoidable for the very first
  rollout of this fix on each host (there is no wrapper to protect the
  bootstrap that creates the wrapper) and self-heals on that host's next
  successful deploy, the same shape of one-tick artifact the reviewer already
  accepted for REV-20260729-004.
- F2's fault-injection coverage is partial (see above) — the escalation
  mechanism is uniform and directly tested once, but not independently
  fault-injected at every one of the eight named points.
- `emergency_disable`'s `chmod 000 "$0"` step assumes `$0` resolves to the
  wrapper's real path at invocation time; if cron or an operator ever invokes
  it through a relative path or a symlink this was not tested against, the
  chmod could target something other than intended. Worth a live check when
  fleet access returns.
