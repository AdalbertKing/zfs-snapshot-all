## F1 (§1) — the left side was not the live crontab — ACCEPTED

Correct, and the framing in your closing criterion is the part I had wrong. I
built the preview to answer *"does the proposed config differ from the current
config?"* when the question the operator is actually consenting to is *"what will
change on this machine?"*. Those coincide only when the installed block already
matches its config, which is exactly the assumption an admin workflow may not
make.

Every kind of drift you list was invisible: a hand edit, an interrupted
deployment, a block installed from a different config, a stale block. In all of
them the preview could print "(bez zmian)" and `--install` would then rewrite the
live crontab.

### Implemented change

`before` is now captured from the installed managed block:

```bash
crontab -l | sed -n '/^# BEGIN zfs-backup-managed/,/^# END zfs-backup-managed/p'
```

`gen-cron.sh --install` replaces exactly that block and leaves every other cron
line untouched, so the block is both the right thing to compare and the whole of
what accepting can change — unrelated lines are preserved by construction rather
than by the preview promising it. An absent crontab or absent block gives an
empty left side, which is the honest answer: everything is new.

The `# Source:` normalisation stays and now earns its place twice over: the live
block names the real config while the proposal renders from a temp file, so
without it every preview would show a spurious change.

Wording changed with the behaviour, since the old line described the old
mechanism:

```
--- co sie zmieni w crontabie (lewa strona = to, co JEST teraz zainstalowane) ---
  (bez zmian -- zainstalowany blok jest juz dokladnie taki)
```

### The test you specified

Config A renders `1 * * * *`, the live crontab holds `44 * * * *`, and the
proposal is still A. The preview must show `-44 * * * *` / `+1 * * * *` and must
not say "bez zmian". It does, and it **fails against the previous version** —
that one case is the whole finding, reproduced mechanically.

## F2 (§2) — the existing side ignored a render failure — ACCEPTED, and removed by construction

The unguarded AND-list you quote is gone: the current config is no longer
rendered at all for this diff, so an invalid current config can no longer produce
a partial `before`. The failure mode is removed rather than handled, which I
prefer where it is available.

Two things remain true and are worth stating so the fail-closed claim is precise:

- The **proposed** side is still explicitly guarded, and now has a regression
  test: a config `gen-cron.sh` rejects makes the preview return non-zero and
  `activate-client` die without touching anything. That guard works only because
  this file sets `pipefail` — the `!` tests the pipeline, not just `sed` — which
  is now written down at the line rather than left as folklore.
- An invalid **current** config still stops the run, just earlier and elsewhere:
  the working copy is a copy of it plus the new sections, and activate-client
  validates the working copy with `gen-cron.sh` before the preview is reached.

## Against your acceptance criterion

> This is the exact config and exact live cron change that accepting will apply.

I believe both halves now hold, with one boundary worth naming rather than
leaving for you to find: the statement is exact for the **managed block**, which
is the only thing `--install` writes. Cron lines outside the block are untouched
and are deliberately not shown — including any that a human added inside the
block by hand, which the install will remove and the diff will therefore display
as a deletion.

## Remaining risk

- `crontab -l` failing for a reason other than "no crontab" is indistinguishable
  here from an empty crontab, and would render the whole block as new. The
  install that follows would then be correct anyway — it replaces the block
  wholesale — so the consequence is a noisy preview, not a wrong action.
- The preview still shows what will be installed **into the invoking user's
  crontab**. That is right today because everything runs as root, and it is the
  next thing to revisit when the collector gains a dedicated account, which is
  the step I am on now.
