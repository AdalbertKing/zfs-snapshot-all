## F1 (§2) — `mkdir allow_dir` does not roll back — DISPUTED on the facts, ACCEPTED one layer down

### Analysis

The call is there, and it was there before the commits under review.

```bash
    if [ ! -d "$allow_dir" ]; then
        created_dir=1
        install -o root -g root -m 0755 -d "$allow_dir" || {
            created_dir=0; _grant_rollback
            warn "could not create $allow_dir -- no quiesce grant was created for $account"; return 1
        }
    fi
```

That is `git show 7dc4a98:deploy.sh` — the base this review compares against. The
line dates from the REV-008 F2 transaction work in `763767b` and `ad5e745` did
not touch it, which is exactly why I think it read as missing: it is not in the
diff. A diff-only read of `ad5e745` shows `did_helper=1` appearing, then the next
hunk starts after the `mkdir` block, so the block looks like unguarded
pre-existing code.

So §2's five-step consequence does not occur. Step 4, "funkcja wychodzi bez
przywrócenia starego helpera", is not reachable: `did_helper=1` is already set,
`pre_helper=1` for an existing helper, and `_grant_rollback` restores it. The
backup directory and both staged temp files are removed on the same path.

**But the review is right that something survives, one layer below where it
looked.** `created_dir=0` was reset *before* calling the rollback, to say "the
directory was not created, do not remove it". That reasoning is wrong for the
realistic failure. `install -d` creates the directory and only *then* applies
owner and mode, so it can fail having already made it. With the flag reset, that
empty root-owned directory is the one residue of a run that reports creating
nothing — which is the same class of defect §2 describes, just smaller and at a
different step.

### Implemented change

The reset is gone. `created_dir` stays 1, and the rollback attempts the `rmdir`.

That is safe without further conditions, which is why it is the whole fix:
`rmdir` refuses a non-empty directory, and this branch only runs when the
directory did not exist beforehand, so there is nothing of another peer's inside
it to lose. If `install -d` failed without creating anything, the `rmdir` fails
silently and nothing changes.

### Tests

§3's two cases, with the honest note that the first one as literally worded is
not reachable:

**"existing grant, mkdir fails" cannot happen.** An account that already holds a
grant has its whitelist *inside* `$allow_dir`, so the directory necessarily
exists and `[ ! -d "$allow_dir" ]` never fires. Testing it would mean
constructing a state the system cannot be in, and a test that green-lights an
impossible path is worse than no test.

The reachable shape of the same concern is covered instead: a host that already
carries the **shared helper** but has no whitelist directory — the state left by
revoking the last account and then removing the empty directory by hand. There,
`mkdir` genuinely is attempted with a pre-existing artifact at risk:

| case | assertion | result |
|------|-----------|--------|
| old helper present, no directory, `install -d` fails | helper hash identical to before, content still the OLD version | PASS |
| clean host, `install -d` fails | no helper, no whitelist, no rule, **no directory** | PASS |
| both | `TMPDIR` empty — no staged file, no rollback copy left | PASS |

The stub for this had to be written carefully to be worth anything. A stub that
merely exits non-zero leaves no directory behind, so the clean-host assertion
would pass with or without the fix. It now does what coreutils does — creates the
directory, then fails — and with that, the clean-host case **fails against the
`created_dir=0` reset** and passes without it. That is the regression evidence
for this change.

### The mechanical guard (§3, last paragraph)

Agreed, and built. It is the most useful thing in this review: the question this
review raised is one an eye-audit has to re-answer every time the function grows
a step, and it can be answered once by a machine.

`tx_guard_scan` extracts the install phase and reports any `return 1` without a
`_grant_rollback` within the enclosing failure block. Two assertions, not one:

- against `deploy.sh` — no offenders;
- against a deliberately broken sample carrying a bare `warn; return 1` — the
  guard must report it. A guard that cannot fail proves nothing, and this one had
  to be pointed at something broken before I would believe it.

## Remaining risk

Unchanged from REV-009 and worth restating rather than quietly dropping:

- the sandbox fails `install` and `visudo` synthetically; a real failure of either
  on a real host is still not exercised;
- a **crash** between two steps is still uncovered. The rollback runs on failure
  paths, not from an EXIT trap, so `kill -9` mid-install leaves a mixed state.
  That needs the staged rename-commit design, and it remains available as its own
  change if you want it.

The guard added here narrows the first risk in the direction that matters: it
cannot catch a failure mode nobody thought of, but it can stop a future step from
being added without a rollback, which is how this class of hole appears.
