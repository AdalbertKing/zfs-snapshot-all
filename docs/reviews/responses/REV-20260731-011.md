## F1 (§2) — `mkdir allow_dir` does not roll back — DISPUTED on the facts, ACCEPTED one layer down

### Analysis

The call is there, and it was there before the commits under review.

```bash
    if [ ! -d "$allow_dir" ]; then
        created_dir=1
        install -o root -g root -m 0755 -d "$allow_dir" || {
            created_dir=0; _grant_rollback
            warn "could not create $allow_dir -- no quiesce grant was created for $account"; return 1
        }
    fi
```

That is `git show 7dc4a98:deploy.sh` — the base this review compares against. The
line dates from the REV-008 F2 transaction work in `763767b` and `ad5e745` did
not touch it, which is exactly why I think it read as missing: it is not in the
diff. A diff-only read of `ad5e745` shows `did_helper=1` appearing, then the next
hunk starts after the `mkdir` block, so the block looks like unguarded
pre-existing code.

So §2's five-step consequence does not occur. Step 4, "funkcja wychodzi bez
przywrócenia starego helpera", is not reachable: `did_helper=1` is already set,
`pre_helper=1` for an existing helper, and `_grant_rollback` restores it. The
backup directory and both staged temp files are removed on the same path.

**But the review is right that something survives, one layer below where it
looked.** `created_dir=0` was reset *before* calling the rollback, to say "the
directory was not created, do not remove it". That reasoning is wrong for the
realistic failure. `install -d` creates the directory and only *then* applies
owner and mode, so it can fail having already made it. With the flag reset, that
empty root-owned directory is the one residue of a run that reports creating
nothing — which is the same class of defect §2 describes, just smaller and at a
different step.

### Implemented change

The reset is gone. `created_dir` stays 1, and the rollback attempts the `rmdir`.

That is safe without further conditions, which is why it is the whole fix:
`rmdir` refuses a non-empty directory, and this branch only runs when the
directory did not exist beforehand, so there is nothing of another peer's inside
it to lose. If `install -d` failed without creating anything, the `rmdir` fails
silently and nothing changes.

### Tests

§3's two cases, with the honest note that the first one as literally worded is
not reachable:

**"existing grant, mkdir fails" cannot happen.** An account that already holds a
grant has its whitelist *inside* `$allow_dir`, so the directory necessarily
exists and `[ ! -d "$allow_dir" ]` never fires. Testing it would mean
constructing a state the system cannot be in, and a test that green-lights an
impossible path is worse than no test.

The reachable shape of the same concern is covered instead: a host that already
carries the **shared helper** but has no whitelist directory — the state left by
revoking the last account and then removing the empty directory by hand. There,
`mkdir` genuinely is attempted with a pre-existing artifact at risk:

| case | assertion | result |
|------|-----------|--------|
| old helper present, no directory, `install -d` fails | helper hash identical to before, content still the OLD version | PASS |
| clean host, `install -d` fails | no helper, no whitelist, no rule, **no directory** | PASS |
| both | `TMPDIR` empty — no staged file, no rollback copy left | PASS |

The stub for this had to be written carefully to be worth anything. A stub that
merely exits non-zero leaves no directory behind, so the clean-host assertion
would pass with or without the fix. It now does what coreutils does — creates the
directory, then fails — and with that, the clean-host case **fails against the
`created_dir=0` reset** and passes without it. That is the regression evidence
for this change.

### The mechanical guard (§3, last paragraph)

Agreed, and built. It is the most useful thing in this review: the question this
review raised is one an eye-audit has to re-answer every time the function grows
a step, and it can be answered once by a machine.

`tx_guard_scan` extracts the install phase and reports any `return 1` without a
`_grant_rollback` within the enclosing failure block. Two assertions, not one:

- against `deploy.sh` — no offenders;
- against a deliberately broken sample carrying a bare `warn; return 1` — the
  guard must report it. A guard that cannot fail proves nothing, and this one had
  to be pointed at something broken before I would believe it.

## Follow-up — crash-safe commit, built at the owner's request

The remaining risk below named a crash mid-install as uncovered and offered the
staged rename-commit as its own change. The owner asked for it, so it is in this
delivery. This is the design REV-20260731-009 §3 called the cleaner alternative.

### What was actually wrong

Everything up to here handles a step that **fails**, because a failure returns
and the rollback runs. It says nothing about a step that never returns. `kill -9`,
the OOM killer, or the power going out ran no rollback at all and left whatever
the half-finished `install` had written — and `install` writes in place, so what
it leaves can be a truncated privileged binary or half a sudoers rule.

### Two properties, no recovery replay

**1. Nothing is written in place.** Each new file is staged as `<dest>.zqg-new`
in its own destination directory and then renamed over the destination.
`rename(2)` is atomic, so every instant a crash can land on finds each
destination holding the whole old file or the whole new one. Staging beside the
destination rather than in `/tmp` is what makes it a rename instead of a
cross-filesystem copy — `mv` across filesystems is a copy, and a copy is exactly
what we are trying to stop doing.

Everything that can fail for an ordinary reason — disk space, permissions, a
missing source, an invalid rule — now happens during staging, before any
destination has changed. The commit phase is three renames and nothing else.

**2. The commit order makes every intermediate state safe:** whitelist, then
helper, then rule.

- The **rule is last** because it is the switch. Until it lands nothing is
  granted at all, so a crash before it leaves a host with no new grant.
- The **whitelist is first** because it is a *restriction*. A crash between it
  and the helper leaves the narrower of the two lists in force. This is the
  direction worth choosing deliberately: an old whitelist may be *wider* than the
  new one, and widening privilege is a real failure while narrowing is not.
- Committing the whitelist before the helper means an old helper may briefly read
  a new whitelist. That is safe because the helper fails **closed** on a
  whitelist it cannot parse — it refuses rather than allows. The assumption is
  that the format stays readable by the previous helper; it is one dataset per
  line plus comments today, and the code says that if it ever gains syntax this
  ordering has to be revisited.

**Recovery is "run it again".** Staged and preserved files left by an interrupted
run are swept, not replayed: this function rewrites all three destinations
anyway, so replaying a half-finished intent would be guessing at which half was
wanted. The next run reports what it found rather than cleaning up silently.

### A detail that decides whether this is safe at all

`/etc/sudoers.d` is **read by sudo**. Staging a rule inside it would be reckless
if sudo parsed everything there — but sudoers.d ignores any file whose name
contains a `.` or ends in `~`. That is why the staged and preserved names carry a
dot, and it is asserted by a test rather than trusted.

The same rule cuts the other way and I checked it: an account name containing a
dot would produce a **final** rule name that sudo silently ignores, i.e. a grant
that appears installed and grants nothing. `pc_is_account` rejects every character
outside `[a-z0-9_-]`, so it cannot happen. That is now written down where the
staging is, because it is load-bearing and was previously accidental.

Since the whole design rests on it, I verified it against a real `sudo` rather
than against the documentation — in an isolated tree, never in the live
`/etc/sudoers.d`, because if the assumption were wrong the test itself would
break `sudo` for every user on the host including root:

```
pve1, visudo 1.9.5p2, @includedir into a throwaway directory
  garbage in <name>.zqg-new   ->  visudo -cf PASSES   (ignored)
  garbage in <name>           ->  visudo -cf FAILS    (read)
```

The second line is the one that makes the first mean anything: without it, a pass
could just as easily mean the include directory was never consulted. Recorded as
a re-check in `deps.conf` for whenever a host's sudo is upgraded — if that
behaviour ever flips, a staged rule becomes live sudoers the moment it is
written.

### Rollback and the shared-directory check

In-run rollback is now a rename too — the preserved file is a **hard link** to the
original inode, so it carries content, owner, mode and xattrs by identity rather
than by a copy that could lose one, and restoring it is atomic.

One consequence had to be chased: `.zqg-*` files sitting in `/etc/zfs-quiesce-allow`
would have made "does any account still hold a grant?" answer yes, which is how
the rollback decides whether it may remove a shared helper. A crashed run would
have looked like a peer that must not be disturbed. Both places that ask that
question now go through `quiesce_allow_dir_empty()`, which ignores staging
artifacts.

## Remaining risk

- The sandbox fails `install`, `visudo` and `mv` synthetically; a real failure of
  any of them on a real host is still not exercised.
- `rename(2)` is atomic but not by itself **durable**. Against `kill -9` and the
  OOM killer — the cases named — the kernel state is consistent and this is
  complete. Against sudden power loss the guarantee comes from the filesystem:
  ZFS is transactional and never exposes partial content, and ext4's default
  ordered mode flushes data before a rename-over-existing-file. I did not add a
  `sync`, because a global flush is a heavy side effect to pay on every run for a
  window this small — but that is a judgement, not a proof, and it is the one
  place where "crash-safe" leans on the filesystem rather than on this code.
- A crash between the whitelist and helper commits leaves an old helper reading a
  new whitelist. Safe today, and safe only while the whitelist format stays
  backward-compatible.

The mechanical guard from §3 covers the other direction: it cannot catch a
failure mode nobody thought of, but it stops a future step from being added
without a rollback, which is how this class of hole appears.
