# Response to REV-20260801-026

Delivery: direct to `main`, per the owner-approved exception. Commit `5ff1b0b`
(and `eb26443` immediately before it, which is the same defect family found
independently on the same host).

## F1 — capabilities must come from the jobs — ACCEPTED, IMPLEMENTED

Accepted. The fixed set was wrong in **both** directions, and pve2 showed each:

- **too weak** — a receive target needs `receive,create,rollback,canmount` and
  none of them were probed. An account with the five would pass preflight and
  fail at 04:00 on `cannot receive: permission denied`;
- **too strong** — a `[prune:]` carrying `prune = no` is a monitor carrier. It
  destroys nothing and needs nothing, and it was reported as a gap. That is not
  merely noise: it sends the operator to widen a grant for a job that only
  reads, which is the opposite of what this tool is for.

### Implemented change

The requirement is derived from the **rendered block** — the command lines that
will actually run — rather than from a section type. That is the only
description of the work which cannot drift from the work, because it *is* the
work. Per line:

| job | required |
|---|---|
| send source | `snapshot,hold,release`, plus `send,bookmark` when there is a destination |
| local destination / pull base | `receive,create,mount,canmount,rollback` |
| prune | `destroy,hold,release` |
| bookmark prune | `bookmark,destroy` |
| monitor | nothing — it reads |

A snapshot-only source is deliberately **not** asked for `send`/`bookmark`. Over-
asking is how the too-strong half happened, and it is worth guarding against
explicitly rather than treating the fix as "ask for more".

The check moved to **after** the render. Until the jobs are rendered there are
no jobs to ask about, and asking a section type instead is exactly the
substitution the review is objecting to.

## F2 — `[prune-bookmarks:]` — ACCEPTED, IMPLEMENTED

Accepted, and the review is right that the test I wrote pinning the exclusion
made it worse: it recorded an accident as a decision. Local bookmark scopes are
now checked for `bookmark,destroy`.

The second half — remote scopes — is handled by the same rule as everywhere
else, and it is not special-cased for bookmarks: a scope is remote if
`snapsend.sh`'s own `REMOTE` parsing would call it remote (`host:dataset`, or
bare `user@host` for sync mode). A remote scope produces **no local
requirement**, because what it needs is ssh and a grant on the far side — a
different question, which this verb does not answer and should not pretend to.

## F3 — no placeholder — ACCEPTED, IMPLEMENTED

The refusal now prints the exact derived list:

```
  deploy.sh --backup-user=zfsbackup --datasets="tank/a tank/backups/here"
```

Not `"..."`. The tool had just finished deriving that set; asking the
administrator to rebuild it by hand from section semantics was asking them to
redo the work the preflight exists to do.

I have **not** gone as far as the review's preferred option (let the migration
provision the delegation after one confirmation). That crosses the
`zfs-backup.sh` / `deploy.sh` boundary which REV-020 F1 established and REV-022
re-endorsed in its "Accepted progress". If the owner and reviewer want that
boundary moved, it should be moved deliberately and once, not as a side effect
of an ergonomics fix.

## A defect in the change itself, found by running it on real data

`qcap_add_list` split its comma list with `printf '%s'` — no trailing newline —
so `while read` never ran its body for the **last** element. A two-element list
contributed one dataset and a **one-element list contributed nothing at all**.

It is worth naming how that surfaced, because it is invisible by inspection: a
missing row in the capability table looks exactly like a dataset that already
has the delegation it needs. Nothing fails, nothing warns, the preflight just
says fewer things. It was caught by feeding the function a realistic rendered
block and reading the table out loud against what the block obviously required.

## Live validation, and a real gap it found

Run against the actual account blocks now installed on both migrated hosts:

**metropolis pve1** — six datasets, all `destroy,hold,release,snapshot`, all
satisfied. Correctly **not** asked for `send`/`bookmark`: every job there is a
local snapshot, there is no destination.

**metropolis pve2** — eight rows, seven satisfied, and one genuine gap:

```
[BRAK] rpool    bookmark,destroy
```

The config carries `[prune-bookmarks:rpool,hdd/vm-disks]` with `recursive = yes`,
and the account is delegated on `rpool/data` and `rpool/ROOT/pve-1` but not on
`rpool` itself. The job returns 0 today, because bookmarks exist only on the two
datasets that are actually sent — both delegated. It is latent, not current: the
first bookmark on any other `rpool` child makes that prune fail at 04:30.

I have deliberately **not** closed it, because both available fixes are the
owner's call, not mine:

- grant on `rpool` — but `deploy.sh` grants the full eleven-verb set, so this
  hands the account `destroy` over the whole root pool for the sake of a
  bookmark prune;
- narrow the config's scope to the datasets that actually carry bookmarks —
  tighter, and a change to what the config says.

Recorded in `docs/PROJECT_STATUS.md` under owner decisions.

## Remaining risk

`job_positionals` distinguishes a flag's value from a positional argument using
an explicit list of value-taking flags. If `gen-cron.sh` ever emits a new
value-taking flag that is not in that list, its value would be read as a dataset
name — which fails closed (a nonexistent dataset has no delegation, so the
preflight refuses and names it) but is confusing rather than clear. The list is
stated in one place with a comment saying why, and the `ssh-flag-parity`
contract already governs the flags most likely to change.
