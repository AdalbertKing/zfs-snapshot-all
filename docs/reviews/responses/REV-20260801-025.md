## F1 — one check precedes several per-pool snapshot commands — ACCEPTED, IMPLEMENTED (late)

### Analysis

Accepted, and my reasoning for deferring it was wrong in a way worth naming. In
the REV-024 response I argued that one check immediately before the snapshot
loop was enough "in spirit and in practice", because the loop is sub-second and
adding a status probe per pool costs IPC *inside* the window.

The cost argument is real. The conclusion does not follow from it. "Usually
sub-second" is not a property of the code, it is an observation about the hosts
I happened to measure; a pool that is busy, resilvering, or simply large makes
the first `zfs snapshot` slow, and nothing in the design bounds it. The comment
in the code even asserted the thing that was not proven — *"every guest stays
frozen until the last group is done"*.

### Implemented change

Both paths re-verify immediately before **each** pool: every VM owned by the run
still reports `frozen=yes`, and the elapsed window is recomputed from the first
successful freeze. Either failing refuses before that pool is touched.

Pools already snapshotted keep their snapshots — they were taken while the
freeze demonstrably held, and destroying good backups because a later pool
failed would be the same mistake in the other direction.

The remote check became a function (`boundary_ok`) precisely so its two callers
cannot drift; the local one takes a context label so the log says which pool it
is about.
