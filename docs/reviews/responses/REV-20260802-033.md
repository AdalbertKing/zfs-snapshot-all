**The seam is smaller than the review assumes, and the reason is worth stating
precisely rather than as "make the argument optional".** The package *format*
already tolerates an absent scope:

- `PEER_CONF_DATASETS` is **not** in the required-key list;
- its validation loop is `for ds in ${PC[PEER_CONF_DATASETS]:-}`;
- `--join`'s grant loop is `for ds in $PEER_CONF_DATASETS`, which on an empty
  list grants nothing and does not fail;
- `--draft-config` already handles an empty manifest list by listing **every**
  candidate unfiltered.

So the data model is ready. What is genuinely new is the **second act**: a
finalize step on the source that grants from the edited file. That is the design
work; the flag is bookkeeping.

**One package-format change is unavoidable.** Sync supplies no target, but
`PEER_CONF_TARGET` is currently required and validated as a dataset name. Either
target becomes optional-when-sync, or a new `PEER_CONF_MODE=backup|sync` key is
added. I propose **both**: an explicit mode, and target required only in backup
mode. Because the key set is fixed and unknown keys are a hard error, a package
carrying `PEER_CONF_MODE` fails on an older peer with a clear message rather
than silently — which is the correct failure and should be documented, not
worked around.

## 3. Minimal design

**New commands: two. New states: one. New parsers: one, small. New files: one.**

```
pve1:  zfs-backup add-client pve2 --mode=backup --lan=<addr> [--target=<or default>]
       zfs-backup add-client pve2 --mode=sync   --lan=<addr>          (no target)
         -> keyscan + pin (unchanged) -> package WITHOUT scope

pve2:  deploy.sh --join=<package>                    (existing command, one behaviour removed)
         -> account + key, ZERO zfs permissions
         -> generates the scope file from every pool, opens $VISUAL/$EDITOR
       deploy.sh --commit-scope[=FILE]               (NEW)
         -> parse fail-closed -> diff against what is granted now -> grant/revoke

pve1:  zfs-backup activate pve2                      (NEW: fetch + existing seed/verify/activate)
         -> fetch the file over the relationship key, check its digest
         -> dry-run -> seed -> verify -> install cron
```

Avoided duplicate representations, explicitly:

- **no second scope manifest.** `PEER_SAVED_DATASETS` in the peer manifest stops
  being an independent list and becomes a **derived cache** of what the scope
  file says — or is dropped in favour of reading the file. Either way there is
  one editable list.
- **the collector's cron config is generated, not authored.** It is not a second
  representation of the choice any more than a binary is a second representation
  of source. A second *editable* dataset list would be; there will not be one.
- **the digest is not a representation.** It is a statement that the
  representation is one (T3).

## 4. One-file lifecycle

| Stage | Host | What happens |
|---|---|---|
| create | pve2 | `--join` inventories **every pool**; active roots default to the first level below each pool, excluding pool roots and known system branches (`rpool`, `rpool/ROOT`, `rpool/ROOT/pve-1`); the full `zfs list` follows as comments, plus a census of snapshot prefixes present on this host (T5) |
| edit | pve2 | `$VISUAL`/`$EDITOR`, `crontab -e` style; repeated freely — the file is inert until finalized (U2) |
| finalize | pve2 | `--commit-scope`: parse fail-closed → show the diff **against what is granted now** → `zfs allow` additions, `zfs unallow` removals **limited to what this relationship granted** (U3) → record the file's digest |
| transfer | pve2 → pve1 | byte-for-byte over the relationship key; no rewriting in transit (T2) |
| validate | pve1 | authoritative parse; digest must equal the one the finalize recorded, else refuse: *"pve2 granted from a different version of this file"* |
| use | pve1 | the same parsed scope drives the generated `[dataset:]` sections and the `[prune:]` ladder |
| re-edit | pve2 | any later edit repeats finalize; the collector refuses to run until the digests match again |

### Grammar

The file uses the project's existing INI shape so an administrator sees one
format, with a **much smaller key set** and no job semantics:

```ini
[dataset:rpool/data]
include_parent   = no
include_children = yes
exclude      = rpool/data/vm-999-disk-0
exclude_tree = rpool/data/scratch
```

**Parser reuse — what can and cannot be reused, and why.**

- **Reusable:** `deploy.sh`'s untrusted-input validators (`pc_is_dataset` above
  all) and its whole discipline — fixed key set, unknown key is fatal, values
  are data. This file arrives from another host and gets exactly the treatment
  `peer.conf` already gets.
- **Not reusable:** `gen-cron.sh`'s parser. Not because the grammar differs — it
  does not — but because its semantics do: it *requires* `use_template`
  referencing an existing `[template:]`, and it carries schedule, retention,
  `-K`/`-k` flags and target. Pointing it at the scope file would fail on the
  first section, and making it tolerate scope-only sections would drag collector
  policy onto the source. That is the U4 boundary.
- Therefore: a small dedicated reader, ~1 section kind and 4 keys, built from
  the existing validators.

Rejected by the grammar, fail-closed, returning the operator to the same file:
option-like names, `.`/`..` segments, control characters, duplicate or ambiguous
sections, unknown keys, and an `exclude`/`exclude_tree` that does not lie under
an included root.

**Exclusions are explicit paths, not regexes** (U5). Today's `-X` is an
unanchored regex — `-X 'lxc'` also removes `rpool/data/mylxcbackup`. Fine for an
expert, a mine for the audience this feature exists for. `snapsend -X` is
unchanged for expert use.

## 5. Online bootstrap

**First, a correction to my own earlier claim, which also narrows this finding.**
I had written that pairing is offline. It is not: `--pair` runs `ssh-keyscan`
against the peer, pins what comes back, and dies when the host is unreachable or
when the name resolves to more than one address. **The network is already
required.** Only the package *transfer* is manual.

**Owner fact that settles the rest:** the administrator running `add-client` on
pve1 has SSH access to pve2. It is the same person who would otherwise walk over
and run `--join`.

### Design (chosen)

- The package is delivered **using the administrator's own credentials**, over
  **the host key we already pinned** (`-o UserKnownHostsFile=<our pin> -o
  StrictHostKeyChecking=yes`). No prompt, no weakening, and the same key the
  relationship will use afterwards. The trust is not weaker than the pairing —
  it *is* the pairing's trust.
- The scope file **returns over the relationship key**, which exists by then.
- **Nothing listens.** No daemon, no token, no new dependency, no replay window,
  no transient secret to store or expire. There is nothing to replay: the
  package carries the collector's **public** key, role, mode, target, account
  name and label — no secret. What matters is integrity, and the human who has
  access to both machines is the integrity.
- Manual transfer remains, using the identical validation and commit path.

### Optional, opt-in: remote `--join` and the editor over `ssh -t` (U10)

My first answer was against this, and it was a reflex from a state we had
already changed. In today's code `--join` grants, so running it remotely would
be the collector provisioning the source. **After U2 it does not grant** — it
creates the account, installs the key, and ends with zero ZFS permissions. The
principle survives untouched, because the protected act is the grant.

Under one explicit flag (`--join-remotely`, name open): run `--join` on pve2, and
open the scope editor there over `ssh -t` so the whole flow is drivable from one
terminal. We are not moving authority, only the keyboard.

Three conditions:

1. **finalize stays local, always** — no flag changes that;
2. it rides the pinned host key; no `accept-new`, no exception;
3. the peer's manifest records that the entry was created **remotely**, from
   which collector and by whose session.

The flag *is* the declaration that the network is trusted. We do not try to
detect that: "trusted network" is not a measurable property and any test would
be theatre.

## 6. LAN-to-WAN flows

Identity is the peer's **host key under a stable alias**, and the generated jobs
already pin it that way. Changing address or port therefore does not invalidate
the pin. Every variant reduces to one question: *does `host:port` change?*

| Case | `host:port` | Action |
|---|---|---|
| routed OpenVPN, same address | unchanged | **re-verify only**, no mutation |
| Tailscale / new private endpoint | changed | one field; alias, key, target, bookmarks, job identity all survive |
| public IP + forwarded port | changed (host **and** port) | same as above |

Relocation always begins the same way:

```
verify current endpoint
  -> reachable, pinned fingerprint matches, dry-run says INCREMENTAL for every dataset
       -> change nothing
  -> unreachable
       -> try the other known endpoints
       -> only then ask for a replacement, pin it to the SAME alias, verify before activation
```

**Source-IP restrictions.** The peer's `authorized_keys` entry is plain — **no
`from=`** — so key auth does not care where the collector connects from. What
can bite is outside our code: a firewall on the peer limiting SSH to the LAN,
`sshd` `AllowUsers`/`Match Address`, fail2ban, and in the port-forward case the
router itself. All present as "cannot connect", not "permission denied", and we
already discriminate those (exit 255).

**The pinned key earns its keep twice here.** With a forwarded port the endpoint
names a *router*, not a machine. If the forward ever lands on a different host,
the key mismatches and the job **fails instead of backing up the wrong
machine**. This is why `accept-new` stays forbidden on this path.

**Catch-up contract.** A real final incremental over the still-working route
before the move (`final-catchup` exists), then re-verify and one real incremental
over the production route before cron. **Confirmed defect:** the messages name
the **source** as the machine being moved; it is the **collector**.

## 7. Failure and retry table

| Situation | Behaviour |
|---|---|
| editor interrupted / file unchanged | nothing granted, nothing transferred; the file stays; re-run the editor |
| malformed or ambiguous scope file | finalize refuses, names line and reason, **reopens the same file**; no partial grant |
| exclusion outside every included root | refused as malformed (typo caught at finalize, not after the first backup) |
| finalize interrupted mid-grant | grants are per dataset and idempotent; re-running converges. The manifest records what was granted, so a partial state is visible rather than guessed |
| revoke blocked by an in-flight hold | **refuse** while a `zfssnapall_inflight` hold from this relationship exists, or release it first — never `zfs unallow` and leave a hold nobody but root can lift (T4) |
| collector cannot fetch the file | relationship unchanged; retry. Scope already granted on the peer is not a problem: nothing consumes it until the collector validates it |
| digest mismatch between file and grant | refuse: the peer granted from a different version. Re-run finalize on the peer |
| dry-run fails for any dataset | no cron installed, config file untouched (existing `activate-client` behaviour) |
| sync: destination pool missing | refuse **before any receive**; the tool creates datasets, never pools |
| sync: destination exists, `written@head > 0` | refuse, with the number ("3.2 GB written since the common snapshot") |
| sync: destination is a live guest disk | **unconditional refusal**, no override |
| sync: peer is a member of the same PVE cluster | refused **at enrolment** (U8); pvesr already owns that job and we would be a second writer |
| endpoint mismatch after relocation | try known endpoints, then ask; never mutate a working endpoint |
| post-relocation plan says FULL | stop and report. A full send after a move is an operator decision, not a side effect — the existing `--allow-stale-catchup` shape is the model |

# Addendum, 2026-08-02 evening — owner decisions and a change of ground

Written after the owner worked through this review with me. Everything below is
**decided**, not proposed; the full record with the reasoning is in
`docs/discussions/ENROLMENT-AGREED-2026-08-02.md` (U1–U11).

## The three questions in §9 are answered

1. **Flag name: `--drive-peer`.** `--trusted-network` and its relatives were
   rejected for naming a property nobody can verify, and for reading as an
   assurance. `--drive-peer` names what happens: this host runs the peer's
   steps.
2. **All three reserved prefixes drop to `:2`** on the collector's own copies —
   `__replicate_`, `__migration__` and `vzdump`. (U6a had kept `__migration__`
   absolute; the owner leveled them.)
3. **Existing clients are migrated only on an explicit `--force`.** Metropolis
   keeps working untouched.

## The ground under §8 has changed: there is now a single crontab writer

Between this response and this addendum, the owner directed a refactor that the
review did not ask for and that changes how its slices land.

**Before:** six crontab write sites in three programs — four hand-rolled
`crontab -l | ... | crontab -` in `deploy.sh`, `gen-cron.sh`'s line-by-line
rebuild, `zfs-backup.sh`'s own reader/restorer/awk — plus **two lines loose in
root's crontab on every host**, indistinguishable from something a human typed.

**Now:** one writer, `lib-cron.sh`, whose only entry point takes the **block
name as an argument**, so writing outside your own block is not expressible.
Two requesters: `deploy.sh` owns `zfs-backup-host`, the job layer owns
`zfs-backup-managed`. Deployed on all four hosts; **zero loose job lines**
anywhere; job counts unchanged (root 3→3 everywhere, accounts 16/12/28/8
unchanged).

Why it was done first, and why it matters to this review: the enrolment adds
**new cron install paths** (activation, teardown of a relation). Under the old
model each would have been a fourth, fifth and sixth writer, and rewriting them
afterwards would mean touching production crontabs again. They will now be
requesters.

Two properties worth the reviewer's attention, because both are behaviour and
not tidying:

- **adoption preserves content.** A hand-tuned schedule keeps its time; only the
  line's location changes. `deploy.sh` promises "already present, leaving it
  alone", and the first thing this refactor did on a live host must not be to
  undo an operator's edit. The updater line is the single deliberate exception,
  normalised because three historical spellings had to collapse to one;
- **every write is read back.** `rc=0` from `crontab(1)` was never evidence, and
  the restore path — the one taken when something has already gone wrong — could
  previously claim success without looking.

`test/cron/run.sh`, 75 checks, stubs `crontab(1)` including a stub that accepts
a write and stores something else.

## One finding of my own, offered for the reviewer's verdict

The config layer has the same shape of problem one level up, and the owner has
agreed to fix it **inside** the enrolment work rather than separately.

`jobs.<host>.v4.conf` has **three machine writers plus the operator** —
`zfs-backup.sh`, `cron2conf.sh`, and a human, who is a *legitimate* writer here
unlike with the crontab. This review adds a fourth (the scope file). So "one
writer" is the wrong goal; **ownership per section** is:

- generated sections carry a marker naming their owner and client, so
  `remove-client` removes its own and never a hand-written section that happens
  to name the same dataset. Today `remove_managed_sections` matches by dataset
  name alone — the same "no owner means guessing" shape the loose crontab lines
  had;
- plus the digest already agreed as T3, so a config cannot drift from what was
  installed and granted.

Stated plainly for balance: the config is **better protected today than the
crontab was** before this refactor (`ensure_cron_config`,
`assert_cron_config_matches_installed`, atomic replace with both-sided restore,
two diffs before every change, and version control in a private repo). This is
not an emergency; it is a decision made at the moment the fourth writer appears.

## What I am starting on

plus tests, no production path touched. Everything else depends on it (grants on
the source, config generation on the collector, the sync preflight), and it
reuses `deploy.sh`'s existing untrusted-input validators rather than growing new

The implementer's position on the remaining slices is unchanged from §8, except
that slices 6–8 now build on `lib-cron.sh` instead of adding cron writers.
