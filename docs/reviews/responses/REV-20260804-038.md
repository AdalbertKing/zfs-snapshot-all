# Response to REV-20260804-038

## F1 — ACCEPTED

### Analysis

Confirmed exactly as described, and confirmed by direct observation before
this review even existed: REV-037's own response file already documents the
zero-byte manifest this finding is about (found live, Gate B, the missing
`PEER_CONF_MODE` local). The review's diagnosis is correct in every detail:
`cat > "$mpath"` and `chmod` were both unchecked, the write went straight to
the final path with no temp-file/rename, and there was no read-back
comparison before `do_join()` printed success. Persistent account/key
mutations happen before this write, so a failed manifest commit really can
leave a real, trusted account with no durable relationship record -- exactly
what happened live.

### Planned or implemented change

`do_join()`'s manifest write is now a five-stage commit, matching the
review's required outcome:

1. `mktemp "${mpath}.XXXXXX"` in `$PEER_STATE_DIR` (same directory as the
   final path -- `mv` across filesystems is not atomic, so this is required,
   not incidental).
2. Render the manifest body into that temp file; `cat`'s exit status is
   checked.
3. `chmod 0600` the temp file; checked.
4. Read back the temp file and compare every field (`role`, `as`, `mode`,
   `target`, `account`, `fingerprint`, `remote`) against the values this
   `do_join()` call actually computed -- refuses to publish before this
   passes.
5. `mv -f` the temp file onto the final path (atomic rename, same
   filesystem); checked.
6. Read back the FINAL path and run the identical field comparison again --
   a different failure class (rename landing something else) than step 4.

Only after step 6 passes does `do_join()` print `Join zakonczony`. Every
failure point (steps 1, 2, 3, 4, 5, 6) returns non-zero via `die`, names the
account and authorized-key path that may already exist, states plainly that
re-running `--join` with the same package is safe and repairs it (the
account/key steps are already idempotent), and explicitly says not to delete
the account or key by hand since they may predate the failed attempt. No
step deletes an existing account or key -- matches "the safe minimum is
fail-closed, accurately report the partial state" exactly.

The read-back comparison is its own function, `verify_join_manifest()`,
taking every expected value as an explicit argument (not the caller's
locals via bash's dynamic scoping) specifically so it is independently
testable -- same reasoning, same extraction technique, as
`remote_scope_stage()` for REV-037 F1.

### Evidence

New suite `test/joinmanifest/run.sh`, **7/7**, registered in
`test/deps.conf`. Against real files, no ssh/zfs/useradd involved:

- a correctly rendered manifest verifies exactly against the values it was

- a remote-origin manifest (`PEER_JOIN_REMOTE=yes` and its three sibling
  fields) verifies including that field;
- **the live incident's own shape** -- a zero-byte file -- is refused, not

  catches it because it compares actual values, not merely "did the file
  get created");
- a single wrong field (fingerprint, then separately account) is refused,
  proving the check compares every field rather than short-circuiting on
  the first match;
- a missing file entirely is refused;
- a legacy-shaped manifest (no `PEER_JOIN_REMOTE` field, `want_remote=""`)
  still verifies -- absence is the expected legacy shape, not a mismatch.

Confirmed the acceptance criterion "a regression test fails against the
reviewed... implementation" in the same sense REV-037's own tests were
confirmed: `verify_join_manifest()` did not exist in the reviewed tree at
all (the reviewed code had no read-back step of any kind), so this suite's
own extraction anchor would not have matched it.

### Not tested here, and why

`do_join()`'s own render/write/chmod/rename sequence around
`verify_join_manifest()` -- i.e., proving the *account creation* and *the
five-stage commit* work together end to end, and that a forced failure at
each of the six numbered stages produces the exact behavior specified --
still needs root (the account/key mutations that precede the manifest write
require it) and a real filesystem for `mktemp`/`mv` semantics. This is the
same standing gap as every other `do_join()`/`do_pair()` real action in this
project (see `test/join/run.sh`'s own header) -- not new to this finding,
and not silently assumed away: it is exactly what the live rerun below
proves instead.

### Remaining risk

`do_commit_scope()` (a different function, out of this review's stated
scope) has the identical non-atomic-write shape for its own
`PEER_JOIN_GRANTED_DATASETS` update (`grep ... > "${mpath}.tmp"; mv
"${mpath}.tmp" "$mpath"`, unchecked, no read-back). Noted here rather than
fixed, since REV-038 explicitly scopes itself to `do_join()`'s persistence
boundary -- worth its own finding if the reviewer wants it addressed,
rather than folded silently into this one.
