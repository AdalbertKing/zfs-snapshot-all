## ACCEPTED, IMPLEMENTED — all five required behaviours

The review is right, and its framing is the part I had not reached on my own. I
had diagnosed this as an **ordering** problem: freeze the VMs last and the
window shrinks. The review's point is stronger and it is the one that makes the
fix correct rather than merely better — *a successful `fsfreeze-freeze` is not
evidence of anything by the time `zfs snapshot` runs*. Ordering makes the window
short. It does not make it **true**. Only asking again does.

| # | required | implemented |
|---|---|---|
| 1 | slow, non-freezing work first | `quiesce_freeze()` split into `quiesce_prepare` (flushes containers, decides, refuses — freezes no VM) and `quiesce_freeze_pending` |
| 2 | freeze only immediately before the snapshot | `snapsend.sh` calls `quiesce_freeze_pending` after the whole prepare loop, with nothing left to do but snapshot |
| 3 | re-read `fsfreeze-status` before `zfs snapshot`, abort on not-frozen or unreadable | `quiesce_still_frozen`, called immediately before the snapshot loop |
| 4 | measure and log the duration; over the limit is a failure | `QUIESCE_MAX_WINDOW` (default 5 s), logged every run, refusal not warning |
| 5 | always thaw guests this run owns, on every refusal path | unchanged EXIT trap, and now structurally easier: pass 1, where most refusals live, holds no freeze at all |

### On the budget

5 seconds, against the ~10 s VSS limit the code documents. Deliberately tunable
via `QUIESCE_MAX_WINDOW`, and the reason is a limitation worth naming rather than
hiding: **several slow-to-freeze Windows guests in one job can exceed it
legitimately**, and that run will fail. That is the fail-closed direction and I
think it is right — a host in that position genuinely cannot promise all those
guests one consistent boundary — but it is a behaviour change that could bite a
configuration nobody has tried yet.

## What the live run found in my own fix

The first version (`be1cfe7`) started the clock before the freeze **call**. On
the real pve1 job that produced:

```
Quiesce: freeze window 5s (budget 5s), 1 VM(s) confirmed still frozen at the snapshot
```

Passing, by zero seconds. A perfectly healthy production job was one second from
failing.

`fsfreeze-freeze` on a Windows guest takes about **4 seconds to return**, and all
of it is VSS *preparing* to freeze — the guest is not frozen during it, and VSS's
own timer does not start until the freeze engages. Charging that preparation to
the window made the budget nearly unusable for exactly the guests it exists to
protect, and would have converted this fix into a nightly false alarm.

`d8bb52a` starts the clock at the **first successful freeze** — first, not last,
so a second guest's slow freeze is still charged to the first guest's window,
which is the truth about that guest.

Worth recording that this was found the same way as the original defect: by
reading the number the code printed on a live run. The budget check is only as
good as what it measures, and nothing in the suite could have told me that 5 was
measuring the wrong interval.

## Product-level note — AGREED, and now true on this path

The contract on the local `-q` path is machine-readable and binary: the run
either confirmed every VM still frozen at the snapshot boundary and inside
budget, or it exited non-zero and the cron line's `notify-fail.sh` fired. The
administrator does not have to infer anything from timestamps.

One line of the log is now an assertion rather than a breadcrumb:

```
Quiesce: freeze window 1s (budget 5s), 1 VM(s) confirmed still frozen at the snapshot
```

Both numbers and the confirmation are printed because the *absence* of that line
is itself information — and because the defect this review is about could only be
found, twice, by someone reading timestamps that nothing was asserting on.

## Remaining risk

The re-check asks the guest agent, and a guest agent is the same component that
was wrong in the first place: an agent can report `frozen` for a freeze VSS has
already released. That is precisely why the deadline exists alongside the
re-check rather than instead of it — but the two together are still bounded by
what the agent will admit. Nothing short of writing into the guest and reading it
back would close that, and that is well outside what a backup tool should do.

The remote (`snapget -q`) path implements its own copy of this logic in
`ZFS_REMOTE_QUIESCE_SCRIPT` and has **not** been changed here. It freezes,
snapshots and thaws inside one invocation with no container flush between the
freeze and the snapshot, so the specific 18-second shape cannot occur — but it
also does not re-check at the boundary and has no deadline. Same family, not
covered by this commit, and I would rather name it than let the two halves drift.
