## §2/F1 — stable relation identity — ACCEPTED, IMPLEMENTED

`HostKeyAlias` and every display/summary string now derive from `CLIENT_NAME`, never from
`label` (deploy.sh's `peer_label()`, address-derived). `label` still exists internally, but only
to locate deploy.sh's own manifest/key files and the physical target dataset path deploy.sh itself
already created under that name -- neither changes without deploy.sh re-pairing, which an endpoint
switch never triggers. `deploy.sh --draft-config` is now called ONLY during `seed` (always over
the LAN endpoint that was actually used to `--pair`) -- calling it again with a different address
would make deploy.sh treat it as an unrelated, unpaired peer (`peer_label()` differs by address).
Every later step reuses the already-fetched `PEER_SAVED_DATASETS`/`PEER_SAVED_TARGET` and connects
directly through whichever endpoint is currently active.

Live-verified on pve0/pve1: the generated cron line's `-O HostKeyAlias=zfs-client-zfsbktest` stayed
`zfs-client-zfsbktest` before and after switching `ACTIVE_ENDPOINT` from `lan` to `vpn` (simulated
with the same address, no second network path available to test with a genuinely different one --
see "Not fully proven" below).

## §3 — state machine — ACCEPTED, IMPLEMENTED

`pending_enroll -> seeding -> seed_complete -> endpoint_verified -> active`. New commands:
`seed` (real, non-dry-run transfer; the only step touching `deploy.sh --draft-config`),
`set-endpoint --lan=/--vpn=HOST[:PORT]` (records an endpoint, switches `ACTIVE_ENDPOINT`, resets
state to `seed_complete` so cron cannot silently keep running against an unverified new endpoint),
`verify-endpoint` (SSH + host-key + `snapget -n`, and specifically checks the output for
"full send" to confirm an incremental base already exists, not just "exit 0"). `activate-client`
now requires `endpoint_verified` (fail-closed otherwise) and unconditionally removes-then-re-adds
each managed dataset's `[dataset:]` section instead of skip-if-present -- proven live: after
`set-endpoint`, `activate-client` regenerated the section (gen-cron reported "no changes" only
because the simulated VPN address was identical to LAN; the removal+re-add itself ran regardless).

Not the reviewer's exact suggested grammar (`ready_for_seed`/`vpn_configured`/`vpn_verified` as
separate states) -- collapsed to one generic `endpoint_verified` gate that works identically for a
permanently-LAN-only client and a LAN-seed-then-VPN client, per the reviewer's own "I don't require
this exact grammar, I require equivalent gates."

## Real defects found during this session's live re-verification (not from the review)

- **Unquoted date fields**: every state-file write used
  `echo "FIELD=$(date '+%Y-%m-%d %H:%M:%S')"` -- the date's own space split the sourced line into
  an assignment plus a bare second "command" that bash tried to execute and failed with
  "command not found". Harmless functionally (no `set -e`, sourcing continued), but real, visible,
  spurious error output on every single client-conf read since `add-client`'s first version. Fixed
  with `printf` and explicit quoting; regression test added.
- `cmd_status` never sourced deploy.sh's peer manifest, so `PEER_SAVED_DATASETS` was always unset
  and `status NAME` printed `Zrodla: ?` unconditionally. Fixed.
