# Response to REV-20260731-013

Delivery: direct to `main`, per the owner-approved exception.

## F1 — the sweep re-arms a mixed grant — ACCEPTED

The finding is correct, the mechanism is exactly as described, and the sentence
that names the damage is the one I should have written myself: it moves the
widening out of the first run's commit path and into the next run's recovery
path.

The restore existed for a reason that was real but narrow. Once the rule is
parked as `.zqg-bak`, that file is the only copy of the previous grant, and the
sweep used to delete leftovers unconditionally — which would have turned an
interrupted update into permanent loss. I fixed that by renaming it back, and in
doing so answered "do not lose it" with "make it live again", which are not the
same requirement.

By the time the rule is parked, the interrupted run has already committed the new
whitelist and helper. Re-arming the old rule therefore activates it against
**those** — and if the recovering run then fails during staging or validation,
before it can suspend anything, the widened combination stays active with nothing
scheduled to clean it up.

## Implemented change

I took the second of the two models you offered: **finish the new transaction
while disabled**. The rule stays parked; nothing is re-armed until a coherent
rule is installed as the commit's last step.

The sweep now distinguishes three cases rather than two:

| state | action |
|---|---|
| `<dest>.zqg-new` present | remove — stale staging |
| `<dest>.zqg-bak` present, destination present | remove — the backup is spare |
| `<dest>.zqg-bak` present, destination **missing** | **leave parked**, and say so |

Nothing is lost by parking, which is what makes this simpler than the
rollback-first model: the file is still on disk under a name sudoers.d ignores,
and `install_quiesce_grant` rewrites all three destinations anyway, so the run
already produces a coherent state or none. `pre_rule` is computed after the
sweep, so a parked rule reads as "no rule exists" — commit step 0 is correctly
skipped, and the new rule goes in last.

The consequence is stated where an administrator will meet it:

> a previous grant run for X was interrupted mid-update: the grant is currently
> DISABLED and its previous content is parked at … It stays disabled until a run
> completes — re-arming it now would activate the old rule against the new
> whitelist. If this run fails, the account keeps no access at all.

That last sentence is the honest part. Your §Required behaviour says an
administrator is better served by a clear stop than by a silently activated mixed
state, and I agree — so the message says plainly that a failing rerun leaves the
account with nothing, rather than letting someone discover it.

## Tests

Both interruption points you named, each followed by a rerun forced to fail
before commit step 0 — once at **validation** (`visudo` rejects the staged rule)
and once during **staging** (the install of the staged rule fails):

| after crash at | assertion |
|---|---|
| whitelist committed | grant parked and not armed |
| whitelist committed | rerun failing at validation activates nothing |
| whitelist committed | rerun failing at staging activates nothing |
| whitelist committed | only a **completed** rerun arms, and with the new grant |
| whitelist + helper committed | the same four |

"Activates nothing" is asserted as the conjunction the boundary actually depends
on: no active dotless rule may coexist with the widened whitelist. And the
completed-rerun case is there so that "nothing is ever activated" cannot be
satisfied by a function that never activates anything.

Your read-only point is covered structurally rather than by provisioning a host:
every `_grant_sweep` reference in `deploy.sh` is inside `install_quiesce_grant`,
and `--check-only` refuses to combine with `--join` at all, so no audit path can
reach the sweep. Both facts are asserted.

```
bash test/quiescehelper/run.sh   PASS=98 FAIL=0   (88 + 10)
bash test/join/run.sh            PASS=42 FAIL=0
bash test/selfupdate/run.sh      PASS=28 FAIL=0 SKIP=7
./test/impact.sh --verify        graph is consistent with the tree
```

Against the previous sweep, **4** cases fail — the four "activates nothing" ones,
which is your scenario reproduced mechanically. The "parked and disabled" cases
pass on both, because the crash itself parks the rule; it was the *next* run that
re-armed it, and that is precisely what the four catch.

  rather add it deliberately than fold it into this fix.
