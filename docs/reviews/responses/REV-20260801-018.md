## F1 — the duplicate guard keyed on the config path — IMPLEMENTED

### Analysis

Accepted, and the reasoning in the review is better than the one I had. My guard
asked "did root's block come from the same config file?" and the review points
out that this is the one question a real migration always answers *no* to,
because the migration is *required* to change that path: a delegated account
cannot read a config under `/root` (0700), so the documented shape moves it to
`/etc/zfs-snapshot-all/`.

Worse than the false negative was what the test encoded. It asserted that a
different config path is "unrelated", which writes the unsafe assumption into
the suite as if it were a decision. Path inequality does not prove anything
about job ownership.

I will add one observation the review did not have, from the preflight on
metropolis pve1: the natural operator reflex is to **copy** the config, not move
it, and the preflight procedure itself copies it in order to render the
proposal. So the hole is not hypothetical for an unusual operator — it is on the
straight-line path through the documented procedure.

### Implemented change

Both blocks are reduced to their job lines with the identity-dependent parts
removed, and **any** intersection is a refusal.

`job_identity()` strips exactly what an ownership change is allowed to alter:
the directory a script is invoked from, and the log a line redirects into.
Everything that decides what a job *does* — schedule, dataset list, pattern,
retention flags, quiesce, monitor thresholds — stays in the comparison. It is
one function, shared by the guard, by the migration verb's dropped-line
detection and by the tests, because writing that `sed` three times is how the
three drift apart.

Genuinely disjoint jobs are still allowed. Two collectors on one host is a real
deployment; the review asks for overlap to fail closed, not for co-existence to
be banned.

The refusal now prints the colliding lines, not just a count — the review's
second requirement, and without it an operator cannot decide anything.

### Evidence

- commit: `1d5a8c4`
- test: `test/zfsbackup/run.sh` section 16, built from the review's own
  regression specification — root's source `/root/scripts/jobs.conf`, the
  account's proposal `/etc/zfs-snapshot-all/jobs.conf`, both rendering the same
  send and prune jobs against `tank/a`. Must refuse.
- also pinned: disjoint jobs under a different path are allowed; the same path
  with the same jobs is still refused; root installing over its own block is
  untouched; a proposal that cannot be rendered fails closed; an unreadable root
  crontab fails closed; `no crontab for X` is the one benign failure;
  `job_identity` gives two owners of one job the same fingerprint but keeps
  `-H24` and `-H48` apart.
- results: `PASS=134 FAIL=0`; 12 of these fail against `HEAD~`.

### Remaining risk

`job_identity()` is a normalisation, and normalisations are only as good as the
list they carry — today seven script basenames and `cron.log`. A future
generated line that embeds a path this list does not know would fingerprint
differently under two owners and read as disjoint. The test that two owners of
one job fingerprint identically is what would catch that, but only for the
shapes the fixture contains.

## F2 — migration must be a verb, not a flag plus manual work — IMPLEMENTED

### Analysis

Accepted. "Decide what happens to root's block first, then re-run" is the tool
telling an administrator to hand-edit two crontabs and move an internal config
file around a live production workload. The review is right that this is not
something to delegate.

### Implemented change

`zfs-backup.sh migrate-to-account <account> [--preflight] [--yes]`, in the
phases REV-020 F3 later specified. The config is **moved**, never copied — a
copy is precisely how two paths come to describe one workload.

One deliberate disagreement, stated because the review sketches the opposite
order. The review's step list installs the target block and then removes root's.
Mine removes root's first. Installing first leaves **both** blocks live for the
width of one step, and the jobs at stake include prunes; two `delsnaps` runs
racing over one dataset set is the outcome worth designing against, and it
destroys data. Removing first can only lose a tick, which the next one makes up.
REV-019's own point 4 asks for an end state of one or the other and never both —
this order satisfies that *and* never passes through "both" on the way.

### Evidence

- commit: `1d5a8c4`
- test: sections 21 and 22 — the host-level block is inserted once, replaced
  rather than accumulated on a repeat run, and removed when the set is empty;
  the dataset set is read from the config; a delegation missing one verb is
  refused; migrating onto an account that already runs a managed block is
  refused before anything is rendered.

### Remaining risk

**The verb has never been run against a real pair of crontabs.** Every check
above is against stubs. It must not be used on a production host until a live
pass exists, and metropolis pve1's migration stays held until then. That is the
same class of gap REV-017 F2 opened for `--local-user`, and the live pass there
found five defects the suite could not — I have no reason to expect fewer here.
