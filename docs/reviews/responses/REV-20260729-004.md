## F1 — update-control state shares a group-writable alert directory — ACCEPTED, IMPLEMENTED

Correct. `UPDATE_STATE_DIR` no longer defaults to `$ALERT_SHARED_DIR`.

### Implemented change

`UPDATE_STATE_DIR` defaults to `/root/.zfs-snapshot-all-update-state`
(root-private, same reasoning Phase 4 already uses to keep notify-fail's own
scripts out of the delegated account's reach: `/root` is `0700`). Four new
functions gate every access:

- `ensure_update_state_dir` — refuses a symlinked path, refuses a path that
  exists and is not a directory, creates it `0700` if absent, and refuses a
  group- or world-writable directory (bitwise against `0022`, not a glob on
  the last digit of `stat`'s output, so an extra setgid/sticky leading digit
  cannot slip past the check).
- `write_state_file` — writes to a private `mktemp` file inside the state
  dir, then `mv`s it over the destination. `rename(2)` replaces the directory
  ENTRY regardless of what is currently there, so this is safe even if the
  destination is a symlink at the moment of the call -- unlike `printf ... >
  "$dst"`, which opens by name and follows a symlink there. Refuses outright
  if the destination is already known to be a symlink.
- `read_state_file` / `remove_state_file` — same refusal for reads and
  removal. Removal of a symlinked "state file" is refused on purpose even
  though `rm -f` on a symlink is not a target-following hazard: a state file
  swapped for a symlink is evidence of tampering, and silently unlinking it
  would hide that from the operator instead of surfacing it.

A one-time migration (Phase 4b, on a non-`--check-only` run) moves an
existing `previous-revision`/`update-hold` out of the old location, so a host
that had already recorded a rollback point -- or was actively HELD -- does not
lose it just because this fix moved the default. `--check-only` reports the
new directory's presence/mode without creating or migrating anything.

## F2 — state-write failures do not stop update or rollback — ACCEPTED, IMPLEMENTED

Correct. Every write is now atomic and checked; every function that used to
`return 0`/continue past an unchecked write now checks the result.

### Implemented change

- `do_self_update`: `ensure_update_state_dir` is checked before anything else.
  Recording A uses `write_state_file`; if it fails, B is never activated (`git
  merge --ff-only` is never even attempted). If the merge itself then fails,
  restoring the prior pointer (or clearing it, if there was none) is also
  checked -- if THAT fails too, the function writes an automatic
  `update-hold` rather than leaving the host silently eligible for the next
  hourly retry with uncertain state.
- `do_rollback`: the hold is written **before** `git reset --hard`, not after,
  and the function `die`s if that write fails -- so rollback never reports
  success without a hold already in place. If the reset itself fails, the
  hold message is rewritten to say so and the function still dies with the
  hold intact (fail closed, not fail open).
- `do_resume_updates`: hold removal is checked (`die`s if the file is still
  there afterward); if the explicit update that follows then fails, the hold
  is restored rather than leaving automatic updates silently re-enabled.

### Evidence

`test/selfupdate/run.sh` case 15. This one needed a mid-session fix: the
first version used `chmod 0500` on the state directory to simulate an
unwritable path, which passed locally (Windows/git-bash, permission bits are
cosmetic there) but **false-FAILed live on both pve0 and pve1** --
`deploy.sh` always runs as root, and root ignores its own DAC permission
bits entirely, so `chmod` cannot make a directory genuinely unwritable to the
process under test. Confirmed directly:

```
$ d=$(mktemp -d); chmod 0500 "$d"; touch "$d/x"; echo $?
0                                    # root: chmod means nothing
```

Fixed to use `chattr +i` (the ext2/3/4 immutable attribute, enforced at the
VFS layer below DAC/capabilities -- blocks root too):

```
$ d=$(mktemp -d); chattr +i "$d"; touch "$d/x"; echo $?
1                                    # root: chattr +i is actually enforced
```

Gated on a new `CAN_IMMUTABLE` probe alongside the existing
`CAN_SYMLINK`/`CAN_CHMOD` ones, so it SKIPs cleanly (not a false pass) on a
filesystem or platform that does not support the attribute. Committed
separately (`91d733b`) from the F1/F2/F3 implementation commit, specifically
because this was a live-only finding against the test, not the implementation.
After the fix: `PASS=30 FAIL=0 SKIP=0` on both hosts.

## F3 — updater does not refuse a dirty checkout — ACCEPTED, IMPLEMENTED

Correct, and the review's own framing of the gap (an edit in a file the
incoming commit never touches) is exactly right -- `--ff-only`'s own refusal
only covers a path collision, not general dirtiness.

### Implemented change

`git status --porcelain` is checked in `do_self_update`, before any state is
touched. If the tree is dirty and a real update is available, the function
refuses and returns non-zero without writing anything. If the tree is dirty
but current already equals target (a no-op), the acceptance criterion "may
report dirtiness but must not overwrite state" is honored literally: a
warning is logged and the function still returns 0, since nothing would have
been written either way.

### Evidence

`test/selfupdate/run.sh` cases 9-10, both against a two-tracked-file fixture
(`mk_scenario`) built specifically so one file is untouched by the incoming
commit:

- case 9: an untracked file blocks the update;
- case 10: a local edit in `other_file`, which the incoming commit never
  touches, blocks the update -- the exact gap named in the review.

Both pass locally and live on pve0/pve1 (`PASS` in all three environments).
Case 3 (pre-existing, a local edit in the SAME file the incoming commit
changes) was updated to assert on the new, earlier diagnostic ("not clean")
instead of the old ff-only-failure message, since the dirty-check now catches
that case before `merge --ff-only` is ever attempted.

## F4 — cron normalization can preserve duplicates or match another updater — ACCEPTED, IMPLEMENTED

Correct on both points: the old check (`grep -qF -- "--self-update"`,
unanchored) could match an unrelated program's cron line, and once a
current-shaped line existed anywhere the branch order meant an old duplicate
next to it was never cleaned up.

### Implemented change

`is_this_repo_updater_line()` replaces the substring check, scoped to
`$REPO_DIR`: matches this repo's current line or either old shape, nothing
else. Every crontab line is now counted (`match_count`, and `exact_count` for
lines byte-identical to the current form). A non-`--check-only` run drops
every matching line and appends exactly one current line, regardless of how
many matched or in what shape; `--check-only` reports the counts without
changing anything.

### Evidence

`test/selfupdate/run.sh`: the matcher tests were rewritten to mirror
`is_this_repo_updater_line`/`normalize_lines` exactly (kept in sync by
comment), adding the cases the review named as missing:

- current + old together → both match, normalize to one;
- two current duplicates → both match (a duplicate is detected), normalize
  to one;
- an unrelated `--self-update` line for another program/repo → does not
  match at all;
- an unrelated line coexisting with this repo's old line → only the real one
  matches.

Live: both hosts already carried the single current-form line from a prior
deploy, so `--check-only` correctly reported "auto-update cron line already
current, leaving it alone" on both, and the full non-check run left it
untouched (verified: `crontab -l` still shows exactly one
`deploy.sh --self-update` line on each host afterward). The
duplicate/mixed-shape injection scenarios themselves were exercised via the
test suite's own throwaway-crontab-line predicate (not against the live
`crontab -l`/`crontab -` of either production host, to avoid touching their
real cron state for a scenario the test suite already covers deterministically).

**One transitional artifact found and understood, not a defect in this fix:**
the rollback target (`feaf0ab`) predates this fix, so `git reset --hard`
checked out the OLD `deploy.sh` -- whose `do_self_update` still defaults
`UPDATE_STATE_DIR` to `$ALERT_SHARED_DIR` and has no hold-file-symlink check
at all. Running `--self-update` immediately after (as a stand-in for the next
hourly cron tick, still on the old checked-out code) therefore looked at the
OLD hold location, found nothing there, and updated straight back to
`df07498` -- the NEW hold at the NEW location was correctly written and
never removed, but the code that ran next didn't know to look for it there.
This is inherent to any change that moves the state schema combined with a
rollback that reverts past the exact commit making that change: it cannot
recur for any pair of revisions both at or after `df07498`, since they all
agree on the new location. Confirmed both `previous-revision` locations and
cleared the stale artifacts via `--resume-updates` (the sanctioned path) plus
removal of the now-orphaned old-location duplicate; both hosts finished this
session at `91d733b`, un-held, with a single state location in use.

  rollback exists, same as before this review.

  `--resume-updates` can still interleave (named as accepted risk in the

  artifact this session found (old code / new state, or vice versa, for
  exactly one hourly tick around the boundary) will recur. Worth a one-line
  note in the next such change rather than a mechanism, given how narrow the
  window is and that it self-heals on the very next tick once both sides
  agree on the code.
