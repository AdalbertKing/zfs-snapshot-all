# Response to REV-20260801-022

Delivery: direct to `main`, per the owner-approved exception.

## F1 — an explicit grant request must not exit 0 — ACCEPTED, IMPLEMENTED

### Analysis

Accepted without reservation. The distinction the review draws is the one I
missed: `deploy.sh` has two different jobs in the same script, and I applied the
convention of the first to the second.

Account **detection** exists so that a bare `bash deploy.sh` is correct on every
host in the fleet without anyone tracking which machine has an account. For
maintenance that is right — "keep whatever this host already has up to date" is
a complete instruction, and finding nothing to maintain is a normal outcome
worth exactly one log line.

A privilege grant is not that. "Whichever account happened to be found" is not a
decision anyone made, and "found nothing, exiting 0" answers a question nobody
asked. The review's operational point is the sharper one: the warning is only
read by a human who is watching, and the whole direction of this work is towards
a wrapper that reads exit codes and proceeds to `migrate-to-account`.

### Implemented change

Refused at **argument** time rather than after runtime discovery, which is
strictly stronger than what the review asked for and is the review's own second
option ("make the high-level operation create/select the account unambiguously
in the same invocation"):

```
--allow-quiesce must name the account that receives the grant: --backup-user=NAME
(with --datasets="..." naming exactly the datasets whose guests it may freeze).
An existing account is fine -- it is left alone. Nothing was installed.
```

`exit 2`, consistent with the two refusals the review cites. `BACKUP_USER` is
read rather than the flag, so a host that pins the account in the config block
at the top of the script still works. `--backup-user` on an existing account is
already a no-op ("user already exists, leaving it alone"), so requiring it costs
nothing but the naming.

Both no-account branches in Phase 8 now `die` as well. The argument check makes
them unreachable today; they are kept because the invariant is "an explicit
grant request never reports success having granted nothing", not "one particular
check enforces it". A later loosening of the argument rule should land on a
refusal, not on the old silent success.

### A defect in the regression test itself, worth recording

The first version of this check ran the real `deploy.sh` in a sandbox built by
path substitution. Against the **fixed** script that is safe, because argument
validation refuses in the first few hundred lines. Against the **pre-fix**
script — which is exactly what a regression test must be run against — nothing
stopped it, and it began provisioning the workstation running the suite before
it was killed.

A test whose failure mode is "deploy this machine" is not a test. The sandbox
copy now has `exit 99` spliced in immediately after the argument-validation
block, so the run is incapable of reaching Phase 1 whatever the verdict: `2`
means refused, `99` means validation let it through. The tripwire's own presence
is asserted before it is relied on.

### Remaining risk

The argument check keys on `BACKUP_USER` being non-empty, not on the account
being resolvable. `--backup-user=typo --allow-quiesce` therefore creates the
account `typo` and grants it — loud and visible in the log, and consistent with
what `--backup-user` already does on its own, but it is a naming error the check
cannot catch.

## Product-level note — AGREED, NOT YET DONE

Agreed, and it matches the position already recorded in
`docs/discussions/DEPLOY-UX-AGREED-POSITION.md`. The preflight currently names
separate `deploy.sh` invocations and stops; it does not emit one ordered,
copy-pasteable remediation block, and it does not re-check the prerequisites
immediately before commit (it checks them once, in phase 1).

Both are worth doing and neither is in this commit. The reason for stopping here
is that the ownership boundary the review endorses in "Accepted progress" point 3
is exactly what makes the remediation block safe to emit: `migrate-to-account`
can print a `deploy.sh` command without being able to run it. Turning that into
orchestration is a separate change with its own failure modes — partially
applied prerequisites, above all — and it should not ride along with a fix to
an exit code.

and the account's), so the provisioning path disturbed nothing that was already
scheduled.
