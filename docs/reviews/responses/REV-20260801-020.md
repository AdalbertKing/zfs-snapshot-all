# Response to REV-20260801-020

Delivery: direct to `main`, per the owner-approved exception. Commit `1d5a8c4`.

## F1 — the runbook is not the product — ACCEPTED, PARTIALLY IMPLEMENTED

### Analysis

Accepted. The list in the review is the correct indictment of
`docs/MIGRATION-ROOT-TO-ACCOUNT.md` as an operational answer: block extraction
and normalisation, two checkouts, config placement and mode, `zfs allow` per
parent dataset, `pair`/`join` and per-guest quiesce grants, the digest exception,
two crontabs in the right order, and rollback across several independent
resources. A competent Linux/ZFS administrator should not need to hold any of
that.

I would add that the document was never *intended* as the operational answer —
it was written as the preflight record for one specific host — but the review is
right that publishing it without the command makes it the answer in practice,
because it is the only thing that exists.

### Implemented change

`zfs-backup.sh migrate-to-account <account> [--preflight] [--yes]` discovers what
the runbook made a human discover:

- the current owner and the live block, from root's crontab;
- the config behind it, from the block's own `# Source:` line;
- whether the account can read that config, asked **as the account**;
- whether the account has its own checkout;
- the dataset set, parsed from the config's own section headers rather than
  supplied by the operator — this is the gap that was missed by hand on pve1
  (`hdd/vm-disks`, four of five datasets);
- `zfs allow` on each of them, where a grant missing one verb is not a grant;
- the quiesce grant, but only if the block actually uses `-q`;
- which lines are host-level and will not move.

`--preflight` runs phase 1 alone, read-only, and prints a capability table.

### What is NOT implemented

The review says the command should "provision/check" capabilities. It **checks**
all of them and **provisions** only the config move. For `zfs allow` and the
quiesce grant it names the exact `deploy.sh` command and refuses.

That is a deliberate stop, not an oversight. Provisioning them from here means
this verb acquiring `deploy.sh`'s privileged surface — delegation and a sudoers
grant — and `docs/discussions/DEPLOY-UX-AGREED-POSITION.md` puts `zfs-backup.sh`
as an orchestration layer *over* `deploy.sh` rather than an extension of it.
Crossing that line is a decision for the owner and the reviewer, and I would
rather be told to cross it than cross it quietly. If the answer is that a
one-command migration must provision, I will implement it.

### Evidence

- commit: `1d5a8c4`
- test: `test/zfsbackup/run.sh` section 22 — the dataset set is read from the
  config; a full delegation passes; one missing `destroy` is refused; an absent
  grant is refused; an account that already runs a managed block is refused
  before anything is rendered
- results: `PASS=134 FAIL=0`; 12 fail against the base

### Remaining risk

Never run against real crontabs. See F3.

## F2 — the digest became an unmanaged orphan — ACCEPTED

### Analysis

Accepted without reservation, and this is the finding I am most glad to have
received before running the migration. My procedure told the operator to remove
the managed block and re-add `alert-digest.sh` as an ordinary root line. Every
consequence the review lists is real: `remove-client` cannot tell whether that
line belongs to this deployment, a second migration duplicates it, no preview
can honestly show the whole change, and the exception has to be remembered
forever by a human.

I had found the digest problem myself during the preflight and solved it in the
worst available way — by writing the exception into a document.

### Implemented change

Host-level lines get their own tool-owned block in root's crontab,
`# BEGIN zfs-backup-host` / `# END zfs-backup-host`, with the same contract
`gen-cron.sh` has with its own: rewritten wholesale, idempotent, and removed
entirely when the set is empty so a reverse migration can hand the lines back.
It appears in the combined preview, is restored by the rollback, and is verified
after the switch.

The set is not a hardcoded list of "digest". It is computed: every line in root's
block whose job identity the account's render does not reproduce. Whatever turns
out to be host-level is carried, not just the one case I happened to find.

### Evidence

- commit: `1d5a8c4`
- test: section 21 — inserted once with surrounding unmanaged lines untouched;
  a repeated write replaces rather than accumulates (the duplication the review
  predicted); an empty set removes the block; and a check that the markers really
  do contain regex metacharacters, because the removal is done with `awk` and a
  literal compare after a `sed` address would have silently failed to match them

### Remaining risk

The block is created by the migration verb and by nothing else. A host that
never migrates has no host block, and `alert-digest.sh` stays inside the
collector block as today. So the "first-class managed state" the review asks for
exists on migrated hosts only. Making `gen-cron.sh` emit host-level lines into
their own block from the start would generalise it — that is a change to the
generator's contract and to every existing crontab, which I have not made
unasked.

## F3 — separate guarantees for preparation and identity switch — ACCEPTED

### Analysis

Accepted; the phase split is the right shape and I have implemented the
reviewer's five phases in the reviewer's order.

### Implemented change

1. **preflight** — read-only, also reachable alone via `--preflight`. A/B/C
   equivalence, config existence and readability, target checkout, ZFS
   delegation, quiesce, host-level lines. Blocking gaps are tracked separately
   from what phase 2 will do itself, so "the tool can fix it" cannot silently
   become "the tool will proceed without it".
2. **prepare** — the config move, touching neither crontab.
3. **preview** — one combined proposal: root's block out, host block in, the
   account's block in, and the config move, with counts on both sides.
4. **commit** — root's block out, then the account's in. See
   `docs/reviews/responses/REV-20260801-019.md` for why that order and not the
   reverse.
5. **verify** — both crontabs read back **as their actual owners**; root must
   hold zero managed blocks and the account exactly one, and the host block must
   have survived. Any surprise restores both crontabs and the config location.

### Evidence

- commit: `1d5a8c4`
- the preflight refuses with a non-zero exit and a listed gap table; no cron
  path is reached when any gate fails

### Remaining risk

The one that matters, and it applies to all three findings: **none of this has
run against a real pair of crontabs.** The guarantees are asserted against
stubbed `crontab`, `getent`, `runuser` and `zfs`. REV-017 F2 made exactly this
point about `--local-user`, and the live pass that followed found five defects
the suite could not see. I expect no better here.

Metropolis pve1's migration therefore stays held — but the reason has changed.
It is no longer the path-keyed guard; it is that the code written to replace the
manual procedure is itself untested against production shapes.
