## F1 — ACCEPTED, IMPLEMENTED

### Analysis

Correct, including the detail that makes it dangerous. `set_host_block` handed
`hostlines` to `cron_block_render` as the **complete new body**, which was right
while `zfs-backup.sh` owned that block alone. Yesterday I made `deploy.sh` a
second requester of the same block. From that moment the deployed shape was

```
# BEGIN zfs-backup-host
15 * * * * update-control.sh --self-update
0 8 * * * check-pool-capacity.sh
# END zfs-backup-host
```

and a migration arriving with one rescued digest line would have replaced all of
it. The failure is silent by construction: the collector jobs migrate correctly,
so the operation reports success while automatic updates and capacity alerting
have been removed from cron.

**I introduced this yesterday and my own test did not see it** — the reviewer
names why: the fixture left `check-pool-capacity` *loose*, outside the block, so
wholesale replacement looked harmless.

### Ownership model, as the review requires

| Line | Owner | Verb |
|---|---|---|
| root updater (`update-control.sh --self-update`) | `deploy.sh` | `cron_block_ensure_line` (normalises three historical spellings) |
| root capacity check | `deploy.sh` | `cron_block_adopt_line` (keeps a hand-tuned schedule) |
| account auto-pull | `deploy.sh`, in the **account's** crontab | `cron_block_adopt_line` |
| `alert-digest` | `gen-cron.sh` while root runs the managed block; **`zfs-backup.sh` at migration**, which carries it into the host block because a delegated account never gets the digest script | merge |

The rule that follows, and is now enforced by the API rather than remembered:
**a requester of a shared block adds its own lines and never speaks for the rest
of the body.** The destructive verb is gone from that path —
`cron_block_merge_render` reads the current body, adds what is missing, and
leaves everything else alone. An empty contribution means "this requester has
nothing to add", not "this block should go".

Teardown is the one case that still needs a whole-block removal, and it stays on
`cron_block_remove`, which is explicit about removing a block by name.

## F4 — ACCEPTED, IMPLEMENTED

`cron_block_locate` counted only the requested name's markers, so

```

...
# END zfs-backup-managed
```

## F2 — ACCEPTED, IMPLEMENTED

The race was real and I can now state exactly what closed it: every public
mutating entry point (`cron_block_install`, `cron_block_remove`,
`cron_block_ensure_line`, `cron_block_adopt_line`) acquires a per-target-user
lock before its first read and releases it after the write's read-back (or the
restore decision), so `cron_read → render → cron_write` is never split across
two processes' views of the same crontab. `gen-cron.sh`'s `GEN_CRON_LOCKFILE`
stays as an outer, coarser lock around its whole `--install` run; it no longer
matters that `deploy.sh` never took it, because the shared lock now sits at the
one place every writer actually passes through.

### Locking model, as implemented

- `cron_lock_acquire`/`cron_lock_release` — `exec {fd}>` a lock file under
  `CRON_LOCK_DIR` (`/run`, falling back to `/tmp`), `flock -w <timeout> "$fd"`.
  A requester does not have to remember a separate lock to be safe, because
  there is no path from a requester to `crontab(1)` that skips this one.
- **Extent:** every mutating function has an internal `*_impl` that does the
  real work unlocked; the public name is a thin wrapper that locks, calls the
  impl, unlocks. `flock(1)` locks are held by an *open file description*, not by
  the process, so a second `exec {fd}>` on the same lock file from the same
  process would self-deadlock rather than succeed — `cron_block_adopt_line`'s
  wrapper therefore calls `cron_block_ensure_line_impl` directly, never the
  locked `cron_block_ensure_line`.
- **Key:** the target user — `cron_lock_acquire_multi`/`_release_multi` take
  several, in **sorted-by-name** order regardless of call order, so a
  transaction naming `(root, zzz)` and one naming `(zzz, root)` can never form a
  cycle. A partial acquisition on refusal releases what it already got.
- **Contention:** `flock -w <timeout>` — bounded wait, then a clear diagnostic
  (`CRON_ERR` names the contention explicitly) and no write. Never a silent,
  unbounded hang.

### A bug the implementation caught on its own way in

`cron_lock_release` read `local user="$1" fd="${CRON_LOCK_FD[$user]:-}"` — one
`local` statement, two assignments. Bash expands **all** the words on a `local`
line before performing any of the assignments, so the `$user` inside the second
field's expansion resolved against whatever `user` meant *before* this call
(nothing, under `set -u`), not the `"$1"` on the same line. Under `set -u` this
is an immediate `unbound variable` abort with the diagnosing message routed to
`/dev/null` one line below it in the caller — the suite died with **no output
at all**, repeatably, until the two assignments were split into two statements.
Recorded because it is the same family of defect this project keeps finding:
an error real, but the report of it silently lost.

### Evidence

- test: `test/cron/run.sh`, sections P–S (+14 checks), driven with a **forced**
  interleaving rather than a timing race: a barrier file proves process A holds
  the lock and is mid-write before process B's `cron_block_install` is even
  started, so B's contention is provable, not hopeful.
  - **P** — both writers survive: A's line into `zfs-backup-host` and B's own
    `zfs-backup-managed` block are both present afterward, and so is the line
    that predates both;
  - **Q** — a lock held by another process refuses within its bounded timeout,
    naming the contention, not a generic error;
  - **R** — a different user's lock is acquired immediately, unaffected by the
    first user's held lock;
  - **S** — `cron_lock_acquire_multi` succeeds regardless of name order, both
    locks are genuinely held and later genuinely released, and a multi-lock
    that cannot complete releases what it already got rather than leaking it.
- results: `test/cron` **111/111** (+14), `zfsbackup` 209/209, `scope` 34/34,
  `join` 42/42, `selfupdate` 28/28, `quiescehelper` 119/119, `gencron` 56/56,
  `impact` 21/21, graph consistent.
- **against the reviewed code** (pre-F2, commit `d7a212f`): the new checks fail
  — but stated precisely, because the failure mode is worth being exact about.
  `cron_lock_acquire` does not exist at all on that commit, so the barrier
  script dies with `command not found` rather than reproducing the lost-update
  artifact through the *old* unlocked read-modify-write path. That is sufficient
  to show the tests exercise genuinely new behaviour, but it is not the same
  claim as "this harness caught the race in the old code's own execution path" —
  the old code had no lock to contend on, so there was nothing for the barrier
  to force a collision against. Said plainly rather than left implied.

1. **`update-control.sh`** — a copy outside `$REPO_DIR` with duplicated
