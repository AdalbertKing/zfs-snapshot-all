## F1 — ACCEPTED, IMPLEMENTED

### Analysis

Correct, including the detail that makes it dangerous. `set_host_block` handed
`hostlines` to `cron_block_render` as the **complete new body**, which was right
while `zfs-backup.sh` owned that block alone. Yesterday I made `deploy.sh` a
second requester of the same block. From that moment the deployed shape was

```
# BEGIN zfs-backup-host
15 * * * * update-control.sh --self-update
0 8 * * * check-pool-capacity.sh
# END zfs-backup-host
```

and a migration arriving with one rescued digest line would have replaced all of
it. The failure is silent by construction: the collector jobs migrate correctly,
so the operation reports success while automatic updates and capacity alerting
have been removed from cron.

**I introduced this yesterday and my own test did not see it** — the reviewer
names why: the fixture left `check-pool-capacity` *loose*, outside the block, so
wholesale replacement looked harmless.

### Ownership model, as the review requires

| Line | Owner | Verb |
|---|---|---|
| root updater (`update-control.sh --self-update`) | `deploy.sh` | `cron_block_ensure_line` (normalises three historical spellings) |
| root capacity check | `deploy.sh` | `cron_block_adopt_line` (keeps a hand-tuned schedule) |
| account auto-pull | `deploy.sh`, in the **account's** crontab | `cron_block_adopt_line` |
| `alert-digest` | `gen-cron.sh` while root runs the managed block; **`zfs-backup.sh` at migration**, which carries it into the host block because a delegated account never gets the digest script | merge |

The rule that follows, and is now enforced by the API rather than remembered:
**a requester of a shared block adds its own lines and never speaks for the rest
of the body.** The destructive verb is gone from that path —
`cron_block_merge_render` reads the current body, adds what is missing, and
leaves everything else alone. An empty contribution means "this requester has
nothing to add", not "this block should go".

Teardown is the one case that still needs a whole-block removal, and it stays on
`cron_block_remove`, which is explicit about removing a block by name.

## F4 — ACCEPTED, IMPLEMENTED

`cron_block_locate` counted only the requested name's markers, so

```
# BEGIN zfs-backup-host
# BEGIN zfs-backup-managed
...
# END zfs-backup-managed
# END zfs-backup-host
```

was a well-formed `zfs-backup-host`, and replacing it deleted the managed block
whole — with the write reporting success, because the result is internally
consistent for the target name alone.

`cron_markers_valid` now checks the layout of **every** managed marker before
any mutation: no nesting, no overlap, no orphan (even a foreign one), no
duplicate name, nothing left open. Refused, never repaired — every automatic
repair here is a guess about whose lines are whose.

foreign orphan `END`, foreign block left open, duplicated foreign name, and the

## F2 — ACCEPTED, next slice

The race is real and I can state it precisely: `cron_read → render → cron_write`
with no lock, `gen-cron.sh`'s `GEN_CRON_LOCKFILE` private to its own run, and
`deploy.sh` never taking it. Read-back proves the write landed; it cannot prove
nothing was lost between the read and the write.

### Locking model

- **A per-target-user lock inside the library**, acquired by every public
  mutating entry point (`cron_block_install`, `cron_block_remove`,
  `cron_block_ensure_line`, `cron_block_adopt_line`, and the whole-crontab
  primitive F3 needs). A requester must not have to remember a lock to be safe —
  that is what F2 is about.
- **Extent:** from the first read to after the read-back, including the
  preliminary read that adoption performs and any restore decision. The restore
  must be inside, or a concurrent writer can land between the failed write and
  the restore.
- **Key:** the target user, so writes to two different users proceed in
  parallel, and two writes to one user serialise regardless of which block they
  name.
- **Multi-user transactions** (the migration touches root and the account) take
  locks in a **deterministic order — sorted by user name** — and hold both for
  the whole transaction. Deadlock is then impossible by construction rather than
  by timeout.
- **Contention:** non-blocking with a short bounded retry, then a clear
  diagnostic and **no write**. A migration that cannot serialise must not
  proceed half-locked.
- Lock files under `/run` where available, falling back to `/tmp`, created with
  the same fail-closed discipline as the rest: if the lock cannot be taken, the
  write does not happen.

### Test

A barrier-controlled test with two processes writing **different** blocks of the
same stubbed crontab, the interleaving forced rather than raced: both survive
with the lock, and the reviewed code loses one. Plus lock-cleanup and
lock-failure paths.

## F3 — ACCEPTED, next slice

`migrate-to-account` still calls `crontab` directly on three paths, and the
library header's claim to be "the ONE way this project writes a crontab" is
therefore not yet true on an ordinary workflow. Stated plainly rather than
softened: I wrote that header while these three sites existed.

### Inventory of every direct `crontab` write site in the tree

| Site | Kind | Verdict |
|---|---|---|
| `zfs-backup.sh:2550` `crontab "$rootnew"` — migration forward | ordinary | **must move to the library** (F3) |
| `zfs-backup.sh:2507` `crontab "$rootcron"` — rollback, root | ordinary | **must move** |
| `zfs-backup.sh:2513` `crontab -u "$acct" "$acctcron"` — rollback, account | ordinary | **must move** |
| `update-control.sh:127` — emergency circuit breaker | **deliberate exception** | keeps its own copy on purpose: it lives outside the repo so it survives a rollback of the repo, and its whole job is to work when the checkout is broken. Sourcing a library from that checkout would defeat it |
| `deploy.sh:1293` — same circuit breaker, `emergency_disable` | **deliberate exception**, with a caveat | same reasoning, but this copy runs *from* the checkout, so it could use the library. It is reached only when writing the update-hold file has already failed, i.e. when the filesystem is misbehaving — the one moment a bigger dependency is least welcome. I propose keeping it and marking it, and I will change it if the reviewer disagrees |
| `cron2conf.sh:121` | **read only** (`crontab -u … -l`), never writes | no action |

The migration needs a whole-crontab operation, because it moves ownership
between two identities in one transaction and the intermediate states are not
expressible as block edits. That will be an explicit library primitive —
`cron_replace_all` — with read-back, the F2 lock, and the marker validation from
F4, not a raw `crontab` hidden in the requester.

### Test

Root-forward liar, account-forward failure, root-restore liar, account-restore
liar; each asserting the mixed-state result the review names, and that the prior
content survives on disk when a restore cannot be verified.

## Emergency and bootstrap paths that stay outside the library

As the review asks, stated explicitly:

1. **`update-control.sh`** — a copy outside `$REPO_DIR` with duplicated
   helpers, so that a rollback of the repo cannot take the thing that performs
   rollbacks. Its cron-line removal is a last-resort circuit breaker.
2. **`deploy.sh`'s `emergency_disable`** — the same breaker on the provisioning
   side, reached only after the update-hold write has already failed.

Everything else is an ordinary requester and belongs inside `lib-cron.sh`.
