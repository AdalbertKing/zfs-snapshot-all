## F1/F2 (both passes) — missing pinned host key must be fatal; HostKeyAlias — ACCEPTED, IMPLEMENTED

`activate-client` and `test` now `die` outright if no pinned host key can be derived (was: `warn`
+ silent fall back to `accept-new`). New `host_key_alias()`/`ensure_alias_known_hosts()` derive a
second, alias-keyed `known_hosts` file from the same already-verified pinned key material --
`deploy.sh`'s own file stays untouched, read-only from here, per the agreed position's "no changes
to `deploy.sh`'s public surface." Every generated `flags` string now carries
`-O HostKeyAlias=zfs-client-<label> -k <alias-file>`.

**Honest scope limit**: this is the mechanical piece (the alias file + flag), not the full
LAN/VPN endpoint-independence model both reviews actually asked for (stable `client_id`/
`relation_id` decoupled from `PEER_HOST`, an endpoint state machine, a real LAN-seed-then-VPN
test). That remains explicitly not built -- see "Not done" below.

Live-verified on pve0/pve1: the generated cron line for the throwaway client carries
`-O HostKeyAlias=zfs-client-192.168.11.11 -k /root/.ssh/pairing/192.168.11.11_alias_known_hosts`.

## F5 (both passes) — basename-only comparison is not proof of same file — ACCEPTED, IMPLEMENTED

`assert_cron_config_matches_installed()` now resolves both the crontab's recorded `# Source:`
value and the target file through `readlink -f`, normalizing a relative name against `$SCRIPT_DIR`
first (matching how `gen-cron.sh`'s own default `-c` resolution actually works, not against
whatever the caller's current working directory happens to be -- the second review's specific
concern). `test/zfsbackup/run.sh`'s case for this was rewritten to actually prove it: a different
real file sharing a basename with the installed one now correctly refuses (the old test's premise
-- that this should PASS -- was itself wrong once canonical comparison replaced basename).

## F4/F6 (both passes) — config edits must be transactional — ACCEPTED, IMPLEMENTED

`activate-client` and `remove-client` now build and validate a **working copy** of the config.
The real file is touched only via `atomic_replace_and_install()`: atomic swap after validation +
dry-run + confirmation all succeed, with automatic rollback to the exact prior content (backed up
before the swap) if `gen-cron.sh --install` then fails. Any failure before that point (validation,
dry-run, "not confirmed") leaves the real file completely untouched -- proven live below.

## F8 (review 1) — inherited `zfs allow` visibility — ACCEPTED, IMPLEMENTED (best-effort)

New `show_effective_grants()` prints `zfs allow` at the target dataset and every ancestor path
component before the activation summary. This does **not** attempt to programmatically separate
"this relation's grant" from "already existing" from "inherited from an ancestor" -- it surfaces
the raw picture at every level and leaves the judgment to the admin, since a full categorization
parser was more than this pass's scope. Live-verified: showed `rpool` (no grant) and
`rpool/zfsbackuptest-src` (exactly the expected `Local+Descendent` grant for the delegated
account, nothing else) -- correctly showing a clean, non-inherited grant in the test case.

## F8 (review 2) — `ensure_cron_config` only checked one template — ACCEPTED, IMPLEMENTED

Now checks each of the four `standard_*` templates independently and appends only what is
missing, using four separate template variables instead of one blob -- the old single-blob append
would also have duplicated already-present templates the moment any one was missing.

## F9 (review 1) — `keep=`/`retain=` wording drift — ACCEPTED, IMPLEMENTED

Fixed in the same pass; comments and the activation summary now say `retain=` throughout.

## Real defect found during this session's live re-verification (not from either review)

Live-testing the fixed `activate-client` on pve0 caught a genuine incompatibility: `gen-cron.sh`
rejects `quiesce=agent` on a **pull** `[dataset:]` section outright (`snapget.sh` has no `-q`
support -- the guest lives on the remote peer, not locally). The owner's "z flush koherentne"
request for daily/weekly/monthly cannot be met by `zfs-backup.sh` today, since it is pull-only.
Removed `quiesce=agent` from the three affected templates (`927aad6`), documented the gap
explicitly in the file header rather than silently dropping the requirement. Getting real
application consistency for a pull client needs either a remote-quiesce feature added to
`snapget.sh` (not attempted) or running that one client in push mode instead -- flagged as a real,
unresolved product gap, not swept under the profile.
