## F1 — Gate G remains unverified

**NEEDS-DISCUSSION — this is an infrastructure-provisioning decision, not
an implementation task.**

### What is actually reachable right now

The environment available to this session is exactly the four hosts on
record in `docs/PROJECT_STATUS.md`'s host table:

- `pve0` (192.168.11.10) / `pve1` (192.168.11.11) — one Proxmox cluster,
  one network path between them.
- metropolis `pve1` (192.168.28.9) / `pve2` (192.168.28.8) — a second,
  separate Proxmox cluster, also one network path between its two
  members.

REV-20260804-039's response already recorded why Gate G could not be run
in the first campaign: "ta para hostów ma dokładnie jedną ścieżkę
sieciową" (`docs/PROJECT_STATUS.md`, REV-037/038/039 summary). That is
still true today — nothing in REV-040/041 touched networking, and no new
route was provisioned between any of the four hosts in the interim.

Gate G's acceptance criteria require a real route change — traffic moved
from path 1 to path 2 while the *logical* endpoint (`host:port` the
collector addresses) stays fixed. That needs either:

1. a second, independently selectable network path between an existing
   paired host and its peer (e.g. a direct LAN link added alongside the
   existing VPN, or a second VPN tunnel), or
2. an isolated lab equivalent that still exercises the real `ssh`/`zfs`
   command path — e.g. two loopback-bound `sshd` listeners on distinct
   local addresses in front of the same scratch account/dataset, with a
   firewall rule used to force the route switch — rather than a stub.

Both options are provisioning decisions on production or production-adjacent
hosts (a new tunnel/route, or a new sshd/account/firewall rule on one of the
four live collectors), not something this session should do unilaterally
under the standing direct-main exception, which covers code delivery, not
network topology changes.

### Question for the owner

Which of the following do you want:

- **(a)** stand up a second network path between one existing pair (state
  which pair and how — second VPN profile, direct LAN, etc.) so Gate G can
  be run against real infrastructure;
- **(b)** authorize building the loopback/lab equivalent described above on
  a named host (which one, and confirmation that a scratch `sshd`
  listener + firewall rule is acceptable there); or
- **(c)** accept Gate G as a documented, deliberately deferred gap (the
  routing-relocation code path is exercised by `test/remote`'s existing
  unit/local coverage, just not proven live) and record that as an
  owner-accepted risk rather than continuing to carry it as blocking.

No production code changes are needed for any of the three; this is a
resourcing/risk-acceptance decision.

- **(c)** accept Gate I as a documented, deliberately deferred gap.
