# Response to REV-20260803-036

All five findings are correct. `deploy.sh --pause`/`--resume` was, as the
review says, experimental — none of these five gaps had been exercised
against anything but the happy path. All five are implemented below.

## F1 — ACCEPTED, IMPLEMENTED

### Analysis

Correct as written: the old `do_pause_one` blanked the live crontab with
`cron_write` BEFORE it even tried `mkdir -p`/`mv` to save the original, and
checked neither. A failure or a process death between those two steps left
the crontab paused with no resume artifact anywhere.

### Proposed / implemented crash-consistent state protocol

1. Read the current crontab into a plain temp file (`cur`), as before.
2. `mkdir -p`/`chmod 700` the state directory, then verify it actually IS a
   writable directory (not a failed mkdir over an existing file, or a
   directory some other identity owns) — refuse before touching anything
   else if not.
3. Refuse if either final target path (`<user>.saved`, and the new
   `<user>.placeholder` from F3) is a symlink.
4. Write the pre-pause crontab, and the exact placeholder text that is about
   to be installed, into two temp files created *inside* the state
   directory (`mktemp "$PAUSE_STATE_DIR/.<user>.saved.XXXXXX"`, same for
   `.placeholder`) — same filesystem as the final path, which is what makes
   the rename in the next step atomic.
5. `chmod 600`, `cmp -s` the saved copy against what was actually read (a
   `cp` that silently truncated would defeat the entire point), `sync` each
   temp file (falls back to a bare `sync` when the coreutils per-file form
   isn't available — best-effort, not load-bearing; the atomic rename is
   what actually matters).
6. Atomically `mv -f` both temp files onto their final names. Any failure at
   this step removes every temp/partial artifact and returns non-zero with
   the live crontab **never touched**.
7. Only now is the placeholder written to the live crontab via `cron_write`
   (verified read-back, as before).
8. If step 7 fails, **both just-committed state files are deleted**. A
   failed pause must never leave behind a state artifact claiming the user
   is paused — this is also what keeps `test/pause/run.sh` section E/P (the
   pre-existing "liar" write-failure regression) passing unchanged: no
   saved-state file after a failed pause, exactly as before.

A crash between step 6 and step 7 leaves an extra, harmless resume file next
to a still-live original crontab — `--pause` just needs to be re-run, and
`do_pause_one`'s existing "already paused" guard would in fact fire first,
correctly, since the state file already exists. That is the direction the
review asked to fail toward, and it is the only direction this design can
fail in: nothing after step 6 can ever run before it.

### F3's exact-match check reuses the same durable write

Rather than re-deriving the placeholder's shape at resume time, the exact
bytes are saved next to the crontab copy at pause time (step 4 above,
`pause_placeholder_path()` = `$PAUSE_STATE_DIR/<user>.placeholder`).
`do_resume_one` now requires `cmp -s "$cur" "$ph_state"` before it will
restore anything, replacing the old `grep -qF "$PAUSE_MARKER" "$cur"`
substring search. A placeholder with one line appended during the window
still contains the marker text and used to pass that grep; it now fails the
byte comparison and is refused with the manual-edit warning, same as an
entirely different crontab always was.

One compatibility note, not a defect: a `--pause` started under the
previous code (before this commit) saved no `.placeholder` companion file.
`--resume` run under this commit against such a state will refuse with "not
byte-for-byte" rather than silently falling back to the old, weaker check.
Not believed to be live anywhere — the review itself calls this feature
experimental and says not to rely on its exit code yet — but flagging it as
the one non-hypothetical operational edge this change introduces. If a real
in-flight pause needs restoring across this exact deploy boundary, the fix
is manual: `crontab <the .saved file>` by hand, once, for that user.

## F2 — ACCEPTED, IMPLEMENTED

### Is per-user block pause/resume now a single `cron_replace_all` transaction?

Yes. `do_pause_blocks_one`/`do_resume_blocks_one` no longer call
`cron_block_install_impl` (which itself writes the live crontab) once per
block. Every block's new shape is rendered locally, in memory-backed temp
files, with `cron_block_render` — a pure function that never touches
`crontab(1)` — chaining `cur → staged → cur` across successive block names
in the loop. The live crontab is replaced exactly once, at the very end,
through `cron_replace_all_impl` (called directly, not through its locked
wrapper, since the calling function already holds the user's lock).

Consequences:

- Any failure during the per-block rendering loop (a malformed block, a
  `mktemp` failure, a `cron_block_render` refusal) aborts immediately with
  the live crontab **completely untouched** — there is nothing partial to
  roll back, because nothing was written yet.
- The single commit at the end is `cron_replace_all_impl`'s own
  lock-held, read-back-verified write — the same primitive
  `migrate-to-account` already trusts for whole-crontab transactions
  (REV-20260802-034 F3).
- An already-paused block, or an empty block, is a legitimate **skip**
  within the same pass, not a failure — the loop keeps rendering the
  remaining blocks and still commits once at the end. `count=0` after the
  loop (nothing was actually pauseable/resumable) is the only case that
  returns non-zero without ever calling `cron_replace_all_impl`.
- Multi-user reporting (root + the delegated account) is unchanged at the
  `do_pause()`/`do_resume()` level: each user is still its own independent
  lock/transaction, and a failure on one does not touch the other's already
  a per-user, all-or-nothing story of its own (see "Notes" below on why this
  boundary was kept at one-user-per-transaction rather than widened).

One correctness gap introduced by this refactor and fixed in the same
commit, not asked for by the review but load-bearing for it: the old
per-block path went through `cron_block_install_impl`, which calls
`cron_body_valid` on the new body before installing it — refusing a body
that contains its own `# BEGIN`/`# END` line, which would corrupt the
marker layout for every write after it. Calling `cron_block_render`
directly bypasses that check. `do_pause_blocks_one`'s body is safe by
construction (every line is either the fixed header or carries the fixed
`#ZSA-PAUSED#` prefix, neither of which can match `^# (BEGIN|END) `), but
`do_resume_blocks_one`'s "kept" lines come from whatever an operator typed
into the crontab during the pause window — genuinely untrusted input. Added
an explicit `cron_body_valid` check on the resume side before rendering.

### Notes and uncertainty — one-user-per-transaction, not fleet-wide

The review's F2 acceptance criteria are stated per-user
("For one user with two managed blocks, one verified crontab write...").
Root and the delegated account remain two separate lock/write transactions,
exactly as before this change. Making a fleet-wide pause spanning both
identities atomic (all-or-nothing across root AND the account) would need a
new primitive — `cron_lock_acquire_multi` already exists for exactly this
shape but nothing today renders two users' crontabs before either write —
and was judged out of scope for this response: the review's acceptance
criteria do not ask for it, and it changes what "one transaction" means at
a level this response should not decide unilaterally. Flagging as a
possible follow-up, not implementing it here.

## F3 — ACCEPTED, IMPLEMENTED

Covered under F1 above (the fix is one change: save the exact placeholder
bytes at pause time, compare byte-exact at resume time).

## F4 — ACCEPTED, IMPLEMENTED

`cron_block_names_present()`'s own comment was wrong and has been corrected:
it returns every name that is *structurally* a managed block, which is not
proof of ownership. A new registry, `PAUSE_KNOWN_BLOCKS="zfs-backup-host
zfs-backup-managed"`, is the single list of names `--pause`'s default block
mode is allowed to touch; a new helper, `pause_known_names()`, filters
`cron_block_names_present()`'s output through it. Both
`do_pause_blocks_one` and `do_resume_blocks_one` now call
`pause_known_names` before iterating. A `certbot`-shaped foreign block
(same `# BEGIN name`/`# END name` grammar, different owner) is left
byte-identical and active by both functions — verified by a new regression
test (see Evidence).

Registration point for a future block: add its name to
`PAUSE_KNOWN_BLOCKS` in `deploy.sh`, nowhere else.

## F5 — ACCEPTED, IMPLEMENTED

### How the shared writer now prevents a later requester from undoing an active pause

The pause marker constants (`CRON_PAUSE_MARKER`, `CRON_PAUSE_BLOCK_MARKER`,
`CRON_PAUSE_LINE_PREFIX`) moved from `deploy.sh` into `lib-cron.sh` — the
single crontab writer every requester (gen-cron.sh, zfs-backup.sh,
deploy.sh itself) already goes through. `deploy.sh` keeps its existing
variable names, now aliased from the canonical ones, so nothing at any of
its own call sites needed to change.

Two new structural recognizers in `lib-cron.sh`:

- `cron_fullcron_paused(curfile)` — true when the WHOLE crontab is exactly
  one line matching the fullcron placeholder's shape.
- `cron_block_paused(curfile, name)` — true when `name`'s block exists and
  its first body line is the block-mode paused header.

And the enforcement point, `cron_paused_guard(curfile, name)`, called from
inside `cron_block_install_impl` and `cron_block_ensure_line_impl` (and
therefore `cron_block_adopt_line`, which calls the same impl) right after
each reads the live crontab and before it renders anything. Both refuse
with a named `CRON_ERR` ("this block is currently paused... run
deploy.sh --resume", or "...paused as a whole (--fullcron)...") rather than
silently building an active body.

Deliberately NOT touched: `cron_replace_all`/`cron_replace_all_impl`. Two
reasons: (1) it is the exact primitive this response's own F2 fix now uses
to COMMIT a pause/resume, so guarding it unconditionally would make
`--pause` refuse itself; a bypass flag on a function only two call sites in
the whole codebase use (deploy.sh's pause code and zfs-backup.sh's
migration rollback) felt like more moving parts than the guard is worth
there. (2) `zfs-backup.sh`'s `migrate-to-account` uses it for a genuinely
different transaction shape — ownership transfer between two crontabs
during a live migration — which the review's F5 acceptance criteria do not
name, and deciding whether a migration should also refuse to proceed against
a paused user looked like a product question, not a technical one. Flagging
this boundary explicitly rather than silently narrowing scope: **a
migration run against a paused user's crontab is not blocked by this
change.**

`cron_block_install`'s only remaining direct callers of the underlying
`*_impl` (`do_pause_blocks_one`/`do_resume_blocks_one`) no longer call it at
all after the F2 refactor — they call `cron_block_render` (which does not
guard, by design — it is the pure rendering primitive both pause and
ordinary writers share) and commit via `cron_replace_all_impl` (also
unguarded, see above). So no bypass parameter was needed anywhere: the
guard lives exactly once, in the two `*_impl` functions ordinary requesters
actually call, and pause/resume's own code never reaches it because it does
not go through those functions any more.

### Forced-interleaving test

Not implemented as a literal concurrent process test (the stub harness is
single-process, like the rest of this suite family) — implemented instead
as the equivalent property the review's own wording allows for
("the requester must fail closed or preserve the paused state"): call the
ordinary entry point (`cron_block_install`, `cron_block_ensure_line`)
directly, synchronously, against an already-paused crontab, and assert
refusal + byte-identical crontab. This is the state a renderer that started
before pause and tried to commit after it would present to `lib-cron.sh` —
the guard cannot distinguish "requester rendered late" from "requester
rendered early, wrote late," because it only ever sees the crontab at write
time, which is the property that makes the guard correct regardless of when
the caller started rendering.

### State cleanup/recovery after a crashed pause/resume

Covered by F1's protocol above for `--fullcron`. For block mode, there is no
separate state file to leak — the paused body IS the crontab, so a crash
mid-`do_pause_blocks_one`/`do_resume_blocks_one` leaves either the original,
unpaused crontab (nothing committed yet) or the fully rendered result
(committed) — the F2 refactor removed every intermediate state a crash
could land in between those two.

## Evidence

Files changed: `lib-cron.sh`, `deploy.sh`, `test/pause/run.sh`.

New/changed regression tests in `test/pause/run.sh` (sections O–V), each
named after the finding it pins:

- **O** (F1): an uncreatable pause-state directory refuses the pause with a
  named diagnostic; live crontab completely untouched.
- **P** (F1): a write that fails read-back (`CRONTAB_MODE=liar`) leaves
  neither the `.saved` nor the new `.placeholder` state file behind.
- **Q** (F3): a placeholder with one line appended during the window is
  refused (byte-exact mismatch, not substring match); the appended line and
  the saved state both survive.
- **R** (F4): a `certbot`-shaped foreign block is left byte-identical and
  active by default-mode pause; the actual managed block still gets paused.
- **S** (F5): an ordinary `cron_block_ensure_line` call against an
  already-paused block is refused, `CRON_ERR` names the pause, crontab
  unchanged.
- **T** (F5): an ordinary `cron_block_install` call against a
  fullcron-paused crontab (no blocks at all, just the placeholder) is also
  refused; crontab still exactly the placeholder.
- **U** (F2, mixed state): one block already paused, one not — the doable
  one still gets paused in the same call; an already-paused block is a
  skip, not a failure, and its own header timestamp is left untouched
  (proof nothing re-rendered it).
- **V** (F2): a forced `mktemp` failure exactly where the SECOND block's own
  rendering would begin (via a `mktemp` shim keyed on
  `MKTEMP_FAIL_AFTER_FILE`, real `mktemp` for every call up to a counted
  threshold) aborts the whole operation; live crontab completely untouched,
  both blocks still active, no pause header anywhere.

Live host verification: **not performed**. This change touches
`cron_block_install`/`cron_block_ensure_line`/`cron_block_adopt_line` —

lines call on every real host, every hour, via the self-update cron job.
The guard added here is inert on every crontab that is not currently in a
paused shape (the overwhelming majority of real runs, since `--pause` has
apparently never been used in production), so the expected live-host risk
is low, but it was not exercised against a real host's actual crontab in
this pass — recommending the next scheduled run against a live host include
a plain `deploy.sh --self-update` + `crontab -l` diff (before/after) on at
least one host as confirmation the guard does not fire against an ordinary,
unpaused crontab.

### Remaining risk

- The one-user-per-transaction boundary noted under F2: a fleet-wide
  (root + delegated account) atomic pause/resume is not implemented; each
  identity's pause is independently atomic, not jointly so.
- `zfs-backup.sh`'s migration path (`cron_replace_all`) is not guarded
  against a paused user, per the F5 scope note above — an explicit,
  intentional boundary, not an oversight, but one the owner may want to
  revisit.
- The pre-`.placeholder`-file compatibility gap noted under F3: a pause
  started before this commit cannot be resumed by `do_resume_one` after
  this commit without a manual `crontab <.saved file>`. Not believed to be
  live anywhere today.
- `cron_write`'s own contract (used directly by `do_pause_one`/
  `do_resume_one`, not through `cron_restore_after_failure`) does not
  itself roll back a partially-accepted write that fails read-back — this
  predates REV-036 and is unchanged by this response; noting it here only
  because F1's new rollback-on-failure logic sits right next to it and
  could be mistaken for covering it. It does not: if `crontab(1)` accepts
  and writes something other than what it was given (the `liar` test mode),
  the live crontab may hold that partial content, and this response's
  rollback only removes the *state* files, not the crontab's own
  garbled content. Out of scope for this review; flagging for a future one
  if it matters.
