# Response to REV-20260731-009

Delivery: direct to `main`, per the owner-approved exception.

## F1 (§2/§3) — rollback protects creation, not update — IMPLEMENTED

### Analysis

The finding is correct, and the example in §2 is exactly what happens. I accept it
without qualification.

`created_helper` / `created_allow` / `created_rule` answered one question: *did
this destination exist before the run?* That is the whole story on a clean host,
and half a transaction on a re-enrolment. Re-running `--join --allow-quiesce`
with a changed dataset list or a newer helper overwrites all three destinations;
`created_*` is 0 for every one of them, so `_grant_rollback()` correctly
concluded there was nothing it had created and did nothing at all.

The stated guarantee — "fully installed, or nothing new" — was accurate about
what it said and wrong about what it implied. "Nothing new" is not the same as
"unchanged", and the second is what an administrator reads it as.

One consequence the review did not name, which makes the defect slightly worse
than described: `install` is not atomic. Coreutils `install` unlinks the
destination and writes a fresh file, so a failure partway through a *replacement*
does not leave the old content behind — it leaves a truncated or partial file at
a path that is either a privileged binary or a sudoers rule. The old code, having
set `created_x=0` on the failing step precisely so it would not remove a file it
had not created, then skipped that destination during rollback. So the failing
step was the one most likely to need repair and the one guaranteed not to get it.

### Implemented change

`install_quiesce_grant()` now takes a rollback copy of every destination that
already exists, after validation and before the first write:

```
/usr/local/sbin/zfs-quiesce-helper
/etc/zfs-quiesce-allow/<account>
/etc/sudoers.d/zfs-quiesce-<account>
```

`cp -p` into a private `mktemp -d`, so owner, mode and timestamps come back with
the content. If a copy cannot be taken the run is refused **before** anything is
replaced, rather than proceeding into a state it could not undo.

Two flags per destination now, where there was one:

- `pre_*` — it existed before the run, so rollback must **restore** it;
- `did_*` — a write was **attempted**, so rollback must act on it.

`did_*` is deliberately set *before* each `install`, not after. That is the fix
for the truncation case above: what decides whether a destination needs repair is
"attempted", not "succeeded". Destinations the run never reached are left alone,
so a failure at the first step really does leave the other two untouched rather
than rewritten with identical bytes.

Restoring is atomic in a way the original install is not: the copy lands beside
the destination and is renamed over it, so a rollback that is itself interrupted
cannot leave a truncated privileged file behind.

Order of rollback is the reverse of install, and the sudoers rule goes first
deliberately: it is the only one of the three that grants anything, so until it is
removed or back to its previous content the account can still reach the helper.

The shared helper (§2, last paragraph) is handled explicitly:

- if it existed before the run it is **restored to its previous version**, even
  though the failure was about a single account — the other peers on the host
  never asked for an upgrade;
- if this run installed it and nobody ended up with a grant, it is removed;
- if this run installed it and another account does hold a grant, it stays and
  the operator is told so — removing it would break relationships this run never
  touched.

§3's last two bullets:

- **validate the restored sudoers state** — when the rule was touched, the
  rollback re-runs `visudo -c` over the whole sudoers state and warns loudly if it
  no longer parses. A broken file there breaks `sudo` for every user on the host,
  root included, so the result of the rollback is checked rather than assumed.
- **report which of the two happened** — the two outcomes now read differently:

```
rolled back to the previous grant, restored: <paths>
rolled back, removed what this run created: <paths>
COULD NOT RESTORE: <paths> -- this host is left holding content from a FAILED
run. Put it right by hand before anything relies on the grant.
```

The third exists because a restore can itself fail, and silently reporting a
rollback that did not happen would be worse than the defect being fixed.

### On §4.4, idempotency

I chose the "explicitly bounded replacement" option rather than content
comparison. An update replaces all three destinations unconditionally: the helper
has to be able to move forward with the repository, and a whitelist rewritten
from the same dataset list is a no-op in content even when the bytes are
rewritten. What is bounded — and now asserted by a whole-tree diff — is the SET of
files touched: these three, and nothing else. The test proves a rerun with
identical input changes no content anywhere in the tree.

## F2 (§5) — the `sudo` package is left behind, silently — IMPLEMENTED

Agreed on both halves: the package is not removed, and the silence was the
problem. Automatic package removal is riskier than leaving a standard dependency
installed, particularly since `sudo` may have been pulled in as a dependency of
something else between the two runs.

When the run installs `sudo` and then fails for any later reason, the failure now
carries:

> the grant was not created. The 'sudo' package was installed by this run and has
> been left in place.

Two dependency-stage exits that returned early without saying anything now route
through the rollback so the notice is not lost.

## Remaining risk

The rollback is proven in a sandbox where `install` and `visudo` are stubs. What
is NOT proven by any of the above:

- a real `install` failure on a real host (the sandbox fails it synthetically);
- `cp -p` preserving ownership across the copy/restore as root on a real host —
  it cannot fail as root, but it is not exercised as root by these tests;
- a **crash** between two steps. The rollback runs on the failure paths of
  `install_quiesce_grant`, not from an EXIT trap, so a `kill -9` of deploy.sh
  mid-install still leaves a mixed state. Making that survivable needs the staged
  rename-commit design §3 mentions as the cleaner alternative, and I did not go
  there for a reason worth stating: the rename-commit protects the same window
  this fix protects, and only differs on the crash case, which is unreachable by
  the workflow that produced the finding (a failed install, not a killed deploy).
  If you want the crash case covered, say so and I will build it as its own
  change rather than fold it in here.

`--allow-quiesce` remains not enabled by default, per §Decision.
