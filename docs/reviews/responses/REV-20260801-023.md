## Remaining fail-closed regression — ACCEPTED, IMPLEMENTED

### Analysis

Accepted, and the review is right about more than the one branch it names.

`55d33a2` fixed the probe — the local path stopped reading "I could not ask" as
"the guest is not running". Having fixed the probe I stopped, and the reason is
worth stating plainly because it is a repeatable mistake: I treated the
already-frozen branch as *pre-existing behaviour I had not changed* rather than
as *the same defect wearing a different hat*. It logs at level 0, it says
something true, and it returns 0 — which is exactly the shape of the bug I had
just spent an hour fixing four lines above it.

The review's argument settles it. This run does not own that freeze. It cannot
say what application boundary the freeze captured, or when. It deliberately will
not thaw it. There is nothing there that constitutes a successful quiesce *of
this run*, so reporting one is a claim the code cannot support.

Going through the function with that rule rather than that branch, five places
degraded, not one:

| branch | old behaviour |
|---|---|
| `frozen=yes` | log level 0, return 0, snapshot proceeds |
| `frozen=unknown` on a running VM | fell through and froze anyway |
| `fsfreeze-freeze` failed | "snapshot will be crash-consistent", proceeds |
| `pct exec sync` failed | same |
| mode fits no guest of that kind | log level 1, proceeds |

### Implemented change

All five refuse with exit 3, before any snapshot is taken.

The last row is beyond the letter of this review, which scopes itself to running
QEMU guests. `quiesce=sync` on a VM and `quiesce=agent` on a container freeze
nothing at all, so under an explicit `-q` they are the same silent downgrade.
Fixing three of five and leaving two would have missed the point of the
exercise. Flagged here rather than buried, because it is a behaviour change the
review did not ask for: a config carrying an explicitly mismatched mode used to
back up with a warning and now fails. Say so if that is too wide.

**"Nothing to quiesce" deliberately stays a success**: a dataset owning no guest,
a guest that does not exist on this node, a guest that is switched off. There the
snapshot is already as consistent as it can possibly be, and failing the backup
would be failing it for succeeding. Both halves are tested, because a fix that
turned every stopped VM into a failed nightly job would be a worse bug than the
one being fixed.

**Thaw failure** (the review's fifth required behaviour): `quiesce_thaw_all` now
returns non-zero, keeps the guest on `QUIESCE_FROZEN` instead of emptying the
list, and retries once before giving up — the usual cause of a first failure is
an agent still busy with the freeze it just performed. Keeping the id *is* the
retry state: the EXIT trap calls the function again after the explicit mid-run
call. `snapsend.sh` turns that into `exit 3`. The snapshots already taken are
kept: they were made inside the freeze window and are valid; what failed is the
release.

### The stale comment

Removed, and it was not stale — the code still followed it:


The first two clauses are still true and are still implemented. "An unreachable

### A defect in the regression test, again worth recording

The first version of the `refuse` section passed nothing and failed everything
for one reason: the helper is reached as `sudo -n <helper>`, and that PATH had no
`sudo` stub. Every helper call failed, so every case reached the *earlier*
refusal ("could not determine the state") — including the cases that were
supposed to prove a freeze had been *attempted*.

Worth recording because the failure was legible only by accident: had the
assertions been "exit code is 3" alone, all of them would have passed, against a
code path none of them was testing. The two checks that read a **trace** rather
than an exit code are what exposed it, which is the argument for having them.

## Product implication — AGREED

Agreed without qualification, and it is the sharper version of what the live run
already demonstrated. The defect in `55d33a2` was found by *reading the log*, not
by the exit code, which is precisely the thing an administrator must never have
to do. After `244ec0d` the contract on the local path is binary: quiesce
delivered what `-q` promised for this run, or the run exits non-zero and the
cron line's `notify-fail.sh` fires.

One thing that contract does **not** yet cover, found in the same live run and
recorded in `docs/PROJECT_STATUS.md` §3 rather than fixed here: the freeze window
can outlive the freeze. VM 106 is `ostype: win10`, VSS lapses a freeze after
~10 s, and the guests are all frozen before any snapshot is taken — one measured
run held it 18 s while `pct exec 101 -- sync` ran. Every branch above reports
success in that case, because the freeze *did* take; it simply was not still in
force at `zfs snapshot`. That is a third instance of the same family and it needs
its own change (ordering, plus re-reading `fsfreeze-status` immediately before
the snapshot), not a rider on this one.
