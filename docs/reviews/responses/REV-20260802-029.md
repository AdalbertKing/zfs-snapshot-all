### What was wrong

ZFS is atomic within a pool and cannot be atomic across pools, so a job spanning
two pools is two separate `zfs snapshot` commands. The check ran once, before
the loop. It certified a boundary that only the first command actually had.

My earlier defence of that — the loop is sub-second, and a probe per pool costs
IPC inside the window — mistook a measurement for a property. "Usually fast" is
an observation about the hosts I measured, not a bound the code enforces. A
busy, resilvering or very large pool makes the first snapshot slow and nothing
stops it. The code comment even asserted the unproven part out loud: *"every
guest stays frozen until the last group is done"*.

### Implemented

Before **each** pool, on both paths:

- every VM owned by this run must still report `frozen=yes`;
- the elapsed window is recomputed from the first successful freeze;
- either failing refuses before that pool is touched;
- the thaw is preserved on the refusal path — `on_exit` remotely, an explicit
  `quiesce_thaw_all` before `exit 3` locally.

Pools already snapshotted keep their snapshots. They were taken while the freeze
demonstrably held, and destroying good backups because a later pool failed is
the same error mirrored.

On "factor one shared invariant and prove both callers use it": the remote
script is a constant streamed to another host and deliberately re-implements
rather than sources this library (the peer may be on a different revision, and a
delegated account cannot read `/root`). So there is no way to share the code.
The remote check is now a **function** (`boundary_ok`) with a single definition
and one call site per pool, which is as close as that constraint allows, and the
suite asserts the invariant on both paths rather than on one.

## UX implication — AGREED

No per-pool timing or ordering is exposed. `QUIESCE_MAX_WINDOW` remains the one
knob and it is documented as an expert override backed by measurement, not a
deployment choice. A quiesced job either proves the boundary for every snapshot
it creates or fails closed.

## Separate documentation defect — ACCEPTED, FIXED

The remediation text still said the whitelist is *PRZEPISYWANA* (rewritten) from
the printed list. That was true of `--allow-quiesce`, which the command no longer
names, and it is exactly the sentence that would make an operator believe
unrelated grants are at risk — the opposite of what `--add-quiesce` guarantees.

It now says the command adds the required datasets and **preserves** what is
already there, including entries from other configs, an older deployment or a
peer relationship, and names the difference from `--allow-quiesce` explicitly.
Pinned by a test that fails if the old word comes back.
