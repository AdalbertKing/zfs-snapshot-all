- Reviewed production range: `0a14a6653d9a392657a35a4f6a4ea205d69a3910..16e2014039d2d9cf77883c35a271be185a435143`
- Status: **OPEN**
- Response required at: `docs/reviews/responses/REV-20260802-034.md`

## Scope

The owner asked for review after the crontab refactor that introduced `lib-cron.sh` and moved the ordinary `deploy.sh`, `gen-cron.sh`, and `zfs-backup.sh` write paths toward one shared implementation.

The direction is correct: read-back verification, fail-closed handling of an unreadable crontab, named blocks, adoption of loose legacy lines, and preserving hand-tuned schedules are all material improvements. The findings below are not an argument to restore the old writers. They identify the remaining places where the new abstraction does not yet enforce the property its header promises.

This review does not treat the deliberately independent, rollback-surviving `update-control.sh` emergency path as an ordinary requester. Claude should nevertheless state explicitly in the response which emergency/bootstrap write paths remain outside `lib-cron.sh` and why each exception is required.

## F1 — `migrate-to-account` replaces the shared host block and drops `deploy.sh` jobs

- Severity: **P1**
- Blocking: **yes**
- Status: **OPEN**
- Affected: `zfs-backup.sh`, `set_host_block()`, `cmd_migrate_to_account()`; `deploy.sh` host-job provisioning

### Evidence

`deploy.sh` and `zfs-backup.sh` now intentionally use the same block name:

```text
zfs-backup-host
```

`deploy.sh` places at least these independently requested lines there:

- root auto-update;
- root capacity check;
- delegated account auto-pull.

`cmd_migrate_to_account()` builds `hostlines` only from job lines dropped from the old `zfs-backup-managed` block. The only currently recognised dropped host-level job is `alert-digest.sh`.

It then calls:

```bash
set_host_block "$rootnew" "$hostlines"
```

`set_host_block()` passes `hostlines` as the complete replacement body to `cron_block_render()`. It does not read and merge the current `zfs-backup-host` body.

Therefore the normal current shape:

```text
# BEGIN zfs-backup-host
auto-update
capacity-check
# END zfs-backup-host

# BEGIN zfs-backup-managed
backup jobs
alert-digest
# END zfs-backup-managed
```

is transformed by `migrate-to-account` into:

```text
# BEGIN zfs-backup-host
alert-digest
# END zfs-backup-host
```

The auto-update and capacity lines disappear.

The existing `test/zfsbackup` host-block case does not model the deployed shape: it leaves `check-pool-capacity` loose outside the block, so wholesale replacement appears to preserve it.

### Failure mode

A successful ownership migration can silently stop:

- automatic code updates and their rollback-aware control path;
- pool/refquota capacity warning.

The collector jobs may migrate successfully, making the operation look healthy while two host-level controls have been removed from cron.

### Required outcome

A requester must not replace content owned by another requester.

Acceptable designs include:

1. separate named blocks for separately owned job families; or
2. one shared host block only if every requester uses ownership-aware line operations and no requester replaces the whole body from a partial inventory.

The chosen design must define who owns `alert-digest`, updater, capacity, and account auto-pull, including teardown and migration.

### Acceptance criteria

- [ ] Starting from the exact deployed shape above, `migrate-to-account` preserves updater and capacity lines byte-for-byte and exactly once.
- [ ] `alert-digest` reaches its intended final owner/location exactly once.
- [ ] Repeating the migration-related render is idempotent.
- [ ] A requester cannot remove another requester's line merely because its own desired list omits it.
- [ ] The test fails against the reviewed code.

### Required verification

- automated: extend `test/zfsbackup/run.sh` with the current managed host-block shape, not a loose-line approximation;
- manual: show before/after `crontab -l` from a throwaway or controlled host containing updater, capacity, digest, and at least one collector job.

## F2 — Shared code without a shared lock still loses concurrent updates

- Severity: **P1**
- Blocking: **yes**
- Status: **OPEN**
- Affected: `lib-cron.sh` mutating entry points; `gen-cron.sh --install`; `deploy.sh`

### Evidence

The mutating library operations follow a read-modify-write sequence:

```text
cron_read
→ cron_block_render / line adoption
→ cron_write
→ read-back verification
```

No shared lock is acquired by `lib-cron.sh` across that sequence.

`gen-cron.sh` retains `GEN_CRON_LOCKFILE`, but that lock is private to a `gen-cron.sh --install` run. `deploy.sh` does not take it when it calls `cron_block_ensure_line()` or `cron_block_adopt_line()`.

A deterministic interleaving is therefore possible:

```text
gen-cron reads crontab A
deploy reads crontab A
gen-cron writes A + new managed block
deploy writes A + new host block
```

Both writers preserved everything outside their target block from the stale copy they read. The last write still removes the first writer's change. Read-back proves only that each individual write landed as requested; it cannot detect that a concurrent update was overwritten.

There is no concurrent-writer case in `test/cron/run.sh`.

### Failure mode

A deployment/audit run overlapping a config activation can remove either:

- the production backup block; or
- the updater/capacity/host block.

This is the same lost-update class the single-writer refactor is intended to eliminate.

### Required outcome

All ordinary mutations of one user's crontab must be serialized by the shared writer itself, not by requester-specific locks.

The lock must cover the complete operation, including:

- initial read;
- validation and render;
- write and read-back;
- any restore decision;
- the preliminary read performed by adoption.

It should be keyed by target user. Multi-user transactions must acquire locks in a deterministic order or otherwise prove they cannot deadlock.

### Acceptance criteria

- [ ] Every public mutating entry point in `lib-cron.sh` obtains the same per-user lock.
- [ ] Requesters do not need to remember a separate lock to be safe.
- [ ] Two concurrent updates to different named blocks both survive.
- [ ] Two concurrent updates to the same owned object have an explicit, tested result rather than last-writer-wins by accident.
- [ ] Lock failure/contention produces a clear diagnostic and no write.
- [ ] The concurrency regression test fails against the reviewed code.

### Required verification

- automated: a deterministic barrier-controlled test with two processes modifying different blocks of the same stubbed crontab;
- automated: lock cleanup and failure-path tests;
- manual: none required if the test controls the interleaving rather than relying on timing.

## F3 — `migrate-to-account` still writes and restores crontabs outside the sole writer

- Severity: **P1**
- Blocking: **yes**
- Status: **OPEN**
- Affected: `zfs-backup.sh`, `cmd_migrate_to_account()`, `_mta_rollback()`

### Evidence

The commit path still performs a direct root crontab write:

```bash
if ! crontab "$rootnew"; then
    ...
fi
```

The rollback path still performs direct writes for both owners:

```bash
crontab "$rootcron"
crontab -u "$acct" "$acctcron"
```

Only the account-side forward install goes through `gen-cron.sh --install` and therefore `lib-cron.sh`.

These direct paths bypass:

- the shared write/read-back verification;
- shared marker validation;
- the required shared serialization from F2;
- the library's distinction between a refused write, a changed crontab, and a failed verified restore.

This also makes the repository's statement “the one way this project writes a crontab” false on an ordinary product workflow, not merely on the deliberately independent emergency updater.

### Failure mode

A direct write may return success without installing the requested content. The migration then proceeds to the second owner with an incorrect assumption about the first, or a rollback reports success without proving the old jobs are back. The result can be duplicate ownership, no owner, or a mixed state.

### Required outcome

Every forward and rollback crontab mutation in `migrate-to-account` must be performed by the shared writer under the transaction's ownership rules.

If the transaction needs a whole-crontab primitive, it must be an explicit library operation with read-back and locking, not a raw `crontab` invocation hidden in the requester. Prefer block-level operations where they can express the intended ownership transition.

### Acceptance criteria

- [ ] No ordinary `migrate-to-account` forward or rollback path invokes `crontab` directly.
- [ ] Both owners' final crontabs are read back and compared with the intended state.
- [ ] A lying `crontab(1)` on the root write is detected before the account write is accepted as a completed migration.
- [ ] A lying/refusing restore produces the correct loud mixed-state result and retains the prior-content artifact.
- [ ] Tests fail against the reviewed direct-write implementation.

### Required verification

- automated: root-forward liar, account-forward failure, root-restore liar, account-restore liar;
- manual: controlled migration with exact before/after block counts for both users.

## F4 — Marker validation is local to the target name and can erase a foreign block

- Severity: **P1**
- Blocking: **yes**
- Status: **OPEN**
- Affected: `lib-cron.sh`, `cron_block_locate()`, `cron_block_render()`

### Evidence

`cron_block_locate()` counts and orders only the `BEGIN`/`END` markers for the requested block name. It does not validate the global marker structure.

For example:

```text
# BEGIN block-A
line A
# BEGIN block-B
line B
# END block-B
# END block-A
```

passes the target-name checks for `block-A`: one A begin, one A end, in order. Replacing A deletes the complete B block because B lies inside A's numeric extent.

An interleaved structure can similarly leave an orphan marker:

```text
# BEGIN block-A
# BEGIN block-B
# END block-A
# END block-B
```

The library header promises malformed markers are refused rather than repaired, and the ownership guarantee depends on one requester being unable to touch another requester's block. That guarantee currently holds only for a well-formed, non-overlapping marker layout.

### Failure mode

A manually damaged, partially written, or historically malformed crontab can cause the next otherwise unrelated block update to delete or orphan another managed block. The write reports success because the produced file is internally consistent for the target name alone.

### Required outcome

Before any mutation, validate the complete managed-marker structure relevant to all named blocks:

- every begin has one matching end of the same name;
- no duplicate block name;
- no nesting or overlap, unless nesting is explicitly designed and ownership-safe;
- no orphan marker.

The conservative expected policy is to refuse all nesting/overlap and require manual repair.

### Acceptance criteria

- [ ] A foreign block nested inside the target block is refused with no write.
- [ ] Interleaved markers are refused with no write.
- [ ] An orphan marker for a foreign name is refused before changing the target block.
- [ ] A normal crontab with multiple adjacent named blocks remains accepted.
- [ ] Tests fail against the reviewed target-local parser.

### Required verification

- automated: nested, interleaved, foreign orphan, duplicate foreign name, and valid adjacent-block cases;
- manual: none required.
